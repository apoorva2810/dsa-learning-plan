One-of-a-kind objects: Singleton

An industrial chocolate boiler must exist exactly once, and a program that creates it twice floods the factory floor. The chapter builds the classic Singleton (one slot, one accessor, a constructor nobody else calls), breaks it with two threads, repairs it three ways, and then asks the uncomfortable question: in Python, and in a codebase with tests, do you want one at all?

After this chapter you can
  • Tell the ChocolateBoiler story and say exactly what a second instance breaks
  • Draw the classic Singleton (class-level slot, guarded constructor, static accessor) and explain lazy vs eager creation
  • Walk through the lazy-initialisation race step by step and name the three fixes
  • Write a singleton in Python three ways (module-level instance, __new__, cached accessor) and know what each gets wrong
  • Argue when Singleton is the wrong tool and what to use instead

The ChocolateBoiler story

▶ Video lesson: The chocolate boiler: one instance, and the race that makes two 4:58 · 9 scenes · narrated, pause anytime and explore

Choc-O-Holic runs an industrial chocolate boiler. It is filled with milk and chocolate, boiled, and drained into the moulding line. The control software has one class for it, ChocolateBoiler, with two flags (empty, boiled) and three operations that check them: you may only fill an empty boiler, only boil a full one that is not yet boiled, and only drain a boiled one. Get the order wrong and 500 gallons go over the floor.

The guards are correct. The bug is that the program ends up with two boilers. The filling station's code did ChocolateBoiler(); so did the controller's. Each object has its own empty flag, each flag says True, and both happily fill(). The real boiler, the steel one in the factory, is told to fill twice.

Some objects must exist exactly once: a hardware controller, a thread pool, a registry, a cache, the object holding the configuration loaded at start-up. Create a second one and you do not get a copy, you get two things that both believe they are the thing. This chapter is about guaranteeing one, and about the price of that guarantee.

Two parts of the program depend on the boiler. The underlined members are class-level (static): the slot that holds the one object and the accessor that hands it out.

Why not just a global?

A global variable is the obvious shortcut and the worst version of it: anyone can reassign it, nothing stops a second ChocolateBoiler(), and the object exists from start-up whether or not this run ever uses it. Singleton makes the class responsible for its own count: the class owns the slot, the class hands out the object, and building one from outside is blocked or at least frowned upon.

The Singleton pattern, named

Singleton ensures a class has only one instance and provides a global point of access to it.

Three parts, in any language:

  1. A class-level slot for the one object (_instance), empty until the first request.
  2. A constructor callers are kept away from. Java makes it private. Python has no private, so the constructor either raises once an instance exists, or the team agrees that ChocolateBoiler() is not how you get a boiler.
  3. A static accessor, get_instance(), that creates the object on the first call and returns the same one ever after. It is the only door.

Map it to the story: the class is ChocolateBoiler, the slot holds the one boiler, and both the filling station and the controller go through get_instance(), so they cannot help sharing it.

Where you have already seen it

  • logging.getLogger("app.db"): one logger object per name, kept in a registry; every call with that name gets the same object back.
  • Python modules: sys.modules guarantees a module body runs once per process, which is why a module is the idiomatic Python singleton (two sections on).
  • None, True, False and Ellipsis: singletons the language itself guarantees, which is why is None is the right comparison.
  • The random module's top-level functions all drive one hidden random.Random() instance.
  • django.conf.settings: one lazily built settings object shared by the whole process.
  • Spring's default bean scope is called singleton: one instance per container, handed out by injection rather than through a static accessor.

The boiler code, before and after

A plain class: anyone can make one

Two call sites, two boilers, two sets of flags. The guards are correct and useless.

class ChocolateBoiler:
    def __init__(self):
        self.empty = True
        self.boiled = False

    def fill(self):
        if self.empty:                        # only an empty boiler may be filled
            self.empty = False
            self.boiled = False

    def boil(self):
        if not self.empty and not self.boiled:
            self.boiled = True

    def drain(self):
        if not self.empty and self.boiled:    # only boiled mixture leaves the boiler
            self.empty = True

# Two parts of the program each make "the" boiler:
station = ChocolateBoiler()
controller = ChocolateBoiler()
station.fill()
controller.fill()      # a different object with its own empty flag: the real boiler is filled twice

Singleton: the class owns its count

One slot, one accessor, a constructor that refuses a second call. The two call sites cannot help sharing the object.

class ChocolateBoiler:
    _instance = None                          # the one slot, on the class, empty until first use

    def __init__(self):
        if ChocolateBoiler._instance is not None:
            raise RuntimeError("one boiler only: use ChocolateBoiler.get_instance()")
        self.empty = True
        self.boiled = False

    @classmethod
    def get_instance(cls):                    # the only door
        if cls._instance is None:             # lazy: nothing exists until somebody asks
            cls._instance = cls()
        return cls._instance

    def fill(self):
        if self.empty:
            self.empty = False
            self.boiled = False

    def boil(self):
        if not self.empty and not self.boiled:
            self.boiled = True

    def drain(self):
        if not self.empty and self.boiled:
            self.empty = True

station = ChocolateBoiler.get_instance()
controller = ChocolateBoiler.get_instance()
assert station is controller                 # same object, same flags
station.fill()
controller.fill()                             # ignored: the one boiler already knows it is full

The multithreading trap

get_instance() as written is check-then-act: read the slot, and if it is empty, create and store. Those are separate steps, and the operating system can pause a thread between any two of them. Two threads that call during the same millisecond can both see the empty slot, and both create. The second store overwrites the first, so the program now has two boilers and no error message: the Singleton quietly stopped being one.

In the book this happens when the boiler controller grows a second thread. In a web service it happens on the first two requests after start-up, which is exactly when nobody is watching. Step through it, then switch the input to the locked version.

Two threads race a lazy get_instance()

Thread A and thread B call the accessor in the same tick. Watch the class slot: without a lock it is written twice; with a lock the second thread never sees it empty.

Three ways to close the window

  1. Lock the whole accessor. with cls._lock: around the check and the store (the second input above). Simple and correct; the cost is a lock acquisition on every call, including the millions made after the object exists. Fine when get_instance() is not on a hot path, which is most of the time.
  2. Create eagerly. Build the instance when the module is imported or the program starts. There is no check, so there is no race. The price is paying for the object even if this run never uses it, and losing the chance to pass construction arguments later.
  3. Double-checked locking. Check without the lock; only if the slot is empty, take the lock and check again before creating. The steady state costs one plain read. In Java this shape needed a volatile field so that no thread could observe a half-built object; in CPython the object is fully built before the reference is stored, so a reader sees None or a finished boiler, never something in between.

    S([get_instance called]) --> C1{slot is None?}
    C1 -->|no| R[return the instance]
    C1 -->|yes| L[acquire the lock]
    L --> C2{still None?}
    C2 -->|no| U[release the lock]
    C2 -->|yes| N[create the instance<br/>store it in the slot]
    N --> U
    U --> R
Double-checked locking. The left branch is the fast path every call takes once the object exists; the lock and the second check are only paid by the callers who arrive while the slot is empty.

Double-checked locking in Python

import threading

class ChocolateBoiler:
    _instance = None
    _lock = threading.Lock()

    @classmethod
    def get_instance(cls):
        if cls._instance is None:                 # 1. fast path: a plain read, no lock
            with cls._lock:                       # 2. slow path: one thread at a time
                if cls._instance is None:         # 3. check again: the race may already be lost
                    cls._instance = cls()
        return cls._instance
Three numbered lines: fast read, lock, second check. Drop the second check and you are back to the race; drop the first and you are back to locking on every call.

Eager vs lazy

Eager: the instance is built when the class or module is loaded. Lazy: it is built on the first get_instance(). The book introduces lazy as the default and eager as the fix for threading; in practice the choice is about cost and ordering at least as much as about threads.

Choose eager when the object is cheap, always needed, and must be ready before anything else runs: a logger, a settings object, a metrics registry. Choose lazy when construction is expensive or can fail (opening a database connection, loading a 2 GB model), when only some code paths need it, or when it needs information that is not known at import time. Lazy buys you the race. Eager buys you import-time side effects, which are their own trap: import boiler should not open a socket.

The accessor, three ways

Built at import. No check, no race, no way to defer or parameterise creation.

class ChocolateBoiler:
    _instance = None

    def __init__(self):
        self.empty = True
        self.boiled = False

    @classmethod
    def get_instance(cls):
        return cls._instance                      # no check, so no race

ChocolateBoiler._instance = ChocolateBoiler()     # built when this module is imported, used or not

Built on first use. Cheap when unused; racy when two threads arrive first together.

class ChocolateBoiler:
    _instance = None

    def __init__(self):
        self.empty = True
        self.boiled = False

    @classmethod
    def get_instance(cls):
        if cls._instance is None:                 # check...
            cls._instance = cls()                 # ...then act: a thread switch here makes two
        return cls._instance

Built on first use, one thread at a time. Correct; every call pays for the lock.

import threading

class ChocolateBoiler:
    _instance = None
    _lock = threading.Lock()

    def __init__(self):
        self.empty = True
        self.boiled = False

    @classmethod
    def get_instance(cls):
        with cls._lock:                           # every call pays for the lock...
            if cls._instance is None:             # ...so check and store are one step
                cls._instance = cls()
            return cls._instance

Singleton in Python

▶ Video lesson: Singleton in Python, and when not to use it 2:56 · 6 scenes · narrated, pause anytime and explore

Python already has most of the machinery, so the class-with-a-static-accessor shape is rarely the best fit. Three idioms, from most to least common:

  • A module-level instance. A module body runs once per process, and import returns the module object cached in sys.modules, so boiler = ChocolateBoiler() at the top of boiler.py is one object for everyone who imports it. The import lock means two threads importing at once still run the body once. This is what most Python code does when it wants "one of these".
  • Override __new__. ChocolateBoiler() keeps working at the call site, but the class returns the stored instance instead of a new one. The catch: __init__ still runs on every call, because the returned object is an instance of the class, so it must be guarded or it resets the state each time.
  • A cached accessor. @functools.cache on a get_boiler() function stores the first result and returns it forever. Lazy, one decorator, and tests can call get_boiler.cache_clear(). The documentation is explicit that the cache is thread-safe for its own data but the wrapped function may run more than once if a second thread calls before the first result is stored; add a lock, or create eagerly, if that matters.

Singleton in Python, three ways

The idiom. The import system is the accessor and the lock.

# boiler.py
# A module body runs once per process; later imports return the object cached in sys.modules.
# The import lock means two threads importing at the same time still run this body once.

class ChocolateBoiler:
    def __init__(self):
        self.empty = True
        self.boiled = False

    def fill(self):
        if self.empty:
            self.empty = False
            self.boiled = False

boiler = ChocolateBoiler()        # the singleton: one object for everyone who imports it

# station.py
#   from boiler import boiler
#   boiler.fill()

When callers must keep writing ChocolateBoiler(). Guard __init__.

class ChocolateBoiler:
    _instance = None

    def __new__(cls, *args, **kwargs):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance                      # the same object every time

    def __init__(self):
        # __init__ runs on EVERY ChocolateBoiler() call, because __new__ returned an
        # instance of this class. Guard it, or the state resets with each call.
        if not hasattr(self, "empty"):
            self.empty = True
            self.boiled = False

a = ChocolateBoiler()
b = ChocolateBoiler()
assert a is b
a.empty = False                                   # state set through a...
assert b.empty is False                           # ...is visible through b: one object

Lazy and resettable in tests; not a lock. Read the thread caveat.

from functools import cache

class ChocolateBoiler:
    def __init__(self):
        self.empty = True
        self.boiled = False

@cache                                  # first call's result is stored and returned forever after
def get_boiler() -> ChocolateBoiler:
    return ChocolateBoiler()

assert get_boiler() is get_boiler()
# tests: get_boiler.cache_clear() gives the next test a fresh boiler
# threads: the docs say the wrapped function may run twice if a second thread calls
#          before the first result is cached; wrap it in a lock or create eagerly

Python note

The book's shape (class slot plus get_instance()) is legal Python, but it fights the language. A module-level instance is the idiom; __new__ is for when callers must keep writing Cls(); functools.cache is for lazily creating something expensive. Whatever shape you pick, the better design is usually still to build the object once in main() and pass it to whoever needs it.

Why Singleton is often an anti-pattern

Singleton is the one pattern in the book its own authors warn you about, and most style guides list it under things to avoid. The guarantee is real; the problems are what the guarantee hides.

  • Hidden global state. Database.get_instance() can be called from anywhere, so nothing in a function's signature tells you it touches the database. The dependency graph of the program becomes invisible.
  • Tests that share state. Every test gets the same instance. A test that leaves the boiler full makes the next test fail, but only when they run in that order. Swapping in a fake means patching a class attribute and remembering to put it back.
  • Coupling to a concrete class. The accessor names the class, so there is no interface to program to, and no way to have a test database and a production one in the same process, or two tenants, or two configurations.
  • One per process is not one per system. A web app with 8 worker processes has 8 "singletons" with 8 different states. The guarantee you actually wanted (one counter, one cache, one boiler) needs a database or a shared service, not a class-level slot.
  • A lifetime you cannot control. Created on first use, destroyed never: no clean shutdown, no re-creation with new settings.

The honest alternative is usually simpler. There is exactly one database object because main() created exactly one and handed it to the services that need it. Same count, nothing hidden, and every test can build its own. That is dependency injection in its plainest form, and it is what frameworks such as Spring or FastAPI's Depends automate for you.

The same 'one database', two ways to get it

Singleton reached from inside

The dependency is invisible in the signature and shared by every test.

class OrderService:
    def place(self, order):
        db = Database.get_instance()          # reached from inside: a hidden dependency
        db.save(order)
        Logger.get_instance().info("placed")

# Nothing in OrderService's signature says it touches a database.
# A test must patch Database._instance and remember to put it back.

One instance, passed in

Still one database in production, because main() made one. Tests build their own; nothing to patch.

class OrderService:
    def __init__(self, db, log):              # dependencies arrive through the front door
        self.db = db
        self.log = log

    def place(self, order):
        self.db.save(order)
        self.log.info("placed")

# main() builds exactly one database and one logger and hands them out:
#   service = OrderService(Database(), Logger())
# a test builds its own:
#   service = OrderService(FakeDatabase(), FakeLogger())

The failure catalogue

Two processes, two singletons

A _instance slot is per interpreter. Under gunicorn with 8 workers, or on 3 machines behind a load balancer, a Singleton counter counts 8 or 24 different things. Shared state belongs in a shared store (a database, Redis), not in a class attribute.

pickle and copy do not go through the door

pickle.loads and copy.copy rebuild objects with cls.__new__(cls) and never call __init__ or get_instance(). With the classic shape you get a second object. With the __new__ shape you get the same object, but its state is then overwritten by whatever was pickled. Either way the count is no longer the class's decision.

Subclassing a singleton

Sub.get_instance() reads cls._instance: if the base already has one it returns a base-class object from a subclass accessor; if not, it creates a Sub and stores it on Sub, and a later Base.get_instance() creates another. Wanting a second kind of the thing is a sign the design wanted a factory or injection, not a singleton.

Tests that pass alone and fail together

Order-dependent failures are the signature of shared mutable state. The usual repair is a _reset_for_tests() class method, which is a method that exists only because the production design has no other way to make a fresh object. Pass the object in instead and the method is not needed.

flowchart TD
    A{Must there be exactly one,<br/>or is one just convenient?} -->|convenient| B[Build one in main<br/>and pass it in]
    A -->|exactly one, enforced| C{Shared across processes<br/>or machines?}

    C -->|no, this process only| E{Must creation be deferred<br/>or parameterised?}
    E -->|no| F[Module-level instance<br/>eager, import does the rest]
    E -->|yes| G[Lazy accessor with a lock<br/>or functools.cache plus a lock]
Most paths end somewhere other than a Singleton class. Only the bottom-right box needs the book's machinery, and it still wants a lock.

Common mistakes

  • Singleton because one is convenient. The pattern is for must not be two. If one is merely enough, build one in main() and pass it in; you keep the count and lose the hiding.
  • __new__ without guarding __init__. ChocolateBoiler() returns the stored object and then re-runs __init__ on it, wiping its state. Every call to the constructor resets the boiler to empty.
  • A lazy accessor with no lock in a threaded program. It works in every test and fails on the first busy start-up. If you cannot prove the first call is single-threaded, lock it or create eagerly.
  • Believing one per process is one per system. Counters, caches and rate limiters in a Singleton are per worker.
  • Config in a Singleton that tests need to vary. Every test that wants a different setting patches a class attribute. Pass a settings object instead.
  • Calling a module of functions a Singleton. A module with no state is just a namespace; the pattern is about one object with state. The same goes for the Borg or Monostate idiom (many objects sharing one __dict__), which is shared state without a single instance.

How to say it in an interview

Say: 'Singleton guarantees one instance and one global access point: a class-level slot plus a get_instance() that creates lazily. The classic trap is the lazy check: two threads can both see an empty slot and both create, so you either create eagerly, lock the accessor, or double-check inside the lock. In Python I would normally use a module-level instance, which the import system already makes unique. And I would still prefer to pass the object in, because a Singleton hides a dependency and makes tests order-dependent.' Then draw the slot, the accessor and the two-thread race.
