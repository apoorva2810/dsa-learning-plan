Well-managed collections: Iterator and Composite

Two restaurants merge and their menus use different containers, so the waitress ends up with one loop per container in every method. Giving each collection an iterator fixes that and teaches the single responsibility principle. Then menus start containing menus, the data becomes a tree, and the Composite pattern lets one call print the whole thing. Python already ships the Iterator pattern as the for loop protocol and generators; this chapter shows where the book's shape maps onto it.

After this chapter you can
  • Explain, with the merged menus, why returning a collection couples every caller to its representation
  • Draw the Iterator class diagram (aggregate, iterator, concrete pairs, client) and map it to the menus
  • State the single responsibility principle and say why traversal is a second responsibility of a collection
  • Write a Python iterable three ways (has_next/next class, __iter__/__next__ class, generator) and pick one
  • Draw Component / Leaf / Composite for the menu tree and explain where the recursion lives
  • Argue transparency versus safety in a Composite and name the trade-off the book makes

The Diner and the Pancake House merge

▶ Video lesson: The merged menus: why two loops, and what fixed them 4:25 · 6 scenes · narrated, pause anytime and explore

Objectville's Pancake House and the Diner next door merge. Lou keeps serving breakfast from his menu, Mel keeps serving lunch from his, and one new waitress is hired to serve both. Each menu is a collection of MenuItem objects (name, description, vegetarian flag, price). The trouble is what the collections are: Lou's menu is a Python list he appends to whenever he invents a pancake; Mel's is a fixed array of six slots with a count, because Mel wants the menu short and the memory predictable. Neither will change his mind.

The waitress is asked for print_menu() (everything), print_breakfast_menu(), print_lunch_menu(), print_vegetarian_menu() and is_item_vegetarian(name). Both menus offer get_menu_items(), which returns their container, so she writes two loops per method: one for a list, one for an array that stops at count. Watch what that costs as the requirements keep coming.

Why 'just make them both a list' is not the fix

Two reasons. Often you cannot: Mel owns his menu and his storage choice, and real code bases are full of collections you do not control (a vendor SDK that returns a cursor, a legacy module that returns a dict). And even if every menu were a list today, the waitress would still be programmed to an implementation: the day one menu needs a dict, a database or lazy loading, every method that loops reopens. The fix has to remove the waitress's knowledge of the container, not standardise the container.

Iterate without exposing the structure

Apply chapter 1's first principle. What varies between the menus is the container and how you step through it. What stays the same is the shape of the conversation the waitress needs: is there another item? give me the next one. That conversation becomes an object, an iterator, with two methods: has_next() and next().

Each menu gets its own iterator class that knows exactly one container. DinerMenuIterator holds a reference to the array, the count and a position; its has_next() is position < count, so the empty slots are never seen. PancakeHouseMenuIterator holds the list and a position. The menus replace get_menu_items() with create_iterator(), which returns a fresh iterator over their own storage. The containers never leave the menu classes again.

The waitress now depends on two small interfaces, Menu (for create_iterator()) and Iterator (for has_next() and next()), and writes one loop. She can hold any number of menus in a list and treat them identically. When the Cafe joins with its dict, the work is one CafeMenu plus one CafeMenuIterator; Waitress is not opened.

What the iterator buys

  • Encapsulation. The container is private. Callers cannot append to Lou's list or blank a slot in Mel's array.
  • Polymorphic iteration. One loop handles a list, an array and a dict, because all three hide behind the same two methods.
  • Independent change. Mel can swap his array for a list tomorrow; the diff is DinerMenuIterator, nothing else.
  • Several walks at once. Each create_iterator() call returns its own position, so two loops over the same menu do not trip over each other.

The waitress, before and after

Containers exposed, loops duplicated

get_menu_items() leaks the live container. Every waitress method carries one loop per container and must know where each one ends.

class MenuItem:
    def __init__(self, name, description, vegetarian, price):
        self.name, self.description = name, description
        self.vegetarian, self.price = vegetarian, price

class PancakeHouseMenu:
    def __init__(self):
        self.menu_items = []                        # a list: grows as Lou invents pancakes
        self.add_item("Regular Pancakes", "with eggs and sausage", False, 2.99)

    def add_item(self, name, description, vegetarian, price):
        self.menu_items.append(MenuItem(name, description, vegetarian, price))

    def get_menu_items(self):
        return self.menu_items                      # hands out the live list

class DinerMenu:
    MAX_ITEMS = 6
    def __init__(self):
        self.menu_items = [None] * self.MAX_ITEMS   # a fixed array: Mel wants a hard cap
        self.count = 0
        self.add_item("BLT", "bacon, lettuce, tomato", False, 2.99)

    def add_item(self, name, description, vegetarian, price):
        if self.count >= self.MAX_ITEMS:
            print("Sorry, the menu is full")
            return
        self.menu_items[self.count] = MenuItem(name, description, vegetarian, price)
        self.count += 1

    def get_menu_items(self):
        return self.menu_items                      # hands out the live array, empty slots included

class Waitress:
    def __init__(self, pancake_house_menu, diner_menu):
        self.pancake_house_menu = pancake_house_menu
        self.diner_menu = diner_menu

    def print_menu(self):
        for item in self.pancake_house_menu.get_menu_items():     # loop 1: a list
            print(item.name, item.price)
        lunch = self.diner_menu.get_menu_items()
        for i in range(self.diner_menu.count):                    # loop 2: an array with a count
            print(lunch[i].name, lunch[i].price)

    # print_breakfast_menu, print_lunch_menu, print_vegetarian_menu and
    # is_item_vegetarian(name) each repeat both loops

Iterators handed out, one loop (Iterator)

Each menu builds an iterator over its own storage. The waitress knows has_next() and next() and nothing about lists, arrays or counts.

from abc import ABC, abstractmethod

class Iterator(ABC):
    @abstractmethod
    def has_next(self) -> bool: ...
    @abstractmethod
    def next(self): ...

class Menu(ABC):
    @abstractmethod
    def create_iterator(self) -> Iterator: ...

class DinerMenuIterator(Iterator):
    def __init__(self, items, count):
        self.items, self.count, self.position = items, count, 0

    def has_next(self):
        return self.position < self.count           # stop at count: the empty slots stay invisible

    def next(self):
        item = self.items[self.position]
        self.position += 1
        return item

class PancakeHouseMenuIterator(Iterator):
    def __init__(self, items):
        self.items, self.position = items, 0

    def has_next(self):
        return self.position < len(self.items)

    def next(self):
        item = self.items[self.position]
        self.position += 1
        return item

class DinerMenu(Menu):                              # MenuItem and add_item as before
    MAX_ITEMS = 6
    def __init__(self):
        self.menu_items = [None] * self.MAX_ITEMS
        self.count = 0

    def create_iterator(self):
        return DinerMenuIterator(self.menu_items, self.count)   # no get_menu_items() any more

class PancakeHouseMenu(Menu):
    def __init__(self):
        self.menu_items = []

    def create_iterator(self):
        return PancakeHouseMenuIterator(self.menu_items)

class Waitress:
    def __init__(self, menus):
        self.menus = menus                          # any number of Menu objects

    def print_menu(self):
        for menu in self.menus:
            self._print_items(menu.create_iterator())

    def _print_items(self, iterator):
        while iterator.has_next():                  # the one loop, for every menu
            item = iterator.next()
            print(item.name, item.price)

Principle: single responsibility

A class should have only one reason to change.

Could the menu just grow has_next() and next() itself and skip the separate iterator? It could, and then DinerMenu would change for two unrelated reasons: when the rules about menu items change (a new field, a cap of eight instead of six), and when the way of walking items changes (reverse order, vegetarian-only, two walks at the same time). Every reason to change is a chance to break the other job. That is the single responsibility principle, and the iterator is its textbook application: managing the collection is one responsibility, traversing it is another, so they live in two classes.

The word for a class whose parts belong together is cohesion. A DinerMenu carrying a walk-state field position is less cohesive than DinerMenu plus DinerMenuIterator, because position has nothing to do with what a menu is. It also breaks the moment two callers walk the menu at once, since there is only one position. A quick test when you suspect a class is doing two jobs: list the changes it will plausibly need in a year and see whether they fall into two unrelated piles.

The same lens explains the original waitress. She had two jobs, printing menus and knowing how each container is laid out, and the second kept forcing edits that had nothing to do with printing. The iterator took the second job away from her.

The Iterator pattern, named

▶ Video lesson: Generators: Python's native Iterator 2:22 · 4 scenes · narrated, pause anytime and explore

Iterator provides a way to access the elements of an aggregate object sequentially without exposing its underlying representation.

Roles in the story: the Aggregate is the Menu interface (it promises create_iterator()); the concrete aggregates are DinerMenu and PancakeHouseMenu; the Iterator interface is has_next() and next(); the concrete iterators are the two menu iterators; the client is Waitress. The pattern also moves the walk state, the position, out of the aggregate and into an object the client owns, which is why two clients can walk the same menu at once and why the aggregate stays cohesive.

Two flavours exist. An external iterator is driven by the client one next() at a time, as above; the client can stop early or interleave two walks. An internal iterator is handed a function and does the walking itself (map, for_each); shorter to call, less control. Python's for loop is external iteration with the bookkeeping hidden, and map() is the internal kind.

Where you have already seen it

  • Every for loop: file objects yield lines, dict.items(), range, enumerate and zip hand out items without showing how they are stored.
  • Database cursors: for row in cursor hides whether rows are buffered in memory, streamed, or fetched in pages.
  • os.scandir() and pathlib.Path.iterdir() return one directory entry at a time instead of building the listing.
  • Paginated API clients (boto3 paginators, Google API page iterators) yield items and hide the next-page token dance.
  • Java's Iterator<T>, JavaScript's Symbol.iterator and generators, C++ iterators: the same two operations under different names.

Iterator in Python, three ways

Two methods and a client-driven while. Clear, and exactly what the class diagram shows; but nothing in Python will call these for you.

class DinerMenuIterator:
    """The book's shape: two methods, and the client drives the loop."""
    def __init__(self, items, count):
        self.items, self.count, self.position = items, count, 0

    def has_next(self) -> bool:
        return self.position < self.count

    def next(self):
        item = self.items[self.position]
        self.position += 1
        return item

# the client (DinerMenu.create_iterator() returns the object above)
iterator = diner_menu.create_iterator()
while iterator.has_next():
    print(iterator.next().name)

The same class, renamed to what the for statement calls. StopIteration replaces has_next(). Use it when the iterator needs extra methods (peek(), reset()) or state you want to inspect.

class DinerMenuIterator:
    """Python's iterator protocol: __next__ returns the next item or raises StopIteration."""
    def __init__(self, items, count):
        self.items, self.count, self.position = items, count, 0

    def __iter__(self):
        return self                          # an iterator is also iterable, so `for` accepts it directly

    def __next__(self):
        if self.position >= self.count:
            raise StopIteration              # has_next() and next() collapsed into one call
        item = self.items[self.position]
        self.position += 1
        return item

class DinerMenu:
    MAX_ITEMS = 6
    def __init__(self):
        self.menu_items, self.count = [None] * self.MAX_ITEMS, 0

    def __iter__(self):
        return DinerMenuIterator(self.menu_items, self.count)   # create_iterator(), spelled the Python way

for item in DinerMenu():                     # for calls iter(menu), then next() until StopIteration
    print(item.name, item.price)

Idiomatic Python. The generator frame keeps the position, return raises StopIteration for you, and itertools.chain merges menus. This is what you write unless you have a reason not to.

import itertools

class DinerMenu:
    MAX_ITEMS = 6
    def __init__(self):
        self.menu_items, self.count = [None] * self.MAX_ITEMS, 0

    def __iter__(self):
        for i in range(self.count):          # a generator: Python builds the iterator object
            yield self.menu_items[i]         # and keeps `position` for you in the frame

class PancakeHouseMenu:
    def __init__(self):
        self.menu_items = []

    def __iter__(self):
        return iter(self.menu_items)         # a list already knows how to iterate: delegate

class CafeMenu:
    def __init__(self):
        self.menu_items = {}                 # keyed by dish name

    def __iter__(self):
        yield from self.menu_items.values()

class Waitress:
    def __init__(self, *menus):
        self.menus = menus

    def print_menu(self):
        for item in itertools.chain(*self.menus):   # three containers, one loop, zero iterator classes
            print(item.name, item.price)

Python note

Python builds the Iterator pattern into the language. The for statement is the client: it calls iter(obj) to get an iterator (your __iter__(), the pattern's create_iterator()), then next(it) until StopIteration. A generator (def __iter__(self): ... yield item) writes the concrete iterator class for you: the frame keeps the position and the exception is raised when the function returns. Hand-write an iterator class only when the walk needs extra operations (peek(), remove(), reset()), must be pickled, or must be inspected mid-walk. itertools.chain merges collections; yield from walks trees.

Menus within menus

▶ Video lesson: Menus within menus: the Composite tree 4:09 · 6 scenes · narrated, pause anytime and explore

The merged restaurant is barely running when the Diner adds a dessert menu: a menu that lives inside the Diner's menu, after the sandwiches. Now the Diner's collection holds MenuItem objects and a Menu. The waitress's loop reaches the dessert menu, asks for .price, and crashes. Patching the loop with if isinstance(item, Menu): walk it too works for one level and breaks at the next sub-menu; adding print_dessert_menu() to the waitress reopens her for every new sub-menu, which is the problem Iterator had just solved coming back through another door.

Draw what the data has become: a tree. The root is "all menus"; its children are the restaurant menus; their children are dishes or further menus; dishes are the leaves. The new requirement has two halves. The waitress must be able to call print_menu() on anything in that tree, dish or menu, and get sensible output. And calling it on the root must print everything, however deep the menus go.

The Iterator pattern treated a flat collection as "a thing I can walk". The Composite pattern treats a tree as "a thing I can call an operation on", where a menu answers the call by forwarding it to each of its children. The recursion is the pattern.

The Composite pattern, named

Composite composes objects into tree structures to represent part-whole hierarchies. Composite lets clients treat individual objects and compositions of objects uniformly.

Three roles. The Component (MenuComponent) is the one type the client knows; it declares the operations for leaves, the operations for composites and the operations both share. The Leaf (MenuItem) implements the leaf operations and has no children. The Composite (Menu) holds a list of components, so it can hold other composites, and implements the shared operations by looping over its children and calling the same operation on each, which is where the recursion comes from. The client (Waitress) holds one component, the root, and never asks what it is.

Transparency or safety

The book puts every operation on MenuComponent, with default implementations that raise UnsupportedOperation. A MenuItem therefore has an add() that fails if anyone calls it. That is transparency: the client treats every node identically and never checks a type, and the price is that some calls are nonsense discovered at runtime. The alternative is safety: child-management methods live on Menu only, so nonsense cannot even be written against a MenuItem, and the price is that a client holding a MenuComponent must check the type before calling add(). There is no free option. The book picks transparency because uniform treatment is the whole point of the pattern. In Python, where everything is duck-typed anyway, a sensible middle is to keep print_menu() and __iter__() on the component and give Menu alone the add() and remove() methods, accepting one isinstance at the single place where menus are built.

Iterating a composite

A tree is also a collection, so the two patterns of this chapter meet. Give MenuItem.__iter__ a single yield self and Menu.__iter__ a yield from child for each child, and for dish in all_menus yields every dish in menu order, however deep. print_vegetarian_menu() becomes a two-line loop with no exception handling, and nothing in the waitress knows the tree exists.

Where you have already seen it

  • File systems: a directory holds files and directories; du, rm -r and Path.rglob() recurse without caring which is which.
  • GUI widget trees and the browser DOM: a panel contains buttons and panels; render() on the root draws everything.
  • unittest.TestSuite holds TestCases and other suites, and run() works on either: a Composite in the standard library.
  • Abstract syntax trees: a BinOp holds operands that may themselves be BinOps; compile() and ast.unparse() recurse over the same node type.
  • Bills of materials and org charts: an assembly's cost is the sum of its parts, some of which are assemblies.

Where should add() and remove() live?

Transparency (the book's choice)

One interface for everything; the client never checks a type. Cost: MenuItem.add() exists and raises at runtime, as the last line shows.

class UnsupportedOperation(Exception):
    pass

class MenuComponent:
    """Transparency: every operation on the one type. Leaves inherit the raising defaults."""
    def __init__(self, name):
        self.name = name
    def add(self, component): raise UnsupportedOperation
    def remove(self, component): raise UnsupportedOperation
    def child(self, i): raise UnsupportedOperation
    @property
    def price(self): raise UnsupportedOperation
    def print_menu(self, depth=0): raise UnsupportedOperation

class MenuItem(MenuComponent):
    def __init__(self, name, price, vegetarian=False):
        super().__init__(name)
        self._price, self.vegetarian = price, vegetarian
    @property
    def price(self): return self._price
    def print_menu(self, depth=0):
        print("  " * depth + f"{self.name}, ${self._price:.2f}" + (" (v)" if self.vegetarian else ""))

class Menu(MenuComponent):
    def __init__(self, name):
        super().__init__(name)
        self._children: list[MenuComponent] = []
    def add(self, component): self._children.append(component)
    def remove(self, component): self._children.remove(component)
    def child(self, i): return self._children[i]
    def print_menu(self, depth=0):
        print("  " * depth + self.name.upper())
        for c in self._children:
            c.print_menu(depth + 1)              # dish or menu: the same call

all_menus = Menu("All menus")
diner = Menu("Diner menu"); all_menus.add(diner)

Safety (child methods on Menu only)

A dish cannot be asked to add(). Cost: code that holds a MenuComponent and wants to add must check isinstance first, so the uniformity leaks a little.

from abc import ABC, abstractmethod

class MenuComponent(ABC):
    """Safety: only what both kinds share. add/remove exist on Menu alone."""
    def __init__(self, name):
        self.name = name
    @abstractmethod
    def print_menu(self, depth=0): ...

class MenuItem(MenuComponent):
    def __init__(self, name, price, vegetarian=False):
        super().__init__(name)
        self.price, self.vegetarian = price, vegetarian
    def print_menu(self, depth=0):
        print("  " * depth + f"{self.name}, ${self.price:.2f}")

class Menu(MenuComponent):
    def __init__(self, name):
        super().__init__(name)
        self._children: list[MenuComponent] = []
    def add(self, component): self._children.append(component)     # only here
    def remove(self, component): self._children.remove(component)
    def print_menu(self, depth=0):
        print("  " * depth + self.name.upper())
        for c in self._children:
            c.print_menu(depth + 1)

def add_special(component: MenuComponent, special: MenuItem):
    if isinstance(component, Menu):              # the price of safety: callers check the type
        component.add(special)
    else:
        raise TypeError("specials can only be added to a Menu")

    ...                                          # name, price, vegetarian, print_menu as before
    def __iter__(self):
        yield self                               # a dish is a sequence of one

class Menu(MenuComponent):
    ...                                          # children, add, remove, print_menu as before
    def __iter__(self):
        for child in self._children:
            yield from child                     # a menu is everything below it, in menu order

class Waitress:
    def __init__(self, all_menus: MenuComponent):
        self.all_menus = all_menus               # one reference: the root of the tree

    def print_menu(self):
        self.all_menus.print_menu()              # recursion inside the tree does the work

    def print_vegetarian_menu(self):
        for dish in self.all_menus:              # Iterator over the Composite: leaves only, in order
            if dish.vegetarian:
                dish.print_menu()
Two one-line generators turn the tree into a sequence of dishes. The waitress's vegetarian menu is a plain for loop: Iterator over Composite.

Common mistakes

  • "Just return a copy of the list." A copy stops callers corrupting the container, but they are still coupled to its type (list methods, indexing), and you pay O(n) per call. Hand out an iterator, not a collection.
  • The aggregate is its own iterator. __iter__ returning self with a position field on the menu means two nested for loops share one position and a second walk starts where the first ended. __iter__ should return a fresh iterator every time; a generator does this automatically.
  • Reusing an exhausted iterator. Python iterators and generators are single-pass: a second for over the same generator object yields nothing. Walk the iterable (the menu) again, not the iterator.
  • has_next() then next() across threads. Two calls give a race; another thread can consume the item in between. Python's single __next__() call avoids the gap, which is one reason the protocol looks the way it does.
  • isinstance all over the client. If the waitress checks isinstance(child, Menu) before every call, the uniform treatment is gone. Push the behaviour into the component (print_menu() on both kinds) and keep the type check, if any, to where the tree is built.
  • Cached totals without invalidation. A composite that caches its total price must drop the cache when a child is added or removed anywhere below it. Either recompute (trees are usually small) or invalidate upwards.
  • Composite for a flat list. No sub-menus means no tree; a list of items and a for loop is the design. Reach for Composite when nesting is real, and for an iterator class when a generator cannot express the walk.
  • Composite confused with Decorator. Both nest objects of the component type. A decorator wraps exactly one object to add behaviour; a composite holds many to aggregate them.

How to say it in an interview

Say: 'Two menus with different containers forced the waitress to write one loop per container in every method, and get_menu_items() leaked their internals. I would give each menu a create_iterator() returning an object with has_next() and next(), so the waitress has one loop and the menus keep their storage private. That is Iterator, and it follows the single responsibility principle: traversal is a second reason for a collection class to change, so it moves out. In Python that is __iter__, usually a generator. When menus started containing menus, I would make the data a tree with one MenuComponent type, MenuItem leaves and Menu composites that forward print_menu() to their children: Composite. Its trade-off is transparency versus safety: one interface for everything means leaves carry operations that fail at runtime.' Then draw Component, Leaf and Composite with the arrow back to Component.
