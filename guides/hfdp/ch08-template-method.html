Encapsulating algorithms: Template Method

Starbuzz's coffee and tea follow the same four-step recipe, and the first refactor, pulling the identical steps into a superclass, leaves the recipe itself written twice. The fix puts the skeleton of the algorithm in the abstract class and defers the steps that vary to subclasses: the Template Method pattern. Along the way: hooks, the Hollywood principle, why sorting is a template method, and the Python view where a key function is often the lighter tool.

After this chapter you can
  • Explain, with the coffee and tea story, why pulling identical methods into a superclass still leaves the algorithm duplicated
  • Draw the Template Method class diagram: the template method, abstract steps, concrete steps and hooks
  • Tell an abstract step from a hook, and say when each is the right kind of step
  • State the Hollywood principle and point to the call direction in a sequence diagram
  • Explain why sorted() is a template method, and when key= beats a subclass in Python

The Starbuzz story

▶ Video lesson: Coffee and tea: one recipe, written twice, then once 5:07 · 7 scenes · narrated, pause anytime and explore

Starbuzz Coffee, the chain from the Decorator chapter, is automating its barista training. The manual has two recipes. Coffee: boil water, brew the coffee grinds, pour into a cup, add sugar and milk. Tea: boil water, steep the tea bag, pour into a cup, add lemon. The first version of the code is a faithful transcript: a Coffee class and a Tea class, each with a prepare_recipe() method that calls its own four private steps.

Lay the two classes side by side and two of the steps are the same method, copied. The obvious repair is a superclass that holds the shared steps. Watch what that repair does and does not fix: the copied method bodies disappear, but the recipe, the order of the four calls, is still spelled out in both subclasses. This chapter is about noticing that second kind of duplication and moving it up as well.

Two recipes, one algorithm

Step through the duplicated design, the half-fix that only pulls up identical methods, and the refactor that moves the recipe itself into the superclass. The second scenario ends with a customer who wants coffee without condiments.

The half-fix. The step bodies that were identical moved up; the recipe, the order of the four calls, is still written in both subclasses, and each names its steps differently.

Duplication you cannot diff

Pulling identical methods into a superclass removes copied bodies. It does nothing for a copied sequence of calls, and a sequence is harder to keep in sync than a body: a bug fix that reorders two steps in Coffee is invisible from Tea. The test is simple: if two methods make the same calls in the same order and differ only in which concrete method each call lands on, the algorithm is duplicated, however different the method names look.

Abstracting the algorithm

The two recipes differ in step 2 and step 4, but only in what those steps do, not in what they are. Dripping water through coffee grinds and steeping a tea bag are both ways to brew. Sugar and milk, or lemon, are both condiments. Give the two steps the generic names brew() and add_condiments(), and the two prepare_recipe() bodies become identical: boil, brew, pour, add condiments.

Identical code moves up. CaffeineBeverage.prepare_recipe() now holds the recipe, and it calls four methods:

  • boil_water() and pour_in_cup(): concrete steps, written once in the superclass, shared by every drink.
  • brew() and add_condiments(): abstract steps, declared in the superclass with no body, so every subclass must supply them.

prepare_recipe() is the template method: it defines the algorithm as a sequence of steps, some of which are deferred to subclasses. The subclasses fill in the blanks without being able to change the sequence. Coffee and Tea shrink to two methods each, and a third beverage is two methods plus a class name.

Two things changed that are easy to miss. The superclass now owns the algorithm: there is one place to read it, one place to fix it, and the order of steps cannot drift between drinks. And the subclasses lost the ability to call their steps themselves; they only provide them. Who calls whom is the subject of the Hollywood section.

The beverage code, before and after

Two recipes, written twice

Identical step bodies are copied, and the four-call sequence is copied too. Nothing ties the two recipes together, so they can drift.

class Coffee:
    def prepare_recipe(self):
        self.boil_water()
        self.brew_coffee_grinds()
        self.pour_in_cup()
        self.add_sugar_and_milk()

    def boil_water(self): print("Boiling water")                  # identical in Tea
    def brew_coffee_grinds(self): print("Dripping coffee through filter")
    def pour_in_cup(self): print("Pouring into cup")              # identical in Tea
    def add_sugar_and_milk(self): print("Adding sugar and milk")

class Tea:
    def prepare_recipe(self):            # same four calls, same order, different names
        self.boil_water()
        self.steep_tea_bag()
        self.pour_in_cup()
        self.add_lemon()

    def boil_water(self): print("Boiling water")                  # copy
    def steep_tea_bag(self): print("Steeping the tea")
    def pour_in_cup(self): print("Pouring into cup")              # copy
    def add_lemon(self): print("Adding lemon")

One recipe, steps deferred (Template Method)

prepare_recipe() holds the algorithm once. Subclasses supply brew() and add_condiments(); customer_wants_condiments() is a hook they may override.

from abc import ABC, abstractmethod

class CaffeineBeverage(ABC):
    def prepare_recipe(self) -> None:           # the TEMPLATE METHOD: fixed order, never overridden
        self.boil_water()
        self.brew()
        self.pour_in_cup()
        if self.customer_wants_condiments():    # a hook decides whether step 4 runs
            self.add_condiments()

    @abstractmethod
    def brew(self) -> None: ...                 # abstract step: subclasses MUST supply

    @abstractmethod
    def add_condiments(self) -> None: ...       # abstract step: subclasses MUST supply

    def boil_water(self) -> None: print("Boiling water")          # concrete step, shared
    def pour_in_cup(self) -> None: print("Pouring into cup")      # concrete step, shared

    def customer_wants_condiments(self) -> bool:                  # hook: subclasses MAY override
        return True

class Tea(CaffeineBeverage):
    def brew(self): print("Steeping the tea")
    def add_condiments(self): print("Adding lemon")

class Coffee(CaffeineBeverage):
    def brew(self): print("Dripping coffee through filter")
    def add_condiments(self): print("Adding sugar and milk")

class CoffeeWithHook(Coffee):
    def customer_wants_condiments(self) -> bool:
        answer = input("Milk and sugar with your coffee? (y/n) ")
        return answer.strip().lower().startswith("y")

Tea().prepare_recipe()       # Boiling water / Steeping the tea / Pouring into cup / Adding lemon
Coffee().prepare_recipe()    # Boiling water / Dripping coffee... / Pouring into cup / Adding sugar and milk

Hooks: steps a subclass may override

A customer wants black coffee. The template calls add_condiments() unconditionally, so the recipe has no way to express "sometimes". A BlackCoffee subclass whose add_condiments() does nothing would work, and it is the override-to-cancel smell from the duck chapter: a method whose whole body exists to undo its parent.

The pattern's answer is a hook: a method in the abstract class with a default implementation, usually empty or returning a constant, that the template calls at a chosen point. customer_wants_condiments() returns True by default; the template runs step 4 only if it says so. A subclass that cares, CoffeeWithHook, overrides it and asks the customer. Tea never mentions it and gets the default. That is the difference between the two kinds of deferred step:

Abstract stepHook
Body in the superclassnone (@abstractmethod)a default (return True, pass)
Subclass must override?yes, or it cannot be instantiatedno
Says to the subclass"you must decide this""you may change this"
Typical usethe parts that genuinely differ per subclassoptional behaviour, conditional steps, before/after extension points
Starbuzz examplebrew(), add_condiments()customer_wants_condiments()

Hooks serve three jobs. A conditional hook decides whether an optional step runs (the condiments question). An extension hook is an empty method the template calls before or after a step, so a subclass can add behaviour without the template knowing: unittest's setUp() and tearDown() are exactly this. An informational hook lets the subclass observe where the algorithm is, for logging or metrics.

The design question each time: should this step be abstract or a hook? Make it abstract when every subclass would have to supply something different anyway; make it a hook when a sensible default exists and most subclasses would just repeat it. Too many abstract steps and writing a subclass becomes a chore; too many hooks and the contract gets vague, because nothing tells the subclass author which of the fifteen methods actually matter. The reference point is Starbuzz: two abstract steps, two concrete steps, one hook.

The template's control flow. The order is fixed; the rounded boxes are concrete, the sharp ones abstract, and the diamond is the hook that lets a subclass choose the path without owning the flow.

The Hollywood principle

Don't call us, we'll call you.

In the beverage design, CaffeineBeverage is the high-level component: it knows the algorithm. Coffee and Tea are low-level components: they know how to do one step. The principle says the high-level component decides when and how the low-level ones are used, and the low-level ones never call up. Coffee.brew() does not call prepare_recipe(), does not call pour_in_cup(), does not peek at where the recipe is. It brews when told to and returns.

Why insist? Because the alternative is dependency rot: high-level classes calling low-level ones, which call back into high-level ones, which depend on sideways classes, until nobody can say who drives what. The Hollywood principle keeps the dependency arrows pointing one way, from the class that owns the algorithm down to the classes that supply its parts, so the algorithm stays readable from a single method.

This is what makes Template Method the shape of every framework. A web framework's request cycle, a test runner, a GUI event loop and an ORM's save path are all template methods: you write do_GET, test_login, on_click or clean(), and the framework calls you at the right moment. The same one-way rule shows up as inversion of control, and the Dependency Inversion Principle from the Factory chapter is a close relative: both say the low-level code should not depend on, or call into, the high-level code. Hollywood is specifically about who calls; dependency inversion is about what you depend on.

Watch the direction of every arrow between the two class lanes in the simulation below. Each one goes down, from the template into the subclass. None go up.

Finding Hollywood violations

A quick audit for any inheritance-based design: list every call from a subclass method into a method of its superclass that is not a plain super().same_method(). Each one is a low-level component calling the high-level one, and each is a place where the algorithm's flow has leaked downwards. In a clean Template Method the list is empty: subclasses implement steps and return.

The Template Method pattern, named

▶ Video lesson: Template Method: the skeleton, the hooks, and who calls whom 3:29 · 5 scenes · narrated, pause anytime and explore

Template Method defines the skeleton of an algorithm in a method, deferring some steps to subclasses. Template Method lets subclasses redefine certain steps of an algorithm without changing the algorithm's structure.

Map the words to Starbuzz. The skeleton is prepare_recipe(): boil, brew, pour, condiments. The deferred steps are brew() and add_condiments(), abstract in CaffeineBeverage. Without changing the structure: a subclass can say how to brew but cannot make brewing happen before boiling. The roles, in the general shape:

  • AbstractClass holds the template_method() and declares the primitive operations it calls. Some primitives are abstract (must be supplied), some concrete (shared), some hooks (may be changed).
  • ConcreteClass implements the abstract primitives and optionally overrides hooks. There may be many, one per variant of the algorithm.

What you get: the algorithm is written once and owned by one class; adding a variant is a small subclass; changes to the shared steps reach every variant. What you pay: the variants are fixed at class-definition time (a Coffee is a coffee for life), the hierarchy grows with the number of variants, and the flow of control is split across two classes, so a reader has to hold both open.

Where you have already seen it

  • unittest.TestCase.run() calls setUp(), your test_* method and tearDown() in a fixed order; you write the steps, the runner owns the sequence.
  • collections.abc.MutableMapping gives you pop(), setdefault(), update(), get(), items() and equality, all written once over the five primitives you implement: __getitem__, __setitem__, __delitem__, __iter__, __len__.
  • http.server.BaseHTTPRequestHandler.handle_one_request() parses the request line and headers, then calls the do_GET or do_POST you wrote.
  • threading.Thread.start() does the bookkeeping and then calls your run(); json.JSONEncoder.default() is a hook called only for objects the encoder cannot serialise.
  • Django's class-based views (dispatch() → get() → get_context_data()) and asyncio.Protocol (connection_made, data_received, connection_lost) are stacks of template methods and hooks.
  • sorted() and list.sort(): the sorting algorithm is the skeleton; __lt__ on the elements, or a key= function, is the step you supply. More on this below.

Three patterns that are often confused. Factory Method is Template Method where the deferred step is 'create the product'; Strategy swaps the whole algorithm by composition instead of overriding steps.

Sorting as a template method, and the Python view

The book's second example is sorting. A sorting routine has a fixed skeleton (compare, swap or merge, repeat) and exactly one step that depends on what is being sorted: how to compare two elements. In Java the sort routine is a static method on an array utility class, so the "subclass" cannot be a subclass of the sorter; the deferred step is handed over by the elements, which implement a comparison method the sorter calls. It is Template Method with the deferred step living on a different object, because you cannot subclass every array.

Python does the same. sorted() runs Timsort, which is not yours to override, and at every comparison it calls __lt__ on the elements. Give Duck an __lt__ that compares weights and sorted(ducks) orders ducks by weight. The sorter calls down into your element's code and never the reverse: the Hollywood principle, with __lt__ as the primitive operation.

The lighter alternative is key=. Instead of teaching the element how to compare, hand sorted() a function that extracts what to compare by. The skeleton is unchanged; the deferred step arrives as an argument instead of a method. key= wins when the ordering is a property of this call (sort by name here, by weight there); __lt__ wins when the ordering is a property of the type, used everywhere the type is compared, including min(), max() and heapq.

Two ways to supply the one varying step of sorted()

from dataclasses import dataclass

@dataclass
class Duck:
    name: str
    weight: int

    def __lt__(self, other: "Duck") -> bool:    # the one step sorted() leaves to the element
        return self.weight < other.weight

ducks = [Duck("Daffy", 8), Duck("Dewey", 2), Duck("Howard", 7)]

print([d.name for d in sorted(ducks)])                         # ['Dewey', 'Howard', 'Daffy']
print([d.name for d in sorted(ducks, key=lambda d: d.name)])   # ['Daffy', 'Dewey', 'Howard']
Timsort is the template method. The first call fills in the comparison step through Duck.__lt__; the second passes the step as a key function and never touches the class.

sorted() owns the algorithm and asks the elements one question, repeatedly. The exact sequence of questions is Timsort's business (here, a binary insertion for three ducks); the answers are the only thing Duck controls.

Template Method in Python, four ways

The abstract class owns the recipe; subclasses supply brew() and add_condiments() and may override the hook. Use it when the steps belong to a type and vary per subclass, not per call.

from abc import ABC, abstractmethod

class CaffeineBeverage(ABC):
    def prepare_recipe(self) -> None:           # the TEMPLATE METHOD: fixed order, never overridden
        self.boil_water()
        self.brew()
        self.pour_in_cup()
        if self.customer_wants_condiments():    # a hook decides whether step 4 runs
            self.add_condiments()

    @abstractmethod
    def brew(self) -> None: ...                 # abstract step: subclasses MUST supply

    @abstractmethod
    def add_condiments(self) -> None: ...       # abstract step: subclasses MUST supply

    def boil_water(self) -> None: print("Boiling water")          # concrete step, shared
    def pour_in_cup(self) -> None: print("Pouring into cup")      # concrete step, shared

    def customer_wants_condiments(self) -> bool:                  # hook: subclasses MAY override
        return True

class Tea(CaffeineBeverage):
    def brew(self): print("Steeping the tea")
    def add_condiments(self): print("Adding lemon")

class Coffee(CaffeineBeverage):
    def brew(self): print("Dripping coffee through filter")
    def add_condiments(self): print("Adding sugar and milk")

class CoffeeWithHook(Coffee):
    def customer_wants_condiments(self) -> bool:
        answer = input("Milk and sugar with your coffee? (y/n) ")
        return answer.strip().lower().startswith("y")

Tea().prepare_recipe()       # Boiling water / Steeping the tea / Pouring into cup / Adding lemon
Coffee().prepare_recipe()    # Boiling water / Dripping coffee... / Pouring into cup / Adding sugar and milk

Python's lightest Template Method: the skeleton is a function, the varying steps are callable parameters, and a hook is a parameter with a default. Right when the steps are few, stateless and decided per call. sorted(key=), functools.reduce, re.sub with a function and most on_*= callbacks have this shape.

# The template as a function: the varying steps arrive as callables, the hook has a default.
from typing import Callable

def prepare_recipe(brew: Callable[[], None],
                   add_condiments: Callable[[], None],
                   wants_condiments: Callable[[], bool] = lambda: True) -> None:
    print("Boiling water")
    brew()
    print("Pouring into cup")
    if wants_condiments():
        add_condiments()

prepare_recipe(lambda: print("Steeping the tea"), lambda: print("Adding lemon"))
prepare_recipe(lambda: print("Dripping coffee through filter"),
               lambda: print("Adding sugar and milk"),
               wants_condiments=lambda: input("Milk and sugar? (y/n) ").startswith("y"))

# sorted(key=), functools.reduce(fn), re.sub(pattern, repl_fn) are all templates of this shape.

Inheritance earns its keep when the steps share state (self._d) or the base class hands back a lot of derived behaviour: five primitives in, a dozen mapping methods out. Passing five callables to a function would be clumsier and would lose the type.

# When the steps share state and the base gives you a lot for free, subclass the skeleton.
from collections.abc import MutableMapping

class LowerDict(MutableMapping):
    """Case-insensitive keys. We write the five primitive steps; the ABC supplies the rest."""
    def __init__(self):
        self._d: dict[str, object] = {}

    def __getitem__(self, key): return self._d[key.lower()]
    def __setitem__(self, key, value): self._d[key.lower()] = value
    def __delitem__(self, key): del self._d[key.lower()]
    def __iter__(self): return iter(self._d)
    def __len__(self): return len(self._d)

headers = LowerDict()
headers["Accept"] = "application/json"
headers.setdefault("ACCEPT", "text/plain")   # setdefault, pop, update, get, items, == are all
headers.update(Host="example.org")           # templates written once over the five primitives
print(headers["accept"], headers.pop("HOST"), len(headers))   # application/json example.org 1

When the skeleton belongs to someone else and runs your code at its chosen moments, you are on the subclass side of a Template Method whether you like it or not. Know which methods are abstract (the test_* you must write) and which are hooks (setUp, tearDown, defaults do nothing).

# A framework that calls you: TestCase.run() is the template, your methods are the steps.
import unittest

class Kettle:
    def __init__(self): self.on = False
    def boil(self): self.on = True
    def off(self): self.on = False

class TestKettle(unittest.TestCase):
    def setUp(self):              # hook: run() calls it before every test; default does nothing
        self.kettle = Kettle()

    def test_boils(self):         # the varying step: run() finds test_* methods by name and calls them
        self.kettle.boil()
        self.assertTrue(self.kettle.on)

    def tearDown(self):           # hook: run() calls it after, even when the test fails
        self.kettle.off()

# unittest.main() would call run() on each test: setUp -> test_boils -> tearDown, in that order, always.
flowchart TD
    A{A fixed order of steps<br/>where only some steps vary?} -->|no| B[Plain method or function]
    A -->|yes| C{Must one object swap the<br/>whole algorithm at runtime?}
    C -->|yes| D[Strategy<br/>compose an algorithm object]
    C -->|no, the skeleton is stable| E{Do the steps share state, or does<br/>the base offer many defaults and hooks?}
    E -->|no| F[Function with callable steps<br/>sorted key=, brew=]
    E -->|yes| G[Template Method<br/>abstract base with abstract steps and hooks]
    G --> H{Is the varying step<br/>creating an object?}
    H -->|yes| I[Factory Method<br/>chapter 4]
    H -->|no| J[Template Method as is]
Pick the lightest tool that still keeps the algorithm in one place.

Common mistakes

  • Every step abstract. A CaffeineBeverage with six abstract methods makes writing Tea a chore and tells the subclass author nothing about which steps matter. Give shared steps bodies, make optional ones hooks, and keep the abstract set to what genuinely differs. Starbuzz needs two.
  • Overriding the template method. A subclass that redefines prepare_recipe() to squeeze in a step has reintroduced the duplicated algorithm with one extra class. Java marks the template final; in Python, mark it with @typing.final (type checkers enforce it) and a comment, and add a hook where the extension was needed.
  • Hooks mistaken for contracts. If a step must be supplied, make it abstract so a missing override fails at instantiation. A hook that silently does nothing when the author forgot it is a bug that ships.
  • Steps calling the recipe, or each other. brew() that calls pour_in_cup() because "it is always next" moves part of the algorithm into the subclass. The flow belongs to the template; steps do their step and return.
  • Deep hierarchies. A template whose steps are themselves templates three levels down means the variants multiply along several axes. That is the signal to compose: Strategy objects for the steps (1 · Welcome to design patterns: Strategy), or callables.
  • Confusing it with Strategy. Template Method varies steps by inheritance, fixed per class. Strategy varies the whole algorithm by composition, swappable per object at runtime. Same chapter 1 principles, opposite choice of mechanism, and the table above tells them apart.

How to say it in an interview

Say: 'Coffee and tea follow the same four-step recipe and differ only in how you brew and what you add. I would put the recipe in an abstract CaffeineBeverage class as a template method, prepare_recipe, that calls boil_water, brew, pour_in_cup and add_condiments in a fixed order, with brew and add_condiments abstract so each drink fills them in and the shared steps written once. A hook such as customer_wants_condiments, with a default, lets a subclass opt into a step without being forced to. The superclass drives the algorithm and calls down into the subclass, never the reverse: that is the Hollywood principle, and it is why frameworks look like this. In Python I would subclass when steps share state or a framework owns the skeleton; for one varying step I would pass a function, like sorted with key.' Then draw the abstract class with the template method, two abstract steps and a hook.
