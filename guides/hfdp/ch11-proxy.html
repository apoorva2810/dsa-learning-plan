Controlling object access: Proxy

Mighty Gumball wants to watch its machines from the office, but the machines live in other processes. The object that solves it, a stand-in with the machine's interface that forwards calls across the wire, is one member of a family: remote, virtual, protection, caching and logging proxies all control how a call reaches the real object without the caller changing. This chapter builds each kind in Python, with __getattr__ doing the work Java needs reflection for, and ends with the question interviewers love: how is this different from Decorator?

After this chapter you can
  • Explain, with the gumball monitor, why a local reference cannot reach a remote object and what the stub and skeleton do
  • Draw the Proxy class diagram (Subject, RealSubject, Proxy, Client) and map each role to the story
  • Implement a virtual proxy that shows a placeholder while the real object loads on another thread
  • Implement a protection proxy in Python with __getattr__, and say what __getattr__ does not intercept
  • Contrast Proxy with Decorator, Adapter and Facade by intent, not by shape

Monitoring the gumball machines

▶ Video lesson: The gumball monitor: a stand-in that crosses the wire 4:52 · 7 scenes · narrated, pause anytime and explore

Chapter 10 ended with a GumballMachine that tracks its location, how many gumballs are left and which state it is in (NoQuarter, HasQuarter, Sold, SoldOut, Winner). The CEO of Mighty Gumball wants to see all of that without leaving the office: a monitor that prints, for every machine, its location, its inventory and its state.

Version one takes an afternoon. GumballMonitor holds a reference to a machine and calls three getters. It works perfectly for the one machine on the developer's desk. The requirement that breaks it is a single word in the brief: the machines are remote. They run in other processes on other hosts, and a Python reference cannot point into another process.

The object that solves this is a proxy: a stand-in with the same interface as the real object, which decides how, when or whether a call reaches it. Watch the remote version keep the monitor's code untouched, then meet its cousins: the proxy that stands in for an image that has not downloaded yet, and the proxy that checks who is asking.

A remote call through the proxy

Step through the monitor reading a local machine, failing to reach a remote one, and then reaching it through a stand-in. The second scenario drops the network mid-call.

Why the patches fail

A reference is a process-local address; no amount of cleverness makes it point at an object in another process. Teaching the monitor to speak sockets does work, but it tangles report logic with transport, and every other client of a machine copies the tangle. The fix is not better network code in the monitor; it is moving the network code into an object that looks like a machine, so that the monitor, the refill tool and the audit job keep calling get_count() and never learn where the answer came from.

Remote proxy: a stand-in that crosses the wire

The remote proxy design has four parts, and the two in the middle are the ones every RPC system shares:

  1. The interface (GumballMachineRemote): the three getters. Both the real machine and the proxy implement it, and the monitor is written against it, not against either class. This is chapter 1's program to an interface doing its most important job: without a shared interface there is nothing to stand in for.
  2. The real subject (GumballMachine): unchanged from chapter 10. It does not know it is being called remotely.
  3. The proxy, which the book (following Java RMI) calls the stub: lives in the client's process, has the interface's methods, and implements each one by packing the method name and arguments into a message, sending it, waiting for the reply and unpacking the result. Nothing else in the client process touches a socket.
  4. The skeleton: lives in the server's process, receives messages, finds the real object, calls the named method for real and sends the result back. In Java RMI both helpers were generated for you; in Python you write them in twenty lines, or let xmlrpc, gRPC or multiprocessing.managers generate them.

Two things the wire forces on you. Everything that crosses it must be serialisable (strings, numbers, lists, dicts; not an open file, a lock or a live object), so arguments and results travel as copies. And the skeleton must only dispatch to methods it means to expose: getattr(obj, name_from_the_network) without an allowlist lets a caller name any attribute on the server.

The monitor code, before and after

The monitor speaks sockets

Transport and report logic in one class; every other client repeats it; a local machine can no longer be monitored at all.

import json, socket

class GumballMonitor:
    """Version two: the monitor talks to the machine's host itself."""
    def __init__(self, host: str, port: int):
        self.host, self.port = host, port

    def _ask(self, method: str):
        with socket.create_connection((self.host, self.port)) as conn:   # the monitor is network code now
            conn.sendall(json.dumps({"method": method}).encode())
            return json.loads(conn.recv(4096))["result"]

    def report(self) -> str:
        location = self._ask("get_location")
        count = self._ask("get_count")
        state = self._ask("get_state")
        return f"{location}: {count} gumballs, {state}"

# The refill tool and the audit job need the same three values, so they copy _ask().
# The machine on the developer's desk cannot be monitored at all: this monitor only speaks sockets.

A proxy speaks sockets; the monitor speaks machine

One interface, two implementations. The monitor loops over machines and proxies with the same line of code; the skeleton exposes exactly three methods.

import json, socket
from typing import Protocol

class GumballMachineRemote(Protocol):                 # the Subject: what monitor code is written against
    def get_location(self) -> str: ...
    def get_count(self) -> int: ...
    def get_state(self) -> str: ...

class GumballMachine:                                 # the real subject, unchanged from chapter 10
    def __init__(self, location: str, count: int):
        self.location, self.count, self.state = location, count, "NoQuarter"
    def get_location(self) -> str: return self.location
    def get_count(self) -> int: return self.count
    def get_state(self) -> str: return self.state

class GumballMachineProxy:                            # the stub: same methods, lives in the office process
    def __init__(self, host: str, port: int):
        self.host, self.port = host, port

    def _call(self, method: str):
        with socket.create_connection((self.host, self.port), timeout=2) as conn:
            conn.sendall(json.dumps({"method": method}).encode())
            return json.loads(conn.recv(4096))["result"]

    def get_location(self) -> str: return self._call("get_location")
    def get_count(self) -> int: return self._call("get_count")
    def get_state(self) -> str: return self._call("get_state")

class GumballSkeleton:                                # server side: bytes in, real method call, bytes out
    EXPOSED = frozenset({"get_location", "get_count", "get_state"})

    def __init__(self, machine: GumballMachine):
        self.machine = machine

    def handle(self, raw: bytes) -> bytes:
        request = json.loads(raw)
        if request["method"] not in self.EXPOSED:     # never let the wire name arbitrary attributes
            return json.dumps({"error": "unknown method"}).encode()
        result = getattr(self.machine, request["method"])()
        return json.dumps({"result": result}).encode()

class GumballMonitor:
    def __init__(self, machine: GumballMachineRemote):   # local or remote: the monitor cannot tell
        self.machine = machine

    def report(self) -> str:
        m = self.machine
        return f"{m.get_location()}: {m.get_count()} gumballs, {m.get_state()}"

machines = [GumballMachine("Boulder", 42), GumballMachineProxy("seattle.mightygumball.internal", 9000)]
for machine in machines:
    print(GumballMonitor(machine).report())           # the second line is a round trip; same monitor code

The Proxy pattern, named

▶ Video lesson: Proxy: the pattern and its kinds 3:52 · 6 scenes · narrated, pause anytime and explore

Proxy provides a surrogate or placeholder for another object to control access to it.

Four roles. The Subject is the interface both share (GumballMachineRemote). The RealSubject does the actual work (GumballMachine). The Proxy implements the Subject, holds a reference to the RealSubject, or something that leads to it such as an address or a URL, and decides what happens when a method is called (GumballMachineProxy). The Client talks to the Subject and does not know, or care, which one it has (GumballMonitor).

"Control access" is deliberately broad. What the proxy controls is where, when, whether or how often the real call happens, and each answer is a named variant:

KindWhat it controlsThe exampleWhere you have seen it
Remote proxyWhere: the subject is in another process or on another hostThe gumball monitorgRPC and Thrift stubs, xmlrpc.client.ServerProxy, multiprocessing.managers proxies
Virtual proxyWhen: the subject is expensive to create and may not be needed yetThe album cover placeholderORM lazy loading, Django's SimpleLazyObject, images in a scrolling list
Protection proxyWhether: the caller's rights decide which methods go throughOwner vs non-owner profile viewsPermission wrappers around services, read-only views of a mutable object
Caching proxyHow often: repeated calls with the same arguments return a stored answerA result cache in front of a slow servicefunctools.lru_cache, HTTP caches, memoised repositories
Logging or smart-reference proxyWhat happens around the call: count, log, lock, releaseAn audit trail of every callunittest.mock.Mock recording calls, weakref.proxy, reference-counting handles
One shape, five intents. The client code is identical in every row; only the proxy's reason for existing changes.

The general shape. The client depends on the interface; the proxy both implements it and holds the real implementer. That double relationship is what makes substitution invisible.

Virtual proxy: the album cover that is not there yet

The second story is a desktop viewer for album covers fetched from the web. The obvious design holds an ImageIcon per album, and ImageIcon downloads its bytes when it is created. Open a window with ten covers and the UI thread spends several seconds inside constructors while the window stays blank.

A virtual proxy stands in for an object that is expensive to create. ImageProxy has the same paint() method as ImageIcon. While the real image does not exist, paint() draws a placeholder and, the first time only, starts the download on a background thread. When the bytes arrive the proxy creates the real ImageIcon itself and stores it; every later paint() just forwards. Two details carry the pattern:

  • The proxy creates the real subject. The view never constructs an ImageIcon; it may never see one. That is the difference from the remote proxy, which forwards to an object that already exists elsewhere.
  • The proxy behaves differently depending on its own state: nothing yet, loading, loaded. You could model the three with chapter 10's State pattern, and for a proxy with more than two or three states you should.

Each tick in the simulation is 100 ms; the download takes about 500 ms.

Painting while the image loads

Follow four threads over one second. In the first scenario the view holds an ImageProxy; in the second it holds the real ImageIcon and pays for the download on the UI thread.

stateDiagram-v2
    [*] --> NotLoaded
    NotLoaded --> Loading : paint, draw placeholder, start the loader
    Loading --> Loading : paint, draw placeholder
    Loading --> Loaded : bytes arrive, ImageIcon created
    Loaded --> Loaded : paint, delegate to ImageIcon
The same paint() call does three different things. The proxy, not the caller, tracks which one applies.

ImageProxy: same paint(), lazy ImageIcon

import threading
from urllib.request import urlopen

class ImageIcon:                                   # the real subject: expensive to create
    def __init__(self, data: bytes):
        self.data = data

    def paint(self, canvas) -> None:
        canvas.draw_image(self.data)

class ImageProxy:                                  # same paint() method; owns the loading
    def __init__(self, url: str):
        self.url = url
        self._image: ImageIcon | None = None
        self._loading = False

    def paint(self, canvas) -> None:
        if self._image is not None:                # loaded: pure forwarding from now on
            self._image.paint(canvas)
            return
        canvas.draw_text("Loading album cover...")  # the placeholder, drawn at once
        if not self._loading:                       # start the fetch exactly once
            self._loading = True
            threading.Thread(target=self._fetch, daemon=True).start()

    def _fetch(self) -> None:
        with urlopen(self.url) as response:
            data = response.read()
        self._image = ImageIcon(data)              # the real subject appears; the next paint() delegates
The None check is the whole proxy; the _loading flag is the start-once guard. If paint() can be called from several threads, protect the flag with a threading.Lock.

Protection proxy: who is asking?

The third story is a matchmaking service. A Person profile has a name, interests and a rating that other members give. Two rules: the owner may edit their interests but may not rate themselves; anyone else may rate but may not edit. Putting if caller is owner checks inside Person spreads access rules through the data model and makes every method know about callers. A protection proxy puts the rules in front of the object instead: one proxy class per kind of caller, each letting through what that caller is allowed to do.

In Java this needs java.lang.reflect.Proxy and an InvocationHandler, a proxy class built at runtime so that you do not write every forwarding method by hand. Python has the same facility built into attribute lookup: __getattr__(self, name) is called only when normal lookup fails. So you define on the proxy the methods you want to intercept, and let everything else fall through to the real object with a one-line __getattr__. The owner proxy defines rate() and raises; set_interests is not defined on it, so me.set_interests(...) falls through to the Person.

Two things __getattr__ does not see, and both bite in interviews:

  • Special methods. len(proxy), proxy == other, for x in proxy and with proxy: look up __len__, __eq__, __iter__, __enter__ on the type, bypassing __getattr__. Define the ones your subject supports.
  • Writes. proxy.interests = "x" calls __setattr__, which by default stores the value on the proxy itself, a silent hole in the guard. Add a __setattr__ that applies the same policy, as the second tab does.
flowchart TD
    A[Attribute access on the proxy] --> B{Does normal lookup find it<br/>on the proxy object?}
    B -->|yes| C[The guard method runs<br/>raise PermissionError]
    B -->|no| D[__getattr__ fires]
    D --> E[getattr on the real Person]
    E --> F[Person does the work<br/>the proxy only forwarded]
Python's lookup order is the dispatcher. Methods defined on the proxy win; everything undefined falls through.

Protection proxy in Python, two ways

The book's shape, in Python: one proxy class per role, guards as ordinary methods, __getattr__ as the forwarder. Readable when there are two or three roles.

class Person:                                   # the real subject
    def __init__(self, name: str):
        self.name = name
        self.interests = ""
        self.ratings: list[int] = []

    def set_interests(self, text: str) -> None: self.interests = text
    def rate(self, stars: int) -> None: self.ratings.append(stars)
    def rating(self) -> float: return sum(self.ratings) / len(self.ratings) if self.ratings else 0.0

class OwnerProxy:
    """The person looking at their own profile: may edit interests, may not rate themselves."""
    def __init__(self, person: Person):
        object.__setattr__(self, "_person", person)

    def rate(self, stars: int) -> None:            # found by normal lookup, so __getattr__ never runs for it
        raise PermissionError("you cannot rate yourself")

    def __getattr__(self, name: str):              # only called when normal lookup fails
        return getattr(self._person, name)         # everything else falls through to the real Person

class NonOwnerProxy:
    """Anyone else: may rate, may not edit interests."""
    def __init__(self, person: Person):
        object.__setattr__(self, "_person", person)

    def set_interests(self, text: str) -> None:
        raise PermissionError("only the owner edits interests")

    def __getattr__(self, name: str):
        return getattr(self._person, name)

joe = Person("Joe")
me, someone = OwnerProxy(joe), NonOwnerProxy(joe)
me.set_interests("bowling, go")                 # allowed: falls through to Person.set_interests
someone.rate(4)                                 # allowed: falls through to Person.rate
print(someone.name, someone.rating())           # reads fall through too: Joe 4.0
# someone.set_interests("...")  raises PermissionError before Person is ever touched

A single class driven by a set of denied names, with __setattr__ gating writes as well. Better when roles are data (loaded from a config or a database) rather than code.

# Person as in the first tab.

class ProtectionProxy:
    """One class for every role: a set of denied names decides what this caller may touch, reads and writes."""
    def __init__(self, subject, denied: frozenset[str], reason: str):
        object.__setattr__(self, "_subject", subject)   # bypass our own __setattr__ while wiring up
        object.__setattr__(self, "_denied", denied)
        object.__setattr__(self, "_reason", reason)

    def __getattr__(self, name: str):
        if name in self._denied:
            raise PermissionError(f"{name}: {self._reason}")
        return getattr(self._subject, name)

    def __setattr__(self, name: str, value) -> None:   # writes go through the same gate
        if name in self._denied:
            raise PermissionError(f"{name}: {self._reason}")
        setattr(self._subject, name, value)

def owner_view(person):
    return ProtectionProxy(person, frozenset({"rate"}), "you cannot rate yourself")

def non_owner_view(person):
    return ProtectionProxy(person, frozenset({"set_interests", "interests"}), "owner only")

# non_owner_view(joe).interests = "x"   raises: the plain-attribute write is gated too

Proxy vs Decorator (and the other wrappers)

▶ Video lesson: Proxy or Decorator? Naming the wrapper by intent 2:33 · 5 scenes · narrated, pause anytime and explore

A proxy and a decorator can be line-for-line identical: a class that implements an interface, holds an object of that interface, and forwards. The pattern is the intent, not the shape.

  • Decorator (chapter 3) adds responsibilities. Mocha(Whip(Espresso())): the client composes the chain, knows it is wrapping, and can stack as many layers as it likes. The wrapped object always exists and is passed in.
  • Proxy controls access: whether, when, where or how often the real call happens. There is usually one proxy, not a stack; the proxy often creates or owns the real subject (the virtual proxy builds the ImageIcon; the remote proxy is the connection); and the client may never see the real object at all.
  • Adapter (chapter 7) changes the interface so an existing class fits where a different one is expected.
  • Facade (chapter 7) offers a simpler interface to a whole subsystem.

The one-sentence test: if removing the wrapper would change what the client gets, it is a decorator; if it would change only how the call reaches the object (or whether it is allowed to), it is a proxy.

Interface first, then intent, then the reason the call needs controlling.

Python note

Java builds dynamic proxies with java.lang.reflect.Proxy; Python builds them with __getattr__ and gets the forwarding for free. Three shortcuts worth knowing: functools.lru_cache is a caching proxy for a function; weakref.proxy(obj) is a smart reference that forwards until the object is collected; multiprocessing.Manager().list() returns a remote proxy whose methods run in the manager process. The cost of the shortcut: isinstance(proxy, Subject) is false unless you register the proxy class or forward __class__, and special methods must be forwarded by hand.

Common mistakes

  • Treating a remote proxy like a local object. for m in machines: m.get_count() is one round trip per machine; put the same loop inside a method and you have the N+1 problem over the network. Remote calls need timeouts, retries, batching, and callers that expect exceptions. The interface hides the wire, not its cost.
  • A virtual proxy without the start-once guard. Every repaint starts another download. And if paint() can run on several threads, the check-then-set on _loading is a race: use a lock.
  • __getattr__ as the whole guard. It does not see special methods (len, ==, iteration, with) or attribute writes. A protection proxy that forgets __setattr__ lets proxy.interests = "x" write to the proxy and look like it worked.
  • Leaking the real subject. A method on the real object that returns self (fluent setters, builders) hands the caller the unproxied object, and every later call bypasses the proxy. Wrap such return values or return the proxy.
  • An unbounded skeleton. getattr(obj, name_from_the_wire)() with no allowlist lets a remote caller invoke anything, including attributes you never meant to expose. Dispatch through an explicit set of method names.
  • Calling it a decorator (or vice versa). Wrapping is the mechanism both share. Name the pattern by intent: add behaviour, or control access.

How to say it in an interview

Say: 'A proxy is a stand-in that implements the same interface as the real object, so the client does not change; the proxy decides how the call reaches it. For the gumball monitor I would put a proxy in the office process whose getters serialise the call and send it to a skeleton on the machine's host, which calls the real object and returns the result; the monitor just calls get_count(). The same shape gives a virtual proxy that shows a placeholder while an image loads on another thread, and a protection proxy that checks who the caller is. In Python I would implement the forwarding with __getattr__, remembering it does not cover special methods or writes. Proxy controls access; Decorator adds behaviour.' Then draw Client, Subject, RealSubject, Proxy.
