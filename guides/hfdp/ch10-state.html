The state of things: State

A gumball machine with four states and four actions is written the obvious way, one if-chain per action, and a fifth state forces every method open. Turning the table on its side, one class per state, gives the State pattern: the machine forwards every action to its current state object, and the state objects move the machine along. The chapter also settles who should own transitions, what adding a state costs before and after, and how State differs from Strategy when the class diagrams look identical.

After this chapter you can
  • Tell the gumball machine story: four states, four actions, and why the if-else version opens every method for a new state
  • Draw the state diagram and the State class diagram of the machine, and show where state = next is written
  • Explain the two ways to own transitions (states vs context) and when each is right
  • Add the Winner state and name exactly what changes and what does not
  • Contrast State with Strategy in one sentence, and pick between match, an Enum transition table and state classes in Python

The Gumball Machine story

▶ Video lesson: The gumball machine: why the if-chains broke, and what fixed it 5:50 · 7 scenes · narrated, pause anytime and explore

Mighty Gumball wants its next machine to run on a small CPU, so the behaviour becomes code. A customer puts in a quarter and turns the crank; a gumball rolls out; if the machine is empty, the quarter comes back. Four actions (insert quarter, eject quarter, turn crank, dispense), four states (no quarter, has quarter, sold, sold out), and one rule: every action must do the right thing in every state. Turning the crank with no coin does nothing, inserting a second coin is refused, a coin inserted into an empty machine is returned.

The first design everyone writes: a state field holding one of four constants, and one method per action whose body is an if/elif chain over the states. It works. This chapter is about what happens to it when the fifth state arrives, and about the design that survives the fifth, sixth and seventh.

One if-chain per action meets a new requirement

Build the four-state machine as a table of (action, state) cells, then add a fifth state and watch every method get opened; or add a fifth action and notice how cheap that is in comparison.

Why the if-else soup rots

The conditional version is organised by action: each method is one row of the state table. But the requirements that arrive are new states, and a state is a column that crosses every row. Each new state opens every method, rewrites the transitions that lead into it, and adds branches nobody checks for completeness: a missing elif is a silent no-op, not an error. With two or three states this is fine. With five, a prize and a refill, every change is a hunt through four methods.

Encapsulate what varies: one class per state

Chapter 1's first principle again: find what varies and pull it out. Here the thing that varies is the behaviour of the machine in each state. Each column of the table becomes its own class, NoQuarterState, HasQuarterState, SoldState, SoldOutState, and each class implements the same four methods, one per action. The machine keeps a reference to the current state object and forwards every action to it:

def insert_quarter(self):
    self.state.insert_quarter()

There is no if on the state anywhere in GumballMachine. "Which state are we in?" is answered by which object is behind self.state; "what does insert do in this state?" is answered by that object's own insert_quarter(). In the soup those two questions were the same elif.

Two things this buys. Each state's behaviour is in one place, readable top to bottom, instead of smeared across four methods. And the interface forces every state to answer every action: forget dispense() in a new state class and the ABC refuses to instantiate it, which is the completeness check the soup never had.

Who owns the transitions?

A state machine is actions plus transitions, and the design has to say who writes self.state = .... There are two honest answers.

The states decide (what this chapter's code does). HasQuarterState.turn_crank() ends with machine.state = machine.sold. The transition sits next to the behaviour that produces the data it depends on: SoldState.dispense() reads the count it has just decremented and picks no_quarter or sold_out; later, HasQuarterState.turn_crank() rolls the die and picks sold or winner. The price is coupling between states: they know one another by name, and adding a state means editing the states that lead into it.

The context decides. The states only act, and the machine holds the map, a table from (state, action) to next state. The whole machine is readable on one screen and the states are independent of each other. But a transition that depends on a result now needs the action to return that result, and the context stops being a dumb delegator.

Rule of thumb: transitions that depend on runtime data belong in the states; fixed transitions can live in a table. What hurts is a mix, half the arrows written in the states and half in the machine, because then nobody can read the state diagram back out of the code.

Where the state objects live. The machine creates one instance of each state in __init__ and keeps them as fields, so a transition is a field assignment, not an allocation, and each state can hold its machine. States that keep no per-machine data could instead be shared by every machine, taking the machine as a method argument (insert_quarter(self, machine)); Python makes either shape a few lines, so choose one and stick to it.

Pick one owner. The chapter's code lets the states decide because two of its arrows depend on data the state has just produced.

The State pattern, named

▶ Video lesson: State: the pattern behind the machine 2:50 · 5 scenes · narrated, pause anytime and explore

What the chapter built has a name:

State allows an object to alter its behavior when its internal state changes. The object will appear to change its class.

Map the words to the machine. The object is the GumballMachine; its internal state is which State object it currently holds; alter its behavior: the same turn_crank() call sells, refuses or pays a prize depending on that object; appear to change its class: from outside, the machine behaves like a SoldOutMachine one minute and a ReadyMachine the next, with a single class and no subclassing.

The roles: the Context (GumballMachine) holds the current state and the data, and delegates. The State interface declares one method per action. The concrete states (NoQuarterState and friends) implement every action and, in this chapter's version, choose the next state.

Where you have already seen it

  • A TCP socket: LISTEN, SYN-RECEIVED, ESTABLISHED, FIN-WAIT, CLOSED. What send() does, and what an incoming segment means, depends entirely on the connection's current state.
  • An order or a payment: created, authorised, captured, refunded. "Cancel" means something different in each one.
  • Media players and game characters: play, pause and stop; standing, jumping, ducking. The same button does different things depending on where you are.
  • A circuit breaker: closed, open, half-open. Each call is handled by the current state, and the states move themselves along on failure counts and timeouts.
  • Lexers, regex engines and protocol parsers: a deterministic finite automaton is a state machine where the current state decides what the next character means.
  • Python's own concurrent.futures.Future and asyncio.Future keep a small _state string and branch on it in a handful of methods: the soup, chosen on purpose, because the machine is tiny and frozen.

The gumball code, before and after

One if-chain per action

Organised by action. A fifth state is a fifth branch in every method, and a forgotten branch is silent.

from enum import Enum, auto

class S(Enum):
    NO_QUARTER = auto(); HAS_QUARTER = auto(); SOLD = auto(); SOLD_OUT = auto()

class GumballMachine:
    def __init__(self, gumballs: int):
        self.gumballs = gumballs
        self.state = S.NO_QUARTER if gumballs > 0 else S.SOLD_OUT

    def insert_quarter(self):
        if self.state is S.NO_QUARTER:
            self.state = S.HAS_QUARTER             # a transition, buried in a branch
        elif self.state is S.HAS_QUARTER:
            print("a quarter is already in the slot")
        elif self.state is S.SOLD:
            print("hold on, your gumball is on its way")
        elif self.state is S.SOLD_OUT:
            print("sold out; coin returned")

    def eject_quarter(self):
        if self.state is S.HAS_QUARTER:
            self.state = S.NO_QUARTER
        elif self.state is S.NO_QUARTER:
            print("no quarter to return")
        elif self.state is S.SOLD:
            print("too late, the crank was turned")
        elif self.state is S.SOLD_OUT:
            print("nothing to return")

    def turn_crank(self):
        if self.state is S.HAS_QUARTER:
            self.state = S.SOLD
            self.dispense()
        elif self.state is S.NO_QUARTER:
            print("insert a quarter first")
        elif self.state is S.SOLD:
            print("one turn per quarter")
        elif self.state is S.SOLD_OUT:
            print("sold out")

    def dispense(self):
        if self.state is S.SOLD:
            self.gumballs -= 1
            print("a gumball rolls out")
            self.state = S.NO_QUARTER if self.gumballs > 0 else S.SOLD_OUT
        # the other three states: nothing happens, and nothing says so

# Winner = a fifth member of S, a fifth branch in all four methods, a die roll in turn_crank.

One class per state (State)

Organised by state. The machine forwards; the state objects act and move the machine. A fifth state is a new class plus the arrow that leads into it.

from __future__ import annotations
from abc import ABC, abstractmethod


class State(ABC):
    """One class per state, one method per action."""
    def __init__(self, machine: GumballMachine):
        self.machine = machine                       # so a state can set the next state

    @abstractmethod
    def insert_quarter(self) -> None: ...
    @abstractmethod
    def eject_quarter(self) -> None: ...
    @abstractmethod
    def turn_crank(self) -> None: ...
    @abstractmethod
    def dispense(self) -> None: ...


class NoQuarterState(State):
    def insert_quarter(self): self.machine.state = self.machine.has_quarter   # the state transitions
    def eject_quarter(self): print("no quarter to return")
    def turn_crank(self): print("insert a quarter first")
    def dispense(self): pass                         # the machine's own move; nothing to give here


class HasQuarterState(State):
    def insert_quarter(self): print("a quarter is already in the slot")
    def eject_quarter(self): self.machine.state = self.machine.no_quarter
    def turn_crank(self): self.machine.state = self.machine.sold
    def dispense(self): pass


class SoldState(State):
    def insert_quarter(self): print("hold on, your gumball is on its way")
    def eject_quarter(self): print("too late, the crank was turned")
    def turn_crank(self): print("one turn per quarter")
    def dispense(self):
        m = self.machine
        m.release_ball()
        m.state = m.no_quarter if m.gumballs > 0 else m.sold_out   # data-driven transition


class SoldOutState(State):
    def insert_quarter(self): print("sold out; coin returned")
    def eject_quarter(self): print("nothing to return")
    def turn_crank(self): print("sold out")
    def dispense(self): pass


class GumballMachine:
    def __init__(self, gumballs: int):
        self.gumballs = gumballs
        self.no_quarter = NoQuarterState(self)       # one object per state, created once
        self.has_quarter = HasQuarterState(self)
        self.sold = SoldState(self)
        self.sold_out = SoldOutState(self)
        self.state: State = self.no_quarter if gumballs > 0 else self.sold_out

    # every customer action is one line of delegation: no if on the state anywhere
    def insert_quarter(self): self.state.insert_quarter()
    def eject_quarter(self): self.state.eject_quarter()
    def turn_crank(self):
        self.state.turn_crank()
        self.state.dispense()                        # asks the state we are in AFTER the turn

    def release_ball(self):
        if self.gumballs > 0:
            self.gumballs -= 1
            print("a gumball rolls out")


m = GumballMachine(2)
m.insert_quarter(); m.turn_crank()                  # a gumball rolls out
m.insert_quarter(); m.turn_crank()                  # a gumball rolls out, then SoldOutState
m.insert_quarter()                                   # sold out; coin returned

Adding the Winner state

The requirement that broke the soup: one turn in ten pays out two gumballs. In the State design it is accounting, not archaeology:

  1. One new class, WinnerState. It answers the customer's actions the way SoldState does, and its dispense() releases two balls (if two are left) before choosing the next state from the count.
  2. One changed method, HasQuarterState.turn_crank(), because the arrow into Winner has to start somewhere: it rolls the die and picks sold or winner.
  3. One new field in the machine, self.winner = WinnerState(self), and a roll() method so a test can fix the die.

NoQuarterState, SoldState, SoldOutState and the machine's four action methods are not opened. Compare the soup: four methods opened, one branch rewritten, twenty cells to re-verify by eye. That is the open-closed principle from chapter 3, delivered by the same move as chapter 1: put the varying thing behind an interface and hold a reference to it.

Honest accounting. The pattern made a new state cheap. It did not make the arrow into it free, and it makes a new action expensive: a fifth action is a fifth method on State, implemented in every state class. The soup had the opposite asymmetry (run the refill scenario in the first sim). Pick the design to match the kind of change you expect; machines grow states far more often than they grow actions, which is why this trade is usually worth it.

The whole change: one new class, one edited method, one new field

class WinnerState(State):                           # NEW: the fifth state is one new class
    def insert_quarter(self): print("hold on, your gumballs are on their way")
    def eject_quarter(self): print("too late, the crank was turned")
    def turn_crank(self): print("one turn per quarter")
    def dispense(self):
        m = self.machine
        m.release_ball()
        if m.gumballs > 0:
            m.release_ball()                        # the prize
            print("you're a winner: two gumballs")
        m.state = m.no_quarter if m.gumballs > 0 else m.sold_out


class HasQuarterState(State):                       # CHANGED: the one arrow into Winner starts here
    def insert_quarter(self): print("a quarter is already in the slot")
    def eject_quarter(self): self.machine.state = self.machine.no_quarter
    def turn_crank(self):
        m = self.machine
        lucky = m.roll() == 0 and m.gumballs > 1    # one chance in ten, and only with two balls left
        m.state = m.winner if lucky else m.sold
    def dispense(self): pass


# GumballMachine gains one field and one method; its four action methods do not change:
#     self.winner = WinnerState(self)
#     def roll(self) -> int: return random.randrange(10)   # tests override this to fix the die
WinnerState is a sibling of SoldState with a second release_ball(). The die roll lives in the state that owns the arrow, and roll() is on the machine so a test can make every customer win.

State vs Strategy, and the Python note

▶ Video lesson: State vs Strategy: same diagram, different intent 3:13 · 6 scenes · narrated, pause anytime and explore

Put the class diagram of 1 · Welcome to design patterns: Strategy next to this chapter's and they are the same drawing: a context holding a reference to an interface with several implementations. The difference is intent, and who changes the reference.

StrategyState
Who picks the current objectThe client, usually at construction, often from configurationThe states (or the context) as events happen
How often it changesRarely; often never after setupConstantly; that is the point
Do the implementations know each other?NoYes, when states own transitions
What the client sees"Configure the algorithm""Same object, different behaviour over time"
The picture that explains itA list of interchangeable algorithmsA state diagram with arrows

The test: if you find yourself drawing arrows between the implementations, you have State. If the caller could pass the implementation in from a config file and never think about it again, you have Strategy. The duck's fly_behavior was set by whoever built the duck; the gumball machine's state is set by the states themselves, and the customer never sees it.

flowchart TD
    A{Does the object's behaviour change over its lifetime?} -->|no, the caller picks once| B[Strategy: inject the algorithm]
    A -->|yes, driven by events| C{How many states, and how much behaviour per state?}
    C -->|2 or 3 states, a line each| D[A field plus if or match<br/>keep it simple]
    C -->|many states, thin behaviour| E[Enum plus a transition table<br/>the table is the diagram]
    C -->|several states, rich behaviour| F{Do transitions depend on runtime data?}
    F -->|no| G[State classes<br/>context or table owns the arrows]
    F -->|yes| H[State classes<br/>states own the arrows]
Pick the lightest shape that keeps the state diagram readable out of the code.

Idiomatic Python for machines where the arrows are the whole story and the states carry little behaviour.

from enum import Enum, auto

class S(Enum):
    NO_QUARTER = auto(); HAS_QUARTER = auto(); SOLD = auto(); SOLD_OUT = auto()

# (state, event) -> next state. A missing pair means "not allowed here".
TRANSITIONS = {
    (S.NO_QUARTER, "insert"): S.HAS_QUARTER,
    (S.HAS_QUARTER, "eject"): S.NO_QUARTER,
    (S.HAS_QUARTER, "crank"): S.SOLD,
}

class GumballMachine:
    def __init__(self, gumballs: int):
        self.gumballs = gumballs
        self.state = S.NO_QUARTER if gumballs > 0 else S.SOLD_OUT

    def handle(self, event: str) -> None:
        nxt = TRANSITIONS.get((self.state, event))
        if nxt is None:
            print(f"{event} is not allowed while {self.state.name}")
            return
        self.state = nxt
        if nxt is S.SOLD:                            # the first side-condition; watch this list grow
            self.dispense()

    def dispense(self) -> None:
        self.gumballs -= 1
        print("a gumball rolls out")
        self.state = S.NO_QUARTER if self.gumballs > 0 else S.SOLD_OUT

# The table IS the state diagram, and a test can assert every arrow in one loop.
# Right when transitions are the whole story; wrong once each state needs real behaviour per event.

Python 3.10+ structural pattern matching: a cleaner if-chain, the same design. Fine for two or three states that will not grow.

from enum import Enum, auto

class S(Enum):
    NO_QUARTER = auto(); HAS_QUARTER = auto(); SOLD = auto(); SOLD_OUT = auto()

class GumballMachine:
    def __init__(self, gumballs: int):
        self.gumballs = gumballs
        self.state = S.NO_QUARTER if gumballs > 0 else S.SOLD_OUT

    def insert_quarter(self) -> None:
        match self.state:                            # Python 3.10+: a tidier if/elif, same design
            case S.NO_QUARTER:
                self.state = S.HAS_QUARTER
            case S.HAS_QUARTER:
                print("a quarter is already in the slot")
            case S.SOLD:
                print("hold on, your gumball is on its way")
            case S.SOLD_OUT:
                print("sold out; coin returned")

# Fine for two or three states that will not grow. A new state still touches every method,
# and match does not warn you about a state you forgot to list.

Python note

Python gives you three shapes for a state machine. A field plus match for two or three states that will not grow. An Enum with a transition table (dict[(state, event)] -> next) when the arrows are the whole story and the states have no behaviour of their own: the table is the diagram and is trivial to test and to draw. State classes when each state has real behaviour per action and the arrows depend on data. A dozen if branches across four methods is the soup; four classes for a two-state flag is ceremony.

Common mistakes

  • The machine still decides. if isinstance(self.state, SoldState): ... inside GumballMachine puts the conditional back where it was removed from. The context forwards; it does not inspect.
  • Half-owned transitions. Some arrows written in the states, some in the machine. Nobody can read the state diagram out of the code any more. Choose one owner.
  • Silent "unsupported" defaults. A base class whose every method is pass lets a forgotten action vanish without a trace, which is exactly the bug the pattern was meant to catch. Use abstract methods, or a default that raises or logs.
  • States hoarding context data. A state that keeps its own copy of the gumball count drifts from the machine's. States read and write the machine's data through the machine.
  • State classes for a boolean. Two states, one line each: use a field. The pattern pays from three or four states with behaviour.
  • Allocating a fresh state object per transition. Fine for stateless states, but then they cannot hold machine. Decide once: per-machine instances that hold the machine, or shared instances that receive it as an argument.
  • Calling it Strategy. Same diagram. If the objects set the next object, it is State.

How to say it in an interview

Say: 'A gumball machine has four states and four actions. The first version had one method per action with an if-chain over the states, so adding a fifth state meant opening every method and rewriting the branch that leads into it. I would make each state its own class behind one interface with the four actions, hold the current state object in the machine and forward every action to it. The state objects decide the transitions, so adding the Winner state is one new class plus the one arrow into it. That is the State pattern: same diagram as Strategy, but the states drive their own changes, while a strategy is chosen by the client.' Then draw the state diagram and the class diagram side by side.
