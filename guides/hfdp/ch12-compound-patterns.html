Patterns of patterns: compound patterns and MVC

The duck simulator comes back with four new requirements, and each one is answered by a pattern from an earlier chapter: Adapter, Decorator, Abstract Factory, Composite, Observer, five patterns in one design with no duck class edited. Then the best-known compound pattern, Model-View-Controller, taken apart into the Observer, Composite and Strategy inside it, and rebuilt in Python.

After this chapter you can
  • Explain what makes a set of patterns a compound pattern, and what does not
  • Say which requirement in the duck simulator called for which pattern, and why the alternatives were worse
  • Show how Decorator and Composite must forward register() so Observer works through the wrappers
  • Name the three patterns inside MVC and point to each in a class diagram and a sequence diagram
  • Write a small MVC application in Python where the model, view and controller can each be replaced alone
  • Explain why a view can be reused for a different model through an adapter and a different controller

The duck simulator, round two

▶ Video lesson: Ducks revisited: five patterns, one requirement each 5:44 · 6 scenes · narrated, pause anytime and explore

Eleven chapters in, the patterns have been shown one at a time. Real designs rarely contain one. A compound pattern is a set of patterns that work together in one design to solve a problem that recurs: not any design that happens to use several patterns, but a combination that has become a known shape of its own. Model-View-Controller is the famous one; the duck simulator is the warm-up that shows how patterns combine.

The simulator from chapter 1 has settled down. Every duck implements a Quackable interface with one method, quack(), and the simulator keeps a list of Quackables and asks each one to quack. Then four requirements land, one after another: a goose must join the pond; the quackologists want quacks counted; ducks must be managed in flocks; and the quackologist wants to be told about each quack as it happens. Each requirement is answered by one pattern, and none of them edits a duck class.

Five requirements, five patterns

Build the simulator one requirement at a time, then follow a single pond.quack() through every layer of the finished design.

How compounds form

Each pattern here answers a requirement that arrived on its own. Nobody sat down to 'use five patterns'. When you read a design with many patterns in it, ask for each one which requirement it serves; a pattern with no requirement behind it is weight, not design.

Five patterns, one requirement each

Adapter: a goose in the pond

Goose has honk(). The simulator calls quack(). The behaviour is right and the interface is wrong, which is exactly the Adapter's job (chapter 7): GooseAdapter implements Quackable, holds a Goose, and its quack() calls goose.honk(). The simulator holds one more Quackable. Nothing in the goose's library changed, and nothing in the simulator changed either.

        <<interface>>
        +quack()
    }

        +honk()
    }
    class GooseAdapter {
        -goose: Goose
        +quack()
    }
    Simulator --> Quackable : calls quack on each
    Quackable <|.. GooseAdapter

The adapter sits between two interfaces that do not match. The simulator keeps talking Quackable; the goose keeps honking.

Adapter: GooseAdapter

from typing import Protocol

class Quackable(Protocol):
    def quack(self) -> None: ...

class MallardDuck:
    def quack(self) -> None: print("Quack")

class Goose:                              # from another library: right behaviour, wrong interface
    def honk(self) -> None: print("Honk")

class GooseAdapter:                       # Adapter: is a Quackable, holds a Goose
    def __init__(self, goose: Goose):
        self.goose = goose
    def quack(self) -> None:
        self.goose.honk()                 # translate the call, nothing more

pond: list[Quackable] = [MallardDuck(), GooseAdapter(Goose())]
for q in pond:
    q.quack()                             # Quack, Honk: the loop never learns which is which
A Protocol is enough for the Quackable role: anything with quack() qualifies, including the adapter.

Decorator: counting quacks

Counting could be added to each duck class, which means editing all of them and the goose's class, which is not ours. Instead, QuackCounter is a Quackable that wraps a Quackable (chapter 3): its quack() adds one to a shared count and delegates to the object inside. Because the counter has the same interface as what it wraps, the simulator holds counters without knowing, and a counter can wrap an adapter as easily as a duck.

    class GooseAdapter {

    Quackable <|.. MallardDuck

The decorator is-a Quackable and has-a Quackable. Both arrows point at the same interface; that is what lets counters stack on anything, adapters included.

Decorator: QuackCounter

class QuackCounter:
    """Decorator: a Quackable that wraps a Quackable. Count, then delegate."""
    count = 0                                   # shared by every counter in the session

    def __init__(self, inner: Quackable):
        self.inner = inner

    def quack(self) -> None:
        QuackCounter.count += 1
        self.inner.quack()                      # the wrapped object does the real work

ducks = [QuackCounter(MallardDuck()), QuackCounter(GooseAdapter(Goose()))]
for d in ducks:
    d.quack()
print(QuackCounter.count)                       # 2, and no duck class was edited
count is class-level state shared by all counters, the simplest version of the book's static field. Inject a tally object instead when tests need isolation.

Abstract Factory: who does the wrapping?

Wrapping is a creation-time decision, and creation happens wherever someone writes MallardDuck(). One forgotten counter and the total is silently wrong. The fix (chapter 4) is to take new away from the simulator: it receives an AbstractDuckFactory and asks it for ducks. CountingDuckFactory returns every duck already wrapped; DuckFactory returns plain ducks. The simulator's code is identical in both cases, which is the dependency inversion principle doing its work: the simulator depends on the abstract factory, never on a duck class.

Abstract Factory: CountingDuckFactory

from abc import ABC, abstractmethod

class AbstractDuckFactory(ABC):
    @abstractmethod
    def create_mallard(self) -> Quackable: ...
    @abstractmethod
    def create_redhead(self) -> Quackable: ...
    @abstractmethod
    def create_rubber_duck(self) -> Quackable: ...

class DuckFactory(AbstractDuckFactory):            # plain ducks
    def create_mallard(self): return MallardDuck()
    def create_redhead(self): return RedheadDuck()
    def create_rubber_duck(self): return RubberDuck()

class CountingDuckFactory(AbstractDuckFactory):    # every duck leaves already wrapped
    def create_mallard(self): return QuackCounter(MallardDuck())
    def create_redhead(self): return QuackCounter(RedheadDuck())
    def create_rubber_duck(self): return QuackCounter(RubberDuck())

def simulate(factory: AbstractDuckFactory) -> None:
    ducks = [factory.create_mallard(), factory.create_redhead(), factory.create_rubber_duck()]
    for d in ducks:                                 # not one constructor call in the simulator
        d.quack()

simulate(CountingDuckFactory())                    # counted
simulate(DuckFactory())                            # same simulator, nothing counted
Pass a different factory and the whole family of products changes; the simulator does not.

Composite: a flock quacks as one

The simulator should treat a group of ducks as a single duck, and allow groups inside groups. Flock implements Quackable and holds a list of Quackables (chapter 9); its quack() calls quack() on each member. A member can be a duck, a counter around a duck, an adapter, or another Flock: the loop does not care, and nesting is recursion for free. The simulator ends up holding one object, the pond, and calling quack() once.

classDiagram
    class Quackable {
        <<interface>>
        +quack()
    }
    class Flock {
        -members: list
        +add(q)
        +quack()
    }
    class MallardDuck {
        +quack()
    }
    class QuackCounter {
        +quack()
    }
    Quackable <|.. Flock
    Quackable <|.. MallardDuck
    Quackable <|.. QuackCounter
    Flock o--> Quackable : members, leaves or flocks
The composite's members are typed as the interface, so a flock can hold another flock. Leaves and composites are treated the same by whoever calls quack().

Composite: Flock

class Flock:
    """Composite: a group of Quackables that is itself a Quackable."""
    def __init__(self):
        self.members: list[Quackable] = []

    def add(self, q: Quackable) -> None:
        self.members.append(q)

    def quack(self) -> None:
        for m in self.members:                 # a leaf quacks; a sub-flock recurses
            m.quack()

factory = CountingDuckFactory()
mallards = Flock()
for _ in range(4):
    mallards.add(factory.create_mallard())

pond = Flock()
pond.add(factory.create_redhead())
pond.add(QuackCounter(GooseAdapter(Goose())))      # adapter inside a decorator inside a composite
pond.add(mallards)                                 # a flock inside a flock
pond.quack()                                       # one call, six quacks, QuackCounter.count == 6
Six quacks from one call: one redhead, one adapted goose, and a nested flock of four mallards.

Observer: a quackologist on watch

The quackologist wants to hear about each quack as it happens, not read a total later. Each leaf Quackable becomes a subject (chapter 2): it owns a small Subject helper that keeps the observer list, and it calls notify() after it quacks. register(observer) is added to the Quackable interface. That last step has a consequence for the wrappers: Flock must forward register() to every member, and QuackCounter must forward it to the object it wraps. Otherwise pond.register(quackologist) registers on the flock object and no duck ever notifies anyone.

The Observer bookkeeping lives in one helper class that every leaf owns, so the duck classes gain two one-line methods instead of a copy of the list management.

Observer: Subject, Quackologist, and the forwarding wrappers

class Observer(Protocol):
    def update(self, duck: object) -> None: ...

class Subject:
    """Observer bookkeeping, written once and owned by every leaf Quackable."""
    def __init__(self, owner):
        self.owner = owner
        self.observers: list[Observer] = []
    def register(self, o: Observer) -> None:
        self.observers.append(o)
    def notify(self) -> None:
        for o in self.observers:
            o.update(self.owner)                   # the leaf, not any wrapper around it

class MallardDuck:
    def __init__(self):
        self.subject = Subject(self)
    def quack(self) -> None:
        print("Quack")
        self.subject.notify()                      # tell whoever is watching
    def register(self, o: Observer) -> None:
        self.subject.register(o)

class Quackologist:
    def update(self, duck) -> None:
        print(f"Quackologist: {type(duck).__name__} just quacked")

class Flock:                                       # the composite forwards registration...
    ...
    def register(self, o: Observer) -> None:
        for m in self.members:
            m.register(o)

class QuackCounter:                                # ...and so does the decorator
    ...
    def register(self, o: Observer) -> None:
        self.inner.register(o)

pond.register(Quackologist())                      # reaches every leaf through flock and counters
pond.quack()
The leaf notifies with itself as the argument, so the observer sees MallardDuck, never the counter.

The whole compound

Put the five together and the interesting part is not any single pattern but how they lean on each other:

  • Everything is a Quackable. Adapter, Decorator and Composite each implement the same interface they consume. That one fact is what lets them stack in any combination: a counter around an adapter inside a flock inside a flock.
  • The wrappers forward what they do not own. QuackCounter forwards quack() and register(); Flock forwards both to every member. A decorator or composite that forgets a method of the interface breaks the pattern that needs it, silently.
  • The factory makes the wrapping reliable. Decorators only work if every object is wrapped; Abstract Factory is the only place that creates leaves, so the decision is made once.
  • The leaf is the subject. Observers register through the wrappers but are notified by the duck itself, so they see what actually quacked.

Model-View-Controller

▶ Video lesson: MVC: three patterns in one 4:23 · 6 scenes · narrated, pause anytime and explore

MVC is the compound pattern everyone has heard of and few can take apart. It splits an interactive program into three parts with fixed responsibilities:

  • the model holds the state and the rules for changing it, and knows nothing about how it is displayed;
  • the view draws the model's state and reports user gestures (a click, a key) without interpreting them;
  • the controller interprets those gestures: it decides what a click means, updates the model, and may tell the view which controls to enable.

The example is a DJ tool: a beat model with a tempo in beats per minute (BPM) and a running beat, a view with a BPM label, a pulsing beat bar and start/stop/+/- buttons, and a controller behind the buttons.

Three patterns are inside:

  1. Observer. The model is a subject. The view registers as a BPM observer and a beat observer and is told when the tempo changes or a beat fires. The model never imports a view.
  2. Composite. The view is a tree of widgets: a window containing a label, a bar and buttons. Redrawing the top node redraws the tree, which is Composite at work.
  3. Strategy. The controller is the view's strategy for handling user actions. The view holds a reference typed as the controller interface and forwards; swap the controller and the same view behaves differently.

A click, and then a reuse

First the DJ view: press + and follow the change around the loop. Then the same view is reused for a heart monitor without editing it.

MVC in Python, and in the wild

The book's MVC has an interface for everything: the model, the controller, each observer kind. Python needs fewer names. Observers are callables, so the model's observer list is a list[Callable[[], None]] and a view subscribes a bound method. The controller interface can be a Protocol or simply a documented set of method names. The composite view is whatever widget tree the toolkit gives you (tkinter widgets already form one).

What does not change is the direction of knowledge: the model imports no GUI module, the view never writes to the model, and the controller is the only object that holds both.

MVC in Python, three ways

Explicit interfaces for model and controller. Worth it when several views or several controllers must plug into the same model, as with the heart monitor.

from abc import ABC, abstractmethod

class BeatModelInterface(ABC):                 # what views and controllers may ask of a model
    @abstractmethod
    def on(self) -> None: ...
    @abstractmethod
    def off(self) -> None: ...
    @abstractmethod
    def set_bpm(self, bpm: int) -> None: ...
    @abstractmethod
    def get_bpm(self) -> int: ...
    @abstractmethod
    def register_bpm_observer(self, o) -> None: ...
    @abstractmethod
    def register_beat_observer(self, o) -> None: ...

class ControllerInterface(ABC):                # what a view may ask of its controller
    @abstractmethod
    def start(self) -> None: ...
    @abstractmethod
    def stop(self) -> None: ...
    @abstractmethod
    def increase_bpm(self) -> None: ...
    @abstractmethod
    def decrease_bpm(self) -> None: ...

class BeatController(ControllerInterface):
    def __init__(self, model: BeatModelInterface, make_view):
        self.model = model
        self.view = make_view(self, model)     # the controller builds the view and hands it both
        self.view.disable_stop_button()
    def start(self):
        self.model.on()
        self.view.disable_start_button()
        self.view.enable_stop_button()
    def stop(self):
        self.model.off()
        self.view.enable_start_button()
        self.view.disable_stop_button()
    def increase_bpm(self):
        self.model.set_bpm(self.model.get_bpm() + 1)
    def decrease_bpm(self):
        self.model.set_bpm(self.model.get_bpm() - 1)

Callables as observers, a dataclass model, a bound method as the view's subscription. tkinter control variables (IntVar, StringVar) are an observable scalar with trace_add.

from dataclasses import dataclass, field
from typing import Callable

@dataclass
class BeatModel:                               # Model: state plus two observer lists
    bpm: int = 90
    running: bool = False
    _on_bpm: list[Callable[[], None]] = field(default_factory=list)
    _on_beat: list[Callable[[], None]] = field(default_factory=list)

    def subscribe_bpm(self, fn): self._on_bpm.append(fn)
    def subscribe_beat(self, fn): self._on_beat.append(fn)

    def set_bpm(self, bpm: int) -> None:
        self.bpm = bpm
        for fn in self._on_bpm: fn()           # observers are plain callables

    def tick(self) -> None:                    # a timer calls this every 60 / bpm seconds
        for fn in self._on_beat: fn()

class BeatView:
    def __init__(self, model: BeatModel, controller):
        self.model, self.controller = model, controller
        model.subscribe_bpm(self.show_bpm)     # a bound method is the observer
        model.subscribe_beat(self.pulse)
    def show_bpm(self): print(f"{self.model.bpm} BPM")      # pull the state
    def pulse(self): print("*")
    def plus_clicked(self): self.controller.increase_bpm()  # forward, decide nothing

# tkinter ships an observable scalar: a control variable notifies on every write
# bpm_var = tk.IntVar(value=90)
# bpm_var.trace_add("write", lambda *_: label.config(text=f"{bpm_var.get()} BPM"))
  • Django calls the same split MTV: its Model is the model, its Template is the view, and the function or class it calls a 'view' plays the controller (the request handler). Django signals (post_save) are Observer.
  • Rails, Spring MVC, ASP.NET MVC keep the classic names: a controller action loads models and renders a view.
  • React with a store (Redux, Zustand): the component tree is a Composite view, store subscriptions are Observer, and reducers or action handlers are the controller strategy. Components re-render by pulling from the store.
  • Qt separates QAbstractItemModel from QListView/QTableView, with signals and slots as the Observer channel.
  • tkinter: IntVar.trace_add("write", callback) is a model notifying a view with no framework at all.

A counter app, before and after MVC

Everything in the button handler

State, policy and drawing in one function. A second display, a test without a window, or a rule change all mean editing the handler.

import tkinter as tk

root = tk.Tk()
count = 0
label = tk.Label(root, text="0")

def on_click():
    global count
    count += 1                                 # state change...
    label.config(text=str(count))              # ...screen update...
    if count >= 10:
        button.config(state="disabled")        # ...and policy, all in the button handler

button = tk.Button(root, text="+1", command=on_click)
label.pack()
button.pack()
root.mainloop()

Model, view, controller

The model can be unit-tested with no Tk at all; a second view subscribes with one line; the limit of 10 is the controller's business and nobody else's.

import tkinter as tk

class CounterModel:                            # Model: state, and an Observer subject
    def __init__(self):
        self.value = 0
        self._observers = []
    def subscribe(self, fn): self._observers.append(fn)
    def increment(self):
        self.value += 1
        for fn in self._observers: fn()        # tell the views; know nothing about them

class CounterController:                       # Controller: what a click means (Strategy)
    def __init__(self, model, view):
        self.model, self.view = model, view
    def plus_clicked(self):
        if self.model.value < 10:
            self.model.increment()
        if self.model.value >= 10:
            self.view.disable_plus()

class CounterView:                             # View: a widget tree that draws the model
    def __init__(self, root, model):
        self.model = model
        self.label = tk.Label(root, text="0")
        self.button = tk.Button(root, text="+1")
        self.label.pack(); self.button.pack()
        model.subscribe(self.refresh)          # the view observes the model
    def set_controller(self, c): self.button.config(command=c.plus_clicked)
    def refresh(self): self.label.config(text=str(self.model.value))   # pull
    def disable_plus(self): self.button.config(state="disabled")

root = tk.Tk()
model = CounterModel()
view = CounterView(root, model)
view.set_controller(CounterController(model, view))
root.mainloop()

Compound patterns you already use

MVC is not the only compound in everyday code. Several standard-library designs are small compounds of the same patterns the duck simulator used.

Common mistakes

  • Pattern fever. Five patterns in one design is not the goal; five requirements each answered as cheaply as possible is. A compound pattern is a recurring combination that solves a recurring problem (interactive apps with state shown in several places, for MVC). Several patterns that happen to share a file are not a compound.
  • Wrappers that forget to forward. The decorator and the composite must implement every method of the interface, including the ones added later. QuackCounter without register() compiles fine in Python and silently disconnects every observer behind it.
  • Wrapping in the wrong order. QuackCounter(GooseAdapter(Goose())) works because the counter wraps a Quackable. GooseAdapter(QuackCounter(...)) does not: the adapter expects a Goose. Order is free only when the types match.
  • Global counters. QuackCounter.count is shared state across the whole process. Fine for a demo; in real code pass a tally object through the factory so tests can isolate it.
  • The view that writes to the model. A button handler that calls model.set_bpm() directly has made the view a controller. Add a second view and the rule now lives in two places.
  • The controller that draws. If the controller sets label text, the model's other observers never see the change. The controller updates the model and lets the notification do the drawing.
  • The model that imports the toolkit. The moment BeatModel imports tkinter, it cannot be tested headless or reused for a web page.
  • Arguing about Django's names. Django's 'view' is a controller by this chapter's vocabulary. The roles are what matter; the names vary by framework.
flowchart TD
    Q{What did the requirement change?} -->|a class with the wrong interface must join| AD[Adapter<br/>translate the interface]

The requirement names the pattern. Read the chapter's four requirements down the left and the simulator's five patterns fall out; the last branch is the compound.

How to say it in an interview

Say: 'A compound pattern is a set of patterns that work together to solve a recurring problem; MVC is the classic one. The model is an Observer subject that knows nothing about displays; the view is a Composite of widgets that observes the model and pulls state; the controller is the view's Strategy, the one object that interprets user actions and updates the model. The payoff is that each part can be replaced alone: the duck simulator shows the same idea, where Adapter, Decorator, Abstract Factory, Composite and Observer were each added for one requirement without editing a duck class.' Then draw the model-view-controller triangle with the three arrows: view reads model, view forwards to controller, controller updates model.
