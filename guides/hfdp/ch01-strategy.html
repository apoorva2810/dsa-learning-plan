Welcome to design patterns: Strategy

A duck simulator gets a new requirement, inheritance does the wrong thing twice, and the fix teaches the three principles that run through the whole book: separate what varies, program to an interface, favour composition over inheritance. The result is the Strategy pattern.

After this chapter you can
  • Explain, with the duck story, why adding behaviour to a superclass is a maintenance trap
  • State the three design principles of chapter 1 and point to where each one appears in the fixed design
  • Draw the Strategy class diagram (context, interface, concrete strategies) and translate it to Python
  • Tell when a plain function is strategy enough in Python, and when a class is worth it
  • Explain HAS-A vs IS-A, and what 'program to an interface, not an implementation' buys you

The SimUDuck story

▶ Video lesson: The duck story: why inheritance broke, and what fixed it 5:07 · 7 scenes · narrated, pause anytime and explore

Joe works on SimUDuck, a pond simulator. It has a Duck superclass with quack(), swim() and an abstract display(), and a subclass for each kind of duck. The executives want the ducks to fly. Joe adds fly() to Duck, every duck inherits it, and the rubber duck flies across the screen at the demo.

This chapter is the book's opening act because the mistake is so natural: flying is a duck thing, put it on Duck. Watch what each repair costs, and notice that the problem is never the code, it is where the behaviour lives.

Inheritance meets a new requirement

Step through the first requirement (fly) and its patches, then the second wave (runtime changes) that no amount of overriding can absorb.

    class RedheadDuck { +display() }

    }
    class DecoyDuck {
        +quack() do nothing
        +display()
        +fly() do nothing
    }
    Duck <|-- MallardDuck
    Duck <|-- RedheadDuck
    Duck <|-- RubberDuck
    Duck <|-- DecoyDuck
The inheritance version after the patches. Count the methods whose whole body is 'do nothing': each one is a subclass fighting its parent.

Why both repairs fail

Inheritance shares code, but it shares it with every subclass forever. The moment one subclass needs to not have a behaviour, you are writing overrides whose only job is to cancel the parent. Interfaces without a shared implementation fix the accident and lose the reuse. Neither moves the behaviour out of the class.

Principle 1: separate what varies

Look at the duck classes and sort their contents into two piles: what is the same for every duck (swimming, having a display) and what varies between ducks and over time (how they fly, how they quack).

Identify the aspects of your application that vary and separate them from what stays the same.

Flying and quacking get pulled out into their own families of classes. The rest of Duck stays where it is. Taking the varying parts out means a later change to flying touches the fly classes and nothing else.

Two behaviour families (left and right) that vary, and the Duck hierarchy in the middle that does not. Follow the highlight: the varying parts, then the interfaces the duck talks to, then the delegation.

Principle 2: program to an interface, not an implementation

Duck declares fly_behavior: FlyBehavior, the supertype, not fly_behavior: FlyWithWings. That one choice is what makes the swap possible: the code that uses the behaviour is written against a promise (fly() exists), not against a particular implementation.

"Interface" here means the idea, not a keyword. In Python the promise can be an ABC, a Protocol, or simply "anything callable". What matters is that Duck never names a concrete behaviour class.

Setting behaviour dynamically

Because the behaviour is a field, it can be assigned after construction. A duck can change how it flies mid-simulation (injured, upgraded, repaired). No class hierarchy can express "this particular duck now flies differently"; a reference can.

Swap behaviours on a live duck

A ModelDuck is created grounded and silent-capable; watch its behaviours get replaced while it runs.

The duck code, before and after

Behaviour inherited (and cancelled)

Every new duck re-audits every inherited method. Behaviour is fixed per class at compile time.

class Duck:
    def quack(self): print("Quack")
    def swim(self): print("All ducks float")
    def fly(self): print("I'm flying")        # added for the new requirement
    def display(self): raise NotImplementedError

class RubberDuck(Duck):
    def quack(self): print("Squeak")
    def fly(self): pass                        # override to cancel the inherited flight

class DecoyDuck(Duck):
    def quack(self): pass                      # cancel
    def fly(self): pass                        # cancel
    def display(self): print("decoy")

Behaviour composed (Strategy)

Duck delegates to whatever behaviour object it holds. New behaviour = new small class; changing a duck = assigning a field.

from abc import ABC, abstractmethod

class FlyBehavior(ABC):
    @abstractmethod
    def fly(self) -> None: ...

class FlyWithWings(FlyBehavior):
    def fly(self): print("I'm flying!")

class FlyNoWay(FlyBehavior):
    def fly(self): print("I can't fly")

class QuackBehavior(ABC):
    @abstractmethod
    def quack(self) -> None: ...

class Quack(QuackBehavior):
    def quack(self): print("Quack")

class MuteQuack(QuackBehavior):
    def quack(self): print("<< silence >>")

class Duck(ABC):
    def __init__(self, fly_behavior: FlyBehavior, quack_behavior: QuackBehavior):
        self.fly_behavior = fly_behavior        # composition: Duck HAS-A behaviour
        self.quack_behavior = quack_behavior

    def perform_fly(self): self.fly_behavior.fly()          # delegate
    def perform_quack(self): self.quack_behavior.quack()
    def swim(self): print("All ducks float, even decoys")

    @abstractmethod
    def display(self) -> None: ...

class ModelDuck(Duck):
    def __init__(self):
        super().__init__(FlyNoWay(), Quack())
    def display(self): print("I'm a model duck")

duck = ModelDuck()
duck.perform_fly()                     # I can't fly
duck.fly_behavior = FlyWithWings()     # change behaviour at runtime
duck.perform_fly()                     # I'm flying!

Principle 3: favour composition over inheritance

IS-A (inheritance): a MallardDuck is a Duck. Reasonable, and still used for the part that does not vary.

HAS-A (composition): a Duck has a FlyBehavior. The duck is assembled from parts, and the parts can be chosen at construction and replaced later.

Composition gives you three things inheritance cannot:

  1. Runtime change. Reassign a field; the object behaves differently from the next call.
  2. Independent variation. Flying and quacking are separate families; 3 + 3 classes cover 3 x 3 combinations. With subclassing, each combination is a class, and the count multiplies.
  3. No accidental sharing. A behaviour reaches only the objects that hold it. Nothing flies by surprise.

The cost: more objects, and one extra hop (perform_fly -> fly_behavior.fly) to follow when reading code. That hop is the price of being able to change the behaviour without touching the duck.

QuestionInheritance (IS-A)Composition (HAS-A)
Where does the behaviour live?In the class hierarchyIn separate objects the class holds
Can one object change behaviour at runtime?NoYes: assign a different object
Adding a variant meansA new subclass (or an override everywhere)One new small class
Two independent behaviour familiesSubclass count multipliesClass counts add
Reading the codeDirect; look up the hierarchyOne delegation hop to follow
Use inheritance for what genuinely does not vary (every duck swims); compose the rest.

The Strategy pattern, named

▶ Video lesson: Strategy: the pattern behind the ducks 1:48 · 4 scenes · narrated, pause anytime and explore

What the chapter built has a name:

Strategy defines a family of algorithms, encapsulates each one, and makes them interchangeable. Strategy lets the algorithm vary independently from the clients that use it.

Map the words to the ducks: the family of algorithms is the fly behaviours; encapsulates each one is one class per behaviour; interchangeable is the shared FlyBehavior interface; the client is Duck, which never changes when a new algorithm arrives.

Where you have already seen it

  • sorted(items, key=...): the key function is a strategy for comparing.
  • A payment gateway chosen per order (StripeGateway, PayPalGateway) behind one charge() method.
  • Compression (gzip, zstd) or serialization (json, msgpack) chosen by configuration.
  • Discount rules in a checkout, retry policies in an HTTP client, routing policies in a load balancer.

The general shape. Duck is the Context; FlyBehavior is the Strategy; FlyWithWings and friends are the concrete strategies.

Strategy in Python, two ways

The book's shape, in Python. Use it when a behaviour carries state or several methods.

Idiomatic Python for single-method strategies: pass a callable.

# In Python a behaviour can be any callable: a function is a one-method strategy.
from dataclasses import dataclass
from typing import Callable

def fly_with_wings() -> str: return "I'm flying!"
def fly_no_way() -> str: return "I can't fly"
def quack() -> str: return "Quack"
def squeak() -> str: return "Squeak"

@dataclass
class Duck:
    name: str
    fly: Callable[[], str]
    quack: Callable[[], str]

mallard = Duck("mallard", fly_with_wings, quack)
rubber = Duck("rubber", fly_no_way, squeak)
rubber.fly = fly_with_wings            # still swappable at runtime
print(mallard.fly(), rubber.quack())   # I'm flying! Squeak

# Reach for classes (ABC + subclasses) when a behaviour needs state or several methods,
# e.g. FlyRocketPowered that tracks remaining fuel.
flowchart TD
    A{Does the behaviour vary between objects or over time?} -->|no| B[Plain method on the class]
    A -->|yes| C{Does one object need to change it at runtime?}
    C -->|no, fixed per kind| D[Subclass per kind is acceptable<br/>if there is one varying axis]
    C -->|yes| E{Does the behaviour need state or several methods?}
    E -->|no| F[Pass a callable<br/>sorted key=, on_error=]
    E -->|yes| G[Strategy classes behind an interface<br/>held by the context]
Pick the lightest tool that still lets the behaviour change where it needs to.

Python note

In Python, functions are objects, so a one-method strategy interface is usually just a callable parameter (key=, on_error=). Promote to a class when the strategy has configuration or state (FlyRocketPowered(fuel=3)), needs several related methods, or when naming the family helps the reader.

Common mistakes

  • Strategy everywhere. If the behaviour never varies, a method is fine. The pattern earns its hop when you have (or confidently expect) more than one implementation or runtime switching.
  • Leaking the concrete type. if isinstance(self.fly_behavior, FlyRocketPowered): ... inside Duck puts the knowledge back where it was removed from. The duck should only call fly().
  • Strategies that reach into the context. If every strategy needs five fields of the duck, pass what it needs as arguments (fly(self, speed)) rather than handing it the whole duck; otherwise the two are coupled again.
  • Confusing it with State. Same shape (context + interchangeable objects). Strategy: the client chooses the object, usually once. State: the objects themselves drive transitions as the context's lifecycle unfolds (chapter 10).

How to say it in an interview

Say: 'The duck simulator put behaviour in the superclass, so every subclass inherited flying, including rubber ducks. I would pull out what varies, flying and quacking, into behaviour interfaces, have Duck hold one of each and delegate to it. Then a new kind of flight is one new class, and a single duck can change behaviour at runtime by reassigning the field. That is Strategy, and it follows composition over inheritance.' Then draw the three-part class diagram.
