Encapsulating invocation: Command

A home-automation remote has seven programmable slots and an undo button, and the devices it must drive share nothing but a power cord. The fix is to turn each request into an object with one method, which separates the thing that asks from the thing that does. That object is a Command, and once a request is an object you can store it in a slot, stack it for undo, bundle it into a macro, queue it for a worker or write it to a log and replay it.

After this chapter you can
  • Explain, with the remote-control story, why an invoker that names its receivers cannot be re-programmed or extended
  • Name the five Command roles (client, invoker, command, concrete command, receiver) and map each to the remote
  • Write a command with execute and undo, including undo that restores saved state rather than applying an inverse
  • Use the NoCommand null object and explain what special case it removes
  • Build a MacroCommand and say why its undo runs in reverse
  • Choose between a Command class and a Python callable or closure, and say what queues and logs get from command objects

The remote with seven slots

▶ Video lesson: The remote-control story: a request becomes an object 4:41 · 6 scenes · narrated, pause anytime and explore

A home-automation company sends a remote control and a request: make it work. The remote has seven slots, each with an on and an off button, and one global undo button. Alongside it come the vendor classes for the devices customers own: Light, Stereo, CeilingFan, GarageDoor, Hottub, TV, Sprinkler. Nobody designed those classes to be driven by a remote. The light has on() and off(); the stereo has on(), set_cd(), set_volume(); the fan has high(), medium(), low(), off(); the garage door has up(), down(), stop(). More vendors will ship more classes later.

The obvious first design puts the knowledge in the remote: a method per button with an `if slot == 0: ... elif slot == 1: ...` chain that calls the right vendor method. Watch what each new requirement does to it.

The remote learns every device

Why the if-chain fails

The remote has two jobs mixed together: noticing a press (the same for every slot, forever) and doing what the press means (different per device, and changeable by the customer). Everything that goes wrong, editing the remote for each vendor, no re-programming, no undo, comes from the second job living inside the first.

The idea: a request is an object

Think of a diner. You tell the waiter what you want; the waiter writes an order slip and drops it on the counter; the cook picks it up and makes the food. The waiter never cooks and the cook never takes orders. The slip is what makes that split work: it carries the whole request, the waiter can hold it, queue it, or hand it to a different cook, and the cook reads it without ever meeting you.

Decouple the object that issues a request from the object that knows how to perform it, by putting the request itself into an object.

For the remote: each slot holds an object with one method, execute(). Pressing the button calls that method and nothing else. What execute() does, which device it talks to and how many vendor calls it makes, is the object's business. The remote goes from knowing every device to knowing one method name.

The Command pattern, named

▶ Video lesson: Command, named: execute, history, undo 3:38 · 5 scenes · narrated, pause anytime and explore

Command encapsulates a request as an object, thereby letting you parameterize other objects with different requests, queue or log requests, and support undoable operations.

Read the definition as a list of what you get once a request is a value you can hold:

  • Parameterize an object with a request: the remote's slots are parameters, and set_command fills them.
  • Queue requests: hand command objects to a worker that calls execute() without knowing what runs.
  • Log requests: write each command down before running it, and replay the log after a crash.
  • Undo: a command knows what it did, so it can know how to take it back.

Five roles take part. The client builds receivers and commands and wires them into the invoker. The invoker stores commands and, at some later moment, calls execute(). The command interface promises execute() (and here undo()). A concrete command holds a receiver and implements the promise by calling receiver methods. The receiver is any object that does real work; it never knows it is being commanded. The invoker and the receiver never meet. That is the whole point.

The remote, before and after

The remote knows every device

A branch per slot, a vendor API per branch, no way to re-program a slot without editing the class, and nothing an undo button could use.

class RemoteControl:
    """Every slot is a branch; every branch knows a vendor API."""
    def __init__(self, light, stereo, fan, garage):
        self.light, self.stereo, self.fan, self.garage = light, stereo, fan, garage

    def on_button(self, slot: int) -> None:
        if slot == 0:
            self.light.on()
        elif slot == 1:
            self.stereo.on()
            self.stereo.set_cd()
            self.stereo.set_volume(11)
        elif slot == 2:
            self.fan.high()
        elif slot == 3:
            self.garage.up()
        # slot 4: the hot tub arrives next week -> edit this class again

    def off_button(self, slot: int) -> None:
        if slot == 0:
            self.light.off()
        elif slot == 1:
            self.stereo.off()
        elif slot == 2:
            self.fan.off()           # and what speed was it before?
        elif slot == 3:
            self.garage.down()

    def undo_button(self) -> None:
        pass                         # reverse what? the remote remembers nothing

The remote knows one method

Slots hold command objects. Pressing is execute(), remembering is append, undoing is pop().undo(). New device: two small classes. New wiring: set_command at runtime.

from abc import ABC, abstractmethod

class Command(ABC):                 # the one interface the remote depends on
    @abstractmethod
    def execute(self) -> None: ...
    @abstractmethod
    def undo(self) -> None: ...

class Light:                        # receiver: a vendor class, untouched
    def __init__(self, room: str):
        self.room, self.is_on = room, False
    def on(self) -> None:  self.is_on = True
    def off(self) -> None: self.is_on = False

class LightOnCommand(Command):      # concrete command: one receiver, one action
    def __init__(self, light: Light): self.light = light
    def execute(self) -> None: self.light.on()
    def undo(self) -> None: self.light.off()

class LightOffCommand(Command):
    def __init__(self, light: Light): self.light = light
    def execute(self) -> None: self.light.off()
    def undo(self) -> None: self.light.on()

class NoCommand(Command):           # null object for an empty slot
    def execute(self) -> None: pass
    def undo(self) -> None: pass

class RemoteControl:                # invoker: knows Command, never a vendor class
    def __init__(self, slots: int = 7):
        self.on_commands: list[Command] = [NoCommand() for _ in range(slots)]
        self.off_commands: list[Command] = [NoCommand() for _ in range(slots)]
        self.history: list[Command] = []

    def set_command(self, slot: int, on: Command, off: Command) -> None:
        self.on_commands[slot], self.off_commands[slot] = on, off

    def on_button(self, slot: int) -> None:
        self._run(self.on_commands[slot])

    def off_button(self, slot: int) -> None:
        self._run(self.off_commands[slot])

    def undo_button(self) -> None:
        if self.history:
            self.history.pop().undo()

    def _run(self, cmd: Command) -> None:
        cmd.execute()
        self.history.append(cmd)

# the client wires receivers into commands and commands into slots
light = Light("living room")
remote = RemoteControl()
remote.set_command(0, LightOnCommand(light), LightOffCommand(light))
remote.on_button(0)        # light.is_on -> True
remote.undo_button()       # light.is_on -> False
remote.on_button(5)        # empty slot: NoCommand runs, nothing happens

Empty slots: the NoCommand null object

Seven slots, three programmed. What is in the other four? The tempting answer is None, and then every button handler starts with if cmd is not None:. Undo gets the same guard. Any new code path that touches a slot gets the same guard, and the one that forgets it crashes the first time a customer presses an unprogrammed button.

The pattern's answer is a command that does nothing on purpose:

class NoCommand(Command):
    def execute(self) -> None: pass
    def undo(self) -> None: pass

remote.on_commands = [NoCommand() for _ in range(7)]   # every slot starts safe

Now every slot always holds a real Command, and the remote has no special case anywhere: execute() on an empty slot does nothing, undoing it does nothing, and the code that runs a programmed slot is the code that runs an empty one. This is the Null Object idea: replace "absent" with a harmless object of the expected type, so callers never branch on absence. You will meet it again as an empty iterator, a logger that discards everything, and a no-op strategy.

Undo, and undo with state

Simple undo is the inverse action: LightOnCommand.undo() calls light.off(). The remote keeps a history of executed commands and undo_button() pops the latest one and calls undo() on it. Because the command that ran is the command that reverses, the remote still names no device.

The ceiling fan breaks the inverse idea. The fan has speeds, and "undo setting it to high" is not "set it to off"; it is "put it back to whatever it was". A command that changes state must save the state it is about to replace before it changes anything, and undo() must restore that snapshot:

  1. prev_speed = fan.speed (snapshot first, always first),
  2. fan.high(),
  3. on undo: fan.set_speed(prev_speed).

The three fan commands differ only in step 2, so a small base class holds steps 1 and 3 and each subclass fills in the change. That shape, a fixed skeleton with one varying step, is chapter 8's Template Method showing up early.

Undo with state. The command reads the fan's speed before changing it, and undo writes that value back, not 'off'.

Undo that restores a snapshot

class CeilingFan:                    # receiver whose state the command must remember
    OFF, LOW, MEDIUM, HIGH = 0, 1, 2, 3

    def __init__(self, room: str):
        self.room, self.speed = room, CeilingFan.OFF

    def high(self) -> None:   self.speed = CeilingFan.HIGH
    def medium(self) -> None: self.speed = CeilingFan.MEDIUM
    def low(self) -> None:    self.speed = CeilingFan.LOW
    def off(self) -> None:    self.speed = CeilingFan.OFF
    def set_speed(self, speed: int) -> None: self.speed = speed


class CeilingFanCommand(Command):
    """Shared by every fan command: snapshot, change, restore."""
    def __init__(self, fan: CeilingFan):
        self.fan = fan
        self.prev_speed = CeilingFan.OFF

    def execute(self) -> None:
        self.prev_speed = self.fan.speed     # 1. snapshot BEFORE touching the receiver
        self.change()                        # 2. then act

    def undo(self) -> None:
        self.fan.set_speed(self.prev_speed)  # 3. undo restores the snapshot, not "the opposite"

    def change(self) -> None:
        raise NotImplementedError


class CeilingFanHighCommand(CeilingFanCommand):
    def change(self) -> None: self.fan.high()

class CeilingFanMediumCommand(CeilingFanCommand):
    def change(self) -> None: self.fan.medium()

class CeilingFanOffCommand(CeilingFanCommand):
    def change(self) -> None: self.fan.off()


fan = CeilingFan("living room")
remote.set_command(1, CeilingFanHighCommand(fan), CeilingFanOffCommand(fan))
remote.set_command(2, CeilingFanMediumCommand(fan), CeilingFanOffCommand(fan))
remote.on_button(1)        # prev_speed = OFF,  fan.speed = HIGH
remote.on_button(2)        # prev_speed = HIGH, fan.speed = MEDIUM
remote.undo_button()       # fan.speed = HIGH   (the medium command's snapshot)
remote.undo_button()       # fan.speed = OFF    (the high command's snapshot)
Snapshot before change, restore on undo. The base class owns that order; subclasses only say what the change is.

Macro commands, queues and logs

▶ Video lesson: One request object, three uses: macro, queue, log 2:26 · 5 scenes · narrated, pause anytime and explore

Once a request is an object, three more things fall out almost for free.

MacroCommand. A command whose execute() runs a list of commands in order and whose undo() runs them in reverse. The remote stores and undoes it like any other command: one slot, one history entry. The reverse order matters whenever later commands depend on earlier ones (open the garage, then start the car). Structurally this is a Composite (chapter 9): a command that contains commands and looks like one.

Queues. A job queue is an invoker with a delay. Producers put command objects; worker threads get them and call execute(). The queue and the workers are written once and never learn what jobs exist: a thumbnail resize, an email, a database migration are all just execute(). The producer returns as soon as the object is queued, which is how you get asynchrony without the producer knowing about threads.

Logs. Write each command down before executing it, in a form you can rebuild it from (a type name and its arguments). If the process crashes, read the log and execute() each entry again in order; the state comes back. This is the write-ahead log under databases and the event stream under event-sourced systems. It only works when execute() is deterministic: a command that reads the clock replays differently.

flowchart LR
    P[Producer] -->|1. append record| J[(Journal)]
    P -->|2. put command| Q{{Job queue}}
    Q -->|get| W1[Worker 1]
    Q -->|get| W2[Worker 2]
    W1 -->|execute| R[(Receivers)]
    W2 -->|execute| R
    J -.->|replay after crash| R
Queue and journal are two invokers that never learn what a command does. The dashed path is recovery: re-executing the journal in order rebuilds the receivers' state.

Three things you can do with a request object

Execute forward, undo backward. The remote sees one command.

class MacroCommand(Command):
    """A command made of commands. The remote cannot tell it from a single one."""
    def __init__(self, commands: list[Command]):
        self.commands = list(commands)

    def execute(self) -> None:
        for cmd in self.commands:            # in the order given
            cmd.execute()

    def undo(self) -> None:
        for cmd in reversed(self.commands):  # last done, first undone
            cmd.undo()


party_on = MacroCommand([LightOnCommand(light), StereoOnWithCDCommand(stereo), CeilingFanHighCommand(fan)])
party_off = MacroCommand([LightOffCommand(light), StereoOffCommand(stereo), CeilingFanOffCommand(fan)])
remote.set_command(4, party_on, party_off)
remote.on_button(4)        # light, stereo, fan: three receivers, one press
remote.undo_button()       # fan, stereo, light: one history entry, reversed

Workers are invokers that run later and in parallel. They depend on execute() and nothing else.

import queue
import threading

jobs: "queue.Queue[Command]" = queue.Queue()

def worker() -> None:
    while True:
        cmd = jobs.get()          # the worker has no idea what the job is
        try:
            cmd.execute()         # it only knows that every job can execute()
        finally:
            jobs.task_done()

for _ in range(4):                # four invokers sharing one queue
    threading.Thread(target=worker, daemon=True).start()

jobs.put(LightOnCommand(light))   # the producer returns immediately
jobs.put(party_on)                # a macro is just another job
jobs.join()                       # wait until every command has executed

A command that is plain data can be written down and rebuilt. Log first, execute second, replay in order.

import json
from dataclasses import dataclass, asdict

@dataclass
class SetThermostat:                       # a command that can be written down
    room: str
    degrees: float
    def execute(self, house) -> None:
        house.thermostats[self.room] = self.degrees

REGISTRY = {"SetThermostat": SetThermostat}

def run_logged(cmd, house, log_path: str) -> None:
    with open(log_path, "a") as f:         # 1. write the request down (durable)
        f.write(json.dumps({"type": type(cmd).__name__, "args": asdict(cmd)}) + "\n")
    cmd.execute(house)                     # 2. then perform it

def replay(house, log_path: str) -> None:  # after a crash: re-run the journal in order
    with open(log_path) as f:
        for line in f:
            rec = json.loads(line)
            REGISTRY[rec["type"]](**rec["args"]).execute(house)

Command in Python, two ways

The book's shape. Use it when a command needs a name (logging, debugging), serialisation, or both execute and undo on one object.

A zero-argument callable is a command without undo. functools.partial binds the receiver and arguments; a closure bundles several calls; execute() can return its own undo.

from functools import partial
from typing import Callable

# A command with execute() and no undo is a zero-argument callable.
light, stereo, fan = Light("living room"), Stereo(), CeilingFan("living room")

def stereo_on_with_cd() -> None:           # a closure bundles receiver + several calls
    stereo.on(); stereo.set_cd(); stereo.set_volume(11)

slots: list[Callable[[], None]] = [
    light.on,                              # a bound method already carries its receiver
    stereo_on_with_cd,
    partial(fan.set_speed, CeilingFan.HIGH),   # partial binds receiver and arguments
    lambda: None,                          # NoCommand
]
slots[0]()                                 # the "remote" calls whatever is in the slot

# Undo with state: let execute() hand back its own undo. Every call captures its own
# snapshot, so the same slot pressed twice gives two independent undos.
def fan_high() -> Callable[[], None]:
    prev = fan.speed
    fan.high()
    return lambda: fan.set_speed(prev)

history: list[Callable[[], None]] = []
history.append(fan_high())                 # press
history.append(fan_high())                 # press again: a second closure, its own prev
history.pop()()                            # undo -> HIGH (prev of the second press)
history.pop()()                            # undo -> OFF  (prev of the first press)

Callable or class?

Python already has first-class 'requests': a bound method such as light.on carries its receiver, and functools.partial(fan.set_speed, 3) carries receiver and arguments. For execute-only commands (GUI callbacks, job queues, atexit), a callable is the idiomatic Command. Reach for a class when the command needs undo state, a readable name in a log, serialisation for replay, or several related operations. The closure-returns-undo trick in the second tab also fixes a real bug: one command object with a single prev_speed field cannot sit twice in a multi-level undo stack.

Where you have already seen it

  • GUI toolkits. tkinter.Button(command=...) and Qt's QAction hold a request to run on click; the widget is the invoker and never knows what the handler does. QUndoStack is a history of command objects with undo/redo.
  • Editors and IDEs. Every keystroke, paste and refactor is a command on an undo stack; the stateful ones carry snapshots, which is why undo of 'replace all' restores the old text rather than deleting the new.
  • Executors and schedulers. concurrent.futures.Executor.submit(fn, *args) queues a callable for a worker; threading.Timer, asyncio.loop.call_later and cron store a request to run later.
  • Task queues. Celery and RQ serialise the task name and arguments, exactly the journal shape, so a worker on another machine can rebuild and execute the request.
  • Databases. The write-ahead log is a journal of commands replayed after a crash; event sourcing keeps the log as the system of record.
  • Redux and friends. An action is a plain-data command, dispatch is the invoker, reducers are the receivers, and time-travel debugging is replaying the log.

Common mistakes

  • Command where a callable would do. If nothing stores, queues, logs or undoes the request, a function parameter is the whole pattern. Classes earn their keep with undo state, names and serialisation.
  • The fat command. A command that does the work itself instead of delegating to a receiver cannot be pointed at a different device, and its logic cannot be reused outside the remote. Keep receivers as the place work happens; commands translate.
  • Undo as the opposite action. Correct for a light, wrong for anything with state. If execute() changes a value, snapshot it first and restore it on undo.
  • One command object on a multi-level undo stack. CeilingFanHighCommand has one prev_speed. Press it twice and the second press overwrites the first snapshot; two undos then land on the same speed. Create a command per press, store (command, snapshot) pairs, or return an undo closure from execute().
  • None in the slots. Every if cmd is not None is a branch the NoCommand object would have removed, and the one you forget is a crash.
  • Macro undo in forward order. The last command's effects are on top; undo them first.
  • Logging non-deterministic commands. A command that reads the clock or a random number replays differently. Resolve such inputs in the client and store the resolved values in the command.

    A{Is the request a value you hand to someone else?} -->|no| B[Just call the method]
    A -->|yes| C{Will it be stored, queued, logged, scheduled or undone?}
    C -->|no, only chosen| D[Strategy, or pass a callable]
    C -->|yes| E{Does undo have to restore an earlier state?}
    E -->|no| F[Command: execute plus an inverse undo]
    E -->|yes| G[Command that snapshots state per press<br/>or pairs with a Memento]
    F --> H{Several requests behind one button?}
    G --> H
    H -->|yes| I[MacroCommand, undo in reverse]
Command and Strategy both wrap behaviour in an object. The difference is what the holder does with it: Strategy is chosen and called; Command is kept, moved, logged and reversed.

How to say it in an interview

Say: 'The remote has to drive devices with unrelated APIs and let customers re-program slots and undo. I would make each request an object with execute and undo, the Command pattern. The remote is the invoker: it holds a command per slot and only ever calls execute, so it never names a device. Each concrete command holds its receiver and translates execute into that device's calls; stateful ones snapshot before changing so undo restores rather than inverts. Empty slots hold a NoCommand so there is no null check, a MacroCommand bundles several commands and undoes them in reverse, and because requests are objects they can also be queued for workers or logged and replayed.' Then draw Client, Invoker, Command, ConcreteCommand, Receiver.
