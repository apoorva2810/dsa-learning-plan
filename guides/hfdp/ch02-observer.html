Keeping your objects in the know: Observer

Weather-O-Rama hands us one object whose readings change and asks for any number of displays that follow it. The first design wires the displays into the subject and breaks at the second requirement; the fix is a list of observers behind a one-method interface. Along the way: the loose coupling principle, push versus pull, the Python idioms (callables, signals, asyncio) and how Observer differs from pub-sub.

After this chapter you can
  • Explain, with the weather station, why a subject that names its displays cannot add or remove one at runtime
  • Draw the Observer class diagram (Subject, Observer, concrete pair) and label the one-to-many arrow
  • State the loose coupling principle and list what it buys the subject and the observers
  • Argue push versus pull with one advantage and one cost each
  • Write a Python subject as a list of callables with an unsubscribe handle, and know when to use classes or a Signal
  • Contrast Observer with pub-sub in one sentence, and name the three runtime hazards of notify()

The Weather-O-Rama story

▶ Video lesson: The weather station: why hard-wired displays broke, and what fixed it 6:11 · 7 scenes · narrated, pause anytime and explore

Weather-O-Rama is building an internet weather station and wants our team to write the display half. Their side is finished: a WeatherData object with three getters, get_temperature(), get_humidity() and get_pressure(), and one method, measurements_changed(), that their hardware calls every time new readings come in. We owe them three displays, current conditions, statistics and a forecast, that redraw whenever the readings change. The contract has one more line: other developers must be able to plug in displays of their own.

The obvious first version writes the three displays into measurements_changed() by name. It works on day one, and that is the trap: the design is wrong in a way that only shows when the second requirement arrives. Step through what each change costs, and keep asking the chapter 1 question: what varies here, and where did we put it?

Why the hard-wired version fails

The first design is not slow, not buggy, and not hard to read. It fails on change: every new display, every removed display and every new sensor value is an edit to WeatherData, and nothing can join or leave while the program runs. It programs to implementations (the concrete display classes) instead of to an interface, which is chapter 1's second principle turned on its head.

The newspaper picture: subject and observers

Think of a newspaper. The publisher prints an issue whenever there is news. You subscribe, and from then on every issue lands in your letterbox; you cancel, and they stop. The publisher keeps a list of addresses and nothing else about you, and anyone can subscribe or cancel at any time without the publisher changing how it prints.

That is the whole pattern. The publisher is the subject: the one object whose state changes. The subscribers are observers: any number of objects that want to hear about it. The subject offers three operations, register_observer, remove_observer and notify_observers, and asks exactly one thing of an observer: an update method it can call. Map it onto the weather station and the hard-wired list of displays turns into data inside WeatherData, a list that grows and shrinks while the program runs.

Observers register, get notified, join late and leave

WeatherData keeps a list. Watch displays register, a reading fan out to every entry, a third-party display join at runtime, and one leave, with the subject's code untouched throughout.

One reading, one loop. The subject makes the same call on every entry in its list and never looks at who is on the other end.

Principle: strive for loosely coupled designs

Two objects are coupled by how much each must know about the other to work. The hard-wired WeatherData knew the concrete class of every display, their number, and the exact shape of their update. The Observer version knows one fact: every entry in its list has update().

Strive for loosely coupled designs between objects that interact.

What that single fact buys:

  1. New observers at any time. Register during start-up, after a click, from a plug-in, at three in the morning; the subject runs the same loop.
  2. New kinds of observer without touching the subject. A heat-index display is a new class that implements Observer; WeatherData is never reopened.
  3. Either side can be reused alone. The subject can drive a logger, a chart or a test double; a display can listen to any subject that honours the same interface.
  4. Changes stay local. Rewrite how a display draws, or how the subject stores readings, and the other side does not notice as long as the update contract holds.

The cost is indirection: reading notify_observers() tells you that something is called, not what. To find the displays you search for register_observer, not for a method call, and a bug in display B shows up as a traceback out of the subject. That trade is worth it whenever the set of interested parties changes at runtime or is decided by someone other than the subject's author.

The weather station, before and after

Displays wired into the subject

The subject names its listeners. Adding, removing or plugging in a display means editing and redeploying WeatherData; nothing changes at runtime.

class WeatherData:
    def __init__(self, current, statistics, forecast):
        self.current = current                  # concrete displays, named here
        self.statistics = statistics
        self.forecast = forecast
        self._temp = self._humidity = self._pressure = 0.0

    def measurements_changed(self):             # called by the station hardware
        t, h, p = self.get_temperature(), self.get_humidity(), self.get_pressure()
        self.current.update(t, h, p)            # one line per display:
        self.statistics.update(t, h, p)         #   add a display  = edit this class
        self.forecast.update(t, h, p)           #   remove one     = edit this class

    def get_temperature(self): return self._temp
    def get_humidity(self): return self._humidity
    def get_pressure(self): return self._pressure

Subject with a list of observers

The subject keeps a list typed as the interface and loops over it. Displays register and leave themselves; the subject is closed to display changes.

from abc import ABC, abstractmethod

class Observer(ABC):
    @abstractmethod
    def update(self, temp: float, humidity: float, pressure: float) -> None: ...

class Subject(ABC):
    @abstractmethod
    def register_observer(self, o: Observer) -> None: ...
    @abstractmethod
    def remove_observer(self, o: Observer) -> None: ...
    @abstractmethod
    def notify_observers(self) -> None: ...

class WeatherData(Subject):
    def __init__(self):
        self._observers: list[Observer] = []    # the list is data, not code
        self._temp = self._humidity = self._pressure = 0.0

    def register_observer(self, o): self._observers.append(o)
    def remove_observer(self, o): self._observers.remove(o)
    def notify_observers(self):
        for o in list(self._observers):         # copy: an observer may unsubscribe mid-loop
            o.update(self._temp, self._humidity, self._pressure)

    def measurements_changed(self): self.notify_observers()
    def set_measurements(self, temp, humidity, pressure):
        self._temp, self._humidity, self._pressure = temp, humidity, pressure
        self.measurements_changed()             # one notification per batch of readings

class CurrentConditionsDisplay(Observer):
    def __init__(self, weather: Subject):
        weather.register_observer(self)         # subscribe in the constructor
    def update(self, temp, humidity, pressure):
        print(f"Current: {temp}F, {humidity}% humidity")

class StatisticsDisplay(Observer):
    def __init__(self, weather: Subject):
        self.readings: list[float] = []         # an observer with state of its own
        weather.register_observer(self)
    def update(self, temp, humidity, pressure):
        self.readings.append(temp)
        print(f"Avg temp {sum(self.readings) / len(self.readings):.1f}F")

weather = WeatherData()
current = CurrentConditionsDisplay(weather)
stats = StatisticsDisplay(weather)
weather.set_measurements(80, 65, 30.4)          # both displays update
weather.remove_observer(stats)
weather.set_measurements(82, 70, 29.2)          # only Current updates

The Observer pattern, named

▶ Video lesson: Observer: the pattern behind the weather station 2:57 · 6 scenes · narrated, pause anytime and explore

Observer defines a one-to-many dependency between objects so that when one object changes state, all of its dependents are notified and updated automatically.

One is the subject (WeatherData); many are the observers (the displays); the state is the latest set of readings; notified and updated automatically is the loop in notify_observers(). The dependency points one way: observers depend on the subject's interface, and the subject depends on nothing concrete.

Where you have already seen it

  • GUI toolkits: button.on_click(handler), tkinter's widget.bind("<Button-1>", fn), Qt's signals and slots. The widget is the subject; your handler is the observer.
  • Django signals: post_save.connect(fn, sender=Order) runs your function after every save without the model knowing your module exists.
  • Spreadsheets: change cell B2 and every formula that references it recomputes. Cells observe the cells they depend on.
  • Model-view: a model notifies its views when it changes, so three windows onto one document stay in sync (chapter 12 builds MVC on exactly this).
  • concurrent.futures.Future.add_done_callback(fn) and asyncio futures: register interest in a result that is not there yet.
  • Reactive libraries (RxJS, RxPY): streams whose subscribers receive every value, with operators to filter and combine them.

Push or pull?

update(temp, humidity, pressure) is the push model: the subject hands every observer every value. It is simple, every observer sees one consistent snapshot, and no observer needs a reference back to the subject. But every observer receives fields it may not use, and the day Weather-O-Rama adds wind speed, the signature of every update in the system changes.

The pull model sends less: update(subject), or just update(), and each observer asks for what it wants through the subject's getters. The signature never changes and the forecast display reads only pressure. The costs: observers now know the subject's getters (a little more coupling), and with threads a reading can change between the notification and the getter. Many real APIs do both: pass a small event object saying what changed and let the observer pull the rest.

Push and pull, side by side

The book's weather station. Right when the data is small and every observer wants most of it.

# Push: the subject hands every observer every value.
from abc import ABC, abstractmethod

class Observer(ABC):
    @abstractmethod
    def update(self, temp: float, humidity: float, pressure: float) -> None: ...

class WeatherData:
    def notify_observers(self):
        for o in list(self._observers):
            o.update(self._temp, self._humidity, self._pressure)

# + simple; observers need no reference back to the subject
# + every observer sees a consistent snapshot of all three values
# - every observer receives fields it may not use
# - add wind speed and the signature of every update() in the system changes

Right when the subject's data grows, or observers want different slices of it.

# Pull: the subject says "something changed"; each observer asks for what it needs.
from abc import ABC, abstractmethod

class Observer(ABC):
    @abstractmethod
    def update(self, subject: "WeatherData") -> None: ...

class WeatherData:
    def notify_observers(self):
        for o in list(self._observers):
            o.update(self)                      # hand over the subject (or nothing at all)
    def get_pressure(self): return self._pressure

class ForecastDisplay(Observer):
    def update(self, weather):
        self.pressure = weather.get_pressure()  # only the one value this display uses

# + the update() signature never changes when the subject gains data
# + observers take only what they need
# - observers now call the subject's getters: a little more coupling
# - with threads, a reading can change between update() and the getter

Observer in Python, four ways

The book's shape in Python. Use it when observers carry state (StatisticsDisplay keeps every reading) or several methods.

Idiomatic Python for a one-method observer: store functions, return an unsubscribe handle.

# The Observer interface has one method, so in Python an observer can be any callable.
from typing import Callable

Listener = Callable[[float, float, float], None]

class WeatherData:
    def __init__(self):
        self._listeners: list[Listener] = []
        self._temp = self._humidity = self._pressure = 0.0

    def subscribe(self, fn: Listener) -> Callable[[], None]:
        self._listeners.append(fn)
        def unsubscribe(): self._listeners.remove(fn)
        return unsubscribe                      # the caller keeps the handle

    def set_measurements(self, temp, humidity, pressure):
        self._temp, self._humidity, self._pressure = temp, humidity, pressure
        for fn in list(self._listeners):        # copy, as before
            fn(temp, humidity, pressure)

weather = WeatherData()
readings = []
stop = weather.subscribe(lambda t, h, p: print(f"Current: {t}F"))
weather.subscribe(lambda t, h, p: readings.append(t))   # any callable: lambda, function, bound method
weather.set_measurements(80, 65, 30.4)
stop()                                                  # unsubscribe
weather.set_measurements(82, 70, 29.2)                  # only the second listener runs

The Django / blinker shape: a module-level object per kind of event, weak references so forgotten receivers do not leak.

# Django signals and the blinker package wrap the idea in a reusable object: one Signal
# per kind of event, connect / disconnect, send. Weak references stop forgotten receivers
# from leaking: when the receiver object dies, it silently drops off the list.
import weakref
from typing import Any, Callable

class Signal:
    def __init__(self) -> None:
        self._receivers: list[weakref.ReferenceType] = []

    def connect(self, receiver: Callable[..., Any]) -> None:
        ref = weakref.WeakMethod(receiver) if hasattr(receiver, "__self__") else weakref.ref(receiver)
        self._receivers.append(ref)             # weak: do not pass a lambda here, it dies at once

    def disconnect(self, receiver: Callable[..., Any]) -> None:
        self._receivers = [r for r in self._receivers if r() is not receiver]

    def send(self, sender: Any, **kwargs: Any) -> list[tuple[Callable[..., Any], Any]]:
        results = []
        for ref in list(self._receivers):
            fn = ref()
            if fn is None:                      # receiver was garbage-collected
                self._receivers.remove(ref)
                continue
            results.append((fn, fn(sender, **kwargs)))
        return results

measurements_changed = Signal()                 # module level, like django's post_save

class Logger:
    def on_change(self, sender, temp, **_):
        print("log", sender, temp)

logger = Logger()
measurements_changed.connect(logger.on_change)  # deleting `logger` later unsubscribes it
measurements_changed.send("station-1", temp=80, humidity=65, pressure=30.4)

Observers that are coroutines wait on an Event and pull the state when woken.

# When the observers are coroutines, asyncio gives the pull model for free: the subject
# wakes everyone waiting on an Event and each waiter reads the state it cares about.
import asyncio

class WeatherData:
    def __init__(self):
        self.changed = asyncio.Event()
        self.temp = 0.0

    def set_measurements(self, temp):
        self.temp = temp
        self.changed.set()                      # wake every coroutine awaiting this event
        self.changed = asyncio.Event()          # a fresh event for the next reading

async def display(weather, name, cycles):
    for _ in range(cycles):
        await weather.changed.wait()            # "something changed"...
        print(name, weather.temp)               # ...pull the value you need

async def main():
    weather = WeatherData()
    tasks = [asyncio.create_task(display(weather, "current", 2)),
             asyncio.create_task(display(weather, "forecast", 2))]
    await asyncio.sleep(0)                      # let both displays start waiting
    weather.set_measurements(80)
    await asyncio.sleep(0)
    weather.set_measurements(82)
    await asyncio.gather(*tasks)                # current 80, forecast 80, current 82, forecast 82

# A waiter that is busy when a reading lands misses it and sees the next one: pull
# gives you "the latest state", not "every change". Use asyncio.Queue per observer
# when every reading must be delivered.

Python note

The Observer interface has one method, so in Python an observer is usually just a callable: keep a list of functions and have subscribe() return the unsubscribe handle. Promote to classes when an observer carries state or wants several events; use a Signal object per event when many modules publish the same kind of change; use asyncio.Event or Condition when the observers are coroutines. Whatever the shape: notify over a copy of the list, decide what one failing observer does to the others, and unsubscribe (or hold weakrefs) when an observer dies.

Observer or pub-sub?

▶ Video lesson: Observer or pub-sub? And the Python shortcut 2:17 · 4 scenes · narrated, pause anytime and explore

Observer and publish-subscribe get confused because both deliver "something happened" to many listeners. The difference is who holds the list and where the call runs.

  • Observer: the subject holds direct references to its observers and calls update() itself, in the same process, synchronously, in list order. The subject knows how many observers it has (not who they are), and an observer that raises or blocks delays everyone after it.
  • Publish-subscribe: a broker (a Kafka topic, an SNS topic, a Redis channel, an in-process event bus) sits between the two sides. Publishers send to a topic; subscribers read from it. Neither side holds a reference to the other, they usually run in different processes, and delivery is asynchronous, which means ordering, retries and at-least-once duplicates are now your problem.

Rule of thumb: inside one program, where the change must be visible before the current call returns, use Observer. Across services, or when the publisher must never wait for a slow subscriber, use pub-sub. The feed in Design Twitter is the pull picture at scale: follow is register_observer, and the timeline is assembled when the user asks for it rather than pushed when the tweet is posted.

Common mistakes

  • Mutating the list while walking it. An observer that calls remove_observer(self) inside its own update() shifts the list under the loop and a neighbour is skipped. Iterate over a copy (for o in list(self._observers)), or queue removals until the loop ends.
  • One bad observer silences the rest. If the second update() raises, the third never runs, and the subject's caller sees a traceback from a display it has never heard of. Decide on purpose: isolate (try/except and log) for independent displays, fail fast for observers whose failure must stop the subject.
  • Forgetting to unsubscribe. A window closes but stays in the list, so it is never garbage-collected and keeps repainting off-screen: a memory leak with CPU attached. Unsubscribe in the teardown path, or hold observers through weakref as Django signals do.
  • Depending on notification order. List order is an implementation detail. If display B needs A's result, B should observe A, or the subject should compute the shared value once and push it.
  • Heavy work inside update(). Notification runs on the subject's thread; a display that writes a file or calls an API stalls the sensor loop. Record the value and hand the work to a queue or a task.
  • Notification storms and re-entrancy. Three setters fire three notifications; batch them, as set_measurements does, and notify once. An observer that updates the subject from inside update() starts a second notification while the first is running: guard against it or forbid it.
  • Reaching for Observer when a return value would do. One caller, one result, right now: return it. The pattern pays off when the set of interested parties varies or is decided elsewhere.

How to say it in an interview

Say: 'Weather-O-Rama gives us one object whose readings change, and we need any number of displays to follow it. Hard-wiring the displays into WeatherData couples it to every concrete display and freezes the list at compile time. I would make WeatherData a subject that keeps a list of observers behind a one-method interface, with register, remove and notify, and have each display implement update and register itself. Then displays come and go at runtime and the subject never changes. That is Observer; the principle is loose coupling, and the decision after that is push versus pull.' Then draw subject, observer, the concrete pair, and the notify loop.
