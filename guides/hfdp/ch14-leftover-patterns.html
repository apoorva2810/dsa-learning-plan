Leftover patterns (appendix)

The book spends thirteen chapters on the patterns you meet most and puts the rest of the Gang of Four catalogue in an appendix. This chapter is that appendix in Python: nine patterns, one page each, with the same layout so you can compare them, two simulations where behaviour over time is the point, and a closing table that separates each one from the pattern it is most often confused with.

After this chapter you can
  • Give the one-line intent of Bridge, Builder, Chain of Responsibility, Flyweight, Interpreter, Mediator, Memento, Prototype and Visitor
  • Draw the small class diagram of each and name the roles (handler and successor, originator and caretaker, element and visitor...)
  • Pick the right one from a symptom: too many classes, a request with several possible receivers, undo, a tiny language
  • Tell each apart from its look-alike: Bridge vs Strategy, Mediator vs Observer, Memento vs Command undo, Visitor vs Iterator, Chain of Responsibility vs Decorator
  • Say what Python gives you for free in each case (copy, ast.NodeVisitor, singledispatch, keyword arguments)

Nine more patterns, one page each

Thirteen chapters covered the patterns you will see every month. The Gang of Four catalogue has more, and the book parks them in an appendix: still real, still worth recognising, but each one solves a narrower problem, and reaching for it before that problem shows up adds indirection nobody asked for.

Every page here has the same layout, so the nine are easy to compare: the problem and the move in one paragraph, the shape as a class diagram, 10-20 lines of Python you could paste into a REPL, the moment to reach for it, and the mistake that usually arrives with it. Two patterns get a simulation, because what they do over time is the whole idea: a Chain of Responsibility passing a request from handler to handler, and Memento undoing a saved game.

What interviews test here is recognition, not implementation. Nobody asks you to write an Interpreter on a whiteboard; they do notice when you say "that is a Mediator, and here is why it is not an Observer". The table at the end is built for exactly that sentence.

Rarer for a reason

Each of these fixes a specific pain: a class count that multiplies, a request with several possible receivers, an undo button, a grammar. Chapter 13's advice applies twice as hard here: name the pain first, then the pattern. A Visitor over three classes with one operation is three indirections for nothing.

Bridge

▶ Video lesson: Bridge, Flyweight, Prototype: fewer classes, fewer objects, cheaper objects 4:02 · 8 scenes · narrated, pause anytime and explore

Bridge decouples an abstraction from its implementation so that the two can vary independently.

A universal remote has to work with every brand of TV. Subclass per combination and you get BasicSonyRemote, BasicLgRemote, ConciseSonyRemote, ConciseLgRemote: two axes of variation (what the remote offers, which TV it drives) multiplied into one hierarchy, and every new brand or feature doubles it. Bridge cuts the hierarchy in two. The abstraction side (RemoteControl and its subclasses) holds a reference to an implementor interface (TV); the implementor side has its own subclasses per brand. A remote talks to the TV only through the interface, so a new remote works with every TV and a new TV works with every remote. Two hierarchies of 2 give 4 combinations from 4 classes instead of 4 subclasses that cannot be mixed.

classDiagram
    class RemoteControl {
        -tv: TV
        +set_channel(n)
        +on()
    }
    class ConciseRemote {
        +next_channel()
    }
    class TV {
        <<interface>>
        +tune(n)
        +on()
    }
    class SonyTV {
        +tune(n)
    }
    class LgTV {
        +tune(n)
    }
    RemoteControl o--> TV : the bridge
    RemoteControl <|-- ConciseRemote
    TV <|.. SonyTV
    TV <|.. LgTV
Two hierarchies joined by one has-a arrow. Either side can grow without the other noticing.

Bridge: a remote hierarchy and a TV hierarchy, joined by a reference

from abc import ABC, abstractmethod

class TV(ABC):                              # implementor side: varies by brand
    @abstractmethod
    def tune(self, channel: int) -> str: ...

class SonyTV(TV):
    def tune(self, channel): return f"Sony: channel {channel}"

class LgTV(TV):
    def tune(self, channel): return f"LG: channel {channel}"

class RemoteControl:                        # abstraction side: varies by features
    def __init__(self, tv: TV):
        self.tv, self.channel = tv, 1       # the bridge: a reference, not a subclass
    def set_channel(self, n: int) -> str:
        self.channel = n
        return self.tv.tune(n)

class ConciseRemote(RemoteControl):         # new remote, works with every TV
    def next_channel(self) -> str: return self.set_channel(self.channel + 1)

print(ConciseRemote(LgTV()).next_channel())   # LG: channel 2
ConciseRemote knows nothing about brands; LgTV knows nothing about remotes. Swap either side freely.

When to use it. Two things vary independently and you can see both axes up front: a feature hierarchy over a platform or driver hierarchy (a drawing API over several rendering back ends, a database API over several drivers, a notification service over several transports), especially when the implementation must be picked at runtime or per platform.

Watch out. It looks exactly like Strategy on the diagram, because both hold an interface reference. The difference is intent and scale: Strategy swaps one algorithm inside one class; Bridge separates two hierarchies that are both designed to grow. And unlike Adapter, which is bolted on afterwards to make an existing class fit, Bridge is planned before the classes exist.

Builder

▶ Video lesson: Builder, Chain of Responsibility, Mediator: who controls the flow 4:41 · 8 scenes · narrated, pause anytime and explore

Builder separates the construction of a complex object from its representation, so the same steps can produce different representations.

A vacation planner builds an itinerary: a variable number of days, each with maybe a hotel, maybe tickets, maybe a meal. A constructor with twelve optional parameters cannot express "day 2 has two events and no hotel", and the client should not have to know how the days are stored. Builder gives the client a builder object with one method per step (add_day, add_hotel, add_ticket) and a final build() that hands back the product. The client controls which steps run and in what order; the builder owns the internal representation and can validate as it goes. Give the same client a different builder and the same sequence of steps produces a different product (a printable itinerary instead of a Vacation object).

classDiagram
    class Client {
        +plan_trip(builder)
    }
    class VacationBuilder {
        <<interface>>
        +add_day(date)
        +add_hotel(name)
        +add_ticket(event)
        +build() Vacation
    }
    class ItineraryBuilder {
        -days: list
        +add_day(date)
        +add_hotel(name)
        +add_ticket(event)
        +build() Vacation
    }
    class Vacation {
        +days: list
    }
    Client --> VacationBuilder : calls steps
    VacationBuilder <|.. ItineraryBuilder
    ItineraryBuilder ..> Vacation : creates
The client drives the steps; the concrete builder hides how the product is put together.

Builder: an itinerary assembled step by step

from dataclasses import dataclass, field

@dataclass
class Vacation:
    days: list[dict] = field(default_factory=list)

class VacationBuilder:
    def __init__(self): self._v = Vacation()
    def add_day(self, date: str):
        self._v.days.append({"date": date, "hotel": None, "tickets": []})
        return self                                   # return self so calls chain
    def add_hotel(self, name: str):
        self._v.days[-1]["hotel"] = name
        return self
    def add_ticket(self, event: str):
        self._v.days[-1]["tickets"].append(event)
        return self
    def build(self) -> Vacation: return self._v

trip = (VacationBuilder().add_day("Jul 1").add_hotel("Grand Patterns")
        .add_ticket("Pattern World").add_day("Jul 2").build())
print(len(trip.days), trip.days[0]["hotel"])        # 2 Grand Patterns
Each step returns self, so the calls chain. The client never touches the days list directly.

When to use it. Construction takes many steps, has repeated or ordered parts (days, rows, nested nodes), or needs validation across steps; or when one construction process must produce several representations (an object, a JSON document, a report). SQL query builders and test-data builders are the everyday cases.

Watch out. Python already covers the simple version: keyword arguments with defaults and dataclasses handle "an object with many optional fields" in one call. A builder that only wraps setters is ceremony. Keep it apart from Factory, which returns the whole product in one call: with Builder the client owns the sequence of steps. Reset or discard a builder after build(); reusing one by accident leaks the previous product's parts into the next.

Chain of Responsibility

Chain of Responsibility gives more than one object a chance to handle a request, passing it along a chain until one of them does.

Mighty Gumball's inbox gets spam, fan mail, complaints and requests for new store locations, and each kind goes to a different team. One big if/elif in the inbox knows about every team and changes whenever a team does. The pattern instead makes each kind of mail a handler with a successor: a handler either takes the request or forwards it unchanged, and the sender only ever talks to the first handler. The order of the chain is configuration, not code; a new kind of mail is one new class linked in. The price is that no handler is guaranteed to answer: a request can fall off the end.

classDiagram
    class Handler {
        <<abstract>>
        -successor: Handler
        +handle(request)
        +matches(request)*
    }
    class SpamHandler {
        +matches(request)
    }
    class FanHandler {
        +matches(request)
    }
    class ComplaintHandler {
        +matches(request)
    }
    class NewLocHandler {
        +matches(request)
    }
    Handler o--> Handler : successor
    Handler <|-- SpamHandler
    Handler <|-- FanHandler
    Handler <|-- ComplaintHandler
    Handler <|-- NewLocHandler
One abstract handler with a self-referencing successor link; the concrete handlers only answer 'is this mine?'. The order they are linked in is the policy.

A message walks the handler chain

Three messages enter the same chain. Watch how far each travels, which handler stops it, and what happens to the one nobody wants.

Chain of Responsibility: handlers linked by successor

from abc import ABC, abstractmethod

class Handler(ABC):
    def __init__(self, successor: "Handler | None" = None):
        self.successor = successor
    def handle(self, mail: str) -> str:
        if self.matches(mail):
            return f"{type(self).__name__} handled: {mail!r}"
        if self.successor:                              # pass it on, unchanged
            return self.successor.handle(mail)
        return f"nobody handled: {mail!r}"              # fell off the end
    @abstractmethod
    def matches(self, mail: str) -> bool: ...

class SpamHandler(Handler):
    def matches(self, mail): return "win a prize" in mail.lower()

class FanHandler(Handler):
    def matches(self, mail): return "love" in mail.lower()

chain = SpamHandler(FanHandler())                     # the order IS the policy
print(chain.handle("I love your gumballs!"))          # FanHandler handled: ...
print(chain.handle("Do you ship to Mars?"))           # nobody handled: ...
handle() is written once in the base class; each subclass is one predicate. The last print shows the fall-off case the simulation warned about.

When to use it. Several objects might handle a request and the right one is known only at runtime, or you want to add and reorder receivers without touching the sender: middleware stacks in web frameworks, event bubbling in GUIs (the widget, then its parent, then the window), logging handlers, exception handling up a call stack, approval workflows.

Watch out. Silent drops, long chains that are slow and hard to debug, and handlers that quietly mutate the request on the way through. It resembles Decorator, which also links objects of one type in a row, but a decorator always forwards and adds something on the way; a chain usually stops at the first handler that accepts.

Flyweight

Flyweight uses sharing to support large numbers of fine-grained objects efficiently.

A landscape designer places 10,000 trees. A Tree object per tree, each carrying its species, a bark texture and a shape as well as its x, y and age, is 10,000 copies of the same texture. Flyweight splits the state. The intrinsic state that every oak shares (species, texture, shape) lives in one immutable TreeType object per species, handed out by a small factory that keeps a dictionary. The extrinsic state that differs per tree (x, y, age) is kept outside, by the client or a manager, and passed in to every operation: tree_type.draw(x, y, age). Memory goes from 10,000 textures to one per species; the trade is that each call has to supply the per-tree state again.

classDiagram
    class TreeFactory {
        -types: dict
        +get(species) TreeType
    }
    class TreeType {
        +species
        +texture
        +draw(x, y, age)
    }
    class Forest {
        -placements: list
        +plant(species, x, y, age)
        +draw_all()
    }
    TreeFactory o--> TreeType : one per key
    Forest --> TreeFactory : get species
    Forest ..> TreeType : draw with x y age
The factory owns the shared objects; the client keeps the per-instance numbers and passes them in.

Flyweight: 10,000 placements, one TreeType

from dataclasses import dataclass

@dataclass(frozen=True)
class TreeType:                      # flyweight: shared and immutable
    species: str
    texture: str                     # imagine 2 MB of bitmap here
    def draw(self, x: int, y: int, age: int) -> str:   # extrinsic state comes in as arguments
        return f"{self.species} at ({x},{y}), {age}y"

class TreeFactory:
    _types: dict[str, TreeType] = {}
    @classmethod
    def get(cls, species: str) -> TreeType:
        if species not in cls._types:                  # one object per species, ever
            cls._types[species] = TreeType(species, texture=f"{species}.png")
        return cls._types[species]

forest = [(TreeFactory.get("oak"), x, 2 * x, 10 + x % 3) for x in range(10_000)]
tree, x, y, age = forest[7]
print(len(TreeFactory._types), tree.draw(x, y, age))   # 1 oak at (7,14), 11y
frozen=True makes the shared object immutable. The forest is a list of (shared type, x, y, age) tuples, not 10,000 heavy objects.

When to use it. Thousands or millions of similar objects where most of the state is identical and memory is measured: glyphs in a text editor (one object per character shape, positions outside), particles, map tiles, tokens in a parser, cells in a spreadsheet. Python does this itself for small integers and interned strings, and functools.lru_cache on a factory function is a one-line flyweight factory.

Watch out. Extrinsic state has to be stored and passed on every call, so you trade CPU and some code clarity for memory; measure before you do it. A mutable flyweight is a shared-state bug waiting to happen. Do not confuse it with an object pool (lends out whole mutable objects and takes them back) or with Singleton (one instance of a class, rather than one instance per key).

Interpreter

Interpreter defines a representation for a language's grammar together with an interpreter that uses that representation to evaluate sentences.

The duck simulator grows a tiny scripting language: right; quack; fly, with a repeat 3 ... form. Rather than one function full of string parsing and conditionals, Interpreter gives one class per grammar rule, each with an interpret(context) method. A sentence becomes a tree of these objects, an abstract syntax tree: Command leaves do the work, Sequence and Repeat nodes hold children and call them. Evaluating a program is a recursive walk of the tree, and the context (here, the duck's action log) carries state between nodes. Extending the language is one new class; reading a rule means reading one small class.

classDiagram
    class Expression {
        <<interface>>
        +interpret(context)
    }
    class Command {
        -name
        +interpret(context)
    }
    class Sequence {
        -parts: list
        +interpret(context)
    }
    class Repeat {
        -times
        -body: Expression
        +interpret(context)
    }
    class Context {
        +log: list
    }
    Expression <|.. Command
    Expression <|.. Sequence
    Expression <|.. Repeat
    Sequence o--> Expression : parts
    Repeat o--> Expression : body
    Expression ..> Context : reads and writes
A Composite whose nodes are grammar rules. Terminals act; non-terminals hold children and recurse.

Interpreter: three grammar rules, one tree, one walk

from abc import ABC, abstractmethod

class Expression(ABC):
    @abstractmethod
    def interpret(self, duck: list[str]) -> None: ...

class Command(Expression):                 # terminal: right | quack | fly
    def __init__(self, name: str): self.name = name
    def interpret(self, duck): duck.append(self.name)

class Sequence(Expression):                # expr ; expr ; ...
    def __init__(self, *parts: Expression): self.parts = parts
    def interpret(self, duck):
        for p in self.parts: p.interpret(duck)

class Repeat(Expression):                  # repeat N expr
    def __init__(self, times: int, body: Expression): self.times, self.body = times, body
    def interpret(self, duck):
        for _ in range(self.times): self.body.interpret(duck)

program = Sequence(Command("right"), Repeat(2, Sequence(Command("quack"), Command("fly"))))
duck: list[str] = []
program.interpret(duck)
print(duck)        # ['right', 'quack', 'fly', 'quack', 'fly']
The tree is built by hand here. In a real system a parser builds it from text, which is a separate job the pattern does not cover.

When to use it. A small, stable grammar you evaluate often: rule engines, feature-flag conditions, search filters (price < 20 and tag:sale), format strings, regular-expression matchers, arithmetic in a spreadsheet cell. The structure pays off when new rules arrive more often than new operations.

Watch out. Grammars grow, and class-per-rule stops scaling past a few dozen rules; for anything bigger use a parser generator or Python's own ast module. The pattern says nothing about parsing text into the tree, which is usually the hard part. The shape is Composite's, and Visitor is often used to walk the same tree with a second operation (type-check, pretty-print) without touching the node classes.

Mediator

Mediator encapsulates how a set of objects interact, so they refer to a mediator instead of to each other.

The smart home has an alarm, a coffee pot, a sprinkler and a calendar. When the alarm rings the coffee pot should brew; the sprinkler should skip at the weekend; the calendar should delay the alarm on holidays. Written directly, every appliance ends up holding references to every other one and a slice of the rules, so changing one rule means editing several classes. Mediator moves all the rules into one object. Appliances (colleagues) know only the mediator: they report events to it (notify(sender, event)) and it tells the right colleagues what to do. The n-squared web of references becomes a star, and the rules live in one place.

classDiagram
    class Mediator {
        <<interface>>
        +notify(sender, event)
    }
    class HomeMediator {
        -weekend: bool
        +notify(sender, event)
    }
    class Appliance {
        <<abstract>>
        -mediator: Mediator
        +send(event)
    }
    class Alarm {
        +ring()
    }
    class CoffeePot {
        +brew()
    }
    class Sprinkler {
        +water()
    }
    class Calendar {
        +check_day()
    }
    Mediator <|.. HomeMediator
    Appliance o--> Mediator : reports to
    HomeMediator --> Appliance : commands
    Appliance <|-- Alarm
    Appliance <|-- CoffeePot
    Appliance <|-- Sprinkler
    Appliance <|-- Calendar
A star instead of a web: four colleagues, one mediator, every rule in one class.

Mediator: appliances report, one object decides

class Appliance:
    def __init__(self, name: str, mediator: "HomeMediator"):
        self.name, self.mediator = name, mediator
    def send(self, event: str) -> None:
        self.mediator.notify(self.name, event)         # colleagues talk to the mediator only

class HomeMediator:
    def __init__(self):
        self.actions: list[str] = []
        self.weekend = False
    def notify(self, sender: str, event: str) -> None: # every rule lives here
        if (sender, event) == ("calendar", "weekend"):
            self.weekend = True
        elif (sender, event) == ("alarm", "rang"):
            self.actions.append("coffee pot: brew")
            self.actions.append("sprinkler: skip" if self.weekend else "sprinkler: water")

home = HomeMediator()
calendar, alarm = Appliance("calendar", home), Appliance("alarm", home)
calendar.send("weekend")
alarm.send("rang")
print(home.actions)        # ['coffee pot: brew', 'sprinkler: skip']
The two if branches are the entire house policy. Appliance never imports another appliance.

When to use it. Many objects interact many-to-many and the rules keep changing: dialog boxes where fields enable and validate each other, chat rooms routing messages between users, an air-traffic-style scheduler, entities in a game level reacting to each other.

Watch out. The mediator becomes the god object that knows everything; split it by concern when its notify turns into a wall of branches. Do not mistake it for Observer: a subject broadcasts to whoever subscribed and holds no rules, while a mediator routes by rules and knows its colleagues by name. Facade is one-way (simplify a subsystem for outsiders); Mediator is two-way coordination among peers.

Memento

▶ Video lesson: Memento, Visitor, Interpreter: going back, walking through, reading a language 4:56 · 8 scenes · narrated, pause anytime and explore

Memento captures an object's internal state, without breaking encapsulation, so the object can be restored to that state later.

A game needs save points and undo. The obvious way, reading the character's fields from outside and stashing them, means every field becomes public and every saver knows the layout. Memento keeps the knowledge inside. The originator (Game) creates a memento, an opaque snapshot of its own state, and it alone can read one back in restore(). A caretaker (History) keeps mementos in a stack and hands the latest one back on undo, without ever looking inside. The game's fields stay private, the history class is trivial, and a save point is one push.

classDiagram
    class Game {
        -level
        -hp
        -gold
        +save() Memento
        +restore(m)
    }
    class Memento {
        -level
        -hp
        -gold
    }
    class History {
        -stack: list
        +backup(game)
        +undo(game)
    }
    Game ..> Memento : creates and reads
    History o--> Memento : stores, never opens
    History --> Game : save and restore
Three roles: the originator makes and reads snapshots, the caretaker only stores them.

Save points and undo on a game character

Watch the memento stack grow on each save and shrink on each undo, while level, hp and gold change only inside the game.

Memento: Game saves itself, History only stacks

from dataclasses import dataclass

@dataclass(frozen=True)
class Memento:                          # opaque to everyone but Game
    level: int
    hp: int
    gold: int

class Game:                             # originator
    def __init__(self): self.level, self.hp, self.gold = 1, 100, 0
    def save(self) -> Memento: return Memento(self.level, self.hp, self.gold)
    def restore(self, m: Memento): self.level, self.hp, self.gold = m.level, m.hp, m.gold
    def fight(self): self.level, self.hp, self.gold = self.level + 1, self.hp - 45, self.gold + 50

class History:                          # caretaker: stores, never inspects
    def __init__(self): self._stack: list[Memento] = []
    def backup(self, game: Game): self._stack.append(game.save())
    def undo(self, game: Game):
        if self._stack: game.restore(self._stack.pop())

game, history = Game(), History()
history.backup(game); game.fight(); game.fight(); game.fight()
print(game.hp)                                   # -35
history.undo(game); print(game.level, game.hp)   # 1 100
History never names level, hp or gold. Make the memento frozen so a stored snapshot cannot drift after it is taken.

When to use it. Undo and redo, checkpoints, transactional rollback, "try this and revert if it fails", and anywhere the object's state must stay private. In Python, __getstate__ / __setstate__ and pickle are the stdlib's memento hooks; dataclasses.replace and copy.copy make a snapshot one line.

Watch out. Big state means big snapshots: a text editor that stores the whole document per keystroke runs out of memory. Store diffs, or combine with Command (store the inverse operation instead of the state). Mementos go stale when the originator's structure changes; version them if they are persisted. It is not Prototype: a memento is a snapshot of state for one object to reload, not a new, independent object.

Prototype

Prototype specifies the kinds of objects to create using a prototypical instance, and creates new ones by copying it.

A game spawns monsters whose definitions are loaded at runtime from data files: an orc with 80 hp and an axe, a troll with regeneration. Constructing one from scratch each time means re-reading or re-validating the definition, and the code that spawns cannot know the class in advance. Prototype keeps one configured instance per kind in a registry and creates new monsters by cloning it. The spawner asks for "orc" and gets an independent copy; the registry can be filled from anywhere, including code that did not exist when the spawner was written. The one real decision is how deep the copy goes.

classDiagram
    class Prototype {
        <<interface>>
        +clone() Prototype
    }
    class Monster {
        -kind
        -hp
        -loot: list
        +clone() Monster
    }
    class MonsterRegistry {
        -prototypes: dict
        +register(name, proto)
        +spawn(name) Monster
    }
    class Spawner {
        +spawn_wave()
    }
    Prototype <|.. Monster
    MonsterRegistry o--> Prototype : by name
    Spawner --> MonsterRegistry : spawn name
New objects come from copying configured instances, not from calling constructors by class name.

Prototype: a registry of configured monsters, cloned on demand

import copy
from dataclasses import dataclass, field

@dataclass
class Monster:
    kind: str
    hp: int
    loot: list[str] = field(default_factory=list)
    def clone(self) -> "Monster":
        return copy.deepcopy(self)          # deep: the loot list is not shared

class MonsterRegistry:
    def __init__(self): self._protos: dict[str, Monster] = {}
    def register(self, name: str, proto: Monster): self._protos[name] = proto
    def spawn(self, name: str) -> Monster: return self._protos[name].clone()

registry = MonsterRegistry()
registry.register("orc", Monster("orc", hp=80, loot=["axe"]))   # configured once (file, DB...)
a, b = registry.spawn("orc"), registry.spawn("orc")
b.loot.append("gold"); b.hp -= 30
print(a.hp, a.loot, b.hp, b.loot)       # 80 ['axe'] 50 ['axe', 'gold']
deepcopy is what keeps a.loot and b.loot separate. With copy.copy the two orcs would share one list.

When to use it. Building an object is expensive (parsed config, loaded assets, a warmed cache), the concrete class is chosen at runtime by name, or you need many variants that differ in a few fields from a template. Python makes this cheap: copy, dataclasses.replace(proto, hp=50), or the classes-are-callables trick when a plain constructor is enough.

Watch out. Shallow versus deep copy is the whole risk: a shared mutable sub-object (the loot list, a connection) turns two clones into one. Deep copies of object graphs with cycles need __deepcopy__ or the memo argument. Prototype is not Factory Method (which creates by class, via subclass or callable) and not Memento (which snapshots state for the same object to reload).

Visitor

Visitor represents an operation to be performed on the elements of an object structure, letting you define a new operation without changing the element classes.

The menu tree from chapter 9 (menus containing menu items) now needs a nutrition report, then a price total, then an allergen list. Adding a method to Menu and MenuItem for each one reopens stable classes every time. Visitor turns the dependency around. Every element gets a single accept(visitor) method, which calls back visitor.visit_<element type>(self). A new operation is a new visitor class with one visit_ method per element type; the elements never change again. The callback is double dispatch: the element's type picks the visit_ method, and the visitor's type picks what that method does.

Double dispatch, one arrow at a time: the element decides which visit method runs, the visitor decides what it does.

Visitor: a calorie count added without touching Menu or MenuItem

from abc import ABC, abstractmethod

class MenuItem:
    def __init__(self, name: str, calories: int, price: float):
        self.name, self.calories, self.price = name, calories, price
    def accept(self, visitor): return visitor.visit_item(self)    # 1st dispatch: which element

class Menu:
    def __init__(self, *items): self.items = items
    def accept(self, visitor): return visitor.visit_menu(self)

class Visitor(ABC):
    @abstractmethod
    def visit_item(self, item: MenuItem): ...
    @abstractmethod
    def visit_menu(self, menu: Menu): ...

class CalorieVisitor(Visitor):             # a new operation; Menu and MenuItem untouched
    def visit_item(self, item): return item.calories
    def visit_menu(self, menu): return sum(i.accept(self) for i in menu.items)   # 2nd dispatch: which visitor

lunch = Menu(MenuItem("Pancakes", 520, 6.5), MenuItem("Waffles", 430, 7.0))
print(lunch.accept(CalorieVisitor()))      # 950
Both accept methods are one line. Everything specific to calories is in CalorieVisitor; a PriceVisitor is another twelve lines next to it.

When to use it. A stable structure with many operations added over time: abstract syntax trees (the stdlib's ast.NodeVisitor is exactly this), document models (export to HTML, to PDF, word count), composite scene graphs, compilers and linters. Python's functools.singledispatch gives the type-based dispatch without an accept method on every element, when you own neither the classes nor the traversal.

Watch out. The axes are swapped on purpose: new operations are cheap, new element types are expensive (every visitor changes). If element types change more often than operations, do not use it. Visitors also need the elements' state to be reachable, which pushes fields public. It is not Iterator (traversal without an operation attached) and not Strategy (one operation swapped, no per-type dispatch).

Telling the nine apart

Each of the nine has a neighbour it gets confused with, usually because the class diagrams look alike. The difference is almost always intent: what varies, who decides, and which direction the dependency points. Learn the right-hand column; it is the sentence that earns the point in an interview.

Python note

Python shortcuts, one per pattern: keyword arguments and dataclasses before Builder; copy.deepcopy and dataclasses.replace for Prototype; functools.lru_cache on a factory for Flyweight; __getstate__ / __setstate__ for Memento; functools.singledispatch or ast.NodeVisitor for Visitor; ast or a parser generator once an Interpreter grammar grows; a list of callables tried in order for a quick Chain of Responsibility. Bridge and Mediator have no shortcut: they are about where responsibilities live, and that is design, not syntax.

Common mistakes

  • Pattern first, pain second. A Visitor over two element types with one operation, a Builder that wraps three setters, a Flyweight for forty objects: each adds a hop and saves nothing. Name what hurts before naming the fix.
  • Chains that lose requests. Without a catch-all handler, a Chain of Responsibility silently drops anything new. Decide what the end of the chain means on day one.
  • Shallow clones. A Prototype whose clone() is copy.copy shares every mutable sub-object between "independent" copies. Test that mutating a clone leaves the prototype alone.
  • Mutable flyweights. A shared object that anyone can change is a race condition with a design pattern's name.
  • Visitor on a moving structure. If element types are still being added weekly, every visitor breaks weekly.
  • The all-knowing mediator. When notify is 300 lines of branches, split by concern or you have rebuilt the web of dependencies inside one class.

How to say it in an interview

Say: 'These are the Gang of Four patterns outside the main thirteen, and the skill is recognising them. Bridge is two hierarchies joined by a reference so both can grow. Builder lets the client drive construction step by step. Chain of Responsibility passes a request along handlers until one takes it, so I would add a catch-all at the end. Flyweight shares immutable state across thousands of objects. Interpreter is one class per grammar rule. Mediator centralises the rules between peers, unlike Observer which just broadcasts. Memento is an opaque snapshot for undo. Prototype clones a configured instance. Visitor adds operations to a closed structure through double dispatch.' Then pick the one the problem actually needs and draw that diagram, not all nine.
