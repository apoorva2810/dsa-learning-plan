Being adaptive: Adapter and Facade

Two wrappers that are often confused. Adapter makes an object you cannot change speak the interface your code expects: a turkey passes for a duck, a legacy cursor becomes a Python iterator. Facade puts one simple entry point in front of a subsystem: one watch_movie() call replaces a dozen on six objects. Along the way: object vs class adapters (and why Python can write the second kind), the principle of least knowledge, and how to tell Adapter, Decorator and Facade apart in one sentence.

After this chapter you can
  • Recognise an interface mismatch (right behaviour, wrong method names) and fix it with an adapter without editing either side
  • Name the four Adapter roles and draw the class and sequence diagrams for the turkey-as-duck example
  • Write an object adapter and a class adapter in Python and say when each is the better choice
  • Adapt a legacy cursor to Python's iterator protocol, and handle the method that has no counterpart
  • Explain what a Facade adds (a simpler path) and does not add (behaviour), and apply the principle of least knowledge
  • State the intent of Adapter, Decorator and Facade in one sentence each, and pick the right one from a description

The story: a turkey in the duck simulator

▶ Video lesson: Adapter: a turkey in the duck simulator 3:51 · 7 scenes · narrated, pause anytime and explore

Back in SimUDuck, the simulator has a test_duck(duck) routine that calls quack() and then fly() on any Duck. A partner ships a library of other birds, and marketing wants its WildTurkey in the pond. A turkey can gobble() and fly(), so the behaviour is all there. The names are wrong: test_duck asks for quack, and the turkey has never heard of it.

You own the simulator but not the bird library, and editing either one is the wrong move. This is the situation Adapter is for: two pieces of code that should work together and cannot, because they do not speak the same interface.

Why the two obvious patches fail

Teaching the client about turkeys (isinstance branches) puts knowledge of concrete types into the one place that was supposed to be free of it, and the next library adds another branch. Editing the turkey is impossible when you do not own it and wrong when other code uses it as a turkey. An adapter leaves both alone.

The Adapter pattern, named

Adapter converts the interface of a class into another interface the clients expect. Adapter lets classes work together that could not otherwise because of incompatible interfaces.

Four roles, all present in the story:

RoleIn the storyWhat it is
ClientDuckSimulatorcode written against the target interface; never changes
TargetDuckthe interface the client expects
AdapteeWildTurkeythe object with the right behaviour and the wrong interface
AdapterTurkeyAdapterimplements the target, holds the adaptee, translates each call

The adapter is the only class that knows both vocabularies. The translation can be a rename (quack -> gobble), one call fanning out into several (fly -> five hops), several collapsing into one (the duck adapter's counter), or a call the target has and the adaptee lacks (dealt with in the iterator section below).

Where you have already seen it

  • io.TextIOWrapper: wraps a bytes stream and presents the text-stream interface (read() returns str).
  • iter(callable, sentinel): adapts a "call me until I return None" API to the iterator protocol.
  • contextlib.closing(thing): adapts anything with a close() to the with statement.
  • DB-API drivers: every database engine behind the same connect() / cursor() / execute().
  • asyncio.to_thread(fn): a blocking function presented as an awaitable.
  • SDK wrappers that make a payment provider's REST API look like your PaymentGateway interface.

Absorbing a foreign interface, before and after

Client knows every vendor type

Each new library adds an isinstance branch to every call site. The client is now coupled to classes it was designed to ignore.

class WildTurkey:                                   # vendor code
    def gobble(self): print("Gobble gobble")
    def fly(self): print("I'm flying a short distance")

class CanadaGoose:                                  # next month's vendor code
    def honk(self): print("Honk")
    def migrate(self): print("I'm flying south")

class DuckSimulator:
    def test_duck(self, bird) -> None:
        if isinstance(bird, WildTurkey):            # the client learns every vendor type...
            bird.gobble()
            for _ in range(5):
                bird.fly()
        elif isinstance(bird, CanadaGoose):         # ...and grows a branch per new library
            bird.honk()
            bird.migrate()
        else:
            bird.quack()
            bird.fly()

One adapter per vendor type

The client is untouched and typed against Duck. Vendor code is untouched. One small class carries all the translation.

from abc import ABC, abstractmethod

class Duck(ABC):                         # Target: the interface the simulator was written against
    @abstractmethod
    def quack(self) -> None: ...
    @abstractmethod
    def fly(self) -> None: ...

class WildTurkey:                        # Adaptee: vendor code, not ours to edit
    def gobble(self) -> None: print("Gobble gobble")
    def fly(self) -> None: print("I'm flying a short distance")

class TurkeyAdapter(Duck):               # Adapter: IS-A Duck, HAS-A turkey
    def __init__(self, turkey: WildTurkey, hops: int = 5):
        self.turkey = turkey
        self.hops = hops

    def quack(self) -> None:
        self.turkey.gobble()             # one-to-one translation

    def fly(self) -> None:
        for _ in range(self.hops):       # one-to-many translation
            self.turkey.fly()

def test_duck(duck: Duck) -> None:       # Client: unchanged
    duck.quack()
    duck.fly()

test_duck(TurkeyAdapter(WildTurkey()))   # Gobble gobble, then five short flights

Object adapter vs class adapter

TurkeyAdapter above is an object adapter: it implements the target and holds an adaptee. The other way to be a duck and a turkey at once is to inherit from both: a class adapter. That needs multiple inheritance, which Java does not have (the book stops there), and Python does.

In Python, class TurkeyClassAdapter(Duck, WildTurkey) is one line of plumbing. Two things to get right:

  1. Method resolution order (MRO). Python looks up a method left to right through the bases. Both Duck (abstract) and WildTurkey declare fly(), so the adapter must define its own fly() and say which parent it means: WildTurkey.fly(self), not a bare super().fly() that would land on the abstract one.
  2. Construction. There is no turkey object to pass in; the adapter is the turkey. If WildTurkey.__init__ takes arguments, the adapter's __init__ must forward them.

The object form is the default because it is looser: it wraps any object with the right methods, including subclasses written after the adapter, and the wrapped object can be swapped at runtime. The class form skips one delegation hop and lets you override pieces of the adaptee's behaviour, at the price of being welded to one adaptee class.

The cursor-to-iterator adapter

The book's second example adapts Java's old Enumeration to the newer Iterator. The Python version of that story is a legacy cursor API, has_more() / next_item() / reset(), that you want to drive with a plain for loop. Python's for speaks exactly one language, the iterator protocol: __iter__() returns an object whose __next__() returns the next item or raises StopIteration.

Mapping the two:

Iterator protocolLegacy cursorTranslation
__next__() when more remainhas_more() then next_item()two calls in, one result out
__next__() at the endhas_more() is Falseraise StopIteration
__iter__()(none)return self
(none)reset()cannot be adapted in the iterator-to-cursor direction

The last row is the important one. Every real adapter meets a method on one side with no counterpart on the other. The honest move is to raise (NotImplementedError, or TypeError for protocol methods) with a message that says why, and to document it. Pretending (reset() that silently does nothing) hides a bug until it is far from its cause.

Iterator adapters in Python

The book's shape in Python: __iter__ returns self, __next__ does the two-call dance and converts has_more() == False into StopIteration.

class LegacyCursor:                      # the old API: has_more(), next_item(), reset()
    def __init__(self, rows):
        self._rows, self._i = list(rows), 0
    def has_more(self) -> bool:
        return self._i < len(self._rows)
    def next_item(self):
        row = self._rows[self._i]
        self._i += 1
        return row
    def reset(self) -> None:
        self._i = 0

class CursorIterator:                    # Adapter: speaks Python's iterator protocol, holds a cursor
    def __init__(self, cursor: LegacyCursor):
        self.cursor = cursor
    def __iter__(self):
        return self
    def __next__(self):
        if not self.cursor.has_more():
            raise StopIteration          # how the protocol says "no more"
        return self.cursor.next_item()

for row in CursorIterator(LegacyCursor(["a", "b", "c"])):
    print(row)                           # a, b, c

The other direction needs a one-item lookahead so has_more() can answer, and reset() has no counterpart: raise and say why, do not fake it.

class IteratorCursor:
    """Adapter the other way: any Python iterable behaves like a LegacyCursor."""
    _END = object()

    def __init__(self, iterable):
        self._it = iter(iterable)
        self._peek = next(self._it, self._END)   # read one ahead so has_more() can answer

    def has_more(self) -> bool:
        return self._peek is not self._END

    def next_item(self):
        if self._peek is self._END:
            raise IndexError("cursor exhausted")
        item, self._peek = self._peek, next(self._it, self._END)
        return item

    def reset(self) -> None:                     # the method with no counterpart
        raise NotImplementedError("iterators run once; reset() cannot be adapted")

cursor = IteratorCursor(x * x for x in range(3))
while cursor.has_more():
    print(cursor.next_item())                    # 0, 1, 4

Before writing an adapter class, check the built-ins: iter(callable, sentinel), a generator, or functools.partial is often the whole adapter.

# Python ships adapters for the most common shapes of "old iteration API".

# 1. The API returns a sentinel when it is done: iter(callable, sentinel) is an adapter.
class Feed:
    def __init__(self, items): self._items = list(items)
    def fetch(self):                      # returns None at the end, like many C-style APIs
        return self._items.pop(0) if self._items else None

for item in iter(Feed(["x", "y"]).fetch, None):
    print(item)                           # x, y

# 2. A generator is the three-method adapter class written in four lines.
def rows_of(cursor):                      # cursor has has_more() / next_item()
    while cursor.has_more():
        yield cursor.next_item()

# 3. Argument-shape adapters: functools.partial fixes a signature a callback expects.
from functools import partial
def log(level, msg): print(level, msg)
warn = partial(log, "WARN")               # now matches on_error(msg)
warn("disk 91% full")

Python note: adapters you do not have to write

Python's protocols are duck-typed, so an adapter rarely needs a base class: anything with __iter__ and __next__ is an iterator, anything with __enter__/__exit__ is a context manager. A generator function is a complete iterator adapter in three lines. iter(fn, sentinel) adapts 'call until None' APIs, contextlib.closing adapts close() to with, and functools.partial adapts a signature. Write a class when the translation needs state (the lookahead buffer, the duck adapter's counter) or several methods.

Facade: the home theatre

▶ Video lesson: Facade: one call for movie night 3:18 · 6 scenes · narrated, pause anytime and explore

You have assembled a home theatre: popcorn popper, dimmable lights, a drop-down screen, a projector, an amplifier and a streaming player, each with its own small class. Watching a film is twelve method calls on six objects, in an order you have to remember (amp on before choosing the source, screen down before the projector lights up). Ending the evening is seven more, in reverse.

Nothing is wrong with the components. The problem is the client's experience of them: too many objects, too many calls, too much ordering knowledge. A HomeTheaterFacade fixes that with two methods, watch_movie(title) and end_movie(), that do the choreography. The components stay exactly as they were, still public, still callable directly when you want the volume at 11.

One call, twelve calls

Follow watch_movie() fanning out across the subsystem, end_movie() reversing it, and what happens to the client when the amplifier is replaced.

Facade provides a unified interface to a set of interfaces in a subsystem. Facade defines a higher-level interface that makes the subsystem easier to use.

Three things to hold on to:

  • A facade simplifies; it does not encapsulate. The subsystem classes remain reachable. Clients that want the full control panel use it; clients that want movie night call one method.
  • A facade adds no behaviour. Everything watch_movie() does could be done by hand with the components. If you find yourself adding logic that only the facade can do, that logic belongs in a component (or you are writing a Decorator or a service, not a Facade).
  • A facade decouples. When the amplifier changes its API, the facade changes and its clients do not. One subsystem can have several facades for different kinds of client, and a facade may be the client of another facade.

Where you have already seen it

  • requests.get(url): one call over a Session, connection pool, adapters, cookie jar and response parsing.
  • subprocess.run(cmd): Popen, pipe set-up, communicate(), exit-code check, all behind one function.
  • shutil.make_archive(...): a facade over zipfile and tarfile.
  • logging.basicConfig(): creates a handler, a formatter and wires them to the root logger.
  • pathlib.Path.read_text(): open, read, close, decode, in one method.
  • A CheckoutService.place_order(cart) that calls inventory, pricing, payment and shipping in the right order.

HomeTheaterFacade

class HomeTheaterFacade:
    def __init__(self, amp, player, projector, lights, screen, popper):
        self.amp = amp                       # the facade HAS the subsystem components
        self.player = player
        self.projector = projector
        self.lights = lights
        self.screen = screen
        self.popper = popper

    def watch_movie(self, title: str) -> None:
        self.popper.on()
        self.popper.pop()
        self.lights.dim(10)
        self.screen.down()
        self.projector.on()
        self.projector.wide_screen_mode()
        self.amp.on()
        self.amp.set_source(self.player)
        self.amp.set_surround_sound()
        self.amp.set_volume(5)
        self.player.on()
        self.player.play(title)

    def end_movie(self) -> None:
        self.popper.off()
        self.lights.on()
        self.screen.up()
        self.projector.off()
        self.amp.off()
        self.player.stop()
        self.player.off()
Plain delegation in a fixed order. No state of its own, no logic a client could not have written; that is what makes it a facade and not a service.

Principle of least knowledge

The facade chapter carries one design principle:

Talk only to your immediate friends.

Also known as the Law of Demeter. The idea: the more objects a piece of code reaches through, the more classes it is coupled to, and the more places a change can break it. display.station.get_thermometer().get_reading().celsius couples the display to four classes; if the station ever stores readings differently, the display breaks even though it only wanted a number.

The rule of thumb allows a method four kinds of call target (the table below): the object itself, its parameters, objects it creates, and its own components. What it should not do is call a method on an object that was returned by another call. When you need something from deep inside a friend, ask the friend for it (station.temperature_c()) and let the friend do the reaching. A facade is this principle applied to a whole subsystem: the client has one friend.

The cost is real: more small forwarding methods, and the risk of wrapper classes that exist only to hide a chain. Apply it at boundaries you expect to change (other teams' objects, vendor libraries, persistence), not to every obj.attr.value in a ten-line script. Fluent builders and pathlib chains that return the same kind of object are fine; the rule is about reaching into different objects' internals.

Least knowledge, before and after

Reaching through three objects

The display knows WeatherStation, the thermometer, the reading class and its field name. Four classes can break it.

class WeatherDisplay:
    def __init__(self, station):
        self.station = station

    def render(self) -> str:
        # three objects deep: display -> station -> thermometer -> reading
        reading = self.station.get_thermometer().get_reading()
        return f"{reading.celsius:.1f} C"

Ask the friend

The display knows one method on one friend. How the station gets a temperature is the station's business.

class WeatherStation:
    def __init__(self, thermometer):
        self._thermometer = thermometer

    def temperature_c(self) -> float:        # the station does the reaching
        return self._thermometer.get_reading().celsius

class WeatherDisplay:
    def __init__(self, station):
        self.station = station

    def render(self) -> str:
        return f"{self.station.temperature_c():.1f} C"   # one friend, one call

Common mistakes

  • An adapter that adds features. If TurkeyAdapter.fly() also logs flights and caches the last one, it is an adapter and a decorator in one class, and the next reader cannot tell which behaviour is translation. Keep translation and enrichment in separate wrappers.
  • Adapting by editing. Adding quack() to the vendor class, or isinstance to the client, "works" and spreads knowledge to exactly the places the pattern exists to protect. Use it only when you own both sides and there is one caller.
  • Faking the unmappable method. A reset() that silently does nothing, a remove() that returns None. Raise with a message instead; a loud failure at the call site beats a quiet wrong answer later.
  • A facade with a brain. Once watch_movie() starts deciding things no component can (billing the account, retrying the projector), it is a service with state and rules, and it should be tested and named as one.
  • Hiding the subsystem. A facade is a convenience, not a wall. Making the components private forces every client that needs fine control to copy or bypass the facade.
  • Least knowledge as dogma. Wrapping every a.b.c in a method produces dozens of one-line forwarders. Apply the principle at boundaries that are likely to change, and let fluent chains over the same type be.

How to say it in an interview

Say: 'Adapter and Facade both wrap objects, but with different intent. Adapter is for an object that does the right job under the wrong interface: I implement the interface my client expects and hold the object, translating each call, so neither the client nor the vendor code changes. The turkey passes for a duck; a legacy cursor passes for a Python iterator. Facade is for a subsystem that is correct but tedious: one class with a few high-level methods that call the components in the right order, while the components stay public. It adds no behaviour, it adds a simpler path, and it is the principle of least knowledge applied to a whole subsystem. Decorator is the third wrapper: same interface, extra behaviour.' Then draw the Adapter class diagram and the facade fan-out.
