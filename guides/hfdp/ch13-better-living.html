Better living with patterns

Twelve chapters ended with a pattern name; this one asks what the names are names of. A pattern is a solution to a problem in a context, with its costs stated. You learn to read and write a pattern description, place the fourteen patterns of chapters 1-12 in the Gang of Four grid, route a design question to a pattern by the thing that varies, tell look-alikes apart by intent, and, most useful in interviews, say when a pattern is not worth its cost and when to take one out.

After this chapter you can
  • Define a pattern as problem, solution and context, and name consequences as the part that keeps it honest
  • Read a catalogue entry quickly: know the template headings and what each one tells you
  • Place the fourteen patterns of chapters 1-12 by purpose (creational, structural, behavioural) and scope (class, object)
  • Route a design question through 'what varies?' to a pattern, and separate Strategy from State, Decorator from Proxy, Adapter from Facade by intent
  • Apply the four habits of thinking in patterns: keep it simple, count the cost, refactor towards a pattern, remove one that never earned its place
  • Name the idiomatic Python form of the common patterns and the signal that says the class form is still right

What a pattern is

▶ Video lesson: What a pattern is, and how the catalogue is organised 5:14 · 7 scenes · narrated, pause anytime and explore

Twelve chapters of stories, and each one ended with a name: Strategy, Observer, Decorator. This chapter steps back and asks what those names are names of.

A pattern is a solution to a problem in a context.

Three words carry the weight. The context is a recurring situation: not "my duck simulator" but "a class whose behaviour varies by object and over time". The problem is the goal you have in that situation together with the constraints pulling against it, the forces: reuse the flying code, do not edit the class for each variant, do not let a rubber duck inherit a behaviour it should not have. The solution is a general arrangement of classes and objects that resolves those forces. It is a design you can describe in a paragraph and draw on a whiteboard, one that has been seen in at least three independent systems (the pattern community's rule of three), and it is not a piece of code you paste. A library is code you import; a pattern is something you re-create each time in whatever language you are using, which is why the same Strategy is a class hierarchy in Java and a key= argument in Python.

A fourth part is easy to forget and is what makes a description honest: the consequences. Every pattern trades something. Strategy buys runtime swapping and pays with more classes and one extra hop to follow when reading. A description that lists no costs is advertising, not a pattern.

So "I used Strategy" is a claim about forces, not about shapes. A class that holds an interface and delegates to it is Strategy only if the algorithm genuinely varies and the client chooses it; the same picture with the objects driving their own transitions is State (10 · The state of things: State). The structure is the result of a pattern, not the pattern.

flowchart LR
    CX[Context<br/>a recurring situation] --> PB[Problem<br/>a goal with constraints]
    PB --> FO[Forces<br/>what pulls against what]
    FO --> SO[Solution<br/>a general arrangement]
    SO --> CQ[Consequences<br/>what you gain and pay]
    CQ -.-> CX
Read a pattern description in this order, and check that the forces on the left are really present before you reach for the solution on the right.

How to describe a pattern

The Gang of Four fixed a template for writing a pattern down, and every catalogue since has kept most of it. Knowing the template does two things for you: you can read any pattern catalogue quickly, because you know where to look for the forces and the costs, and you can recognise when something you built deserves a write-up for your team. The chapters in this track follow the same skeleton under friendlier headings.

Two patterns from this track, written up with the template

Strategy, written as a catalogue entry

Intent. Define a family of algorithms, encapsulate each one, and make them interchangeable, so the algorithm varies independently of the clients that use it.

Motivation. A duck simulator whose ducks fly and quack differently; behaviour added to the superclass reaches subclasses that should not have it (1 · Welcome to design patterns: Strategy).

Applicability. Several related classes differ only in behaviour; you need variants of an algorithm; an algorithm uses data the client should not know about; a class has a conditional that selects between behaviours.

Participants. Context holds a Strategy and delegates to it; Strategy declares the common interface; ConcreteStrategy implements one algorithm.

Consequences. Gain: swapping at runtime, no conditionals, reuse by composition. Pay: clients must know the strategies to pick one; more objects; one interface that has to suit every algorithm in the family.

Known uses. Sorting with a key function, retry policies, payment gateways, compression codecs.

Related. State has the same structure and a different intent; Template Method varies steps by inheritance instead of composition.

Observer, written as a catalogue entry

Intent. Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically.

Motivation. A weather station with several displays that must all refresh when a new reading arrives (2 · Keeping your objects in the know: Observer).

Applicability. A change in one object requires changes in others, and you do not know how many; an object must notify others without knowing who they are.

Participants. Subject keeps the list and notifies; Observer declares update(); ConcreteSubject holds the state; ConcreteObserver reacts.

Consequences. Gain: loose coupling, broadcast, observers added and removed at runtime. Pay: update cascades that are hard to trace; observers that do not know what changed unless the data is pushed; dangling references when nobody unregisters.

Known uses. GUI event listeners, model-view bindings, message buses, asyncio futures with callbacks.

Related. Mediator centralises the communication in one object; publish-subscribe adds a broker between subject and observers.

The catalogue

The Gang of Four sorted their 23 patterns along two axes. Purpose asks what the pattern is for: creational patterns are about making objects, structural patterns about how classes and objects are put together, behavioural patterns about how objects share work and talk to each other. Scope asks what the pattern fixes at compile time and what it leaves to runtime: class-scope patterns use inheritance, so the relationship is settled when the class is written; object-scope patterns use composition, so it can change while the program runs. Nearly everything in this book is object scope, which is the composition-over-inheritance principle of 1 · Welcome to design patterns: Strategy showing up in the shape of the catalogue itself.

Below: the fourteen patterns from chapters 1 to 12 with the thing each one lets you vary, then the full grid, then a flowchart that routes by the question you are actually asking. The nine patterns the book leaves for its appendix are in 14 · Leftover patterns (appendix).

Same shape, different intent

Several patterns draw the same class diagram. That is not a flaw in the catalogue; it is the reason the catalogue exists. A diagram shows structure, and a pattern is named by intent: the problem it was chosen to solve. When two patterns share a picture, the difference is in who decides and why, and that is what to say when you name one.

Say the question, not just the names. The question is what shows you chose the pattern for its intent and not for its silhouette.

Thinking in patterns

▶ Video lesson: Thinking in patterns, and when not to 3:14 · 5 scenes · narrated, pause anytime and explore

Knowing twenty-three patterns is the easy part. The skill is knowing when not to use one. Four habits:

Keep it simple. The goal is the simplest design that solves today's problem, not the most pattern-rich one. Patterns are a means. If a plain function or a single if solves the problem and nothing varies, that is the right design, and a pattern would be noise.

Patterns are not free. Each one adds an interface to maintain, more classes, an indirection the reader has to follow, and a name the team has to know. Those costs are worth paying when the forces are present: real variation, a real need for runtime change, a real second implementation. Count the forces before you count the patterns.

Refactor towards them. Patterns show up most reliably during refactoring, not on day one. The first version has one case. The second arrives and you write an if. The third makes the shape obvious: this is what varies. Now the forces are real, and the catalogue tells you the name of the refactoring you are about to do. Design on day one for the variation you are sure of, and let the rest earn its way in.

Know when to take one out. A pattern whose variation never arrived is dead weight: an interface with one implementation, a factory that only ever makes one class, a Singleton that is a global in a hat. Removing it is as much a design act as adding it was. Inline the one case and delete the scaffolding.

One more thing patterns give you even when you do not apply them: a shared vocabulary. "Decorate the stream" says in three words what would otherwise take a paragraph, and a design review conducted in pattern names stays at the level of design instead of dropping into line-by-line code.

flowchart TD
    A{Does it vary today,<br/>or are you sure it will?} -->|no| B[Write the simplest<br/>thing that works]
    A -->|yes| C{Do the forces match<br/>a pattern you know?}
    C -->|no| D[Refactor by hand<br/>and name what varies]
    C -->|yes| E[Apply the smallest<br/>version that fits]
    B --> F[Revisit when the<br/>second case lands]
    E --> G{Months later, did<br/>the variation arrive?}
    G -->|no| H[Remove it and<br/>inline the one case]
    G -->|yes| I[Keep it, it is<br/>paying its way]
A pattern enters when the forces are real and leaves when they turn out not to be. Both moves are design.

The same settings loader, two ways

Pattern-first

Three patterns and five classes for a problem with one case. Every reader pays the indirection; nobody gets flexibility, because nothing varies.

# Day 1 of a settings loader, designed "properly" before any need appeared
from abc import ABC, abstractmethod
import json

class SettingsSource(ABC):
    @abstractmethod
    def load(self) -> dict: ...

class JsonFileSource(SettingsSource):
    def __init__(self, path: str): self.path = path
    def load(self) -> dict:
        with open(self.path) as f:
            return json.load(f)

class SettingsSourceFactory(ABC):
    @abstractmethod
    def create(self) -> SettingsSource: ...

class JsonSourceFactory(SettingsSourceFactory):
    def __init__(self, path: str): self.path = path
    def create(self) -> SettingsSource: return JsonFileSource(self.path)

class Settings:
    _instance = None                       # Singleton, "in case two loads disagree"
    def __new__(cls, factory: SettingsSourceFactory):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance.values = factory.create().load()
        return cls._instance

settings = Settings(JsonSourceFactory("settings.json"))
# 5 classes, 3 patterns, one JSON file. Nothing varies yet.

Need-first

One function today. The comment names the signal that would justify a pattern later, and which one.

# The same job, the day it is needed
import json

def load_settings(path: str = "settings.json") -> dict:
    with open(path) as f:
        return json.load(f)

settings = load_settings()

# When a second source really arrives (environment variables, a secrets
# manager), the forces change: "the source varies, the caller does not care
# which". That is when a Strategy-shaped loader earns its keep:
#
#     def load_settings(source: Callable[[], dict]) -> dict:
#         return source()
#
# ...with one callable per source. Still no factory, still no singleton.

Patterns are not free

Every pattern adds at least one interface, one more class and one indirection. Three patterns on a problem with no variation is three times the reading cost for zero flexibility. The test for each pattern in a design: name the second implementation that exists or is scheduled. If you cannot, take it out.

Patterns Python gives you for free

Many of the 23 patterns exist because the Java and C++ of the 1990s could not pass a function around, could not add behaviour to an object at runtime, and made the class the only unit of reuse. Python can do all three, so several patterns shrink to a language feature. The pattern is still there, with the same forces and the same intent; only the ceremony is gone. Know both forms: the class form when you need state, several methods or a name the team will recognise, and the idiomatic form the rest of the time.

Five intents, no class diagram

import json
from functools import partial

# Strategy: any callable is a one-method strategy
def export_csv(rows): return "\n".join(",".join(map(str, r)) for r in rows)
def export_json(rows): return json.dumps(rows)
EXPORTERS = {"csv": export_csv, "json": export_json}      # Simple Factory: a dict lookup

def export(rows, fmt="csv"):
    return EXPORTERS[fmt](rows)                             # delegate to the chosen strategy

# Observer: a list of callables
class Thermometer:
    def __init__(self): self._listeners = []; self.reading = None
    def subscribe(self, fn): self._listeners.append(fn)
    def set(self, value):
        self.reading = value
        for fn in self._listeners: fn(value)                # notify

# Command: a closure or a partial is a request packaged for later
undo_stack = [partial(print, "undo: set volume back to", 3)]

# Iterator: a generator is an iterator with no class at all
def countdown(n):
    while n: yield n; n -= 1

# Singleton: a module is created once and shared; this file *is* the instance
CONFIG = {"theme": "dark"}
Each block is a pattern from this track with its ceremony removed. The forces are unchanged: the exporter still varies, the listeners still do not know each other.

Python note

Saying 'this is a Strategy' about a key= argument is correct and useful: the forces and intent are identical, only the ceremony differs. In an interview, name the pattern and then say which form you would write and why. That shows you know the idea and are not copying the class diagram.

Anti-patterns

An anti-pattern is the mirror image of a pattern: a recurring solution that looks attractive, gets applied often, and makes things worse, together with a known way out. Describing one takes the same discipline as describing a pattern: the problem, the tempting solution, why people fall for it, what it costs, and the refactored solution. Writing anti-patterns down is how a team stops relearning the same lesson.

Several of the ones below are patterns applied without their forces, which is why this section sits where it does.

Most of these are a pattern (or a habit) applied where its forces are absent. The cure is the same every time: name what varies, or admit that nothing does.

Three anti-patterns, written up like patterns

Golden hammer

Problem. A team must solve design problems of many kinds with limited time.

Tempting solution. Reach for the pattern you know best: Strategy for everything that could conceivably vary, Singleton for everything shared, Observer for every call between two modules.

Why it attracts. Familiarity feels like speed, and the pattern did solve the last problem.

What it costs. Problems get bent to fit the tool: a one-case Strategy, an Observer chain nobody can trace, a Singleton that is really a global.

Refactored solution. Describe the forces of the new problem before naming anything, use the catalogue's flowchart rather than your habit, and be willing to answer "no pattern".

Speculative generality

Problem. You expect requirements to change and want to be ready.

Tempting solution. Abstract everything now: an interface for each class, a factory for each object, hooks for steps nobody has asked to vary.

Why it attracts. It looks like experience, and adding abstraction feels productive.

What it costs. Every reader pays the indirection, every change crosses three files, and when variation does arrive it is usually somewhere else.

Refactored solution. Write the concrete version and keep tests. When the second case arrives, write an if. At the third, refactor towards the pattern whose forces you can now see. Delete abstractions that still have one implementation after a year.

Singletonitis

Problem. Several parts of a program need the same object: a configuration, a connection pool, a logger.

Tempting solution. Make the class a Singleton and call get_instance() wherever it is needed.

Why it attracts. No parameters to thread through; it works immediately.

What it costs. Hidden dependencies (a class's collaborators do not appear in its signature), tests that leak state into each other, and one more thing that cannot be swapped for a fake.

Refactored solution. Pass the object in (constructor injection). If one instance really is required, create it once at the top of the program or as a module-level object, and keep the class itself ordinary (5 · One-of-a-kind objects: Singleton).

The Gang of Four and the pattern community

The catalogue in this chapter comes from Design Patterns: Elements of Reusable Object-Oriented Software (1994) by Erich Gamma, Richard Helm, Ralph Johnson and John Vlissides, who have been "the Gang of Four" ever since. The book named 23 patterns, fixed the creational / structural / behavioural split and the catalogue template above, and borrowed the very idea of a pattern from the architect Christopher Alexander, whose A Pattern Language (1977) described towns and buildings as solutions to recurring problems in a context. Around the book grew a community: the Hillside Group (1993) and its PLoP conferences (Pattern Languages of Programs, since 1994), where patterns are workshopped before they are published, and a shelf of later catalogues for other levels of design, from Fowler's enterprise application patterns and Hohpe and Woolf's integration patterns to Nystrom's game programming patterns and the cloud and microservice catalogues of the last decade. Head First Design Patterns, the book this track follows, is a teaching retelling of the Gang of Four catalogue. When you meet a pattern that neither book covers, the template in this chapter is how you read it.

Common mistakes

  • Naming the shape, not the intent. Any wrapper becomes "a Decorator", any lookup "a Factory". Say the forces: we wrap to add behaviour and the wrappers stack is Decorator; we wrap to control access to one object is Proxy.
  • Pattern-first design. Choosing patterns before the problem is understood. Patterns are refactoring targets far more often than starting points.
  • Counting patterns as a merit. Five patterns on a small problem is a smell, not a strength. Each one should be able to name its second implementation.
  • Never removing one. A pattern whose variation did not arrive is overhead. Inline it and keep the tests.
  • Treating the catalogue as complete. The 23 cover object-oriented design at class scale. Concurrency, distribution and architecture have their own catalogues, and the technique of writing a pattern down applies to all of them.
  • Forgetting the Python form. Describing Strategy well and then writing an ABC with one method when a callable was the idiomatic answer. Know both forms and say which you would use.

How to say it in an interview

Say: 'A design pattern is a general solution to a recurring design problem in a context, with its trade-offs stated. I use patterns in two ways: as vocabulary in design discussions, and as refactoring targets once code has shown that something really varies. On a new problem I start with the simplest design and reach for a pattern when its forces are present. For example, three export formats chosen at runtime is Strategy, and in Python that is a dictionary of callables rather than a class hierarchy unless the formats carry state.' Then, for any specific pattern, give the intent, the shape, and one cost.
