Decorating objects: Decorator

A coffee shop needs condiments on every drink in any combination. Subclassing explodes, flags in the superclass turn one method into the place every menu change lands, and the fix teaches the open-closed principle: wrap objects in other objects of the same type that delegate and add. That is the Decorator pattern, and Python has it built into its syntax.

After this chapter you can
  • Tell the Starbuzz story and name the two designs that fail, and why each one fails
  • State the open-closed principle and point to where the decorator design is open and where it is closed
  • Draw the Decorator class diagram (component, concrete component, decorator, concrete decorators) and explain why the decorator extends the component
  • Trace cost() through a chain of wrappers inward to the plain object and back out
  • Explain how Python's @decorator syntax and io stream layering are the same pattern, and when to use each shape
  • Distinguish Decorator from Proxy, Adapter, Strategy and plain subclassing by intent

The Starbuzz story

▶ Video lesson: The Starbuzz story: class explosion, flags, and the open-closed fix 4:44 · 6 scenes · narrated, pause anytime and explore

Starbuzz Coffee is growing fast, and its ordering system was written for a smaller menu. There is an abstract Beverage class with a description and an abstract cost(), and one subclass per drink: HouseBlend, DarkRoast, Espresso, Decaf. Each subclass returns its own price. Clean enough.

Then the menu gets condiments: steamed milk, soy, mocha, whip, each with a price, in any combination, and the bill has to add them up. The first design that comes to mind is a subclass per combination. The second is a set of condiment flags in Beverage. Both feel reasonable for about a week.

Watch the costs land in the simulation. It is the duck lesson from 1 · Welcome to design patterns: Strategy from a new angle: the problem is never the arithmetic, it is deciding at compile time, in a class hierarchy, something that is decided per order at the counter.

Why both repairs fail

A subclass per combination bakes the combination into a type: 4 drinks x 16 condiment subsets is 64 classes before sizes, and a mocha price change edits half of them. Flags in the superclass keep the class count down but move every condiment and every price into the one class all drinks share: a price change, a new condiment or 'double mocha' means opening it, and drinks that should never have whip inherit the flag anyway. Both decide at compile time what the counter decides per order.

The open-closed principle

The principle this chapter introduces:

Classes should be open for extension, but closed for modification.

Closed for modification: code that already works, has been tested and has shipped is not edited when a new requirement lands. Open for extension: new behaviour can still be added, by writing new code next to the old rather than inside it. The two halves sound contradictory until you see a design that does both. Strategy did it in chapter 1 (a new FlyBehavior class, no edit to Duck); Decorator does it here (a new condiment class, no edit to any beverage).

The flag design violates it in the most direct way. Every new condiment and every price change is an edit to Beverage.cost(), the one method every drink in the system depends on. Each edit is a chance to break something that already worked, and each needs the whole menu re-tested.

Closed where, exactly?

You cannot close a class against every kind of change, and trying to makes code abstract and hard to read. Pick the axes that actually change, here which condiments an order has and how many, and design so that those changes arrive as new classes or new objects. Leave everything else plain. The fixed design below is open along exactly one axis: new condiment types, and new combinations of them, including a condiment applied twice.

Wrapping: how a decorator works

A decorator is an object that wraps another object and stands in for it. Four facts make the trick work:

  1. Same supertype. A Mocha is a Beverage, so it can go anywhere a Beverage can, including inside another condiment.
  2. Holds a reference. The decorator keeps the wrapped object in a field (self.beverage). That is has-a, chapter 1 again.
  3. Delegates, then adds. Mocha.cost() asks the wrapped beverage for its cost and adds 0.60. The extra work can happen before the delegated call, after it, or on both sides.
  4. Nests. Because of fact 1 you can wrap a wrapper: Whip(Mocha(Mocha(DarkRoast()))). Each layer knows only the one object directly inside it.

The client holds the outermost object and calls cost() once. It has no idea it is talking to four objects. The call travels inward through every layer to the plain beverage, which answers first, and the answer travels back out, growing at each layer. That inward-then-outward trip is the heart of the pattern; watch it in the simulation, then in the sequence diagram.

The Decorator pattern, named

▶ Video lesson: Decorator: wrap, delegate, add 3:33 · 5 scenes · narrated, pause anytime and explore

What the chapter built has a name:

Decorator attaches additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality.

Additional responsibilities are the condiments; dynamically means at the counter, per order, by wrapping, not at compile time by subclassing; alternative to subclassing is the point of the whole chapter: new behaviour without a class per combination.

The roles, mapped to the story:

RoleIn Starbuzz
Component (the interface everyone shares)Beverage
Concrete component (the thing that gets wrapped)HouseBlend, DarkRoast, Espresso, Decaf
Decorator (abstract: is-a component, has-a component)CondimentDecorator
Concrete decorators (one responsibility each)SteamedMilk, Soy, Mocha, Whip

Where you have already seen it

  • Python's io layering. open("f.txt") hands you a TextIOWrapper around a BufferedReader around a FileIO; each has read() and adds one job (decoding, buffering, the raw system call).
  • Java's java.io streams, the textbook example: a BufferedInputStream around a FileInputStream, a DataInputStream around either, all InputStreams.
  • gzip.GzipFile(fileobj=...) and ssl.SSLSocket: a file-like or socket-like object wrapping another and adding compression or encryption behind the same methods.
  • WSGI and ASGI middleware: an application is a callable; middleware is a callable that holds the application and adds logging, authentication or compression around the call.
  • @functools.lru_cache, @functools.wraps, @retry: function decorators wrap a callable in another callable, which is this pattern for functions (see the Python note).
  • GUI toolkits: a scrollbar or border around any widget, drawn by delegating draw() to the widget and then painting the frame.

The Starbuzz code, before and after

Condiments as flags in the superclass

Every condiment and every price lives in one method all drinks share. A new topping or a price change opens it; a boolean cannot count; iced tea gets a whip flag.

class Beverage:
    def __init__(self, description: str, base_cost: float):
        self.description = description
        self._base_cost = base_cost
        self.milk = self.soy = self.mocha = self.whip = False   # one flag per condiment

    def cost(self) -> float:                   # every condiment price lives here
        total = self._base_cost
        if self.milk:  total += 0.30
        if self.soy:   total += 0.45
        if self.mocha: total += 0.60           # double mocha? a bool cannot say it
        if self.whip:  total += 0.35
        return total

class DarkRoast(Beverage):
    def __init__(self): super().__init__("Dark Roast", 2.60)

class IcedTea(Beverage):                       # inherits milk and whip flags it should not have
    def __init__(self): super().__init__("Iced Tea", 1.90)

order = DarkRoast()
order.mocha = True
order.whip = True
print(f"{order.cost():.2f}")                   # 3.55

Condiments as decorators

Each condiment is a Beverage that holds a Beverage, delegates inward and adds its price. Orders are wrapped at runtime; new condiment = new class; nothing existing is edited.

from abc import ABC, abstractmethod

class Beverage(ABC):                           # Component: what every order is
    @abstractmethod
    def description(self) -> str: ...
    @abstractmethod
    def cost(self) -> float: ...

class DarkRoast(Beverage):                     # Concrete component: knows only its own price
    def description(self): return "Dark Roast"
    def cost(self): return 2.60

class HouseBlend(Beverage):
    def description(self): return "House Blend"
    def cost(self): return 2.40

class CondimentDecorator(Beverage):            # Decorator: IS-A Beverage and HAS-A Beverage
    def __init__(self, beverage: Beverage):
        self.beverage = beverage               # the object being wrapped

class Mocha(CondimentDecorator):
    def description(self): return self.beverage.description() + ", Mocha"
    def cost(self): return self.beverage.cost() + 0.60     # delegate inward, then add

class Whip(CondimentDecorator):
    def description(self): return self.beverage.description() + ", Whip"
    def cost(self): return self.beverage.cost() + 0.35

order = Whip(Mocha(Mocha(DarkRoast())))       # assembled at the counter, at runtime
print(order.description())                     # Dark Roast, Mocha, Mocha, Whip
print(f"{order.cost():.2f}")                   # 4.15

Python note: decorators for callables, wrappers for streams

▶ Video lesson: Python note: @decorator is the same pattern 2:32 · 6 scenes · narrated, pause anytime and explore

Python has the pattern built into its syntax. @timed above a def means fetch = timed(fetch): timed takes a callable and returns a callable that holds the original and calls it, adding behaviour around the call. Check the four facts: same supertype (callable in, callable out), holds a reference (the closure over fn), delegates and adds, nests (@timed above @retry is timed(retry(fetch)), outermost first, exactly like Whip(Mocha(...))).

Two details carry over from the beverages. The description problem ("Dark Roast, Mocha, Whip") becomes __name__ and __doc__ for functions: a wrapper hides them unless you copy them across with functools.wraps. And the same-type rule is what lets layers stack: a decorator that returns something that is not callable breaks every decorator above it, just as a condiment that was not a Beverage could not be wrapped again.

For objects rather than callables, the io module is a decorator chain you use every day, and __getattr__ can forward every method you do not override to the wrapped object, so a wrapper that changes one method does not have to restate the other twenty.

Decorator in Python, three ways

The book's shape in Python. Use it when the wrapped thing has several methods and state, or when the decoration is chosen per object from data (an order, a config).

from abc import ABC, abstractmethod

class Beverage(ABC):                           # Component: what every order is
    @abstractmethod
    def description(self) -> str: ...
    @abstractmethod
    def cost(self) -> float: ...

class DarkRoast(Beverage):                     # Concrete component: knows only its own price
    def description(self): return "Dark Roast"
    def cost(self): return 2.60

class HouseBlend(Beverage):
    def description(self): return "House Blend"
    def cost(self): return 2.40

class CondimentDecorator(Beverage):            # Decorator: IS-A Beverage and HAS-A Beverage
    def __init__(self, beverage: Beverage):
        self.beverage = beverage               # the object being wrapped

class Mocha(CondimentDecorator):
    def description(self): return self.beverage.description() + ", Mocha"
    def cost(self): return self.beverage.cost() + 0.60     # delegate inward, then add

class Whip(CondimentDecorator):
    def description(self): return self.beverage.description() + ", Whip"
    def cost(self): return self.beverage.cost() + 0.35

order = Whip(Mocha(Mocha(DarkRoast())))       # assembled at the counter, at runtime
print(order.description())                     # Dark Roast, Mocha, Mocha, Whip
print(f"{order.cost():.2f}")                   # 4.15

The idiomatic shape when the thing being extended is a callable and the addition is cross-cutting: timing, caching, retries, authentication.

# A function decorator is the same idea for callables: take a callable, hold it, delegate to it,
# add behaviour around the call, and return something of the same type (another callable).
import functools
import time

def timed(fn):
    @functools.wraps(fn)                       # keep fn's name and docstring (the "description" problem)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = fn(*args, **kwargs)           # delegate to the wrapped callable
        print(f"{fn.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper

def retry(times: int):                         # a decorator with a parameter: Mocha(beverage) with a price
    def decorate(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            for attempt in range(times):
                try:
                    return fn(*args, **kwargs)
                except ConnectionError:
                    if attempt == times - 1:
                        raise
        return wrapper
    return decorate

@timed                                         # outer layer
@retry(times=3)                                # inner layer: fetch = timed(retry(3)(fetch))
def fetch(url: str) -> str:
    return "payload for " + url

fetch("https://example.com")                   # timed -> retry -> fetch, then back out

The object form in the standard library, plus __getattr__ forwarding so a wrapper only has to spell out the method it changes.

import gzip
import io

# open("report.log") builds this chain for you; each layer has read() and adds one job.
raw = io.FileIO("report.log", "rb")                   # concrete component: bytes from the OS
buffered = io.BufferedReader(raw)                     # decorator: fewer syscalls, same read()
text = io.TextIOWrapper(buffered, encoding="utf-8")   # decorator: decodes bytes to str

# gzip.GzipFile wraps any file-like object and adds decompression behind the same read().
with gzip.GzipFile(fileobj=open("report.log.gz", "rb")) as gz:
    head = gz.read(100)

class Forwarding:
    """A decorator that changes one method and forwards the other twenty untouched."""
    def __init__(self, wrapped):
        self._wrapped = wrapped
    def read(self, size=-1):
        data = self._wrapped.read(size)
        return data.upper()                           # the added responsibility
    def __getattr__(self, name):                      # everything else: delegate as-is
        return getattr(self._wrapped, name)
flowchart LR
    T["TextIOWrapper<br/>bytes to str"] -->|"wraps"| B["BufferedReader<br/>fewer system calls"] -->|"wraps"| F["FileIO<br/>raw bytes from the OS"]
What open('f.txt') returns: three objects, each with read(), each adding one job. Pass 'rb' and the outer layer is simply not added.

Python note

Reach for @decorator functions when the thing being extended is a callable and the addition is cross-cutting (timing, caching, retries, auth). Reach for the class shape when the wrapped object has several methods and state, or when the decoration is chosen per object at runtime from data. Either way keep the wrapper the same type as what it wraps, and preserve identity details (functools.wraps, __getattr__ forwarding, a __repr__) so the layers stay invisible to callers.

Decorator and its look-alikes

Several patterns are "an object standing in front of another object". They differ in intent, and interviewers ask for the intent, not the shape.

PatternSame interface as the wrapped object?IntentTypical layering
DecoratorYesAdd responsibilities (behaviour, state) around an objectMany layers, composed by the client at runtime
Proxy (chapter 11)YesControl access: lazy loading, remote calls, permissionsOne layer, usually created for the client
Adapter (chapter 7)No: converts to the interface the client expectsMake an incompatible interface fitOne layer
Strategy (chapter 1)Not a wrapper: a part the context holdsSwap how one operation is doneThe context holds exactly one
SubclassYes, by inheritanceExtend a class, fixed for every instance at compile timeOne level per variant
Decorator and Proxy share a structure; the difference is what the extra layer is for.

Same shape, different intents. Decide by what the extra layer is for and whether callers must see the same interface.

Common mistakes

  • Type checks on the chain. isinstance(order, DarkRoast) is false once the drink is wrapped. Code that inspects concrete types defeats the pattern; decorators are only transparent to clients that program to the component interface (chapter 1's second principle).
  • Decorators that know their neighbours. A Whip that checks whether it wraps a Mocha to adjust its price couples layers that were meant to be independent. Each layer should use only the component interface of the object inside it.
  • Forgetting the delegation. A decorator that returns 0.35 instead of self.beverage.cost() + 0.35 has cut the chain. Every overridden method must call through, before or after adding its own work.
  • Losing identity. Wrappers hide the original's name, docstring and attributes. For functions use functools.wraps; for objects forward with __getattr__ or give the decorator a __repr__ that shows the chain.
  • Too many small objects. Twenty layers make stack traces long and construction verbose. Hide the wrapping behind a factory or builder (chapter 4) when clients should not assemble chains by hand.
  • Decorator where a flag would do. One optional behaviour that never stacks and never changes at runtime is a boolean parameter or a subclass. The pattern earns its objects when behaviours combine and are chosen per instance.

How to say it in an interview

Say: 'Starbuzz needed condiments on every drink in any combination. A subclass per combination explodes, and condiment flags in the superclass push every price change into one shared method and give iced tea a whip flag. I would make each condiment a small class that extends Beverage and holds a Beverage: it delegates cost() inward and adds its own price. Orders are built by wrapping at runtime, so a new condiment is a new class and nothing existing is edited, which is the open-closed principle. That is Decorator; Python's @decorator syntax is the same idea for functions.' Then draw the component / decorator diagram and trace one cost() call inward and back out.
