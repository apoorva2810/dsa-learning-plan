Baking with OO goodness: the Factory patterns

A pizza store's ordering code names every pizza class, so every menu change reopens it; then the franchises want their own pizzas but must keep the process; then they start cutting corners on ingredients. Each requirement moves object creation one step further from the code that uses the objects: Simple Factory, Factory Method, Abstract Factory. Behind all three sits the dependency inversion principle: depend on abstractions, not on concrete classes.

After this chapter you can
  • Explain, with the PizzaStore story, why a constructor call inside otherwise stable code is a design decision
  • Tell Simple Factory, Factory Method and Abstract Factory apart by what varies and by inheritance vs composition
  • Draw the Factory Method class diagram (creator, concrete creators, product, concrete products) and write it in Python
  • Draw the Abstract Factory class diagram (ingredient factories) and explain why the family stays consistent
  • State the dependency inversion principle, say what gets inverted, and apply its three guidelines with judgement
  • Replace an if-chain of constructors with a Python registry, and know when a classmethod constructor is enough

The PizzaStore story

▶ Video lesson: The pizza store: from an if-chain to Factory Method 5:48 · 7 scenes · narrated, pause anytime and explore

A pizza store's order_pizza(kind) does two jobs in one method: it decides which pizza class to instantiate (an if / elif chain over "cheese", "greek", "pepperoni"), and it runs the four steps every pizza goes through: prepare(), bake(), cut(), box(). Marketing changes the menu; the method is reopened. Marketing changes it again; reopened again. The four steps never change, but they live in the method that does.

In Python there is no new keyword, but CheesePizza() is the same thing: a constructor call that hard-codes a concrete class into the code that contains it. Instantiation is not wrong. Instantiating inside code that should stay closed is the trap this chapter is about, and the three factories are three ways of moving that decision somewhere it can change safely.

The ordering code meets the menu, then the franchises

Step through two menu changes and the simple factory that absorbs them; then switch scenario to see why a factory handed in from outside cannot protect the store's process.

Why 'new' is a design decision

Every constructor call names a concrete class, which means the code containing it depends on that class. Scattered through a codebase, those calls are the reason a new product type means a dozen edits. The factories do not remove instantiation (something has to call the constructor); they move it to one place whose job is to change.

Simple Factory: an idiom, not a pattern

The first move is small. Take the if chain out of order_pizza and put it in its own class, SimplePizzaFactory, with one method create_pizza(kind) that returns a Pizza. The store holds a factory and asks it; the store's code no longer names a single concrete pizza.

What did we gain? The chain is still there, but it has one home. The store, the menu printer and the web order form all ask the same factory, so a menu change is one edit instead of three. The store's own code is closed.

Why is this called an idiom rather than a pattern? Nothing in it varies by subclass or by configuration: there is exactly one factory, and the decision inside it is a lookup. It is a habit worth having, and it is the first thing most people mean when they say "factory", but there is no abstraction whose implementations are swapped. The two real patterns in this chapter add exactly that.

In Python the simple factory is often a module-level function, or, since classes are callables, a dictionary from name to class (see the Python note below).

Constructors inside the process

Which-pizza and how-to-make-it share a method. Four concrete classes are named in code that should be closed.

class PizzaStore:
    def order_pizza(self, kind: str) -> "Pizza":
        # the part that changes with the menu...
        if kind == "cheese":
            pizza = CheesePizza()
        elif kind == "pepperoni":
            pizza = PepperoniPizza()
        elif kind == "clam":
            pizza = ClamPizza()
        elif kind == "veggie":
            pizza = VeggiePizza()
        else:
            raise ValueError(f"unknown pizza: {kind}")
        # ...glued to the part that never changes
        pizza.prepare()
        pizza.bake()
        pizza.cut()
        pizza.box()
        return pizza

Creation moved into a simple factory

The store asks the factory and runs the process. Menu changes touch the factory only, and every client shares it.

class SimplePizzaFactory:
    """The if-chain has one home now; every client that needs a pizza asks here."""
    def create_pizza(self, kind: str) -> "Pizza":
        if kind == "cheese":
            return CheesePizza()
        if kind == "pepperoni":
            return PepperoniPizza()
        if kind == "clam":
            return ClamPizza()
        if kind == "veggie":
            return VeggiePizza()
        raise ValueError(f"unknown pizza: {kind}")

class PizzaStore:
    def __init__(self, factory: SimplePizzaFactory):
        self.factory = factory                      # the store HAS-A factory

    def order_pizza(self, kind: str) -> "Pizza":
        pizza = self.factory.create_pizza(kind)     # no concrete pizza class named in the store
        pizza.prepare()
        pizza.bake()
        pizza.cut()
        pizza.box()
        return pizza

Factory Method: the subclass decides

Franchises change the problem. New York wants thin crust and marinara, Chicago wants deep dish and plum tomato, and each region should pick its own pizzas. Passing a regional factory into the store (`PizzaStore( NYPizzaFactory())`) gets the pizzas right, but the store class is just a class: franchisees copy it, change the baking, drop the box. The thing we most want to protect, the process, is the thing least protected.

The fix turns the relationship around. PizzaStore becomes abstract. It keeps order_pizza() with the four steps, and declares create_pizza(kind) as an abstract method that it calls but does not implement. Each region is a subclass (NYPizzaStore, ChicagoPizzaStore) whose only job is to implement create_pizza and return its own pizzas. The process lives in one place that subclasses cannot bypass; the product choice lives in the subclass.

Factory Method defines an interface for creating an object, but lets subclasses decide which class to instantiate. Factory Method lets a class defer instantiation to subclasses.

Map the words to the pizzas. The interface for creating an object is create_pizza(kind). Subclasses decide means NYPizzaStore.create_pizza returns NYStyleCheesePizza while ChicagoPizzaStore.create_pizza returns ChicagoStyleCheesePizza. Defer means PizzaStore.order_pizza calls self.create_pizza without knowing which implementation will answer.

The roles have names: the Creator (PizzaStore) contains the code that uses the product and the abstract factory method; concrete creators (NYPizzaStore) implement it; the Product (Pizza) is what the creator's code programs against; concrete products (NYStyleCheesePizza) are what the concrete creators return. The two hierarchies run in parallel: every concrete creator knows its own slice of the product hierarchy and nobody else's.

"Lets subclasses decide" does not mean the decision is made while the program runs: it is made by which creator subclass you instantiate. NYPizzaStore() is the whole choice.

The dependency inversion principle

▶ Video lesson: Dependency inversion: turn the arrows around 1:47 · 4 scenes · narrated, pause anytime and explore

Look at the first PizzaStore again and draw an arrow from every class to every class it names. The store, the high-level component that owns the business process, points at NYStyleCheesePizza, ChicagoStyleClamPizza and six more low-level details. Change any detail and the arrow drags the store along.

Dependency inversion principle: depend on abstractions. Do not depend on concrete classes.

After the Factory Method, the store depends on Pizza only. And look at the concrete pizzas: they now depend on Pizza too, by implementing it. The arrows from the low-level classes, which used to be pointed at, now point up at the abstraction. That reversal is the "inversion": high level and low level both hang off the abstraction, and neither knows the other.

This is chapter 1's "program to an interface" with a direction added. Programming to an interface says use the supertype. Dependency inversion says especially in your high-level policy code, let nothing concrete flow upward; the abstraction belongs to the high level, and details conform to it.

Three guidelines, and the honest footnote

  1. No variable holds a reference to a concrete class. Calling a constructor does exactly that, which is why creation goes through a factory.
  2. No class derives from a concrete class. Derive from an abstraction; deriving from a concrete class depends on its implementation.
  3. No method overrides an implemented method of a base class. If you have to, the base class was not really an abstraction.

You will break all three before lunch (str, list, dict are concrete classes, and you depend on them freely). The guidelines are a direction to lean in, and the lean matters most where a class is likely to change: the pizzas, not the strings. In Python the abstraction is an ABC or a Protocol, and type hints make the direction visible: def order_pizza(self, kind: str) -> Pizza shows the store depending on the abstraction, not on a region.

Interface vs inversion

Programming to an interface is about the type you write down; dependency inversion is about the direction of the arrows across layers. Say the first when you explain a field (factory: PizzaIngredientFactory), the second when you explain an architecture (the store never imports a regional module). Then add the footnote: you depend on concrete classes that are stable all the time, and that is fine.

Abstract Factory: families of ingredients

▶ Video lesson: Abstract Factory: one family of ingredients at a time 3:25 · 5 scenes · narrated, pause anytime and explore

The franchises keep the process now, but a new report comes in: some are using cheaper ingredients. The ingredients vary by region as a family: New York means thin crust dough, marinara sauce, reggiano cheese and fresh clams; Chicago means thick crust, plum tomato, mozzarella and frozen clams. What must never happen is a mix: Chicago sauce on a New York crust.

So we add a second kind of factory. PizzaIngredientFactory is an interface with one creation method per ingredient (create_dough, create_sauce, create_cheese, create_clams), and there is one concrete factory per region. Pizza.prepare() becomes abstract; a CheesePizza is given an ingredient factory when it is created and, in prepare, asks that factory for each ingredient. It never names ThinCrustDough. The regional store's create_pizza is where the two patterns meet: NYPizzaStore creates an NYPizzaIngredientFactory and hands it to the pizzas it creates.

Abstract Factory provides an interface for creating families of related or dependent objects without specifying their concrete classes.

Roles: the AbstractFactory is PizzaIngredientFactory; concrete factories are the regional ones; abstract products are Dough, Sauce, Cheese; concrete products are ThinCrustDough and friends; the client is CheesePizza, which holds a factory and uses only the abstract product types.

Two things to notice. First, each method of an abstract factory is usually itself a factory method (a concrete factory subclass decides the class), so the patterns nest. Second, and this is the distinction interviewers probe: Factory Method creates one product through inheritance (you subclass the creator), while Abstract Factory creates a family through composition (you hand the client a factory object). The price of Abstract Factory is its interface: adding a new ingredient kind, say create_pepperoni, changes the interface and every concrete factory at once.

Build a pizza from one ingredient family

A pizza asks its factory for each ingredient in turn. Switch region to watch every ingredient change together while the pizza code stays identical.

The ingredient factories in Python

from abc import ABC, abstractmethod

# The product families: one abstraction per ingredient kind, one concrete class per region.
class Dough: name = "dough"
class ThinCrustDough(Dough): name = "thin crust dough"
class ThickCrustDough(Dough): name = "thick crust dough"
class Sauce: name = "sauce"
class MarinaraSauce(Sauce): name = "marinara sauce"
class PlumTomatoSauce(Sauce): name = "plum tomato sauce"
class Cheese: name = "cheese"
class ReggianoCheese(Cheese): name = "reggiano cheese"
class MozzarellaCheese(Cheese): name = "mozzarella cheese"

class PizzaIngredientFactory(ABC):              # the abstract factory: one method per product
    @abstractmethod
    def create_dough(self) -> Dough: ...
    @abstractmethod
    def create_sauce(self) -> Sauce: ...
    @abstractmethod
    def create_cheese(self) -> Cheese: ...

class NYPizzaIngredientFactory(PizzaIngredientFactory):        # one concrete factory per family
    def create_dough(self) -> Dough: return ThinCrustDough()
    def create_sauce(self) -> Sauce: return MarinaraSauce()
    def create_cheese(self) -> Cheese: return ReggianoCheese()

class ChicagoPizzaIngredientFactory(PizzaIngredientFactory):
    def create_dough(self) -> Dough: return ThickCrustDough()
    def create_sauce(self) -> Sauce: return PlumTomatoSauce()
    def create_cheese(self) -> Cheese: return MozzarellaCheese()

class Pizza(ABC):
    def __init__(self, name: str):
        self.name = name
        self.dough: Dough | None = None
        self.sauce: Sauce | None = None
        self.cheese: Cheese | None = None

    @abstractmethod
    def prepare(self) -> None: ...                 # abstract now: the ingredients vary by region
    def bake(self) -> None: print("Oven: 12 minutes at 220 C")
    def cut(self) -> None: print("Slice: 8 wedges")
    def box(self) -> None: print("Box it, logo side up")

class CheesePizza(Pizza):                          # the client of the abstract factory
    def __init__(self, factory: PizzaIngredientFactory):
        super().__init__("cheese pizza")
        self.factory = factory                     # composition: the family is handed in

    def prepare(self) -> None:
        self.dough = self.factory.create_dough()   # never names ThinCrustDough or ThickCrustDough
        self.sauce = self.factory.create_sauce()
        self.cheese = self.factory.create_cheese()

class NYPizzaStore(PizzaStore):                    # PizzaStore from the Factory Method section
    def create_pizza(self, kind: str) -> Pizza:    # the factory method now wires in the family
        factory = NYPizzaIngredientFactory()
        if kind == "cheese":
            pizza = CheesePizza(factory)
            pizza.name = "New York style cheese pizza"
            return pizza
        raise ValueError(f"not on the New York menu: {kind}")
CheesePizza is the client: it holds a PizzaIngredientFactory and uses only Dough, Sauce and Cheese. NYPizzaStore.create_pizza is where Factory Method hands Abstract Factory to the product.

Factories in Python

Where you have already seen it

  • pathlib.Path("/tmp") returns a PosixPath or a WindowsPath: a simple factory hidden inside __new__.
  • dict.fromkeys(...), datetime.fromtimestamp(...), int.from_bytes(...), Path.home(): classmethod constructors, the Python shape of "a named way to build this class".
  • logging.getLogger(name): a factory with a registry; it hands back the existing logger or creates one.
  • collections.defaultdict(list) and dataclasses.field(default_factory=list): the factory is a callable you pass in, and a class is a perfectly good callable.
  • Django's class-based views: get_form_class() and get_queryset() are factory methods the base view calls inside a fixed request flow; your subclass decides the class.
  • A database driver behind a common API gives you a connection, a cursor and type adapters that match each other: an abstract factory of a family that must not be mixed.

The book's shape vs the idiom

The book's Factory Method is an abstract method you override. Python has two shortcuts that keep the idea and drop the ceremony. A registry (dict[str, type[Pizza]]) replaces the if chain, and a decorator can fill it as classes are defined. A class attribute on the creator subclass (menu = {...}) lets the subclass decide without overriding a method, because self.menu is looked up on the real class of self. And a classmethod is the right home for an alternative constructor that builds one class several ways.

Factory Method in Python, three ways

The book's shape in Python: an abstract create_pizza on the creator, implemented per region, called by the inherited order_pizza.

from abc import ABC, abstractmethod

class Pizza(ABC):
    name: str = "pizza"
    dough: str = ""
    sauce: str = ""
    toppings: tuple[str, ...] = ()

    def prepare(self) -> None:
        print(f"Preparing {self.name}: {self.dough}, {self.sauce}, {', '.join(self.toppings)}")
    def bake(self) -> None: print("Oven: 12 minutes at 220 C")
    def cut(self) -> None: print("Slice: 8 wedges")
    def box(self) -> None: print("Box it, logo side up")

class NYStyleCheesePizza(Pizza):
    name, dough, sauce = "NY style cheese pizza", "thin crust", "marinara"
    toppings = ("grated reggiano",)

class ChicagoStyleCheesePizza(Pizza):
    name, dough, sauce = "Chicago deep dish cheese pizza", "extra thick crust", "plum tomato"
    toppings = ("shredded mozzarella",)
    def cut(self) -> None: print("Slice: 12 squares")        # a product may vary a step

class PizzaStore(ABC):
    def order_pizza(self, kind: str) -> Pizza:
        pizza = self.create_pizza(kind)       # the factory method: the subclass decides the class
        pizza.prepare()
        pizza.bake()
        pizza.cut()
        pizza.box()
        return pizza

    @abstractmethod
    def create_pizza(self, kind: str) -> Pizza: ...

class NYPizzaStore(PizzaStore):
    def create_pizza(self, kind: str) -> Pizza:
        if kind == "cheese":
            return NYStyleCheesePizza()
        raise ValueError(f"not on the New York menu: {kind}")

class ChicagoPizzaStore(PizzaStore):
    def create_pizza(self, kind: str) -> Pizza:
        if kind == "cheese":
            return ChicagoStyleCheesePizza()
        raise ValueError(f"not on the Chicago menu: {kind}")

ethan = NYPizzaStore().order_pizza("cheese")       # thin crust, cut into wedges
joel = ChicagoPizzaStore().order_pizza("cheese")   # deep dish, cut into squares

The idiom. A dict from name to class is the simple factory, a decorator fills it, and a class attribute on the subclass is a factory method without an override.

# 1. Classes are callables, so a dict from name to class IS a simple factory.
PIZZAS: dict[str, type[Pizza]] = {}

def register(name: str):
    def add(cls: type[Pizza]) -> type[Pizza]:
        PIZZAS[name] = cls
        return cls
    return add

@register("cheese")
class CheesePizza(Pizza): ...

@register("clam")
class ClamPizza(Pizza): ...

def create_pizza(name: str) -> Pizza:
    try:
        return PIZZAS[name]()               # look the class up, then call it
    except KeyError:
        raise ValueError(f"unknown pizza: {name}") from None

# 2. Factory Method without an override: the subclass decides with a class attribute.
class PizzaStore:
    menu: dict[str, type[Pizza]] = {}

    def order_pizza(self, kind: str) -> Pizza:
        pizza = self.menu[kind]()           # looked up on type(self), so the subclass decides
        pizza.prepare(); pizza.bake(); pizza.cut(); pizza.box()
        return pizza

class NYPizzaStore(PizzaStore):
    menu = {"cheese": NYStyleCheesePizza, "clam": NYStyleClamPizza}

class ChicagoPizzaStore(PizzaStore):
    menu = {"cheese": ChicagoStyleCheesePizza, "clam": ChicagoStyleClamPizza}

When the variation is how to build one class rather than which class: alternative constructors named for what they build from.

from dataclasses import dataclass

@dataclass
class Pizza:
    name: str
    dough: str
    sauce: str
    toppings: tuple[str, ...] = ()

    # Alternative constructors: a classmethod is a factory that lives on the class itself.
    @classmethod
    def ny_style(cls, kind: str) -> "Pizza":
        return cls(f"NY style {kind}", "thin crust", "marinara", ("grated reggiano",))

    @classmethod
    def chicago_style(cls, kind: str) -> "Pizza":
        return cls(f"Chicago style {kind}", "thick crust", "plum tomato", ("mozzarella",))

    @classmethod
    def from_order(cls, order: dict) -> "Pizza":   # parse-and-build in one named place
        return cls(order["name"], order.get("dough", "thin crust"), order["sauce"],
                   tuple(order.get("toppings", ())))

pizza = Pizza.ny_style("cheese")

    C -->|no| E{Should a subclass decide,<br/>inside a fixed algorithm?}
    E -->|yes| F[Factory Method<br/>abstract create step, or a class attribute]
    E -->|no| G{Several products that<br/>must match each other?}
    G -->|yes| H[Abstract Factory<br/>one object creates the family]
    G -->|no| I[Pass a callable<br/>default_factory style]
Ask what varies before choosing a factory. Most Python code stops at the second or third box.

Common mistakes

  • A factory for one class. PizzaFactory.create() that can only ever return Pizza is ceremony. Reach for a factory when the class varies, or when you confidently expect it to.
  • The chain comes back. if isinstance(pizza, ChicagoStyleCheesePizza): inside order_pizza, or the store importing one regional module "for a special case", re-creates the dependency the factory removed.
  • Factory Method confused with Abstract Factory. The first is a method you override (inheritance, one product). The second is an object you pass in (composition, a family). Both hide concrete classes.
  • Abstract Factory with a growing interface. Every new ingredient kind edits every concrete factory. If product kinds are added more often than families, a registry keyed by product name fits better.
  • Simple factory that cannot be replaced. A module-level function called from everywhere is hard to swap in tests. Pass the factory in (the store has-a factory) and tests can inject a fake.
  • Implicit registries. globals()[name]() or getattr(module, kind.title() + "Pizza")() is a factory that breaks on a rename and that no IDE can follow. Write the dict.

How to say it in an interview

Say: 'The store's order method both chose the pizza class and ran the fixed preparation steps, so every menu change reopened code that should be closed. First I would move the choice into a simple factory, so the store names no concrete pizza. When franchises need their own pizzas but the same process, I'd make creation an abstract method on the store that each regional subclass implements: that is Factory Method, and the process stays in the superclass. If the pizzas need matching ingredient families, I'd hand each pizza an ingredient factory: Abstract Factory, composition instead of inheritance. All three follow dependency inversion: the store depends on Pizza, never on a pizza class.' Then draw Creator / ConcreteCreator / Product / ConcreteProduct.
