Design a search autocomplete system

Type three letters and five good suggestions should already be on screen. This chapter walks the interview for that problem: scope and estimate, an offline pipeline that turns search logs into a trie whose nodes cache their best completions, an online path that answers a prefix in time proportional to its length, the trade-offs of refreshing, filtering and sharding that trie, and the follow-ups interviewers ask next.

After this chapter you can
  • Turn the scope questions into a traffic, log and trie-size estimate, and read the number of shards off it
  • Draw the two-service design, an offline data-gathering pipeline and an online query path, and say why they only share data
  • Explain why a trie with the best completions cached at every node answers a prefix in time proportional to its length, and what that costs in memory and update work
  • Describe the pipeline from search logs to a published trie: sampling, decayed counts, cut-offs and an atomic swap
  • Choose between a weekly rebuild and in-place updates, and take a bad suggestion down in seconds with a filter layer
  • Shard the trie by first-letter ranges chosen from query statistics, and explain why equal ranges fail

Step 1 · Understand the problem and establish scope

Type be into a search box and a list drops down: beach, bell, bean. That list is autocomplete (also called typeahead), and it has to be on screen before the next keystroke. The backend answers one question, tens of thousands of times a second: given the characters typed so far, which few complete queries do we show?

Assumptions we design for (in the interview you would ask about each one):

  • Prefix matching only. Suggestions start with exactly what was typed: be offers beach, not maybe.
  • Five suggestions, ranked by popularity: how often people searched each query in the past. No personalisation.
  • Lowercase letters and spaces, English only, no spelling correction. Other languages come up in the wrap-up.
  • 30 million daily active users, about 6 searches each per day.
  • Fast: p99 under 100 ms end to end, or the list lags behind the typing.
  • Highly available, eventually fresh: the search box must keep working when suggestions fail, and a new popular query may take days to appear.
  • Removable: we must be able to take a suggestion down quickly.

Questions worth asking before you draw anything

  1. Must a suggestion start with what was typed, or may it match inside a query?
  2. How many suggestions, and what decides the order: popularity, recency, the user's own history?
  3. Which languages and characters? Do we correct typos?
  4. How many users and searches, and what response time makes the box feel instant?
  5. How fresh must suggestions be: this morning's news, or last week's trend?
  6. Can a suggestion ever need to be removed, and how fast?

Back-of-the-envelope: traffic, logs and trie size

Change any assumption (the method is the one in 2 · Back-of-the-envelope estimation). Requests per search is the typed characters times the share of keystrokes that actually send a request (debouncing, covered later, skips some). The trie rows assume a compact native node: a character, child links and 5 query ids. With the defaults the lookups reach about 17,000 a second (50,000 at peak) and the trie about 50 GB, which is too much for one server: it needs 4 shards.

Step 2 · Propose a high-level design

Split the system into two services that never call each other and only share data.

  • The query service is online. It receives a prefix and returns up to five suggestions. It only reads.
  • The data-gathering service is offline. It turns the searches users actually submit into counts, and the counts into the structure the query service reads: a trie held in RAM (the trie cache) and its durable, versioned copy (the Trie DB).

The tempting first design is a table of (query, count) and one SQL query per keystroke:

SELECT query FROM query_counts
WHERE query LIKE 'be%'
ORDER BY count DESC
LIMIT 5;

An index on query finds the matching range quickly, but the database must then rank every match by count. For a one-letter prefix such as b, that is a large slice of the table. It works for a prototype with 100,000 queries and collapses at 200 million queries and 50,000 requests a second. The fix is to stop computing the answer per request and precompute it per prefix; the next section shows how. Run keystrokes through the boxes

Each keystroke is one request. Watch the counters on the boxes: the browser cache absorbs the backspace, and in the second scenario a freshly replaced trie server falls back to the Trie DB until its shard has loaded. Latencies are illustrative orders of magnitude.

The API is one idempotent GET, so browsers, CDNs and proxies may cache it. limit defaults to 5, lang selects the trie, and the version in the body makes a stale shard easy to spot.

Step 3 · Deep dive: the trie with the best queries at every node

▶ Video lesson: The trie that answers a prefix 5:17 · 8 scenes · narrated, pause anytime and explore

A trie (prefix tree) stores strings one character per edge, so queries that start the same way share one path and every node stands for a prefix. If you have not met it yet, Tries and Implement Trie (Prefix Tree) cover the structure itself; here it is the index for prefix lookups.

Finding the node for bea costs one step per typed character: p steps for a prefix of length p. The expensive part comes next. A plain trie knows the queries below a node only by visiting them, so a lookup walks to the node, visits all c nodes underneath and sorts the complete queries it found: O(p + c + c log c). That is the selection problem of Top K Frequent Elements, repeated on every keystroke, and c is largest exactly when the prefix is shortest, which is when most keystrokes happen.

Two changes remove almost all of that cost:

  1. Cap the prefix length (say 50 characters). Longer input is cut off, so p is bounded by a constant and a pasted paragraph costs no more than a short word.
  2. Cache the best results at every node (the top-k list). When the trie is built, each node stores the best k queries of its subtree. After the walk the answer is already there: O(p), however many queries live below.

Typing into a trie that caches its best queries

A toy log of nine queries, with k = 3 so the lists stay readable. The number beside a node is this week's searches, in thousands, for the query that ends there. Type beach letter by letter, then switch scenario: bakes swings to another branch and ends in a dead end, and the last scenario answers b without any stored lists.

Rows two and three differ in one thing: whether the work grows with the size of the subtree or with the length of what the user typed.

The trie in Python

Correct and tiny, but the three numbered steps are the cost: a walk, a scan of everything below, and a sort.

MAX_PREFIX = 50          # characters; longer input is cut off, so p is bounded by a constant

def suggest_slow(root, prefix, k=5):
    node = root
    for ch in prefix[:MAX_PREFIX]:                  # 1. walk p edges
        node = node.kids.get(ch)
        if node is None:
            return []
    found = []                                      # 2. visit EVERY node below the prefix
    stack = [(node, prefix)]
    while stack:
        cur, text = stack.pop()
        if cur.own:
            found.append((cur.own, text))
        stack.extend((kid, text + ch) for ch, kid in cur.kids.items())
    found.sort(reverse=True)                        # 3. sort every candidate
    return [text for _, text in found[:k]]

The whole lookup is the walk. Lists are (score, query) pairs, best first, so there is nothing to sort at request time.

MAX_PREFIX = 50          # characters; longer input is cut off, so p is bounded by a constant

def suggest(root, prefix):
    node = root
    for ch in prefix[:MAX_PREFIX]:                  # the only loop: one step per typed character
        node = node.kids.get(ch)
        if node is None:
            return []                               # no stored query starts with this prefix
    return [query for _, query in node.top]         # already ranked: the best K of this subtree

One post-order pass: each node merges its own query with the lists of its children and keeps the best K. heapq.nsmallest keeps a heap of size K (see Heap / Priority Queue), so a node costs about its candidates times log K.

import heapq

K = 5

class Node:
    __slots__ = ("kids", "own", "top")

    def __init__(self):
        self.kids = {}        # next character -> Node
        self.own = 0          # score of the query that ends exactly here, 0 if none
        self.top = []         # cached: the best K (score, query) pairs of this subtree, best first

def insert(root, query, score):
    node = root
    for ch in query:
        node = node.kids.setdefault(ch, Node())
    node.own = score

def fill(node, prefix=""):
    """One post-order pass: a node's list is the best K of its own query plus its children's lists."""
    pool = [(node.own, prefix)] if node.own else []
    for ch, kid in node.kids.items():
        pool.extend(fill(kid, prefix + ch))         # children are finished first
    node.top = heapq.nsmallest(K, pool, key=lambda e: (-e[0], e[1]))
    return node.top

The same merge, applied only along one path, leaf first. It stops at the first list that comes out identical.

import heapq

K = 5

def refresh(node, prefix):
    pool = [(node.own, prefix)] if node.own else []
    for kid in node.kids.values():
        pool.extend(kid.top)                        # the children's lists are already correct
    node.top = heapq.nsmallest(K, pool, key=lambda e: (-e[0], e[1]))

def set_score(root, query, score):
    """Update one query in place and return how many lists were rewritten."""
    path = [root]
    for ch in query:
        path.append(path[-1].kids.setdefault(ch, Node()))
    path[-1].own = score
    rewritten = 0
    for depth in range(len(query), -1, -1):         # the query's node first, then each ancestor up to the root
        node = path[depth]
        before = node.top
        refresh(node, query[:depth])
        if node.top == before:
            break                                   # unchanged list: nothing above it can change either
        rewritten += 1
    return rewritten

Making the lists and the trie smaller

Store ids, not strings

A popular query can appear in the list of every node on its path, one per character. If each list holds k small integers that index one shared table of query texts, that is 18 integers, not 18 copies of the text. Ids are what keep the estimate's 40 bytes per node realistic.

Skip lists that cannot help

A node whose subtree holds k queries or fewer needs no list of its own: scanning that tiny subtree costs about the same as reading a list. Most deep nodes fall in this group, so this removes most of the lists.

Compress chains (radix tree)

Where a node has a single child, store the whole stretch as one edge labelled with a string: the chain bea, beac, beach becomes one edge labelled ch from bea to beach. A prefix that ends in the middle of an edge (beac) has the same subtree as the node at the end of that edge, so it reads that node's list. Fewer nodes, the same answers.

Step 3 · Deep dive: the offline pipeline and the query path

flowchart LR

  LOG --> AGG[Aggregators]
  AGG --> CNT[(Query counts)]
  CNT --> TB[Trie builders]
  TB --> TDB[(Trie DB<br/>snapshots)]
  TDB --> SRV[Trie servers<br/>load and swap]
From a search to a live suggestion: seven stages, none of them on the lookup path.

Why offline? A slow job must never be able to slow a lookup, and the two halves have opposite shapes: logging is a firehose of appends, serving is a flood of tiny reads. Choices worth saying out loud:

  • Sample. Keep one event in N at random. Popular queries still appear thousands of times, so their ranking holds; rare queries vanish, which is fine because they would never reach a top 5.
  • Weight recent weeks more. Score a query as the sum over weeks of count × 0.5^(weeks ago ÷ H), with a half-life H such as 8 weeks. Old fads fade, and a rising query overtakes a steady one with the same total.
  • Apply cut-offs. Drop queries below a minimum count and below a minimum number of distinct users, so one person's private query can never become a public suggestion.
  • Clean before building. Lowercase, collapse spaces, drop blocklisted terms and anything shaped like an email address or a phone number.
  • Publish atomically. Write versioned snapshots; servers validate a new one, switch in one step and keep the old version for rollback.

Where the finished trie lives

Serialise each shard's trie as one blob (or a few) with a version number. Trie servers read it at start-up and at each release, then serve from RAM. Writes are bulk and atomic; there is no partial update, and the Trie DB is not on the lookup path in steady state.

tries/s-z/2026-w44.bin     one blob per shard and version
  header   version, node count, k, checksum
  body     nodes in depth-first order: character, child offsets, k query ids
queries/2026-w44.bin       query id -> text

Make the prefix the key and the node's list the value. A lookup is a single GET with no trie walk, one prefix can be rewritten alone, and a managed store can hold it. The price is one row per node, and a short prefix such as b becomes one very hot key (the browser and CDN caches absorb that).

be     ->  [("beach", 85), ("bell", 60), ("bean", 40)]   version 2026-w44
bea    ->  [("beach", 85), ("bean", 40)]                 version 2026-w44

Snapshots when each shard fits in RAM and you rebuild in batches, as in this design. Key-value when you want to patch single prefixes, or to serve straight from a managed store without holding a trie in memory. Either way the lookup path sees a prefix and gets back a short list.

Step 3 · Deep dive: updating the trie and removing suggestions

Two ways to refresh the lists

Rebuild fills every list from the leaves up in one pass, each node merging at most two short lists. Update in place changes one query and then climbs: a quiet query's change dies out after a couple of nodes, a trending query's change climbs to the root. Watch which nodes are rewritten.

Rebuild and swap, or update in place?

Rebuild and swap (the default)

A batch job builds a complete new trie from the latest counts and ships it as a new version; servers load it beside the old one, check it and switch.

  • Readers never see a half-updated trie.
  • Lists are computed once per node, in one linear pass, with whatever ranking logic you like.
  • A bad build is undone by switching back to the previous version.
  • Cost: data is as old as the last build (days), and a server needs memory for two versions during the swap.

Update in place

Apply count changes to the live trie: set the node's count, then recompute the lists of its ancestors, stopping when one is unchanged.

  • Fresh within minutes.
  • One update rewrites up to p lists, and the nodes near the root are rewritten by thousands of different queries, so they become lock hot spots.
  • Readers need atomic list swaps; a bug damages the live trie instead of a build artefact.
  • Use it only when the trie is small and freshness is worth the risk, and batch the increments first.

What updating in place costs

Applied one search at a time, every search rewrites one list per character of its query, and the busiest first-letter node is rewritten by every search that starts with that letter. Batching coalesces a whole window of increments into one rewrite per node.

Removing a suggestion

Delete the query from the trie

Removal is an update: set the count to zero and rewrite every ancestor list that contained the query, on every shard and replica. It is not instant (replicas apply it at different moments), and the next rebuild brings the query back unless the source counts are cleaned too.

Filter layer in front of the trie

Blocklist rules are tiny, so they reach every API server within seconds. Each lookup drops blocked entries from the list it just read. The trie stores a few spare entries per node (say 8 instead of 5) so filtering never leaves the list short. The builders apply the same rules at the next build, so the query leaves the trie for good and the filter stays as the safety net.

flowchart LR
  OPS[Trust and safety] --> BL[(Blocklist rules)]
  BL -. pushed in seconds .-> FIL[Filter<br/>in API server]
  API[API server] --> TC[(Trie cache<br/>8 per node)]
  TC --> FIL
  FIL --> OUT[5 suggestions]
  BL -. applied at next build .-> TB[Trie builders]
A rule changes what users see in seconds; the trie itself is cleaned at the next build.

Step 3 · Deep dive: sharding the trie

The estimate says the trie is about 50 GB. One server cannot hold it, because it must keep the old and the new version side by side for the swap, so the trie is split. Splitting by first letter keeps whole subtrees together: a prefix lives on the shard that owns its first letter, so every lookup touches exactly one shard and nothing needs merging. The catch is that letters are not equally popular. This is the same sharding-key question as in Scaling databases: replication, sharding, partitioning, with a skewed key.

Cutting the alphabet into shards

First the naive rule (equal numbers of letters), then the shard map manager's rule (equal shares of traffic). The second scenario uses 8 shards and shows where first-letter ranges run out.

Balanced ranges and routing

from bisect import bisect_right
from string import ascii_lowercase

# percent of all queries that start with each letter, from the aggregated counts
SHARE = dict(a=5, b=8, c=11, d=5, e=3, f=5, g=3, h=4, i=2, j=1, k=2, l=3, m=7, n=2, o=2, p=6, q=1, r=4, s=11, t=6,
             u=1, v=1, w=3, x=1, y=1, z=2)

def balanced_starts(share, shards):
    """First letter of every shard's range, chosen so each shard gets about the same share of queries."""
    total = sum(share.values())
    running, cum = 0, []
    for ch in ascii_lowercase:
        running += share.get(ch, 0)
        cum.append(running)
    starts, prev = ["a"], -1
    for i in range(1, shards):
        goal = total * i / shards
        # the letter that ends shard i-1: running total closest to the goal, leaving a letter for every later shard
        end = min(range(prev + 1, 26 - (shards - i)), key=lambda j: (abs(cum[j] - goal), j))
        starts.append(ascii_lowercase[end + 1])
        prev = end
    return starts

STARTS = balanced_starts(SHARE, 4)                  # ['a', 'd', 'l', 's']  ->  a-c, d-k, l-r, s-z

def shard_for(prefix):
    return bisect_right(STARTS, prefix[0]) - 1      # 'be' -> 0: the a-c shard
The map is the list of range starts; routing is one binary search. The same walk works on two-letter prefixes when a single letter is too heavy.

Step 4 · Wrap up

Follow-up questions to expect

Other languages and scripts

Key nodes by Unicode code point after normalising (NFKC, case folding) instead of 26 letters, and keep children in a hash map: one Chinese character can have thousands of continuations. Run one trie per language, chosen from the request's lang parameter.

Different top suggestions per country

Partition the logs by locale before aggregating and build one trie per country; serve each from nearby regions or edge caches. The same code with different counts.

Trending queries and breaking news

A weekly build cannot see them. Add a small real-time overlay next to the main trie; the diagram below shows it.

Ranking beyond raw counts

Decay old counts (done above), add click-through on suggestions, and guard against feedback loops where showing a suggestion makes it more popular. Ranking stays offline: the stored list is the output of whatever model you choose.

Personalisation

Blend a few suggestions from the user's own history, kept on the device or in a per-user store, ahead of the global five. Per-user data never goes into the shared trie.

Spelling mistakes

Out of scope for prefix matching. Later: a separate spell service, or fuzzy matching with edit-distance automata, merged into the same response.

Gaming the ranking

Bots repeating a query can push it into the top 5. Count distinct users, cap one user's contribution per day, and keep the minimum-distinct-users cut-off.

What I would add with more time

Measure first: the share of suggestions users accept, and keystrokes saved, tell you whether a ranking change helped, so A/B test every change. After that: regional replicas near users, a small personal layer, and typo tolerance.

flowchart LR
  EV[Search events] --> BATCH[Weekly batch build]
  EV --> STREAM[Stream processor<br/>last 30 minutes]
  BATCH --> MAIN[(Main trie)]
  STREAM --> HOT[(Hot overlay)]
  MAIN --> MERGE[Merge and rank]
  HOT --> MERGE
  MERGE --> OUT[5 suggestions]
Trending without a second full trie: a small overlay, merged at query time. The streaming part is a Message queues & streaming (Kafka) job.

Fail open

Suggestions are an optimisation. Give the lookup a tight timeout (about 50 ms) and, on any error or timeout, return an empty list instead of an error, so typing and searching keep working. The browser should ignore failed suggestion requests silently.

What breaks, and what the user sees

An API server dies

Nothing visible. The servers are stateless and the load balancer routes around it.

One trie replica dies

Nothing visible: each shard has three replicas. A replacement loads the latest snapshot; until then the API server falls back to the Trie DB for its prefixes.

A whole shard is unreachable

No suggestions for prefixes in that letter range. The tight timeout returns an empty list, search still works, and the browser cache still serves recent prefixes. Alert on shard availability.

A bad build ships

Servers validate before switching (node count within a band of the previous version, sample prefixes return what they should), a canary replica goes first, and the previous version is kept for an instant rollback.

The log pipeline stalls

Suggestions get stale but nothing breaks. Alarm on freshness: the age of the newest counts in the live trie.

A suggestion must disappear now

Add a blocklist rule. The filter applies it within seconds, and the next build removes the query from the trie.

The 60-second answer

Autocomplete is a read-heavy lookup, so I precompute the answers. Offline, a pipeline samples the search logs, aggregates counts with a recency decay, drops rare and single-user queries, and builds a trie in which every node stores its best five completions. Online, a stateless API server walks the typed prefix, capped at 50 characters, and returns that node's list: the cost follows the prefix length, never the number of queries below it. I estimate about 17,000 lookups per second on average and 50,000 at peak, and a trie of roughly 50 GB, so I shard it by first-letter ranges chosen from query statistics, with three replicas each. The browser debounces, cancels stale requests and caches answers, which removes much of the traffic before it starts. I refresh the trie with a weekly rebuild and swap, add a small real-time overlay for trending queries, and remove bad suggestions within seconds with a blocklist filter. If suggestions fail, the search box still works.
