Design a chat system

A chat system looks like a CRUD app until you notice that the server has to speak first. This chapter walks the interview in four steps: scope and an estimate that is dominated by open connections rather than message rate; the move from polling to WebSockets and the split into stateless API servers and stateful chat servers; deep dives on message storage and ids, service discovery, one-to-one and group message flows with per-user inboxes and device cursors, and presence built on heartbeats; and the failure modes and follow-ups you close with.

After this chapter you can
  • Estimate message rate, concurrent sockets, chat servers, heartbeat load and storage, and say which number sizes the fleet
  • Compare polling, long polling and WebSockets on delay, wasted requests and server cost, and justify WebSockets for receiving
  • Draw the architecture, say which services are stateless and which are not, and explain why the chat tier needs service discovery
  • Give each conversation an order with sequence numbers, and explain why timestamps from clients fail
  • Trace a one-to-one and a group message through ids, storage, per-user inboxes and delivery, and sync a returning device from its cursor
  • Design presence with heartbeats and a grace period, and explain why status changes fan out only to small audiences

Step 1 · Understand the problem and establish scope

A chat system lets people exchange short messages in real time, one to one and in groups, see who is around, and pick up a conversation on another device. It looks like a CRUD app until you notice who has to speak first: the server must deliver a message to a person who never asked for it. That one requirement brings long-lived connections, a service tier that cannot be stateless, and ordering rules that an ordinary request/response API never needs.

These are the answers this chapter assumes after the first few minutes of questions:

  • Chat types: one to one, and groups of up to 200 members.
  • Devices: phones and a web client. One person can be signed in on several devices at once, and all of them show the same history.
  • Content: text only, up to a few thousand characters. Images and files are a follow-up.
  • Delivery: a message to an online recipient arrives well under a second. A message to an offline recipient waits and arrives when a device comes back, with a push notification as a nudge.
  • Guarantees: once the sender sees "sent" the message is never lost, and everyone in a conversation sees it in the same order.
  • Presence: a green dot for a user's friends and for the members of small groups.
  • History: kept for five years and paged on demand.
  • Scale: 20 million daily active users.

The hld track has a case study of the same problem that stresses delivery receipts and a session registry (Case study: chat application). This chapter takes the interview-walk angle instead: transport, services, ids, inboxes and presence.

Questions worth asking in the first two minutes

  • Is it one to one only, or groups too, and how large can a group be?
  • Which clients: phone, web, desktop? Several devices per person at the same time?
  • Text only, or images, video and files? What is the largest message?
  • How long is history kept, and must it be searchable?
  • Is end-to-end encryption required? It changes what the server is allowed to see.
  • Can a message be lost, duplicated or reordered? How fresh must presence be?

The second-to-last answer decides whether the server may read messages at all, and the last one fixes the delivery guarantee. Interviewers listen for both.

Messages, sockets, servers and storage

Change the daily users, the share of people online at peak, or the sockets one server can hold, and watch which number moves the server count. Messages are tiny. The open connections and their heartbeats are what stress the system. Background on the method: Back-of-envelope estimation.

Read the outputs as decisions:

  • About 35 thousand messages per second at peak is modest. A key-value store partitioned by conversation absorbs it, and the chat servers are not CPU-bound.
  • 7 million concurrent sockets size the fleet. At 60 thousand sockets per server and 25% headroom that is 146 chat servers, limited by memory (about 1.5 GB of connection state each) and file descriptors, not by CPU.
  • About 467 thousand heartbeats per second, more than 13 times the peak message rate. They must be answered in memory on the chat server, and presence is stored only when it changes (see the presence section).
  • About 132 thousand inbox entries per second: every message writes a small pointer for each member, which is the price of the inbox design in the message-flow section.
  • 180 GB of new messages a day, close to a petabyte after five years with three replicas. The data is append-only and the newest rows are read most, so partition by conversation and keep recent data on the fastest storage.

Step 2 · Propose a high-level design: connections and services

▶ Video lesson: WebSockets and the architecture 5:59 · 9 scenes · narrated, pause anytime and explore

Sending is the easy half. When Alice taps send, her app can make an ordinary HTTP request, or write a frame to a socket it already has, and wait for an acknowledgement. Receiving is the hard half: Bob's app asked for nothing, and plain HTTP only lets the client start an exchange. Three techniques close that gap. Run them side by side on one timeline. Messages M1 and M2 reach the server at 7 s and 15 s, and each client may only use the tools of its own technique.

Polling, long polling and a WebSocket on the same 30 seconds

Step through the moments something happens. Watch the request counters, the held-request bars on the long-poll lane, and the delay each client suffers. The second scenario polls three times as often to show what a shorter interval buys and costs.

'Why not just poll faster?' Polling every 2 s cuts the delay to about 1 s and triples the empty requests. Only a held-open connection gets both low delay and low cost.

Two kinds of service, two ways to scale

Stateless: the API servers

Login, sign-up, profile, settings, group membership, history pages, and the lookup that says which chat server to use. Each call carries everything needed to serve it, so any server can answer any request.

  • A load balancer in front, and servers added freely (Load balancers, reverse proxies & API gateways)
  • A dead server costs only the calls in flight, which clients retry
  • Rolling deploys are boring

Stateful: the chat servers

A chat server owns the live socket of every device connected to it. A socket lives in one process on one machine, so a message for Bob can only leave through the server that holds Bob's socket.

  • Scaling out means choosing where each new connection lands
  • A crash drops thousands of connections at once, and their apps reconnect elsewhere
  • A deploy must drain connections gently, or the reconnects arrive as a wave

Step 3 · Deep dive: message storage and ordering

Chat data has two very different shapes.

Profiles, settings, friend lists and group membership are small, relational, and read far more than written. An ordinary relational database with replicas handles them.

Message history is huge and append-heavy. Nearly every read asks for the newest few dozen messages of one conversation, in order. Now and then a user jumps far back (a search hit, a quoted reply), which is a random read in the long tail. A key-value or wide-column store (HBase and Cassandra are the usual examples) fits well: partition by conversation, sort by message id inside the partition, and one read returns a screenful already in order. A relational index over billions of rows would spend its cache on a long tail that nobody reads twice. Databases: SQL vs NoSQL covers the general trade-off.

The message tables

A one-to-one chat is just a conversation with two members, so one message table serves both kinds. The key (conv_id, msg_id) is the access pattern: one partition per conversation, rows in id order. An inbox entry is only a pointer.

Everyone in a conversation must see the same order, and a later message must have a larger id, so that a range read returns history already sorted. A global auto-increment column would do it, but key-value stores do not offer one and a single counter for the whole system is a bottleneck. A global Snowflake-style generator works too (7 · Design a unique ID generator in distributed systems), yet chat needs less than that: ids only have to be ordered inside one conversation.

How to order the messages of a conversation

Order by timestamp

Two messages sent in the same millisecond tie. Client clocks are wrong by seconds, sometimes by hours, and a user can set one on purpose. Server clocks drift apart, so two chat servers can stamp a reply before the message it answers.

A sequence number per conversation

Each conversation has its own counter: 1, 2, 3 and so on. The server that stores a message takes the next value, so order is plain numeric order, with no ties and no clocks. The counter must be unique only inside one conversation, so there is no global coordination: millions of conversations are millions of tiny independent counters.

Step 3 · Deep dive: service discovery

After login the app needs the address of one chat server. DNS round robin hands out addresses blindly: it knows nothing about load, geography, or which servers are alive. A service registry does. Apache ZooKeeper is the classic choice (etcd and Consul play the same role): a small replicated tree of nodes with two properties that matter here.

  • An ephemeral node exists only while the session of the process that created it is alive. A chat server registers one at start-up with its address, region and load. If the server crashes, its session times out and the node disappears, so the list always means "who is alive".
  • A watch tells interested clients when a node appears or disappears, so API servers refresh their list without polling.

ZooKeeper is built for many reads and few writes, because every write is replicated through a quorum. So chat servers refresh their load figure every few seconds, not on every connection.

Choosing the best chat server, and surviving a crash

First scenario: Alice logs in and the discovery rule narrows three servers to one. Second scenario: the server she is on crashes and the ephemeral node, the watch and a jittered retry bring her back on another one.

Step 3 · Deep dive: message flows, inboxes and sync

▶ Video lesson: Message flows: ids, inboxes and sync 4:41 · 8 scenes · narrated, pause anytime and explore

Four rules shape every flow below.

  1. Store first, deliver second. The message is written to the message store before the sender sees "sent". Delivery can then fail and be retried without losing anything.
  2. The server assigns the order. The sender picks only a client message id, used to recognise retries. The chat server asks the ID generator for the next message id of that conversation.
  3. Every member gets an inbox entry. An inbox is a per-user list of pointers (conversation id and message id), numbered by that user's own counter. The body is stored once.
  4. Delivery reads from the inbox. Online and offline recipients take the same path: the entry is written, and it is delivered now if a chat server holds the user's socket, or later when a device syncs.

Two numbers are easy to confuse. The message id orders one conversation and is shared by all its members. The inbox position orders everything one user's devices must receive, across all conversations, and is private to that user.

One-to-one message, recipient online

One body in the message store and one small pointer per member. The pointers are what grow with group size, and the push is only a nudge for the member who did not acknowledge.

Per-user inboxes: fan-out, an offline member, and two devices

First scenario: follow one group message through the id, the store and three inboxes, and watch Dan catch up from his cursor. Second scenario: Bob's laptop sleeps through two messages and syncs later.

What a returning device runs: replay everything above the cursor

def sync_device(inbox, store, user_id: int, cursor: int, send, page_size: int = 200) -> int:
    """Replay what this device missed, oldest first. cursor is the last inbox position it applied."""
    while True:
        entries = inbox.read_after(user_id, cursor, limit=page_size)   # pointers with position > cursor
        if not entries:
            return cursor                                              # caught up: the live stream takes over
        for entry in entries:
            message = store.get(entry.conv_id, entry.msg_id)           # the body is stored once, by (conversation, id)
            send({"type": "message", "position": entry.position, **message})
        cursor = entries[-1].position                                  # the device acks this and remembers it
The device cursor, often called cur_max_message_id, is a position in the user's own inbox. That makes it comparable across conversations, which per-conversation message ids are not.

Decide to send a push from a missing ack, not from presence. Presence is deliberately slow to say 'offline' (up to the grace period), so a message sent in that window would never trigger a push. Wait a few seconds for the delivery ack and, if it does not come, ask the push service. The push pipeline itself is in 10 · Design a notification system.

How group size changes the design

A pointer in every member's inbox

  • Write cost: one append per member per message. A group of 200 is 200 small writes.
  • Read cost: one range read on one inbox returns everything new, from every conversation.
  • Delivery: each member's chat server watches only that member's inbox.
  • Pick it when groups are small to medium (up to a few hundred members) and reads dominate.

One log per conversation, members keep cursors

  • Write cost: one append per message, whatever the size of the group.
  • Read cost: a device keeps a cursor per conversation and must find which of its many conversations have news, usually from a small 'conversation X changed' notice.
  • Delivery: work moves to read time, like fan-out on read (11 · Design a news feed system).
  • Pick it when the audience is huge: thousands of members or broadcast channels.

Step 3 · Deep dive: online presence

▶ Video lesson: Online presence: heartbeats and the grace period 4:01 · 8 scenes · narrated, pause anytime and explore

Presence is a status, online or offline, plus a last-seen time, shown next to a friend's name. Signing in sets it to online and signing out sets it to offline. The hard case is the one with no goodbye: a phone in a tunnel, a dead battery, a killed app. The server simply stops hearing from the client.

The obvious rule, "offline when the socket closes", fails in practice. Mobile connections drop and return all day, and every flip would be written and published to every friend. The fix is a heartbeat with a grace period. While connected, the app sends a tiny frame every H seconds. The presence server remembers when it last heard one, and declares the user offline only after T seconds of silence, where T is a clear multiple of H. The sim uses H = 10 s and T = 25 s. Run the three situations.

Heartbeats, silence and the grace period

The lanes are Alice's app, the presence server, the presence store and Bob's app. Watch what Bob's screen shows in each situation.

Heartbeats are the busiest stream in the system: about 467 thousand per second in the estimate, more than 13 times the peak message rate. Answer them in memory on the chat or presence server and write to the shared presence store only when the status changes, or in batches. A database write per heartbeat would be a load test of your own database.

Presence fan-out through channels

flowchart LR
    Alice[Alice app] -->|status change| PS[Presence server]
    PS --> Store[(Presence store<br/>status and last seen)]
    PS -->|publish| CB[Channel Alice-Bob]
    PS -->|publish| CC[Channel Alice-Carol]
    PS -->|publish| CD[Channel Alice-Dan]
    CB --> Bob[Bob app]
    CC --> Carol[Carol app]
    CD -.-> Dan[Dan app<br/>closed]
A status change is published once per friend channel, so the cost grows with the number of friends listening. That is why large groups do not get live dots.

Step 4 · Wrap up

Failure modes and what the design does about them

What failsWhat would go wrongWhat the design does
A chat server crashesthousands of sockets drop at onceApps notice missed pongs and reconnect through the API tier after a random, growing delay. Service discovery steers them to other servers, and each app sends its cursor to fetch what it missed. Nothing stored is lost.
A send is retried after a lost acka duplicate messageThe client resends with the same client message id. The server looks up (conversation, client message id) first and returns the original message id.
The message store loses a nodewrites to that partition failReplication and quorum writes keep the partition available. The chat server returns an error rather than an ack, and the client retries.
The write succeeds but an inbox append failsstored but not deliveredThe server retries the appends before acknowledging. A unique key on (conversation, message id) inside each inbox makes repeating them harmless.
ZooKeeper is unreachableno new connectionsConnected users keep chatting because the message path never touches it. API servers fall back to their last cached list.
The presence store is downno green dotsShow statuses as unknown. Chat is unaffected, because presence fails open.
The push provider is downno nudgesUsers get their messages on the next app open through sync. The push was only a hint.
A data centre restartsmillions reconnect togetherJittered exponential backoff on the client, rate limits on the login path, and gradual re-registration of chat servers spread the wave.
Notice how often the answer is the same three parts: store before ack, a client-chosen id to make a retry safe, and a cursor to catch up.

Follow-up questions interviewers ask next

How do you send photos and videos?

The app uploads the file straight to object storage with a pre-signed URL, so the bytes never pass through a chat server. The chat message carries only the object key, the size and a small thumbnail. Recipients download through a CDN. Scan uploads for malware and strip metadata such as location. See Object storage (S3) & CDNs.

How would you add end-to-end encryption?

Keys live only on the devices. The server stores and relays ciphertext, so it can no longer read, search or filter content, and features that need plaintext (server-side search, link previews, spam scanning) move to the client. With several devices the sender encrypts a copy for each recipient device, which multiplies inbox entries. Group chats need a shared key that changes when members leave. The Signal protocol's Double Ratchet is the reference design.

What do you cache?

The newest page of the busiest conversations, in an in-memory cache in front of the message store; the user's conversation list; and group membership. Clients keep a local database of recent messages, so opening the app is instant and sync only fills the gap above the cursor.

How do you support a channel with 50,000 members?

One inbox entry per member would be 50,000 writes per message. Switch to one shared log per channel, let each device keep a cursor per channel, and tell connected members 'channel X has news' so they pull on demand. Show presence only for the first few dozen members, fetched when the list is opened.

Read receipts and typing indicators?

A typing indicator is ephemeral: relay it between connections and never store it. A read receipt is a cursor per member per conversation ('read up to message 311'), one tiny update instead of one per message. A group shows the minimum across members, or a count.

How do you stop abuse?

Rate limit sends per user at the chat server (4 · Design a rate limiter), cap group sizes and invitations, and offer block and report. Without end-to-end encryption the server can also scan content for spam.

The 60-second summary

I would split the system into stateless API servers for login, profiles and history, and stateful chat servers that each hold the WebSockets of their users, because a held-open connection gives instant delivery without the wasted requests of polling. Service discovery in ZooKeeper tells the API tier which chat server is closest and has room. A message goes to a chat server, which takes the next sequence number for that conversation, writes the body once to a key-value store, appends a pointer to the inbox of every member, and only then acknowledges the sender. Chat servers deliver from the inboxes. Offline users get a push notification and catch up by sending their cursor when they reconnect. Presence uses heartbeats and a grace period, so a tunnel does not flap the green dot, and it is pushed only to friends and small groups. The number that sizes the fleet is concurrent sockets, about seven million here, not messages per second.
