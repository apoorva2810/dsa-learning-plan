Design a web crawler

A web crawler is a loop: take a URL from a queue, download the page, keep what is new, and queue the links it found. This chapter walks the interview for it in four steps: scope and a back-of-the-envelope estimate, the eleven-stage pipeline, deep dives into BFS, the URL frontier (politeness, priority, freshness), the downloader and robustness against duplicates and spider traps, and a wrap-up you can say in a minute.

After this chapter you can
  • Estimate a crawl: pages per month to fetch rate, downloads in flight, storage, and 'have I seen this URL?' lookups per second
  • Draw the crawler pipeline from seed URLs to URL storage and say what each stage decides or stops
  • Explain why a crawler is BFS with a queue and a seen set, and what goes wrong with DFS or without the set
  • Design the URL frontier: one queue per host for politeness, front queues for priority, a re-crawl policy for freshness
  • List the downloader's speed-ups: robots and DNS caches, partitioning by host, nearby servers, short timeouts
  • Protect the crawl from duplicate content, duplicate URLs, spider traps and junk with checksums, a URL-seen filter and hard caps

Step 1 · Understand the problem and establish scope

A web crawler (also called a spider or a bot) starts from a list of known pages, downloads them, follows the links it finds, and repeats. Systems that need web data usually start with one:

  • Search engines crawl to build the index that answers queries.
  • Archives such as the Internet Archive keep dated snapshots of pages.
  • Data teams crawl for price comparison, research corpora and machine-learning training sets.
  • Monitors look for broken links, leaked content or misuse of a brand.

"Design a web crawler" sounds small and hides a long list of decisions, so agree on them before drawing anything (the four-step method is in 3 · A framework for system design interviews). For this chapter we assume:

  • Purpose: feed a search index. Only the HTML of each page matters.
  • Scale: 1.5 billion pages fetched per month, and the last 12 months are kept.
  • Content: HTML only for now, but the design must leave room for other types.
  • Freshness: new and changed pages show up within days, popular ones sooner.
  • Duplicates: a page whose content we already hold is dropped.
  • Behaviour: polite to the sites we visit, robust against broken pages and crashes, scalable by adding machines, extensible with new modules.

Questions a strong candidate asks

  1. What is the crawl for? A search index, an archive and a price scraper store different things and need different freshness.
  2. How many pages per month, and how long do we keep them? This fixes the fetch rate and the storage.
  3. HTML only, or images, PDFs and video too? Each type adds a downloader, a parser and storage.
  4. How fresh must pages be? 'Within a day' for news and 'within a month' for archives are very different schedules.
  5. Do we run JavaScript? Rendering pages in a browser multiplies the cost of every fetch.
  6. What counts as a duplicate, and which sites are off limits? This sets the dedup design and the robots policy.

Back-of-the-envelope: how big is this crawl?

Change the inputs and read the outputs (the method is in Back-of-envelope estimation). The peak factor is catch-up headroom, not user traffic: after an outage the crawler must work through a backlog faster than its average. 'In flight' is Little's law, rate × time per download. Sanity check: the IRLbot paper reports one server sustaining about 1,800 pages per second for 41 days, so even this peak is within reach of a few machines. Raw throughput is not the hard part; politeness and the seen-set are.

What moves between the stages

from dataclasses import dataclass, field


@dataclass(frozen=True)
class CrawlTask:
    url: str                       # absolute and normalised
    host: str                      # the unit of politeness: queues, DNS and robots caches are all per host
    priority: int                  # 0 is the most urgent
    lease_until: float             # no result by then: the frontier hands the URL out again


@dataclass
class FetchResult:
    url: str
    status: int                    # HTTP status, or 0 for a timeout or DNS failure
    body: bytes = b""


@dataclass
class ParsedPage:
    url: str
    text: str
    checksum: str                  # the key for "content seen?"
    links: list[str] = field(default_factory=list)


class UrlFrontier:
    def add(self, url: str, priority: int) -> None: ...            # called when "URL seen?" says the URL is new
    def next(self, now: float) -> CrawlTask | None: ...            # None while every host is cooling down
    def done(self, task: CrawlTask, ok: bool) -> None: ...         # starts the host's pause, or schedules a retry
The data passed between stages is small and explicit. The host is the key everything is organised around: the frontier's queues, the DNS cache and the robots cache are all per host.

Step 3 · Deep dive: BFS over the web graph

The web is a directed graph: pages are nodes and hyperlinks are directed edges. Crawling is graph traversal from the seeds, so the first design choice is the traversal order.

  • DFS follows one chain of links as far as it goes before backing up. On the web 'as far as it goes' can be thousands of pages (calendars, archives, generated listings), and the pages visited in a row usually belong to one site.
  • BFS takes every page one hop from the seeds, then every page two hops away, and so on. It needs only a FIFO queue, reaches many sites early, and tends to meet well-linked pages first: a study of a large crawl found that breadth-first order discovers high-PageRank pages early (PageRank scores a page by how many well-linked pages point to it).

So the crawler is BFS, and the queue is the frontier. Pages also link back to each other all the time (home page to article and back), so BFS needs a seen set to avoid queuing a page twice. Run the three scenarios below. Pages are named by site: n is a news site, b a blog, s a shop.

From a graph exercise to a crawler

The first crawler you would write

Recursive DFS. It loops for ever on cycles, has no depth limit, hammers one site, and a single slow server stalls everything.

def crawl(url):
    html = fetch(url)                  # no timeout, no robots check, no pause between requests
    save(url, html)                    # stores duplicates too
    for link in extract_links(html):
        crawl(link)                    # recursion is DFS: cycles loop for ever, depth hits the stack limit

The same crawler, hardened

A queue instead of recursion, a seen set for URLs and one for content, a pause per host, a timeout, and a filter before anything enters the queue.

import time


def crawl(seeds):
    frontier, seen, seen_content = UrlFrontier(), set(), set()
    for url in filter(None, map(normalise, seeds)):
        seen.add(url)
        frontier.add(url, priority=0)
    while not frontier.empty():
        task = frontier.next(now())                    # a URL whose host is allowed right now
        if task is None:
            time.sleep(0.05)                           # every host is cooling down
            continue
        page = fetch(task.url, timeout=10)             # robots rules and DNS come from caches
        frontier.done(task, ok=page is not None)       # starts the host's pause
        if page is None:
            continue
        digest = checksum(page)
        if digest in seen_content:
            continue                                   # same content under another URL
        seen_content.add(digest)
        save(task.url, page)
        for link in extract_links(page, base=task.url):
            link = normalise(link)
            if link and passes_filter(link) and link not in seen:
                seen.add(link)
                frontier.add(link, priority_of(link))

Step 3 · Deep dive: the URL frontier

▶ Video lesson: The URL frontier: polite first, important first 4:42 · 8 scenes · narrated, pause anytime and explore

In a graph exercise the frontier is a queue. In a crawler it is the component that decides which URL is fetched next, and that decision has four jobs:

  • Politeness. Every site is somebody else's server. Many simultaneous requests slow it down for real visitors, and the owner will throttle or block you. The rule: one request in flight per host, with a pause between consecutive requests.
  • Priority. A news front page that changes hourly and has thousands of inbound links deserves a slot before an archive page nobody links to.
  • Freshness. Pages change, so crawled URLs must come back on a schedule.
  • Volume. Billions of URLs do not fit in memory, and a plain disk file is too slow for constant inserts and removals. Real frontiers keep the bulk on disk, with in-memory buffers at the head and tail of each queue so most operations never touch the disk (see Message queues & streaming (Kafka) for durable queues).

Politeness: one queue per host

A plain BFS queue breaks the first rule, because links cluster: most links on a page point to the same site, so hundreds of URLs of one host sit side by side in the queue and are fetched in a burst. The fix is a queue per host and a clock per host, the earliest time that host may be contacted again. A free worker takes a URL from a queue whose clock has expired. The pause is usually a few seconds; a common rule of thumb makes it about ten times as long as the last download took. Some sites ask for a delay with a Crawl-delay line in robots.txt, which is not part of the standard.

Politeness in time: a shared queue versus a queue per site

Three workers download the same URLs (a1 is the first URL of site a.example, and so on). The lower lanes show how many requests each site receives and when it is cooling down. Switch scenarios.

Politeness is cheap across sites and expensive within one

With thousands of sites to rotate through, a worker nearly always finds one that is ready, so the pause costs almost nothing (third scenario). The cost lands on one huge site: 10 million pages at one request every 3 seconds is 30 million seconds, almost 11 and a half months. Politeness fixes the rate, not the backlog. So which pages get that site's few slots matters, and that is the job of priority.

Freshness: when does a crawled URL come back?

Re-fetch everything every N days. It is easy to build and easy to reason about, but wasteful: a news front page is stale after an hour while a company's 'About' page stays the same for years, and both are visited at the same rate. Use it as the baseline to beat.

Give each URL its own interval. When a visit finds the page changed, come back sooner next time; when it did not, back off. The interval converges on the page's real change rate without storing a model.

MIN_HOURS, MAX_HOURS = 1, 24 * 30


def next_interval(hours: float, changed: bool) -> float:
    """How long to wait before visiting a page again."""
    hours = hours / 2 if changed else hours * 2        # changed: come back sooner, unchanged: back off
    return min(MAX_HOURS, max(MIN_HOURS, hours))


# start at 24 h: unchanged visits give 48, 96, 192 ... up to 720 h; every change halves the wait again

Make a visit that finds nothing new cheap. Send If-None-Match or If-Modified-Since with the saved ETag (a version tag the server sent) or date, and an unchanged page answers 304 Not Modified with no body. A sitemap can also publish a last-modified date per URL; search engines use it only while it keeps matching reality, so treat it as a hint, not a fact.

from urllib.error import HTTPError
from urllib.request import Request, urlopen


def refetch(url: str, etag: str | None, last_modified: str | None):
    headers = {}
    if etag:
        headers["If-None-Match"] = etag
    if last_modified:
        headers["If-Modified-Since"] = last_modified
    try:
        with urlopen(Request(url, headers=headers), timeout=5) as resp:
            return resp.read(), resp.headers.get("ETag"), resp.headers.get("Last-Modified")   # changed: new body
    except HTTPError as err:
        if err.code == 304:
            return None, etag, last_modified                                                   # unchanged: no body sent
        raise

Step 3 · Deep dive: a fast, well-behaved downloader

The downloader spends nearly all of its time waiting for other people's servers, so its speed comes from not waiting twice. Four levers do most of the work, and a fifth rule keeps the crawler welcome:

  1. Partition by host. Route every URL to a crawl server by its host name, so one server owns all URLs of a site.
  2. Cache what repeats. DNS answers and robots rules are looked up once per host, not once per page (see DNS & what happens when you type a URL and Caching).
  3. Sit near the sites. Fewer miles mean shorter round trips and fewer timeouts.
  4. Give up quickly. A short timeout, a size cap and a type check keep one slow server from holding a worker.
  5. Obey robots.txt. The Robots Exclusion Protocol (RFC 9309) lets a site list the paths a crawler must not fetch.

The downloader's guards, in Python

Fetch the rules once per host and reuse them. Following RFC 9309: a 4xx answer means the site has no rules; a 5xx answer or a network error means treat the whole site as off limits until the file can be read; do not trust a cached copy for more than a day.

import time
from urllib.robotparser import RobotFileParser

ROBOTS_TTL = 24 * 3600                 # RFC 9309: do not reuse a cached copy for more than 24 hours
_robots: dict[str, tuple[float, RobotFileParser]] = {}


def rules_for(host: str, fetch_robots) -> RobotFileParser:
    """fetch_robots(url) -> (status, text): your downloader, with its timeouts. Status 0 means a network error."""
    now = time.time()
    hit = _robots.get(host)
    if hit and now < hit[0]:
        return hit[1]
    status, text = fetch_robots(f"https://{host}/robots.txt")
    rules, ttl = RobotFileParser(), ROBOTS_TTL
    if status == 200:
        rules.parse(text.splitlines())
    elif 400 <= status < 500:
        rules.allow_all = True         # "unavailable": the site publishes no rules
    else:
        rules.disallow_all = True      # "unreachable" (5xx or network error): stay away until it recovers
        ttl = 600                      # ...and look again in 10 minutes, not tomorrow
    _robots[host] = (now + ttl, rules)
    return rules


def may_fetch(url: str, host: str, fetch_robots, agent: str = "ExampleBot") -> bool:
    return rules_for(host, fetch_robots).can_fetch(agent, url)

An uncached lookup can take tens to hundreds of milliseconds and many resolver libraries block the calling thread. Look each host up once and reuse the answer until its TTL runs out.

import socket
import time

DNS_TTL = 300                          # seconds; real answers carry their own TTL, the standard library hides it
_dns: dict[str, tuple[float, list[str]]] = {}


def resolve(host: str) -> list[str]:
    now = time.time()
    hit = _dns.get(host)
    if hit and now < hit[0]:
        return hit[1]                  # cache hit: no network round trip
    infos = socket.getaddrinfo(host, 443, type=socket.SOCK_STREAM)
    addresses = sorted({info[4][0] for info in infos})
    _dns[host] = (now + DNS_TTL, addresses)
    return addresses

A socket timeout bounds each wait, not the whole download, so a server that sends one byte every few seconds can still hold a worker. Add a total deadline, a size cap and a content-type check.

import time
from urllib.request import Request, urlopen

MAX_BYTES = 2 * 1024 * 1024            # a 2 MiB cap: bigger bodies are rarely useful HTML
CHUNK = 16 * 1024


def fetch(url: str, total_timeout: float = 10.0) -> bytes | None:
    deadline = time.monotonic() + total_timeout
    request = Request(url, headers={"User-Agent": "ExampleBot/1.0 (+https://example.org/bot)", "Accept": "text/html"})
    try:
        with urlopen(request, timeout=3) as resp:                  # 3 s per socket operation: connect and each read
            if "text/html" not in resp.headers.get("Content-Type", ""):
                return None                                        # not HTML: do not even read the body
            body = bytearray()
            while chunk := resp.read(CHUNK):
                body += chunk
                if len(body) > MAX_BYTES or time.monotonic() > deadline:
                    return None                                    # too big, or a slow drip past the total deadline
            return bytes(body)
    except (OSError, ValueError):
        return None                                                # DNS failure, refused, timed out, bad URL

Step 3 · Deep dive: staying robust

▶ Video lesson: Staying robust: duplicates, traps and noise 3:51 · 7 scenes · narrated, pause anytime and explore

The web is not a clean graph. Three kinds of mess get past a naive crawler.

Duplicate content. One article lives at many URLs: mirrors, print views, ?utm_source= variants. After parsing, compute a checksum of the visible text and look it up in the content seen? store. An exact match stops the page. Checksums only catch identical text; near duplicates (the same article under a different ad block) need a similarity hash such as SimHash.

Duplicate URLs. HTTP://Example.org:80/a?b=2&a=1#top and http://example.org/a?a=1&b=2 are, for crawling purposes, one page. Normalise every URL before the URL seen? check: lowercase the scheme and host, drop the default port and the fragment, sort the query parameters, strip tracking parameters. The check itself must answer 'seen it?' for billions of URLs in microseconds, which is a sizing question (below).

Traps and noise. A spider trap is a set of pages that generates endless new URLs: a calendar that links to next month for ever, a session ID in every link, a relative link that appends itself to the path. Each URL is new and the content is almost new, so both seen-checks wave everything through. Only hard caps stop a trap. Noise is milder: pages that are mostly ads, spam or code add cost and no value, so the parser drops them on simple signals such as almost no visible text or a failed validation.

How big is the URL-seen set?

An exact set stores a fingerprint per URL. A Bloom filter stores a few bits per URL instead and answers 'definitely new' or 'probably seen': a small false-positive rate, never a false negative. A common design puts the Bloom filter in front of the exact store, so only a 'probably seen' answer costs a lookup there (Bloom filters also appear in Caching).

A spider trap eats the crawl

Each round is one politeness interval: every site with work left gets one request. Three ordinary sites have 4, 3 and 5 pages. The fourth has a calendar that links to the next month for ever. Compare the run without guards with the run that has a per-site budget.

URL hygiene in Python

Run this on every extracted link, before the seen check, so that equal URLs become equal strings.

from urllib.parse import parse_qsl, urlencode, urljoin, urlsplit, urlunsplit

DEFAULT_PORT = {"http": 80, "https": 443}
TRACKING = {"fbclid", "gclid"}


def normalise(url: str, base: str | None = None) -> str | None:
    if base:
        url = urljoin(base, url)                       # relative link -> absolute URL
    parts = urlsplit(url.strip())
    scheme = parts.scheme.lower()
    if scheme not in DEFAULT_PORT or not parts.hostname:
        return None                                    # mailto:, javascript:, ftp:, empty host ...
    try:
        port = parts.port
    except ValueError:
        return None                                    # garbage such as http://host:abc/
    netloc = parts.hostname.lower()
    if port not in (None, DEFAULT_PORT[scheme]):
        netloc += f":{port}"
    query = sorted((k, v) for k, v in parse_qsl(parts.query, keep_blank_values=True)
                   if not k.startswith("utm_") and k not in TRACKING)
    return urlunsplit((scheme, netloc, parts.path or "/", urlencode(query), ""))    # "" drops the #fragment


# normalise("HTTP://Example.org:80/a?b=2&utm_source=x&a=1#top")  ->  "http://example.org/a?a=1&b=2"

Three cheap checks and a budget. The numbers are examples: tune them per crawl.

from collections import Counter
from urllib.parse import urlsplit

MAX_URL_CHARS = 2000
MAX_SEGMENTS = 12
MAX_REPEATS = 2
PAGES_PER_HOST = 50_000                # per crawl pass; raise it for hosts that earn it


def verdict(url: str, pages_so_far: dict[str, int]) -> str:
    """'drop', 'park' or 'ok' for an already normalised URL."""
    parts = urlsplit(url)
    segments = [s for s in parts.path.split("/") if s]
    if len(url) > MAX_URL_CHARS or len(segments) > MAX_SEGMENTS:
        return "drop"                                              # runaway path
    if max(Counter(segments).values(), default=0) > MAX_REPEATS:
        return "drop"                                              # /a/b/a/b/a/b ...: the path feeds on itself
    if pages_so_far.get(parts.hostname, 0) >= PAGES_PER_HOST:
        return "park"                                              # budget used up: keep the URL, do not fetch yet
    return "ok"

Hash the visible text, not the raw HTML, so changed ads and timestamps in markup do not hide a duplicate.

import hashlib
import re

seen_content: set[str] = set()


def content_checksum(html: str) -> str:
    text = re.sub(r"(?is)<(script|style)\b.*?</\1>", " ", html)      # drop scripts and styles
    text = re.sub(r"(?s)<[^>]+>", " ", text)                         # drop the tags
    text = " ".join(text.lower().split())                            # collapse whitespace, ignore case
    return hashlib.sha256(text.encode("utf-8")).hexdigest()[:32]     # 128 bits: accidental collisions are negligible


def is_duplicate(html: str) -> bool:
    digest = content_checksum(html)
    if digest in seen_content:
        return True
    seen_content.add(digest)
    return False

Step 4 · Wrap up

The life of one URL

stateDiagram-v2
  [*] --> Discovered
  Discovered --> Queued: passes the filters and the seen check
  Queued --> Blocked: robots rules forbid the path
  Queued --> Fetching: host is due and a worker is free
  Fetching --> Stored: new content
  Fetching --> Duplicate: checksum already known
  Fetching --> RetryLater: timeout or server error
  RetryLater --> Queued: backoff has passed
  RetryLater --> Dead: too many failures
  Stored --> Queued: re-crawl is due
  Blocked --> [*]
  Duplicate --> [*]
  Dead --> [*]
Every URL is in exactly one of these states. Failures have a way out, so nothing is retried for ever.

Say it in a minute

'I would build the crawler as a loop. Seed URLs go into a URL frontier. Download workers take a URL whose host is due, check cached robots rules and a cached DNS answer, and fetch the page. The parser extracts text and links; a checksum lookup drops content we already hold, and new pages go to storage. Links are normalised, filtered and checked against a URL-seen set before they re-enter the frontier. The frontier has two layers: front queues order URLs by priority, and one back queue per host enforces a pause between requests to the same site. Hosts are partitioned across crawl servers with consistent hashing, so politeness and caches stay local. For robustness I add timeouts and size caps, depth, length and per-host budget limits against spider traps, and checkpoints so a crash resumes. At 1.5 billion pages a month that is about 580 fetches a second on average and 150 terabytes of new pages a month.'

Go deeper

  • System Design Interview – An Insider's Guide, volume 1 (Alex Xu) — the book this track distils; chapter 9 is the web crawler
  • RFC 9309: Robots Exclusion Protocol — how to read robots.txt, what to do when it is missing or unreachable, and how long to cache it
  • Heydon and Najork: Mercator, a scalable, extensible Web crawler — the classic design: per-host queues, bounded memory, pluggable modules
  • Najork and Wiener: Breadth-first crawling yields high-quality pages — the evidence that BFS order finds well-linked pages early
  • Lee, Leonard, Wang, Loguinov: IRLbot, scaling to 6 billion pages and beyond — a single server at about 1,800 pages per second, with per-site budgets against spam and traps
  • Manning, Raghavan, Schütze: Introduction to Information Retrieval, the URL frontier — front queues for priority and back queues for politeness, with the timing heap
