Design a unique ID generator in distributed systems

Many machines must mint ids at the same moment, without asking each other, and the ids must be numeric, fit in 64 bits and sort by time. This chapter walks the four interview steps, compares multi-master auto-increment, UUIDs, a ticket server and a Snowflake-style generator, builds a Snowflake id bit by bit, and covers sequence overflow, clock skew, backwards clocks and how to size the fields.

After this chapter you can
  • Turn 'generate unique ids' into requirements and estimate the throughput and the bits they need
  • Explain why multi-master auto-increment stepping cannot give time order and is hard to grow
  • Compare UUIDs, a ticket server and a Snowflake-style generator on size, order, coordination and failure
  • Lay out the 64-bit Snowflake id (1 + 41 + 5 + 5 + 12) and state what each field can hold
  • Walk next_id(): a new millisecond resets the sequence, a full sequence waits for the next millisecond
  • Name what can still go wrong (backwards clocks, shared worker ids, skew) and the guard for each

Step 1 · Understand the problem and establish scope

Every row in a distributed system needs a name no other row has: an order, a message, a payment. On one database that is solved for you. AUTO_INCREMENT hands out 1, 2, 3 and never repeats. The interview question begins when many machines must mint ids at the same moment without asking each other first.

Answers we will assume to the clarifying questions:

  • Unique. No two ids are ever equal, across every machine and every data centre.
  • Numeric, at most 64 bits. One BIGINT column. Eight bytes to index, join and sort.
  • Ordered by time, roughly. An id made later is larger, to the precision of the clock. Then ORDER BY id is close to ORDER BY created_at, and a range of ids is a range of time.
  • Fast and available. Tens of thousands of ids per second at peak. No single machine whose failure stops everybody from writing, and ideally no network call per id.
  • Gaps are fine. We never promise consecutive numbers. Gap-free invoice numbers are a different problem with a different answer.

What a strong candidate asks

Questions worth asking before you draw anything: What are the ids for (primary keys, or shown in URLs)? Must they be numbers, and in how many bits? Must they sort by time, and how exactly: strictly across machines, or roughly? How many ids per second at peak, from how many machines and data centres? For how many years must they stay unique? Is a gap acceptable? Is a guessable id? Each answer removes a design, and saying which one it removes is what Step 1 is for.

How many ids, and how many bits?

Change the traffic and watch two numbers: how many ids the fleet must mint, and how many bits it takes just to count them. With the defaults, 6.3 trillion ids need only 43 bits. The id has 64, so the other 21 bits are free to carry structure: when the id was made, and by whom.

The signal that picks the design: ask the questions from the top and stop at the first answer that fits.

We pick the generator and run it inside each service as a library. next_id() -> int is a function call, so a new row costs no network hop and nothing is shared between servers at runtime. The only thing a generator needs from outside, once, at startup, is a worker identity nobody else holds (see the clocks section).

If many languages need ids, or you want one place to manage worker identities, wrap the same code in a small id service: POST /v1/ids with {"count": 100} returns {"ids": ["291502507275239424", ...]}. Ask for ids in batches so the extra hop is amortised, and return them as strings.

Deep dive 1 · Auto-increment stepping, and why ordering breaks

The first idea reuses what every database has. In multi-master replication each server accepts writes, and two settings keep their numbers apart: auto_increment_increment is the step, set to the number of servers k, and auto_increment_offset is the lane a server owns. With k = 3, server A hands out 1, 4, 7, server B hands out 2, 5, 8 and server C hands out 3, 6, 9. The lanes never meet, so there are no collisions and no coordination.

That earns numeric and 64-bit, and little else. In the simulation the requests arrive in the order of the clock, but each server counts at its own pace. Watch for ids that are handed out later but are smaller.

Three lanes, nine orders

Scenario 1 shows the ordering problem. Scenario 2 adds a server and shows what a changed step does to a newcomer that has not caught up with replication.

What stepping costs you

Ordering. A busy lane runs ahead of a quiet one, so id order is not time order, and a reader that polls with id > last_seen silently skips rows from the slower lanes. Growth. The step is a cluster-wide setting: a new server means changing every server and seeding the newcomer above all existing ids, which widens the ordering gap. Cost. Every id is still a database write, and across data centres each lane is only as available as replication.

Deep dive 2 · UUIDs and ticket servers: close, but not enough

Two more candidates, and where each one stops

A UUID is 128 bits, written as 32 hex digits in an 8-4-4-4-12 pattern, for example 3f2c9a1e-7b44-4d0e-9c1a-5b8e2d6f0a13. Version 4 fills 122 of those bits with random data (the other six mark the version and variant), so every server can make ids alone with no coordination at all.

Collisions are not the problem: you would need about 2.7 quintillion ids for even odds of one duplicate. The problems are the 128 bits (twice the budget, 16 bytes in every index entry and foreign key), the hex text, and the randomness. A random key lands in a random place of a B-tree, splitting pages and pushing hot pages out of memory, where a time-ordered key appends at the right edge.

Newer formats put time first. UUIDv7 (RFC 9562) starts with a 48-bit Unix timestamp in milliseconds followed by random bits. ULID is 48 bits of time plus 80 random bits, written as 26 characters. Both sort by time and need no coordination, which fixes the index problem.

They are still 128 bits and not a number, so against our requirements (64-bit, numeric) they fail. Against a requirement with no size cap they are a good default.

One small database whose only table has an auto-increment column. A service asks for a number, the server runs a one-row replace and returns the new counter, and the service uses it as its id. It is the simplest design that gives strictly increasing 64-bit numbers.

Its weaknesses are structural. Every id costs a network round trip, and the server sits on the critical path of every write: a single point of failure. Running two with odd and even steps removes the single point and brings back everything from the previous section. Handing out ids in blocks (a service takes 1,000 at a time and spends them locally) cuts the round trips, but ids from different services then interleave, and a service that crashes wastes the rest of its block.

CREATE TABLE tickets (
    id   BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    stub CHAR(1) NOT NULL UNIQUE
);

REPLACE INTO tickets (stub) VALUES ('a');     -- always the same row, so the table never grows
SELECT LAST_INSERT_ID();                      -- this connection's new number

Deep dive 3 · The Snowflake layout, bit by bit

▶ Video lesson: Building a Snowflake id, bit by bit 6:29 · 6 scenes · narrated, pause anytime and explore

Instead of asking a database for a counter, build the id from three things every machine already has: what time it is, who it is, and how many ids it has already made in this millisecond. Pack them into 64 bits, most significant first:

  • 1 sign bit, always 0. The id stays positive in signed 64-bit types.
  • 41 bits of timestamp: milliseconds since an epoch you choose.
  • 5 bits of datacentre and 5 bits of machine: together a 10-bit worker id.
  • 12 bits of sequence: a counter for the ids one worker makes inside one millisecond.

The order is not arbitrary. Comparing two integers looks at the highest bits first, so with the timestamp on top a later millisecond always wins and numeric order is time order. The worker id comes next so that two workers never make the same number in the same millisecond. The counter sits at the bottom to separate the ids one worker makes within one millisecond.

The three right-hand bands are the low 22 bits: who made the id and which one it was. Everything to the left is time, which is why sorting the integers sorts by creation time.

Build one id, field by field

The three rows are one integer. The small numbers above the cells count from the right inside each row, so only the bottom row shows the id's own bit numbers. Under each row, the decimal values of the fields in it, separated by bars. A field takes its colour when it is filled in.

Deep dive 4 · One millisecond, many ids: the sequence field

Inside one worker the interesting part is the sequence. It counts ids made in the current millisecond and returns to 0 when the millisecond changes. Twelve bits hold 4,096 values, so one worker can mint 4,096 ids per millisecond, about 4.1 million per second. That is 68 times our 60,000-per-second fleet peak, from a single worker.

The generator is a short function. It reads the clock, compares it with the last millisecond it used, and takes one of three paths. Step through it, then read the code.

flowchart TD
  S([next_id called]) --> C[Read the clock in ms]
  C --> B{now is before<br/>last_ms?}
  B -->|yes| X[Clock moved back:<br/>refuse or wait]
  B -->|no| E{now equals<br/>last_ms?}
  E -->|no, a new ms| R[sequence = 0]
  E -->|yes, same ms| I[sequence + 1,<br/>keep 12 bits]

  O -->|yes| W[Wait for the<br/>next ms]
  O -->|no| P[Pack timestamp, datacentre,<br/>machine and sequence]
  R --> P
  W --> P
  P --> D([Return the id])
Three paths through next_id(): new millisecond, same millisecond, and same millisecond with a full counter.

The generator in Python

Thread-safe, with an injectable clock so a test can make time jump forwards and backwards.

import threading
import time

EPOCH_MS = 1_704_067_200_000                      # 2024-01-01 00:00:00 UTC, our own epoch
SEQUENCE_BITS, MACHINE_BITS, DATACENTRE_BITS = 12, 5, 5
MAX_SEQUENCE = (1 << SEQUENCE_BITS) - 1           # 4095
MACHINE_SHIFT = SEQUENCE_BITS                     # 12
DATACENTRE_SHIFT = MACHINE_SHIFT + MACHINE_BITS   # 17
TIMESTAMP_SHIFT = DATACENTRE_SHIFT + DATACENTRE_BITS   # 22


class ClockMovedBackwards(Exception):
    pass


class SnowflakeGenerator:
    def __init__(self, datacentre: int, machine: int, clock_ms=lambda: time.time_ns() // 1_000_000):
        if not (0 <= datacentre < 1 << DATACENTRE_BITS and 0 <= machine < 1 << MACHINE_BITS):
            raise ValueError("datacentre and machine must each fit in 5 bits")
        self.datacentre, self.machine = datacentre, machine
        self.clock_ms = clock_ms
        self.last_ms = -1
        self.sequence = 0
        self.lock = threading.Lock()

    def next_id(self) -> int:
        with self.lock:
            now = self.clock_ms()
            if now < self.last_ms:                        # the clock went backwards
                raise ClockMovedBackwards(f"clock is {self.last_ms - now} ms behind")
            if now == self.last_ms:                       # same millisecond: next sequence number
                self.sequence = (self.sequence + 1) & MAX_SEQUENCE
                if self.sequence == 0:                    # 4,096 ids already made in this millisecond
                    now = self._wait_for_next_ms(self.last_ms)
            else:                                         # a new millisecond: start counting again
                self.sequence = 0
            self.last_ms = now
            return (((now - EPOCH_MS) << TIMESTAMP_SHIFT)
                    | (self.datacentre << DATACENTRE_SHIFT)
                    | (self.machine << MACHINE_SHIFT)
                    | self.sequence)

    def _wait_for_next_ms(self, last_ms: int) -> int:
        now = self.clock_ms()
        while now <= last_ms:                             # spins for less than a millisecond
            now = self.clock_ms()
        return now

Fields come back out with shifts and masks. This is also how you turn an id into a creation time, or build the smallest id for a given time to use as a range-scan boundary.

EPOCH_MS = 1_704_067_200_000

def decode(snowflake_id: int) -> dict:
    """Unpack an id with shifts and masks. The layout is 1 | 41 | 5 | 5 | 12."""
    return {
        "created_ms": (snowflake_id >> 22) + EPOCH_MS,    # drop the 22 low bits, add the epoch back
        "datacentre": (snowflake_id >> 17) & 0b11111,     # keep 5 bits
        "machine": (snowflake_id >> 12) & 0b11111,        # keep 5 bits
        "sequence": snowflake_id & 0xFFF,                 # keep the low 12 bits
    }

print(decode(291502507275239424))
# {'created_ms': 1773566813589, 'datacentre': 3, 'machine': 12, 'sequence': 0}

The sequence fills up

Same worker, same millisecond. Scenario 1 shows the guard; scenario 2 shows what happens without it.

The one line that matters

Counter without a guard

At the 4,097th id of a millisecond the extra bit lands in the machine field. The id now looks like another worker's.

def pack_unguarded(ts, datacentre, machine, sequence):
    sequence += 1
    return (ts << 22) | (datacentre << 17) | (machine << 12) | sequence
    # at 4096 the extra bit lands in the machine field

Mask, test for zero, wait

The mask keeps the counter inside its twelve bits. The zero test catches the wrap, and the wait moves to a fresh millisecond, where sequence 0 has not been used.

def pack_guarded(ts, datacentre, machine, sequence):
    sequence = (sequence + 1) & 4095
    if sequence == 0:                  # wrapped: 4,096 ids used in this millisecond
        ts = wait_for_next_ms(ts)
    return (ts << 22) | (datacentre << 17) | (machine << 12) | sequence

Deep dive 5 · Clocks, restarts and worker ids

Uniqueness now rests on two promises: no two live workers share a (datacentre, machine) pair, and a worker never issues the same (millisecond, sequence) twice. The second holds only while the worker's clock does not run backwards. Real clocks do.

NTP keeps clocks within about a millisecond inside a well-run data centre and tens of milliseconds across the internet. It corrects small errors by slightly slowing or speeding the clock, but it steps the clock when the error is large (the classic ntpd threshold is 128 ms), and a step can go backwards. A virtual machine resuming from a pause, or a leap second, does the same.

Two different problems follow. Skew between machines only blurs the ordering: ids from two machines whose clocks differ by 5 ms can sort up to 5 ms out of true order, but they stay distinct because the worker ids differ. A clock that jumps backwards on one machine threatens uniqueness, because that worker could repeat a millisecond it has already used.

sequenceDiagram
  participant App as Caller
  participant G as Generator

The generator's memory of last_ms is what turns a silent duplicate into a visible error.

Three policies for a backwards clock

What Twitter's original code did. Safe and loud. The caller retries, and another worker can answer. Alert on the error rate, because a stepped clock usually means an NTP problem.

if now < self.last_ms:
    raise ClockMovedBackwards(self.last_ms - now)     # the caller retries, another worker may answer

Right for jitter of a few milliseconds. Set a cap: a large step needs a human, not a long sleep while callers queue.

MAX_WAIT_MS = 5

behind = self.last_ms - now
if behind > 0:
    if behind > MAX_WAIT_MS:                          # a real step, not jitter: do not hide it
        raise ClockMovedBackwards(behind)
    time.sleep(behind / 1000)                         # a few ms: let the clock catch up
    now = self.clock_ms()
    if now < self.last_ms:
        raise ClockMovedBackwards(self.last_ms - now)

Read the wall clock once at startup and measure elapsed time with a monotonic clock, which NTP steps cannot move backwards. The ids can drift from true time, so re-anchor on restart and alert on drift. Persist the last timestamp used so a restart cannot start behind it.

START_WALL_MS = time.time_ns() // 1_000_000           # read the wall clock once, at startup
START_MONO_NS = time.monotonic_ns()                   # a clock that never goes backwards

def now_ms() -> int:
    return START_WALL_MS + (time.monotonic_ns() - START_MONO_NS) // 1_000_000

Step 4 · Wrap up

Follow-up questions, and short answers

  • Can ids be strictly ordered across machines? Only through a single sequencer, which brings back the bottleneck, or with logical clocks. Snowflake ids are ordered to the millisecond, within the clock skew. For the strict order of one entity's changes, store a version number on the entity.
  • One worker needs more than 4,096 ids per millisecond. Run more workers, or move bits from the timestamp to the sequence (see the calculator below).
  • More than 1,024 workers. The same trade: take bits from the sequence or the timestamp.
  • Do the ids leak anything? Yes: creation time, and over time volume. If that matters, keep the Snowflake id internal and show users an opaque id.
  • What would you add with more time? A lease service for worker ids, a persisted floor timestamp so restarts cannot go back in time, metrics for waits and backwards-clock errors, and a property test that runs many threads against a fake clock that jumps forwards and backwards.

What a bit budget buys

The 63 bits after the sign bit are shared by four jobs. Give one field more bits and another must give some up. Try 39 / 8 / 8 / 8 to see a long-lived, small-fleet layout, or 38 / 6 / 7 / 12 for a bigger fleet.

A 60-second answer

'Ids must be unique, 64-bit, numeric and roughly sorted by time at tens of thousands per second. Multi-master auto-increment can't sort by time and is rigid to grow, UUIDs are 128-bit and random, and a ticket server is a hop and a single point of failure. So I'd use a Snowflake-style generator: one sign bit, 41 bits of milliseconds since a custom epoch, which lasts 69 years, 5 bits of datacentre, 5 of machine, and a 12-bit sequence that resets every millisecond and waits for the next one if it fills, 4,096 ids per millisecond per worker. Each service builds ids locally, so there is no coordination on the write path. The risks are operational: a backwards clock, which I refuse or wait out, and duplicate worker ids, which I prevent by leasing them from a registry.'
