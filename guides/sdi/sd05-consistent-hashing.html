Design consistent hashing

Consistent hashing answers one question for cache fleets, sharded stores and load balancers: which server owns this key, in a way that survives servers joining, leaving and crashing. Walk the interview steps: why hash(key) % N breaks, the hash ring, which keys move when the pool changes, virtual nodes for even load, and the alternatives, with a simulation for every mechanism.

After this chapter you can
  • Show with numbers why hash(key) % N remaps most keys when the server count changes, and what that does to a cache
  • Build a hash ring: place servers and keys, find a key's owner clockwise, handle the wrap-around, and implement the lookup with a sorted list and a binary search
  • State exactly which keys move when a server joins or leaves, and why they all land on one neighbour
  • Explain the two weaknesses of the basic ring, fix them with virtual nodes, and quote the load spread you get for a given count
  • Choose between a ring, rendezvous hashing, jump hash and fixed slots, and name real systems that use each
  • Run the interview script: scope, estimate, high-level design, deep dives, wrap-up

Step 1 · Understand the problem and establish scope

Spreading data over many machines raises the same question again and again: which machine holds this key? A cache fleet decides which cache server holds user:42. A sharded database decides which shard stores a row. A load balancer that wants session affinity decides which backend serves a user. Each time the answer must come from a calculation any client can repeat, without asking a central table, and it must keep working while machines come and go.

Pin the problem down before drawing anything. This chapter works with these answers, and an interview answer should say them out loud so the interviewer can correct you:

  • Function: owner(key) returns exactly one server for every key, the same answer on every client. Servers can be added and removed at any time, and they can crash.
  • Balance: each server holds about the same share of the keys, within a few per cent.
  • Stability: when the server set changes, as few keys as possible change owner. This is the property that gives consistent hashing its name.
  • Scale: 10 to a few hundred servers, tens of millions of keys, lookups in microseconds and in-process.
  • Out of scope here: replication, quorums and failure detection. They sit on top of the placement function this chapter builds, and 6 · Design a key-value store covers them.

Questions a strong candidate asks

  • What lives on these servers: cache entries (a lost key costs one database read) or the system of record (a lost key is lost data)? That decides whether a moved key needs a data copy.
  • How often does the server set change: planned deploys only, or crashes and autoscaling several times a day?
  • Are the servers identical, or do some have more memory and capacity?
  • Is key popularity flat, or does a handful of keys (a celebrity, a flash sale) take a large share of the traffic?
  • Who does the routing: a client library, a proxy tier, or the servers themselves?
  • Do we need each key on several servers?

What one server change costs

A cache pool of ten servers gains an eleventh. Compare what the two placement schemes do to the keys and to the database behind the cache. Reads are assumed to be spread evenly over the keys, so the share of keys that move is also the share of cache hits that turn into misses. The estimating method is the one from 2 · Back-of-the-envelope estimation.

Step 2 · Propose a high-level design

Three roles are enough.

  • Servers hold the keys. They need to know nothing about each other or about placement.
  • A router answers one question, owner(key), from a small description of the pool. It can be a library inside every client, a proxy tier, or code inside the servers themselves (the table below compares them).
  • A membership source tells every router when a server joins, leaves or fails, so that all routers hold the same ring. Two routers with different rings send the same key to different servers.

The interface the router offers is deliberately tiny:

  • add_server(name, weight) and remove_server(name) change the pool.
  • owner(key) returns the server for a key. A store that keeps replicas also needs owners(key, n), the first n different servers for a key.

The rest of the chapter is about computing owner so that these calls disturb as few keys as possible. Session affinity at a load balancer (Load balancers, reverse proxies & API gateways) is the same problem with requests in place of keys.

Step 3 · Deep dive: why hash mod N breaks

The obvious placement function is a remainder. Hash the key to a number, divide by the number of servers and keep what is left:

server = servers[hash(key) % len(servers)]

It is fast, it needs only the server list, and it spreads keys evenly when the hash is good. Its flaw is that N is part of the formula. Change N and the remainder changes for almost every key.

How many? Take one server out of a list of four and a key keeps its server only when hash % 4 and hash % 3 happen to name the same machine, which is true for about one hash in four. In general, removing one of N servers leaves only about 1/N of the keys where they were, and adding a server to N leaves about 1/(N + 1). With 10 servers, one crash relocates roughly 90% of the keys.

For a cache that is an outage, not an inconvenience. A moved key is missing from its new server, so each read of it is a miss that falls through to the database, at the moment the pool is one server short. Caching calls the result an avalanche. The simulation uses twelve keys with a toy three-digit hash so you can check every remainder by hand, and its last step repeats the experiment on 100,000 keys. Step 3 · Deep dive: the hash ring

▶ Video lesson: The hash ring: moving only the keys that must move 5:20 · 8 scenes · narrated, pause anytime and explore

Servers and keys on one circle

Choose a hash function with a wide output (MD5 or SHA-1 cut to 64 bits, or a fast one such as MurmurHash) and treat its output range as a ring: the biggest value is followed by 0 again, like the hours on a clock face. The pictures use a toy ring of 360 positions so the numbers are easy to read. A real ring has 2^32 positions or far more.

  1. Hash every server name (or address) onto the ring.
  2. Hash every key onto the same ring with the same function.
  3. A key belongs to the first server met walking clockwise from the key.

The ring itself is never stored. The only state is the sorted list of server positions, and any router holding the same list computes the same owners.

Lookup is a binary search

Keep the positions in a sorted array. To place a key, hash it and binary-search for the first position at or after the hash. If the search runs off the end, wrap to element 0. That costs O(log n) per lookup and a few bytes per server, so a router can hold the whole ring in memory. It is the same search as Search Insert Position.

A hash ring with virtual nodes in Python

import bisect
import hashlib


def position(text: str) -> int:
    """A stable 64-bit position. Python's built-in hash() is salted per process, so two clients would disagree."""
    return int.from_bytes(hashlib.md5(text.encode()).digest()[:8], "big")


class HashRing:
    def __init__(self, vnodes: int = 100):
        self.vnodes = vnodes
        self._points: list[int] = []           # sorted positions of every virtual node
        self._server_at: dict[int, str] = {}   # position -> server name

    def add_server(self, name: str, weight: int = 1) -> None:
        for i in range(self.vnodes * weight):
            pos = position(f"{name}#{i}")
            self._server_at[pos] = name
            bisect.insort(self._points, pos)

    def remove_server(self, name: str) -> None:
        self._points = [p for p in self._points if self._server_at[p] != name]
        self._server_at = {p: s for p, s in self._server_at.items() if s != name}

    def owner(self, key: str) -> str:
        i = bisect.bisect_left(self._points, position(key))             # first point at or after the key
        return self._server_at[self._points[i % len(self._points)]]     # i == len means: wrap to point 0

    def owners(self, key: str, n: int = 3) -> list[str]:
        """Replica set: walk clockwise and keep the first n DIFFERENT servers."""
        start = bisect.bisect_left(self._points, position(key))
        found: list[str] = []
        for step in range(len(self._points)):
            server = self._server_at[self._points[(start + step) % len(self._points)]]
            if server not in found:
                found.append(server)
                if len(found) == n:
                    break
        return found


ring = HashRing(vnodes=100)
for name in ("cache-a", "cache-b", "cache-c"):
    ring.add_server(name)

keys = [f"user:{i}" for i in range(10_000)]
before = {k: ring.owner(k) for k in keys}
ring.add_server("cache-d")
moved = sum(ring.owner(k) != before[k] for k in keys)
print(moved / len(keys))          # about 0.25: only the new server's share moves
A sorted list of points plus bisect is the whole data structure. The built-in hash() is salted per process, so two clients would place the same key differently; use a stable hash such as MD5 cut to 64 bits. Run it: only about a quarter of the keys move when the fourth server arrives.

Moving from modulo hashing to a ring

hash(key) % N

  • The owner depends on N, so every change of N reshuffles about (N − 1) / N of the keys.
  • State: the server list.
  • Balance: even, if the hash is good.
  • After a crash: a miss storm on the database.

Hash ring

  • The owner depends on a key's neighbours, so a join or a leave moves only about 1/N of the keys, the ones next to the change.
  • State: the sorted server positions.
  • Balance: depends on where the points happen to land (next section).
  • After a crash: only the dead server's keys miss.

Step 3 · Deep dive: uneven load and virtual nodes

▶ Video lesson: Virtual nodes: even load and gentler failures 4:03 · 7 scenes · narrated, pause anytime and explore

The basic ring fixes the reshuffling and leaves two problems.

  1. Arcs are random. A server owns the arc between its predecessor and itself. Four random points rarely cut a circle into four equal arcs, so one server may own 40% of the keys and another 8%. A fleet sized for the average overloads the big one and wastes the small one.
  2. A leaving server dumps its whole arc on one neighbour. The clockwise successor now owns its own arc plus the dead server's. If it was already busy it may fail next, and then its successor inherits again: a cascading failure.

A third problem looks similar and is different. One hot key, such as a celebrity profile, sits at a single position, and no placement scheme can split one key. Virtual nodes do not fix it; Caching lists what does (replicate the key, cache it in front).

Virtual nodes

Stop giving each server one point. Hash every server v times (S0#0, S0#1, ... S0#99) and put all the points on the ring. They are virtual nodes: one machine, many places. A server's load is now the sum of many small arcs, and a sum of many random pieces stays close to its average. When a server leaves, each of its small arcs passes to the point that follows it, which belongs to a different server almost every time, so the extra load spreads over all the survivors. When one joins, it takes small slices from many servers instead of one big slice from one.

What an interviewer is listening for

Keep three problems apart. Uneven arcs and a neighbour that inherits everything are fixed by virtual nodes. One key that is simply too popular is not: replicate it under several names or cache it in front. Servers of different size are handled by giving the big ones more virtual nodes, in proportion to their capacity.

Step 3 · Deep dive: which keys move, and how they move

The rule behind the ring simulation fits in two lines, and it is worth saying in the interview:

  • A server joins at position p. Walk counter-clockwise from p to the next server point. The keys on that stretch used to belong to p's clockwise neighbour and now belong to the newcomer. Nothing else moves.
  • A server leaves. Its keys pass to its clockwise neighbour. Nothing else moves.

With virtual nodes the rule applies to each of the v points, so a newcomer takes v small slices, each from whichever server owned the point after it.

Replicas use the same walk. A store that keeps each key on N servers starts at the key and collects the first N different physical servers going clockwise, skipping extra points of a server it already has (and, in production, servers in the same rack or zone). HashRing.owners above does exactly that. What a "move" costs depends on what the servers hold:

Moving keys in a cache and in a store

Cache pool

  • Nothing is copied. Routers learn the new ring and each affected key simply misses once.
  • Cost: one database read per moved key, which is why a small moved share matters.
  • A short disagreement between routers is harmless: a request that reaches the wrong server just misses.

Data store

  • Data must be copied. The newcomer streams the affected ranges from their old owners and serves them only after it has caught up.
  • The old owners drop the moved data after a grace period, once every router has the new ring.
  • Routers that disagree can send a write to the wrong place, so the hand-over needs versions or forwarding (6 · Design a key-value store).

Step 3 · Deep dive: alternatives and where this is used

Four ways to place keys on a changing pool

The classic answer and the subject of this chapter: sorted points, a binary search, virtual nodes for balance. Lookup is O(log n), memory is O(n × v), and a join or a leave touches about 1/N of the keys. Use it when servers come and go and the ring fits in memory. Weights are just more points.

ring = HashRing(vnodes=100)
ring.add_server("cache-big", weight=2)     # twice the points, so about twice the keys
ring.add_server("cache-small")
print(ring.owner("user:42"), ring.owners("user:42", n=2))

Also called highest random weight. Every server scores the key and the highest score wins. There is no ring, no virtual nodes and no state beyond the server list. Removing a server moves only its keys, and they spread over all the others because each key's second-best server differs. The price is that a lookup scores every server: fine for tens of servers, too slow for thousands.

import hashlib


def score(server: str, key: str) -> int:
    return int.from_bytes(hashlib.md5(f"{server}|{key}".encode()).digest()[:8], "big")


def rendezvous_owner(key: str, servers: list[str]) -> str:
    """Highest random weight: every server scores the key and the top score wins."""
    return max(servers, key=lambda s: score(s, key))


pool = ["cache-a", "cache-b", "cache-c", "cache-d"]
print(rendezvous_owner("user:42", pool))
pool.remove("cache-b")                      # only the keys that scored highest on cache-b move
print(rendezvous_owner("user:42", pool))

A tiny function from Google engineers (Lamping and Veach, 2014): hash the key to an integer, and it returns a bucket number from 0 to N − 1 using no memory and about log N steps. It spreads keys very evenly. The catch: buckets must be numbered consecutively and can only be added or removed at the end, and there are no weights. A good fit for numbered shards that are replicated for failure.

def jump_hash(key: int, buckets: int) -> int:
    """Lamping and Veach (2014). Buckets are numbered 0 .. buckets-1. No ring, no table, about log(buckets) steps."""
    b, j = -1, 0
    while j < buckets:
        b = j
        key = (key * 2862933555777941757 + 1) & 0xFFFFFFFFFFFFFFFF
        j = int((b + 1) * ((1 << 31) / ((key >> 33) + 1)))
    return b


# growing from 10 to 11 shards moves only the keys that now land in shard 10
moved = sum(jump_hash(k, 10) != jump_hash(k, 11) for k in range(100_000))
print(moved / 100_000)                      # about 1/11

Hash the key to one of a fixed number of slots (Redis Cluster uses 16,384) and keep a table saying which node owns each slot. Adding a node means moving whole slots, with their data, one at a time. The key-to-slot step never changes; only the slot-to-node table does. You gain explicit control (move this slot now) and simple rebalancing tools. You give up automatic placement, and every client needs the current table. Kafka's fixed partition count is the same idea.

import zlib

SLOTS = 16384                               # Redis Cluster uses CRC16 of the key; crc32 stands in here

# the small table that gets rebalanced: slot -> node
slot_to_node = {slot: "node-a" if slot < 8192 else "node-b" for slot in range(SLOTS)}


def node_for(key: str) -> str:
    return slot_to_node[zlib.crc32(key.encode()) % SLOTS]      # key -> slot never changes


# adding node-c: reassign some slots, copy only those slots' keys, publish the new table
for slot in range(0, SLOTS, 3):
    slot_to_node[slot] = "node-c"

Step 4 · Wrap up

Follow-up questions interviewers ask (click to reveal)

How do you handle servers of different sizes?

Weight the virtual nodes. A server with twice the memory and capacity gets twice as many points, so it owns about twice the share of the ring. The code above takes a weight argument for exactly this.

How do replicas work on the ring?

Start at the key and walk clockwise, collecting the first N different physical servers. Skip points of a server you already have, and in production skip servers in the same rack or zone. 6 · Design a key-value store builds quorum reads and writes on top of this list.

How do all the routers agree on the ring?

Either a coordination service that holds a versioned ring and pushes changes, or gossip between servers that converges on the same membership. During the gap a request may reach the previous owner. For a cache that is one extra miss; for a store the hand-over protocol (forwarding, versions) covers it.

What about a hot key?

Placement cannot help: one key is one point. Replicate the key under several names and read one at random, put an in-process cache in front, or use bounded-load consistent hashing, which caps each server at a small multiple of the average load and spills extra requests to the next server on the ring (Mirrokni, Thorup and Zadimoghaddam).

Why not keep a table from key to server?

It needs memory for every key, a directory service every client must reach and keep in sync, and it becomes a hot spot. The ring needs only the sorted server positions and recomputes the answer anywhere. Fixed slots are the middle ground: a small table of slots rather than keys.

Which hash function?

One that mixes well and gives the same output on every machine and in every language: MD5 or SHA-1 cut to 64 bits is fine for placement (this is not a security use), MurmurHash or xxHash is faster. Never use a per-process salted hash such as Python's hash(). Changing the function later reshuffles everything, so version it.

Failure modes and what to do about them (click to reveal)

Routers disagree about the ring

Two clients with different rings send one key to two servers: reads miss, writes land in the wrong place. Version the ring, push changes from one source of truth, and make stores tolerate a request that reaches a previous owner.

A crash overloads the neighbour

With one point per server the successor inherits everything and may fail next. Virtual nodes spread the load over every survivor. Also keep headroom: a pool of N servers needs to survive N − 1 at peak.

A server flaps

A machine that joins and leaves every minute makes the ring churn and moves data each time. Use failure detection with some patience, and in a store keep a down node's place for a while instead of removing it at the first missed heartbeat.

Two points land on the same position

With 64-bit positions this is astronomically rare, but code must still have a deterministic tie-break, or one server silently overwrites another's point as in a naive dictionary.

The database melts after a change

Even a ring moves 1/N of the keys, and those all miss at once. Add new servers one at a time, warm them (fill from the previous owner or from traffic) before routing to them, and protect the database with request coalescing (Caching).

The 60-second summary

I would route with a hash ring. Servers and keys are hashed onto the same 64-bit circle, and a key belongs to the first server clockwise from it, found by a binary search over the sorted server positions. When a server joins or leaves, only the keys on the arc next to it move, about 1/N of them, where hash % N would move almost all and send a miss storm to the database. A plain ring is uneven and dumps a dead server's load on one neighbour, so each server gets 100 to 200 virtual nodes, which brings the load spread under about 10% and spreads a failure over every survivor. Bigger machines get proportionally more points. The router needs only the sorted point list, kept in sync by a membership service or gossip. For a store, replicas are the next N distinct servers clockwise, and a joining server streams its ranges before it takes traffic. A single hot key is not fixed by any of this, so I would replicate it or cache it in front.
