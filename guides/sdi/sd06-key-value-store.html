Design a key-value store

A key-value store is the simplest database interface and one of the hardest to run at scale. This chapter walks the interview for a Dynamo-style store: scoping and sizing, the CAP choice, a hash ring with replicas, quorum reads and writes, vector clocks for conflicts, gossip, hinted handoff and Merkle trees for failures, and the commit-log, memtable and SSTable machinery inside each node.

After this chapter you can
  • Scope a key-value store with the interviewer and size its cluster from storage and throughput numbers
  • Explain what a network partition forces the store to choose, and defend an AP design with tunable consistency
  • Place keys and replicas on a hash ring and choose N, W and R with the W + R > N overlap rule
  • Detect conflicting writes with vector clocks and say who resolves them
  • Describe how the cluster notices failures (gossip), keeps serving (hinted handoff) and repairs itself (Merkle trees)
  • Walk through a node's write path and read path: commit log, memtable, SSTables and Bloom filters

Step 1 · Understand the problem and establish scope

A key-value store keeps items as key → value pairs. The key is unique and is the only way in; the store treats the value as opaque bytes. Picture a Python dict that lives on many machines. Cassandra, Riak, DynamoDB and Redis all belong to this broad family, and this chapter builds a Dynamo-style one: always writable, grown by adding nodes, and tunable between fast and fresh.

What to agree with the interviewer before drawing anything:

  • Operations. put(key, value) and get(key) on a single key. No joins, no multi-key transactions, no secondary indexes.
  • Item size. Small: a typical value is about 4 KB (a cart, a session, a profile fragment) and none exceeds 100 KB. Larger blobs go to object storage and the store keeps a pointer (see Object storage (S3) & CDNs).
  • Scale. Billions of items and tens of terabytes: more than any one machine can hold or serve.
  • Availability. Reads and writes keep working while nodes, racks or a whole data centre are down. A customer adding to a cart during a network problem should not see an error page.
  • Consistency is a dial. Each request chooses how fresh its read must be and pays in latency for more.
  • Latency. p99 under 20 ms inside a region.
  • Elasticity. The cluster grows and shrinks by adding or removing nodes, with no downtime and no manual re-sharding. Every node does the same job, so no node is a single point of failure.

Questions to ask before you design

A strong candidate asks, before drawing:

  1. How big are keys and values, and do we ever scan ranges? (picks the storage engine and hash versus range partitioning)
  2. What is the read to write ratio, and what is the peak load? (sizes the cluster)
  3. If it must be one, is a failed request or a stale answer worse? (the CAP choice)
  4. One data centre or several, and must we survive losing one? (replica placement)
  5. Can two clients write the same key at once, and who merges? (conflict handling)
  6. Any transactions, TTLs or secondary indexes? (keeps the scope small)

The four-step shape of the interview is in 3 · A framework for system design interviews.

How many nodes? Storage and throughput

Both limits matter and the larger one sets the cluster size. A write reaches all N replicas and a quorum read asks R of them, so the cluster does more work than the clients request. With these defaults throughput, not disk, decides the size: change the inputs and watch which limit wins.

Step 2 · Propose a high-level design

Start with the simplest thing that works. On one machine a key-value store is a hash table:

A key-value store on one machine

class SingleNodeStore:
    """The whole API on one machine. Everything else in this chapter is what you add when this is not enough."""

    def __init__(self) -> None:
        self._data: dict[str, bytes] = {}

    def put(self, key: str, value: bytes) -> None:
        self._data[key] = value

    def get(self, key: str) -> bytes | None:
        return self._data.get(key)

Everything else in this chapter is what you add when that machine is not enough:

  • Too much data for memory. Compress values, keep the hot keys in memory and spill the rest to disk. That postpones the problem without removing it: 24 TB of values (the estimate above) at hundreds of thousands of requests per second is beyond any single server.
  • Too much traffic. One machine has one network card and a finite number of disk operations per second.
  • One machine is one failure. When it crashes the data is unreachable, and when its disk dies the data is gone.

So we partition the keys across many nodes and replicate each key onto several. Once copies live on machines joined by a network that can fail, every read and write raises three questions, and the rest of the chapter answers them: which copies must answer, what if they disagree, and what if some are unreachable?

Step 3 · CAP: what the store does during a partition

Copies on different machines mean the machines must talk, and networks fail. The CAP theorem says that when the network splits a cluster into groups that cannot reach each other (a partition), a store can keep only one of two promises:

  • Consistency: every read returns the latest write, as if there were a single copy.
  • Availability: every request to a live node gets an answer.

Partitions are not optional (a failed switch or an overloaded link produces one sooner or later), so the real question is what the store does during one. The theory has its own chapter, Consistency models & the CAP theorem. Here is what it decides for this design.

flowchart TD
  Sync[Replicas A, B and C agree] --> Cut{{Partition: C is cut off}}
  Cut --> CP[CP choice: C refuses<br/>what it cannot confirm]
  Cut --> AP[AP choice: C keeps<br/>answering and accepting]
  CP --> CPout[No stale reads<br/>errors for clients of C]
  AP --> APout[Every request answered<br/>replicas drift apart]
  APout --> Merge[After the heal: detect<br/>and merge versions]
  CPout --> Catch[After the heal: C<br/>copies from the majority]
The same partition, two policies. Follow each branch to the bill that comes after the heal.

The same put, two policies

CP: refuse when the majority is out of reach

Correct and strict; the minority side is down for writes until the partition heals.

def put(self, key, value):
    if len(self.reachable_replicas(key)) < self.majority:
        raise Unavailable("cannot reach a majority, refusing the write")
    self.replicate_and_commit(key, value)      # acknowledged only when a majority has it

AP: accept now, reconcile later

Always answers; the price is conflicting versions that something must detect and merge.

def put(self, key, value, context):
    version = self.clock.next_version(context)   # a vector clock, not a lock
    self.store.write(key, value, version)        # a local write is always possible
    self.hints.add_for_missing_replicas(key, value, version)
    return "OK"                                  # conflicts are detected and merged later

Decide per kind of data, from the cost of being wrong. One cluster can serve both if consistency is tunable per request.

How to state it

Say the choice first and defend it with the product, not the theorem: 'This store holds carts and sessions, where an error page costs more than a briefly stale item, so I choose availability during partitions (AP) and make consistency tunable per request. For the few values that must never be wrong I raise W and R, or keep them in a CP store.' Then say what you give up: conflicting writes that must be detected and merged.

Step 3 · Partitioning and replication on the ring

Partitioning: split the keys

Billions of items cannot sit on one node, so each node holds a slice. Modulo hashing (hash(key) % node_count) is the obvious scheme and a poor one: change the node count and almost every key maps somewhere new, so every scale-out moves almost all the data (the experiment is in 5 · Design consistent hashing).

Consistent hashing avoids that. Nodes and keys are hashed onto the same circle, and a key belongs to the first node clockwise from its position. Adding or removing a node moves only the keys in the arc beside it. Giving each server many tokens (virtual nodes) evens out the load, and a larger machine can simply take more tokens. For a key-value store that buys even spread, automatic growth (a new node takes arcs from its neighbours) and an easy way to express unequal hardware.

Replication: put each key on N nodes

One copy is not enough, because the node holding it will fail. The coordinator stores each key on N nodes, three by default. The replica set is found by walking clockwise from the key's position and taking the first N tokens that belong to different servers. Step through a walk that meets a duplicate on the way, then one that wraps around the end of the ring.

Finding the replicas of one key

Eight tokens, four servers. The first input skips a token whose server already holds a copy; the second wraps past the end of the ring.

The replica set is a pure function of the key and the ring layout, so every coordinator computes the same answer with no lookup. Real placement rules add one more filter: skip servers in a rack, zone or data centre that already holds a copy, so a single failure domain cannot take every replica (see the data-centre outage below).

Step 3 · Quorums: choosing N, W and R

▶ Video lesson: Quorums and vector clocks: how copies agree 5:29 · 9 scenes · narrated, pause anytime and explore

Replication raises a question: with N copies, how many must a client wait for? Three numbers answer it.

  • N: how many replicas each key has.
  • W: the write quorum. The coordinator sends a write to all N replicas but reports success after W acknowledgements.
  • R: the read quorum. The coordinator asks the replicas and answers after R replies, returning the highest version it saw.

Waiting for fewer replicas is faster, because the operation finishes with the W-th or R-th fastest reply instead of the slowest, and it survives more failures: N − W dead replicas for writes, N − R for reads. What it loses is a guarantee about what a read will see.

The rule that ties the three together: if W + R > N, every read quorum shares at least one replica with every write quorum. A write touched W replicas and a read asks R, so together they count W + R places among only N replicas, and some replica must be counted twice. That replica holds the latest acknowledged write, and its higher version wins the read.

Quorum calculator

Try N = 3 with W = 1, R = 1: the overlap drops to zero and both failure counts rise to two. Fast, available, and possibly stale.

A quorum write and read, with latencies

Flag flag:dark-mode flips from off to on. Each replica has a fixed reply time. The read is deliberately given the unluckiest replicas it could get, to test the overlap rule.

Choosing W and R is a decision about the cost of a stale read and the shape of the traffic.

W + R > N is not linearizability

W + R > N makes a read overlap the latest acknowledged write. It does not make the store linearizable. Two concurrent writes can still land on different replicas, a write that returned an error may be partly applied and show up later, and a sloppy quorum (below) breaks the overlap while a replica is away. Dynamo-style stores are eventually consistent by design. If an interviewer wants linearizable single-key operations, say you would add conditional writes backed by a consensus protocol, or use a CP store, and point to Consistency models & the CAP theorem.

The vocabulary an interviewer expects: strong consistency (a read always returns the latest write; typically costs availability), eventual consistency (replicas converge if writes stop; reads may be stale meanwhile) and the practical middle ground, where a quorum read plus read repair (the coordinator writes the newest version back to any replica it saw lagging) keeps most data fresh most of the time. Dynamo and Cassandra live in that middle ground.

Step 3 · Vector clocks: detecting conflicting writes

When replicas accept writes independently (W < N, partitions, sloppy quorums), two clients can update one key without seeing each other's change. The store has to notice, and a timestamp cannot tell it: a timestamp says which write has the bigger number, not whether one write knew about the other.

A vector clock is a small map from node name to counter that travels with every version of a value.

  • Write. The coordinator starts from the clock in the context the client passed in, adds one to its own counter (creating it at 1 if absent) and stores the new version with that clock.
  • Compare clocks A and B. If every counter in A is at most the matching counter in B (a missing counter counts as 0), A is an ancestor of B and B may replace it. If neither is at most the other, the writes are concurrent: a conflict.
  • Read. Return every version that nothing else descends from (the siblings), with the larger counter per node as the context.
  • Resolve. The client merges the siblings and writes the result back with that context, producing a version that descends from all of them.

Vector clocks in Python

def compare(a: dict[str, int], b: dict[str, int]) -> str:
    """'before' if a is an ancestor of b, 'after' if a descends from b, 'equal', or 'concurrent'."""
    nodes = a.keys() | b.keys()
    a_le_b = all(a.get(n, 0) <= b.get(n, 0) for n in nodes)      # a missing counter counts as 0
    b_le_a = all(b.get(n, 0) <= a.get(n, 0) for n in nodes)
    if a_le_b and b_le_a:
        return "equal"
    if a_le_b:
        return "before"
    if b_le_a:
        return "after"
    return "concurrent"


def merge(a: dict[str, int], b: dict[str, int]) -> dict[str, int]:
    """The context handed to a client that read two siblings: the larger counter for every node."""
    return {n: max(a.get(n, 0), b.get(n, 0)) for n in sorted(a.keys() | b.keys())}


def tick(clock: dict[str, int], node: str) -> dict[str, int]:
    """What a coordinator does when it stores a write that is based on `clock`."""
    return {**clock, node: clock.get(node, 0) + 1}


v2 = tick({"N1": 1}, "N2")                 # Ben's write through Node 2   -> {'N1': 1, 'N2': 1}
v3 = tick({"N1": 1}, "N1")                 # Asha's write through Node 1  -> {'N1': 2}
print(compare(v2, v3))                     # concurrent: neither knew about the other
v4 = tick(merge(v2, v3), "N3")             # Asha's merged write through Node 3
print(v4, compare(v4, v2), compare(v4, v3))   # {'N1': 2, 'N2': 1, 'N3': 1} after after
compare is the whole conflict detector. Run it on the clocks from the simulation: v2 and v3 are concurrent, v4 descends from both.

Three ways to settle siblings

Keep the version with the latest timestamp and discard the rest. It needs no client logic and always converges, which is why Cassandra does it. The cost is silent data loss when writes are concurrent, and it trusts wall clocks that can be seconds apart. Fine for data where overwriting is the point: a last-seen time, a cache entry, a value with one writer.

The store returns all siblings and the application decides, because only it knows what a merge means for a cart or a document. Nothing is lost; the price is code, and the care needed for removals.

def resolve(siblings: list[set[str]]) -> set[str]:
    """Packing list: keep every item that anyone added."""
    return set().union(*siblings)


print(resolve([{"tent", "stove"}, {"tent", "map"}]))    # {'tent', 'stove', 'map'} (set order may vary)

# Caveat: union also brings back an item that one writer deliberately removed. Real carts store removals as
# tombstones ("removed: stove, with its version") so the merge can tell 'never added' from 'added then removed'.

A CRDT (conflict-free replicated data type) is built so that merging two copies, in any order, any number of times, gives the same result: grow-only sets, counters, add-wins sets. Riak ships some as built-in types. You give up arbitrary values for a menu of structures whose merge is already defined.

Clocks can grow

A clock gains one entry per node that ever coordinated a write of the key, so it can grow. Dynamo bounds it by storing a timestamp beside each entry and dropping the oldest entry once the clock passes a threshold. That can blur ancestry, so the store may see a conflict that is not one, and the Dynamo authors report it has not been a problem in practice. Say that you would cap the clock and accept the occasional extra sibling.

Step 3 · Handling failures: gossip, hints and Merkle trees

▶ Video lesson: Failure handling: gossip, hints and Merkle trees 4:54 · 8 scenes · narrated, pause anytime and explore

Detecting failures with gossip

With hundreds of nodes something is always failing, and a coordinator must know before it picks replicas. One node's opinion is not enough: a missing reply may be a lost packet, or a problem on the observer's own side.

The brute-force answer is all-to-all heartbeats, every node pinging every other node each second. That is N × (N − 1) messages per round: about 250,000 per second at 500 nodes. Gossip is the cheaper answer. Each node keeps a table of heartbeat counters, bumps its own counter every round and sends the table to a few random peers, who merge it into theirs. Traffic is only N × fanout (1,500 messages per round at fanout 3), and news still reaches every node in a number of rounds that grows like log N, because the set of nodes that know roughly doubles each round at first.

Gossip heartbeats and a node marked down

Node 4 crashes after round 3. The grid shows every node's table; red cells are entries flagged as down. Watch the last heartbeat of Node 4 travel from table to table, and notice that each node reaches its verdict alone.

Two design decisions hide in that run. First, the timeout trades speed against false alarms: a short one catches crashes fast and also flags a node that merely paused for garbage collection, a long one is calm and slow. Production detectors such as Cassandra's phi-accrual detector emit a suspicion level that adapts to observed delays, instead of a fixed yes or no. Second, each verdict is local: two nodes can disagree for a few rounds, as the run shows, and the design has to tolerate that. A coordinator that still picks a replica another node already considers dead simply gets a timeout and moves on. What happens next is the subject of the two sections below: short outages are covered by hints, long ones by repair.

A replica is down for a while: sloppy quorum and hinted handoff

A strict quorum counts only the key's N home replicas, so if too many are down, writes fail although the cluster is full of healthy nodes. A sloppy quorum relaxes that: the coordinator takes the first N healthy nodes it meets walking the ring and counts their acknowledgements. A stand-in that receives a write meant for a down replica keeps it in a separate hint store, labelled with the intended owner. When gossip reports the owner back, the stand-in sends it the hinted writes and deletes them: hinted handoff.

Strict quorum versus sloppy quorum

Strict quorum

Only the key's N home replicas count. With W = 2 and two of three homes down, writes fail. The overlap rule holds, so reads are as fresh as W + R > N promises. Choose it when a refused write is better than a surprising read.

Sloppy quorum with hinted handoff

The first N healthy nodes on the ring count, and stand-ins keep hints for the absent replicas. Writes succeed with homes down. Reads that follow may miss a write that only stand-ins hold. Choose it when the store must stay writable (carts, sessions).

What sloppiness costs

A write acknowledged by A and the stand-in D can be missed by a read that asks B and C, because D is not a home replica and nobody asks it. So a sloppy quorum trades the overlap guarantee for availability until the hint is handed off. Hints are also kept for a limited window, typically hours, and a stand-in can crash before it hands them over. That is why a second mechanism exists.

A replica is gone for good: anti-entropy with Merkle trees

When a replica is replaced, has been away longer than hints are kept, or silently lost some data, the replicas must be compared and the differences copied. This repair is called anti-entropy. Comparing every key of a multi-terabyte replica is out of the question; a Merkle tree (hash tree) makes the comparison cost depend on how much differs, not on how much exists.

  1. Split the replica's key range into a fixed number of buckets and hash each bucket's contents into a leaf.
  2. Hash each pair of children into their parent, up to a single root that summarises everything.
  3. To compare, swap roots. Equal roots mean identical data: stop. Otherwise swap the two children's hashes and descend only into the children that differ.
  4. At the leaves, exchange the items of the few differing buckets and keep the newer version of each key (the vector clock decides).

Two replicas find the bucket that differs

Eight buckets, two replicas. Hashes are shortened to four hex digits. Red nodes differ, green nodes match, and grey nodes were skipped without being read.

Why the tree pays off at scale

The same walk on production-sized replicas. Each level costs two hash comparisons, so finding one differing bucket takes about twice the tree depth, however many keys there are.

A Merkle tree in Python

import hashlib


def digest(text: str) -> str:
    return hashlib.md5(text.encode()).hexdigest()[:8]


def build_tree(buckets: list[dict[str, str]]) -> list[list[str]]:
    """levels[0] holds the leaf hashes, levels[-1] holds [root]. The bucket count must be a power of two."""
    level = [digest(";".join(f"{k}={v}" for k, v in sorted(b.items()))) for b in buckets]
    levels = [level]
    while len(level) > 1:
        level = [digest(level[i] + level[i + 1]) for i in range(0, len(level), 2)]
        levels.append(level)
    return levels


def differing_buckets(a: list[list[str]], b: list[list[str]]) -> list[int]:
    """Walk down from the root and descend only where the two trees' hashes differ."""
    if a[-1] == b[-1]:
        return []                                    # identical roots: nothing to repair
    frontier = [0]                                   # node indexes at the current level, starting at the root
    for depth in range(len(a) - 2, -1, -1):           # go one level down per iteration
        frontier = [child for i in frontier for child in (2 * i, 2 * i + 1) if a[depth][child] != b[depth][child]]
    return frontier


replica_a = [{"k03": "v2"}, {"k12": "v4", "k18": "v1"}, {"k21": "v3"}, {"k36": "v5"}]
replica_b = [{"k03": "v2"}, {"k12": "v4"}, {"k21": "v3"}, {"k36": "v4"}]
print(differing_buckets(build_tree(replica_a), build_tree(replica_b)))     # [1, 3]
differing_buckets visits two nodes per level instead of every leaf. Real systems keep one tree per key range, rebuild it in the background, and use far more buckets than keys can be compared in memory.

A whole data centre is gone

Step 3 · Inside a node: the write path and the read path

▶ Video lesson: Inside a node: the write path and the read path 5:13 · 8 scenes · narrated, pause anytime and explore

Everything so far happens between nodes. Inside one node the question is how to store its share of the keys so that writes are cheap and reads are not painful. A Dynamo-style store can use any local engine; disks are fast at sequential writes and slow at random ones, so Cassandra and the Bigtable, LevelDB and RocksDB family use a log-structured merge tree (LSM) engine with a handful of parts:

PartLives inJob
Commit logdisk, append-onlyevery write is appended here first; replayed after a crash
Memtablememory, sorted by keyabsorbs recent writes and answers reads for them
SSTabledisk, immutable, sorteda memtable flushed in key order; never edited, only replaced
Bloom filtermemory, one per SSTabletells a read which SSTables cannot hold the key
Compactionbackground, diskmerges SSTables, keeps the newest version of each key, drops deleted data
A write touches the first two parts; a read consults the memtable, then filters, then SSTables.

The write path

A write is two cheap steps and an acknowledgement: append to the commit log, insert into the memtable. When the memtable reaches a size threshold it is flushed to disk as a new SSTable, and the log segment it covered is discarded.

flowchart TD
  Put[put key and value] --> Log[Append to the commit log<br/>sequential disk write]
  Log --> Mem[Insert into the memtable<br/>sorted, in memory]
  Mem --> Ack[Acknowledge the write]
  Mem --> Full{Memtable full?}
  Full -- no --> Wait[Keep absorbing writes]
  Full -- yes --> Flush[Flush to a new SSTable<br/>sorted, immutable]
  Flush --> Recycle[Recycle the log segment<br/>start an empty memtable]
The client's answer comes from the memtable insert; the flush happens in the background, off the request path.

Now watch it happen, including a power cut at the end.

From put to SSTable, and back from a crash

The memtable flushes at four keys so you can watch it. The four views are the node's boxes, the commit log, the memtable and the SSTables.

The read path

A read can find the key in the memtable (recent writes), in any SSTable, or nowhere, and the same key can appear in several SSTables, where the newest wins. Checking every SSTable would cost one disk read each. A Bloom filter removes most of that cost: a bit array with a few hash functions per key. Adding a key sets its bits; asking about a key checks them. One 0 bit proves the key is absent. All 1s only mean 'maybe', because other keys may have set the same bits.

(Stopping at the first hit is right when a write replaces the whole value. A store that updates individual columns must merge the pieces it finds across files.)

flowchart TD
  Get[get key] --> InMem{In the memtable?}
  InMem -- yes --> Return[Return the value]
  InMem -- no --> Next[Take the next SSTable<br/>newest first]
  Next --> Filter{Bloom filter says maybe?}
  Filter -- no --> More{More SSTables?}
  Filter -- yes --> Read[Read the SSTable from disk]
  Read --> Found{Key found?}
  Found -- yes --> Return
  Found -- no --> More
  More -- yes --> Next
  More -- no --> Missing[Return not found]
Disk is touched only on the 'maybe' branch. Everything above it happens in memory.

Building and querying a Bloom filter

One SSTable's filter, 20 bits and 3 hash functions, so small that false positives are easy to see.

Bloom filter sizing

Filters are sized by bits per key. The false-positive rate is about (1 − e^(−k/b))^k for k hash functions and b bits per key; the best k is about 0.69 × b. At 10 bits per key, 1% of lookups for absent keys cost a wasted read.

get(key): memtable, filters, SSTables

The node from the write path: a memtable and two SSTables, each SSTable with its filter. Pick a key and follow the lookup newest to oldest.

A toy LSM node in Python

import bisect
import hashlib


class BloomFilter:
    def __init__(self, bits: int = 1024, hashes: int = 3) -> None:
        self.bits, self.hashes, self.array = bits, hashes, bytearray(bits)

    def _positions(self, key: str) -> list[int]:
        digest = hashlib.md5(key.encode()).digest()                      # spread, not security
        h1, h2 = int.from_bytes(digest[:8], "big"), int.from_bytes(digest[8:], "big") | 1
        return [(h1 + i * h2) % self.bits for i in range(self.hashes)]   # k positions from two hashes

    def add(self, key: str) -> None:
        for p in self._positions(key):
            self.array[p] = 1

    def might_contain(self, key: str) -> bool:
        return all(self.array[p] for p in self._positions(key))         # one 0 bit proves absence


class SSTable:
    """Immutable and sorted, with a Bloom filter kept in memory in front of it."""

    def __init__(self, items: dict[str, bytes]) -> None:
        self.keys = sorted(items)
        self.values = [items[k] for k in self.keys]
        self.bloom = BloomFilter(bits=max(64, 10 * len(self.keys)))      # about 10 bits per key
        for k in self.keys:
            self.bloom.add(k)

    def get(self, key: str) -> bytes | None:                              # stands in for an index lookup plus a disk read
        i = bisect.bisect_left(self.keys, key)
        return self.values[i] if i < len(self.keys) and self.keys[i] == key else None


class LsmNode:
    def __init__(self, flush_at: int = 4) -> None:
        self.commit_log: list[tuple[str, bytes]] = []                      # pretend this is an append-only file
        self.memtable: dict[str, bytes] = {}
        self.sstables: list[SSTable] = []                                  # newest last
        self.flush_at = flush_at

    def put(self, key: str, value: bytes) -> None:
        self.commit_log.append((key, value))                               # 1. durable first
        self.memtable[key] = value                                         # 2. then the in-memory map
        if len(self.memtable) >= self.flush_at:
            self.flush()

    def flush(self) -> None:
        self.sstables.append(SSTable(self.memtable))                       # 3. one sequential write of sorted data
        self.memtable, self.commit_log = {}, []                            #    the log segment is no longer needed

    def get(self, key: str) -> bytes | None:
        if key in self.memtable:                                           # newest data first
            return self.memtable[key]
        for table in reversed(self.sstables):                              # then newest SSTable first
            if table.bloom.might_contain(key):                             # skip tables that cannot hold the key
                value = table.get(key)
                if value is not None:
                    return value
        return None

    def recover(self) -> None:
        self.memtable = dict(self.commit_log)                              # replay the log after a crash


node = LsmNode(flush_at=4)
for k, v in [("dan", b"1"), ("ana", b"2"), ("eve", b"3"), ("ben", b"4"), ("ana", b"5"), ("hal", b"9")]:
    node.put(k, v)
print(node.get("ana"), node.get("ben"), node.get("zed"))                   # b'5' b'4' None
node.memtable = {}                                                         # simulate a crash: RAM is lost
node.recover()
print(node.get("hal"))                                                     # b'9'
About seventy lines hold the whole write and read path: log, memtable, flush, a Bloom filter per SSTable, newest-first lookup and crash recovery.

Compaction, deletes and the commit-log dial

Compaction

Over time a node piles up SSTables, and old versions of the same key sit in several of them. Background compaction merges a few SSTables into one, keeping the newest version of each key: a k-way merge of sorted files, the same idea as Merge k Sorted Lists. It buys faster reads and reclaimed space with extra background I/O. Typical strategies merge files of similar size, or keep levels with non-overlapping key ranges.

Deletes and tombstones

Immutable files cannot have a key erased, so a delete is written like any other write: a marker called a tombstone, which reads treat as 'not found'. The tombstone must outlive repair on every replica. If it were dropped early, a replica that missed the delete could offer the old value back and repair would resurrect it. Compaction removes tombstones only after a grace period of days.

How durable is an acknowledged write?

Appending to the commit log is only durable once the operating system has flushed it to the device. That is a dial: flush on every write (safest, slowest), flush in small batches, or flush periodically and let the other replicas cover the last few moments after a power cut.

Why an LSM engine and not a B-tree?

LSM tree (this chapter)

Writes are sequential appends and bulk flushes, so write throughput is high. A read may consult several files, which filters and compaction keep manageable. Background compaction costs I/O, and space usage swings between compactions. A good fit for write-heavy, key-lookup workloads.

B-tree (update in place)

A read follows one root-to-leaf path, so read latency is steady, and range scans are cheap. Every write updates pages in place, which means random I/O plus a write-ahead log, and pages split as they fill. A good fit for read-heavy workloads and for stores that need ordered scans.

Follow-up questions interviewers ask next

How do you add a node?

The new node takes its tokens, announces itself through gossip and streams the key ranges it now owns from their current replicas. It starts serving them once caught up, and the old owners drop what they no longer own. Only the neighbouring ranges move, which is the point of consistent hashing.

How do you handle a hot key?

A key's traffic lands on its N replicas however large the cluster is. Put a cache in front, split the value over several keys (cart:mira#0 to #7) and merge on read, or give that key a higher N so more replicas share the reads, at the cost of a wider write fan-out. Hot-key tactics are in Caching.

Why not run Raft or Paxos per partition?

That gives a CP store: a leader per key range orders the writes and a majority acknowledges them, so single-key operations are linearizable and a minority partition stops serving. etcd and Spanner work this way. It is the right answer when the interviewer says consistency first; the Dynamo-style design is the right answer when availability and latency come first.

How do you support range scans or secondary indexes?

Hash partitioning scatters adjacent keys, so a range scan would have to ask every node. Either partition by key range (hot spots and rebalancing become your problem) or keep the index as a separate table keyed by the indexed value, updated alongside the data and eventually consistent. See Databases: SQL vs NoSQL and Scaling databases: replication, sharding, partitioning.

What would you monitor?

Replication lag, hint backlog and age, repair progress, p99 latency per operation and per consistency level, compaction backlog, memtable and disk pressure, and gossip flaps (nodes marked down and up again repeatedly, usually a sign of an overloaded node or a timeout set too short).

With more time: authentication and per-tenant quotas, encryption at rest and in transit, snapshots and backups, a per-key TTL, conditional writes for the few operations that need compare-and-set, and tracing a request across coordinator and replicas.

The 60-second summary

I would build a Dynamo-style store. Keys are partitioned over a consistent-hashing ring with virtual nodes, and each key is replicated onto the next three distinct servers, spread across data centres. Any node can coordinate a request: it sends the operation to the replicas and answers after W acknowledgements or R replies, so N = 3, W = 2, R = 2 gives overlapping quorums, and I can lower W or R where a stale read is harmless. The store is AP, so concurrent writes can happen; vector clocks detect them and the client merges the siblings. Gossip tells every node who is alive. While a replica is down a neighbour holds its writes as hints, and Merkle trees repair replicas that diverged for good. Each node stores data LSM-style: a commit log, a memtable, immutable SSTables, and Bloom filters so reads skip files that cannot hold the key.
