Design a URL shortener

Walk the interview for a URL shortener: scope it and size it, draw the API and the two flows, then spend the deep dive on the question everyone is asked, how a long URL becomes a short code. You will run both answers side by side (hashing with collision handling, and base 62 of a unique number), choose between 301 and 302 with analytics in mind, and keep redirects fast with a cache sized from your own estimate.

After this chapter you can
  • Scope the problem with the interviewer and estimate writes, reads, storage, cache size and code length from a handful of assumptions
  • Draw the architecture in whiteboard order and trace the redirect and shortening flows as sequence diagrams
  • Choose between 301 and 302 and defend the choice with caching and analytics
  • Spell a unique number in base 62 by hand, and explain why 7 characters are enough for ten years
  • Run the hash-and-resolve-collisions loop, say what a Bloom filter saves, and state the signal that favours each method
  • Size an LRU cache for the hot links and say what happens on a cold start

Step 1 · Understand the problem and establish scope

A URL shortener turns a long link such as https://recipes.example.net/pasta/carbonara-classic-roman?servings=4 into a short one such as https://go.example/J8ZJNn, and sends anyone who opens the short link to the long one. The product is tiny. The interview is about volume, so spend the first minutes turning the one-line prompt into numbers you can design against.

These are the answers we assume the interviewer gave:

  • Two operations. Shorten a long URL into a short URL, and redirect a short URL to the long one.
  • Volume. 30 million new URLs a day. Each one is followed about 20 times on average, so redirects run at about 20 times the create rate.
  • Lifetime. A link works for 10 years. Editing and deleting links are out of scope (expiry comes up as a follow-up).
  • Alphabet. Digits and letters only (0-9, a-z, A-Z, 62 symbols), and the code should be as short as the volume allows.
  • Quality. A redirect should feel instant (under about 50 ms at the service, p99), and no single failure should break links that already exist.
  • Out of scope. User accounts, custom aliases, QR codes.

Questions a strong candidate asks

Ask before you draw. Five questions turn an open prompt into a design:

  1. How many new URLs a day, and how often is each one followed? Every estimate depends on it.
  2. How long must a link live, and can it be edited or deleted? This sets storage, and whether a redirect may be cached.
  3. Must the same long URL always get the same short URL? This decides how you generate codes.
  4. Is click analytics in scope, and how fresh must it be? This decides 301 versus 302.
  5. Which characters may a code use, and how long may it be? This decides the encoding.

Say your assumptions out loud, write them down and move on. Nobody expects the "right" numbers, only that you have some.

Traffic, storage, cache and code length

Every number is an assumption you can change. Try 100 million new URLs a day, or 100 redirects per URL, and watch which outputs move and which stay put. The cache lines use the 80/20 rule: a fifth of the day's distinct links draws most of the clicks.

Read the outputs as decisions:

  • About 350 creates per second is easy for one database primary. The write path is a correctness problem (never hand out a code twice), not a throughput problem.
  • About 7,000 redirects per second, 28,000 at peak, is the number that shapes the design. Reads outnumber writes 20 to 1 and nearly all of them are lookups by one key, so a cache pays for itself. A redirect response is a few hundred bytes, so even the peak is only about 11 MB per second: bandwidth is not the constraint.
  • About 20 TB after ten years (2 TB a year) outgrows one comfortable node, so plan to shard on the code.
  • 7 characters. 62⁶ is 56.8 billion, too few for 110 billion URLs. 62⁷ is 3.5 trillion, so seven characters carry ten years of growth and use about 3% of the space.
  • About 7.5 GB of cache holds the hot links. It fits in a single cache node's memory and leaves roughly 5,600 reads per second at peak for the database, which a few replicas can serve.

Run requests through the boxes

First a create: the request picks up a number from the ID generator, spells it in base 62 and writes one row. Then a link is opened twice: the first click misses the cache and reads the database, the second is answered from memory.

The whole API is two endpoints. Creating is a POST that returns the new short URL. Redirecting is a GET on the short URL itself, so the link stays short; it answers with a status and a Location header, not a page. Which status is a real decision, covered next.

Step 3 · Deep dive: 301 or 302?

One short link, opened twice by the same browser

sequenceDiagram

  Note over B,O: Second visit after a 302
  B->>S: GET /J8ZJNn again
  S-->>B: 302 with Location
  B->>O: GET the long URL
The two statuses differ in one respect that matters here: whether the browser may remember the answer. After a 301 the second visit never reaches the shortener. After a 302 it does, and that is where the click gets counted.

What each status buys you

301 Moved Permanently

Says the move is permanent. Browsers and other caches may keep the answer and skip us on the next visit.

  • Gain: repeat visitors never reach our servers, so load and latency drop.
  • Give up: those clicks are invisible, so counts undercount. We cannot change or switch off the target for anyone who already followed the link, and a wrong redirect can stay in browsers for a long time.

302 Found (our default)

Says the move is temporary. Without explicit cache headers nothing keeps the answer, so every click reaches us.

  • Gain: exact click counts, referrer and country; links can be edited, expired or blocked at once.
  • Give up: our redirect tier serves every click. The estimate already budgets for it: 28,000 per second at peak, with the cache answering most of them.

The signal that picks one

Pick 301 when load is the pain and nobody asks for click numbers. Pick 302 when the product sells analytics or must be able to turn a link off. RFC 9110 lets a cache reuse a 301 with no extra header, but a 302 only when the response carries an explicit freshness lifetime. That also turns the switch into a dial: a 301 with a short max-age, or a 302 with private, max-age=60, lets repeat visitors skip you for a bounded time. State the signal, not just the answer.

Step 3 · Deep dive: hash the URL and resolve collisions

The first way to name a link needs no counter. Run the long URL through a hash function, which turns any input into a fixed-size number that looks random, and keep a few characters of the result.

  1. Hash the long URL. SHA-1 gives a 160-bit number, MD5 gives 128 bits, CRC32 gives 32.
  2. Read the digest as one big number and keep its last 7 base-62 digits (the number modulo 62⁷).
  3. Look the code up in the table. If it is free, insert it. If a row with the same long URL holds it, return it. If a row with a different long URL holds it, that is a collision: change the input and try again.

Keeping 7 base-62 digits throws away most of the digest and leaves about 42 bits, so two URLs can share a code. The retry rule is not optional. Which hash you pick matters little, because it only has to spread values evenly. A bare CRC32 does not work on its own: 2³² is 4.3 billion codes, and we need 110 billion.

flowchart TD
  U[Long URL] --> H[Hash it]
  H --> K[Keep 7 base 62 digits]
  K --> Q{Code in the table?}
  Q -- free --> I[Insert code and URL]
  Q -- same URL --> R[Return the existing code]
  Q -- other URL --> S[Append a salt]
  S --> H
The loop has three exits from the table check. Only 'other URL' sends you around again.

How often does a new URL land on a taken code?

At a given moment n codes are taken out of base^k, so one new URL collides with probability about n / base^k. Leave the defaults for a table near the end of its ten-year life. Then set the symbols per character to 16 (hex digits) to see why a hex digest cut to 7 characters cannot work.

The collision loop, with and without a Bloom filter

Six requests through the loop. Request 4 repeats request 1, and request 5 hashes to the same two digits as request 2. In the second scenario a Bloom filter (a small array of bits set by hashing each stored code) answers 'definitely not there' for most new codes, so most lookups disappear. Watch the lookup counter.

What the filter does not do

A Bloom filter only saves reads. 'Maybe' still needs the table, and two creates can both see 'absent' in the same instant, so the unique constraint on the code column is what really prevents two URLs from sharing a code (the loser's insert fails and retries with a salt). The filter also costs memory: roughly 10 bits per stored code for a 1% false-positive rate, which is 1.2 GB for a billion codes and about 120 GB for a hundred billion. At 350 creates per second a plain indexed lookup is the simpler choice; the filter pays off when creates are 100 times higher or each lookup is expensive.

Step 3 · Deep dive: base 62 of a unique ID

The second way skips hashing. Give every new URL a number nobody has used, and write that number in base 62. A number and its base-62 spelling are the same quantity, like 255 and ff in decimal and hex; only the alphabet changes.

  • Symbols: 0-9 are the values 0 to 9, a-z are 10 to 35, A-Z are 36 to 61.
  • Each position is worth 62 times the one to its right: 1, 62, 3,844, 238,328, and so on.
  • To spell a number, divide by 62 again and again. Each remainder is one symbol, found from the right-hand end.

Run the conversion three times: on a compact counter, on a wide timestamp-based ID of the kind 7 · Design a unique ID generator in distributed systems builds, and backwards, the way a redirect would read a code.

Spelling a number in base 62

The first scenario needs 6 characters. The second shows what a 64-bit Snowflake-style ID does to the code length. The third decodes a code back to the number it spells, which is the primary key of its row.

No two different numbers spell the same, so a collision is impossible and a create needs no read. All the difficulty moves into producing unique numbers, and there are three usual sources:

  • A database counter (auto-increment, or a single ticket table): simple, but every create waits on one machine, and that machine is a single point of failure.
  • Leased ranges: a coordinator hands each web server a block of, say, 10,000 numbers, and the server hands them out from memory. A crashed server wastes the unused part of its block, which is harmless in a space of 3.5 trillion.
  • A distributed generator such as Snowflake: no coordination per ID, but each ID packs time, machine and sequence into 63 bits. The second scenario shows the cost: 11 characters instead of 6 or 7.

Two consequences to mention. The code length grows with the counter: 6 characters until the counter passes 56.8 billion, then 7. And consecutive counters give consecutive codes, so anyone can guess the next one. If that matters, scramble the number with a keyed permutation before encoding (the Case study: URL shortener chapter builds one).

Base 62 in Python

Divide, keep the remainder, repeat. The first remainder is the last symbol, so reverse at the end.

ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"


def to_base62(number: int) -> str:
    if number == 0:
        return ALPHABET[0]
    symbols = []
    while number > 0:
        number, remainder = divmod(number, 62)
        symbols.append(ALPHABET[remainder])
    return "".join(reversed(symbols))


print(to_base62(41_358_902_177))      # J8ZJNn

Multiply the running value by 62 and add the next symbol. The redirect handler can use the result as the primary key.

# ALPHABET is the same string as in the Encode tab
def from_base62(code: str) -> int:
    number = 0
    for symbol in code:
        number = number * 62 + ALPHABET.index(symbol)
    return number


print(from_base62("J8ZJNn"))          # 41358902177

Most creates never leave the process. A crash loses at most one block of numbers.

class RangeIds:
    """Hands out numbers from a block leased from a coordinator."""

    def __init__(self, coordinator, block: int = 10_000):
        self.coordinator = coordinator
        self.block = block
        self.next_id = 0
        self.end = 0

    def next(self) -> int:
        if self.next_id == self.end:                      # block used up: lease another
            self.next_id = self.coordinator.lease(self.block)
            self.end = self.next_id + self.block
        value = self.next_id
        self.next_id += 1
        return value

Neither is wrong: they fail in different places

Hash and resolve collisions

Wins when one long URL should keep one code, or you would rather not run an ID service.

  • Fixed length, and codes cannot be predicted from each other.
  • The lookup you need anyway also finds repeats, so deduplication is free.
  • No shared counter: any web server can create.

Costs: every create reads the table first (or asks a Bloom filter), collisions are certain and handled by retry, and the code space is fixed by the characters you keep.

Base 62 of a unique ID

Wins when creates are frequent or lookups are expensive.

  • A collision is impossible, so a create is one insert with no read.
  • A redirect decodes the code to the primary key: a direct integer lookup.
  • Codes are as short as the counter allows.

Costs: you must run a source of unique numbers that stays available, codes are guessable unless you scramble the number, and the same URL submitted twice gets two codes unless you pay for an index on the long URL.

Step 3 · Deep dive: caching hot links

Redirects suit a cache unusually well. A link never changes after it is created, so a cached copy cannot go stale. Popularity is heavily skewed, so a small set of links serves most clicks. And the value is tiny: one long URL. The general patterns are in Caching; here is how they land on this problem.

  • Pattern. Cache-aside: look in the cache, on a miss read the table, fill the cache, answer. Creates do not touch the cache, because most links are clicked rarely and the first click fills it.
  • Size. From the estimate: 30 million hot links at about 250 bytes is 7.5 GB. That fits one node, but run a few with replicas for availability. Check the hot set against the capacity: the next simulation shows what happens when it does not fit.
  • Eviction. LRU. Links that go cold age out on their own. Entries can carry a long TTL anyway, so a deleted link eventually disappears even if the delete never reached the cache.
  • Cold start. After a restart, or when a node joins, every click misses at once. Size the replicas for that spike, or warm the cache from a list of the most-clicked codes before it takes traffic.
  • Unknown codes. A scanner guessing codes always misses. Cache the 404 for a short time, and rate-limit 404s per IP.

A stream of clicks against an LRU cache

Watch the cache contents (least recently used first) and the database counter. In the first scenario the hot links fit and one-off links push each other out. In the second the hot set is bigger than the cache and LRU evicts each link just before it is needed again. The last two compare a cold start with a warmed one. The number to watch in production is the hit ratio: a sudden drop means a cold start, or a hot set that no longer fits.

What interviewers ask next

How do you stop abuse of the create endpoint?

Rate-limit creates per API key and per IP at the gateway with a token bucket (4 · Design a rate limiter). On create, accept http and https only, cap the length, and check the destination against a blocklist of phishing and malware domains. Re-scan from time to time, because a page can turn bad after the link exists.

How do you scale the web tier?

It is stateless, so add servers behind the load balancer and scale on request rate or CPU. Nothing sticks to a server, and a lost server loses nothing.

How do you scale the database?

Reads first: redirect misses go to read replicas. Then writes and size: shard on a hash of the code (5 · Design consistent hashing), not on ranges of a sequential ID, which would send every create to the newest shard. A key-value store shards for you; Scaling databases: replication, sharding, partitioning and Databases: SQL vs NoSQL cover the options.

A link is opened a few milliseconds after it was created. Can a replica answer 404?

Yes, replication lags. On a replica miss, check the primary before answering 404, or read the primary for codes newer than a few seconds. Creation itself is strongly consistent because the insert goes to the primary.

How do you count clicks?

Because we answer 302, every click reaches a web server. After sending the response it publishes a small event (code, time, country, referrer) to a queue. Workers aggregate per code and minute and write to a separate analytics store. A queue outage drops or buffers events and never touches a redirect (Message queues & streaming (Kafka)).

How do you keep it available?

Run every tier in at least two availability zones: web servers behind health checks, cache nodes with replicas, a database with a standby that is promoted on failure. Redirects read immutable data, so they survive a failover from the cache and the replicas, and only creates pause for a moment.

What about expiry or deleting a link?

Store an expires_at and compare it on every read, delete the cache key when a link is disabled, and sweep expired rows later in batches. Do not reuse a code for years: an old printed link must not suddenly point at a stranger's page.

A 60-second summary

'I would confirm scope first: shorten and redirect, 30 million new URLs a day and about 20 redirects per URL. That is roughly 350 creates and 7,000 redirects a second, 28,000 at peak, and about 20 TB over ten years, so a sharded store with a cache in front. Seven base-62 characters give 3.5 trillion codes, plenty for 110 billion URLs. Redirects answer 302 so every click can be counted. For the code I would use base 62 of an ID leased in ranges, which cannot collide and needs no lookup on create, or hash with collision resolution if one URL must keep one code. Reads are cache-aside with LRU, and I would warm the cache after a restart. I would rate-limit creates, replicate the database, and send click events through a queue.'
