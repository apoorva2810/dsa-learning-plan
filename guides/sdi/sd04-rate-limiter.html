Design a rate limiter

A rate limiter caps how often a client may call a service and answers the excess with HTTP 429. This chapter walks the interview: scope and a back-of-envelope estimate, where the limiter lives and how a request flows through it, five algorithms (token bucket, leaking bucket, fixed window, sliding window log, sliding window counter) simulated on the same traffic, how rules reach the limiter, and what changes when many servers share one set of counters: races, atomic Redis scripts, synchronisation, regions and failure.

After this chapter you can
  • Ask the scoping questions that change the design: who is limited, by what key, where the limiter runs, what happens on failure
  • Estimate limiter traffic, Redis nodes and counter memory with a back-of-envelope calculation
  • Draw the request path: gateway, limiter middleware, rules cache, Redis counters, and a 429 with Retry-After
  • Explain token bucket, leaking bucket, fixed window, sliding window log and sliding window counter, and choose between them
  • Show how a read-then-write counter lets extra requests through, and fix it with an atomic Redis command or Lua script
  • Discuss synchronising many limiter instances, latency across regions, monitoring and fail-open behaviour

Step 1 · Understand the problem and set the scope

A rate limiter caps how many requests a client may send in a period and turns the rest away, normally with HTTP status 429 Too Many Requests. It keeps one noisy or abusive client from starving everyone else, holds a service inside the capacity it was sized for, caps the bill for a paid downstream API, and enforces the quotas a product sells (a free plan gets 100 calls a minute, a paid plan gets more).

The prompt is deliberately open, so the first job is to narrow it. For this chapter assume the answers below, and say them out loud in an interview so the interviewer can correct you.

  • What is limited: calls to a public HTTP API, per client. The client is an API key, or the source IP address for anonymous calls. Limits can differ per route and per plan.
  • Where it runs: on the server side, as one shared component in front of many API servers. A limiter inside the client app can be bypassed, so it cannot be the control.
  • Scale: about 400,000 active clients in the busiest hour, in a few regions.
  • Latency: the check adds about a millisecond, not tens of milliseconds.
  • On rejection: return 429 with headers that say when to come back. Do not drop requests silently.
  • Failure: if the limiter's own store is down, ordinary routes keep working (fail open) and abusable ones do not.

Questions a strong candidate asks

  • Who is limited: an API key, a user, an IP address, or a combination? Does the rule differ per route or plan?
  • Does the limiter run in the client, in each service, or at a gateway we already have?
  • How many clients and requests per second, and in how many regions?
  • A hard limit (never above N) or a soft one (a small overshoot is fine)? This decides how exact the counters must be.
  • What does a rejected caller see: a bare 429, or headers that say when to retry?
  • If the limiter itself breaks, should the API fail open or fail closed?

How big is the limiter itself?

The limiter sits on every request, so its own cost matters. Change the assumptions and watch the Redis node count and the memory of two designs: a couple of numbers per client (token bucket, counters) against one timestamp per request (sliding window log). The method is the one from 2 · Back-of-the-envelope estimation.

Step 2 · Propose a high-level design

▶ Video lesson: The design walk: gateway, limiter and Redis 4:37 · 8 scenes · narrated, pause anytime and explore

Where the limiter can live

There are three places to put it, and only two can be trusted.

  • In the client. The caller throttles itself. A good SDK backs off and honours Retry-After, but a forged or buggy client simply will not, so this is politeness, not control.
  • In each service. Every API service links a limiter library and counts its own traffic. Fine for one service. With many services you get many copies of the logic, many rule files and no view of one client's total.
  • As middleware in front of the services. Usually the API gateway (Load balancers, reverse proxies & API gateways). Every request already passes through it, so the limiter is one more step in that pipeline, with the rules in one place. Proxies and gateways such as Envoy, NGINX, Kong and AWS API Gateway ship one.

Say gateway middleware unless the scope says otherwise, and name what you give up: one more component on the hot path of every request.

A limiter library in every service, or one at the gateway

Limiter library in each service

  • Each team picks an algorithm and keeps its own rule file.
  • A client calling three services gets three separate budgets, and nobody sees its total.
  • Rejected requests have already reached the service and cost it a thread, parsing and authentication work.
  • No extra hop when the counters stay in the process.

Choose it when there is one service, one team, and the limit is purely local, such as a concurrency cap on one heavy endpoint.

Middleware at the gateway

  • One implementation and one rules store; changing a limit during an incident is one edit.
  • The client's total is visible across every route behind the gateway.
  • Rejected requests are turned away before they touch a service.
  • The gateway gains a dependency: the limiter must be fast and must fail safely.

Choose it when several services sit behind one entry point, limits depend on the plan, or limits must change without a deploy.

One request through the boxes

The rule is 100 requests per minute per API key on the search route. Switch scenarios: the 100th call, the 101st call, and a call while Redis is unreachable. The badge on Redis is the client's counter against the limit.

What happens to a rejected request

  • Reject with 429. The default: cheap, immediate, and it tells the client when to return.
  • Delay it. Queue it, as a leaking bucket does. Good for work that can wait, such as webhook deliveries; bad for an interactive call, where the client just holds a connection open.
  • Degrade. Serve a cheaper answer, such as a cached result. Rarely right for an API, sometimes right for a search box.

Whichever you choose, count rejections per rule and per client. That is how you find a rule that is too tight, or a customer who needs a higher plan.

What the client sees

A rejected call must say why and when to retry, otherwise clients retry blindly and make the overload worse. Return status 429 and a Retry-After header with the seconds to wait (RFC 6585 defines the status, RFC 9110 the header). Most APIs also send their limit and the client's remaining budget on every response, so well-behaved clients can slow down before they are cut off. The X-RateLimit-* names below are the common convention; an IETF draft proposes standard RateLimit and RateLimit-Policy fields.

The 100th call and the 101st

HTTP/1.1 200 OK
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0

HTTP/1.1 429 Too Many Requests
Retry-After: 23
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
Content-Type: application/json

{"error": "rate_limited", "detail": "100 requests per minute per key. Retry in 23 seconds."}
The call that uses the last of the budget succeeds and says so; the next one is refused with the time until the window resets.

Where the counters live

Counters change on every request and expire on a schedule, so they want a fast in-memory store with built-in expiry and atomic operations. A relational database writes to disk on every update and would become the bottleneck. A dictionary in each limiter process is fast but private to one instance, which the distributed section shows is not enough. Redis fits: INCR is atomic, keys expire on their own, and one node serves tens of thousands of simple operations a second (the calculator above puts the peak at a handful of nodes). Caching covers Redis in general.

Step 3 · Deep dive: five algorithms on the same traffic

▶ Video lesson: Five limiters on the same traffic 6:55 · 10 scenes · narrated, pause anytime and explore

One rule, one stream of traffic

The five algorithms below enforce the same promise: about 4 requests per 8 seconds per client. The numbers are tiny so you can follow every request; a real rule might say 100 per minute. All five replay the same 16 requests over 24 seconds: one early request, a burst of 3 at second 7, a burst of 4 at second 8 (the first second of the next window), a trickle of one request a second from 9 to 12, a quiet spell, and a burst of 4 at second 19.

In every simulation the top chart is that traffic, coloured by the limiter's decision: green means every request that second got through, amber means some were rejected (the label ✗2 counts them), red means all were. Faded bars have not happened yet. Read each run by asking three things: what does it remember per client, what does it do with the burst at seconds 7 and 8, and what does it do afterwards.

Token bucket: bursts up to the bucket size

A bucket holds up to 4 tokens and gains half a token per second, which is the rule's 4 per 8 seconds. Every request needs one whole token. Watch the bucket drain when the bursts arrive at seconds 7 and 8, and refill during the quiet spell. The second scenario uses a smaller bucket: the size is the burst you allow. AWS API Gateway throttles with this algorithm, exposing the refill rate and the bucket size as its two settings.

Leaking bucket: a steady outflow, with waiting

Requests join a queue of up to 4 and a worker releases one every 2 seconds, so the API sees a steady 4 per 8 seconds whatever arrives. The two bottom charts matter here: how full the queue is, and what the API actually receives. NGINX documents its limit_req module as a leaky bucket: it delays excess requests so that they are processed at a defined rate.

Fixed window counter: the boundary burst

One counter per 8-second window (shaded), reset to zero when the window changes. Cheap and easy to explain. Look at seconds 7 and 8: the budget of one window is spent in its last second and the next window's budget in its first.

Sliding window log: exact, one timestamp per request

The limiter stores a timestamp for every request it lets through and, before each decision, discards the ones older than 8 seconds. It is exact because it looks at the real last 8 seconds, not at a calendar window. The cost is the log itself.

Sliding window counter: the weighted estimate

Two counters instead of a log: the previous window's total and the current window's. The estimate for the last 8 seconds is current + previous × share, where share is the part of the previous window that still overlaps the last 8 seconds. Watch it fall from 1 to 0 as the current window ages, and compare seconds 8 to 12 with the fixed window.

The five limiters in Python

Time is passed in, so the class is easy to test. The refill is lazy: it is computed from the elapsed time on each call, so no timer runs for idle clients.

class TokenBucket:
    """Refills lazily: no timer per client, just arithmetic on each call."""

    def __init__(self, size: float, per_second: float):
        self.size, self.rate = size, per_second
        self.tokens, self.updated = float(size), None

    def allow(self, now: float) -> bool:
        if self.updated is not None:
            self.tokens = min(self.size, self.tokens + (now - self.updated) * self.rate)
        self.updated = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False                         # answer 429


bucket = TokenBucket(size=4, per_second=0.5)  # 4 per 8 s on average, bursts of up to 4

This is a queue and a worker, not a counter. In a gateway the queue holds the waiting requests and a timer or worker releases them at the fixed rate.

from collections import deque


class LeakingBucket:
    """A bounded FIFO queue plus a worker that drains it at a fixed rate."""

    def __init__(self, size: int):
        self.size = size
        self.queue: deque = deque()

    def offer(self, request) -> bool:
        if len(self.queue) >= self.size:
            return False                     # queue full: answer 429
        self.queue.append(request)
        return True

    def release(self):
        """Call once every `every` seconds from a timer or worker loop; at most one request leaves."""
        return self.queue.popleft() if self.queue else None


bucket = LeakingBucket(size=4)               # the worker calls release() every 2 s: 4 per 8 s

The window number is now // window. In Redis that number goes into the key and the key gets a TTL.

class FixedWindow:
    def __init__(self, limit: int, window: int):
        self.limit, self.window = limit, window
        self.window_id, self.count = None, 0

    def allow(self, now: float) -> bool:
        window_id = int(now // self.window)  # which calendar window are we in?
        if window_id != self.window_id:
            self.window_id, self.count = window_id, 0     # a new window: reset the counter
        if self.count >= self.limit:
            return False
        self.count += 1
        return True

The deque only ever holds timestamps still inside the window, so its length is at most limit. Rejected requests are not recorded in this version.

from collections import deque


class SlidingWindowLog:
    def __init__(self, limit: int, window: float):
        self.limit, self.window = limit, window
        self.log: deque[float] = deque()     # timestamps of requests let through, oldest first

    def allow(self, now: float) -> bool:
        while self.log and self.log[0] <= now - self.window:
            self.log.popleft()               # slide the window forward
        if len(self.log) >= self.limit:
            return False
        self.log.append(now)
        return True

Two integers and a division. share is 1 at the start of a window and falls to 0 at its end.

class SlidingWindowCounter:
    def __init__(self, limit: int, window: int):
        self.limit, self.window = limit, window
        self.window_id, self.current, self.previous = 0, 0, 0

    def allow(self, now: float) -> bool:
        window_id = int(now // self.window)
        if window_id != self.window_id:      # roll over: the old current becomes the previous window
            self.previous = self.current if window_id == self.window_id + 1 else 0
            self.current, self.window_id = 0, window_id
        share = 1 - (now % self.window) / self.window      # part of the previous window still in the last `window` seconds
        if self.current + 1 + self.previous * share > self.limit:
            return False
        self.current += 1
        return True

How to choose out loud

Default to the token bucket and say why: two numbers per client, bursts are allowed on purpose, and a refill rate is easy to explain to customers. Then show you know when to switch: a leaking bucket when the thing behind you needs a steady flow, a sliding window counter when the contract is 'N per minute' and boundary spikes would hurt, the log only when the limit is small and exactness is contractual, the fixed window when the cheapest possible counter is good enough.

Step 3 · Deep dive: rules and how they reach the limiter

A limiter whose limits are hard-coded turns every change into a deploy. Treat rules as data.

  • A rule says who (the key: API key, user, IP, plus route and plan), how much (requests per unit of time) and how (which algorithm, what burst).
  • Rules live in a version-controlled store and are reviewed like code. A typo that sets a limit to 0, or a match that covers every client, blocks everyone, so validate before they ship.
  • Limiter instances do not read the store per request. Workers pull changes every few seconds into a cache the limiter reads locally, so an edit takes effect in seconds without a restart.
  • Ship a new rule in shadow mode first: the limiter computes the decision and records 'would reject' in metrics, but lets the request through. Switch to enforcing when the numbers look right.

rules.yaml

# rules.yaml: one entry per limit. The first matching rule wins.
rules:
  - id: login-by-ip
    match: { route: "POST /v1/login" }
    key: ip
    algorithm: fixed_window
    limit: 10
    per: minute
    on_store_error: fail_closed        # a password endpoint is abusable, so do not fail open

  - id: search-free
    match: { route: "GET /v1/search", plan: free }
    key: api_key
    algorithm: sliding_window_counter
    limit: 100
    per: minute

  - id: search-pro
    match: { route: "GET /v1/search", plan: pro }
    key: api_key
    algorithm: token_bucket
    size: 500                          # the burst a client may send at once

Step 3 · Deep dive: one limit enforced by many servers

▶ Video lesson: The read-then-write race 4:28 · 8 scenes · narrated, pause anytime and explore

On one machine a limiter is a dictionary and a lock. Behind a load balancer a client's requests spread over many limiter instances, which creates two problems that never show up in a single process.

Problem 1: the read-then-write race

A check has three parts: read the counter, compare it with the limit, write the new value. If two instances run those parts at the same time for the same client, both can read the same number, both decide to allow, and both write the same result back. One increment is lost, and the client passes more requests than the rule allows. The window is a few milliseconds wide, which sounds small until you remember that bursts are exactly when requests from one client arrive together.

Two limiters, one counter

The counter holds 3 and the limit is 4, so exactly one of two simultaneous requests should pass. Run the naive version first, then the two fixes. The time axis is in milliseconds and the numbers are illustrative.

The fix: make check-and-update one atomic step

Redis runs one command at a time, so a single command is atomic. INCR reads, adds one and returns the new value with no gap, and for a fixed window that is the whole algorithm. A token bucket or a sliding log needs several steps (read two fields, compute, write them back), so put those steps in a Lua script and send it with EVAL. Redis runs the script from start to finish before it looks at the next command, which its scripting documentation calls atomic execution, so nothing can slip in between your read and your write. A distributed lock around the sequence is also correct, but it adds round trips, serialises every check for that client, and needs an expiry for holders that crash.

From racy to atomic, in redis-py

Two separate round trips. Between the read and the write, any other limiter can change the counter.

import redis

r = redis.Redis()
LIMIT = 4


def allow_racy(client: str) -> bool:
    key = f"rl:{client}"
    count = int(r.get(key) or 0)             # 1. read
    if count >= LIMIT:                       # 2. decide, on a number another limiter may already have changed
        return False
    r.set(key, count + 1, ex=60)             # 3. write: overwrites any increment made since step 1
    return True

Enough for a fixed window. The pipeline matters: if the process died between a bare INCR and its EXPIRE, the key would never expire (the Redis INCR page lists this pitfall in its rate limiter pattern).

import time

import redis

r = redis.Redis()


def allow_fixed_window(client: str, limit: int = 100, window: int = 60) -> bool:
    key = f"rl:{client}:{int(time.time()) // window}"
    pipe = r.pipeline()                      # MULTI/EXEC: both commands run as one unit
    pipe.incr(key)                           # atomic: reads, adds one, returns this request's number
    pipe.expire(key, window, nx=True)        # set the TTL once, so old windows clean themselves up (Redis 7+)
    count, _ = pipe.execute()
    return count <= limit

The whole read-refill-spend-write cycle is one script. The key is passed in KEYS so a cluster can route the call by hash slot. The clock comes from Redis (TIME); a script may read it before writing since Redis 5, which replicates a script's effects instead of the script.

import redis

r = redis.Redis()

TOKEN_BUCKET = """
local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])                  -- tokens per second
local t   = redis.call('TIME')                      -- the clock comes from Redis, not from the caller
local now = t[1] + t[2] / 1000000
local state  = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(state[1]) or capacity
local ts     = tonumber(state[2]) or now
tokens = math.min(capacity, tokens + (now - ts) * rate)
local allowed = 0
if tokens >= 1 then
  tokens = tokens - 1
  allowed = 1
end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', KEYS[1], math.ceil(capacity / rate) * 2)
return allowed
"""

bucket = r.register_script(TOKEN_BUCKET)            # uploaded once, then called by its hash


def allow_token_bucket(client: str, size: int = 4, per_second: float = 0.5) -> bool:
    return bucket(keys=[f"rl:tb:{client}"], args=[size, per_second]) == 1

A sorted set scored by timestamp is a log you can trim by range. The script trims, counts and adds in one step.

import uuid

import redis

r = redis.Redis()

SLIDING_LOG = """
local window_ms = tonumber(ARGV[1])
local limit     = tonumber(ARGV[2])
local t   = redis.call('TIME')
local now = t[1] * 1000 + math.floor(t[2] / 1000)             -- milliseconds, from Redis
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window_ms)    -- slide the window
if redis.call('ZCARD', KEYS[1]) < limit then
  redis.call('ZADD', KEYS[1], now, ARGV[3])                    -- the member must be unique per request
  redis.call('PEXPIRE', KEYS[1], window_ms)
  return 1
end
return 0
"""

log = r.register_script(SLIDING_LOG)


def allow_sliding_log(client: str, limit: int = 100, window_ms: int = 60_000) -> bool:
    return log(keys=[f"rl:log:{client}"], args=[window_ms, limit, uuid.uuid4().hex]) == 1

One clock for all instances

Take the time from Redis, not from the limiter machine. Window keys built from time.time() on different hosts put one client's requests into different windows when the clocks differ by even a second. The scripts above call TIME inside Redis, so every instance sees one clock.

Problem 2: keeping many instances in agreement

Even with atomic updates, each instance must read the same counter. If every instance keeps its own, a client whose requests are spread over N instances can send N times the limit before any single instance objects.

Step 3 · Deep dive: regions, latency and monitoring

The further a caller is from the data centre, the longer each round trip to the limiter takes. A check that costs a millisecond inside a region costs a hundred milliseconds or more across an ocean, and it happens on every request. So run limiters, with their own Redis, in each region close to users, often at the edge locations of a CDN or in regional gateways. The price is the trade from Consistency models & the CAP theorem: the regions agree eventually, not instantly.

What to monitor

Two questions: is the limiter doing its job, and is it healthy?

  • Effectiveness. Rejections per rule and per client. A rule that never rejects is too loose; one that rejects a paying customer's normal traffic is too tight. In shadow mode, the share of traffic that would be rejected.
  • Health. Latency of the check at p99 (not the average), Redis error and timeout rate, the fail-open count, how old the rules cache is, and the hottest Redis keys and shard CPU.
  • Alarms. A sudden jump in rejections across many clients (usually a bad rule or a traffic spike: check which first), fail-open events lasting more than a minute, and a rules cache older than a few minutes.

  Call -->|no| Policy{Which route?}
  Policy -->|ordinary API route| Open[Fail open<br/>allow, count, alert]
  Policy -->|login or SMS route| Closed[Fail closed or<br/>local fallback limiter]
A design is not finished until it says how it fails: decide the behaviour before the outage, per route.

The failure catalogue

One client hammers one Redis key

All of a client's checks land on the same shard. A client sending hundreds of thousands of requests a second can saturate that shard before its limit does anything. Block it earlier: after a few rejections, keep the client in a small in-process deny list for a few seconds, or drop it at the edge.

Clocks disagree

Window keys built from each machine's own clock split a client across windows. Take the time from Redis inside the script, or from one synchronised source.

A bad rule ships

A limit of 0, or a match that covers everyone, rejects all traffic. Validate rules in review, roll them out in shadow mode first, and keep a one-step rollback.

Clients retry in lockstep

If every rejected client retries at the same second, the retries are the next burst. Send Retry-After with a little random jitter and tell clients to back off exponentially with jitter (Reliability patterns).

Everyone's window resets together

Calendar windows reset for all clients at the same instant, which concentrates traffic just after the boundary. Offset each client's window (hash the client id into the start time) or use a sliding algorithm.

Follow-up questions interviewers ask

Hard or soft limits?

A hard limit never lets more than N through, which needs atomic, central counters. A soft limit tolerates a small overshoot, which allows local counters with periodic sync and keeps latency lowest.

Which layer should limit?

Coarse, cheap limits (per IP, connection floods) belong at the edge, in the load balancer or a DDoS service, working on network and transport details. Precise limits by API key, user and route belong at the gateway, which can read the request.

How should well-behaved clients behave?

Read the limit headers, cache responses, batch calls, honour Retry-After, back off with jitter, and avoid starting scheduled jobs all at minute zero.

Rate limit or quota?

A rate limit smooths traffic per second or minute. A quota caps a day or a month and often drives billing, so it needs durable, accurate counters and cannot rely on keys that merely expire.

Requests that cost different amounts

Charge heavy endpoints more than one token, so an export that scans a table costs as much budget as fifty simple reads.

Where else does the same idea appear?

A crawler's politeness delay per host (9 · Design a web crawler) and per-user caps on notifications (10 · Design a notification system) are rate limiters too, and retries with backoff (Reliability patterns) are the client half of the same contract.

What would you add with more time?

Limits that tighten when the backend is slow (load shedding), priority classes so health checks and paying tiers are never starved, per-tenant fairness, a usage dashboard for customers, and replaying production traffic against a new rule before enforcing it.

The 60-second summary

I would run the limiter as middleware in the API gateway, keyed by API key and route. Rules live in a reviewed store, are synced by workers into an in-memory cache, and roll out in shadow mode first. Counters live in Redis, updated by one atomic Lua script per check so concurrent limiters cannot race, sharded by client key and replicated. The default algorithm is a token bucket, two numbers per client with deliberate bursts; where the contract is 'N per minute' and boundary spikes matter I would use a sliding window counter. Over the limit the gateway returns 429 with Retry-After and the remaining budget. If Redis is unreachable, ordinary routes fail open and sensitive ones fall back to a local limiter, with an alert either way. Across regions the counters sync asynchronously, trading a small overshoot for local latency. I would watch rejections per rule, check latency, Redis errors and the fail-open count.
