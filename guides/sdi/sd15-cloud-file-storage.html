Design Google Drive (cloud file storage)

A file-sync service looks like 'upload a file', but the interesting work starts after that: cutting files into hashed blocks so an edit costs kilobytes instead of gigabytes, a strongly consistent metadata store that decides which version is current, telling the other devices, and keeping both versions when two devices edit at once. This chapter walks the interview's four steps and runs the block-level delta sync, the commit protocol and the conflict handling as pictures you can step through.

Step 1 · Understand the problem and establish scope

A cloud file storage service keeps users' files online, lets them open those files from a browser or a phone, and ships a desktop client that mirrors a folder to the cloud and keeps every device in step. The bytes themselves are the easy part, because an object store already holds them. The hard part is syncing: moving only what changed, deciding which version is current, and telling the other devices.

What we assume after asking:

  • Clients: web, mobile, and a desktop sync client that watches a folder, works offline and catches up when it reconnects.
  • Features: upload and download, sync across a user's devices, shared folders, version history, change notifications. Out of scope: real-time co-editing of a document, full-text search, previews.
  • Files: any type, up to 20 GB each, so uploads must survive dropped connections.
  • Scale: 120 million registered users, one in five active on a given day, 5 GB free per user.
  • What matters most: never lose a file; other devices see a change within seconds; an edit sends only the bytes that changed; every device agrees on the current version.
  • Security: encrypted in transit and at rest.

Questions a strong candidate asks first

  1. Which clients do we support, and must the desktop client work offline?
  2. Is sharing in scope, and with which permissions?
  3. What are the maximum file size and the quota per user?
  4. Do we keep version history, and for how long?
  5. Is real-time co-editing in scope, or only file-level sync?
  6. If two devices edit the same file at once, is it acceptable to keep both versions?

Back-of-the-envelope: storage, traffic and metadata

Change any assumption. 'Promised' space adds up every quota; 'stored' is what people actually use. The peak factor scales the average to the busiest second, and bandwidth is QPS × file size × 8 bits.

Step 2 · Propose a high-level design

Read the estimate before drawing. Upload QPS is modest (hundreds to a few thousand per second), but storage is tens of petabytes and peak bandwidth is tens of gigabits. The metadata is tiny by comparison, around 30 TB, yet that is still tens of billions of rows, more than one database machine should hold and serve. The estimate splits the system in two:

  • Bytes (huge, immutable, cheap per GB) belong in object storage. Use one rather than build one; Object storage (S3) & CDNs covers durability, pre-signed URLs and storage tiers.
  • Metadata (small, mutable, must be exactly right) belongs in a transactional database with a cache in front.

The smallest design that works is one server with a database and a local disk. Here is why it stops working, and what replaces it:

From one server to split tiers

Start: one server does everything

A web server, a database and a local disk on one machine.

  • The disk is the capacity limit, and the machine is the durability limit: lose it and the files are gone.
  • Every upload and download streams through the web tier, so a few big transfers starve ordinary requests.
  • Metadata and bytes scale in different ways, but here they scale together or not at all.

Split bytes from metadata

Object storage for the bytes, a transactional database for the metadata, stateless servers in front.

  • Durability and capacity come from the object store (replicated across zones, effectively unlimited).
  • The API tier handles small requests, while block bytes flow through their own servers.
  • Each part scales on its own axis: storage by adding data, metadata by sharding, servers by adding machines.

Step 3 · Deep dive: block servers and delta sync

▶ Video lesson: Block servers and delta sync 6:08 · 10 scenes · narrated, pause anytime and explore

A file is not stored as one object. The client cuts it into blocks (fixed slices, 4 MB here), names each block by the SHA-256 hash of its bytes, and a file version is nothing more than an ordered list of block hashes. That one decision pays for four things:

  • Delta sync. After an edit only the blocks whose hash changed travel. Editing a few bytes of a 36 MB file moves one 4 MB block, not 36 MB.
  • Resumable uploads. Blocks are independent, and uploading the same block twice is harmless. A dropped connection costs at most the block in flight, and no upload session has to be tracked.
  • Deduplication. A block the service already stores is never uploaded or stored twice, whether it came from an earlier version, another file or another user.
  • Cheap history. Version 4 shares eight of its nine blocks with version 3, so keeping both costs one extra block.

Who does what. Splitting and hashing happen on the client, because only the client can tell which blocks are unchanged before sending a byte. (A browser upload has no earlier state to compare with, so it can send the whole file and let a block server do the cutting.) Block servers are the service side of the same pipeline: they check hashes, encrypt, write to cloud storage, and read blocks back for downloads.

The client does the cheap, early work (split, hash, decide, compress). The block server does the trusted, final work (verify, encrypt, store).

Delta sync, block by block

A 36 MB file is nine 4 MB blocks (in this toy one character is one MB). Cells show the first four hex digits of each block's SHA-256 and labels show the content. Switch scenarios: an in-place edit, an insertion that shifts every later block, the same insertion with content-defined blocks, and a file the service already holds for another account.

The client side in Python: split, hash, decide, send

import hashlib
import zlib

BLOCK_SIZE = 4 * 1024 * 1024                       # 4 MiB


def block_index(path: str) -> list[tuple[str, int, int]]:
    """One pass over the file: [(sha256_hex, offset, length), ...]. Only hashes stay in memory."""
    index, offset = [], 0
    with open(path, "rb") as f:
        while chunk := f.read(BLOCK_SIZE):
            index.append((hashlib.sha256(chunk).hexdigest(), offset, len(chunk)))
            offset += len(chunk)
    return index


def hashes_to_send(current: list[str], last_synced: list[str], service_has) -> list[str]:
    """Blocks that must travel: not in the last synced version, and not stored by the service."""
    known = set(last_synced)                       # already part of this file's history
    send = []
    for h in current:
        if h in known:
            continue                               # unchanged, or repeated inside the file
        known.add(h)
        if not service_has(h):                     # a real client batches this into one request
            send.append(h)
    return send


def pack(raw: bytes) -> bytes:
    """Compress before encrypting: ciphertext looks random and does not compress."""
    return zlib.compress(raw, 6)


def sync_file(path, base_version, last_synced, service_has, put_block, commit):
    index = block_index(path)
    current = [h for h, _, _ in index]
    wanted = set(hashes_to_send(current, last_synced, service_has))
    with open(path, "rb") as f:
        for h, offset, length in index:
            if h in wanted:
                wanted.discard(h)                  # a block repeated inside the file goes up once
                f.seek(offset)
                put_block(h, pack(f.read(length))) # PUT /blocks/<hash>, idempotent
    commit(base_version, current)                  # the call that makes version N+1 visible; may answer need_blocks
Hashes stay in memory; block bytes are read again only for the blocks that must travel. The commit call is what makes the new version visible.

Go deeper

Why an insertion breaks fixed-size blocks, and what fixes it

With fixed cut points, adding three bytes near the start shifts every later byte, so every later block hashes differently even though the content is nearly identical. Content-defined chunking picks cut points from the data: slide a small window over the bytes, compute a rolling hash, and cut wherever the hash matches a pattern (for example its low 22 bits are zero, which gives blocks of about 4 MB on average, with a minimum and maximum size). The same content cuts in the same places after an insertion, so only the blocks around the edit change. rsync finds matching blocks at any offset with a rolling checksum (The rsync algorithm), and the low-bandwidth file system LBFS chunks files by content (LBFS, SOSP 2001). The price is more client CPU and variable-size blocks.

Compress, then encrypt

A good cipher turns data into bytes that look random, and random bytes do not compress. So the order is compress first, encrypt second. Skip compression for formats that are already compressed, and detect them by extension or by sampling the entropy of the first block.

Which hash?

Deduplication treats equal hashes as equal bytes, so the hash must be collision-resistant: SHA-256, not CRC or MD5. With a hash for which collisions can be crafted, one user could upload a block that collides with another user's block and make the service serve the wrong bytes. The server recomputes every hash it is given.

End-to-end encryption versus deduplication

If the client encrypts with a key only the user holds, the service sees random bytes. It cannot deduplicate across users (the same file encrypts differently for each), cannot generate previews, and cannot scan for malware. Some products accept that trade ('zero knowledge'); most consumer drives encrypt at rest with service-held keys and keep these features.

Must the bytes pass through block servers?

No. The API can hand the client short-lived pre-signed URLs (Object storage (S3) & CDNs) so blocks go straight to the object store, which takes the block servers out of the byte path. The costs: the service can no longer check the hash before the write (verify afterwards and quarantine a mismatch), and compression and encryption move to the client or into the object store. Keep block servers when you need that control.

Very large files

A 20 GB file is about 5,000 blocks. The client uploads several blocks in parallel to fill the connection and keeps per-block progress in its local database. The commit carries 5,000 hashes of 32 bytes, about 160 KB, which is fine. The same independent-parts trick appears in video uploads (14 · Design YouTube).

Step 3 · Deep dive: the metadata database and strong consistency

The metadata database answers every question except "what are the bytes": who owns what, which files sit in which folder, the latest version of each file, which blocks make up each version, and what changed since a device last looked.

Files live in namespaces rather than in one tree per user. A user's own root folder is a namespace, and so is every shared folder, with its own list of members. A namespace is the unit of ordering and of sharding. Each one has a journal, an append-only log of changes numbered by a growing cursor. A device syncs a namespace by asking for the journal entries after the last cursor it saw.

Block rows are content-addressed and shared; everything else hangs off a namespace. VERSION_BLOCK is how a version points at its blocks, and why history is cheap: a new version adds rows, not data.

Why metadata must be strongly consistent. If two devices can see different "latest" versions of a file, they build edits on different bases and someone's work disappears. A user who saves on the laptop and opens the phone expects the new file. So file metadata lives in a store with transactions and one authority per shard: in practice a relational database, sharded by namespace_id so a commit touches one shard. (Databases: SQL vs NoSQL covers the choice, Scaling databases: replication, sharding, partitioning the sharding, and Consistency models & the CAP theorem what you give up during a partition.)

What does not need it. Blocks are immutable and named by their content, so they can be cached, replicated and re-uploaded freely. And the whole design has one decision point, the commit transaction, which compares base_version with the latest version. Everything else may lag a little without breaking correctness: a stale read costs a wasted upload and a conflict, never a lost update.

Step 3 · Deep dive: upload and download flows

▶ Video lesson: Upload, download and conflicts 5:50 · 9 scenes · narrated, pause anytime and explore

Uploading looks like one request but is a short conversation, because the client has to find out which blocks the service lacks. The API server owns the commit; block servers only ever see blocks.

  1. Negotiate. The client sends the version it wants to create: path, base_version and the ordered list of block hashes. If every block is already stored, the commit succeeds at once. Otherwise the API server replies with the hashes it lacks. A stale base is already rejected here, so a doomed upload moves no bytes.
  2. Upload the missing blocks, in parallel, straight to block servers. Each upload is idempotent.
  3. Commit. The client repeats the commit. The API server now runs one transaction: check that the file's latest version equals base_version (the check that counts, because someone may have committed in the meantime), insert the new version and its block list, move the file pointer, append a journal entry. Only then does the version exist for anyone.

Simpler designs fire the metadata request and the block upload in parallel and mark the version pending until both finish. Negotiating first avoids pending rows and lets the service skip blocks it already has.

Blocks first, commit last: the version becomes visible only when every block is durable.

The ordering rule

A version must never become visible before all of its blocks are durable. Blocks first and commit last is why a crash at any moment leaves either the old version or the new one, never a torn mix. Blocks that were uploaded for a commit that never happened are just unreferenced garbage; a collector removes them after a grace period.

Step 3 · Deep dive: telling the other devices, long polling or WebSocket

After a commit, every other device that syncs the folder must find out quickly. Two decisions: what to send and over what channel.

What to send: a hint, not data. The event is only "namespace 71 changed, cursor 4812". The device then pulls the details from the journal. That keeps the channel tiny and makes loss harmless: if an event is dropped, duplicated or late, the next pull returns exactly the missing entries. It also means publishing after the commit, without a distributed transaction, is acceptable. Google's Drive API follows the same pattern: a notification only says that changes exist, and the client reads the change feed from a saved page token (Drive API: changes and notifications).

Who gets it. Devices subscribe to the namespaces they sync, and the notifier fans a publish out to the members' devices. A device that is offline gets nothing now and catches up from the journal when it reconnects. An offline queue only saves it a round trip.

Over what channel. A device must hear about changes it did not ask for, which plain request and response cannot do. Two options:

Long polling versus WebSocket for change hints

Long polling

The client sends GET /changes/wait?cursor=4811. The server holds the request open until something changes in a namespace the device syncs, or until about 30 to 60 seconds pass, then answers. The client handles the answer and immediately sends the next request.

  • Plain HTTP: works through proxies, firewalls and ordinary load balancers, and a dropped request is simply retried.
  • One-way, which is all this problem needs: hints are rare next to chat messages, and tiny.
  • Costs a held request per device and a new request after every event.
  • Held requests must stay under proxy and load-balancer idle timeouts (RFC 6202 lists the known issues).

WebSocket

The client upgrades an HTTP connection to a WebSocket (RFC 6455) and keeps it open. Either side can send a message at any time.

  • Lowest latency and overhead per message, and bidirectional.
  • Pays off when messages are frequent and flow both ways: chat, presence, live cursors.
  • The service must hold millions of stateful connections: heartbeats, reconnect storms after a deploy, load balancers that support long-lived upgrades.
  • A backgrounded phone loses the socket; the operating system's push channel (APNs, FCM) is the reliable wake-up there.

The signal for choosing. Rare, small, one-way hints: long polling, the simplest thing to operate. Frequent two-way messages: WebSocket, as in Case study: chat application and 12 · Design a chat system. Whichever you pick, keep a slow safety-net poll every few minutes, in case a hint is lost.

Step 3 · Deep dive: sync conflicts

A conflict is two commits built on the same base version. It is normal in a sync product: laptops edit offline for hours, and a shared folder has several writers. You cannot prevent conflicts (locking a file while someone is offline for a day is not an option), so you detect them cheaply and resolve them without losing data.

Detection is the base-version check. Every commit says which version it started from. Inside the commit transaction the database compares that number with the file's latest version. Equal: accept and bump. Different: someone else got there first, so reject with a conflict answer that includes the latest version. This is optimistic concurrency control (compare and set): no locks are held while people think.

Resolution is a policy. Run the same story under three policies and compare what survives.

Step 3 · Deep dive: saving storage and money

Storage is the bill. Four levers, in order of effort:

  1. Deduplicate blocks. Blocks are named by hash, so "is this already stored?" is one index lookup. Two versions of a file, two files, or two users' copies of the same installer share one stored block. A background job keeps a reference count per block, and a garbage collector deletes a block only when nothing references it, it is older than a grace period (an upload can be seconds away from its commit), and a final check of the version rows agrees.
  2. Limit history intelligently. Do not just cap the count. Keep every version from the last day, one per day for a month, one per week after that, and anything the user named or restored. Versions share blocks, so history costs only the changed blocks, but a large file that changes all day still adds up. Dropped versions release their blocks to the collector.
  3. Compress what compresses and skip what does not.
  4. Move cold data to a cheaper tier. Blocks used only by old versions, and files nobody has opened for months, move to an infrequent-access or archive class by lifecycle rule. Reads still work, but they are slower or cost a retrieval fee. Decide per block, across every file and user that references it.

Cross-user deduplication leaks information

If the server answers 'already stored, no upload needed', anyone can learn whether someone has uploaded a given file: upload it and watch whether bytes are requested. Worse, if knowing a block's hash were enough to download it, a leaked hash list would be a leaked file. Fixes: deduplicate only inside an account (gives up the cross-user savings); make the client prove it holds the bytes before the server skips the upload (proofs of ownership); and never treat a bare hash as a capability, because every block read is authorised against a version the caller can access.

Step 4 · Wrap up

This question tests three things: whether you separate bytes from metadata, whether you think in blocks rather than whole files, and whether you treat consistency and conflicts as part of the design instead of edge cases. Close by showing that every component can fail without losing a file.

Follow-up questions interviewers ask next

Mistakes that cost points
  • Re-uploading the whole file on every edit.
  • Treating file metadata as eventually consistent, which allows lost updates.
  • Pushing file contents through the notification channel instead of a small hint.
  • Last-write-wins for people's documents.
  • Making a version visible before all of its blocks are durable.
  • Forgetting the garbage collector, or deleting a block the moment its count reaches zero.
  • Deduplicating across users without thinking about what the answer 'already stored' reveals.
How do shared folders work?

A shared folder is a namespace with several members and roles (viewer, editor). Each member's tree mounts it as a folder. Permission checks live in the API server; all members' devices subscribe to the same namespace, so one commit notifies everyone. A folder shared with 100,000 people makes the notifier's fan-out the bottleneck, which batching and per-connection coalescing address.

How would you add search and previews?

Consume the journal asynchronously: a worker reads each new version, extracts text or renders a thumbnail, and writes to a search index or a thumbnail store. Keep it out of the commit path, so a slow indexer can never delay a sync.

What happens on delete?

A delete is a new version marked as a tombstone, so it syncs like any edit. The versions stay recoverable for a retention period (the trash); when that expires the blocks lose their references and the collector reclaims them.

Can you support real-time co-editing?

That is a different design. Collaborative documents store a log of operations and merge keystrokes with operational transformation or CRDTs, so there is no whole-file conflict to resolve. File sync stays as designed for everything else.

How do you scale the block index and the journal?

The block index is keyed by hash, so shard it by hash prefix (5 · Design consistent hashing shows the placement trick) or let the object store's own listing be the index. The journal lives with its namespace on the namespace shard, so a hot shared folder is a hot shard: split by namespace, never inside one.

What would you add with more time?

Metrics for sync latency, conflict rate and dedup ratio; per-user rate limits (4 · Design a rate limiter); malware scanning on upload; regional placement for data residency; a bandwidth-saving mode for mobile; and content-defined chunking if the traffic shows files that are edited by insertion.

Interview script: cloud file storage

The 60-second summary

Each client keeps a local database and cuts files into 4 MB blocks named by their SHA-256. To save, it sends the new version's ordered hash list and the version it started from. The API server answers with the hashes it lacks; the client uploads only those to block servers, which verify, encrypt and store them in object storage. One metadata transaction then checks the base version, adds the version and a journal entry, and publishes a hint. Other devices hear it over long polling, read the journal from their cursor and fetch only missing blocks. Metadata is strongly consistent (relational, sharded by namespace) and blocks are immutable. A stale base is a conflict: first commit wins and the loser keeps a conflicted copy. Dedup, capped history and cold tiers cut the bill.
