Scale from zero to millions of users

Start with one server and add one thing at a time, each in answer to a bottleneck you can name: a separate database, a load balancer, replicas, a cache, a CDN, a stateless web tier, a second data centre, a message queue, tooling, and finally sharding. The chapter shows the order, the price of every step, how each piece fails, and how to say it all in a system design interview.

After this chapter you can
  • Retell the path from one server to a sharded, multi-data-centre system, naming the bottleneck behind each step and its price
  • Pick relational or non-relational storage for each kind of data using concrete access-pattern signals
  • Size a web tier from daily users to servers with the calculator, including headroom and spares
  • Explain what happens when a replica, the primary, a cache node or a whole data centre fails, and what limits the damage
  • Choose a sharding key, and explain resharding, the celebrity problem and why joins get de-normalised

The journey in one picture

▶ Video lesson: The growth story: from one server to millions 6:14 · 10 scenes · narrated, pause anytime and explore

Pantry is a recipe site. People browse recipes, save favourites and post their own with photos. On launch day it has three users (you and two friends) and runs on one rented machine.

This chapter replays Pantry's growth to millions of users. There is no big redesign anywhere in the story. Each step is a small addition that removes one bottleneck you can name, and each addition has a price: more money, more moving parts, or a new way to fail. Bottleneck, fix, price is the pattern an interviewer wants to hear when they say "make this scale".

Click through the picture once to see the whole arc. The sections after it take each addition apart.

Pantry grows: one component per step

The picture is rebuilt at every step: boxes and arrows appear, and occasionally an old arrow is replaced. Green marks what was just added, red marks the pain. The user counts are illustrative; your own thresholds will differ.

Ask before you add anything

Open with the questions that decide how far down this list you need to go:

  • How many users are there today, and how fast is that growing?
  • What is the read-to-write ratio?
  • Which requests must be fast, and which can finish later?
  • What does ten minutes of downtime cost?
  • Is the traffic in one region or worldwide?

An internal tool with 500 users stops after the second step. A consumer product with a global audience walks the whole list.

One server, then a separate database

With one machine, a page view takes four hops. The browser asks DNS for the machine's IP address, DNS answers, the browser sends an HTTP request to that address, and the server replies. A website gets HTML to render. A mobile app calls the same server and gets JSON instead. DNS is a service you rent from your registrar or a cloud provider, not something you run.

sequenceDiagram
  participant B as Browser or app
  participant D as DNS
  participant S as The one server
  B->>D: Where is pantry.example?
  D-->>B: 203.0.113.7
  B->>S: GET /recipes/lasagna
  S-->>B: HTML page or JSON
Everything after the third arrow happens inside one machine: the app, its database and its files.

The first split is almost always to move the database onto its own machine. The two parts want different things. Web code burns CPU and holds nothing you cannot rebuild; a database wants memory, fast disks and careful backups. On one box they starve each other, and a memory leak in the app takes the data down with it. Apart, each tier is sized and scaled on its own terms, and the web tier becomes something you can restart or replace at will.

Relational, or something else?

Decide per kind of data, not per company. Relational databases (MySQL, PostgreSQL) store rows in tables, join them, run transactions and answer questions you have not thought of yet. Pantry's users, recipes, favourites and comments refer to each other, so they start here, and for most products that is also where they stay. Non-relational stores (key-value, document, wide-column, graph) give up some of that flexibility in exchange for something else, usually scale-out, latency or a looser schema. Reach for one because of a named access pattern ("sessions are fetched by key 5,000 times a second"), not because it sounds modern. Step through the decision below; the long version is in Databases: SQL vs NoSQL.

flowchart TD
  Q{What does the data look like?}
  REL[(Relational)]
  KV[(Key-value)]
  DOC[(Document)]
  COL[(Wide-column)]
  OBJ[(Object storage)]
  Q -->|related rows, joins, transactions| REL
  Q -->|fetch by key, huge rate, tiny latency| KV
  Q -->|self-contained records, shape changes often| DOC
  Q -->|endless appends, queried by key and time| COL
  Q -->|big files such as photos and video| OBJ
Start from the shape of the data and how you read it, then pick the store. One product usually uses several.

Scale up or scale out? Add a load balancer

When one web server runs hot there are two ways to add capacity. Vertical scaling (scale up) means a bigger machine. Horizontal scaling (scale out) means more machines doing the same job.

Two ways to add web capacity

Scale up: a bigger machine

  • Good: no code change and no coordination. Often the right first move, and for a database it can be the right move for a long time.
  • Limits: there is a largest machine you can rent; near the top, price grows faster than capacity.
  • Failure: one machine is one failure. Resizing usually needs a restart.

Scale out: more machines

  • Good: capacity grows by adding cheap machines, with no practical ceiling. Losing one costs a fraction of capacity.
  • Needs: a load balancer in front, and servers that are interchangeable.
  • Cost: more machines to deploy, monitor and patch.

Scaling out needs a load balancer. It owns the public address and DNS points at it, so users never reach a web server directly. It forwards each request to one of the web servers over the private network, and it stops sending traffic to any server that fails its health check. Lose one of three web servers and the site loses a third of its capacity, not the site. The algorithms (round robin, least connections) and Layer 4 versus Layer 7 are in Load balancers, reverse proxies & API gateways.

The balancer is now the one thing every request depends on, so it runs as a redundant pair; managed cloud balancers already do. Scaling out also quietly assumes the servers are interchangeable. Pantry's are not yet, which the stateless-tier section fixes.

How many web servers do we need?

Peak traffic divided by what one server can safely do, rounded up, plus spares. Safe capacity sits below the maximum on purpose: spikes and failed servers need room. Say the formula out loud in an interview; the exact figures matter less. 2 · Back-of-the-envelope estimation covers the numbers worth memorising.

Database replication and failover

Most apps read far more than they write: Pantry sees roughly 50 recipe views for every recipe saved. So split the database by job. One primary accepts every write and records it in a change log. Replicas copy that log and serve reads. More replicas means more read capacity, and the data now lives on several machines instead of one.

Replication is usually asynchronous: the primary confirms a write once it is on its own disk and ships it to the replicas a moment later. Replicas normally trail by milliseconds, and by seconds when they are busy, so a read from a replica can briefly show old data. A semi-synchronous setup makes the primary wait for one replica before confirming, which closes the gap at the price of slower writes.

Run the timeline below. A monitor pings every database once a second, and three misses in a row mean "dead": one lost packet should not trigger a failover.

What happens when the primary, or the replicas, die

Switch scenarios to kill the primary, one replica, or every replica. Watch which lanes keep working, how long the monitor needs to notice, and what is lost.

What failsWhat users seeWhat limits the damage
One replicaNothing; reads shift to the othersSeveral replicas; the pool drops the dead one; a replacement copies a snapshot and catches up from the log
Every replicaSlower pages; the primary now serves reads tooA cache in front; spare replicas; alerts on pool size and replication lag
The primaryWrites fail for seconds to minutes; reads still workHealth checks, automatic promotion of the most complete replica, retries in the application
The old primary returnsPossibly two machines accepting writes (split brain)Fence it off, then let it rejoin as a replica; never promote it back automatically

Replication adds copies and failure modes together. The asynchronous gap (acknowledged but not yet copied) is the one to name in an interview; Consistency models & the CAP theorem explains the trade-off behind it.

Caching: the cache tier and the CDN

▶ Video lesson: Caching and the CDN 4:38 · 9 scenes · narrated, pause anytime and explore

A cache keeps the answer to a question you ask often, in memory, so the next asker does not make the database do the work again. It pays off when data is read far more than it changes and the same keys come up repeatedly. Pantry's "popular this week" page is the textbook case: identical for every visitor, rebuilt rarely, requested all day.

The flow is short. The web server asks the cache first. On a hit it replies at once. On a miss it reads a replica, stores the result in the cache with a time-to-live (TTL), and then replies. (Many texts call this read-through caching. Because the web server itself does the fetching and the filling, Caching calls it cache-aside, and goes deeper on patterns and failure modes.)

flowchart LR
  W[Web servers]
  C[Cache]
  R[(Replicas)]
  P[(Primary)]
  W -->|1 ask the cache| C
  W -->|2 on a miss, read| R
  W -->|3 writes| P
  P -->|4 change log| R
Reads try the cache, then a replica. Writes only ever go to the primary.

A page view with and without a cache

Twelve page views for two recipes over 47 seconds. Compare no cache, a cache whose entries live 30 seconds, and a cache whose only node crashes halfway.

What does a cache save on the database?

Start from the peak of about 2,800 page views per second that the web-tier estimate produced. Change the hit ratio and watch how many database servers the reads need. Writes are small by comparison, which is why the first fixes for a busy database are almost always about reads.

Five decisions when you add a cache

When is a cache worth it?

When data is read far more often than it changes and the same keys repeat. Poor fits: data that must be exact every time (an account balance) and keys read only once. If few reads repeat, the hit ratio stays low and the cache is mostly overhead.

Expiry

Give every entry a TTL. Too short and the cache keeps missing; too long and users see stale recipes. Add a little random jitter so a batch of entries filled together does not expire together.

Eviction

Memory is finite. When the cache is full it must drop something. LRU (least recently used) is the usual default; LFU (least frequently used) and FIFO are alternatives. Details in Caching.

Consistency

Updating the database and updating the cache are two separate operations, so they can disagree. On a write, delete the cached key instead of writing the new value, and let the next read reload it; the TTL is the safety net. Across data centres this is harder, because a delete in one site does not reach the other instantly.

Single point of failure

One cache node is one point of failure, and a restart leaves it empty, so the database suddenly takes every read (run the crash scenario above). Run several nodes, ideally in different failure zones. Leave spare memory so they do not evict constantly. Make the web tier treat any cache error as a miss, never as a failure.

A content delivery network is a cache somebody else runs, in dozens or hundreds of edge locations near your users. Photos, CSS and JavaScript are the same for everyone, so they suit it perfectly: a hit never reaches Pantry's servers, and the bytes travel a short distance instead of a long one. Decide four things:

  • What to put there. Public static files and video segments. Not personalised pages, and not rarely requested files, because you pay for what the CDN stores and transfers.
  • How long. The origin sends Cache-Control: max-age=.... A longer TTL means more hits and more staleness.
  • How to change a file early. Version the file name (best), purge by path (emergencies), or wait for the TTL.
  • What if the CDN is down. Clients should be able to fall back to the origin, and the origin must be able to absorb the extra load. Deep dive: Object storage (S3) & CDNs.
sequenceDiagram
  participant A as Asha in Pune
  participant E as CDN edge in Mumbai
  participant O as Origin
  participant B as Ben in Pune
  A->>E: GET /img/lasagna.jpg
  E->>O: not cached, fetch it
  O-->>E: file plus Cache-Control max-age 86400
  E-->>A: file, now stored at the edge
  B->>E: GET /img/lasagna.jpg
  E-->>B: file from the edge, origin not contacted
The first visitor in a region pays for the trip to the origin. Everyone after, until the TTL runs out, is served locally.

Changing a file the CDN already holds

Send a TTL with the file and accept up to that much staleness. Fine for files that rarely change and never need to change at a precise moment.

# Response headers the origin sends with a static file
headers = {
    "Cache-Control": "public, max-age=86400",   # edges and browsers may reuse the file for 24 hours
    "ETag": '"3f9a2c"',                          # lets a cache ask "has this changed?" cheaply
}

Put a fingerprint of the content in the file name. A changed file has a new name, so nothing needs purging and old copies simply stop being requested. Browsers get the new file too. Pair it with a very long TTL.

import hashlib

def fingerprinted(name: str, content: bytes) -> str:
    """app.js plus its bytes becomes app.<hash of the bytes>.js"""
    digest = hashlib.sha256(content).hexdigest()[:8]
    stem, _, ext = name.rpartition(".")
    return f"{stem}.{digest}.{ext}"

print(fingerprinted("app.js", b"console.log('v1')"))
print(fingerprinted("app.js", b"console.log('v2')"))   # different bytes, different URL: no purge needed

Every CDN has an API that removes a path from all its edges. Use it for emergencies (a wrong image, a legal takedown), not for routine deploys. Purges take seconds to minutes to spread, some providers rate-limit or charge for them, and they do nothing to copies already sitting in browsers.

A stateless web tier, then more than one data centre

A web server is stateful when it remembers something about a user between requests: a login session in its memory, a half-finished upload on its disk. That works with one server. With three behind a load balancer it fails at random: the second request lands on a server that has never heard of the user, and they are logged out.

There are two fixes. Sticky sessions make the balancer pin each user to one server. A shared session store moves the state out of the servers into a fast store they all read; sessions are looked up by key, which is the textbook non-relational case.

sequenceDiagram
  participant U as User
  participant L as Load balancer
  participant A as Web server A
  participant B as Web server B
  participant S as Session store
  U->>L: POST /login
  L->>A: forward to A
  A->>S: save session s81 for user 42
  A-->>U: 200 with cookie s81
  U->>L: GET /favourites with cookie s81
  L->>B: forward to B this time
  B->>S: load session s81
  S-->>B: user 42
  B-->>U: favourites of user 42
The cookie carries only a session id. Whichever server receives the next request finds the user in the shared store.

Keeping the user logged in

Sticky sessions

  • The balancer remembers which server each user belongs to and always routes them there.
  • Quick to switch on, with no change to the application.
  • But the balancer now holds state, load drifts to uneven, and when that server dies or is scaled in, its users are logged out. Deploys must drain servers one by one.

Shared session store

  • Sessions live in a fast store all web servers read; the cookie carries only an id.
  • Any server serves any request, the balancer can use any algorithm, and servers can be killed at will.
  • Costs one more component to run (replicate it) and an extra lookup, around a millisecond, per request.

Once no web server holds anything that cannot be rebuilt, the tier is stateless, and a lot gets easier. Capacity follows load automatically: an autoscaler adds servers when average CPU stays above, say, 60% and removes them when traffic falls. A bad server is killed and replaced, not repaired. A release rolls out one server at a time.

Everything so far sits in one data centre, which leaves two problems. Users far away wait for every round trip (from India to a data centre in the US, a round trip is typically 200 ms or more, and a page needs several), and a power, network or cooling failure takes the whole site down. The fix is a second data centre running the same stack, with geo-DNS answering each lookup with the address of the closest one. If a data centre fails, DNS stops returning it and the others absorb its traffic, which they must have spare capacity for.

Three things get hard:

  • How fast failover is. DNS answers are cached for their TTL, so users keep going to a dead site until the old answers expire, unless the TTL is short.
  • Keeping the data in step. Each data centre has its own database and cache. A user may be routed to a different site over time, so data has to be replicated across the distance, and some of it is allowed to be slightly stale.
  • One release, many sites. The same build and configuration must reach every site, and be tested from each.
flowchart TD
  U[Users]
  G[Geo DNS]
  A[Data centre A]
  B[Data centre B]
  U -->|1 look up the site| G
  G -->|2 nearest answer| A
  G -->|2 nearest answer| B
  A <-->|async data sync| B
Normal day: each user reaches the nearest site. Failure: DNS stops answering with the dead site, and the survivor takes everything.

Message queues, logging, metrics and automation

Some work is slow and does not have to finish before the user gets an answer: importing a recipe from another website (fetch the page, parse the ingredients, tidy the text), emailing a chef's followers, rebuilding a recommendation list. If the web server does it inline, requests pile up behind it and a burst of imports takes the site down.

A message queue splits the job in two. The web server (the producer) writes a small message, such as "import recipe from link 9231", to the queue and replies at once. Workers (the consumers) pull messages at their own pace. They only share the queue, so each side can be scaled, or can fail, on its own: if workers stop, messages wait instead of vanishing, and if a burst arrives the queue absorbs it. The queue's length tells you how many workers you need. Delivery guarantees, retries and dead-letter queues are in Message queues & streaming (Kafka).

flowchart LR
  W[Web server]
  Q{{Message queue}}
  K1[Worker 1]
  K2[Worker 2]
  S[(Recipe database)]
  W -->|1 enqueue job| Q
  Q -->|2 pull| K1
  Q -->|2 pull| K2
  K1 -->|3 save the recipe| S
  K2 -->|3 save the recipe| S
The web server's part ends at the queue. Everything slower happens on the other side of it.

Sharding the database

▶ Video lesson: Sharding the database 3:44 · 7 scenes · narrated, pause anytime and explore

Replicas multiply reads, but every write still lands on one primary, and that one machine holds every row. A bigger primary buys time and then runs out: there is a largest machine, the price per unit of capacity climbs near the top, and it is still one machine to lose. The next step is sharding: split the rows over several databases (shards) with the same schema, and let a small routing layer pick the shard from a sharding key.

Pantry's key is the user id and the rule is shard = user_id mod 3. Each shard keeps its own replicas, so everything in the replication section still applies per shard. Run the three scenarios below: the easy case, the one that hurts, and the cost of adding a shard.

Routing users to shards

Three shards, rule user_id mod 3. Compare an even spread of sign-ups, a celebrity whose traffic makes one shard hot, and adding a fourth shard.

Choosing the sharding key

Keys that cause trouble

  • created_at (or any ever-growing id): each new row has a larger key than every earlier one, so with range sharding all new writes hit the newest shard.
  • country: a handful of values and very uneven sizes. One shard ends up holding a third of the world.
  • recipe_id: spreads rows well, but one user's favourites, comments and uploads end up on every shard, so a profile page fans out to all of them.

A key that works: user_id

  • High cardinality, so rows spread evenly.
  • Everything a user owns lands on one shard, so most requests touch exactly one.
  • Known on every request, so routing needs no lookup.
  • Not perfect: busy users weigh more than quiet ones (the celebrity problem below).

Sharding trades capacity for three new problems. Name all three in an interview.

  • Resharding. Under plain mod, going from 3 to 4 shards sends about 75% of the rows somewhere new (the third scenario shows 9 of 12). Real systems avoid it with consistent hashing, which moves only about one row in four, or with many small virtual shards that move between machines whole. 5 · Design consistent hashing builds the idea.
  • The celebrity problem. An even spread of rows is not an even spread of traffic. One chef with millions of followers makes one shard the busiest by far (second scenario). Cache the hot data, and if that is not enough, give the key its own shard or split it across several.
  • Joins across shards. A query that joins data on shard 1 with data on shard 3 becomes several queries and a merge in application code. The usual answer is to de-normalise: copy the few fields you need next to the data that reads them.

Shard last

Before you shard, check that the cheaper moves are used up: indexes and query fixes, a cache, read replicas and a bigger primary. Each is easier to adopt and far easier to undo. Sharding changes how every query is routed, so it is the last lever to pull, and interviewers expect you to approach it with caution.

De-normalising a favourites page

A user's favourites live on the user's shard, but each recipe lives on its author's shard. Listing twenty favourites means twenty extra queries on other shards.

def favourites_page(user_id: int) -> list[dict]:
    rows = shard_for(user_id).query(
        "SELECT recipe_id, author_id FROM favourites WHERE user_id = %s", user_id)
    page = []
    for row in rows:                      # one extra query per favourite, and each runs on another shard
        recipe = shard_for(row["author_id"]).query_one(
            "SELECT title, photo FROM recipes WHERE id = %s", row["recipe_id"])
        page.append(recipe)
    return page

Copy the title and photo into the favourite when it is saved. The page is now one query on one shard. The price is stale copies when a recipe is edited, which a background job has to repair.

def save_favourite(user_id: int, recipe: dict) -> None:
    # copy what the favourites page needs, so reading it touches one shard
    shard_for(user_id).execute(
        "INSERT INTO favourites (user_id, recipe_id, title, photo) VALUES (%s, %s, %s, %s)",
        user_id, recipe["id"], recipe["title"], recipe["photo"])

def favourites_page(user_id: int) -> list[dict]:
    return shard_for(user_id).query(
        "SELECT recipe_id, title, photo FROM favourites WHERE user_id = %s", user_id)

# The price: when an author renames a recipe, the copies are stale until a background job refreshes them.

Follow-up questions to expect

The load balancer is a single point of failure. Now what?

Run two or more, in different failure zones, behind one virtual address, or let a managed balancer do it. DNS health checks can stop returning an unhealthy balancer.

A user saves a recipe and the next page does not show it. Why?

They read from a replica that has not applied the write yet (asynchronous replication lag). Read a user's own recent data from the primary for a short window, or carry the log position of their write and wait for a replica to reach it. See Scaling databases: replication, sharding, partitioning.

The cache and the database disagree. What do you do?

Delete the cached key on every write (do not set it), keep a TTL as the backstop, and accept that a reader who fetched just before the write can re-fill the old value for up to one TTL. See Caching.

Traffic doubles in a minute. What absorbs it?

The CDN takes the static share. The stateless web tier autoscales, but new servers take minutes to start, so keep headroom. The cache takes repeated reads. The queue turns a burst of slow work into a backlog. Rate limiting protects what remains. See Reliability patterns.

What gets harder with two data centres?

Consistency across the distance. Replication between sites is asynchronous, so a user routed to the other site can briefly see old data, and conflicting writes need a rule. See Consistency models & the CAP theorem.

What would you build next?

Split the application into services owned by separate teams, add a search index, put rate limiting at the edge, and copy events into a warehouse for analytics.

A 60-second answer

'I would start with one server and say what breaks first. I would split the database off and keep it relational unless an access pattern says otherwise. I would scale the web tier out behind a load balancer, which means making it stateless by moving sessions to a shared store. Reads dominate, so I would add replicas and a cache in front of them, and put static files on a CDN. Slow work goes on a message queue with workers sized by queue length. Past one data centre I would add geo-DNS and replicate the data. Past one primary I would shard by user id and accept the costs: resharding, hot users and de-normalised data. Throughout I would watch logs, metrics and alerts, and automate deploys.'
