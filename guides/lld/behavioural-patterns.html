Behavioural patterns

Six behavioural patterns, each as intent, class diagram, runnable Python and the Pythonic shortcut: Strategy, Observer, Command, State, Template Method (with Chain of Responsibility) and Iterator. You will watch strategies swap at runtime, an event bus deliver synchronously and asynchronously, undo and redo stacks move commands around, and a vending machine change behaviour with its state. Just as important, you will learn when a plain function, an Enum or a generator makes the pattern unnecessary.

After this chapter you can
  • Pick the behavioural pattern from the force you face (what varies?) and name the Pythonic shortcut when one exists
  • Swap strategies at runtime and say when a plain function replaces a class hierarchy
  • Build an event bus that survives a failing subscriber and explain sync vs async delivery trade-offs
  • Implement undo and redo with command objects and two stacks, and say what a command must remember to be undoable
  • Model a lifecycle with State objects or an Enum plus a table, and tell State apart from Strategy
  • Use generators for lazy iteration and explain iterable vs iterator

What behavioural patterns are for

Creational patterns decide how objects get made, structural patterns decide how they are wired together, and behavioural patterns decide who does what at runtime and how the parts talk to each other. They are the ones interviewers reach for most. "Design a notification system", "design a vending machine" and "design a text editor with undo" are all behavioural problems in disguise.

You are almost never asked to recite a pattern. You are asked to design something, and the follow-up is "now add one more X". The pattern is the answer to what varies, so start from that question and let the map below point at the pattern.

Start from the thing that changes. Step through for one example of each force.

Python changes the economics. Functions are objects, so a one-method strategy is a function. An Enum and a dict give you a state machine in ten lines. Generators are the iterator pattern built into the language. Each pattern below is shown in its textbook shape, then in the form you would write in Python, with the signal that tells you when the shortcut is enough. SOLID principles explains why these shapes are good (open/closed, dependency inversion); here we use them.

What the interviewer is really asking: can you see the change coming and isolate it? A strong opening is: 'The part that will keep changing is the discount rule, so I'll put it behind an interface and keep Checkout stable.' Name the pattern after you have shown the shape, not before. Then be ready to say when a plain function or an if is enough. That is the senior signal.

Strategy: swap the algorithm

▶ Video lesson: Strategy: swap the algorithm, not the caller 4:24 · 7 scenes · narrated, pause anytime and explore

Intent: put each variant of an algorithm behind one interface, so the code that uses the algorithm never branches on which variant it got.

A checkout applies a discount. Today it is "10% off", next quarter it is "20% off lines with 10 or more units", then a loyalty tier. If Checkout.total() contains the rules, every promotion edits it and can break the others. With a strategy, Checkout holds a reference to a discount rule and calls it. A new promotion is a new class or function; Checkout is not edited.

Branching on a flag vs injecting the behaviour

Every promotion edits total()

class Checkout:
    def total(self, items, promo):
        subtotal = sum(q * p for _, q, p in items)
        if promo == "PCT10":
            return subtotal * 0.9
        elif promo == "BULK":
            return sum(q * p * (0.8 if q >= 10 else 1) for _, q, p in items)
        elif promo == "FLAT5":
            return max(subtotal - 5, 0)
        return subtotal

Checkout calls whatever it was given

class Checkout:
    def __init__(self, discount):        # any callable: items -> amount off
        self.discount = discount

    def total(self, items):
        subtotal = sum(q * p for _, q, p in items)
        return round(subtotal - self.discount(items), 2)

# a new promotion is a new function; Checkout is not edited
checkout = Checkout(discount=lambda items: 5.0)

Swap strategies on a live Checkout

The same Checkout prices the same cart four times. Only the strategy object behind its discount field changes. Switch to the big basket to see the bulk rule start to matter.

Three spellings of the same pattern

Use classes when a strategy carries configuration or needs several methods. A frozen dataclass gives you equality and a readable repr for free.

from abc import ABC, abstractmethod
from dataclasses import dataclass

class DiscountStrategy(ABC):
    @abstractmethod
    def discount(self, items) -> float: ...          # amount to subtract from the subtotal

@dataclass(frozen=True)
class PercentOff(DiscountStrategy):
    pct: float
    def discount(self, items):
        return sum(q * p for _, q, p in items) * self.pct / 100

@dataclass(frozen=True)
class BulkDiscount(DiscountStrategy):
    min_qty: int
    pct: float
    def discount(self, items):
        return sum(q * p * self.pct / 100 for _, q, p in items if q >= self.min_qty)

class Checkout:
    def __init__(self, strategy: DiscountStrategy):
        self.strategy = strategy
    def total(self, items):
        subtotal = sum(q * p for _, q, p in items)
        return round(subtotal - self.strategy.discount(items), 2)

cart = [("book", 2, 12.0), ("pen", 10, 1.5)]
checkout = Checkout(PercentOff(10))
print(checkout.total(cart))                  # 35.1
checkout.strategy = BulkDiscount(10, 20)     # swap at runtime
print(checkout.total(cart))                  # 36.0

A strategy with one method and a bit of configuration is a function, and closures carry the configuration. This is the idiomatic default in Python.

from typing import Callable, Sequence

Item = tuple[str, int, float]                       # (sku, quantity, unit price)
Discount = Callable[[Sequence[Item]], float]        # a strategy: items -> amount off

def percent_off(pct: float) -> Discount:
    return lambda items: sum(q * p for _, q, p in items) * pct / 100

def bulk(min_qty: int, pct: float) -> Discount:
    return lambda items: sum(q * p * pct / 100 for _, q, p in items if q >= min_qty)

class Checkout:
    def __init__(self, discount: Discount = lambda items: 0.0):
        self.discount = discount
    def total(self, items):
        subtotal = sum(q * p for _, q, p in items)
        return round(subtotal - self.discount(items), 2)

cart = [("book", 2, 12.0), ("pen", 10, 1.5)]
checkout = Checkout()
print(checkout.total(cart))                  # 39.0
checkout.discount = percent_off(10)
print(checkout.total(cart))                  # 35.1
checkout.discount = bulk(10, 20)
print(checkout.total(cart))                  # 36.0

The 'which strategy?' decision still has to live somewhere. A lookup table keeps it in one place and turns a config value into behaviour.

from typing import Callable

Items = list[tuple[str, int, float]]
Discount = Callable[[Items], float]

def percent_off(pct: float) -> Discount:
    return lambda items: sum(q * p for _, q, p in items) * pct / 100

DISCOUNTS: dict[str, Discount] = {
    "none": lambda items: 0.0,
    "member": percent_off(10),
    "welcome": lambda items: 5.0,
}

def checkout_total(items: Items, plan: str) -> float:
    discount = DISCOUNTS.get(plan, DISCOUNTS["none"])     # unknown plan: no discount, not a crash
    return round(sum(q * p for _, q, p in items) - discount(items), 2)

cart = [("book", 2, 12.0), ("pen", 10, 1.5)]
for plan in ("none", "member", "welcome", "vip"):
    print(plan, checkout_total(cart, plan))      # 39.0, 35.1, 34.0, 39.0

When not to use it

  • One algorithm, no sign of a second. Write the function. When the second variant arrives you will know what the two really have in common, and the extraction is a ten-minute refactor.
  • Two branches on a config flag. An if is easier to read than an interface with two implementations.
  • The strategy needs the context's internals. If every strategy reaches into Checkout for more data, the interface is wrong. Pass the data the strategy needs as arguments instead.
  • Python already has the hook. sorted(key=...), max(key=...), functools.partial and a dict of callables are strategies you use daily.

Say: 'Discounts are a strategy: Checkout holds a Discount callable and the pricing rules live in small functions or classes behind it. A new promotion means adding one, not editing Checkout, which is the open/closed principle. I would keep it a plain callable until a rule needs state or several methods, then promote it to a class.' Interviewers follow up with 'how does the right strategy get chosen?': a lookup keyed by customer plan or promotion code, built once at start-up.

Observer: tell everyone who cares

▶ Video lesson: Observer: one event, many reactions 4:05 · 7 scenes · narrated, pause anytime and explore

Intent: let one object announce that something happened without knowing who reacts. Subscribers register interest; the publisher loops over them.

Two flavours get named interchangeably. In the textbook Observer, the object that changes (the subject) keeps its own list of observers. In publish/subscribe, a broker sits in the middle and publishers and subscribers never meet. Interviewers use both words loosely, so say which shape you mean. Here it is a small in-process event bus with topics, which is what most LLD answers need.

The same publish(), naive and safe

Naive loop

def publish(self, topic, payload):
    for handler in self._subs[topic]:      # list may change while we loop
        handler(payload)                    # one exception stops everyone after it

Copy, isolate, log

def publish(self, topic, payload):
    for handler in list(self._subs[topic]):          # iterate over a copy
        try:
            handler(payload)
        except Exception:
            logging.exception("subscriber %r failed on %s", handler, topic)

Three event buses

The version to write in an interview. subscribe returns an unsubscribe handle so callers never need to hold on to the handler just to remove it.

import logging
from collections import defaultdict
from typing import Any, Callable

Handler = Callable[[dict[str, Any]], None]

class EventBus:
    def __init__(self) -> None:
        self._subs: dict[str, list[Handler]] = defaultdict(list)

    def subscribe(self, topic: str, handler: Handler) -> Callable[[], None]:
        self._subs[topic].append(handler)
        return lambda: self._subs[topic].remove(handler)      # call it to unsubscribe

    def publish(self, topic: str, payload: dict[str, Any]) -> None:
        for handler in list(self._subs[topic]):              # copy: a handler may unsubscribe itself
            try:
                handler(payload)
            except Exception:
                logging.exception("subscriber %r failed on %s", handler, topic)

bus = EventBus()
sent = []
bus.subscribe("order.placed", lambda e: sent.append(f"email {e['id']}"))
unsubscribe = bus.subscribe("order.placed", lambda e: sent.append(f"stock {e['id']}"))
bus.publish("order.placed", {"id": 1})
unsubscribe()
bus.publish("order.placed", {"id": 2})
print(sent)       # ['email 1', 'stock 1', 'email 2']

A thread pool takes the handlers off the publisher's thread. publish returns at once; close() waits for in-flight handlers (needed in scripts and tests).

import logging
import time
from collections import defaultdict
from concurrent.futures import ThreadPoolExecutor

class AsyncBus:
    def __init__(self, workers: int = 4):
        self._subs = defaultdict(list)
        self._pool = ThreadPoolExecutor(max_workers=workers)

    def subscribe(self, topic, handler):
        self._subs[topic].append(handler)

    def publish(self, topic, payload):
        for handler in list(self._subs[topic]):
            self._pool.submit(self._run, handler, payload)     # returns immediately

    @staticmethod
    def _run(handler, payload):
        try:
            handler(payload)
        except Exception:
            logging.exception("subscriber failed")             # the publisher will never see this

    def close(self):
        self._pool.shutdown(wait=True)

bus = AsyncBus()
done = []
bus.subscribe("order.placed", lambda e: (time.sleep(0.05), done.append("email")))
bus.subscribe("order.placed", lambda e: done.append("analytics"))
bus.publish("order.placed", {"id": 1})
bus.close()
print(sorted(done))       # ['analytics', 'email']

A bus that stores bound methods keeps their objects alive forever. WeakMethod lets the subscriber be garbage-collected, and the bus prunes dead entries as it goes.

import weakref

class WeakBus:
    def __init__(self):
        self._subs = {}                                   # topic -> list of weak references

    def subscribe(self, topic, bound_method):
        self._subs.setdefault(topic, []).append(weakref.WeakMethod(bound_method))

    def publish(self, topic, payload):
        live = []
        for ref in self._subs.get(topic, []):
            handler = ref()                               # None once the owner object was freed
            if handler is not None:
                live.append(ref)
                handler(payload)
        self._subs[topic] = live                          # prune the dead ones

class Widget:
    def on_event(self, payload):
        print("widget got", payload)

bus, widget = WeakBus(), Widget()
bus.subscribe("tick", widget.on_event)
bus.publish("tick", 1)       # widget got 1
del widget                   # last reference gone: CPython frees it at once
bus.publish("tick", 2)       # prints nothing, and the bus did not keep the widget alive

Pitfalls that come up in review

  • A failing subscriber breaks the publisher. Isolate every call (try/except plus a log line), or deliver asynchronously.
  • Mutation during iteration. A handler that unsubscribes itself, or subscribes another handler, changes the list the publisher is looping over. Iterate over a copy.
  • Leaks. The bus holds strong references, so a subscriber that never unsubscribes is never freed. Return an unsubscribe handle or hold bound methods weakly.
  • Hidden ordering. Do not rely on subscription order. If handler B needs handler A's result they are not independent observers; call them in sequence explicitly.
  • Re-entrancy. A handler that publishes the topic it is handling can recurse forever.
  • Threads. An async bus needs a lock (or a copy-on-write list) around subscribe and unsubscribe.

When not to use it

  • There is exactly one listener. Call it directly. An event bus with one subscriber is indirection with no payoff and makes the control flow harder to follow.
  • The publisher needs the answer. Observers return nothing useful. If you need a result (a price, a yes/no authorisation), that is a call, or a strategy.
  • Events must not be lost. In-memory delivery dies with the process. Use a durable queue and make handlers idempotent, because most brokers deliver at least once.

Say: 'Order placement publishes order.placed. Inventory, email and analytics subscribe, so a fourth reaction never touches the order code. In process I would isolate failures per subscriber and deliver synchronously when the work is cheap; for slow or cross-service reactions I would publish to a queue so delivery is durable and retried.' Expect follow-ups on ordering (do not depend on it), leaks (unsubscribe, weak references), a slow subscriber (async or queue) and duplicates (make handlers idempotent).

Command: requests as objects (undo and redo)

▶ Video lesson: Command: undo and redo with two stacks 4:27 · 7 scenes · narrated, pause anytime and explore

Intent: wrap a request in an object so it can be stored, passed around, queued, logged and, when it has an inverse, undone.

The moment a feature says "undo", a plain method call is not enough: doc.insert(...) leaves no record of what happened. A command object is that record. It carries what it needs to do the job (do()) and what it needs to reverse it (undo()). History then becomes two stacks: commands you can undo, and commands you have undone and could redo.

Undo and redo with two stacks

Follow one command at a time. execute pushes on the undo stack, undo moves the top command to the redo stack, redo moves it back. Watch what a brand-new edit does to the redo stack.

Command in Python

The full shape. DeleteText captures what it removes inside do(), so redo and undo always agree with what actually happened.

from abc import ABC, abstractmethod

class Command(ABC):
    @abstractmethod
    def do(self) -> None: ...
    @abstractmethod
    def undo(self) -> None: ...

class Document:
    def __init__(self, text: str = ""):
        self.text = text

class InsertText(Command):
    def __init__(self, doc: Document, pos: int, text: str):
        self.doc, self.pos, self.text = doc, pos, text
    def do(self):
        d = self.doc
        d.text = d.text[:self.pos] + self.text + d.text[self.pos:]
    def undo(self):
        d = self.doc
        d.text = d.text[:self.pos] + d.text[self.pos + len(self.text):]

class DeleteText(Command):
    def __init__(self, doc: Document, pos: int, n: int):
        self.doc, self.pos, self.n = doc, pos, n
        self.removed = ""                             # filled in by do(): undo needs it
    def do(self):
        d = self.doc
        self.removed = d.text[self.pos:self.pos + self.n]
        d.text = d.text[:self.pos] + d.text[self.pos + self.n:]
    def undo(self):
        d = self.doc
        d.text = d.text[:self.pos] + self.removed + d.text[self.pos:]

class History:
    def __init__(self):
        self._undo: list[Command] = []
        self._redo: list[Command] = []

    def execute(self, cmd: Command) -> None:
        cmd.do()
        self._undo.append(cmd)
        self._redo.clear()                            # a new edit invalidates the redo branch

    def undo(self) -> None:
        if self._undo:
            cmd = self._undo.pop()
            cmd.undo()
            self._redo.append(cmd)

    def redo(self) -> None:
        if self._redo:
            cmd = self._redo.pop()
            cmd.do()
            self._undo.append(cmd)

doc, history = Document(), History()
history.execute(InsertText(doc, 0, "Hello"))
history.execute(InsertText(doc, 5, " World"))
history.execute(DeleteText(doc, 0, 6))
print(repr(doc.text))     # 'World'
history.undo()
history.undo()
print(repr(doc.text))     # 'Hello'
history.redo()
print(repr(doc.text))     # 'Hello World'

For small cases a command is just a (do, undo) pair of callables. Closures capture the arguments, so there is no class to write.

doc = {"text": ""}

def insert(pos, s):
    def do():
        doc["text"] = doc["text"][:pos] + s + doc["text"][pos:]
    def undo():
        doc["text"] = doc["text"][:pos] + doc["text"][pos + len(s):]
    return do, undo

class History:
    def __init__(self):
        self._undo, self._redo = [], []
    def run(self, do, undo):
        do()
        self._undo.append((do, undo))
        self._redo.clear()
    def undo(self):
        if self._undo:
            do, undo = self._undo.pop()
            undo()
            self._redo.append((do, undo))
    def redo(self):
        if self._redo:
            do, undo = self._redo.pop()
            do()
            self._undo.append((do, undo))

history = History()
history.run(*insert(0, "Hello"))
history.run(*insert(5, "!"))
print(doc["text"])        # Hello!
history.undo()
print(doc["text"])        # Hello

A command can contain commands. Undo has to run the children in reverse order, or the positions they captured no longer match the text.

class Doc:
    def __init__(self, text=""):
        self.text = text

class Insert:
    def __init__(self, doc, pos, s):
        self.doc, self.pos, self.s = doc, pos, s
    def do(self):
        self.doc.text = self.doc.text[:self.pos] + self.s + self.doc.text[self.pos:]
    def undo(self):
        self.doc.text = self.doc.text[:self.pos] + self.doc.text[self.pos + len(self.s):]

class Macro:
    def __init__(self, *commands):
        self.commands = commands
    def do(self):
        for c in self.commands:
            c.do()
    def undo(self):
        for c in reversed(self.commands):             # last done, first undone
            c.undo()

doc = Doc()
wrap = Macro(Insert(doc, 0, "<b>"), Insert(doc, 3, "hi"), Insert(doc, 5, "</b>"))
wrap.do()
print(doc.text)           # <b>hi</b>
wrap.undo()
print(repr(doc.text))     # ''

Beyond undo

The same object shows up wherever a request has to outlive the call that made it:

  • Job queues. A Celery task is a command: a name plus arguments, serialised, run later and retried on failure.
  • Audit logs and event sourcing. Store the commands (or the events they produce) and rebuild state by replaying them.
  • GUI actions. A menu item, a toolbar button and a keyboard shortcut all trigger the same command object.
  • Macros. Record commands as they execute, replay them on demand.

When not to use it

  • No undo, queueing or logging is needed. A method call is a method call. Wrapping it in a class adds files and no capability.
  • State is small and snapshots are cheap. Saving a copy of the document before each edit (a memento) is simpler than writing an inverse for every operation. It stops being viable when the state is large or when edits are frequent.
  • History is unbounded. A long session grows the stacks forever. Cap them (collections.deque(maxlen=100)) and decide what 'oldest undo dropped' means for users.

Say: 'Each edit is a command with do and undo. A History holds an undo stack and a redo stack: executing a new command clears redo, undo pops and pushes onto redo, redo does the reverse. Commands capture whatever undo needs; delete stores the text it removed. I'd cap the history size, and typing a word should be one undo step, so consecutive inserts merge into one command.' Expect follow-ups on grouping, on operations that cannot be reversed, and on multi-user editing, which needs operational transforms or CRDTs and is a different conversation.

State: behaviour that follows the lifecycle

Intent: let an object change its behaviour when its internal state changes, by delegating each event to a state object instead of branching on a status field.

A vending machine answers insert_coin() differently when it is idle, when it already holds money, while it is dispensing and when it is sold out. Written as if self.status == ..., every method ends up with the same four-way ladder, and a new "out of service" state means editing all of them. The grid below is what that ladder encodes.

The if/elif ladder vs state objects

Status flag and a ladder per method

class VendingMachine:
    def insert_coin(self, cents):
        if self.status == "IDLE":
            self.credit += cents
            self.status = "HAS_MONEY"
        elif self.status == "HAS_MONEY":
            self.credit += cents
        else:                                  # DISPENSING or SOLD_OUT
            raise InvalidAction("not now")

    def select(self, item):
        if self.status == "HAS_MONEY":
            ...                                # check stock and price, then status = "DISPENSING"
        else:
            raise InvalidAction("not now")

    # refund(), item_dropped(), restock(): the same ladder again.
    # A fifth status means editing every method.

State in Python

The full machine. Run it: the busy rejection and the change returned both come from the state classes, with no if on a status anywhere.

class InvalidAction(Exception):
    pass

class VendingMachine:
    def __init__(self, prices: dict[str, int], stock: dict[str, int]):
        self.prices, self.stock = prices, dict(stock)
        self.credit = 0
        self.selected = None
        self.state: State = Idle() if any(stock.values()) else SoldOut()

    # The machine never branches on its state: it forwards every event to the current state object.
    def insert_coin(self, cents):   self.state.insert_coin(self, cents)
    def select(self, item):         self.state.select(self, item)
    def refund(self):               return self.state.refund(self)
    def item_dropped(self):         return self.state.item_dropped(self)
    def restock(self, item, qty):   self.state.restock(self, item, qty)

class State:
    # Default: the event is not allowed here. Each subclass overrides only what is legal.
    def _reject(self, event):
        raise InvalidAction(f"{event} is not allowed when {type(self).__name__}")
    def insert_coin(self, m, cents):  self._reject("insert_coin")
    def select(self, m, item):        self._reject("select")
    def refund(self, m):              self._reject("refund")
    def item_dropped(self, m):        self._reject("item_dropped")
    def restock(self, m, item, qty):  # legal everywhere, so the default accepts it
        m.stock[item] = m.stock.get(item, 0) + qty

class Idle(State):
    def insert_coin(self, m, cents):
        m.credit += cents
        m.state = HasMoney()                      # the transition lives in the class it leaves from

class HasMoney(State):
    def insert_coin(self, m, cents):
        m.credit += cents
    def select(self, m, item):
        if m.stock.get(item, 0) == 0:
            raise InvalidAction(f"{item} is out of stock")
        if m.credit < m.prices[item]:
            raise InvalidAction(f"{item} costs {m.prices[item]}, credit is {m.credit}")
        m.credit -= m.prices[item]
        m.stock[item] -= 1
        m.selected = item
        m.state = Dispensing()
    def refund(self, m):
        cents, m.credit = m.credit, 0
        m.state = Idle()
        return cents

class Dispensing(State):
    def item_dropped(self, m):                    # called by the hardware when the item has fallen
        change, m.credit, m.selected = m.credit, 0, None
        m.state = Idle() if any(m.stock.values()) else SoldOut()
        return change

class SoldOut(State):
    def restock(self, m, item, qty):
        super().restock(m, item, qty)
        m.state = Idle()

machine = VendingMachine({"cola": 150}, {"cola": 1})
machine.insert_coin(100)
machine.insert_coin(100)
machine.select("cola")                                  # credit 200 >= 150: Dispensing
try:
    machine.insert_coin(100)                            # busy
except InvalidAction as e:
    print(e)                                            # insert_coin is not allowed when Dispensing
print(machine.item_dropped(), type(machine.state).__name__)   # 50 SoldOut
machine.restock("cola", 3)
print(type(machine.state).__name__, machine.stock)     # Idle {'cola': 3}

When states differ only in which transitions are allowed, and not in what the events do, a table is lighter than classes.

from enum import Enum, auto

class InvalidAction(Exception):
    pass

class S(Enum):
    IDLE = auto()
    HAS_MONEY = auto()
    DISPENSING = auto()
    SOLD_OUT = auto()

TRANSITIONS = {
    (S.IDLE, "insert_coin"): S.HAS_MONEY,
    (S.HAS_MONEY, "refund"): S.IDLE,
    (S.HAS_MONEY, "select"): S.DISPENSING,
    (S.DISPENSING, "item_dropped"): S.IDLE,
    (S.SOLD_OUT, "restock"): S.IDLE,
}

def fire(state: S, event: str) -> S:
    try:
        return TRANSITIONS[(state, event)]
    except KeyError:
        raise InvalidAction(f"{event} not allowed in {state.name}") from None

s = fire(S.IDLE, "insert_coin")
print(s)                                     # S.HAS_MONEY
try:
    fire(s, "item_dropped")
except InvalidAction as e:
    print(e)                                 # item_dropped not allowed in HAS_MONEY

When not to use it

  • Two states and a boolean. is_open is clearer than an Open class and a Closed class.
  • States differ only in transitions. An Enum plus a transition dict (second tab) is shorter and easy to persist or print. Move to classes when each state needs real, different code for the same event.
  • Persistence. State objects with data are awkward to save. Store the state name and rebuild the object when loading.
  • Concurrency. A transition is read-modify-write. If events can arrive from several threads, serialise them with a lock or a queue (Concurrency & thread safety).

Say: 'An order has a lifecycle: created, paid, shipped, delivered, plus cancelled. cancel() means something different in each, so I'd use the State pattern: a base class that rejects every event by default, one subclass per state overriding only the legal events, and an order that forwards calls to its current state. The state performs the transition. If the lifecycle had no per-state behaviour I'd use an Enum and a transition table instead.' Follow-ups: how to add a Returned state (one class plus the arrows into it), how to persist it, and how to stop two threads from transitioning at once.

Template Method and Chain of Responsibility

Template Method

Intent: fix the order of an algorithm's steps in one place and let subclasses fill in the steps that vary.

An import job always runs extract, transform, validate, load. Only the details change: CSV or JSON in, a table or an API out. The base class owns run(), the template method, and calls the steps. Subclasses override steps and never the order. That is the Hollywood principle: don't call us, we'll call you. It is how unittest.TestCase (setUp, the test, tearDown) and Django's class-based views work.

classDiagram
  class Importer {
    <<abstract>>
    +run(source) int
    +extract(source)
    +transform(row)
    +is_valid(row)
    +load(rows)
    +on_done(loaded, skipped)
  }
  class CsvToList
  class JsonToApi

run() is the template and is never overridden. extract and load are abstract; transform, is_valid and on_done have defaults, so subclasses override only what they need (the optional ones are called hooks).

An import template

import csv
from abc import ABC, abstractmethod

class Importer(ABC):
    def run(self, source) -> int:                    # the template method: the order is fixed here
        rows = [self.transform(r) for r in self.extract(source)]
        good = [r for r in rows if self.is_valid(r)]
        self.load(good)
        self.on_done(len(good), len(rows) - len(good))
        return len(good)

    @abstractmethod
    def extract(self, source): ...                   # required step

    @abstractmethod
    def load(self, rows): ...                        # required step

    def transform(self, row): return row             # optional steps with defaults ("hooks")
    def is_valid(self, row): return True
    def on_done(self, loaded, skipped): pass

class CsvToList(Importer):
    def __init__(self):
        self.table = []
    def extract(self, source):
        return list(csv.DictReader(source))          # any iterable of lines
    def transform(self, row):
        return {**row, "qty": int(row["qty"])}
    def is_valid(self, row):
        return row["qty"] > 0
    def load(self, rows):
        self.table.extend(rows)
    def on_done(self, loaded, skipped):
        print(f"loaded {loaded}, skipped {skipped}")

importer = CsvToList()
print(importer.run(["sku,qty", "book,2", "pen,0", "cup,5"]))    # prints 'loaded 2, skipped 1', then 2
print(importer.table)       # [{'sku': 'book', 'qty': 2}, {'sku': 'cup', 'qty': 5}]

Inheritance vs passing the steps in

Template Method: a subclass per variant

Good when you are writing a framework that other people extend, or when the variants share many hooks. The cost is coupling: subclasses depend on the base class's step order, and a new step in the base class can break every child.

class CsvToList(Importer):
    def extract(self, source): return list(csv.DictReader(source))
    def load(self, rows): self.table.extend(rows)
    def is_valid(self, row): return int(row["qty"]) > 0

CsvToList().run(lines)

A function that takes the steps

Usually enough inside one codebase. The 'skeleton' is a function, the steps are callables, and there is no hierarchy to learn.

def run_import(extract, load, transform=lambda r: r, is_valid=lambda r: True):
    rows = [transform(r) for r in extract()]
    load([r for r in rows if is_valid(r)])

run_import(lambda: csv.DictReader(lines), table.extend, is_valid=lambda r: int(r["qty"]) > 0)

Chain of Responsibility

Intent: pass a request along a sequence of handlers. Each one may answer it, change it, or hand it on, and the sender does not know which handler will finish the job.

Web middleware is the everyday case: authenticate, rate-limit, validate, then run the business handler. An expense approval flow is the interview classic: a manager approves up to 5,000, a director up to 50,000, a VP beyond that.

flowchart LR
  R[Request] --> A{Authenticated?}
  A -->|no| X1[401 stop]
  A -->|yes| L{Under rate limit?}
  L -->|no| X2[429 stop]
  L -->|yes| V{Valid body?}
  V -->|no| X3[400 stop]
  V -->|yes| H[Business handler]
Every link makes one of three choices: answer, reject, or pass on. Inserting a link (logging, caching) touches none of the others.

Chain of Responsibility in Python

The idiomatic version: handlers are functions in a list, and the first one that returns something answers.

def authenticate(req):
    return {"status": 401} if "user" not in req else None      # None means: pass it on

def rate_limit(req):
    return {"status": 429} if req.get("calls", 0) > 100 else None

def handle(req):
    return {"status": 200, "body": f"hello {req['user']}"}

CHAIN = [authenticate, rate_limit, handle]

def dispatch(req):
    for link in CHAIN:
        response = link(req)
        if response is not None:                              # this link answered: stop here
            return response
    raise RuntimeError("no handler answered")

print(dispatch({"user": "ann"}))                 # {'status': 200, 'body': 'hello ann'}
print(dispatch({}))                              # {'status': 401}
print(dispatch({"user": "bob", "calls": 500}))   # {'status': 429}

The textbook shape. Each handler holds a reference to the next, which suits approval flows where the order is part of the domain.

from dataclasses import dataclass
from typing import Optional

@dataclass
class Approver:
    name: str
    limit: float
    next: Optional["Approver"] = None

    def approve(self, amount: float) -> str:
        if amount <= self.limit:
            return f"{self.name} approved {amount:,.0f}"
        if self.next is None:
            return f"nobody can approve {amount:,.0f}"
        return self.next.approve(amount)                      # pass it on

vp = Approver("VP", 1_000_000)
director = Approver("Director", 50_000, vp)
manager = Approver("Manager", 5_000, director)
print(manager.approve(3_000))        # Manager approved 3,000
print(manager.approve(20_000))       # Director approved 20,000
print(manager.approve(2_000_000))    # nobody can approve 2,000,000

Handlers that can act before and after the rest of the chain (timing, transactions, logging) receive a call_next function.

from functools import reduce

def authenticate(req, call_next):
    if "user" not in req:
        return {"status": 401}
    return call_next(req)

def rate_limit(req, call_next):
    if req.get("calls", 0) > 100:
        return {"status": 429}
    return call_next(req)

def handler(req):
    return {"status": 200, "body": f"hello {req['user']}"}

def build_chain(middlewares, final):
    # wrap from the inside out so that middlewares[0] runs first
    return reduce(lambda nxt, mw: (lambda req: mw(req, nxt)), reversed(middlewares), final)

app = build_chain([authenticate, rate_limit], handler)
print(app({"user": "ann"}))              # {'status': 200, 'body': 'hello ann'}
print(app({}))                           # {'status': 401}

When not to use them

  • Template Method with deep hierarchies. Subclasses silently depend on the base class's order and hooks (the fragile base class problem). If only one or two steps vary, pass functions. If a subclass needs to override run() itself, the skeleton is wrong.
  • Chain when exactly one handler is always right. Use a dict dispatch (HANDLERS[kind](request)); a chain makes you read every link to find the one that fires.
  • Chain when the order secretly matters. Authentication before rate limiting by user is an ordering contract. Write it down and test the order, and decide what happens when the request falls off the end (a default handler or an error).

Say: 'The import always runs extract, transform, validate, load, so the base class owns that order and subclasses override the steps. If I were not writing a framework I'd pass the steps as callables instead, to avoid a hierarchy.' For a chain: 'Approval is a chain: each approver approves within their limit or passes the request up. Adding a level is one more link, and the requester never knows who approved.'

Iterator and generators

Intent: let consumers walk a collection one item at a time without knowing how it is stored. In Python the pattern is part of the language, so the skill is knowing the protocol and the generator that implements it for you.

  • An iterable is anything you can loop over. It has __iter__(), which returns an iterator.
  • An iterator has __next__(), which returns the next item or raises StopIteration, and __iter__(), which returns itself.
  • A generator function (any function containing yield) returns an iterator for free. Its body runs until a yield, hands out a value and pauses with all its local variables intact.
sequenceDiagram
  participant L as for loop
  participant G as generator
  L->>G: iter(g)
  G-->>L: returns g itself
  L->>G: next(g)
  G-->>L: runs to yield 1 and pauses
  L->>G: next(g)
  G-->>L: resumes, yields 2 and pauses
  L->>G: next(g)
  G-->>L: body ends, raises StopIteration
for x in g: is a loop around next(g). The generator keeps its place between calls; nothing runs until the first next.

Four ways to write an iterator

The protocol spelled out. You track the position yourself and signal the end with StopIteration.

class Countdown:
    def __init__(self, start):
        self.n = start
    def __iter__(self):
        return self                      # an iterator is its own iterable
    def __next__(self):
        if self.n <= 0:
            raise StopIteration
        self.n -= 1
        return self.n + 1

print(list(Countdown(3)))                # [3, 2, 1]

The same thing in four lines. The while loop's state lives in the paused frame, so there is nothing to track by hand. Note that a generator is single-use.

def countdown(start):
    while start > 0:
        yield start
        start -= 1

g = countdown(3)
print(list(g))        # [3, 2, 1]
print(list(g))        # []  the generator is exhausted; call countdown(3) again for a fresh one

squares = (n * n for n in range(5))      # a generator expression is the one-line form
print(sum(squares))   # 30

yield from hands each item of an inner iterable to the consumer. Pages are fetched only when the consumer asks for more items than it has seen.

from itertools import islice

PAGES = {None: {"items": [1, 2], "next": "a"},
         "a": {"items": [3], "next": "b"},
         "b": {"items": [4, 5], "next": None}}

def get_page(token):
    print("GET page", token)
    return PAGES[token]

def fetch_all(get_page):
    token = None
    while True:
        page = get_page(token)
        yield from page["items"]
        token = page["next"]
        if token is None:
            return

print(list(islice(fetch_all(get_page), 3)))   # GET page None, GET page a, then [1, 2, 3]: page 'b' never fetched

Make __iter__ a generator function and every for loop over the object gets a fresh generator. The same trick gives a tree an in-order traversal.

class Playlist:
    def __init__(self, songs):
        self.songs = songs
    def __iter__(self):
        for s in self.songs:             # a new generator on every call, so the object can be looped repeatedly
            yield s.title()

pl = Playlist(["blue monday", "africa"])
print(list(pl), list(pl))                # both passes work

class TreeNode:
    def __init__(self, val, left=None, right=None):
        self.val, self.left, self.right = val, left, right

    def __iter__(self):                  # in-order traversal
        if self.left:
            yield from self.left
        yield self.val
        if self.right:
            yield from self.right

root = TreeNode(2, TreeNode(1), TreeNode(3))
print(list(root))                        # [1, 2, 3]

Gotchas and when to skip it

  • Single use. Iterating a generator twice yields nothing the second time. Anything meant to be looped over repeatedly should be an iterable object whose __iter__ returns a fresh iterator.
  • Laziness hides errors. The body does not run until the first next(), so an exception inside it surfaces at the consumer, not where you created the generator.
  • Resources. A with open(...) inside a generator is released when the generator is closed or garbage-collected. If the consumer stops early and that matters, call .close() or wrap it in contextlib.closing.
  • You need len(), indexing or several passes. Build a list. Laziness buys constant memory; it costs random access.
  • Recursion depth. A recursive generator such as the tree traversal uses one stack frame per level, like any recursion (Recursion & the call stack).

Say: 'For traversals I'd expose __iter__ as a generator. The tree yields from its left subtree, yields its own value, then yields from the right. Callers get a lazy, re-iterable sequence without knowing the structure, and itertools.islice takes the first k without walking the rest.' Be ready for iterable vs iterator, for what happens on a second pass over a generator, and for the O(h) stack depth of the recursive version.

Telling the patterns apart, and when to skip them

Interviewers love the look-alikes. The cleanest answer says who decides and what the variants know about each other. Strategy and State are the pair asked most often, because both delegate to an interchangeable object.

Strategy vs State

Strategy

  • Who picks? The client, once: from config, a plan, a request.
  • Do the variants know each other? No. They are independent and interchangeable.
  • How often does it change? Rarely. A swap is a deliberate act.
  • The question it answers: how do we compute this?
checkout = Checkout(discount=percent_off(10))     # the caller chooses

State

  • Who picks? The object itself, as events arrive.
  • Do the variants know each other? Yes. Each state names the states it leads to.
  • How often does it change? Constantly: every event may move it.
  • The question it answers: what can I do now, and what comes next?
class Idle(State):
    def insert_coin(self, m, cents):
        m.credit += cents
        m.state = HasMoney()                      # the state chooses its successor

Say: 'Both delegate to an interchangeable object. With Strategy the client picks the object, once, and the variants know nothing about each other. With State the object swaps itself as events arrive, and each state knows which states can follow it. Strategy answers 'how do we compute this?'; State answers 'what can I do now, and what comes next?'.'

Other pairs that get asked: Template Method vs Strategy (vary steps by inheritance vs vary the whole algorithm by composition), Command vs Strategy (a command is a request with its receiver and often an inverse; a strategy is an algorithm), and Observer vs Chain (every observer gets the event; a chain stops at the first handler that answers).

Practice: an editor with undo and live listeners

Two patterns in one small design: Command for the edits and Observer for the listeners. Time-box it, write the class diagram on paper first, then code. The reference solution opens after you have tried.

Text editor with undo/redo and change listeners

35:00

Build a small Editor class.

  • Editor(text="") holds the current text in editor.text.
  • insert(pos, s) and delete(pos, n) edit the text. Both must be undoable.
  • undo() and redo() behave like any editor. A fresh edit discards the redo history. Calling either one when there is nothing to do is a no-op.
  • subscribe(listener) registers a callback listener(text) that is called after every change to the text, including undo and redo. It returns a function that unsubscribes.
  • A listener that raises must not stop the other listeners and must not make the edit fail.

Use the Command pattern for the edits and an observer mechanism for the listeners.

What to notice

  • The editor is the invoker (it owns the stacks) and the subject (it owns the listeners). The commands know the editor but nothing about history or listeners.
  • Delete.do stores removed while it runs. Insert can undo itself from its arguments alone.
  • _notify is called from four places and iterates over a copy. Undo and redo notify too, because the text changed.
  • Both stretch goals are small: merging is a merge(other) method on commands, and a history cap is a collections.deque(maxlen=n) for _undo.
import logging
from abc import ABC, abstractmethod
from typing import Callable


class Command(ABC):
    @abstractmethod
    def do(self, ed: "Editor") -> None: ...
    @abstractmethod
    def undo(self, ed: "Editor") -> None: ...


class Insert(Command):
    def __init__(self, pos: int, s: str):
        self.pos, self.s = pos, s

    def do(self, ed):
        ed.text = ed.text[:self.pos] + self.s + ed.text[self.pos:]

    def undo(self, ed):
        ed.text = ed.text[:self.pos] + ed.text[self.pos + len(self.s):]


class Delete(Command):
    def __init__(self, pos: int, n: int):
        self.pos, self.n, self.removed = pos, n, ""

    def do(self, ed):
        self.removed = ed.text[self.pos:self.pos + self.n]       # undo needs this, so capture it now
        ed.text = ed.text[:self.pos] + ed.text[self.pos + self.n:]

    def undo(self, ed):
        ed.text = ed.text[:self.pos] + self.removed + ed.text[self.pos:]


class Editor:
    def __init__(self, text: str = ""):
        self.text = text
        self._undo: list[Command] = []
        self._redo: list[Command] = []
        self._listeners: list[Callable[[str], None]] = []

    # -- observer side --
    def subscribe(self, listener: Callable[[str], None]) -> Callable[[], None]:
        self._listeners.append(listener)
        return lambda: self._listeners.remove(listener)

    def _notify(self) -> None:
        for fn in list(self._listeners):                          # copy: a listener may unsubscribe itself
            try:
                fn(self.text)
            except Exception:
                logging.exception("listener %r failed", fn)       # isolate: one bad listener must not stop the rest

    # -- command side --
    def _execute(self, cmd: Command) -> None:
        cmd.do(self)
        self._undo.append(cmd)
        self._redo.clear()                                        # a new edit discards the redo branch
        self._notify()

    def insert(self, pos: int, s: str) -> None:
        self._execute(Insert(pos, s))

    def delete(self, pos: int, n: int) -> None:
        self._execute(Delete(pos, n))

    def undo(self) -> None:
        if self._undo:                                            # empty stack: no-op and no notification
            cmd = self._undo.pop()
            cmd.undo(self)
            self._redo.append(cmd)
            self._notify()

    def redo(self) -> None:
        if self._redo:
            cmd = self._redo.pop()
            cmd.do(self)
            self._undo.append(cmd)
            self._notify()


logging.disable(logging.CRITICAL)           # keep the demo quiet; the broken listener below would log a traceback
seen = []
ed = Editor()
stop = ed.subscribe(seen.append)
ed.subscribe(lambda text: 1 / 0)             # a broken listener must not stop anything
ed.insert(0, "Hello")
ed.insert(5, " World")
ed.delete(0, 6)
assert ed.text == "World"
ed.undo()
ed.undo()
assert ed.text == "Hello"

assert ed.text == "Hello World"

assert ed.text == "Hello World!"
