Structural patterns: wrapping and composing

Creational patterns build objects. Structural patterns decide how objects are put together. Five come up in interviews, and four of them (Adapter, Decorator, Proxy, Facade) look the same on a class diagram: one object holds another and forwards calls to it. What differs is the intent, and in particular what happens to the interface. Start from what you need to change, and the map below points at the pattern.

The same wrapping mechanism, four different reasons. Interviewers ask for exactly this distinction.

In an interview, answer 'what is the difference?' by saying what happens to the interface: an Adapter changes it, a Decorator and a Proxy keep it, a Facade replaces it with a smaller one. Then say the intent: fit, extend, guard, simplify.

Adapter: make an incompatible interface fit

Intent: convert the interface of a class you cannot (or should not) change into the interface your code expects.

The classic case is a third-party SDK. Your checkout wants charge(order_id, amount, currency, token) and a charge id back. The vendor offers create_charge(amount_minor=..., cur=..., source=..., idem=...) and returns a dict with a status string. Units differ (cents vs Decimal), names differ and errors are signalled differently. If vendor calls spread through the codebase, a vendor change or a second vendor becomes a search-and-replace across modules, and every test needs the vendor or a patch.

Vendor calls everywhere vs one adapter

The SDK leaks into every module

# checkout.py
resp = vendor.create_charge(amount_minor=int(total * 100), cur="usd", source=token, idem=order_id)
if resp["status"] != "succeeded":
    raise RuntimeError(resp)

# refunds.py (written by someone else, six months later)
vendor.create_refund(charge=charge_id)

# reports.py
rows = [c for c in vendor.list_charges(since=ts) if c["cur"] == "usd"]

Domain code sees only our interface

# checkout.py
charge_id = gateway.charge(order_id, total, "USD", token)

# refunds.py
gateway.refund(charge_id)

# The vendor's names, units and status strings live in one class: VendorGateway.
# Tests pass a FakeGateway. A second vendor is a second adapter.

Wrapping a vendor SDK

from decimal import Decimal
from typing import Protocol

class PaymentFailed(Exception):
    pass

class PaymentGateway(Protocol):                      # the interface our domain code wants
    def charge(self, order_id: str, amount: Decimal, currency: str, token: str) -> str: ...
    def refund(self, charge_id: str) -> None: ...

class VendorClient:                                  # stand-in for the third-party SDK we cannot change
    def create_charge(self, *, amount_minor: int, cur: str, source: str, idem: str) -> dict:
        return {"id": "ch_" + idem, "status": "succeeded"}
    def create_refund(self, charge: str) -> dict:
        return {"id": "re_" + charge, "status": "succeeded"}

class VendorGateway:                                 # the adapter: our interface outside, the SDK inside
    def __init__(self, client: VendorClient):
        self._client = client

    def charge(self, order_id, amount, currency, token):
        resp = self._client.create_charge(
            amount_minor=int(amount * 100),          # Decimal to integer cents (floats drift, see below)
            cur=currency.lower(), source=token,
            idem=order_id)                           # our order id doubles as the vendor's idempotency key
        if resp["status"] != "succeeded":
            raise PaymentFailed(resp)                # vendor status strings become our exception
        return resp["id"]

    def refund(self, charge_id):
        self._client.create_refund(charge_id)

class FakeGateway:                                   # same interface, no network: for tests
    def __init__(self):
        self.charges = []
    def charge(self, order_id, amount, currency, token):
        self.charges.append((order_id, amount))
        return f"fake-{order_id}"
    def refund(self, charge_id):
        pass

def checkout(gateway: PaymentGateway, order_id: str, total: Decimal) -> str:
    return gateway.charge(order_id, total, "USD", token="tok_visa")

print(checkout(VendorGateway(VendorClient()), "o-17", Decimal("19.99")))     # ch_o-17
fake = FakeGateway()
print(checkout(fake, "o-18", Decimal("5.00")), fake.charges)                 # fake-o-18 [('o-18', Decimal('5.00'))]
print(int(Decimal("19.99") * 100), int(19.99 * 100))                          # 1999 1998: floats lose a cent

Notes for Python

  • Own the interface. PaymentGateway belongs to the domain package and is shaped by what checkout needs. The adapter is the only module that imports the SDK.
  • Translate both ways. Arguments in (Decimal to minor units, currency case, order id as idempotency key) and results out (a status dict becomes a charge id or PaymentFailed). Vendor exception types should not escape either.
  • Use a Protocol. With typing.Protocol the adapter does not inherit from the interface, so the domain package never imports from the infrastructure package.
  • Object adapter over class adapter. Wrap an instance (composition) instead of subclassing the SDK class. SDK internals can change without breaking you, and tests can pass a fake client.

When not to use it

  • You own both sides. Change the interface directly.
  • The shape already matches. An adapter that only renames one method adds a hop and isolates nothing. Wrap when the shape differs (units, errors, auth, pagination) or the dependency is volatile, external or hard to fake.

Say: 'I'd define a PaymentGateway interface in the domain with the operations checkout needs, and write a VendorGateway adapter that is the only code importing the SDK. It converts Decimal to cents, maps status strings to a return value or PaymentFailed, and uses the order id as the idempotency key. Tests inject a fake gateway; a second vendor is a second adapter.' Follow-ups: Adapter vs Facade (an adapter makes one thing fit an interface that already exists, a facade defines a new, simpler interface over many things) and where retries go (a decorator around the gateway).

Decorator: add behaviour without subclassing

▶ Video lesson: Decorator: wrap, stack, and mind the order 4:40 · 7 scenes · narrated, pause anytime and explore

Intent: attach extra behaviour to an object by wrapping it in another object with the same interface. Wrappers can be stacked, and the combination is chosen at runtime.

The name covers two things in Python. The GoF Decorator wraps an object that has an interface (a Notifier). Python's @decorator syntax applies the same idea to functions: @retry replaces a function with a wrapper that has the same call signature and does extra work around the original. The syntax is sugar for fetch = retry(fetch).

A decorator both implements the interface and holds one, which is what lets wrappers nest to any depth.

Subclass per combination vs wrappers

Inheritance

Three channels (SMS, email, push) and three behaviours (logging, retries, rate limiting) give 3 x 2³ = 24 classes, such as LoggingRetryingEmailNotifier. Each new behaviour doubles the count, and every combination is fixed at import time.

Wrappers

3 channels + 3 wrappers = 6 classes. The combination is chosen where the object is built, per environment or per customer.

notifier = RateLimited(Logging(Retrying(EmailNotifier())))

Decorators in Python

The GoF shape. Each wrapper holds an inner Notifier and calls it. Run it: the retry wrapper absorbs two failures, and the logging wrapper sees only the final success.

class SmsNotifier:
    def __init__(self, failures=0):
        self.failures = failures                 # simulate a flaky gateway
    def send(self, user, message):
        if self.failures:
            self.failures -= 1
            raise ConnectionError("gateway timeout")
        print(f"SMS to {user}: {message}")

class LoggingNotifier:
    def __init__(self, inner):
        self._inner = inner
    def send(self, user, message):
        print(f"[log] sending to {user}")
        self._inner.send(user, message)
        print(f"[log] sent to {user}")

class RetryingNotifier:
    def __init__(self, inner, attempts=3):
        self._inner, self._attempts = inner, attempts
    def send(self, user, message):
        for attempt in range(1, self._attempts + 1):
            try:
                return self._inner.send(user, message)
            except ConnectionError:
                print(f"[retry] attempt {attempt} failed")
                if attempt == self._attempts:
                    raise

notifier = LoggingNotifier(RetryingNotifier(SmsNotifier(failures=2)))     # stack at the wiring point
notifier.send("ann", "your order shipped")

The same idea for functions. retry(times=3) is a decorator factory: three nested functions (factory, decorator, wrapper) is the standard shape for decorators with arguments.

import functools
import time

def retry(times=3, delay=0.0, on=(Exception,)):
    def decorator(fn):
        @functools.wraps(fn)                      # keep fn's name, docstring and signature info
        def wrapper(*args, **kwargs):
            for attempt in range(1, times + 1):
                try:
                    return fn(*args, **kwargs)
                except on:
                    if attempt == times:
                        raise
                    time.sleep(delay * attempt)
        return wrapper
    return decorator

def timed(fn):
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            print(f"{fn.__name__} took {(time.perf_counter() - start) * 1000:.1f} ms")
    return wrapper

calls = {"n": 0}

@timed                       # outermost: times all attempts together
@retry(times=3)              # inside: retries the raw function
def flaky_fetch(key):
    'Fetch a value; fails twice, then works.'
    calls["n"] += 1
    if calls["n"] < 3:
        raise TimeoutError("slow")
    return key.upper()

print(flaky_fetch("abc"), flaky_fetch.__name__, calls["n"])    # ABC flaky_fetch 3

When the wrapper must remember something between calls, a class with __call__ is tidier than a mutable closure variable.

import functools

class counted:
    def __init__(self, fn):
        functools.update_wrapper(self, fn)        # copy __name__, __doc__ ... onto the instance
        self.fn, self.calls = fn, 0
    def __call__(self, *args, **kwargs):
        self.calls += 1
        return self.fn(*args, **kwargs)

@counted
def ping():
    'Return pong.'
    return "pong"

ping()
ping()
print(ping.calls, ping.__name__, ping.__doc__)    # 2 ping Return pong.

Why functools.wraps matters

Without it

def shout(fn):
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs).upper()
    return wrapper

@shout
def greet(name):
    'Return a greeting.'
    return f"hello {name}"

print(greet.__name__, greet.__doc__)     # wrapper None

With it

import functools

def shout(fn):
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs).upper()
    return wrapper

@shout
def greet(name):
    'Return a greeting.'
    return f"hello {name}"

print(greet.__name__, greet.__doc__)     # greet Return a greeting.

Stacking order changes what a decorator sees

Two decorators wrap the same function: @timed measures a call, @cached stores results. Run the same two calls with each one outermost and compare the timer samples.

Rules of thumb

  • Order is part of the design. @a above @b above def f means f = a(b(f)). The top decorator is the outermost wrapper and runs first. Retry outside a timeout behaves differently from timeout outside retry, and authentication before caching is a security decision.
  • Keep the interface. The wrapper takes *args, **kwargs and returns what the wrapped callable returns; the class version has the same methods. A wrapper that changes the interface is an adapter.
  • Preserve identity. Without functools.wraps, tools that read __name__ see wrapper: loggers, help(), pytest fixtures, and Flask, which raises "View function mapping is overwriting an existing endpoint function" when two decorated views both look like wrapper.

When not to use it

  • One behaviour in one place. Write the code inline; a decorator hides control flow.
  • Deep stacks. Tracebacks fill with wrapper frames and the order becomes folklore. Keep wrappers thin, few and well named.
  • The behaviour needs the function's internals. A decorator only sees arguments and results. If it must change what happens in the middle, use a hook (Template Method) or a strategy.

Say: 'Instead of a subclass for every combination of retry, logging and rate limiting, I'd write each as a wrapper that implements the same Notifier interface and compose them where the object is built: Logging(Retrying(Sms())). Three wrappers and three channels is six classes instead of twenty-four. In Python the function version is @retry with functools.wraps, and I'd point out that the stacking order matters.'

Facade: one door to a messy subsystem

Intent: give callers a single, simple interface to a group of classes that have to be used together in a particular way.

Uploading an avatar means: validate the file, resize it to two widths, store each variant, record the URLs. That is four classes, a strict order, and error handling at every join. If each endpoint (web, mobile API, admin tool) repeats the sequence, the copies drift: one forgets validation, another stores before resizing. A facade owns the sequence once.

A facade over four subsystems

class Validator:
    def check(self, data: bytes) -> None:
        if not data:
            raise ValueError("empty file")

class Resizer:
    def to_widths(self, data: bytes, widths=(64, 256)) -> dict[int, bytes]:
        return {w: data[:w] for w in widths}               # stand-in for real image work

class BlobStore:
    def __init__(self):
        self.blobs = {}
    def put(self, key: str, data: bytes) -> str:
        self.blobs[key] = data
        return f"https://cdn.example/{key}"

class MetadataDB:
    def __init__(self):
        self.rows = {}
    def record(self, user_id: str, urls: dict[int, str]) -> None:
        self.rows[user_id] = urls

class AvatarService:                                        # the facade: one method for the whole workflow
    def __init__(self, validator, resizer, store, db):      # subsystems are injected, so tests pass fakes
        self._validator, self._resizer, self._store, self._db = validator, resizer, store, db

    def upload(self, user_id: str, data: bytes) -> dict[int, str]:
        self._validator.check(data)
        variants = self._resizer.to_widths(data)
        urls = {w: self._store.put(f"avatars/{user_id}/{w}.jpg", blob) for w, blob in variants.items()}
        self._db.record(user_id, urls)
        return urls

service = AvatarService(Validator(), Resizer(), BlobStore(), MetadataDB())
print(service.upload("u1", b"x" * 1000))
try:
    service.upload("u2", b"")
except ValueError as e:
    print("rejected:", e)                                   # the failure rule lives in one place too

Notes for Python

  • A convenience, not a wall. The subsystems stay public. Advanced callers can bypass the facade, and the facade can be tested by injecting fakes.
  • Orchestration only. Validation rules belong in Validator, resizing in Resizer. When the facade starts to hold business rules it turns into a god class (Extensibility & modularity).
  • It does not have to be a class. A module-level function (upload_avatar(user_id, data)) is a facade too. In the standard library, subprocess.run is a facade over Popen.

When not to use it

  • One caller and a two-step sequence. Call the two things directly; a facade here is a layer to read for no gain.
  • The subsystem is already simple. A facade that forwards one call to one class is an alias.

Say: 'The upload workflow is validate, resize, store, record. I'd put that sequence in an AvatarService facade so the web and mobile endpoints each make one call, and the order and error handling exist once. The subsystems are injected, so tests use fakes. I'd keep the facade to orchestration so it does not grow into a god class.' Follow-up: 'Facade vs Adapter?' An adapter makes an existing thing fit an existing interface; a facade invents a smaller interface.

Composite: treat one and many alike

▶ Video lesson: Composite: one and many answer the same call 4:32 · 7 scenes · narrated, pause anytime and explore

Intent: compose objects into a tree and let clients treat a single object and a group of objects through the same interface.

A file system is the textbook case. A directory contains files and other directories, and "how big is this?" has to work on any of them. Without Composite every caller writes if isinstance(node, Directory): ... else: ..., once per operation. With it, the recursion lives in one place: a directory's size() asks its children, whatever they are. UI toolkits (a panel holding buttons and panels), menus, org charts and expression trees have the same shape.

The loop at the bottom is the whole idea: a Directory contains Nodes, and a Directory is a Node.

A file-system composite

from abc import ABC, abstractmethod
from collections.abc import Iterator

class Node(ABC):
    def __init__(self, name: str):
        self.name = name
    @abstractmethod
    def size(self) -> int: ...
    @abstractmethod
    def walk(self, prefix: str = "") -> Iterator[str]: ...      # yields full paths

class File(Node):
    def __init__(self, name: str, size: int):
        super().__init__(name)
        self._size = size
    def size(self) -> int:
        return self._size
    def walk(self, prefix=""):
        yield prefix + self.name

class Directory(Node):
    def __init__(self, name: str):
        super().__init__(name)
        self._children: dict[str, Node] = {}

    def add(self, node: Node) -> "Directory":
        if node.name in self._children:
            raise ValueError(f"{node.name} already exists in {self.name}")
        self._children[node.name] = node
        return self                                              # chaining: d.add(a).add(b)

    def size(self) -> int:
        return sum(child.size() for child in self._children.values())    # the recursion: no isinstance anywhere

    def walk(self, prefix=""):
        path = f"{prefix}{self.name}/"
        yield path
        for child in self._children.values():
            yield from child.walk(path)

root = (Directory("root")
        .add(Directory("src").add(File("a.py", 4)).add(File("b.py", 2)))
        .add(Directory("docs").add(File("c.md", 1))
             .add(Directory("img").add(File("d.png", 5)).add(File("e.png", 3)))))
print(root.size())                 # 15
print(list(root.walk())[:4])       # ['root/', 'root/src/', 'root/src/a.py', 'root/src/b.py']

size() recurses through a tree

Watch the call stack grow as size() descends into directories and shrink as sizes bubble back up. The labels beside the nodes show each size once it is known. The second scenario starts from a subdirectory: a part is a whole too.

Design decisions

  • Shared interface, shared operations. Put the operations that make sense for both leaf and composite (size, walk, render) on Node.
  • Where does add() live? On Directory only (type-safe: a File has no add), or on Node with File.add raising (uniform for clients, but a runtime error). Python code usually keeps add on the composite.
  • Cycles. A node that becomes its own ancestor makes size() recurse forever. Reject it in add (walk up the parents) or keep trees immutable.
  • Parent pointers make path() and remove() easy, but they create reference cycles and must be kept consistent.
  • Cost. A recursive operation is O(n) in the number of nodes and uses O(h) stack for a tree of height h. If size() is called often, cache it and invalidate up the parent chain on change.

When not to use it

  • The structure is not a tree. A flat list needs a loop, and a graph with shared nodes needs cycle handling.
  • Clients must treat leaves and composites differently anyway. Then the uniform interface is a fiction; model them as separate types.

Say: 'A file system is a Composite. Node declares size() and walk(); File is the leaf; Directory holds children, which are Nodes, and implements size() by summing them. Callers never check the type. I'd put add on Directory, reject duplicate names, and guard against cycles if nodes can move.' Follow-ups: caching sizes (invalidate up the parent chain), adding find (another method on the interface, or a visitor if operations keep growing).

Proxies in Python

Three proxies for the same interface. Note the order in the demo: the access check wraps the cache, so a cached report is never served to someone who could not have fetched it.

from abc import ABC, abstractmethod

class ReportService(ABC):
    @abstractmethod
    def report(self, name: str) -> str: ...

class RealReportService(ReportService):
    def __init__(self):
        self.calls = 0
    def report(self, name):
        self.calls += 1                               # imagine 40 ms of work here
        return f"<{name} report>"

class CachingProxy(ReportService):
    def __init__(self, inner):
        self._inner, self._cache = inner, {}
    def report(self, name):
        if name not in self._cache:
            self._cache[name] = self._inner.report(name)
        return self._cache[name]

class AccessProxy(ReportService):
    def __init__(self, inner, roles):
        self._inner, self._roles = inner, roles
    def report(self, name):
        if "analyst" not in self._roles:
            raise PermissionError(f"{name}: analyst role required")
        return self._inner.report(name)

class LazyProxy(ReportService):
    def __init__(self, factory):
        self._factory, self._real = factory, None
    def report(self, name):
        if self._real is None:
            print("creating the real service")       # happens once, on first use
            self._real = self._factory()
        return self._real.report(name)

real = RealReportService()
service = AccessProxy(CachingProxy(real), {"analyst"})
print(service.report("q3"), service.report("q3"), real.calls)    # <q3 report> <q3 report> 1
try:
    AccessProxy(CachingProxy(real), {"guest"}).report("q3")
except PermissionError as e:
    print(e)                                                       # q3: analyst role required

lazy = LazyProxy(RealReportService)
print("lazy proxy built")                                          # nothing has been created yet
print(lazy.report("q1"), lazy.report("q2"))                        # creating the real service, then both reports

One proxy class that forwards any method. Handy for logging or tracing, but Python looks up special methods on the type, so len(p) and p[0] are not forwarded unless you define them.

class LoggingProxy:
    def __init__(self, target):
        self._target = target

    def __getattr__(self, name):              # called only when normal lookup on the proxy fails
        attr = getattr(self._target, name)
        if not callable(attr):
            return attr
        def call(*args, **kwargs):
            shown = ", ".join(map(repr, args))
            print(f"-> {name}({shown})")
            return attr(*args, **kwargs)
        return call

p = LoggingProxy([3, 1, 2])
p.append(0)                    # -> append(0)
print(p.count(1))              # -> count(1), then 1
try:
    len(p)
except TypeError as e:
    print("TypeError:", e)     # object of type 'LoggingProxy' has no len()

Proxy or decorator?

The code is often identical: a caching proxy and a caching decorator are the same class. The difference is intent. A decorator adds behaviour and is handed the object it wraps. A proxy controls access to the real subject and often creates or locates it itself (lazily, remotely). If you can say "this decides whether the real object is used", call it a proxy.

When not to use it

  • Python already has the hook. functools.cached_property is a lazy attribute, and functools.lru_cache is a caching wrapper. Reach for a proxy class when the interface is bigger than one function.
  • Hiding a design problem. A cache in front of an N+1 query pattern treats the symptom. Fix the query.
  • Dynamic proxies for important interfaces. __getattr__ forwarding does not forward special methods, confuses isinstance and type checkers, and hides the real interface from readers. Prefer explicit forwarding.

Say: 'A proxy has the same interface as the real service and decides whether to forward. I'd put the access check first, then the cache, then the real call, so cached data is never served to someone who could not have fetched it. Caching or logging could equally be decorators; what makes it a proxy is that it controls access to the real object, for example by creating it lazily.'

Flyweight in one screen

Intent: save memory by sharing the identical, immutable part of many small objects.

A game draws 100,000 trees. Each tree has a position that is different for every tree, and a type (species, colour, a 1 MB texture) that is identical for every oak. Storing the type inside each tree costs about 100,000 x 1 MB = 100 GB. Sharing three tree types costs about 3 MB. The trick is to split the state:

  • Intrinsic state is shared, immutable and identical across many objects: the tree type.
  • Extrinsic state differs per object and is stored cheaply in it, or passed in by the caller: x, y.

A factory hands out the shared objects, so equal requests return the very same instance.

Sharing tree types

from dataclasses import dataclass
from functools import cache

@dataclass(frozen=True, slots=True)
class TreeType:                                  # intrinsic state: identical for every oak, so it can be shared
    name: str
    colour: str
    texture: str

@cache                                           # the flyweight pool: equal arguments return the same object
def tree_type(name: str, colour: str, texture: str) -> TreeType:
    return TreeType(name, colour, texture)

@dataclass(slots=True)
class Tree:                                      # extrinsic state: different for each tree
    x: int
    y: int
    kind: TreeType

forest = [Tree(i, i * 2, tree_type("oak", "green", "oak.png")) for i in range(100_000)]
print(len({id(t.kind) for t in forest}), len(forest))    # 1 100000: one TreeType shared by every tree
  • Python shortcuts. @functools.cache on a factory function is a one-line flyweight pool, and a frozen dataclass makes the shared object safe to share. slots=True shrinks the per-tree objects further.
  • CPython does it too. Small integers and many short strings are shared rather than copied. That is an implementation detail: compare values with ==, never is.
  • When not to use it. With a few hundred objects, or a shared part of a few bytes, the indirection costs more than it saves. Measure memory before you restructure.

Telling the look-alikes apart

Decorator vs Proxy

Decorator

  • Adds behaviour: logging, retries, compression.
  • Is handed the object it wraps.
  • Meant to be stacked in any order you choose.
  • The question it answers: what extra should happen around this call?
notifier = Logging(Retrying(Sms()))

Proxy

  • Controls access to the real subject: lazy, allowed, cached, remote.
  • Often creates or locates the real object itself.
  • Usually one layer, and the client may not know it is there.
  • The question it answers: should this call reach the real object, and when?
reports = LazyProxy(RealReportService)

The other pair people mix up is Adapter vs Facade. An adapter makes one existing thing fit an existing interface. A facade invents a smaller interface over many things. If you are bridging a mismatch, it is an adapter; if you are hiding complexity, it is a facade.

Interview script for any structural pattern

Say: 'All four wrap an object. An Adapter changes the interface so a vendor class fits ours. A Decorator keeps the interface and adds behaviour, and I stack them. A Proxy keeps the interface and controls access to the real object: lazy creation, permission checks, caching. A Facade gives a new, smaller interface over many objects. In the standard library io.TextIOWrapper adapts, functools.lru_cache decorates, weakref.proxy proxies and subprocess.run is a facade over Popen.'

Mini file system with a read-only proxy

30:00

Model a tiny file system.

  • File(name, size) and Directory(name) share a Node interface.
  • Directory.add(node) returns the directory (so calls chain) and raises ValueError if the name already exists in that directory.
  • node.size() is the file's size, or the sum of everything below a directory.
  • node.walk() yields every path at or below the node, for example root/src/a.py. Directory paths end with /.
  • node.find(predicate) returns the paths of all files at or below the node for which predicate(file) is true.
  • Then add ReadOnly(directory): a proxy that forwards size, walk and find but raises PermissionError on add.

Client code must not use isinstance to tell files from directories.

What to notice

  • There is no isinstance anywhere. size, walk and find each exist in a leaf version and a composite version, and the composite versions call the same method on their children.
  • Paths are an argument, not state. That avoids parent pointers and the reference cycles they create.
  • ReadOnly is a proxy, not a decorator: it exists to refuse one operation on an object it was given, and the client cannot tell it from a directory for reads. add lives on Directory and ReadOnly only, because a File has nothing to add to (the 'safe' composite design).
from abc import ABC, abstractmethod
from typing import Callable, Iterator


class Node(ABC):
    def __init__(self, name: str):
        self.name = name

    @abstractmethod
    def size(self) -> int: ...

    @abstractmethod
    def walk(self, prefix: str = "") -> Iterator[str]: ...

    @abstractmethod
    def find(self, predicate: Callable[["File"], bool], prefix: str = "") -> list[str]: ...


class File(Node):
    def __init__(self, name: str, size: int):
        super().__init__(name)
        self.bytes = size

    def size(self) -> int:
        return self.bytes

    def walk(self, prefix=""):
        yield prefix + self.name

    def find(self, predicate, prefix=""):
        return [prefix + self.name] if predicate(self) else []


class Directory(Node):
    def __init__(self, name: str):
        super().__init__(name)
        self._children: dict[str, Node] = {}

    def add(self, node: Node) -> "Directory":
        if node.name in self._children:
            raise ValueError(f"{node.name!r} already exists in {self.name!r}")
        self._children[node.name] = node
        return self

    def size(self) -> int:
        return sum(c.size() for c in self._children.values())

    def walk(self, prefix=""):
        path = f"{prefix}{self.name}/"
        yield path
        for child in self._children.values():
            yield from child.walk(path)

    def find(self, predicate, prefix=""):
        path = f"{prefix}{self.name}/"
        return [hit for c in self._children.values() for hit in c.find(predicate, path)]


class ReadOnly(Node):                                    # a protection proxy around a Directory
    def __init__(self, inner: Directory):
        super().__init__(inner.name)
        self._inner = inner

    def size(self):
        return self._inner.size()

    def walk(self, prefix=""):
        return self._inner.walk(prefix)

    def find(self, predicate, prefix=""):
        return self._inner.find(predicate, prefix)

    def add(self, node):
        raise PermissionError(f"{self.name!r} is read-only")


root = Directory("root")
src = Directory("src").add(File("a.py", 4)).add(File("b.py", 2))
docs = Directory("docs").add(File("c.md", 1)).add(Directory("img").add(File("d.png", 5)))
root.add(src).add(docs)

assert root.size() == 12
assert list(root.walk()) == ["root/", "root/src/", "root/src/a.py", "root/src/b.py", "root/docs/", "root/docs/c.md",
                             "root/docs/img/", "root/docs/img/d.png"]
assert root.find(lambda f: f.name.endswith(".py")) == ["root/src/a.py", "root/src/b.py"]
assert root.find(lambda f: f.bytes > 4) == ["root/docs/img/d.png"]
try:
    src.add(File("a.py", 1))
except ValueError:
    pass
else:
    raise AssertionError("duplicate name accepted")

ro = ReadOnly(root)
assert ro.size() == 12 and list(ro.walk())[0] == "root/"
try:
    ro.add(File("x", 1))
except PermissionError:
    pass
else:
    raise AssertionError("read-only proxy accepted a write")
print("all assertions passed")
