Extensibility & modularity

Extensibility is the cost of the next change. This chapter shows how to spot a god class with a cohesion check, how dependency injection, registries and feature flags turn the next variant into a new file instead of an edit, how interfaces at boundaries make code testable, and how to stop yourself over-engineering. A stepped refactoring of a monolithic OrderService ties it together, and a timed exercise lets you do it yourself.

After this chapter you can
  • Spot a god class from cohesion clusters, fan-out, change history and test setup, and say where to cut it
  • Use constructor injection and a composition root, and tell dependency inversion, injection and inversion of control apart
  • Refactor a monolithic service into collaborators, interfaces and extension points in three safe steps
  • Build a plugin registry with decorator registration and name its failure modes
  • Roll out behaviour behind a sticky, monotonic feature flag and keep flags out of the core logic
  • Decide when an extension point earns its cost, using the rule of three

Extensibility is the cost of the next change

Nobody asks whether a design is "extensible" in the abstract. They ask what happens when the product manager says "we need gift cards", "add a Slack notification", or "support a second warehouse". Extensibility is how much existing code you have to touch to add the next variant.

Two numbers tell you where you stand:

  • Files touched per new variant. In a design with a low change cost, a new payment method is one new file and one line of registration. In a design with a high cost, it is edits to place_order, the pricing code, the confirmation email, the analytics mapping and every test that mocks any of them.
  • Reasons to change, per class. If you can list several unrelated reasons (the coupon rules changed, Stripe changed its API, marketing rewrote the receipt), the class does too much, and each of those changes puts the others at risk.

This is the open/closed principle (SOLID principles) made practical: add behaviour by adding code, not by editing code that already works. The chapter first shows how to spot the problem (a god class), then the tools that fix it (dependency injection, registries, flags, interfaces at boundaries), then the discipline that stops you overdoing it (YAGNI). Start with the map.

Name the thing that makes the change expensive, then pick the tool. Each branch has its own section below.

What the interviewer is really asking when they say 'make it extensible': they will pick one variation (a new vehicle type, payment method or notification channel) and ask you to add it live. A strong answer names the extension points before being asked ('payment methods are pluggable, pricing rules are a list') and then shows the change is a new class plus one line of registration. A weak answer is a framework for variations nobody mentioned.

Spotting a god class

▶ Video lesson: Spotting a god class 3:42 · 7 scenes · narrated, pause anytime and explore

A god class knows too much and does too much. It rarely started that way: it is the class that was easiest to add the next method to. Here is one from a shop codebase.

OrderService: one class, six jobs (sketch)

import os
import smtplib
import sqlite3

import requests
import stripe


class OrderService:
    def __init__(self):
        self.db = sqlite3.connect("shop.db")
        self.prices = {"book": 12.0, "pen": 1.5}
        self.coupons = {"SAVE10": 0.10, "FREESHIP": 5.0}
        self.stripe_key = os.environ["STRIPE_KEY"]
        self.smtp_host = "smtp.corp.example"
        self.analytics_url = "https://analytics.example/track"

    def place_order(self, user_id, items, method, coupon=None):
        self._check_stock(items)
        total = self._price(items, coupon)
        self._charge(method, total)
        self._save(user_id, items, total)
        self._send_confirmation(user_id, total)
        self._track("order_placed", total)
        return total

    def _check_stock(self, items):
        for sku, qty in items:
            row = self.db.execute("SELECT stock FROM inventory WHERE sku = ?", (sku,)).fetchone()
            if row is None or row[0] < qty:
                raise ValueError(f"out of stock: {sku}")

    def _price(self, items, coupon):
        total = sum(self.prices[sku] * qty for sku, qty in items)
        if coupon == "SAVE10":
            total *= 1 - self.coupons["SAVE10"]
        elif coupon == "FREESHIP":
            total -= self.coupons["FREESHIP"]
        elif coupon is not None:
            raise ValueError(f"bad coupon {coupon}")
        return total

    def _charge(self, method, total):
        if method == "card":
            stripe.api_key = self.stripe_key
            stripe.Charge.create(amount=int(total * 100), currency="usd", source="tok_visa")
        elif method == "paypal":
            requests.post("https://paypal.example/pay", json={"amount": total})
        else:
            raise ValueError(f"unknown payment method {method}")

    def _save(self, user_id, items, total):
        self.db.execute("INSERT INTO orders (user_id, total) VALUES (?, ?)", (user_id, total))
        self.db.commit()

    def _send_confirmation(self, user_id, total):
        with smtplib.SMTP(self.smtp_host) as smtp:
            smtp.sendmail("shop@example.com", f"{user_id}@example.com", f"Your order: {total:.2f}")

    def _track(self, event, value):
        requests.post(self.analytics_url, json={"event": event, "value": value})

Count the jobs: stock check (SQL), pricing and coupons, payments (Stripe and PayPal), persistence (SQL), the confirmation email, and analytics. Each talks to a different system and changes on its own schedule: marketing adds a coupon, finance adds a provider, someone rewrites the email. That is divergent change, one class edited for many unrelated reasons. It is also why testing is painful: the first assertion needs a database, Stripe, an SMTP server and an HTTP endpoint.

The class is only 53 lines long, so size alone would not flag it. These signals are more reliable. Treat the thresholds as smoke detectors, not verdicts.

Cohesion is the strongest signal because it finds the seams, not just the symptom.

The cohesion check is a short script. A cluster is a set of methods that touch a common field. Methods in different clusters share no state, so nothing forces them to live in the same class.

class_report.py: find the seams

import ast

def class_report(source: str) -> list[dict]:
    """Smoke-detector metrics for every top-level class in a source string."""
    tree = ast.parse(source)
    imported = {(a.asname or a.name).split(".")[0]
                for n in ast.walk(tree) if isinstance(n, (ast.Import, ast.ImportFrom)) for a in n.names}
    reports = []
    for cls in (n for n in tree.body if isinstance(n, ast.ClassDef)):
        funcs = [n for n in cls.body if isinstance(n, ast.FunctionDef)]
        init = next((f for f in funcs if f.name == "__init__"), None)
        fields = []                                           # attributes assigned in __init__, in order
        for node in ast.walk(init) if init else []:
            if isinstance(node, ast.Assign):
                for target in node.targets:
                    if (isinstance(target, ast.Attribute) and isinstance(target.value, ast.Name)
                            and target.value.id == "self" and target.attr not in fields):
                        fields.append(target.attr)
        uses = {f.name: sorted({n.attr for n in ast.walk(f)   # which fields does each method touch?
                                if isinstance(n, ast.Attribute) and isinstance(n.value, ast.Name)
                                and n.value.id == "self" and n.attr in fields})
                for f in funcs if f.name != "__init__"}
        clusters: list[dict] = []                             # methods that share a field end up in one cluster
        for name, used in uses.items():
            merged = {"methods": [name], "fields": set(used)}
            for c in [c for c in clusters if c["fields"] & merged["fields"]]:
                merged["methods"] += c["methods"]
                merged["fields"] |= c["fields"]
                clusters.remove(c)
            clusters.append(merged)
        reports.append({
            "class": cls.name,
            "lines": cls.end_lineno - cls.lineno + 1,
            "methods": len(uses),
            "fields": fields,
            "uses": uses,
            "clusters": sorted((sorted(c["methods"]) for c in clusters), key=lambda m: (-len(m), m[0])),
            "fan_out": sorted({n.id for n in ast.walk(cls) if isinstance(n, ast.Name) and n.id in imported}),
        })
    return reports


if __name__ == "__main__":
    import sys
    for r in class_report(open(sys.argv[1]).read()):
        print(f"{r['class']}: {r['lines']} lines, {r['methods']} methods, {len(r['fields'])} fields, "
              f"fan-out {len(r['fan_out'])} {r['fan_out']}")
        for i, methods in enumerate(r["clusters"], 1):
            print(f"  cluster {i}: {', '.join(methods)}")
Run it as python class_report.py order_service.py. It only reads the source with ast; it never imports or runs it.

Find the seams: methods x fields

Step through the methods one at a time, then watch the rows and columns reorder into blocks. Each block is a candidate class.

You still apply judgement. _check_stock and _save share the database connection but are different ideas (inventory vs orders), so you would probably split them and give both the connection. The matrix finds the seams; design decides which to cut.

The smell catalogue (click each)

God class

One class that knows and does too much. It grows because it is the easiest place to add the next method. Fix: extract collaborators along the data seams.

Divergent change

One class edited for many unrelated reasons (a coupon rule, a vendor, an email template). It is the cause of god classes. Fix: split by reason to change.

Shotgun surgery

One change needs small edits in many classes: adding a payment method touches six files. The opposite problem, a concept scattered around. Fix: gather it behind one interface or registry.

Type-switch ladder

if kind == ... elif kind == ... repeated in several methods, edited for every new kind. Fix: polymorphism, a strategy or a dict dispatch.

Feature envy

A method that mostly uses another class's data. Fix: move it next to the data.

Hard-wired dependencies

A class builds its own collaborators (sqlite3.connect(...) in __init__), so tests need real infrastructure and nothing can be swapped. Fix: constructor injection.

Long constructor

Eight parameters means eight collaborators. Fix: split the class. A container that auto-wires the arguments hides the symptom without curing it.

Dependency injection and inversion of control

▶ Video lesson: Dependency injection, in plain words 3:46 · 6 scenes · narrated, pause anytime and explore

A class that builds its own collaborators (self.db = sqlite3.connect("shop.db")) has decided, forever, which implementation it uses. Dependency injection (DI) hands the collaborators in from outside, usually through the constructor. That is all it is: no framework, no container, no annotations.

Three related terms get mixed up in interviews, so keep them apart:

  • Dependency inversion (the D in SOLID) is the design rule. High-level code owns the abstraction it needs, and low-level details implement it.
  • Dependency injection is the technique. Dependencies are passed in instead of created inside.
  • Inversion of control (IoC) is the style. A framework or a start-up function calls your code and supplies what it needs, instead of your code reaching out to build things. Flask routes, pytest fixtures and FastAPI's Depends(...) are all IoC.

The composition root (sketch)

def build_app(config: dict) -> OrderService:
    # The ONE place that knows concrete classes. Everything below this line receives abstractions.
    connection = sqlite3.connect(config["db_path"])
    return OrderService(
        inventory=SqlInventory(connection),
        pricing=Pricing(DISCOUNTS),
        gateways={"card": StripeGateway(config["stripe_key"]), "paypal": PayPalGateway()},
        orders=SqlOrders(connection),
        notifier=SmtpNotifier(config["smtp_host"]),
    )

if __name__ == "__main__":
    app = build_app(load_config())          # tests build their own graph with fakes instead

Practical rules

  • One composition root. A main() or build_app() at start-up is the only code that names concrete classes and wires the graph.
  • Constructor injection by default. The object is complete once built, its needs are visible in its signature, and its fields can be treated as immutable.
  • Defaults for the boring seams. now: Callable[[], datetime] = datetime.now keeps call sites short and stays overridable.
  • A long constructor is information. Eight parameters means eight collaborators, which means a god class. Splitting the class cures it; a container only hides it.
  • Python rarely needs a framework. Plain constructors and a build_app() function carry most services. Tools such as dependency-injector or FastAPI's Depends automate wiring in big graphs; they do not change the design.
  • Avoid the service locator. Calling registry.get("gateway") inside a method makes the dependency invisible, hard to fake and order-dependent.

Say: 'I'd inject the payment gateway, repository and notifier through the constructor, as small interfaces the order service owns. One composition root builds the real ones at start-up; tests pass fakes, so no patching and no network. That is dependency inversion achieved with plain dependency injection, no framework.' Follow-ups: DI vs service locator (locator hides dependencies), DI vs inversion of control (technique vs style), and what you do when the constructor gets long (split the class).

Refactoring OrderService in three safe steps

The cohesion matrix showed where the seams are. Now cut along them in three steps, each small enough to keep the tests green. If there are no tests, the first move is a characterization test: call place_order once with the outside world stubbed and pin what it returns. Keep it green through every step, and do not combine steps in one commit.

  1. Extract each cluster into its own class (single responsibility).
  2. Depend on interfaces and inject the implementations (dependency inversion).
  3. Open the variation points with a registry, a rule table and events (open/closed).

Step 2: interfaces, injection, and a test with fakes

from typing import Protocol

class Inventory(Protocol):                          # interfaces the service owns, in its own words
    def reserve(self, basket: dict[str, int]) -> None: ...

class PaymentGateway(Protocol):
    def charge(self, order_id: str, amount: float) -> str: ...

class OrderRepository(Protocol):
    def save(self, user_id: str, basket: dict[str, int], total: float) -> str: ...

class Notifier(Protocol):
    def order_placed(self, user_id: str, total: float) -> None: ...

class Pricing:                                      # pure logic, no IO: stays a concrete class
    PRICES = {"book": 12.0, "pen": 1.5}
    def price(self, basket, coupon=None):
        subtotal = sum(self.PRICES[sku] * qty for sku, qty in basket.items())
        if coupon == "SAVE10":
            return round(subtotal * 0.9, 2)
        elif coupon == "FREESHIP":
            return round(subtotal - 5.0, 2)
        elif coupon is not None:
            raise ValueError(f"bad coupon {coupon!r}")
        return subtotal

class OrderService:
    def __init__(self, inventory: Inventory, pricing: Pricing, gateways: dict[str, PaymentGateway],
                 orders: OrderRepository, notifier: Notifier):
        self._inventory, self._pricing, self._gateways = inventory, pricing, gateways
        self._orders, self._notifier = orders, notifier

    def place_order(self, user_id, basket, method, coupon=None):
        gateway = self._gateways.get(method)
        if gateway is None:
            raise ValueError(f"unknown payment method {method!r}")
        total = self._pricing.price(basket, coupon)
        self._inventory.reserve(basket)
        order_id = self._orders.save(user_id, basket, total)
        gateway.charge(order_id, total)
        self._notifier.order_placed(user_id, total)
        return order_id

# ---- tests: fakes instead of a database, Stripe and SMTP ----
class FakeInventory:
    def __init__(self, stock): self.stock = dict(stock)
    def reserve(self, basket):
        for sku, qty in basket.items():
            if self.stock.get(sku, 0) < qty:
                raise ValueError(f"out of stock: {sku}")
        for sku, qty in basket.items():
            self.stock[sku] -= qty

class FakeGateway:
    def __init__(self): self.charged = []
    def charge(self, order_id, amount):
        self.charged.append((order_id, amount))
        return f"fake-{order_id}"

class InMemoryOrders:
    def __init__(self): self.rows = []
    def save(self, user_id, basket, total):
        self.rows.append((user_id, basket, total))
        return f"o-{len(self.rows)}"

class SpyNotifier:
    def __init__(self): self.sent = []
    def order_placed(self, user_id, total): self.sent.append((user_id, total))

def test_card_order_with_coupon():
    gateway, notifier = FakeGateway(), SpyNotifier()
    service = OrderService(FakeInventory({"book": 5}), Pricing(), {"card": gateway}, InMemoryOrders(), notifier)
    order_id = service.place_order("u1", {"book": 2}, "card", coupon="SAVE10")
    assert gateway.charged == [(order_id, 21.6)]            # 2 books = 24.00, minus 10%
    assert notifier.sent == [("u1", 21.6)]

def test_unknown_method_reserves_nothing():
    inventory = FakeInventory({"book": 5})
    service = OrderService(inventory, Pricing(), {"card": FakeGateway()}, InMemoryOrders(), SpyNotifier())
    try:
        service.place_order("u1", {"book": 1}, "bitcoin")
    except ValueError:
        pass
    assert inventory.stock == {"book": 5}

Step 3: registry, rule table and events (runnable)

import logging
from typing import Callable, Protocol

# ---- extension point 1: payment methods register themselves ----
class PaymentGateway(Protocol):
    def charge(self, order_id: str, amount: float) -> str: ...

PAYMENT_METHODS: dict[str, Callable[[], PaymentGateway]] = {}

def payment_method(name: str):
    def register(factory):
        if name in PAYMENT_METHODS:
            raise ValueError(f"payment method {name!r} is already registered")
        PAYMENT_METHODS[name] = factory
        return factory
    return register

@payment_method("card")
class CardGateway:
    def charge(self, order_id, amount):
        return f"card-{order_id}"

# ---- extension point 2: coupons are a table of rules ----
DISCOUNTS: dict[str, Callable[[float], float]] = {         # coupon code -> amount off a subtotal
    "SAVE10": lambda subtotal: subtotal * 0.10,
    "FREESHIP": lambda subtotal: 5.0,
}

class Pricing:
    PRICES = {"book": 12.0, "pen": 1.5}
    def __init__(self, discounts):
        self._discounts = discounts
    def price(self, basket, coupon=None):
        subtotal = sum(self.PRICES[sku] * qty for sku, qty in basket.items())
        if coupon is None:
            return subtotal
        rule = self._discounts.get(coupon)
        if rule is None:
            raise ValueError(f"bad coupon {coupon!r}")
        return round(subtotal - rule(subtotal), 2)

# ---- extension point 3: side effects subscribe to an event ----
class EventBus:
    def __init__(self):
        self._subs = {}
    def subscribe(self, topic, handler):
        self._subs.setdefault(topic, []).append(handler)
    def publish(self, topic, event):
        for handler in list(self._subs.get(topic, [])):
            try:
                handler(event)
            except Exception:
                logging.exception("subscriber failed")

Plugin registries

▶ Video lesson: Plugin registries 3:30 · 7 scenes · narrated, pause anytime and explore

A registry is a dict from a name to an implementation. It turns 'which implementations exist' from code (an if/elif ladder) into data, so a new variant adds itself and the core never lists them. You used one in step 3. Run the scenarios below to see registration and dispatch, and the two ways it commonly goes wrong.

Registering and dispatching plugins

Modules in the payments/ package register themselves when imported. Watch the registry grow, then look at the forgotten-import and duplicate-key scenarios.

Three ways to fill a registry

The default. The decorator runs when the module is imported, so the plugin registers where it is defined. It returns the class unchanged, so the class stays directly usable.

EXPORTERS: dict[str, type] = {}

def exporter(fmt: str):
    def register(cls):
        if fmt in EXPORTERS:
            raise ValueError(f"exporter for {fmt!r} is already registered by {EXPORTERS[fmt].__name__}")
        EXPORTERS[fmt] = cls
        return cls                                  # return the class itself, unchanged
    return register

@exporter("csv")
class CsvExporter:
    def export(self, rows):
        return [",".join(map(str, row)) for row in rows]

def export(fmt, rows):
    try:
        cls = EXPORTERS[fmt]
    except KeyError:
        raise ValueError(f"no exporter for {fmt!r}; known: {sorted(EXPORTERS)}") from None
    return cls().export(rows)

print(export("csv", [(1, "a"), (2, "b")]))          # ['1,a', '2,b']
try:
    export("xml", [])
except ValueError as e:
    print(e)                                         # no exporter for 'xml'; known: ['csv']

Zero ceremony when variants are classes anyway: Python calls __init_subclass__ on the base class every time someone subclasses it, and class keywords pass the key.

class Exporter:
    registry: dict[str, type] = {}

    def __init_subclass__(cls, *, fmt=None, **kwargs):
        super().__init_subclass__(**kwargs)
        if fmt is not None:
            if fmt in Exporter.registry:
                raise ValueError(f"{fmt!r} is already registered")
            Exporter.registry[fmt] = cls

class CsvExporter(Exporter, fmt="csv"):
    pass

class YamlExporter(Exporter, fmt="yaml"):
    pass

print(sorted(Exporter.registry), Exporter.registry["csv"].__name__)    # ['csv', 'yaml'] CsvExporter

How registries go wrong

  • Import side effects. Registration happens when the module is imported. A plugin nobody imports does not exist, as the second scenario showed. Import plugin modules explicitly at start-up, discover them with pkgutil.iter_modules and importlib.import_module, or use entry points.
  • Duplicate names. A silent overwrite means the last import wins and you debug by import order. Raise on duplicates.
  • Global mutable state. A module-level registry survives between tests. Snapshot and restore it in a fixture, or pass registries around as objects.
  • Discoverability. Put the known keys in every error message (known: ['card', 'upi']).
  • Unversioned interfaces. Plugins written by other teams outlive your refactors. Document the plugin protocol, give it a version, and fail clearly when a plugin does not satisfy it.

Feature flags

A feature flag is a runtime switch that chooses between two behaviours without a deploy. It is one more extension point, except that the variation is decided by configuration data instead of code that ships. Typical uses:

  • Dark launch. The code is deployed but off. Turn it on when ready.
  • Gradual rollout. 1%, 10%, 50%, 100% of users, watching error rates between steps.
  • Kill switch. Turn a misbehaving integration off in seconds, with no rollback.
  • Experiment. Half the users see variant B and you compare a metric.

The subtle part is deciding who is in the 10%. The simulation hashes each user into a bucket.

A sticky, monotonic rollout

Step through 10%, 25%, 50% and 100%. Cells in green are users for whom the flag is on. Notice that nobody ever drops out as the percentage rises, and that a second flag selects a different group.

A small flag service

import hashlib

class Flags:
    def __init__(self, config: dict[str, dict]):
        self._config = config                                # e.g. loaded from a file or a flag service

    def enabled(self, name: str, user_id: str | None = None) -> bool:
        cfg = self._config.get(name)
        if cfg is None or not cfg.get("on", False):
            return False                                     # unknown or switched off: fail closed
        pct = cfg.get("rollout", 100)
        if pct >= 100:
            return True
        if user_id is None or pct <= 0:
            return False
        digest = hashlib.sha256(f"{name}:{user_id}".encode()).hexdigest()
        return int(digest, 16) % 100 < pct                   # sticky: same user, same answer, on every server

users = [f"user{i}" for i in range(1000)]
on = {}
for pct in (10, 25, 50, 100):
    flags = Flags({"new_pricing": {"on": True, "rollout": pct}})
    on[pct] = {u for u in users if flags.enabled("new_pricing", u)}
print({pct: len(group) for pct, group in on.items()})         # {10: 100, 25: 253, 50: 498, 100: 1000}
assert on[10] <= on[25] <= on[50] <= on[100]                    # raising the percentage only adds users
print(Flags({}).enabled("missing", "user1"))                   # False: unknown flags are off

Decide once, pass the strategy

def build_pricing(flags, user_id):
    return PricingV2() if flags.enabled("new_pricing", user_id) else PricingV1()

service = OrderService(inventory, pricing=build_pricing(flags, user.id))   # the core never sees the flag

Rules that keep flags cheap

  • Hash, don't roll dice. A random choice per request flips a user between behaviours. Hashing flag:user_id into a bucket makes the answer sticky across requests and servers, and raising the percentage only adds users.
  • Salt with the flag name. Otherwise the same 10% of users get every experiment first.
  • Fail closed. An unknown flag, a missing config or a flag-service outage should mean 'off', the old known behaviour.
  • Decide once, at the edge. Evaluate the flag where the request enters, or at the composition root, and pass the chosen strategy down. Scattered checks multiply the code paths.
  • Flags are debt. Every live flag doubles the paths to test. Give each one an owner and an expiry, and delete the flag and the dead branch when the rollout is done.
  • Not for entitlements. Which customers may use a feature (plans, tenants, roles) is a long-lived permission, not a rollout switch.
  • Keep the service behind an interface, as Flags is above, so tests set flags directly.

Interfaces at boundaries, and testing seams

A boundary is any place where your code meets something you do not control, or that is slow or non-deterministic: the network, the disk, a database, the clock, randomness, another team's service. Put an interface on your side of each boundary, shaped by what your code needs. Production passes the real implementation and tests pass a fake. That is 'ports and adapters' (hexagonal architecture) in a sentence: the domain defines the ports, the infrastructure supplies the adapters.

The place where a test can substitute behaviour without editing the code under test is called a seam.

A clock seam

from datetime import datetime, timezone
from typing import Callable

class TokenService:
    def __init__(self, ttl_s: int, now: Callable[[], datetime] = lambda: datetime.now(timezone.utc)):
        self._ttl, self._now = ttl_s, now                    # the seam: production passes nothing, tests pass a fixed clock

    def is_expired(self, issued_at: datetime) -> bool:
        return (self._now() - issued_at).total_seconds() > self._ttl

fixed = datetime(2024, 1, 1, 12, 0, 30, tzinfo=timezone.utc)
service = TokenService(ttl_s=60, now=lambda: fixed)

assert service.is_expired(datetime(2024, 1, 1, 11, 58, 0, tzinfo=timezone.utc))       # issued 150 s ago

Fakes over mocks

A fake is a small working implementation, such as an in-memory repository. A mock records how it was called. Tests that assert outcomes against fakes (the order is saved, the stock went down) survive refactors. Tests that assert call sequences against mocks break whenever you restructure code that still behaves correctly. Keep mocks for the edges where all you care about is that something was sent. Patching with unittest.mock.patch is the last resort, for code you cannot change.

When the interviewer asks 'how would you test this?' Say: 'I put an interface on each boundary I do not control: the payment provider, the clock, the id generator. Production gets real adapters from the composition root and tests get in-memory fakes, so unit tests run in milliseconds with no network. I'd rather inject a clock than patch datetime.' Then name two tests you would write first: the happy path against fakes, and the failure path (the charge raises) asserting that nothing is left half-done.

YAGNI vs extensibility

Every extension point has a price: another interface to read, another hop in the debugger, another thing that can drift out of sync. Against it stands YAGNI ('you aren't gonna need it'). The way to reconcile the two is not a rule about how much to abstract. It is a question about evidence: do you have real variants today, and is the next one likely?

flowchart TD
  S[A requirement touches this code] --> Q1{Do two real variants exist today}
  Q1 -->|no| N1[Write the simple version in one function]
  Q1 -->|yes| Q2{Will more arrive, or will others add them}
  Q2 -->|no| N2[Extract an interface or a dict, no registry]
  Q2 -->|yes| Q3{Can the people adding them edit your repository}
  Q3 -->|yes| N3[Registry in your repo with decorator registration]
  Q3 -->|no| N4[Plugin API with a versioned interface and entry points]
Each step up costs more and needs more evidence. Stop at the first box that fits.

The rule of three. The first time, write it directly. The second time, notice the duplication and tolerate it. The third time, extract, now with three real examples to design the interface from. An abstraction designed from one example fits that example's accidents.

In an LLD round

You have about 90 minutes (The machine-coding round, step by step). Spend extension effort where the problem statement hints at change. The follow-up is almost always 'now add another vehicle type / payment method / notification channel', so make that pluggable and keep everything else plain. Say it out loud: 'I'll make payment methods pluggable because that is the likely extension; pricing stays a function until it varies.' That sentence shows judgement, which is what the round is measuring.

Say: 'I don't add an extension point until there are two real variants, or the requirements tell me a third is coming. Vehicle types and payment methods are named in the problem, so they get an interface and a registry. The clock and the id generator get a seam because tests need one. Everything else stays a plain function until a second case shows up.' Interviewers read that as the opposite of over-engineering, and it still answers 'what if we add X?'.

What to notice

  • A PDF format is @register(FORMATS, "pdf") on a new function. A weekly report is @register(QUERIES, "weekly"). A Slack destination is one more callable in the destinations dict at the composition root. No existing function is edited.

import csv
import io
import json
from datetime import date
from pathlib import Path
from typing import Callable

Rows = list[tuple[str, float]]

# Each variation point is a name -> callable table. A new variant is new code plus one registration line.
FORMATS: dict[str, Callable[[Rows], str]] = {}
QUERIES: dict[str, Callable[[date], tuple[str, tuple]]] = {}

def register(table: dict, name: str):
    def decorator(fn):
        if name in table:
            raise ValueError(f"{name!r} is already registered")
        table[name] = fn
        return fn
    return decorator

@register(FORMATS, "csv")
def to_csv(rows: Rows) -> str:
    out = io.StringIO()
    csv.writer(out).writerows(rows)
    return out.getvalue()

@register(FORMATS, "json")
def to_json(rows: Rows) -> str:
    return json.dumps([{"region": region, "total": total} for region, total in rows])

@register(QUERIES, "daily")
def daily(today: date):
    return "SELECT region, SUM(amount) FROM sales WHERE day = %s GROUP BY region", (today,)

@register(QUERIES, "monthly")
def monthly(today: date):
    return "SELECT region, SUM(amount) FROM sales WHERE month = %s GROUP BY region", (today.month,)

class SalesRepository:                                    # adapter around the database driver
    def __init__(self, connect: Callable):                # connect() returns a DB-API connection; the DSN comes from config
        self._connect = connect

    def totals(self, report_type: str, today: date) -> Rows:
        try:
            build = QUERIES[report_type]
        except KeyError:
            raise ValueError(f"unknown report {report_type!r}; known: {sorted(QUERIES)}") from None
        sql, params = build(today)
        cursor = self._connect().cursor()
        cursor.execute(sql, params)
        return cursor.fetchall()

def file_destination(directory: Path) -> Callable[..., None]:
    def send(body: str, name: str) -> None:
        (directory / name).write_text(body)
    return send

def email_destination(send_mail: Callable[[str, str], None]) -> Callable[..., None]:
    def send(body: str, to: str) -> None:
        send_mail(to, body)
    return send

def smtp_mail(host: str, sender: str) -> Callable[[str, str], None]:       # the production half of email_destination
    def send(to: str, body: str) -> None:
        import smtplib
        with smtplib.SMTP(host) as server:
            server.sendmail(sender, to, body)
    return send

class ReportService:
    def __init__(self, fetch: Callable[[str, date], Rows], formats: dict, destinations: dict,
                 today: Callable[[], date] = date.today):
        self._fetch, self._formats, self._destinations, self._today = fetch, formats, destinations, today

    def generate(self, report_type: str, fmt: str, destination: str, **options) -> None:
        render = self._pick(self._formats, fmt, "format")              # validate first: fail before any slow work
        send = self._pick(self._destinations, destination, "destination")
        rows = self._fetch(report_type, self._today())
        send(render(rows), **options)

    @staticmethod
    def _pick(table: dict, key: str, kind: str):
        try:
            return table[key]
        except KeyError:
            raise ValueError(f"unknown {kind} {key!r}; known: {sorted(table)}") from None
