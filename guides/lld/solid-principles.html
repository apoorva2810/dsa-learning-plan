SOLID principles

SOLID is five heuristics for one question: when the next requirement arrives, how much working code do you have to open? This chapter takes each principle as a realistic Python violation and its fix, draws the fixed design, names the smell that gives the violation away, and gives the interview question that probes it. Two simulations count the cost of change in a god class and show a broken subtype contract, and a decision flowchart helps you name the principle from the symptom.

After this chapter you can
  • Apply SRP by asking which actor requests changes, and split a class along those lines without over-splitting
  • Replace a type-switch ladder with polymorphism or a registry, and explain which axis of change the design is closed against
  • State a subtype contract (preconditions, postconditions, exceptions) and enforce it with a contract test
  • Split a wide interface into role Protocols declared by the clients that use them
  • Invert a dependency on a vendor SDK with a port owned by the domain, and explain how DIP differs from dependency injection
  • Name the violated principle from a symptom, and say when applying SOLID would be over-engineering

What SOLID is for

SOLID is five design principles for object-oriented code, collected by Robert C. Martin around 2000; the acronym came a few years later, from Michael Feathers. None of them is a law. Each is a heuristic for one question: when the next requirement arrives, how much working code do you have to open?

LetterPrincipleThe question it asks
SSingle responsibilityWho asks for changes to this class?
OOpen/closedCan I add the next variant without editing old code?
LLiskov substitutionCan every subtype stand in for its base without surprises?
IInterface segregationDoes each client see only the methods it uses?
DDependency inversionDo business rules depend on details, or the other way round?

Interviewers rarely ask you to recite these. They test them by changing the requirements halfway through: 'now add gift cards', 'now make it testable without Stripe', 'some carriers cannot take heavy parcels'. Your design either absorbs the change in one new class or it does not. Each section below gives the principle in one line, a realistic violation in Python, the fix, the fixed design as a class diagram, the smell that gives the violation away, and the interview question that probes it.

The five are not independent. Step through how they support each other.

Four principles feed one payoff: the next requirement lands as new code in one place.

If an interviewer asks 'is this SOLID?', do not walk through all five letters. Name the one the current requirement stresses and show the change: 'a new payment method is one new class and one registry line, so checkout is closed for modification'. A principle is only convincing when it is attached to a concrete change.

S: Single responsibility

▶ Video lesson: S and O: one reason to change, add instead of edit 4:34 · 7 scenes · narrated, pause anytime and explore

One line: a class should have one reason to change. Martin's sharper version: it should answer to one actor, one person or team who requests changes to it.

'One reason to change' is easy to misread as 'does one thing', which leads to classes with one method each. The useful test is about people. List who would ask for changes to the class. If finance (tax rules), the design team (invoice layout), the platform team (storage) and the CRM team (email delivery) would all edit the same file, four schedules collide in it.

The danger is worse than merge conflicts. Code that serves two actors tends to share helpers, and a change made for one actor silently changes behaviour for the other. Below, _rounded serves both the tax total and the printed line prices. The design team asks for whole rupees on the printed lines, a developer edits _rounded, and the tax total changes in the same commit. Finance finds out at month end.

One class for four teams, or one class per team

Violation: Invoice answers to four actors

Tax, layout, storage and email in one class. The shared _rounded couples finance to design.

import smtplib
import sqlite3
from decimal import ROUND_HALF_UP, Decimal

class Invoice:
    def __init__(self, email: str, lines: list[tuple[str, int, int]]) -> None:
        self.email = email
        self.lines = lines                      # (description, qty, unit price in paise)

    def _rounded(self, paise: Decimal) -> int:  # shared by tax AND printed prices
        return int(paise.quantize(Decimal(1), rounding=ROUND_HALF_UP))

    def total(self) -> int:                     # finance: GST at 18%
        subtotal = sum(qty * price for _, qty, price in self.lines)
        return self._rounded(Decimal(subtotal) * Decimal("1.18"))

    def render_html(self) -> str:               # design team: layout
        rows = "".join(f"<tr><td>{d}</td><td>{self._rounded(Decimal(q * p)) / 100:.2f}</td></tr>"
                       for d, q, p in self.lines)
        return f"<table>{rows}</table><p>Total {self.total() / 100:.2f}</p>"

    def save(self) -> None:                     # platform team: storage
        with sqlite3.connect("billing.db") as db:
            db.execute("INSERT INTO invoices (email, total) VALUES (?, ?)",
                       (self.email, self.total()))

    def send(self) -> None:                     # CRM team: delivery
        with smtplib.SMTP("smtp.example.com") as smtp:
            smtp.sendmail("billing@example.com", self.email, self.render_html())

# Design wants whole rupees on the printed lines, so someone edits _rounded.
# total() uses it too: finance's numbers change in the same commit.

Fix: one class per actor, plus a coordinator

Each class answers to one team. The service only sequences the steps.

from dataclasses import dataclass
from decimal import ROUND_HALF_UP, Decimal
from typing import Protocol

@dataclass(frozen=True)
class Line:
    description: str
    qty: int
    unit_paise: int

@dataclass(frozen=True)
class Invoice:                                  # finance: amounts and tax
    email: str
    lines: tuple[Line, ...]
    gst_percent: int = 18

    def subtotal(self) -> int:
        return sum(line.qty * line.unit_paise for line in self.lines)

    def total(self) -> int:
        exact = Decimal(self.subtotal() * (100 + self.gst_percent)) / 100
        return int(exact.quantize(Decimal(1), rounding=ROUND_HALF_UP))

class HtmlRenderer:                             # design team: layout and display rounding
    def render(self, inv: Invoice) -> str:
        rows = "".join(f"<tr><td>{line.description}</td><td>₹{line.qty * line.unit_paise // 100}</td></tr>"
                       for line in inv.lines)
        return f"<table>{rows}</table><p>Total ₹{inv.total() / 100:.2f}</p>"

class InvoiceRepository(Protocol):             # platform team implements this
    def add(self, inv: Invoice) -> None: ...

class Mailer(Protocol):                         # CRM team implements this
    def send(self, to: str, html: str) -> None: ...

class InvoiceService:                           # sequences the steps, owns no rules
    def __init__(self, repo: InvoiceRepository, renderer: HtmlRenderer, mailer: Mailer) -> None:
        self._repo, self._renderer, self._mailer = repo, renderer, mailer

    def issue(self, inv: Invoice) -> None:
        self._repo.add(inv)
        self._mailer.send(inv.email, self._renderer.render(inv))

The smell. You need 'and' to describe the class: it computes totals and renders and stores and emails. Requests from different teams land in the same file. Testing a pure rule, such as tax, needs a database or an SMTP server. Groups of methods share no fields with each other; Extensibility & modularity shows how to find those groups mechanically with a methods-by-fields matrix.

Do not over-split. SRP is about reasons to change, not method counts. Invoice.subtotal and Invoice.total change together, for the same people, so they stay together. A class per method gives you more files with the same coupling.

Interviewer: 'Finance wants 12% GST on books, and design wants a new invoice layout. Which classes change?' Strong answer: 'One each. The tax rule lives in Invoice and the layout in HtmlRenderer, so neither change opens the other's file. The tax test needs no database or mail server, because storage and delivery sit behind interfaces. InvoiceService does not change at all: it only sequences the steps.'

O: Open/closed

One line: a class should be open for extension and closed for modification. Add a new variant by adding code; do not edit code that already works and is already tested. Bertrand Meyer stated the principle in 1988; the reading used today, extension through polymorphism, is Martin's.

The classic violation is a type switch: a string such as method that the code branches on in several places. Each new value means finding every ladder and adding a branch, and missing one is a run-time ValueError: unknown method in a path that worked yesterday. The fix moves the body of each branch into its own class behind one interface. The ladder disappears, because each object already knows how to behave.

A ladder per operation, or a class per variant

Violation: three ladders on the method name

Gift cards mean a new branch in pay, refund and fee, inside a class that works today.

class Checkout:
    def pay(self, method: str, amount: int) -> str:
        if method == "card":
            return card_gateway.charge(amount)
        elif method == "upi":
            return upi_gateway.collect(amount)
        raise ValueError(f"unknown method {method}")

    def refund(self, method: str, payment_id: str) -> None:
        if method == "card":
            card_gateway.refund(payment_id)
        elif method == "upi":
            upi_gateway.reverse(payment_id)
        else:
            raise ValueError(f"unknown method {method}")

    def fee(self, method: str, amount: int) -> int:
        if method == "card":
            return amount * 2 // 100            # 2%
        elif method == "upi":
            return 0
        raise ValueError(f"unknown method {method}")

# Adding gift cards edits all three methods.
# Forget one, and gift-card refunds fail in production.

Fix: one class per method, behind one interface

Checkout calls the interface. A new variant is a new class plus one registry entry.

from abc import ABC, abstractmethod

class PaymentMethod(ABC):
    @abstractmethod
    def charge(self, amount: int) -> str: ...
    @abstractmethod
    def refund(self, payment_id: str) -> None: ...
    @abstractmethod
    def fee(self, amount: int) -> int: ...

class Card(PaymentMethod):
    def charge(self, amount): return card_gateway.charge(amount)
    def refund(self, payment_id): card_gateway.refund(payment_id)
    def fee(self, amount): return amount * 2 // 100

class Upi(PaymentMethod):
    def charge(self, amount): return upi_gateway.collect(amount)
    def refund(self, payment_id): upi_gateway.reverse(payment_id)
    def fee(self, amount): return 0

PAYMENT_METHODS: dict[str, type[PaymentMethod]] = {"card": Card, "upi": Upi}

class Checkout:
    def pay(self, method_name: str, amount: int) -> str:
        try:
            method = PAYMENT_METHODS[method_name]()   # the one lookup, at the edge
        except KeyError:
            raise ValueError(f"unknown method {method_name!r}") from None
        return method.charge(amount)

# The new requirement: one new class and one entry. Checkout is not opened.
class GiftCard(PaymentMethod):
    def charge(self, amount): return gift_ledger.debit(amount)
    def refund(self, payment_id): gift_ledger.credit(payment_id)
    def fee(self, amount): return 0

PAYMENT_METHODS["gift_card"] = GiftCard

Principles are easiest to judge by counting. Four requests, two designs: where do the edits land?

Run the god class first, then the open/closed design. Compare the badge on OrderService with the badge on Checkout, and look at what request 4 costs in each.

The smell. An if/elif or match on a type code (kind, type, method, channel) that appears in more than one place and grows with every variant. Adding one variant edits several files, which is called shotgun surgery. A raise ValueError("unknown ...") at the end of each ladder is the giveaway.

One switch is fine. Something has to turn the string "gift_card" from the request into a GiftCard object. Do it once, at the edge, in a factory or a registry (Creational patterns), and never in the business logic.

You cannot close against everything. The fourth request added an operation, and it cost more in the open/closed design. Choose the axis to close from the requirements. If new payment methods arrive every quarter, close against those. If new reports over a fixed set of methods arrive every week, a function per report with a match on the method can be the better design. Saying this out loud separates a reasoned answer from a recited one.

Interviewer: 'How would you add a new payment method?' Strong answer: 'Write GiftCard(PaymentMethod) with charge, refund and fee, and register it under "gift_card". Checkout, refunds and fees do not change, so their tests do not need re-reading. The only shared edit is the registry entry, and a registration decorator moves even that into the new module.' Then name the cost you accepted: a new operation on every method touches every class.

L: Liskov substitution

▶ Video lesson: L and I: keep the promise, and promise less 4:10 · 6 scenes · narrated, pause anytime and explore

One line: code that works with a base type must keep working when it is handed any subtype, without knowing which one it got. Barbara Liskov stated the idea in 1987, and with Jeannette Wing she later defined it as behavioural subtyping.

Real-world 'is-a' is not enough. A subtype must keep the base type's promises, which come down to four rules:

  • Preconditions cannot be strengthened. A subtype accepts every input the base accepts.
  • Postconditions cannot be weakened. A subtype delivers everything the base promises about its results.
  • Invariants are preserved. Whatever is always true of the base (a balance is never negative) stays true.
  • No new exceptions. A subtype does not raise errors that callers of the base have no reason to expect.

Here is a shipping module. The base class promises a price for any parcel weight. Two subclasses break that promise in different ways, and the bugs surface in cheapest(), which is correct and mentions neither subclass.

A promise broken by two subclasses, and the contract that fixes it

Violation: one subclass raises, one returns a magic 0

LetterPost strengthens the precondition. Freight weakens the postcondition.

import math

class ShippingRate:
    def quote(self, weight_kg: float) -> int:
        """Price in rupees for any weight above zero."""
        raise NotImplementedError

class Courier(ShippingRate):
    def quote(self, weight_kg):
        return 60 + 12 * math.ceil(weight_kg)

class LetterPost(ShippingRate):
    def quote(self, weight_kg):
        if weight_kg > 2:
            raise ValueError("2 kg at most")   # the base never said quote() raises
        return 40

class Freight(ShippingRate):
    def quote(self, weight_kg):
        if weight_kg < 20:
            return 0                           # means 'not for me'; callers read 'free'
        return 150 + 4 * math.ceil(weight_kg)

def cheapest(rates: list[ShippingRate], weight_kg: float) -> int:
    return min(rate.quote(weight_kg) for rate in rates)

# cheapest(rates, 3)   -> ValueError from LetterPost
# cheapest(rates, 0.5) -> 0 from Freight: free delivery, refused parcel

Fix: the contract says how a carrier declines

Declining is part of the base contract, so no subclass needs to surprise anyone.

import math
from abc import ABC, abstractmethod

class ShippingRate(ABC):
    @abstractmethod
    def quote(self, weight_kg: float) -> int | None:
        """Price in rupees, or None if this carrier cannot take the parcel.
        Never raises for a weight above zero."""

class Courier(ShippingRate):
    def quote(self, weight_kg):
        return 60 + 12 * math.ceil(weight_kg)

class LetterPost(ShippingRate):
    MAX_KG = 2

    def quote(self, weight_kg):
        return 40 if weight_kg <= self.MAX_KG else None

class Freight(ShippingRate):
    MIN_KG = 20

    def quote(self, weight_kg):
        if weight_kg < self.MIN_KG:
            return None
        return 150 + 4 * math.ceil(weight_kg)

class NoCarrier(Exception):
    pass

def cheapest(rates: list[ShippingRate], weight_kg: float) -> int:
    quotes = [q for rate in rates if (q := rate.quote(weight_kg)) is not None]
    if not quotes:
        raise NoCarrier(f"nobody ships {weight_kg} kg")   # one documented failure
    return min(quotes)

What Python checks, and what it does not

mypy and pyright compare signatures. An override that narrows a parameter type, or widens the return type, is reported as an incompatible override, and mypy's documentation explains the error in terms of the Liskov substitution principle. Both broken subclasses above pass that check, because their signatures match the base. Behaviour is the part that needs a test, and the cheapest one is a contract test: a single test, parametrised over every subclass, that checks the base class's promises.

import pytest

CARRIERS = [Courier(), LetterPost(), Freight()]

@pytest.mark.parametrize("rate", CARRIERS, ids=lambda r: type(r).__name__)
@pytest.mark.parametrize("kg", [0.1, 2, 3, 25, 400])
def test_quote_contract(rate, kg):
    price = rate.quote(kg)                       # must not raise
    assert price is None or (isinstance(price, int) and price > 0)

The smell. An override that raises NotImplementedError, or silently does nothing, for a method the base promises. isinstance(x, SomeSubclass) checks in callers, there to special-case one subtype. Docstrings that say 'do not call save() on this one'. A subclass that needs extra set-up before its methods work. Tests that skip one subclass.

The textbook case is Square(Rectangle). With setters, code that sets the width to 2 and the height to 5 expects an area of 10; a square that keeps its sides equal reports 25. Geometry says a square is a rectangle. LSP says a mutable square is not a mutable rectangle, because it cannot keep the promise that width and height change independently.

Interviewer: 'Can Square extend Rectangle?' Strong answer: 'Only if neither can be mutated. If Rectangle has set_width and set_height, callers rely on the two being independent, and a square must break that to stay square. So I would make both immutable value objects, where a square is just a rectangle with equal sides, or make them siblings under a Shape with area(). In general I ask what callers of the base rely on, not whether the nouns sound like is-a.'

I: Interface segregation

One line: no client should be forced to depend on methods it does not use. Split wide interfaces into small role interfaces, each named after what one kind of client needs.

Wide interfaces usually start as 'everything the storage vendor can do'. Below, BlobStore has six abstract methods. A read-only CDN mirror must implement all six, so it stubs five with raise NotImplementedError: an LSP violation waiting to fire for any caller that trusts the interface. The thumbnail job uses two methods, but its test fake must provide six. Every change to set_retention pulls the thumbnail code into the review, although it never calls it.

One interface for every client, or one per role

Violation: six methods for everyone

The mirror stubs what it cannot do. The worker depends on four methods it never calls.

from abc import ABC, abstractmethod

class BlobStore(ABC):
    @abstractmethod
    def get(self, key: str) -> bytes: ...
    @abstractmethod
    def put(self, key: str, data: bytes) -> None: ...
    @abstractmethod
    def delete(self, key: str) -> None: ...
    @abstractmethod
    def list_keys(self, prefix: str) -> list[str]: ...
    @abstractmethod
    def signed_url(self, key: str, ttl_s: int) -> str: ...
    @abstractmethod
    def set_retention(self, prefix: str, days: int) -> None: ...

class CdnMirror(BlobStore):                 # read-only, forced to claim six methods
    def get(self, key): return http_get(f"https://cdn.example.com/{key}")
    def put(self, key, data): raise NotImplementedError("read-only")
    def delete(self, key): raise NotImplementedError("read-only")
    def list_keys(self, prefix): raise NotImplementedError
    def signed_url(self, key, ttl_s): raise NotImplementedError
    def set_retention(self, prefix, days): raise NotImplementedError

class ThumbnailWorker:
    def __init__(self, store: BlobStore) -> None:   # calls 2 methods, depends on 6
        self.store = store

    def run(self, key: str) -> None:
        self.store.put(f"thumbs/{key}", shrink(self.store.get(key)))

Fix: role Protocols declared by the clients

Each client names the methods it calls. Implementations claim only what they can do.

from typing import Protocol

class Reader(Protocol):
    def get(self, key: str) -> bytes: ...

class Writer(Protocol):
    def put(self, key: str, data: bytes) -> None: ...

class ReadWriter(Reader, Writer, Protocol):
    pass

class ThumbnailWorker:
    def __init__(self, store: ReadWriter) -> None:  # exactly the two methods it calls
        self.store = store

    def run(self, key: str) -> None:
        self.store.put(f"thumbs/{key}", shrink(self.store.get(key)))

class CdnMirror:                                    # no stubs: it only has get()
    def get(self, key: str) -> bytes:
        return http_get(f"https://cdn.example.com/{key}")

class FakeStore:                                    # the whole test double
    def __init__(self) -> None:
        self.blobs: dict[str, bytes] = {}

    def get(self, key: str) -> bytes:
        return self.blobs[key]

    def put(self, key: str, data: bytes) -> None:
        self.blobs[key] = data

# S3Store keeps all six methods and satisfies every protocol
# above without inheriting from any of them.

The smell. Implementations full of raise NotImplementedError or empty bodies. Test fakes, or MagicMocks, standing in for methods the code under test never calls. An interface named after a vendor or an implementation (S3StoreInterface) rather than a role (Reader). Unrelated clients pulled into a review whenever the wide interface changes.

Python makes the fix cheap. A Protocol can be declared next to the client that needs it, and existing classes match it structurally, so splitting an interface never forces you to edit the implementations. The standard library works this way: collections.abc.Sized, Iterable and Container each require one method, and Collection combines them. Do not go to the other extreme: a protocol per method for a class with a single client is noise. Split when two clients need different subsets.

Interviewer: 'The Printer interface has print, scan and fax. The new kiosk device only prints. What do you do?' Strong answer: 'Split by client role into Printer, Scanner and Fax protocols. The kiosk implements Printer, the office machine implements all three, and each client takes the one it uses. Stubbing scan() on the kiosk to raise would also break LSP, because any caller that trusts the wide interface would crash on it.'

D: Dependency inversion

▶ Video lesson: D: point the arrows at the rules 3:48 · 7 scenes · narrated, pause anytime and explore

One line: high-level policy should not depend on low-level details. Both should depend on an abstraction, and the abstraction belongs to the policy side.

Policy is the code that would survive a change of vendor: 'an order is paid before it is saved; amounts must be positive'. Details are the payment SDK, the database driver and the email library. When the order module imports stripe and psycopg, the arrows point from policy to details. A change in a detail ripples into the rules, and testing a rule needs the network.

Inversion means two things. The order package declares the interfaces it needs, in its own words (PaymentGateway.charge(amount), not Stripe's PaymentIntent), and the adapters, not the rules, import the vendor libraries. The import arrow between an adapter and the policy then points from the detail to the policy.

Rules that import the vendor, or a vendor that adapts to the rules

Violation: the rules build their own details

Testing 'amount must be positive' needs STRIPE_KEY, DATABASE_URL and two mock.patch calls.

import os

import psycopg
import stripe

class OrderService:
    def __init__(self) -> None:
        stripe.api_key = os.environ["STRIPE_KEY"]              # vendor set-up in the rules
        self.db = psycopg.connect(os.environ["DATABASE_URL"])  # a real database, every time

    def place(self, user_id: int, amount: int) -> str:
        if amount <= 0:
            raise ValueError("amount must be positive")
        intent = stripe.PaymentIntent.create(amount=amount, currency="inr")
        with self.db.transaction():
            self.db.execute(
                "INSERT INTO orders (user_id, amount, charge_id) VALUES (%s, %s, %s)",
                (user_id, amount, intent.id))
        return intent.id

Fix: ports owned by the domain, adapters outside

The rules import only their own ports. The adapter imports both the port's shape and the SDK.

# orders/ports.py: owned by the orders package, no vendor imports
from typing import Protocol

class PaymentGateway(Protocol):
    def charge(self, amount: int) -> str: ...         # returns a charge id

class OrderRepository(Protocol):
    def add(self, user_id: int, amount: int, charge_id: str) -> None: ...

# orders/service.py: the rules
class OrderService:
    def __init__(self, payments: PaymentGateway, orders: OrderRepository) -> None:
        self._payments = payments
        self._orders = orders

    def place(self, user_id: int, amount: int) -> str:
        if amount <= 0:
            raise ValueError("amount must be positive")
        charge_id = self._payments.charge(amount)
        self._orders.add(user_id, amount, charge_id)
        return charge_id

# adapters/stripe_gateway.py: the detail fits the port
class StripeGateway:
    def __init__(self, stripe_module) -> None:
        self._stripe = stripe_module

    def charge(self, amount: int) -> str:
        return self._stripe.PaymentIntent.create(amount=amount, currency="inr").id

DIP is not the same as dependency injection. Injection is a technique: pass collaborators in instead of building them inside. You can inject a concrete Stripe client and still have the order rules shaped by Stripe's API. DIP is about ownership and direction: the rules define the interface in their own terms, and details adapt to it. Injection is the usual way to deliver the adapter. Extensibility & modularity covers injection, composition roots and test seams in depth.

The smell. Business modules that import vendor SDKs, drivers, requests, smtplib or boto3, or read os.environ. Constructors that build their own collaborators. Tests full of mock.patch("orders.service.stripe"): patching a module's internals means the seam is missing. Interfaces that mirror the vendor (create_payment_intent(...)) instead of the need (charge(amount)).

Do not invert everything. The standard library, dataclasses and pure helpers are details too, but they are stable and free of side effects. Put an interface where something is volatile (a vendor you might switch), slow (network, disk) or non-deterministic (the clock, random numbers).

Interviewer: 'How do you unit-test OrderService without calling Stripe?' Strong answer: 'OrderService depends on a PaymentGateway protocol that the orders package defines. In production main.py passes a StripeGateway adapter; in tests I pass a FakeGateway that records charges and can be told to fail. There is no patching. Switching provider is a new adapter, and the order rules and their tests do not change.'

Over-applying SOLID (click each)

A class per method (SRP taken literally)

Splitting by method instead of by actor scatters one concept across files that always change together. If two classes are always edited in the same commit, for the same person, merge them.

An interface with one implementation 'for later' (OCP and DIP)

An interface earns its place when there are two implementations (a test fake counts), or when it guards a volatile, slow or non-deterministic boundary. Otherwise it is indirection with no payoff. With Protocol, extracting the interface later is a small change, so wait for the second variant.

A plugin registry for two variants that never change

Two payment methods that have not changed in three years do not need a registry; a two-branch if inside one factory function is fine. Introduce the registry at the third variant, or when other teams need to add variants without editing your code.

A protocol per method (ISP taken literally)

Split an interface when two clients need different subsets. A class with one client and three methods that are always used together needs one protocol, not three.

Deep inheritance to stay 'open'

GiftCard(Card(PaymentMethod)) chains make every subclass depend on how its parents work (the fragile base class problem). Keep one level of implementation behind an interface and compose the shared parts.

import smtplib

class Channel:
    def send(self, to: str, text: str) -> None: raise NotImplementedError
    def send_bulk(self, to: list[str], text: str) -> None: raise NotImplementedError
    def schedule(self, to: str, text: str, at: str) -> None: raise NotImplementedError

class EmailChannel(Channel):
    def send(self, to, text):
        with smtplib.SMTP("smtp.example.com") as smtp:
            smtp.sendmail("noreply@example.com", to, text)
    def send_bulk(self, to, text):
        for address in to:
            self.send(address, text)
    def schedule(self, to, text, at):
        raise NotImplementedError("email cannot be scheduled")

    def send(self, to, text):

        sms_vendor_send(to, text)

Reference solution (open after your attempt)

Design notes. NotificationService depends on three small protocols and two dicts, so new channels and events are data, not code edits (OCP). Wording lives in TEMPLATES, delivery in the adapters and auditing behind AuditLog (SRP). The 160-character rule became part of the Sender contract, so Sms shortens instead of raising (LSP). BulkSender is separate, so Sms is never forced to stub send_bulk, and run_campaign cannot be handed a sender that lacks it (ISP). The adapters receive their vendor clients and the service receives the adapters, so the tests use fakes and no patching (DIP). In an interview, say which of these you would do first if time ran out: the senders dict and the injected audit log, because they unlock testing.

import smtplib
from dataclasses import dataclass
from typing import Protocol


# ---- contracts, owned by the notifications package -----------------------------
class Sender(Protocol):
    def send(self, to: str, text: str) -> None: ...        # shortens text it cannot fit; never raises for length


class BulkSender(Protocol):
    def send_bulk(self, to: list[str], text: str) -> None: ...


class AuditLog(Protocol):
    def record(self, line: str) -> None: ...


@dataclass(frozen=True)
class User:
    id: str
    channel: str                                            # "email", "sms", "push", ...
    address: str                                            # email address, phone number or device token


# ---- wording: one place, one reason to change ---------------------------------
TEMPLATES: dict[str, str] = {
    "order_placed": "Order {order_id} confirmed",
    "order_shipped": "Order {order_id} is on its way",
}


def render(event: str, order_id: str) -> str:
    try:
        return TEMPLATES[event].format(order_id=order_id)
    except KeyError:
        raise ValueError(f"unknown event {event!r}; known: {sorted(TEMPLATES)}") from None


# ---- dispatch: closed for modification -----------------------------------------
class NotificationService:
    def __init__(self, senders: dict[str, Sender], audit: AuditLog) -> None:
        self._senders = dict(senders)
        self._audit = audit

    def notify(self, user: User, event: str, order_id: str) -> None:
        text = render(event, order_id)
        try:
            sender = self._senders[user.channel]
        except KeyError:
            raise ValueError(f"no sender for {user.channel!r}; known: {sorted(self._senders)}") from None
        sender.send(user.address, text)
        self._audit.record(f"{event} {order_id} {user.id}")


def run_campaign(sender: BulkSender, addresses: list[str], text: str) -> None:
    sender.send_bulk(addresses, text)                      # only senders that really support bulk fit here


# ---- adapters: details that fit the contracts ----------------------------------
class SmtpEmail:                                            # Sender and BulkSender
    def __init__(self, host: str, from_addr: str = "noreply@example.com") -> None:
        self._host, self._from = host, from_addr

    def send(self, to: str, text: str) -> None:
        self.send_bulk([to], text)

    def send_bulk(self, to: list[str], text: str) -> None:
        with smtplib.SMTP(self._host) as smtp:
            for address in to:
                smtp.sendmail(self._from, address, text)


class Sms:                                                  # Sender only: no bulk, no stubs
    LIMIT = 160

    def __init__(self, client) -> None:                     # the vendor client is injected
        self._client = client

    def send(self, to: str, text: str) -> None:
        if len(text) > self.LIMIT:
            text = text[: self.LIMIT - 1] + "…"             # the contract: shorten, never raise
        self._client.send(to, text)


class FileAudit:
    def __init__(self, path: str) -> None:
        self._path = path

    def record(self, line: str) -> None:
        with open(self._path, "a", encoding="utf-8") as f:
            f.write(line + "\n")


# ---- tests with fakes only -------------------------------------------------------
class FakeSender:
    def __init__(self) -> None:
        self.sent: list[tuple[str, str]] = []

    def send(self, to: str, text: str) -> None:
        self.sent.append((to, text))


class ListAudit:
    def __init__(self) -> None:
        self.lines: list[str] = []

    def record(self, line: str) -> None:
        self.lines.append(line)


email, sms, audit = FakeSender(), FakeSender(), ListAudit()
service = NotificationService({"email": email, "sms": sms}, audit)
service.notify(User("u1", "email", "ann@example.com"), "order_placed", "A1")
assert email.sent == [("ann@example.com", "Order A1 confirmed")]
assert audit.lines == ["order_placed A1 u1"]

# a new channel and a new event: no edit to NotificationService
push = FakeSender()
TEMPLATES["order_delivered"] = "Order {order_id} was delivered"
service = NotificationService({"email": email, "sms": sms, "push": push}, audit)
service.notify(User("u2", "push", "device-9"), "order_delivered", "A2")
assert push.sent == [("device-9", "Order A2 was delivered")]

# LSP: SMS shortens long text instead of raising
class RecordingClient:
    def __init__(self) -> None:
        self.texts: list[str] = []

    def send(self, to: str, text: str) -> None:
        self.texts.append(text)

client = RecordingClient()
Sms(client).send("+910000000000", "x" * 500)
assert len(client.texts[0]) == Sms.LIMIT
