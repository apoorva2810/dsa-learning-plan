OOP foundations in Python

LLD interviewers use small object models to see whether you can protect invariants, choose between inheritance and composition, and write contracts that other code can rely on. This chapter covers the Python tools for that: properties, composition, polymorphism and duck typing, ABC versus Protocol, dataclasses with correct equality and hashing, the method resolution order behind super(), and alternative constructors.

After this chapter you can
  • Protect an object's invariants with a narrow public API and properties, and explain why name mangling is not privacy
  • Choose inheritance or composition from the shape of the variation, and show the subclass explosion composition avoids
  • Replace an isinstance ladder with polymorphism, and explain duck typing
  • Pick between abc.ABC and typing.Protocol for an interface and defend the choice in one sentence
  • Write value objects with dataclasses, keep __eq__ and __hash__ consistent, and say what __slots__ buys
  • Work out a class's MRO by C3 linearisation and predict what super() calls next

What an LLD interviewer looks for in your classes

An object bundles state with the code that is allowed to change it. When an interviewer asks you to design a parking lot, a cache or a booking system, they are not checking that you can recite the four pillars. They are watching for four things:

  • Responsibilities. Each class has one job that you can state in a sentence.
  • Boundaries. It is clear which class owns which data, and callers cannot corrupt it.
  • Extensibility. A new requirement (a premium plan, a second payment gateway) lands as a small, local change.
  • Idiomatic Python. Properties instead of getters, dataclasses for plain data, protocols or ABCs for contracts. No Java written in Python syntax.

The classic pillars are tools for those four goals. Encapsulation protects invariants. Abstraction lets callers depend on what an object does instead of how it does it. Inheritance shares code and expresses is-a. Polymorphism lets one call site work with many implementations.

You will express designs as class diagrams. Step through the legend once, so the arrows here and in every other LLD chapter are familiar.

Encapsulation: guard the invariants, not the secrets

▶ Video lesson: Encapsulation: guard the rules, not the secrets 3:41 · 7 scenes · narrated, pause anytime and explore

Encapsulation means an object's data can only change through code that checks the rules. Those rules are the object's invariants: a balance never goes negative, a booking starts before it ends, a cart holds at most 50 lines. If any caller can write to the fields directly, every caller has to remember the rules, and one of them will forget.

Python has no private keyword. It has three naming conventions, and only the third is touched by the language:

SpellingMeaningEnforced by
namepublic API, callers may use itnothing
_nameinternal, may change without noticeconvention and linters
__namerenamed to _ClassName__name inside the class bodya compile-time rename

Look at what the rename does.

Name mangling is not privacy

class Account:
    def __init__(self, owner: str, balance: int = 0) -> None:
        self.owner = owner
        self.__balance = balance           # stored as _Account__balance

acct = Account("Ann", 100)
print(acct.__dict__)                       # {'owner': 'Ann', '_Account__balance': 100}
acct._Account__balance = -5                # still reachable: the rename is not a lock
print(acct.__dict__["_Account__balance"])  # -5
try:
    acct.__balance                         # the un-mangled name simply does not exist
except AttributeError as exc:
    print(exc)                             # 'Account' object has no attribute '__balance'

Double underscores exist for one narrow job: stopping a subclass from accidentally overwriting a helper attribute of its base class. They do not protect data, and an interviewer who asks 'is __x private in Python?' wants to hear exactly that. Protect invariants by design instead: no public mutable fields, validation inside the methods that change state, and defensive copies of any mutable object you hand out.

flowchart LR
  Caller[Caller code] -->|deposit 50| API[Public API<br/>deposit, withdraw, balance]
  API --> Guard{Rules hold?}
  Guard -->|no| Err[Raise ValueError]
  Guard -->|yes| State[(Private state<br/>_balance, _history)]
  Caller -.->|acct._balance = -5| State
The solid path is the only way state changes. The dotted path is possible in Python, and it is a bug in the caller, not something the language stops.

Who owns the rules?

Public fields: every caller owns the rules

Nothing stops balance going negative, and history is a list anyone can clear.

class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance
        self.history = []

acct = Account("Ann", 100)
acct.balance -= 500        # overdrawn, no error
acct.history.clear()       # audit trail erased

Narrow API: the class owns the rules

balance is read-only, history is a copy, and the rules live in withdraw.

class InsufficientFunds(Exception):
    pass

class Account:
    def __init__(self, owner: str, balance: int = 0) -> None:
        self.owner = owner
        self._balance = balance
        self._history: list[tuple[str, int]] = []

    @property
    def balance(self) -> int:
        return self._balance           # read-only: no setter

    @property
    def history(self) -> tuple:
        return tuple(self._history)    # a copy, so callers cannot edit it

    def withdraw(self, amount: int) -> None:
        if amount <= 0:
            raise ValueError("amount must be positive")
        if amount > self._balance:
            raise InsufficientFunds(self._balance)
        self._balance -= amount
        self._history.append(("withdraw", amount))

Do I write getters and setters? No. Start with a plain public attribute. If you later need validation or a computed value, turn it into a @property with the same name, and no caller changes. That is why Java-style get_x() and set_x() pairs are noise in Python.

class Product:
    def __init__(self, name: str, price: int) -> None:
        self.name = name
        self.price = price               # this assignment goes through the setter below

    @property
    def price(self) -> int:
        return self._price

    @price.setter
    def price(self, value: int) -> None:
        if value < 0:
            raise ValueError("price cannot be negative")
        self._price = value

Keep properties cheap and free of side effects, because callers assume attribute access is fast. Anything slow or with side effects should be a method with a verb name.

Inheritance versus composition

▶ Video lesson: Inheritance versus composition 4:35 · 7 scenes · narrated, pause anytime and explore

Inheritance models is-a: a subclass gets its base class's methods, fields and promises. Composition models has-a or uses-a: one object holds another and delegates to it. The advice 'favour composition over inheritance' is not a ban on subclasses. It warns about one failure: using subclasses to vary behaviour along more than one axis.

Say a report can be rendered as PDF, CSV or HTML (axis one: format) and delivered by email or Slack (axis two: channel). Step through what inheritance does to that.

One subclass per combination, or two small collaborators

Inheritance: formats x channels

Every combination is a class. Rendering and sending code is copied between them.

class Report:
    def __init__(self, rows):
        self.rows = rows

class PdfEmailReport(Report):
    def render(self): ...      # PDF logic
    def deliver(self): ...     # email logic

class PdfSlackReport(Report):
    def render(self): ...      # the same PDF logic, copied
    def deliver(self): ...     # Slack logic

class CsvEmailReport(Report):
    def render(self): ...      # CSV logic
    def deliver(self): ...     # the same email logic, copied
# ... and CsvSlack, HtmlEmail, HtmlSlack

Composition: formats + channels

Report holds a formatter and a sender. Each varies on its own.

from dataclasses import dataclass
from typing import Protocol

class Formatter(Protocol):
    def format(self, rows: list[dict]) -> bytes: ...

class Sender(Protocol):
    def send(self, name: str, payload: bytes) -> None: ...

@dataclass(frozen=True)
class Report:
    name: str
    formatter: Formatter           # chosen independently
    sender: Sender                 # of this one

    def run(self, rows: list[dict]) -> None:
        self.sender.send(self.name, self.formatter.format(rows))

class CsvFormatter:
    def format(self, rows):
        header = ",".join(rows[0]) if rows else ""
        lines = [",".join(str(v) for v in r.values()) for r in rows]
        return "\n".join([header, *lines]).encode()

class PrintSender:                 # stands in for Email or Slack
    def send(self, name, payload):
        print(f"[{name}]", payload.decode())

Report("daily", CsvFormatter(), PrintSender()).run([{"id": 1, "total": 40}])

The hidden cost of inheritance is the fragile base class. A subclass depends on how its base class works, not only on what it promises. Subclassing built-in containers shows it: list.extend does not call an overridden append, so this counter misses most additions.

class CountingList(list):
    adds = 0

    def append(self, item):
        self.adds += 1
        super().append(item)

items = CountingList()
items.append(1)
items.extend([2, 3, 4])
print(items.adds, items)     # 1 [1, 2, 3, 4]

Hold a list inside your own class and expose only the operations you intend to support. Composition makes the surface area your decision.

If asked 'inheritance or composition?', answer with the variation axes. 'There is one axis and a true is-a relationship, so a small hierarchy is fine. There are two independent axes, or I want to swap behaviour at run time, so I compose.' Then name the cost: with subclasses the class count multiplies (formats x channels), with composition it adds (formats + channels).

Polymorphism and duck typing

Polymorphism means one call site works with many implementations. shape.area() runs different code for a Circle and a Rectangle, and the caller neither knows nor cares which one it has. Python gives you three routes:

  1. Subtype polymorphism. Subclasses override a method declared on a shared base.
  2. Duck typing. There is no shared base at all. If the object has the method, the call works. 'If it walks like a duck and quacks like a duck, treat it as a duck.'
  3. Data-model hooks. Special methods such as __len__, __iter__ and __eq__ make your class work with len(), for and ==. This is polymorphism built into the language.

The smell that polymorphism removes is the isinstance ladder.

Ask the object, do not inspect its type

isinstance ladder

Every new shape means editing area, and the same ladder tends to be copied into perimeter, draw and to_json.

import math

class Circle:
    def __init__(self, radius):
        self.radius = radius

class Rectangle:
    def __init__(self, width, height):
        self.width, self.height = width, height

def area(shape):
    if isinstance(shape, Circle):
        return math.pi * shape.radius ** 2
    elif isinstance(shape, Rectangle):
        return shape.width * shape.height
    raise TypeError(f"unknown shape {shape!r}")   # a new shape edits this function

Polymorphic method

Each class knows its own area. The caller only says area().

import math

class Circle:
    def __init__(self, radius):
        self.radius = radius

    def area(self):
        return math.pi * self.radius ** 2

class Rectangle:
    def __init__(self, width, height):
        self.width, self.height = width, height

    def area(self):
        return self.width * self.height

shapes = [Circle(1), Rectangle(2, 3)]
total = sum(s.area() for s in shapes)    # a Triangle with area() needs no change here

With polymorphism the knowledge about each type lives with the type, so a new type is a new class and nothing else moves. SOLID principles calls this the open/closed principle.

Notice that Circle and Rectangle share no base class. That is duck typing: the contract is 'has an area() method' and nothing declares it. Python style is EAFP (easier to ask forgiveness than permission). Call the method, and handle AttributeError or TypeError at a boundary where you can do something about it, instead of scattering isinstance and hasattr checks. Keep the try block narrow so it cannot hide unrelated bugs.

isinstance is not banned. It is the right tool at system boundaries, such as parsing input or handling a union of types. In the middle of business logic it usually means a method is missing.

When you cannot add a method because the class belongs to someone else, functools.singledispatch gives you the same open-ended dispatch on a function:

from functools import singledispatch

@singledispatch
def describe(obj) -> str:
    return f"object {obj!r}"

@describe.register
def _(obj: int) -> str:
    return f"integer {obj}"

@describe.register
def _(obj: list) -> str:
    return f"list of {len(obj)}"

print(describe(3), describe([1, 2]), describe("x"))   # integer 3 list of 2 object 'x'

The third route, the data model, is worth a quick reference. Define the method and your object joins the language's own protocols:

Contracts: ABC versus Protocol

A contract says what an object must be able to do so that other code can rely on it. Python gives you two formal ways to write one, plus an informal third:

  • abc.ABC with @abstractmethod is nominal. A class counts as a Notifier because it inherits from Notifier. A subclass that forgot an abstract method cannot be instantiated, so you get a TypeError at construction instead of halfway through a request.
  • typing.Protocol is structural. A class counts as a Notifier if it has the right methods, whether or not it has heard of the protocol. Static checkers (mypy, pyright) verify the match. At run time nothing is enforced, and a missing method fails with AttributeError when it is called.
  • Duck typing with no declaration. The contract lives in a docstring or in the reader's head.

The same contract three ways

Nominal: inherit to join. Shared code can live in the base class.

from abc import ABC, abstractmethod

class Notifier(ABC):
    @abstractmethod
    def send(self, to: str, text: str) -> None: ...

    def send_all(self, recipients: list[str], text: str) -> None:   # shared code lives in the base
        for to in recipients:
            self.send(to, text)

class EmailNotifier(Notifier):
    def send(self, to: str, text: str) -> None:
        print(f"email to {to}: {text}")

class BrokenNotifier(Notifier):
    pass                                      # forgot send()

EmailNotifier().send_all(["ann@example.com"], "deploy done")
try:
    BrokenNotifier()                          # fails here, at construction
except TypeError as exc:
    print("TypeError:", exc)

Structural: match the shape to join. Checked by mypy or pyright, not at run time.

from typing import Protocol

class Notifier(Protocol):
    def send(self, to: str, text: str) -> None: ...

def alert_all(notifier: Notifier, recipients: list[str], text: str) -> None:
    for to in recipients:
        notifier.send(to, text)

class SlackClient:                            # does not import or inherit Notifier
    def send(self, to: str, text: str) -> None:
        print(f"slack {to}: {text}")

alert_all(SlackClient(), ["#ops"], "disk is full")   # a type checker accepts it: the shape matches

No declaration. Fine for a script, weak for a design you have to defend.

def alert_all(notifier, recipients, text):
    for to in recipients:
        notifier.send(to, text)               # anything with .send(to, text) works

class Pager:
    def send(self, to, text):
        print(f"page {to}: {text}")

alert_all(Pager(), ["oncall"], "db is down")

Neither is better. They answer different questions.

The standard library mixes both ideas. collections.abc.Sized and Iterable are ABCs that recognise any class with __len__ or __iter__, which is why isinstance([], Sized) is true with no inheritance involved.

A workable default: type function parameters with the narrowest Protocol they need, and give a family of implementations that share code an ABC base. In the interview, say which you chose in one sentence: 'I made PaymentMethod an ABC because the card and UPI classes share retry logic', or 'a Protocol, because the checkout only needs pay() and I want to fake it in tests'. Either answer is fine. Having no contract at all is not.

Value objects: dataclasses, equality, hashing and __slots__

Many classes in an LLD design are plain data with a few rules: a Money, a Seat, a Location, a Booking. Writing __init__, __repr__ and __eq__ by hand for each is noise, and the hand-written versions drift out of sync when a field is added. @dataclass generates them from annotated fields. The two options that matter in interviews are frozen and slots.

Dataclass options

Compares by value. Not hashable, because its fields are mutable.

from dataclasses import dataclass, field

@dataclass
class Seat:
    row: str
    number: int
    held_by: str | None = None
    tags: list[str] = field(default_factory=list)   # never `= []`: dataclass rejects mutable defaults

a, b = Seat("A", 1), Seat("A", 1)
print(a)               # Seat(row='A', number=1, held_by=None, tags=[])
print(a == b)          # True: fields are compared in order
print(a is b)          # False: two distinct objects
try:
    hash(a)
except TypeError as exc:
    print(exc)         # unhashable type: 'Seat'

Assignment raises FrozenInstanceError, and a matching __hash__ is generated. To 'change' a frozen value, build a new one with dataclasses.replace. Prefer this for value objects such as money, coordinates and IDs.

from dataclasses import dataclass, replace, FrozenInstanceError

@dataclass(frozen=True)
class Point:
    x: int
    y: int

p = Point(2, 3)
print(hash(p) == hash(Point(2, 3)))   # True: equal values hash equally
try:
    p.x = 5
except FrozenInstanceError as exc:
    print(exc)                         # cannot assign to field 'x'
q = replace(p, x=5)                    # a "change" is a new value
print(p, q, len({p, q}))               # Point(x=2, y=3) Point(x=5, y=3) 2

Python 3.10+. Fixed storage for the declared fields, no per-instance __dict__.

from dataclasses import dataclass

@dataclass(slots=True)
class Counter:
    count: int = 0

c = Counter()
c.count += 1
try:
    c.cnt = 1                          # a typo: with a __dict__ this silently makes a new attribute
except AttributeError:
    print("typo caught")
print(hasattr(c, "__dict__"))          # False

Two rules connect == and hashing, and interviewers like to ask about them:

  1. If a == b, then hash(a) == hash(b). Otherwise a set or dict looks in the wrong place and treats equal objects as different.
  2. An object's hash must not change while the object is in a set or used as a dict key.

Python protects you from rule 1 by default. A class that defines __eq__ without __hash__ becomes unhashable, and so does a default @dataclass. @dataclass(frozen=True) generates both consistently. Rule 2 is on you: hashing on fields that you later mutate silently breaks the container. Step through it, then switch to the frozen scenario.

A mutable key goes missing from a set

A point is stored in a set, and then its field changes. In the mutable run the set can no longer find it. In the frozen run the change is impossible, so you build a new value instead.

Dataclass equality is strict about the class: Point(1, 2) == (1, 2) is False, and an instance of a subclass does not equal an instance of its base class.

__slots__ replaces the per-instance __dict__ with fixed storage for the named attributes. You get two things. Attribute typos (p.colour = ...) raise AttributeError instead of silently creating a new attribute, and instances take less memory. How much less depends on the CPython version. Measured with tracemalloc on 3.12, an object with three int attributes cost about 192 bytes with a __dict__ and about 160 with slots, int objects included; older versions saved more. That matters with millions of instances (cells of a grid, rows of a log) and rarely otherwise, so measure before you claim it. The costs: no dynamic attributes, no weak references unless you add __weakref__, and a layout conflict if you inherit from two bases that both define non-empty slots.

super() and the method resolution order

▶ Video lesson: What super() really calls 4:20 · 6 scenes · narrated, pause anytime and explore

When a class has several bases, Python needs one fixed order in which to search for a method. That order is the method resolution order (MRO), available as ClassName.__mro__. Python computes it with the C3 linearisation algorithm, which guarantees that a class comes before its bases, that the order of bases in the class statement is respected, and that each class appears once.

super() does not mean 'my parent'. Inside a method of class B, super() means 'the next class after B in the MRO of type(self)'. For an instance of D(B, C), the next class after B is C, not A. That is what makes cooperative multiple inheritance work, and it is the usual surprise.

Calling the base by name, or cooperating through super()

Explicit base calls: A runs twice

B and C each name A, and D calls both. The shared base initialises twice.

class A:
    def __init__(self):
        print("A init")

class B(A):
    def __init__(self):
        print("B init")
        A.__init__(self)           # hard-wires the parent

class C(A):
    def __init__(self):
        print("C init")
        A.__init__(self)

class D(B, C):
    def __init__(self):
        print("D init")
        B.__init__(self)
        C.__init__(self)

D()      # D, B, A, C, A: A ran twice

Cooperative super(): every class once

Each class calls super(), so the chain follows the MRO and visits every class exactly once.

class A:
    def __init__(self, **kw):
        print("A init")
        super().__init__(**kw)     # next class in the MRO of the object

class B(A):
    def __init__(self, **kw):
        print("B init")
        super().__init__(**kw)

class C(A):
    def __init__(self, **kw):
        print("C init")
        super().__init__(**kw)

class D(B, C):
    def __init__(self, **kw):
        print("D init")
        super().__init__(**kw)

D()      # D, B, C, A: each class once
print([k.__name__ for k in D.__mro__])   # ['D', 'B', 'C', 'A', 'object']

The call chain follows D.__mro__ = D, B, C, A, object. Note that B hands over to C, its sibling, and not to its own base A.

For a class K(B1, B2) the rule is L[K] = K + merge(L[B1], L[B2], [B1, B2]), where L[x] is the linearisation of x. The merge repeatedly takes the first head (front item) that does not appear in the tail (everything after the head) of any list, appends it to the result, and deletes it from the front of every list. If no head qualifies, the declaration is inconsistent and Python raises TypeError.

Watch it work on the diamond, then try the other scenarios. Swapping the bases changes the answer, and some declarations cannot be linearised at all. The simulation cross-checks its answer against real Python classes.

C3 linearisation, one merge round at a time

Each round looks at the head of every list. A head that is still in someone's tail is rejected; the first safe head goes into the result.

Rules of thumb:

  • Call super() with no arguments, in every override that extends a base method. Skip it only when you mean to replace the base behaviour completely.
  • In a cooperative hierarchy, accept **kwargs and pass them on. Each class takes what it needs and forwards the rest. The last stop, object.__init__, accepts none, so a leftover keyword is a loud TypeError instead of a silent typo.
  • Put mixins before the main base: class Service(LoggingMixin, BaseService). The mixin comes first in the MRO, so its methods run first and can call super() to reach the real implementation.
  • Multiple inheritance is rare in interview designs. Know the diamond, the MRO and the mixin pattern. Do not volunteer a deep hierarchy.

Alternative constructors and a useful __repr__

__init__ takes the values the object stores. Callers often start from something else: a string, a dict from JSON, minutes instead of seconds. Python has one __init__, so extra ways to build an object are @classmethods, usually named from_.... The standard library uses the same idiom: datetime.fromisoformat, dict.fromkeys, int.from_bytes.

Alternative constructors and repr

class Duration:
    def __init__(self, seconds: int) -> None:
        if seconds < 0:
            raise ValueError("duration cannot be negative")
        self.seconds = seconds

    @classmethod
    def from_minutes(cls, minutes: float) -> "Duration":
        return cls(round(minutes * 60))

    @classmethod
    def from_hms(cls, text: str) -> "Duration":
        hours, minutes, seconds = (int(part) for part in text.split(":"))
        return cls(hours * 3600 + minutes * 60 + seconds)

    def __repr__(self) -> str:
        return f"{type(self).__name__}(seconds={self.seconds!r})"


class Timeout(Duration):
    pass


print(Duration.from_minutes(1.5))      # Duration(seconds=90)
print(Timeout.from_hms("0:02:03"))     # Timeout(seconds=123)
print([Timeout(5)])                    # [Timeout(seconds=5)]
from_minutes and from_hms validate through __init__, so there is one place where the rules live.

Why the factory takes cls

Hard-coded class name

A subclass calling the factory still gets the base class back.

class Duration:
    def __init__(self, seconds):
        self.seconds = seconds

    @staticmethod
    def from_minutes(minutes):
        return Duration(round(minutes * 60))     # always a Duration

class Timeout(Duration):
    pass

print(type(Timeout.from_minutes(2)).__name__)    # Duration, not Timeout

@classmethod and cls

cls is whichever class the method was called on, so subclasses inherit a working factory.

class Duration:
    def __init__(self, seconds):
        self.seconds = seconds

    @classmethod
    def from_minutes(cls, minutes):
        return cls(round(minutes * 60))          # cls is the class that was called

class Timeout(Duration):
    pass

print(type(Timeout.from_minutes(2)).__name__)    # Timeout

A @staticmethod receives neither self nor cls. It is an ordinary function that lives in the class namespace for organisation. If it needs nothing from the class, a module-level function is usually clearer.

__repr__ versus __str__. __repr__ is for developers: unambiguous, showing the type and the field values. It is what appears in tracebacks, debuggers, logs and inside containers (print([obj]) calls repr on each element). __str__ is for end users and falls back to __repr__ when it is missing, so if you write only one, write __repr__. Use !r in f-strings so strings show their quotes, and type(self).__name__ so subclasses label themselves correctly. Dataclasses generate a __repr__ for you.

Model a shopping cart that uses the ideas from this chapter.

  • Money: an immutable value object holding integer minor units and a currency. Equal values compare equal and hash equally. Money.from_str('12.50 EUR') builds one. Adding two amounts of different currencies raises ValueError.
  • LineItem: SKU, unit price and quantity, with a total property.
  • Discount: a contract with one method, amount_off(subtotal) -> Money. Provide PercentOff and FlatOff. A discount never takes off more than the subtotal.
  • Cart: add(sku, unit_price, qty), items (callers must not be able to edit the cart's list through it), subtotal() and total(), which applies the discounts in order.

Adding a brand-new discount type (for example 'round down to a whole rupee') must not require editing Cart.

Reference solution (open after your attempt)

Design notes. Money validates in __post_init__ and keeps all arithmetic in one place, so the cart never touches raw integers. Cart knows only the Discount protocol, which is why DropPaise at the bottom needed no edit to it. items returns a tuple, which is a copy. Discounts apply to the remaining amount, so order matters; say that aloud in an interview, because it is a business rule hiding in a loop.

from dataclasses import dataclass
from typing import Protocol, Sequence


@dataclass(frozen=True, slots=True)
class Money:
    amount_minor: int                      # 1250 means 12.50; integers, never floats
    currency: str = "INR"

    def __post_init__(self) -> None:
        if self.amount_minor < 0:
            raise ValueError("money cannot be negative")

    @classmethod
    def from_str(cls, text: str) -> "Money":
        # Money.from_str('12.50 EUR') -> Money(1250, 'EUR')
        number, currency = text.split()
        whole, _, frac = number.partition(".")
        return cls(int(whole) * 100 + int((frac + "00")[:2]), currency)

    def _same_currency(self, other: "Money") -> None:
        if self.currency != other.currency:
            raise ValueError(f"currency mismatch: {self.currency} vs {other.currency}")

    def __add__(self, other: object) -> "Money":
        if not isinstance(other, Money):
            return NotImplemented
        self._same_currency(other)
        return Money(self.amount_minor + other.amount_minor, self.currency)

    def __sub__(self, other: object) -> "Money":
        if not isinstance(other, Money):
            return NotImplemented
        self._same_currency(other)
        return Money(self.amount_minor - other.amount_minor, self.currency)   # raises if negative

    def __mul__(self, factor: int) -> "Money":
        return Money(self.amount_minor * factor, self.currency)


@dataclass(frozen=True, slots=True)
class LineItem:
    sku: str
    unit_price: Money
    qty: int = 1

    @property
    def total(self) -> Money:
        return self.unit_price * self.qty


class Discount(Protocol):
    def amount_off(self, subtotal: Money) -> Money: ...      # how much to subtract, never more than subtotal


@dataclass(frozen=True)
class PercentOff:
    percent: int

    def amount_off(self, subtotal: Money) -> Money:
        return Money(subtotal.amount_minor * self.percent // 100, subtotal.currency)


@dataclass(frozen=True)
class FlatOff:
    amount: Money

    def amount_off(self, subtotal: Money) -> Money:
        return Money(min(self.amount.amount_minor, subtotal.amount_minor), subtotal.currency)


class Cart:
    def __init__(self, currency: str = "INR", discounts: Sequence[Discount] = ()) -> None:
        self._currency = currency
        self._items: list[LineItem] = []
        self._discounts = tuple(discounts)

    @property
    def items(self) -> tuple[LineItem, ...]:                 # a copy: callers cannot edit our list
        return tuple(self._items)

    def add(self, sku: str, unit_price: Money, qty: int = 1) -> None:
        if qty <= 0:
            raise ValueError("quantity must be positive")
        if unit_price.currency != self._currency:
            raise ValueError("item currency does not match the cart")
        self._items.append(LineItem(sku, unit_price, qty))

    def subtotal(self) -> Money:
        total = Money(0, self._currency)
        for item in self._items:
            total = total + item.total
        return total

    def total(self) -> Money:
        remaining = self.subtotal()
        for discount in self._discounts:                      # Cart knows the protocol, not the classes
            remaining = remaining - discount.amount_off(remaining)
        return remaining

    def __repr__(self) -> str:
        return f"Cart(items={len(self._items)}, subtotal={self.subtotal()!r})"


# A new discount type: no edit to Cart.
@dataclass(frozen=True)
class DropPaise:
    def amount_off(self, subtotal: Money) -> Money:
        return Money(subtotal.amount_minor % 100, subtotal.currency)


cart = Cart(discounts=[PercentOff(10), FlatOff(Money.from_str("5.00 INR")), DropPaise()])
cart.add("pen", Money.from_str("20.50 INR"), qty=3)
cart.add("pad", Money.from_str("45 INR"))
assert cart.subtotal() == Money(10650)
# 10% of 106.50 = 10.65 -> 95.85; flat 5.00 -> 90.85; DropPaise -> 90.00
assert cart.total() == Money(9000), cart.total()
assert len({Money(100), Money(100), Money(100, "EUR")}) == 2
assert len(cart.items) == 2
