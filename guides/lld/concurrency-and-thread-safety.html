Concurrency & thread safety

Many LLD questions hide a shared-state race: two users book the same seat, two threads update one balance, a retried request charges twice. This chapter lets you watch an interleaving go wrong, explains what the GIL does and does not protect, and walks through Lock, RLock, Semaphore, Condition, Event and Queue, deadlock and its fixes, lock granularity, compare-and-swap, immutability, message passing, thread pools and idempotency. It ends with the classic double-booking problem, solved in memory and in the database.

After this chapter you can
  • Explain what the GIL protects and what it does not, and why read-modify-write and check-then-act code still races
  • Choose between threads, processes and asyncio for an I/O-bound or a CPU-bound workload
  • Pick the right primitive (Lock, RLock, Semaphore, Condition, Event, Queue) for a sharing problem and keep critical sections small
  • Recognise the four conditions for deadlock and break one with lock ordering, timeouts or try-lock
  • Prevent double booking with a per-seat lock, optimistic locking and database guards (conditional UPDATE, SELECT ... FOR UPDATE, unique constraint)
  • Make retried operations idempotent so a repeated request cannot repeat its effect

Threads, processes, asyncio and the GIL

Concurrency means several tasks are in progress during the same period. Parallelism means several tasks run at the same instant on different cores. Thread-safety questions are about concurrency: as soon as two tasks can interleave and touch the same data, the order of their steps decides the result.

Python offers three models. They differ in what a task is and in who decides when it pauses.

What the GIL protects

CPython's Global Interpreter Lock is a mutex inside the interpreter: only the thread holding it executes Python bytecode. A thread gives it up when it blocks (I/O, time.sleep, waiting on a lock), when it calls C code that releases it (many NumPy operations, hashlib on large buffers, zlib), and when another thread has waited longer than the switch interval (5 ms by default, see sys.getswitchinterval()).

Two consequences are worth saying in one breath:

  • Threads do not speed up CPU-bound pure-Python code, because one thread runs at a time. They do speed up I/O-bound code, because a thread waiting on a socket does not hold the GIL.
  • The GIL protects the interpreter, not your invariants. It stops two threads from corrupting a list while both append. It does nothing for a rule that spans several operations: read then write, check then act, debit one account then credit another.

Python 3.13 added an optional build without the GIL (the free-threaded build, PEP 703) and 3.14 supports it officially (PEP 779). The default build keeps the GIL, but code that is only correct because of it breaks on the free-threaded build, so write code that is correct without it.

Start at the top: the answer depends on what the work waits on, not on which model you like.

'Python has a GIL, so I do not need locks' ends a thread-safety discussion badly. Say instead: the GIL keeps the interpreter consistent, not my invariants. Anything that is read-modify-write or check-then-act across more than one operation needs its own lock, and a free-threaded build removes the safety net entirely.

asyncio is concurrent too

An asyncio program runs on one thread and switches only at await. Between two awaits nothing else runs, so counter += 1 with no await in the middle cannot be interrupted. A check before an await and an act after it is still a race, because every other coroutine may run at the await.

The same check-then-act bug, in asyncio

import asyncio

async def book(seat, user):
    if seat.owner is None:                        # check
        await save_hold_to_db(seat, user)         # every other coroutine may run here
        seat.owner = user                         # act: the check is stale by now
        return True
    return False

seat_lock = asyncio.Lock()                        # one per seat in real code

async def book_safely(seat, user):
    async with seat_lock:                         # other coroutines wait at this line, not in the middle
        if seat.owner is None:
            await save_hold_to_db(seat, user)
            seat.owner = user
            return True
        return False
The primitives differ (asyncio.Lock, not threading.Lock); the reasoning about invariants is identical.

A race condition you can watch

▶ Video lesson: A race condition you can watch 4:08 · 8 scenes · narrated, pause anytime and explore

A race condition is a bug whose outcome depends on the timing of operations on shared state. The textbook form is read-modify-write: counter += 1 looks like one step but is three. The interpreter reads the current value, adds 1 to a private copy, then writes the result back.

What counter += 1 compiles to

LOAD_GLOBAL   counter     # read the shared value onto this thread's stack
LOAD_CONST    1
BINARY_OP     +=          # add on the private copy
STORE_GLOBAL  counter     # write the result back to the shared variable
Simplified dis.dis output from CPython 3.12. Opcode names differ between versions; the read-add-write shape does not.
flowchart LR
  R[1. Read<br/>counter] --> M[2. Add 1<br/>private copy] --> W[3. Write<br/>counter]
Three separate steps. The GIL makes each one atomic; it says nothing about what runs between them.

Interleavings of two counter += 1 operations

Step through all three scenarios. Thread boxes are the instructions each thread runs; the counter lane shows the shared value changing; arrows show values moving between a thread and the counter. Notice that no step is wrong on its own.

What to take from the lanes:

  • Every step is individually fine. The failure lives in the interleaving: the second thread read before the first wrote.
  • The result depends on timing, so tests pass for weeks and production fails on its busiest day.
  • A lucky schedule gives the right answer, so "it worked when I ran it" proves nothing.

Vocabulary the interviewer expects you to use precisely:

  • Critical section: code that touches shared state and must not interleave with other threads touching the same state.
  • Atomic: indivisible. No other thread can observe, or slip into, a half-finished state.
  • Invariant: a rule that must hold whenever no thread is mid-update (a balance never goes negative, a seat has at most one owner). Locks exist to protect invariants, not variables.
  • Read-modify-write and check-then-act: the two shapes of race in nearly every LLD problem. Increment is the first; "if the seat is free, take it" is the second.

Why your demo may not fail

'It passed on my machine' proves nothing. On CPython 3.9 and earlier, a bare counter += 1 loop run by four threads loses a large share of its increments. On 3.10 to 3.13 (with the GIL) the interpreter only offers a thread switch at certain points, such as function calls and loop jumps, so that exact loop almost never fails. On a free-threaded build it fails again, badly. Put any call, I/O or sleep between the read and the write, as real code always has, and it fails on every version. The language never promised atomicity, so do not depend on the accident.

Check-then-act: unprotected vs one critical section

Check, then act (race)

import time

class Account:
    def __init__(self, balance):
        self.balance = balance

    def withdraw(self, amount):
        if self.balance >= amount:        # check
            time.sleep(0.001)             # stand-in for a DB call, a log line, a fraud check
            self.balance -= amount        # act: the check may be stale
            return True
        return False

Check and act under one lock

import threading, time

class SafeAccount:
    def __init__(self, balance):
        self.balance = balance
        self._lock = threading.Lock()     # guards balance

    def withdraw(self, amount):
        with self._lock:                  # check and act are one critical section
            if self.balance >= amount:
                time.sleep(0.001)
                self.balance -= amount
                return True
            return False

Reproduce it yourself

import threading

def hammer(account, attempts=5):
    start = threading.Barrier(attempts)       # line the threads up so they really overlap
    results = []

    def go():
        start.wait()
        results.append(account.withdraw(100))

    threads = [threading.Thread(target=go) for _ in range(attempts)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    return results.count(True), account.balance

print(hammer(Account(100)))        # (5, -400): five withdrawals of 100 from a balance of 100
print(hammer(SafeAccount(100)))    # (1, 0): exactly one succeeds
The sleep makes the race window wide enough to hit on every Python version.

The toolbox: Lock, RLock, Semaphore, Condition, Event, Queue

A lock (mutex) lets one thread at a time into a critical section, and the other primitives refine that idea. Choose by what the threads need to do, not by habit. Each tab shows the smallest realistic use.

The six primitives in threading and queue

Mutual exclusion. Use with so the lock is released even when the body raises, and guard every access path to the data with the same lock object.

import threading

class Counter:
    def __init__(self):
        self._value = 0
        self._lock = threading.Lock()      # guarded by: _value

    def increment(self) -> int:
        with self._lock:                   # acquire on entry, release on exit (even on exceptions)
            self._value += 1
            return self._value

A reentrant lock: the thread that holds it can acquire it again, and must release it as many times. You need it when a locked method calls another locked method of the same object. With a plain Lock that inner call would wait forever, for yourself.

import threading

class Inventory:
    def __init__(self):
        self._lock = threading.RLock()
        self._stock: dict[str, int] = {}

    def add(self, sku: str, qty: int) -> None:
        with self._lock:
            self._stock[sku] = self._stock.get(sku, 0) + qty

    def add_many(self, items: dict[str, int]) -> None:
        with self._lock:                   # outer acquisition
            for sku, qty in items.items():
                self.add(sku, qty)         # inner acquisition by the same thread: fine with RLock

A counter of permits: acquire takes one (and blocks at zero), release gives one back. Use it to cap concurrency: three downloads at a time, a pool of ten connections. Prefer BoundedSemaphore, which raises if you release more than you acquired.

import threading

downloads = threading.BoundedSemaphore(3)      # at most 3 threads inside at once

def download(url: str) -> bytes:
    with downloads:                            # blocks while 3 downloads are running
        return http_get(url)

A lock plus a wait queue: a thread waits until a predicate about shared state becomes true. wait() releases the lock while sleeping and re-acquires it before returning. Always wait in a while loop: another thread may have taken the item first, and a wake-up does not prove the predicate holds.

import threading
from collections import deque

class BoundedBuffer:
    def __init__(self, capacity: int):
        self._items = deque()
        self._capacity = capacity
        self._cond = threading.Condition()     # owns an internal lock

    def put(self, item) -> None:
        with self._cond:
            while len(self._items) >= self._capacity:   # re-check after every wake-up
                self._cond.wait()
            self._items.append(item)
            self._cond.notify_all()            # wake consumers (and blocked producers)

    def get(self):
        with self._cond:
            while not self._items:
                self._cond.wait()
            item = self._items.popleft()
            self._cond.notify_all()
            return item

A flag that threads can wait for. One thread calls set(), and every thread blocked in wait() is released. Good for start gates and for shutting workers down. It carries no data.

import threading

stop = threading.Event()

def worker():
    while not stop.is_set():
        do_one_unit_of_work()
        stop.wait(timeout=0.5)         # sleeps, but wakes at once when stop is set

t = threading.Thread(target=worker)
t.start()
# ... later, on shutdown:
stop.set()
t.join()

A thread-safe FIFO with the locking and waiting built in. Producers put, consumers get. A bounded queue (maxsize) pushes back on producers that outrun consumers. Usually the best answer to 'how do threads hand work to each other'.

import queue
import threading

jobs: queue.Queue = queue.Queue(maxsize=100)   # bounded: put() blocks when full (back-pressure)
DONE = object()                                # sentinel that tells consumers to stop

def producer():
    for n in range(1000):
        jobs.put(n)
    jobs.put(DONE)

def consumer():
    while True:
        item = jobs.get()                      # blocks while the queue is empty
        if item is DONE:
            jobs.put(DONE)                     # pass the sentinel on to the next consumer
            break
        process(item)

workers = [threading.Thread(target=consumer) for _ in range(4)]

Rules of thumb that interviewers like to hear: one lock per invariant; hold it for the shortest time; do no I/O and call no unknown code while holding it; write down which lock guards which field (# guarded by self._lock).

Classic mistakes (the failure catalogue)

A new lock on every call

with threading.Lock(): inside a method creates a fresh lock each time, so no two threads ever contend for it. The lock must be shared: create it once (usually in __init__) and use that object everywhere.

Locking the write but not the read

A reader that skips the lock can see a half-updated state (the debit done, the credit not yet). Every access path to the protected data takes the same lock.

Check outside the lock, act inside

if not seat.taken: outside and with lock: seat.taken = True inside still races: two threads pass the check. Check and act belong in one critical section, or the code must re-check after acquiring the lock.

Holding a lock across I/O or callbacks

Network calls, sleep, logging handlers and user callbacks inside a critical section turn a microsecond lock into a seconds-long queue, and may take other locks you did not plan for (deadlock). Do the slow work before or after; hold the lock only for the state change.

Skipping the release

A bare lock.acquire() ... lock.release() leaves the lock held forever if an exception jumps over the release. with lock: always releases.

Silent thread exceptions

An exception in a Thread target prints a traceback and ends only that thread; the program carries on, possibly half-working. Use futures (future.result() re-raises) or catch and report inside the worker.

Assuming compound operations on built-ins are atomic

d[k] = v is safe on a dict; if k not in d: d[k] = compute() and d[k] += 1 are not. The container protects its own structure, not your logic.

Deadlock: a cycle of waiting

▶ Video lesson: Deadlock: a cycle of waiting 3:56 · 7 scenes · narrated, pause anytime and explore

A deadlock is a cycle of waiting: each thread holds something another one needs and waits for something another one holds, so none can move. Two threads and two locks are enough. Thread A runs with x: with y: and thread B runs with y: with x:. If A takes x while B takes y, each then waits for the lock the other holds. Nothing wakes either of them: CPU use drops to zero, requests pile up behind the stuck work, and a thread dump shows both threads parked in acquire.

The simulation draws the situation as a wait-for graph. Run all three scenarios: the bug and two fixes.

Two threads, two locks

Circles A and B are threads; X and Y are locks. An arrow from a lock to a thread means held by; from a thread to a lock it means wants. A loop of arrows is a deadlock. The lanes chart shows the same story over time.

A deadlock needs all four of these conditions at once (the Coffman conditions). Prevention means breaking one of them.

  F3[Timeouts<br/>give up and let go] -.-> NP[No preemption<br/>nobody takes a lock away]
  F4[One global<br/>lock order] -.-> CW[Circular wait<br/>A waits B waits A]

Solid arrows: the four conditions that together cause a deadlock. Dotted arrows: the usual fix that breaks each condition.

Acquiring two locks

Argument order (deadlock-prone)

def transfer(src, dst, amount):
    with src.lock:                 # thread 1: transfer(a, b)    thread 2: transfer(b, a)
        with dst.lock:             # each holds one lock and waits for the other
            src.balance -= amount
            dst.balance += amount

One global order

def transfer(src, dst, amount):
    if src is dst:
        return
    first, second = sorted((src, dst), key=lambda acct: acct.id)   # same order in every thread
    with first.lock:
        with second.lock:
            src.balance -= amount
            dst.balance += amount

Two reusable ways to acquire several locks safely

Sort the locks by any fixed key and acquire them in that order. id() is stable for live objects and works for any lock. De-duplicate first: taking the same plain Lock twice blocks on yourself.

from contextlib import ExitStack, contextmanager

@contextmanager
def locked_in_order(*locks):
    unique = {id(lock): lock for lock in locks}      # the same lock twice would block on itself
    with ExitStack() as stack:
        for key in sorted(unique):                   # one global order, whatever the caller passes
            stack.enter_context(unique[key])
        yield

with locked_in_order(a.lock, b.lock):                # same result for (a, b) and (b, a)
    a.balance -= 10
    b.balance += 10

When there is no natural order, try for the second lock without waiting forever. If it fails, release the first, sleep for a random, growing time and start over.

import random
import time

def transfer_with_timeout(src, dst, amount, attempts=5) -> bool:
    for attempt in range(attempts):
        if src.lock.acquire(timeout=0.05):               # returns False instead of waiting forever
            try:
                if dst.lock.acquire(timeout=0.05):
                    try:
                        src.balance -= amount
                        dst.balance += amount
                        return True
                    finally:
                        dst.lock.release()
            finally:
                src.lock.release()                       # let go of the first lock before backing off
        time.sleep(random.uniform(0, 0.01) * 2 ** attempt)   # exponential back-off with jitter
    return False

How do you avoid deadlock? A strong answer: 'Deadlock needs a cycle of waiting, so I remove the cycle. Where one operation must hold two locks, I take them in one global order, for example by account id, so no thread can hold the higher lock while asking for the lower. Where there is no natural order I use try-lock with a timeout and back off, releasing what I hold. And I keep critical sections small and free of calls into unknown code, which removes most chances to form a cycle.'

Finding a deadlock. Python has no deadlock detector. In production you see stuck threads: dump every thread's stack with faulthandler.dump_traceback_later(30) or py-spy dump --pid <pid> and look for threads waiting in acquire on locks held by each other. Databases do detect them: they keep the same wait-for graph, find a cycle, abort one transaction (the victim) and let you retry. Finding a cycle in a directed graph is the algorithm behind Course Schedule.

Two relatives to name when asked: livelock (threads keep reacting to each other and make no progress, like two people stepping aside in a corridor; random back-off fixes it) and starvation (a thread never gets the lock because others keep winning).

Lock granularity, contention and atomic operations

Granularity is how much data one lock protects.

  • Coarse: one lock for the whole structure. Simple and hard to get wrong, but every operation queues behind every other.
  • Fine: one lock per object (per seat, per account). Operations on different objects run side by side. The price is complexity: an operation that touches several objects needs several locks, which is where deadlock comes from. Lock them in a fixed order.
  • Striped: a fixed array of N locks, picked by hash(key) % N. Fine-grained concurrency without one lock object per key. Two keys may share a stripe, which costs a little contention and never correctness.
  • Read-mostly data: the standard library has no read-write lock. Share an immutable snapshot and swap the reference (next section).

Contention is time spent waiting for a lock instead of working. A simple model shows why shrinking the critical section matters more than adding threads.

How far can one lock scale?

Every operation does work microseconds in parallel, then crit microseconds inside one lock. The lock can serve at most 1 / crit operations per second, however many threads queue for it. The same shape as Amdahl's law, with the serial fraction crit / (work + crit). Try halving crit and compare with doubling the threads.

Granularity: one lock or one per seat

Coarse: one lock for the venue

Simple and obviously correct. Booking seat 12A blocks booking seat 40Z, so throughput is capped at one booking at a time.

class Venue:
    def __init__(self, seat_ids):
        self._lock = threading.Lock()                  # one lock for everything
        self._owner = {s: None for s in seat_ids}

    def book(self, seat_id, user) -> bool:
        with self._lock:
            if self._owner[seat_id] is not None:
                return False
            self._owner[seat_id] = user
            return True

Fine: one lock per seat

Only bookings of the same seat wait for each other. Multi-seat bookings now need several locks, so they must take them in a fixed order.

class Venue:
    def __init__(self, seat_ids):
        self._locks = {s: threading.Lock() for s in seat_ids}   # one lock per seat
        self._owner = {s: None for s in seat_ids}

    def book(self, seat_id, user) -> bool:
        with self._locks[seat_id]:
            if self._owner[seat_id] is not None:
                return False
            self._owner[seat_id] = user
            return True

Lock striping: a bounded set of locks for unbounded keys

import threading

class StripedCounters:
    def __init__(self, stripes: int = 16):
        self._locks = [threading.Lock() for _ in range(stripes)]
        self._shards = [{} for _ in range(stripes)]

    def incr(self, key: str, by: int = 1) -> int:
        i = hash(key) % len(self._locks)            # the same key always maps to the same stripe
        with self._locks[i]:
            shard = self._shards[i]
            shard[key] = shard.get(key, 0) + by
            return shard[key]
Sixteen locks protect any number of keys. Two keys that share a stripe wait for each other, which is harmless.

Atomic operations and compare-and-swap

An atomic operation completes as one indivisible step. Hardware offers compare-and-swap (CAS): set this location to new, but only if it still holds expected, and tell me whether it worked. With CAS you can update shared state without holding a lock while you think: read the value, compute the new one, CAS it in, and if somebody else got there first, read again and retry. That loop is optimistic: it assumes conflicts are rare and pays only when one happens.

Python exposes no CAS instruction for ordinary objects, so the sketch below guards the compare-and-set itself with a tiny lock. The pattern is what matters, because it returns in databases (UPDATE ... WHERE version = ?), in DynamoDB conditional writes and in HTTP If-Match requests.

Compare-and-swap and the retry loop

import threading

class AtomicInt:
    def __init__(self, value: int = 0):
        self._value = value
        self._lock = threading.Lock()              # protects only the compare-and-set itself

    def get(self) -> int:
        return self._value

    def compare_and_set(self, expected: int, new: int) -> bool:
        with self._lock:
            if self._value != expected:
                return False                      # somebody changed it since we read it
            self._value = new
            return True


def increment(counter: AtomicInt) -> int:
    while True:
        seen = counter.get()                      # read, with no lock held
        if counter.compare_and_set(seen, seen + 1):   # write only if nothing changed
            return seen + 1
        # lost the race: loop, read the new value, try again
The same shape as optimistic locking on a database row. It wins when conflicts are rare and loses when everyone fights over one value.

Sharing less: immutability, message passing and pools

The cheapest lock is the one you never need. Four ways to share less:

  • Immutability: data that cannot change cannot race. Frozen dataclasses, tuples and frozenset are safe to read from any thread. To change something, build a new object and swap one reference (copy-on-write).
  • Confinement: state touched by exactly one thread needs no lock. Thread-local storage and per-request objects do this.
  • Message passing: one thread owns the state; others send it messages through a queue.Queue and get answers back through futures. The owner runs the check-then-act sequence alone, so it cannot race.
  • Partitioning: split the data (by seat, by user id) so each worker owns a slice. This is also how databases scale beyond one machine.

Three ways to avoid sharing

Readers take a reference and never lock. A writer builds a whole new object and replaces the reference in one assignment, so a reader sees the old snapshot or the new one, never a mixture.

import threading
from dataclasses import dataclass, replace

@dataclass(frozen=True)
class PriceList:
    version: int
    prices: tuple[tuple[str, int], ...]          # immutable all the way down

class PriceService:
    def __init__(self, initial: PriceList):
        self._current = initial                  # readers only ever read this one reference
        self._write_lock = threading.Lock()      # only writers contend with each other

    def snapshot(self) -> PriceList:
        return self._current                     # no lock: the object can never change

    def publish(self, prices: dict[str, int]) -> None:
        with self._write_lock:
            self._current = replace(self._current, version=self._current.version + 1,
                                    prices=tuple(sorted(prices.items())))

A single thread owns the balance. Everyone else sends it a request and waits on a Future. There is no lock, because the check and the act run in one thread, one request at a time.

import queue
import threading
from concurrent.futures import Future

class Wallet:
    def __init__(self, balance: int = 0):
        self._balance = balance                  # touched only by the worker thread
        self._inbox: queue.Queue = queue.Queue()
        threading.Thread(target=self._run, daemon=True).start()

    def withdraw(self, amount: int) -> Future:
        reply: Future = Future()
        self._inbox.put((amount, reply))
        return reply                             # the caller waits with reply.result()

    def _run(self) -> None:
        while True:
            amount, reply = self._inbox.get()
            if amount <= self._balance:          # check and act cannot be interleaved here
                self._balance -= amount
                reply.set_result(True)
            else:
                reply.set_result(False)

Each thread gets its own copy of the variable (a request id, a database connection). Nothing is shared, so nothing races. In asyncio use contextvars.ContextVar instead, because many coroutines share one thread.

import threading

_local = threading.local()

def handle(request):
    _local.request_id = request.id               # visible only to this thread
    process(request)

def current_request_id():
    return getattr(_local, "request_id", None)   # each thread sees its own value

Thread pools with concurrent.futures

Creating a thread per task does not scale and makes results awkward to collect. concurrent.futures gives you a pool and a Future per task: a handle for a result that does not exist yet. future.result() waits for it and re-raises the worker's exception in the caller, which fixes the silent-thread-exception problem. Use ThreadPoolExecutor for I/O-bound work and ProcessPoolExecutor for CPU-bound pure Python.

One pool for I/O, one for CPU

from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor, as_completed

def fetch(url: str) -> int:
    ...                                              # blocking network call; returns the number of bytes

def crunch(n: int) -> int:
    return sum(i * i for i in range(n))              # pure-Python CPU work

def download_all(urls: list[str]) -> dict[str, int]:
    sizes: dict[str, int] = {}
    with ThreadPoolExecutor(max_workers=16) as pool:                 # I/O-bound: threads
        futures = {pool.submit(fetch, url): url for url in urls}
        for fut in as_completed(futures):                            # yields each future as it finishes
            url = futures[fut]
            try:
                sizes[url] = fut.result()                            # re-raises the worker's exception here
            except Exception as exc:
                sizes[url] = -1
                print(f"{url} failed: {exc!r}")
    return sizes                                                     # leaving the with-block joins the workers

if __name__ == "__main__":                                           # needed for process pools on Windows and macOS
    with ProcessPoolExecutor() as pool:                              # CPU-bound: one process per core by default
        print(list(pool.map(crunch, [5_000_000] * 4)))
ThreadPoolExecutor defaults to min(32, cpu_count + 4) workers; pass max_workers when the work or the downstream service has its own limit.

Idempotency: retries without repeated effects

An operation is idempotent if doing it twice has the same effect as doing it once. PUT /seats/12A {owner: ann} is idempotent. POST /bookings and balance -= 100 are not: each repeat adds another booking or takes another 100. Retries are everywhere: a client times out and tries again, a load balancer resends, a queue delivers at least once, a user double-clicks Pay. If the operation is not idempotent, every retry repeats its effect. Back-off and jitter (see Reliability patterns) make retries polite, but they do not make them safe.

The standard fix is an idempotency key. The client generates a unique id (a UUID) once per intent and sends the same id on every retry. The server records key → result and, when it sees the key again, returns the stored result instead of repeating the work. Stripe's API works this way and documents that keys may be pruned once they are 24 hours old. Queue consumers do the same with a message id, because at-least-once delivery means duplicates are normal (see Message queues & streaming (Kafka)).

sequenceDiagram
  participant C as Client
  participant S as Booking API
  participant DB as Database
  C->>S: POST /bookings, key k1
  S->>DB: INSERT key k1
  DB-->>S: inserted, we own k1
  S->>DB: INSERT booking, store result under k1
  S--x C: response lost (timeout)
  C->>S: retry POST /bookings, key k1
  S->>DB: INSERT key k1
  DB-->>S: conflict, k1 already exists
  S->>DB: SELECT stored result for k1
  DB-->>S: booking b-123
  S-->>C: 201 booking b-123 (same as before)
The retry never reaches the booking code: the key conflict short-circuits it and the stored answer is replayed.

Idempotency keys in code

The first caller for a key becomes the owner and runs the action. Concurrent callers with the same key wait on the owner's Future and receive the same result. A failure is not remembered, so a later retry may run the action again.

import threading
from concurrent.futures import Future

class IdempotencyStore:
    def __init__(self):
        self._lock = threading.Lock()
        self._slots: dict[str, Future] = {}

    def run_once(self, key: str, action):
        with self._lock:                         # claiming the key is the atomic step
            slot = self._slots.get(key)
            owner = slot is None
            if owner:
                slot = self._slots[key] = Future()
        if not owner:
            return slot.result()                 # a twin is running (or has run): share its answer
        try:
            slot.set_result(action())            # the real work happens exactly once
        except Exception as exc:
            with self._lock:
                del self._slots[key]             # let a later retry try again
            slot.set_exception(exc)
        return slot.result()

A primary key on the idempotency key makes the claim atomic across every server. Postgres makes a concurrent INSERT ... ON CONFLICT DO NOTHING on the same key wait for the first transaction to finish, so the twin sees the stored result.

# CREATE TABLE idempotency_keys (
#     key        text PRIMARY KEY,
#     response   jsonb,
#     created_at timestamptz NOT NULL DEFAULT now()
# );
from psycopg.types.json import Jsonb

def create_booking(conn, key: str, user_id: int, seat_id: str) -> dict:
    with conn.transaction():
        claimed = conn.execute(
            "INSERT INTO idempotency_keys (key) VALUES (%s) ON CONFLICT (key) DO NOTHING", (key,)
        ).rowcount == 1                          # 0 rows: somebody already holds this key
        if not claimed:
            (response,) = conn.execute(
                "SELECT response FROM idempotency_keys WHERE key = %s", (key,)
            ).fetchone()
            return response                      # replay the stored answer
        booking = book_seat(conn, seat_id, user_id)          # the real work, same transaction
        conn.execute("UPDATE idempotency_keys SET response = %s WHERE key = %s", (Jsonb(booking), key))
        return booking

Three details that separate a good answer from a vague one: claim the key before the work, atomically (a unique constraint), otherwise two concurrent retries both pass a 'seen it?' check; store the result, not just the fact that the key was seen, so the retry receives the same answer; and scope and expire keys (per user and endpoint, pruned after a day or so).

Interview classic: two users, one seat

▶ Video lesson: Two users, one seat 4:04 · 7 scenes · narrated, pause anytime and explore

The problem. A cinema, airline or concert site shows seats. Many users select seats at once, and two users must never end up holding the same seat for the same show. At on-sale time the collision is the normal case, because everyone wants the same front-row seats.

The bug always has the same shape: check-then-act on shared state. if seat is free: assign it is two steps, and anything that runs between them invalidates the check. The fix has one shape too: make check-and-act one atomic step, using something every contender must pass through. That something is a lock, a compare-and-swap, a database row lock or a constraint.

Real systems add a middle state. A seat is held for a few minutes while the user pays, then booked or released, so the seat becomes a small state machine instead of a boolean.

stateDiagram-v2
  [*] --> Available
  Available --> Held : hold
  Held --> Booked : pay
  Held --> Available : expire
  Booked --> Available : cancel
Every arrow is a conditional update that can fail; the question 'who gets the seat' is decided on the way out of Available.

Alice and Bob book seat 12A at the same moment

Same race, three strategies. In the first, watch the two timelines overlap and both users get a confirmation. In the other two, watch how the loser is turned away cleanly.

In-memory solutions (one process)

The check and the act are separate. The call in between stands for any real work (logging, pricing, a payment hold) and gives another thread time to pass the same check.

class Seat:
    def __init__(self, seat_id: str):
        self.seat_id = seat_id
        self.owner = None

    def audit(self, user: str) -> None:
        ...                                   # log, price check, fraud check

    def book(self, user: str) -> bool:
        if self.owner is None:                # check
            self.audit(user)                  # any call or I/O here lets another thread in
            self.owner = user                 # act
            return True
        return False

Check and act share one critical section. A booking that spans several seats takes the locks in sorted order (no deadlock between two multi-seat bookings) and is all-or-nothing.

import threading
from contextlib import ExitStack

class Seat:
    def __init__(self, seat_id: str):
        self.seat_id = seat_id
        self.owner = None
        self.lock = threading.Lock()

    def book(self, user: str) -> bool:
        with self.lock:                       # check and act are one critical section
            if self.owner is not None:
                return False
            self.owner = user
            return True


def book_many(seats: dict[str, Seat], seat_ids: list[str], user: str) -> bool:
    chosen = [seats[i] for i in sorted(set(seat_ids))]        # fixed order: no deadlock
    with ExitStack() as stack:
        for seat in chosen:
            stack.enter_context(seat.lock)
        if any(seat.owner is not None for seat in chosen):
            return False                                      # all or nothing
        for seat in chosen:
            seat.owner = user
        return True

No lock is held while the caller thinks. The seat state carries a version; the write succeeds only if the version is unchanged. A tiny lock guards the compare-and-set itself.

import threading

class Seat:
    def __init__(self, seat_id: str):
        self.seat_id = seat_id
        self._state = (None, 0)               # (owner, version), replaced as one unit
        self._lock = threading.Lock()         # guards only the compare-and-set

    def read(self) -> tuple:
        return self._state

    def compare_and_set(self, expected_version: int, owner: str) -> bool:
        with self._lock:
            _, version = self._state
            if version != expected_version:
                return False                  # somebody wrote after we read
            self._state = (owner, version + 1)
            return True


def book(seat: Seat, user: str, retries: int = 3) -> bool:
    for _ in range(retries):
        owner, version = seat.read()          # no lock held while we decide
        if owner is not None:
            return False                      # already taken: a clean 'no'
        if seat.compare_and_set(version, user):
            return True
        # the seat changed after we read it: loop, re-read, decide again
    return False

Run the same test against the broken class (put a time.sleep(0.001) between check and act) and it fails; against the locked class it never does. A concurrency test that cannot fail on the broken code proves nothing.

from concurrent.futures import ThreadPoolExecutor

def test_only_one_winner():
    seat = Seat("12A")
    with ThreadPoolExecutor(max_workers=50) as pool:
        results = list(pool.map(lambda n: seat.book(f"user{n}"), range(200)))
    assert results.count(True) == 1           # exactly one of 200 contenders wins

In-process locks stop at the process boundary

A threading.Lock coordinates the threads of one process. Behind a load balancer there are several app servers, and several processes per server, each with its own lock, so two requests for seat 12A can pass their own locks at the same moment. Once state outlives or spans processes, the database is the arbiter: every server must go through it, and it already knows how to check and update atomically.

The database versions

With the seat in a database, four tools make check and write one atomic step. Each tells the loser clearly (zero rows updated, an exception, or a wait followed by a re-check), so the API can answer seat taken instead of failing.

Four database guards (psycopg-style Python, PostgreSQL SQL)

One statement does the check and the write. The database applies it under the row's lock, so two concurrent updates serialise and the second matches zero rows. This is compare-and-swap in SQL and the best default.

def book_seat(conn, show_id: int, seat_id: str, user_id: int) -> bool:
    cur = conn.execute(
        "UPDATE seats SET status = 'BOOKED', user_id = %s "
        "WHERE show_id = %s AND seat_id = %s AND status = 'AVAILABLE'",
        (user_id, show_id, seat_id),
    )
    return cur.rowcount == 1          # 1: we got it. 0: somebody else did, or the seat does not exist

Lock the rows, read them, decide, write. Needed when the decision takes more than one statement, such as several seats or a price lookup. Lock rows in a fixed order (ORDER BY) so two bookings cannot deadlock. Variants: NOWAIT fails instead of waiting; SKIP LOCKED passes over rows another transaction holds.

def book_seats_locking(conn, show_id: int, seat_ids: list[str], user_id: int) -> bool:
    with conn.transaction():
        rows = conn.execute(
            "SELECT seat_id, status FROM seats "
            "WHERE show_id = %s AND seat_id = ANY(%s) "
            "ORDER BY seat_id "
            "FOR UPDATE",                 # row locks, taken in a fixed order
            (show_id, seat_ids),
        ).fetchall()
        if len(rows) != len(seat_ids) or any(status != "AVAILABLE" for _, status in rows):
            return False                  # nothing changed; leaving the block ends the transaction
        conn.execute(
            "UPDATE seats SET status = 'BOOKED', user_id = %s "
            "WHERE show_id = %s AND seat_id = ANY(%s)",
            (user_id, show_id, seat_ids),
        )
        return True

Make the duplicate impossible to store. The second INSERT waits for the first transaction, then fails. This is the last line of defence: keep it even when another mechanism does the main work.

# CREATE TABLE bookings (
#     booking_id bigserial PRIMARY KEY,
#     show_id    int  NOT NULL,
#     seat_id    text NOT NULL,
#     user_id    int  NOT NULL,
#     UNIQUE (show_id, seat_id)          -- at most one booking per seat per show
# );
from psycopg.errors import UniqueViolation

def book_seat_insert(conn, show_id: int, seat_id: str, user_id: int) -> bool:
    try:
        with conn.transaction():
            conn.execute(
                "INSERT INTO bookings (show_id, seat_id, user_id) VALUES (%s, %s, %s)",
                (show_id, seat_id, user_id),
            )
        return True
    except UniqueViolation:
        return False                      # the database refused the second row

Optimistic locking in SQL. Read the row with its version; update only WHERE version = :seen and bump it. Zero rows means someone wrote first: re-read and decide again.

def book_seat_optimistic(conn, show_id: int, seat_id: str, user_id: int, retries: int = 3) -> bool:
    for _ in range(retries):
        row = conn.execute(
            "SELECT status, version FROM seats WHERE show_id = %s AND seat_id = %s",
            (show_id, seat_id),
        ).fetchone()
        if row is None or row[0] != "AVAILABLE":
            return False                  # taken, or no such seat
        cur = conn.execute(
            "UPDATE seats SET status = 'BOOKED', user_id = %s, version = version + 1 "
            "WHERE show_id = %s AND seat_id = %s AND version = %s",
            (user_id, show_id, seat_id, row[1]),
        )
        if cur.rowcount == 1:
            return True
        # zero rows: the version moved after we read it; loop and look again
    return False

Pessimistic: lock the row, then decide. SELECT ... FOR UPDATE takes a row lock that lasts until the transaction ends. A second transaction asking for the same row waits, and when it finally gets the row it sees the committed result.

Bob's SELECT does not return until Alice commits. When it does, it reads the new state, so Bob's check is never stale.

Optimistic: decide, then verify. Nobody waits. The write carries the version that was read; if the version has moved, zero rows change and the caller re-reads.

The service that ties the chapter together

from contextlib import ExitStack
from dataclasses import dataclass
from uuid import uuid4

@dataclass(frozen=True)
class Booking:
    booking_id: str
    seat_ids: tuple[str, ...]
    user: str


class BookingService:
    def __init__(self, seats: dict[str, "Seat"]):
        self._seats = seats                                   # Seat has .seat_id, .owner and .lock (per-seat lock tab)
        self._idempotency = IdempotencyStore()                # from the idempotency section

    def book(self, request_id: str, seat_ids: list[str], user: str) -> Booking | None:
        return self._idempotency.run_once(request_id, lambda: self._book_once(seat_ids, user))

    def _book_once(self, seat_ids: list[str], user: str) -> Booking | None:
        chosen = [self._seats[i] for i in sorted(set(seat_ids))]      # fixed lock order: no deadlock
        with ExitStack() as stack:
            for seat in chosen:
                stack.enter_context(seat.lock)
            if any(seat.owner is not None for seat in chosen):
                return None                                           # all or nothing: 'seat taken'
            for seat in chosen:
                seat.owner = user
            return Booking(uuid4().hex, tuple(s.seat_id for s in chosen), user)
A retry with the same request_id replays the first answer, including a 'taken'. A new request gets a fresh attempt.

Follow-ups to expect (click to reveal)

'What if the user wants two adjacent seats?'

Make the booking all-or-nothing. In memory, take the seat locks in sorted order and release them all if any seat is taken. In SQL, one transaction with SELECT ... FOR UPDATE ORDER BY seat_id, or a single UPDATE ... WHERE seat_id IN (...) AND status = 'AVAILABLE' and check that the row count equals the number of seats, rolling back otherwise.

'The user picks a seat but pays five minutes later.'

Add the Held state with a held_until timestamp. The conditional update treats status = 'AVAILABLE' OR held_until < now() as free, so an expired hold needs no sweeper to be reusable; a periodic job only tidies up. Payment confirmation is itself a conditional update: HELD by me and not expired → BOOKED.

'We run twelve app servers.'

In-process locks do not coordinate them. Let the database arbitrate (conditional update, row lock, unique constraint). A Redis lock with a TTL (SET key value NX EX 30) can reduce load, but a holder that pauses past the TTL can still proceed after the lock expired, so correctness must rest on the database constraint or a fencing token, never on the lock alone.

'Ten thousand people click the same seat at once.'

Keep the critical section tiny: a single conditional UPDATE, no long transactions, no network calls while a lock is held. Add a waiting room or rate limit at the edge so the database sees a manageable rate. The losers fail fast (the seat is gone), which is cheap.

'The payment failed after the hold.'

Release the hold with a conditional update (HELD by me → AVAILABLE) and make the release idempotent, so a duplicate failure callback does nothing. Stale holds expire on their own anyway.

'The user double-clicks Pay.'

Send an idempotency key from the client, store it with a unique constraint, and replay the stored result. The unique constraint on (show_id, seat_id) is the backstop if the key is missing.

'Why not just use SERIALIZABLE isolation?'

It is correct: the database aborts one of two conflicting transactions with a serialization failure. But the application must catch that error and retry, and throughput drops under contention. For one well-known race, an explicit conditional update or row lock is simpler and cheaper.

How do you stop two users booking the same seat? A strong answer: 'Booking is a check-then-act on one seat, so I make the pair atomic. In memory that is a per-seat lock, taken in sorted order when a booking spans several seats. With several servers the database must arbitrate: a conditional UPDATE that only matches available seats, checking the row count, plus a unique constraint on show and seat as the last line of defence. Seats are held for a few minutes with an expiry before payment, and the request carries an idempotency key so a retry cannot book twice. The loser gets a clean "seat taken", not an error.'
