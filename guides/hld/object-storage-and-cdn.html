Object storage (S3) & CDNs

Object storage keeps the bytes of a system cheaply and durably, and a CDN keeps the hot ones close to users. This chapter covers how object storage differs from block and file storage, how S3 is organised, what eleven nines really means, how presigned and multipart uploads keep big files off your servers, and how CDNs cache, invalidate and protect content, so you can design upload-and-serve systems with confidence.

After this chapter you can
  • Choose between block, file and object storage from the access pattern
  • Describe S3's model (flat keys, metadata, versioning, storage classes, lifecycle) and its consistency guarantees
  • Explain durability versus availability, and compare replication with erasure coding by overhead and fault tolerance
  • Design direct-to-S3 uploads with presigned URLs and multipart upload, including failure and resume
  • Explain how a CDN decides hit or miss, and choose between invalidation and versioned file names
  • Decide what to serve from a CDN and what from the app, including private content with signed URLs

Block, file and object storage

Most system designs touch three kinds of storage. They differ in how you address data and what you may do to it.

  • Block storage exposes a raw disk: fixed-size blocks at numbered addresses, with a filesystem put on top by the operating system. It is fast and supports tiny in-place writes, which is why databases run on it. A volume is normally attached to one machine at a time (AWS EBS).
  • File storage is a shared filesystem: directories, files, permissions, and the right to modify any byte range. Many machines mount it at once over NFS or SMB (AWS EFS). It suits software that expects a POSIX filesystem.
  • Object storage is a huge key-value store for whole blobs: PUT an object under a key, GET it back, DELETE it. There is no in-place edit; to change an object you write a new one. In exchange you get practically unlimited capacity, very high durability, HTTP access from anywhere, and the lowest price per GB (AWS S3, Google Cloud Storage, Azure Blob).

Start from the access pattern, not the product. Most application data that is written once and read many times ends at the top-right.

In a design, user-generated files (photos, videos, documents) go to object storage and the database stores only the key and metadata (owner, size, content type, status). Keeping the bytes out of the database keeps it small, keeps backups fast, and lets clients move bytes without passing through your servers.

The S3 model

S3 has few concepts, which is part of why it scales so well:

  • A bucket is a container with a globally unique name, created in one region.
  • An object is a blob of up to 5 TiB plus metadata, stored under a key: a string such as photos/2026/cat.jpg.
  • The namespace is flat. There are no directories. The / in a key is an ordinary character; the console, and ListObjectsV2 with Prefix and Delimiter, simulate folders by grouping keys that share a prefix.
  • Metadata is system fields (size, Content-Type, ETag, last-modified time), your own key-value pairs, and up to 10 tags that lifecycle and access rules can match.
  • With versioning on, an overwrite creates a new version instead of replacing the old one, and a delete only adds a delete marker. Any earlier version can be restored, and you pay for all of them.

Request rate scales per prefix: S3 supports at least 3,500 writes and 5,500 reads per second for each prefix, and a bucket can have as many prefixes as you like, so one very hot prefix is the thing to avoid, not a big bucket.

One flat list of keys per bucket. Everything that looks like a folder is a shared prefix.

Storage classes let you pay less for data you rarely read. The trade is always the same: lower price per GB-month, higher price (or delay) per retrieval, and a minimum storage duration you are billed for even if you delete earlier.

A lifecycle rule for logs: the object ages through colder classes and is finally deleted. Days count from creation.

Lifecycle rules also expire old versions of versioned objects and abort incomplete multipart uploads. Both are silent cost leaks if you forget them. Very small objects (under about 128 KB) are poor candidates for transitions: per-request transition fees and minimum billable sizes can cost more than they save.

Durability is not availability

▶ Video lesson: Durability is not availability 3:57 · 7 scenes · narrated, pause anytime and explore

Two numbers are easy to mix up.

Durability is the probability that an object is not lost over a year. S3 Standard is designed for 99.999999999% (eleven nines): lose one object per 10¹¹ object-years. Store ten million objects and you should expect to lose one about every 10,000 years.

Availability is the fraction of time you can read it. S3 Standard is designed for 99.99%, which allows about 53 minutes a year in which requests may fail. The data is safe; you just cannot reach it right now.

They have different causes and fixes. Durability comes from redundancy plus fast repair. Availability comes from redundancy across fault domains, plus retries and, if you need it, a second region.

Two ways to survive a dead disk:

  • Replication keeps full copies. Three copies tolerate two losses at 3.0× the storage. Reads and repairs are simple and fast.
  • Erasure coding splits an object into k data shards and adds m parity shards, such that any k of the k + m rebuild it. A 6 + 3 scheme tolerates three losses at only 1.5× the storage. The price is CPU, and rebuilding a shard means reading k others.

S3 stores each object redundantly in at least three Availability Zones. AWS does not publish the exact scheme, so the calculator below is a toy model with independent failures, not S3's configuration.

Eleven nines, replication and erasure coding

The first block turns nines into plain numbers. The second is a toy durability model: an object is lost if more than the tolerated number of its copies or shards fail inside one repair window. Shorten the repair time and watch the loss probability collapse; add a parity shard and it collapses further. Real systems are limited by correlated failures (a bad firmware version, a fire, an operator error), which this model ignores.

The same toy model, exactly, with math.comb

from math import comb

def p_object_lost(n: int, tolerate: int, w: float) -> float:
    """Chance that MORE than `tolerate` of n shards die inside one repair window (independent failures)."""
    return sum(comb(n, j) * w**j * (1 - w) ** (n - j) for j in range(tolerate + 1, n + 1))

afr, repair_h = 0.02, 6                    # 2% annual disk failure rate; 6 hours to rebuild a lost shard
w = afr * repair_h / 8760                  # chance a given disk fails during one repair window
windows_per_year = 8760 / repair_h

for name, n, tolerate in [("2 copies", 2, 1), ("3 copies", 3, 2), ("erasure 6+3", 9, 3), ("erasure 10+4", 14, 4)]:
    print(f"{name:13} annual loss per object ~ {windows_per_year * p_object_lost(n, tolerate, w):.1e}")

# 2 copies       annual loss per object ~ 2.7e-07
# 3 copies       annual loss per object ~ 3.8e-12
# erasure 6+3    annual loss per object ~ 6.5e-15   (and 1.5x storage instead of 3x)
# erasure 10+4   annual loss per object ~ 1.4e-18
Each extra tolerated failure multiplies the loss probability by roughly w, about 1e-5 here, which is why a few more shards, spread over independent fault domains, buys so many nines.

If asked 'how does S3 get eleven nines?', say: redundancy across at least three AZs (copies or erasure-coded shards), checksums verified continuously, and automatic repair that restores lost shards quickly. Then add the caveat that durability does not protect against you: an accidental delete or overwrite is durable too. That is what versioning, MFA delete, object lock and cross-region replication are for.

Getting bytes in: presigned URLs and multipart

▶ Video lesson: Direct uploads: presigned URLs and multipart 4:22 · 7 scenes · narrated, pause anytime and explore

The naive upload path sends the file to your API, which forwards it to S3. That doubles the bandwidth through your servers, ties up a worker for the whole upload, and puts a size limit on your load balancer. The better path lets the client talk to S3 directly, using a presigned URL: a normal S3 URL with an expiry and a signature computed by your server from its own credentials. S3 verifies the signature and applies the signer's permissions to exactly that operation on exactly that key. Signing is a local computation, so your server makes no call to S3 to create it.

sequenceDiagram
  participant C as Client
  participant A as API server
  participant S as S3
  participant W as Event consumer
  C->>A: POST /uploads (name, size, type)
  A->>A: authorise, pick a key, sign a URL
  A-->>C: presigned PUT URL and the key
  C->>S: PUT the bytes to that URL
  S-->>C: 200 OK with an ETag
  S->>W: ObjectCreated event
  W->>A: mark the upload complete, start processing
Your servers handle a few hundred bytes of JSON; S3 handles the gigabytes.

Presigned uploads with boto3

Simple, but the URL cannot cap the object size by itself. Sign the content type, keep the expiry short, and check the size after the upload.

import uuid

import boto3
from botocore.config import Config

s3 = boto3.client("s3", config=Config(signature_version="s3v4"))
BUCKET = "acme-uploads"

def create_upload(user_id: str, content_type: str) -> dict:
    key = f"uploads/{user_id}/{uuid.uuid4()}"          # the server picks the key
    url = s3.generate_presigned_url(
        "put_object",
        Params={"Bucket": BUCKET, "Key": key, "ContentType": content_type},
        ExpiresIn=900,                                 # 15 minutes
    )
    return {"key": key, "url": url}                    # the client must send the same Content-Type header

A POST policy lets S3 enforce rules for you, including a size range and the content type.

def create_image_upload(user_id: str) -> dict:
    key = f"uploads/{user_id}/{uuid.uuid4()}"
    post = s3.generate_presigned_post(
        Bucket=BUCKET, Key=key,
        Fields={"Content-Type": "image/jpeg"},
        Conditions=[{"Content-Type": "image/jpeg"},
                    ["content-length-range", 1, 10 * 1024 * 1024]],   # 1 byte to 10 MiB
        ExpiresIn=600,
    )
    return {"key": key, **post}      # {"url": ..., "fields": {...}}: the browser submits a multipart/form-data POST

For large files the server opens the multipart upload and presigns one URL per part. The client uploads parts in parallel and returns the ETags.

def start_big_upload(user_id: str, parts: int) -> dict:
    key = f"uploads/{user_id}/{uuid.uuid4()}"
    upload = s3.create_multipart_upload(Bucket=BUCKET, Key=key, ContentType="video/mp4")
    urls = [
        s3.generate_presigned_url(
            "upload_part",
            Params={"Bucket": BUCKET, "Key": key, "UploadId": upload["UploadId"], "PartNumber": n},
            ExpiresIn=3600)
        for n in range(1, parts + 1)                    # part numbers start at 1
    ]
    return {"key": key, "upload_id": upload["UploadId"], "part_urls": urls}

def finish_big_upload(key: str, upload_id: str, etags: dict[int, str]) -> None:
    s3.complete_multipart_upload(
        Bucket=BUCKET, Key=key, UploadId=upload_id,
        MultipartUpload={"Parts": [{"PartNumber": n, "ETag": e} for n, e in sorted(etags.items())]})

A presigned URL carries the signer's permissions and, if it was signed with temporary credentials (an IAM role session), it stops working when those credentials expire, even if you asked for a longer expiry. The maximum lifetime is 7 days with long-lived IAM user keys. You cannot revoke one URL individually; you can only shorten expiries, disable the signing credentials, or delete the object.

Multipart upload: parallel parts, one failure, one crash

A 128 MiB file in eight parts. The small label under a finished cell is the ETag S3 returned for that part. Switch scenarios to see a single failed part retried, and a client crash followed by a resume.

Rules of thumb for multipart: use it above roughly 100 MB (the SDKs switch automatically at a configurable threshold), it is required above 5 GiB, parts are 5 MiB to 5 GiB (the last may be smaller), an upload has at most 10,000 parts (so at most 5 TiB), and a part can be retried or uploaded in parallel without touching the others. The object is invisible until CompleteMultipartUpload. Until then the stored parts are billed, so an abort-incomplete-uploads lifecycle rule is not optional.

Consistency, and what S3 will not do

Since December 2020 S3 gives strong read-after-write consistency for every request: once a PUT or DELETE succeeds, any later GET or LIST sees it. (Older tutorials describe eventual consistency for overwrites. That is out of date.) What S3 still does not do:

  • No in-place edit, append or rename. To change one byte you upload a whole new object. A rename is a copy followed by a delete. Treat objects as immutable values; this is also what makes them so cacheable.
  • No transactions across objects. Concurrent writers to one key are last writer wins. For coordination use conditional writes (If-None-Match: * creates only if the key is absent; If-Match with an ETag replaces only if the object is unchanged) or put the coordination in a database.
  • LIST is not a query engine. It returns up to 1,000 keys per call, by prefix. Anything beyond browsing a prefix ("all videos by user 42 uploaded last week") needs an index of keys and metadata in a database.
  • Cross-region replication is asynchronous. The replica lags the source, so do not read your writes from it.

CDN: caching at the edge

▶ Video lesson: CDN: caching at the edge 4:02 · 6 scenes · narrated, pause anytime and explore

A CDN (content delivery network) is a cache run by someone else, at hundreds of edge locations near your users. A hit is served from a few milliseconds away and never reaches your servers. A miss is fetched from your origin (S3, a load balancer, an app server), stored at the edge for its TTL, and served. Real CDNs add a regional layer between the edges and the origin, and many offer an optional origin shield: a single designated cache that sits in front of the origin and absorbs the misses of every edge. Without it, each edge location pulls its own copy of a new popular file from your origin; with it, those misses collapse into one request. (Simultaneous misses at one location are also collapsed into a single origin request, so a viral file does not stampede you.)

Cache keys, TTLs and invalidation

The cache key decides when two requests share one cached response. Every extra ingredient (a header, a cookie, a query parameter) splits the cache and lowers the hit ratio, so include only what changes the response: Accept-Encoding for compression, a ?w=400 image width. Leave out tracking parameters, and never forward Cookie on static files.

TTLs come from the origin's headers. Cache-Control: max-age=N applies to browsers and shared caches, s-maxage=N to shared caches only. An ETag or Last-Modified lets an expired copy be revalidated with a cheap 304. If the origin says nothing, CloudFront's default is 24 hours.

So how do you ship a new version of a file? Two options.

Shipping a new version of app.js

Invalidate the old URL

Same URL, new bytes. You tell the CDN to forget the file.

  • An API call that takes seconds to minutes to reach every location
  • Costs money past a free quota (CloudFront: the first 1,000 paths a month are free)
  • Does nothing for copies in users' browsers, which keep the old file until max-age runs out
  • During the rollout some users see old JS with new HTML

Version the URL

New bytes, new URL: app.3f9a2c.js, named after a hash of the content.

  • Cache it for a year and mark it immutable
  • Only the small HTML page that names the bundle has a short TTL
  • Nothing to invalidate; old and new files coexist during a rollout, and a rollback is just a different HTML page
# the HTML page that names the current bundle: stay close to fresh
Cache-Control: public, max-age=60, stale-while-revalidate=300

# fingerprinted assets: the URL changes whenever the bytes do, so cache them for a year
Cache-Control: public, max-age=31536000, immutable

stale-while-revalidate lets the cache serve a slightly old copy instantly while it refreshes in the background; most CDNs also support stale-if-error, which keeps serving the last good copy while your origin is down.

Private content, cost, and where the CDN stops

Public files are easy. For private content (paid videos, user documents) the edge must check authorisation without calling your app on every request. The pattern: your app, which knows who the user is, creates a signed URL (or signed cookies, which cover many files such as video segments) with an expiry and a signature made from a private key. The CDN holds the matching public key, verifies the signature at the edge, and only then serves. Lock the origin so that only the CDN can read it (CloudFront Origin Access Control), otherwise people can bypass the checks by going straight to the bucket.

sequenceDiagram
  participant U as User
  participant A as App
  participant E as CDN edge
  participant S as S3 origin
  U->>A: GET /videos/42 (logged in)
  A->>A: check the user may watch it
  A-->>U: signed URL, expires in 10 min
  U->>E: GET the signed URL
  E->>E: verify signature and expiry
  E->>S: fetch with origin access control
  S-->>E: video bytes
  E-->>U: video bytes (cached for later)
Authorisation happens once, in your app. After that the edge enforces it with arithmetic, not a database call.

Where the money goes. Storage (per GB-month, by class), requests (per thousand GETs and PUTs), and data transfer out to the internet, which is usually the biggest line for media. Transfer into S3 is free, and so is transfer from S3 to CloudFront. Transfer out to users is billed per GB at list prices of roughly $0.02 to $0.12 depending on region and volume tier. A CDN does not make bytes free: it moves them to the CDN's (tiered, often discounted) rate, removes the S3 request fees for hits, and above all keeps the load off your origin. Many tiny objects hurt differently: a million 1 KB GETs cost more in request fees than in bandwidth.

What the CDN takes off your origin

Hit ratio is the lever. At 95% the origin sees one request in twenty and one twentieth of the bandwidth. The price is an illustrative list price per GB; the point is the relative size of the numbers, not the exact dollars.

Where the CDN stops. Not everything belongs at the edge. The rule: cache a response at a shared edge only if the same bytes are right for many users for at least a few seconds.

flowchart TD
  A{Same bytes for<br/>many users?} -->|yes| B{Rarely changes, or the<br/>URL changes with it?}
  A -->|no| APP[Serve from the app<br/>personalised or private]
  B -->|yes| CDN1[CDN with a long TTL]
  B -->|no| C{Can it be seconds stale?}
  C -->|yes| CDN2[CDN with a short TTL<br/>and stale-while-revalidate]
  C -->|no| APP
Even a 5-second TTL turns 10,000 requests per second for the same URL into a handful at the origin.

How to talk about it in an interview

Follow-up questions to expect

How do you stop someone uploading something huge or malicious?

Use a presigned POST policy with content-length-range and an allowed content type. Land uploads under a quarantine prefix, let the ObjectCreated consumer scan them, and only then mark them available. Serve user uploads from a separate domain, with Content-Disposition: attachment where possible, and keep S3 Block Public Access on.

How do you serve a private image only to its owner?

Signed URLs or signed cookies at the CDN with a short expiry, and an origin that only the CDN can read. For low volume, an authenticated endpoint that streams the object is simpler.

A celebrity posts and millions of people request the same new image at once.

The edge collapses concurrent misses into one origin request, an origin shield collapses them across locations, and every later request is a hit. S3's per-prefix limits never come into play behind a CDN.

How do you delete a user's data completely?

With versioning on, a delete only adds a marker, so delete every version (or let a lifecycle rule expire noncurrent versions). Then deal with CDN copies (invalidate), replicas and backups, and derived objects such as thumbnails. Design for it up front with per-user prefixes.

What if the region or the bucket is unavailable?

Replicate to a second bucket in another region, configure the CDN with an origin failover group, and let it serve stale copies while the origin is down. Uploads degrade first, and that is usually acceptable.

Object storage and CDN checklist for a design discussion

A strong answer to 'design photo upload and serving': 'Clients ask the API for a presigned POST URL, with a 10 MB limit and image content types, and upload straight to S3. An ObjectCreated event goes to SQS, and workers scan the image and create thumbnails. The database stores only the key, owner and status. Reads go through CloudFront with content-hashed keys and a one-year TTL; private photos use signed URLs. A lifecycle rule moves originals to Standard-IA after 30 days and aborts incomplete multipart uploads after 7. S3 gives eleven nines of durability; versioning protects against accidental deletes.'
