Case study: chat application

Design a chat service for tens of millions of users: hold millions of WebSocket connections, give every conversation a server-assigned order, make sends idempotent, track sent, delivered and read cheaply, fan out to groups, deliver to users who were offline, and route each message to the server that holds the recipient's socket. You finish with a five-sentence answer you can say out loud.

After this chapter you can
  • Run the interview script on a chat system: requirements, estimates, API, data model, high-level design, deep dives, trade-offs
  • Compare WebSockets, long polling and SSE, and justify WebSockets for the chat path
  • Order messages with per-conversation sequence numbers, de-duplicate retries with client message ids, and track receipts as watermarks
  • Design group fan-out, offline delivery with push notifications, and heartbeat-based presence
  • Route messages across chat servers with a session registry, and survive a server crash without a reconnect storm

Requirements and scope

A chat application lets people exchange messages in near real time, one to one or in groups, and receive them later if they were offline. It looks like a CRUD app until three things sink in. The server has to push to clients, which means holding open connections. Order and delivery have to be right per conversation. And the connection layer is stateful, in a system where everything else tries to be stateless.

Fix the scope first and say the numbers out loud.

Requirements to confirm with the interviewer

Ask about group size limits, multi-device, whether end-to-end encryption is required (it changes what the server can do) and how long history is kept. Then say the sentence that frames the whole design: messages are tiny, so the hard problems are connections and ordering, not bandwidth.

Estimates that shape the design

Chat is unusual because the message rate is not the bottleneck. Put the message rate and the connection count side by side and see which one sizes the fleet. Heartbeats, the small periodic pings that keep a connection alive and detect dead peers, are included because they are easy to forget and turn out to be a load of their own.

Messages, sockets, servers and storage

Read the outputs as decisions:

  • About 70 thousand messages per second at peak is modest. A store partitioned by conversation absorbs it, and the chat servers are not CPU-bound.
  • 10 million concurrent sockets are the real cost. At 100 thousand per server that is about 130 servers with headroom, sized by connections and memory (about 2 GB of connection state per server at 20 KB each), not by CPU.
  • About 330 thousand heartbeats per second. Answer them on the chat server and refresh presence in batches; a Redis write per heartbeat would be a load test of its own.
  • About 370 GB of new message data per day, roughly 400 TB a year with three replicas. It is append-only and read mostly near the newest messages, so partition by conversation and move old data to cheaper storage.

API and data model

The chat path is a WebSocket carrying small typed frames in both directions. Everything that is not latency-critical (history, the conversation list, group management, uploads) stays plain REST, where caching, retries and load balancing are boring and well understood.

The client chooses client_msg_id; the server chooses seq. Receipts carry 'up to' a sequence number, never one id per message.

Three details interviewers like. The client message id is generated on the phone before the first attempt, so a resend after a lost ack can be recognised as the same message. The sequence number is assigned by the server, per conversation, and it is the only thing that defines order. And receipts are cumulative: 'delivered up to 41' covers every earlier message in one small frame.

Every hot read is 'the newest messages of one conversation', so the message table is partitioned by conv_id and sorted by seq inside each partition: one partition read returns a screenful in order. A wide-column store (Cassandra, ScyllaDB) or a key-value store with sort keys (DynamoDB) fits that shape; very busy conversations add a time bucket to the partition key so no partition grows without limit. Memberships hold each member's two receipt watermarks, and devices hold push tokens.

The send path is chat server, store, registry, chat server. Push, presence, REST and media hang off it without slowing it down.

In this design the chat servers do two jobs: they hold sockets, and they run the send path (assign a sequence number, store, route). That is fine for an interview answer. At larger scale the two are often split: thin connection servers that only hold sockets, and a stateless message service behind them. The split means a deploy of message logic does not drop millions of connections, and each tier scales on its own metric: sockets for one, messages per second for the other.

Deep dive 1: the real-time connection

▶ Video lesson: One WebSocket, from upgrade to delivered 4:21 · 6 scenes · narrated, pause anytime and explore

HTTP is request and response: the client asks, the server answers. Chat needs the server to speak first, the moment a message arrives for you. Three techniques give you that.

  • Long polling keeps a normal HTTP request open until the server has something to say, answers, and the client immediately asks again.
  • Server-Sent Events (SSE) keep one HTTP response open and stream events down it. The client sends anything it has to say with ordinary POST requests.
  • WebSockets upgrade an HTTP connection into a persistent, two-way channel with its own light framing (RFC 6455).

Chat needs low-latency traffic in both directions, so WebSocket is the primary transport. The others are fallbacks or fit other products.

The usual answer is WebSocket for the chat path, REST for everything that is not latency-critical and mobile push when the app is closed. Some client libraries fall back to long polling automatically when a proxy breaks WebSockets. Step through a connection from the first byte to the first delivery receipt.

Keeping a connection alive

  • NATs, carrier networks and proxies silently drop TCP connections that stay idle too long (often after a few minutes, sometimes less), so both sides exchange a heartbeat every 20 to 30 s. Two missed heartbeats mean the connection is dead.
  • Mobile operating systems suspend background apps and their sockets. That gap is what push notifications fill.
  • When a connection drops, the app reconnects with jittered exponential backoff (Reliability patterns) and resumes with a sync from its cursors, so nothing sent in between is lost.

Deep dive 2: ordering, delivery states and idempotent sends

▶ Video lesson: Order, receipts and safe resends 4:17 · 6 scenes · narrated, pause anytime and explore

Order is a per-conversation sequence number

Sorting by timestamp looks natural and breaks in practice. Phone clocks are off by seconds or minutes, two servers' clocks differ by milliseconds, and two messages can carry the same millisecond. Chat needs a total order within each conversation and nothing more, so give each conversation a counter and stamp every message with the next value when the server accepts it. Arrival order at the server becomes the conversation's order, every member sorts by seq, and timestamps stay for display only.

Assign the number and write the message in one step, at a single owner per conversation: the conversation's partition leader, a lock on its row, or one actor per conversation. If two servers could hand out 41 and 42 and commit them in the opposite order, a reader that has already seen 42 would skip 41 forever when it asks for 'everything after 42'.

stateDiagram-v2
  [*] --> Pending: user taps send
  Pending --> Sent: server ack with seq
  Pending --> Failed: no ack, retries used up
  Failed --> Pending: user taps retry
  Sent --> Delivered: recipient device acks
  Delivered --> Read: recipient opens the chat
  Read --> [*]
The sender's view of one message. Only Pending and Failed live on the phone alone; the rest are facts the server reports.

Receipts are watermarks

Storing 'delivered' and 'read' as rows per message and per member grows with both. Instead each membership holds two numbers, delivered_upto and read_upto, and every ack moves them forward. Message 41 is delivered to Bob when his delivered_upto is at least 41; in a group it is delivered to everyone when the minimum across members reaches 41. Idempotent sends

A phone on a train sends a message, the server stores it, and the ack is lost in a tunnel. The app cannot tell 'never arrived' from 'arrived, ack lost', so it resends. The client message id makes the resend harmless: the server keeps a unique index on (conv_id, sender_id, client_msg_id) and answers a duplicate with the sequence number it already assigned. It is the idempotency-key pattern from Reliability patterns, applied to every message.

The resend writes nothing and delivers nothing new. Alice and Bob each see one message.

The send path: store once under the conversation's lock, then deliver

def store_message(db, conv_id: str, sender: str, client_msg_id: str, body: str) -> int:
    """Store a message once and return its sequence number. Safe to call again with the same client_msg_id."""
    with db.transaction():
        # the row lock serialises senders in this conversation, so sequence order is also commit order
        last = db.fetch_one("SELECT last_seq FROM conversations WHERE conv_id = %s FOR UPDATE", (conv_id,))["last_seq"]
        dup = db.fetch_one("SELECT seq FROM messages WHERE conv_id = %s AND sender_id = %s AND client_msg_id = %s",
                           (conv_id, sender, client_msg_id))
        if dup:
            return dup["seq"]                    # a resend: answer with the number already assigned
        seq = last + 1
        db.execute("INSERT INTO messages (conv_id, seq, sender_id, client_msg_id, body) VALUES (%s, %s, %s, %s, %s)",
                   (conv_id, seq, sender, client_msg_id, body))
        db.execute("UPDATE conversations SET last_seq = %s WHERE conv_id = %s", (seq, conv_id))
        return seq


def deliver_after_store(registry, router, push, members: list[str], sender: str, message: dict) -> None:
    by_server: dict[str, list[str]] = {}
    others = [m for m in members if m != sender]
    for user, servers in registry.lookup_many(others).items():   # one batched read for all members
        if not servers:
            push.notify(user, conv_id=message["conv_id"])      # a wake-up; the app syncs by sequence number
        for server in servers:
            by_server.setdefault(server, []).append(user)
    for server, users in by_server.items():
        router.forward(server, users, message)                 # one internal message per chat server, not per member
One lock per conversation is the single owner. A busy group sends a few messages a second, so serialising them costs nothing; the unique index on (conv_id, sender_id, client_msg_id) stays as a backstop.

Deep dive 3: groups, offline users, presence and encryption

Group fan-out

A group message is stored once, with the group's next sequence number; fan-out is about delivery, not copies. The sender's server looks up every member's connections in the registry, groups them by chat server and sends one internal message per server. Members without a connection get a push notification and catch up by cursor when they open the app. A 200-member group costs 199 deliveries per message, which is why the estimate has a deliveries-per-message input.

Past a few thousand members (a company-wide channel, a broadcast list), pushing every message to every member stops making sense, because most of them are not looking. Large channels switch to fan-out on read: deliver live only to members who have the channel open, send everyone else a light 'new activity' badge, and let them fetch when they open it. It is the same trade-off as fan-out on write versus read in a news feed (Case study: news feed).

flowchart LR
  S[Sender's server] --> ST[(Store once, seq 7)]
  S --> REG[(Registry lookup<br/>for all members)]
  S --> G1[Chat server 1]
  S --> G2[Chat server 2]
  S --> PU[Push service]
  G1 --> M1[Bob and Dan]
  G2 --> M2[Erin]
  PU --> M3[Carol, offline]
One write, one batched lookup, one forward per chat server, and pushes only for members with no connection.

Offline delivery and push notifications

The store is the offline queue. Each device remembers a cursor per conversation, the highest seq it holds; on reconnect it sends its cursors and the server returns everything above them, in order. Nothing is copied into a per-user mailbox that has to be kept in step. A user in hundreds of conversations should not send hundreds of cursors, so many designs add a per-user activity log ('conversation c9 reached 41'), which needs one cursor per device to answer 'what changed since I was last here?'.

Push notifications (APNs for Apple devices, FCM for Android and the web) are a wake-up, not the delivery. They can be delayed, collapsed or dropped, and carry only a few kilobytes. Send them only to devices with no live connection, collapse repeats per conversation, and never treat 'push sent' as 'delivered': only an ack from the device moves delivered_upto.

Multi-device falls out of the same pieces. The registry maps a user to all their connected devices, each device keeps its own cursors, and a read on the phone moves read_upto, which the server relays to the laptop so its unread badge clears.

Presence

Presence (online, typing, last seen) is the most-read and least-important data in the system, and it may be slightly wrong. Design it to be cheap:

flowchart LR
  APP[Bob app] -- heartbeat every 30 s --> CS[Chat server]
  CS -- batched refresh --> PS[(Presence store<br/>TTL 60 s)]
  PS -- change events --> PUB[Presence fan-out]
  PUB --> W[Friends viewing Bob]
Heartbeats stop at the chat server. Only changes travel further, and only to people who are looking.

End-to-end encryption

With end-to-end encryption (the Signal protocol, used by Signal and WhatsApp) the server stores and forwards ciphertext it cannot read. Most of this design is unchanged, because routing, sequence numbers, receipts and push all work on metadata. What changes: the server cannot search, preview or moderate content; push payloads must be generic or encrypted for the device; each recipient device has its own keys, so a group message is encrypted per device or with a group sender key that is replaced when membership changes; and a new device cannot read old messages unless an existing device sends it an encrypted copy. Name these consequences in an interview; do not design the cryptography.

Deep dive 4: scaling the connection layer

Chat servers are stateful: each holds tens of thousands of open sockets, and a message for Bob can leave only through the server that holds Bob's socket. Two things follow.

  • Sticky routing. A connection stays on the server that accepted it for its whole life, so the load balancer only places new connections. Least-connections is the right algorithm; round robin drifts as connections close at different rates.
  • A session registry maps each user (each device) to the server that holds it: bob → cs2, written on connect, deleted on a clean disconnect, and given a TTL of about a minute that the server refreshes in batches, so a crashed server's entries expire on their own. Every send reads the registry once per recipient, batched for groups.

The alternative is to compute the server: send each user to hash(user_id) with consistent hashing, so any server can work out where Bob must be. That saves the lookup, but the load balancer must route by user at connect time and every change to the fleet moves users between servers. Deploys, crashes and reconnect storms

  • A crashed server takes about 100 thousand sockets with it. If every client reconnects at once, the remaining servers face 100 thousand TLS handshakes in the same second. Clients reconnect with jittered exponential backoff, and servers cap the rate at which they accept new connections (Reliability patterns).
  • Deploys drain instead of killing: stop accepting new connections, close existing ones gradually over several minutes with a WebSocket close frame (code 1001, 'going away') so clients reconnect elsewhere, then stop. Rolling 130 servers this way takes time, which is one more reason to keep message logic out of the connection servers.
  • Never trust the registry blindly. An entry can be stale for up to its TTL. A failed forward means 'treat as offline', and the message is safe in the store anyway.
  • Delivery is at-least-once end to end: a message can arrive twice (a forward retried after a timeout, a sync that overlaps a live delivery), so clients de-duplicate by seq, which they store anyway for ordering.

What interviewers ask next

How do you keep order in a busy group with many senders?

One owner per conversation assigns the sequence number in the same step as the write: the conversation's partition leader, a row lock, or an actor per conversation. Order is per conversation only, so there is no global bottleneck; a group sends a few messages a second, far below what one owner can serialise.

What if the recipient's server crashes right after you forwarded the message?

Nothing is lost, because the message was stored before it was acked to the sender. Bob's delivered watermark only moves when his device acks, so on reconnect his cursor is still below the message and the sync returns it. The client drops any duplicate by seq.

How does a user on three devices see one consistent inbox?

The registry maps the user to all connected devices, and each device keeps its own cursors, so each catches up independently. Read state lives on the membership (read_upto), and the server relays changes to the other devices so their unread badges clear.

How would you deliver to a channel with 100,000 members?

Not by pushing every message to every member. Deliver live to the members viewing the channel, send a light 'new activity' marker to the rest, and let them fetch on open (fan-out on read). Rate-limit push notifications per member and per channel.

How do you store years of history cheaply?

Partition by conversation plus a time bucket (say a month) so no partition grows without limit, keep recent buckets on fast storage and move old ones to cheaper tiers. Media lives in object storage behind a CDN, and messages hold links.

How would you add search?

Feed a search index from the message stream asynchronously, partitioned by user or conversation and filtered by membership at query time. With end-to-end encryption the server cannot index content, so search runs on the device.

How do you run this in several regions?

Users connect to the nearest region. Each conversation has a home region that assigns its sequence numbers; other regions forward sends there and receive deliveries back, which adds a cross-region hop only for conversations that span regions.

What do you monitor?

Send-to-deliver latency (p50 and p99), the share of sends acked, connections per server, reconnect rate (a spike means a crash or a bad deploy), registry staleness (failed forwards), push failures, and sync sizes on reconnect.

A five-sentence model answer

'I would confirm scope first: one-to-one chat and groups of a few hundred, sent, delivered and read receipts, presence, offline delivery and several devices per user, for 50 million daily users. That is about 70 thousand messages a second at peak but 10 million open connections, so the fleet is sized by sockets: roughly 130 chat servers holding WebSockets behind a layer-4 load balancer, with a Redis session registry that maps each device to its server. A send is stored once in a store partitioned by conversation, with a sequence number from a single owner per conversation and a client message id that makes resends idempotent, and only then acknowledged as sent. Delivery forwards to the recipient's server, or sends a push and lets the device sync from its cursor on reconnect; receipts are per-member watermarks, and groups fan out once per chat server. Presence comes from heartbeats with a TTL and goes only to people who are looking, and clients reconnect with jittered backoff so a server crash does not become a stampede.'
