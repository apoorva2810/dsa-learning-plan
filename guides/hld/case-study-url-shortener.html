Case study: URL shortener

Design a service that turns long URLs into short codes and redirects them at tens of thousands of requests per second. You will size it, choose between three ways of generating unique codes, decide between 301 and 302, keep analytics off the hot path, and finish with a five-sentence answer you can say out loud.

After this chapter you can
  • Run the interview script on a URL shortener: requirements, estimates, API, data model, high-level design, deep dives, trade-offs
  • Size the system from links per day and read:write ratio, and derive the code length from the retention period
  • Compare counter + base62, hash + collision check, and a pre-generated key service, and pick one for a stated reason
  • Explain why the redirect path is a cache-aside read and when a 301 or a 302 is the right status
  • Keep click analytics off the hot path, and handle expiry, custom aliases and abuse

Requirements and scope

A URL shortener turns https://www.example.com/products/2026/summer-sale?utm=mail into https://sho.rt/aZ3kQ9x and sends anyone who opens the short link to the original page. The product is trivial. The engineering is a read-heavy key-value service with three real problems: generating unique codes without a bottleneck, answering redirects in a few milliseconds at tens of thousands of requests per second, and counting clicks without slowing a redirect down.

Use the first five minutes to fix the scope. Say the checklist out loud and write down the numbers you assume.

Requirements to confirm with the interviewer

The interviewer is checking whether you ask before you draw. Four questions remove most of the ambiguity: do links expire, can users pick their own alias, is analytics in scope and how fresh must it be, and how many links per day. State your assumptions and move on; do not wait for a perfect answer.

Estimates that shape the design

Each number below changes a design decision. Change the inputs and see which outputs move.

Two assumptions carry most of the weight: the read:write ratio (people click a link far more often than they create it) and the retention (links live for years, so storage only grows). The cache figure is an upper bound because it pretends every redirect in a day goes to a different link. Real traffic repeats popular links, so the true working set is much smaller.

Traffic, storage and code length

Read the outputs as decisions:

  • About 120 creates per second is within reach of a single primary, so the write path is a correctness problem (unique codes), not a throughput problem.
  • About 12k redirects per second on average and 35k at peak is where a cache earns its place. The store alone would need many replicas.
  • About 9 TB after five years is too much for one comfortable node and it only grows. Shard on the code from the start.
  • 6 characters already cover 18 billion links (62^6 is about 56.8 billion). Use 7 (62^7 is about 3.5 trillion) for headroom and for the scattering trick later in this chapter.

API and data model

Two public endpoints do almost all the work. The redirect lives at the root so the short link stays short; the management API is versioned.

The create call returns 201 with the canonical short URL. A taken alias is 409, not 400.

Three details interviewers like. The create call accepts an Idempotency-Key, otherwise a client that retries after a timeout creates two links (see Reliability patterns). A taken alias is 409 Conflict, because the request was valid but clashes with existing state. And the redirect carries no auth: anyone with the link may follow it.

The hot path is one lookup by short_code, so the core table is shaped like a key-value map: short_code is the primary key and the partition key, and nothing on the redirect path needs a join. Analytics goes to its own rollup table written by workers, never by the redirect handler. The key pool exists only if you choose the pre-generated key design below. A secondary index on user_id serves 'list my links'.

Deep dive 1: generating the short code

▶ Video lesson: Generating a code nobody else has 4:46 · 7 scenes · narrated, pause anytime and explore

Every link needs a code nobody else has, which is a distributed-systems problem in disguise: many API instances create links at once and none may issue the same code. There are three families of answer.

  • Counter + base62. Get a unique integer and write it in base 62 (0-9a-zA-Z). Uniqueness is inherited from the integer, so there is no collision to detect. The integer comes from a database sequence or, to avoid a hot spot, from ranges: each API instance leases a block (say 10,000 ids) from a coordinator and hands them out from memory.
  • Hash + collision check. Hash the long URL and keep enough bits for 7 characters. Identical URLs get identical codes, which is free de-duplication if you want it. But 7 characters are only 3.5 trillion values, and the birthday effect gives about 1,400 colliding pairs after just 100 million links. Every create becomes a conditional insert that may need a retry with a salt.
  • Pre-generated keys (a key service). An offline job fills a pool with random unique codes; API instances claim batches of 1,000. Codes are random and uniqueness is settled in advance, so the create path does no hashing or retrying. The price is one more component to run and keep available.

Start at the top. The first question that matters is whether the same URL must always map to the same code.

Base62: from counter to short code

Counter + base62, one division at a time. The remainders come out in reverse order, so the last step reads them backwards. The last two scenarios add fixed-width padding and the scatter step.

A raw counter produces sequential codes: someone who sees aZ3kQ9x can guess the next one and walk through other people's links. You can fix that without giving up uniqueness by running the counter through a keyed permutation of the code space. A Feistel network is the classic tool: it splits the number into two halves and mixes them over a few rounds with a keyed hash, and it is a permutation whatever the round function is. 62^7 is not a power of two, so run it over 42 bits (2^42, about 4.4 trillion, is the next power of two) and, if the result lands outside the code space, run it again. This 'cycle-walking' takes 1.25 passes on average. Distinct counters still give distinct codes, so there is still no collision check, and without the key the next code is hard to predict.

It does not replace authorization: for private content use real access control, not a secret URL.

Base62 encode, decode and a keyed scatter

import hashlib

ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
BASE = len(ALPHABET)            # 62
SPACE = BASE ** 7               # 3,521,614,606,208 possible 7-character codes
HALF = 21                       # 2 * 21 = 42 bits: 2**42 is the smallest power of two above 62**7
MASK = (1 << HALF) - 1
SECRET = b"load-me-from-your-secrets-manager"


def encode(n: int, width: int = 7) -> str:
    chars = []
    while n:
        n, r = divmod(n, BASE)
        chars.append(ALPHABET[r])
    return "".join(reversed(chars)).rjust(width, ALPHABET[0])


def decode(code: str) -> int:
    n = 0
    for ch in code:
        n = n * BASE + ALPHABET.index(ch)
    return n


def _round(half: int, round_no: int) -> int:
    msg = half.to_bytes(4, "big") + bytes([round_no])
    return int.from_bytes(hashlib.blake2b(msg, key=SECRET, digest_size=4).digest(), "big") & MASK


def _feistel(n: int, rounds: int = 4) -> int:
    left, right = n >> HALF, n & MASK
    for round_no in range(rounds):
        left, right = right, left ^ _round(right, round_no)
    return (left << HALF) | right


def scatter(counter: int) -> int:
    """Keyed bijection on [0, 62**7): permute 42 bits, and permute again while the result is outside the space."""
    n = _feistel(counter)
    while n >= SPACE:
        n = _feistel(n)
    return n


print(encode(125, width=0))       # '21'
print(encode(scatter(125)))       # 7 characters that look random and change with SECRET
Redirects never call decode(): the code is just a primary key. Decoding matters only if you shard by id range.

The three strategies in code

Each API instance leases a block of ids from a coordinator (a single row updated atomically, or etcd/ZooKeeper) and serves from memory. A crash wastes the unused part of one block, which does not matter in a 3.5 trillion space.

class RangeAllocator:
    def __init__(self, coordinator, block: int = 10_000):
        self.coordinator = coordinator
        self.block = block
        self.next_id = 0
        self.limit = 0                      # exclusive end of the current range

    def next_code(self) -> str:
        if self.next_id >= self.limit:      # range exhausted: lease a new one
            start = self.coordinator.lease(self.block)   # UPDATE ... SET next = next + :block RETURNING
            self.next_id, self.limit = start, start + self.block
        value = self.next_id
        self.next_id += 1
        return encode(scatter(value))

No coordination, but every create is a conditional insert that can fail. Salt the hash on conflict. Without a salt, the same URL always maps to the same code.

import hashlib


def code_from_url(long_url: str, salt: int = 0) -> str:
    digest = hashlib.sha256(f"{salt}:{long_url}".encode()).digest()
    n = int.from_bytes(digest[:6], "big") % SPACE      # 48 bits folded into the 7-character space
    return encode(n)


def create(long_url: str, store) -> str:
    for salt in range(5):
        code = code_from_url(long_url, salt)
        if store.insert_if_absent(code, long_url):     # unique primary key / conditional put
            return code
    raise RuntimeError("too many collisions")

SKIP LOCKED lets many callers claim disjoint batches at once without waiting for each other. The delete and the return are one statement, so a key cannot be handed out twice.

CLAIM_SQL = """
DELETE FROM unused_keys
WHERE short_code IN (
    SELECT short_code FROM unused_keys LIMIT %(n)s FOR UPDATE SKIP LOCKED
)
RETURNING short_code
"""


class KeyAllocator:
    def __init__(self, db, batch: int = 1000):
        self.db, self.batch, self.keys = db, batch, []

    def next_code(self) -> str:
        if not self.keys:
            rows = self.db.fetch(CLAIM_SQL, {"n": self.batch})
            if not rows:
                raise RuntimeError("key pool is empty: page the on-call")
            self.keys = [r["short_code"] for r in rows]
        return self.keys.pop()

Deep dive 2: the redirect path

The redirect is the product. Its job is to parse the code, find the long URL and send a Location header; everything else is making that cheaper and safer. Redirects with a cache: hit and miss counters

Watch the counters on the cache box and the store. The first scenario has a few hot links; the second is a scan of one-off links where an LRU cache cannot help; the last two replay a scraper hitting codes that do not exist, with and without negative caching.

301 or 302?

301 Moved Permanently

Browsers and CDNs may cache the redirect indefinitely, so repeat visitors never reach your servers again. That cuts load and latency. It also means you cannot count those clicks, cannot change or expire the target for anyone who already followed the link, and a wrong redirect stays in people's browsers.

302 Found (the default here)

Not cached unless you say so, so every click reaches the service. You keep exact analytics, expiry, take-down and editable targets. The cost is that your redirect tier carries all the traffic, which the cache and estimates above already budget for. A middle path is 301 with a short Cache-Control: max-age, trading some analytics accuracy for load.

Cache details

  • Key and value. url:{code} maps to the long URL plus expires_at, so expiry is checked even on a hit.
  • TTL. The mapping rarely changes, so an hour or more is fine, capped at the time left before expires_at. When an owner edits or disables a link, delete the key.
  • Eviction. LRU keeps the hot set in memory and lets one-off links age out. A scan of one-off links, as in the second scenario, defeats it and is why the hit ratio is a metric to watch.
  • Negative caching. Cache 'this code does not exist' for a short time, so typos and scrapers stop at the cache.
  • Hot key. A viral link sends all its traffic to one Redis shard. Add a few-second in-process cache in each redirect instance, or store the key under several suffixes and read one at random.
  • Cache down. Fail open to the store behind a circuit breaker. The store then sees about 12k reads per second instead of a few hundred, so plan its degraded mode: per-IP rate limits and a bounded queue.

The store

The access pattern is single-key reads and append-style writes with rare updates, with no joins. A key-value or wide-column store (DynamoDB, Cassandra) shards and replicates that out of the box, and a sharded relational database also works. Either way, shard on a hash of the code, not on code ranges: a counter-based scheme produces sequential codes, and range sharding would send every new write to the last shard. Conditional writes provide the uniqueness guarantee: a primary key in SQL, attribute_not_exists in DynamoDB, IF NOT EXISTS in Cassandra (slower, it runs a consensus round). See Scaling databases: replication, sharding, partitioning for partitioning and rebalancing.

Deep dive 3: analytics, expiry, aliases and abuse

Click analytics without slowing redirects

The redirect handler publishes one small event (code, timestamp, country, user-agent class, referrer) to a queue and returns. Consumers aggregate in memory by code and minute and flush in batches into rollup rows, so a link with a million clicks costs thousands of writes, not a million. Delivery is at-least-once, so a crash between a flush and the offset commit can count a batch twice. That is fine for dashboards; for billing, dedupe on an event id. Unique visitors use a HyperLogLog sketch instead of a set. Message queues & streaming (Kafka) covers partitioning and delivery guarantees.

A batching click aggregator

import time
from collections import Counter


class ClickAggregator:
    """Count clicks per (code, minute) in memory and write them in one batched upsert."""

    def __init__(self, sink, flush_every: float = 5.0):
        self.sink = sink
        self.flush_every = flush_every
        self.counts: Counter = Counter()
        self.last_flush = time.monotonic()

    def on_event(self, event: dict) -> None:
        minute = event["ts"] // 60 * 60
        self.counts[(event["code"], minute)] += 1
        if time.monotonic() - self.last_flush >= self.flush_every:
            self.flush()

    def flush(self) -> None:
        if self.counts:
            # INSERT ... ON CONFLICT (code, minute) DO UPDATE SET clicks = clicks + EXCLUDED.clicks
            self.sink.upsert_add(self.counts)
            self.counts = Counter()
        self.last_flush = time.monotonic()
Hot links collapse many events into one row update per flush. Commit the queue offset only after the flush succeeds.

Expiry

Expiry has two halves. The read path compares expires_at with the clock on every lookup, so a link stops working at the right moment even if no job has run. A sweeper reclaims space later: a background job scans an index on expires_at and deletes rows in small batches, or the store does it with a native TTL (DynamoDB and Cassandra can). The cache TTL must never outlive expires_at.

stateDiagram-v2
  [*] --> Active: created
  Active --> Expired: expires_at passes
  Active --> Disabled: reported as abuse
  Expired --> Purged: sweeper deletes the row
  Disabled --> Purged: retention window ends
  Purged --> [*]
The redirect path only distinguishes Active from everything else. Purging is housekeeping.

Custom aliases

  • Validate: 4 to 20 characters from A-Za-z0-9_-, reject reserved words (api, admin, login, static) and run a profanity check.
  • Claim with the same conditional insert as generated codes and answer 409 to the loser. 'Check then insert' has a race: two requests both see the alias free and both write.
  • Aliases and generated codes share one key space. If the allocator produces a code that already exists as an alias, the conditional insert fails and it takes the next value.

Abuse

  • Rate-limit creates per API key and per IP with a token bucket (Reliability patterns).
  • Validate the destination: http and https only, a maximum length, and a check against a phishing and malware blocklist before saving. Re-scan periodically, because a page can turn malicious after the link was created.
  • Take-down path: set the status to Disabled and delete the cache key. Optionally show a warning page instead of a 404 for flagged links.
  • Enumeration: random or scattered codes in a 3.5 trillion space are impractical to guess. Rate-limit 404s per IP and put the redirect tier behind a CDN or WAF for floods.

What interviewers ask next

How do you avoid collisions with many API servers?

Each instance gets its own id range or key batch, so ids cannot overlap by construction. The conditional insert stays as a backstop. A single shared sequence would work at 120 creates per second but is a bottleneck and a single point of failure at 100 times that.

What if the key service or the range coordinator is down?

Instances keep creating from what they hold: a 10,000-id range lasts about 17 minutes at 10 creates per second per instance. Run the coordinator as a replicated pair and alert when a batch is under 20 percent. Worst case creates fail while redirects keep working.

How do you shard the store, and what about one viral link?

Shard on a hash of short_code, with consistent hashing so adding a node moves only a fraction of keys. A viral link is a hot key: the cache absorbs it, an in-process cache in each redirect instance absorbs the rest, and the store sees only misses.

How do you let an owner change a link's target?

Update the row and delete the cache key. This works immediately with 302 because browsers do not cache it. With 301, copies in browsers and CDNs stay stale, which is one more reason to default to 302.

Should the same long URL always get the same code?

Usually not: different owners want separate analytics, expiry and take-down. If you need de-duplication per user, add a unique index on user and a hash of the long URL rather than deriving the code from the URL.

How would you run this in several regions?

Serve redirects from local caches and read replicas. Create in a home region, or give each region its own id range so they can create independently without overlap. Replication lags, so on a local miss ask the home region once before answering 404.

How do you show real-time click counts?

Aggregators flush every few seconds, so the dashboard reads the rollup plus an in-memory delta. 'Near real time' is enough; exact counts come from a batch job over the raw events.

What do you monitor and alert on?

Redirect p50 and p99 and error rate, cache hit ratio (a sudden drop is usually a deploy or a flushed cache), store read QPS, key pool depth, 404 rate (scrapers), create rate-limit rejections, and analytics queue lag.

A five-sentence model answer

'I would confirm scope first: create, redirect, optional alias and expiry, best-effort analytics, 100 redirects per create and about 10 million new links a day. That is roughly 120 creates and 12 thousand redirects a second, 9 TB over five years, so a sharded key-value store with a Redis cache in front, and 7 base62 characters give 3.5 trillion codes. Codes come from a counter that each API instance leases in ranges and scrambles with a keyed permutation, so they are unique without a collision check and not trivially guessable. Redirects are cache-aside lookups that answer 302, which keeps analytics and expiry correct, and click events go to a queue and are aggregated asynchronously so the hot path is one cache read. Abuse is handled with per-key rate limits and a URL reputation check on create, and I would watch cache hit ratio, p99 redirect latency, key-range headroom and the 404 rate.'
