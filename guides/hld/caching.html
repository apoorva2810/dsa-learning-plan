Caching

Caches trade a little staleness for a lot of speed. This chapter shows where caches sit, how reads and writes flow through them, how eviction and invalidation work, the ways caches fail in production, and how to talk about all of it in a system design interview.

After this chapter you can
  • Explain where a cache helps (and where it cannot) using latency and hit-ratio numbers
  • Choose between cache-aside, read-through, write-through, write-back and write-around, and say why
  • Walk through LRU eviction and explain why a hash map + linked list gives O(1) operations
  • Name the three classic failure modes (stampede, hot key, penetration) and a fix for each
  • Pick TTLs and invalidation strategies and state the consistency you are giving up

Why cache at all?

▶ Video lesson: Why cache at all? 3:23 · 7 scenes · narrated, pause anytime and explore

A cache is a smaller, faster store that holds copies of data that lives somewhere slower. The whole idea rests on one observation: access is skewed. A few keys (today's top stories, the logged-in user's profile, the product on the front page) get most of the reads. Keep those copies close and the slow store barely notices the traffic.

Two numbers decide whether a cache is worth it:

  • Hit ratio: the fraction of reads the cache can answer. 90% is common for user-facing reads; 99% is possible for very skewed workloads.
  • The latency gap between the cache and the source. Memory on the same host is ~100 ns, Redis over the network ~0.5-1 ms, a database query 5-50 ms, a call to another service 10-200 ms.

Effective latency and database load

Move the hit ratio and watch what the database sees. The average latency formula is h × cache + (1 − h) × (cache + source): a miss pays for the cache lookup and the trip to the source.

Average latency improves a lot; tail latency does not. A miss still costs the full trip. If the interviewer asks 'what about p99?', the answer is: p99 is dominated by misses, so you either raise the hit ratio (warm the cache, bigger cache, longer TTL) or make the source itself faster.

Where caches live

There is rarely one cache. A request to a web application can be answered at several layers, each closer to the user than the next. Step through the diagram: each layer answers a different kind of staleness tolerance and traffic.

flowchart LR
  B[Browser cache] --> CDN[CDN edge]
  CDN --> GW[API gateway / reverse proxy]
  GW --> APP[App server<br/>in-process cache]
  APP --> R[(Distributed cache<br/>Redis / Memcached)]
  APP --> DB[(Database)]
  DB --> BC[DB buffer pool]
Layers a read can be answered at, nearest the user first. Everything to the left is cheaper and staler.

In an interview, say which layer you mean. 'Add a cache' is vague; 'cache the rendered feed per user in Redis with a 60 s TTL, and let the CDN cache images' is a design.

Read patterns: cache-aside and read-through

▶ Video lesson: Cache-aside, step by step 3:15 · 6 scenes · narrated, pause anytime and explore

Cache-aside (also 'lazy loading') is the default. The application owns the logic: look in the cache; on a miss, read the source, then write the result into the cache for next time. Only requested data is cached, and the cache can fail without taking the application down (it degrades to 'always miss').

Read-through moves that logic into the cache layer itself (or a library): the application only ever talks to the cache, which fetches from the source on a miss. Same data flow, different owner. Managed caches such as DAX for DynamoDB work this way.

sequenceDiagram
  participant C as Client
  participant A as App
  participant R as Redis
  participant D as Database
  C->>A: GET /users/42
  A->>R: GET user:42
  R-->>A: nil (miss)
  A->>D: SELECT * FROM users WHERE id=42
  D-->>A: row
  A->>R: SET user:42 {row} EX 300
  A-->>C: 200 OK (user)
Cache-aside on a miss. On a hit the sequence is just the first three arrows with a value instead of nil.

Cache-aside in Python

import json
import redis

r = redis.Redis()
TTL = 300  # seconds

def get_user(user_id: int) -> dict:
    key = f"user:{user_id}"
    cached = r.get(key)
    if cached is not None:
        return json.loads(cached)              # hit
    row = db.fetch_user(user_id)                # miss: go to the source of truth
    r.set(key, json.dumps(row), ex=TTL)         # fill for next time
    return row

A miss for a key that does not exist (user 999999) would hit the database every time. Cache the absence too, with a short TTL.

MISSING = "__missing__"

def get_user(user_id: int) -> dict | None:
    key = f"user:{user_id}"
    cached = r.get(key)
    if cached == MISSING:
        return None
    if cached is not None:
        return json.loads(cached)
    row = db.fetch_user(user_id)
    if row is None:
        r.set(key, MISSING, ex=30)              # short TTL: the user might be created soon
        return None
    r.set(key, json.dumps(row), ex=TTL)
    return row

If Redis is down, cache-aside should degrade to 'always miss', not to an outage. Wrap the cache calls and treat errors as misses; alert on the error rate.

def cache_get(key: str):
    try:
        return r.get(key)
    except redis.RedisError:
        metrics.incr("cache.error")
        return None                           # behave like a miss

def cache_set(key: str, value: str, ttl: int) -> None:
    try:
        r.set(key, value, ex=ttl)
    except redis.RedisError:
        metrics.incr("cache.error")           # never let the cache break the request

Write patterns

▶ Video lesson: Write patterns: who fixes the stale copy? 3:35 · 6 scenes · narrated, pause anytime and explore

Reads are the easy half. The moment data changes, every copy in every cache is wrong until something fixes it. The write pattern decides who fixes it and when.

PatternWhat happens on a writeCache is…RiskUse when
Write-throughApp writes to cache and database synchronouslyalways freshslower writes; caches data that may never be readread-heavy data that must be fresh right after a write (user profile)
Write-back (write-behind)App writes to cache; cache flushes to the DB later, in batchesfresh; DB lagsdata loss if the cache dies before flushingvery write-heavy counters, analytics, where losing seconds of data is acceptable
Write-aroundApp writes to the DB only; the cache entry is deleted or left to expirestale until next read fills ita read right after the write missesdata written once and read rarely (logs, large blobs)
Cache-aside + invalidateApp writes to the DB, then DELs the keyempty until next readrace window between the write and the delete (see below)the common default with cache-aside reads
Write strategies. Most systems combine cache-aside reads with 'write to the DB, then invalidate'.

Delete, don't set, after a write

Set the new value in the cache after writing the DB

Two writers race: writer A writes v1 to the DB, writer B writes v2, then B sets the cache to v2, then A's slower SET lands with v1. The DB says v2, the cache says v1 until the TTL expires.

Delete the key after writing the DB

Both writers DEL user:42. Whoever reads next misses and fills from the DB, which has the latest value. There is still a tiny window (read-miss fills with an old row while a write is in flight), which is why the TTL stays as a safety net.

flowchart TD
  W[Write request] --> DB[(Write to database)]
  DB --> DEL[DEL cache key]
  DEL --> R1[Next read misses]
  R1 --> FILL[Read DB, fill cache]
  W -. write-through .-> BOTH[Write DB and SET cache in one step]
  W -. write-back .-> WB[SET cache now, flush to DB later]
The invalidate-on-write path (solid) and the two alternatives (dotted).

Eviction: what to throw away when the cache is full

▶ Video lesson: LRU eviction, step by step 4:01 · 6 scenes · narrated, pause anytime and explore

A cache has less room than the source, so something must go. LRU (least recently used) evicts the entry that has gone longest without being read, on the bet that recent use predicts future use. It is the default in most libraries and a classic interview problem: an O(1) implementation needs a hash map for lookups and a doubly linked list to move an entry to the 'most recent' end and to drop the 'least recent' end.

LRU eviction step by step

Capacity 3. Watch the recency list: a hit moves a key to the MRU end; an insert into a full cache evicts the key at the LRU end.

Other policies and when they beat LRU

LFU (least frequently used)

Evicts the key with the fewest accesses. Better than LRU when a scan of many one-off keys would otherwise flush the genuinely popular ones. Redis offers an approximate LFU (allkeys-lfu). Weakness: an old key that was popular once stays forever unless counts decay.

FIFO / random

Cheap and surprisingly close to LRU for many workloads. Memcached's slab allocator uses per-size-class LRU; Redis samples a few keys and evicts the best candidate rather than keeping a perfect order, which is why its policies are called approximate.

TTL-based

Not an eviction policy for capacity, but for staleness: entries expire after a fixed time regardless of use. Combine with LRU: TTL bounds staleness, LRU bounds size.

Admission policies (TinyLFU)

Instead of only choosing what to evict, decide whether a new key is worth admitting at all, using a frequency sketch of recent requests. Used by Caffeine (Java). Mention it if asked how to protect a cache from scans.

TTL, invalidation and the consistency you give up

Every cached copy is a promise that stale within bounds is acceptable. Make the bound explicit:

  • A TTL is the maximum staleness you tolerate when nothing invalidates the key. 30 s for a feed, 5 min for a profile, 24 h for a country list.
  • Explicit invalidation (DEL on write) gets you close to read-your-writes for the common path. It needs every write path to know every key it affects, which is where bugs hide (the admin tool that updates the row directly, the batch job, the other service).
  • Versioned keys sidestep invalidation: store user:42:v17; a write bumps the version in one place and old keys simply expire. Costs memory for the dead versions.
  • Event-driven invalidation publishes change events (CDC from the database or a message bus); a consumer deletes or refreshes keys. Decouples writers from cache knowledge, adds a propagation delay.

'There are only two hard things in computer science: cache invalidation and naming things.' The joke is old because the problem is real: staleness bugs are invisible in tests and show up as 'I changed my name but it still shows the old one'. Always state the TTL and the invalidation path together.

sequenceDiagram
  participant R1 as Reader
  participant W as Writer
  participant C as Cache
  participant D as Database
  R1->>C: GET user:42
  C-->>R1: miss
  R1->>D: SELECT (returns name=Ann)
  W->>D: UPDATE name=Anna
  W->>C: DEL user:42
  R1->>C: SET user:42 name=Ann
  Note over C: stale 'Ann' until TTL
The cache-aside race: a slow reader fills the cache with a row it read before a write landed. The TTL is the safety net; very short 'fill' windows make it rare.

How caches fail in production

▶ Video lesson: How caches fail: the stampede 3:58 · 7 scenes · narrated, pause anytime and explore

Cache stampede: with and without protection

A hot key expires and many requests miss at once. Compare the unprotected run with the lock-based rebuild.

The failure catalogue (click each)

Stampede / thundering herd

Many concurrent misses on the same key hit the source at once, typically right after a TTL expiry or a cache restart. Fixes: a per-key lock so one request rebuilds; early recompute (refresh with probability rising as the TTL nears its end); request coalescing in the app; serving the stale value while refreshing in the background (stale-while-revalidate).

Hot key

One key (a celebrity's profile, a flash-sale product) receives more traffic than one cache node can serve; the node saturates while others idle. Fixes: replicate the key under several suffixes (key#0..key#9) and pick one at random; add a tiny in-process cache in front for that key; use client-side caching with short TTLs.

Cache penetration

Requests for keys that do not exist (bad IDs, scrapers) always miss and always hit the database. Fixes: negative caching with a short TTL; a Bloom filter of existing IDs in front of the database; input validation.

Avalanche (mass expiry)

Many keys were filled at the same moment (deploy, warm-up) and expire together, so the hit ratio collapses in one second. Fix: add random jitter to TTLs (ttl + random(0, ttl/10)).

Cache node failure

A node holding 1/N of the keys dies; its keys all miss at once and, with naive modulo sharding, every key moves. Fixes: consistent hashing so only 1/N keys move; replicas; fail open in the application.

Memory pressure and large values

A few multi-megabyte values evict thousands of small hot keys. Fixes: cap value size, compress, store large blobs in object storage and cache only the pointer.

TTL jitter and lock-based rebuild in one helper

import json, random, time
import redis

r = redis.Redis()

def get_or_rebuild(key: str, loader, ttl: int = 300, lock_ttl: int = 5):
    cached = r.get(key)
    if cached is not None:
        return json.loads(cached)
    lock_key = f"lock:{key}"
    # SET NX: only one caller gets True and rebuilds; the lock expires on its own if that caller crashes
    if r.set(lock_key, "1", nx=True, ex=lock_ttl):
        try:
            value = loader()
            jitter = random.randint(0, ttl // 10)        # spread expiries: no avalanche
            r.set(key, json.dumps(value), ex=ttl + jitter)
            return value
        finally:
            r.delete(lock_key)
    # somebody else is rebuilding: wait briefly, then retry the cache
    for _ in range(20):
        time.sleep(0.05)
        cached = r.get(key)
        if cached is not None:
            return json.loads(cached)
    return loader()                                       # give up waiting, serve from the source
The lock is a key with NX (set only if absent) and its own expiry, so a crash cannot leave the key locked forever.

Redis in one screen

Redis is the usual distributed cache in interviews because it is more than a key-value store: its data structures let you cache shapes, not just blobs, and do a few things (leaderboards, rate limits) that a plain cache cannot.

StructureCommandsTypical cache use
StringGET SET INCR SETEXserialized objects, counters, rate-limit buckets
HashHGET HSET HGETALLan object with fields you update independently (user profile)
ListLPUSH LRANGE LTRIMa recent-items feed capped at N entries
SetSADD SISMEMBER SINTERmembership checks, tags, 'who liked this'
Sorted setZADD ZRANGE ZRANKleaderboards, time-ordered feeds, sliding-window rate limits
Bitmap / HyperLogLogSETBIT PFADD PFCOUNTdaily-active flags, approximate unique counts
Pick the structure that matches the read you need to make cheap.

Operational facts worth knowing: Redis is single-threaded for command execution (so one slow command such as KEYS * blocks everyone; use SCAN); it persists optionally (RDB snapshots, AOF log) but a cache should be designed to lose it; Redis Cluster shards keys across nodes by hash slot (16,384 slots), so multi-key commands must share a slot (use hash tags {user:42}:…); a typical node serves ~100k simple ops/s.

CDNs: the cache at the edge

A CDN is a cache run by someone else, placed near users. Its hits never reach your data centre at all, which makes it the single biggest latency and cost win for static and semi-static content. You control it with the same HTTP headers browsers obey: Cache-Control: public, max-age=86400, ETag for revalidation, and cache-busting file names (app.3f9a2c.js) so deploys do not need invalidation. For API responses, cache only what is identical for every user (or vary explicitly on a header) and keep TTLs short. The Object storage (S3) & CDNs chapter goes deeper.

flowchart LR
  U1[User in Mumbai] --> E1[Edge: BOM]
  U2[User in Dublin] --> E2[Edge: DUB]
  E1 -- miss --> O[Origin: S3 / app]
  E2 -- miss --> O
  E1 -. hit .-> U1
  E2 -. hit .-> U2
Each edge caches independently; the first user in a region pays the miss, everyone after is served locally.

How to talk about caching in the interview

Caching checklist for a design discussion

A strong answer sounds like: 'Feed reads are 50:1 read-heavy, so I cache the rendered feed per user in Redis (key feed:{user_id}, ~2 KB), cache-aside with a 60 s TTL plus jitter, invalidated when the user posts. Expected hit ratio ~95%, so the database sees ~250 reads/s instead of 5,000. Hot celebrity feeds get per-key locks on rebuild. If Redis is down we fail open to the database with a circuit breaker.'
