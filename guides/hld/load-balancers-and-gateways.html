Load balancers, reverse proxies & API gateways

Every system design has a box labelled 'load balancer'. This chapter shows what that box actually decides: which layer it reads (L4 or L7), how it picks a server (round robin to consistent hashing), how it notices failures and drains traffic for deploys, where TLS ends, and how it differs from a reverse proxy and an API gateway. It finishes with global routing and the question interviewers always ask next: what if the load balancer fails?

After this chapter you can
  • Explain the difference between L4 and L7 balancing and choose one from the requirements (routing, TLS, protocol)
  • Compare round robin, weighted, least-connections, hashing and consistent hashing, and match each to a slow-server, sticky or cache-affinity scenario
  • Describe how health checks, outlier detection and connection draining keep failures and deploys away from users
  • Decide between sticky sessions and stateless services, and where to terminate TLS
  • Tell a reverse proxy, a load balancer and an API gateway apart by responsibility, and trace a request through a gateway
  • Remove the load balancer as a single point of failure and route traffic globally with DNS, GSLB and anycast

What a load balancer does

One server has a ceiling: a few thousand requests a second, one machine's memory, and one machine's chance of failing. A load balancer (LB) sits in front of a pool of interchangeable servers and does three jobs:

  • Spread requests across the pool so no server is overloaded, which is how you scale out.
  • Detect servers that are down or unhealthy and stop sending them traffic, which is how you stay available.
  • Hide the pool behind one stable address, so servers can be added, removed and upgraded without clients noticing.

Balancing happens at several tiers of a typical system, not only at the front door. Step through the usual places.

flowchart LR
  User[Users] --> DNS[DNS and global routing]
  DNS --> L4[L4 balancer]
  L4 --> L7[L7 balancer or gateway]
  L7 --> Svc[Service instances]
  Svc --> Rep[(Database replicas)]
Each arrow can hide a balancing decision. Naming the tier is part of a good answer.

Say which balancer you mean

'Add a load balancer' is vague. 'An L7 balancer in front of the API tier, three instances across zones, least-request balancing, health checks every 5 seconds, and an L4 in front of it for stable IPs' is a design. Say the layer, the algorithm and the failure behaviour.

L4 versus L7

▶ Video lesson: L4 versus L7: what the balancer can see 3:57 · 6 scenes · narrated, pause anytime and explore

The layer numbers describe what the balancer can see. An L4 (transport layer) balancer works on TCP or UDP connections: it sees source and destination IP addresses and ports, picks a backend, and forwards packets or bytes without reading the payload. It works for any protocol (HTTP, gRPC, databases, game traffic) and is very fast. An L7 (application layer) balancer terminates the connection, parses the request (method, host, path, headers, cookies) and routes by content. It costs more CPU per request and understands specific protocols, but it can do things an L4 balancer cannot.

flowchart LR
  C1[Client] --> L4[L4 balancer<br/>sees IP and port]
  L4 --> A1[Server A]
  L4 --> A2[Server B]
  C2[Client] --> L7[L7 balancer<br/>sees the HTTP request]
  L7 -->|"path /api"| P1[API pool]
  L7 -->|"path /static"| P2[Static pool]
  L7 -->|"host video"| P3[Video pool]
Top: an L4 balancer chooses a backend per connection. Bottom: an L7 balancer reads each request and chooses a pool by its content.

Many products do both. What matters is which layer's information your routing decision needs.

How an L4 balancer forwards traffic

NAT mode

The balancer rewrites the destination address of each packet to the chosen backend, remembers the connection in a table, and rewrites the replies on the way back. All traffic in both directions passes through the balancer.

Direct server return (DSR)

The balancer only changes the destination hardware (MAC) address, so the backend, which also holds the virtual IP, replies straight to the client and bypasses the balancer on the way back. Ideal when responses are far larger than requests (downloads, video). It needs the servers on the same layer-2 network, or tunnelling.

Proxy mode

The balancer terminates the client's TCP connection and opens a separate one to the backend. This is how most L7 balancers work, and some L4 ones. It allows connection reuse to backends, but it doubles the number of connections and the balancer sees both directions.

The follow-up to expect

A common production layout is L4 in front of L7: the network balancer gives you static IPs and absorbs connection floods, and a fleet of L7 balancers behind it does content routing. If an interviewer mentions gRPC or HTTP/2, remember that an L4 balancer pins a long-lived connection to one backend, so you need per-request (L7) or client-side balancing to spread it.

Balancing algorithms

▶ Video lesson: Balancing algorithms: which server gets the request? 4:15 · 7 scenes · narrated, pause anytime and explore

The balancer needs a rule for choosing a server. The right rule depends on three things: whether requests cost about the same, whether the servers are equal, and whether the same client should keep reaching the same server.

Start with round robin or least-request. Reach for hashing only when you need affinity, and for consistent hashing when the pool changes.

Watch five algorithms handle the same traffic

Twelve (or sixteen) requests reach three servers. Each server has some number of slots and needs some number of ticks per request; a request that finds every slot busy waits in line, so a slow or small server shows up as growing latency. Compare the scenarios: the same traffic, a different rule, a very different outcome.

Choosing an algorithm in the interview

Round robin is the right default and the right first answer. Mention least-request the moment someone says requests vary in cost or servers can be slow, weights for mixed hardware or canaries, and hashing only when a cache or session needs affinity. Every algorithm that tracks load needs slow start for servers that just joined, or the empty newcomer gets all the traffic.

Hash-based routing has a sharp edge: what happens when the pool changes? Servers fail, autoscaling adds and removes them, and every change alters N. Run both versions below on the same nine keys and the same failure.

A server dies: modulo hashing versus a consistent hash ring

Orange keys had to move because their server died. Red keys moved for no reason. Count them in each scenario.

The same idea at interview depth: with hash % N, going from 3 servers to 2 moves about two thirds of all keys, because the divisor changed for everyone. On a hash ring, only the keys owned by the departed server move, about one third here and 1/N in general. For a cache tier that difference is the gap between a small blip and a stampede on the database. Production implementations place every server at many ring positions ("virtual nodes") so that the load is even and a failed server's keys are shared among all survivors.

Consistent hashing in Python

import hashlib

def h(value: str) -> int:
    """A stable 64-bit hash. Python's built-in hash() is randomised per process, so never use it for routing."""
    return int.from_bytes(hashlib.md5(value.encode()).digest()[:8], "big")

def pick_modulo(key: str, servers: list[str]) -> str:
    return servers[h(key) % len(servers)]
import bisect

class HashRing:
    """Consistent hashing: each server owns many small arcs of the ring (virtual nodes)."""

    def __init__(self, servers=(), vnodes: int = 100):
        self.vnodes = vnodes
        self._points: list[int] = []        # sorted positions on the ring
        self._owner: dict[int, str] = {}    # position -> server
        for s in servers:
            self.add(s)

    def add(self, server: str) -> None:
        for i in range(self.vnodes):
            p = h(f"{server}#{i}")
            bisect.insort(self._points, p)
            self._owner[p] = server

    def remove(self, server: str) -> None:
        for i in range(self.vnodes):
            p = h(f"{server}#{i}")
            self._points.remove(p)
            del self._owner[p]

    def get(self, key: str) -> str:
        # first point clockwise from the key's position, wrapping around the end
        i = bisect.bisect(self._points, h(key)) % len(self._points)
        return self._owner[self._points[i]]
# uses h, pick_modulo and HashRing from the previous tabs
keys = [f"user:{i}" for i in range(10_000)]
servers = ["s1", "s2", "s3"]

before = {k: pick_modulo(k, servers) for k in keys}
moved = sum(before[k] != pick_modulo(k, ["s1", "s3"]) for k in keys)
print(f"modulo: {moved / len(keys):.0%} of keys moved")      # about 67%

ring = HashRing(servers)
before = {k: ring.get(k) for k in keys}
ring.remove("s2")
moved = sum(before[k] != ring.get(k) for k in keys)
print(f"ring:   {moved / len(keys):.0%} of keys moved")      # about a third: only the keys s2 owned

When to bring up consistent hashing

Say 'consistent hashing' when a stateful or cache-like tier is behind the balancer (a cache cluster, a sharded service, sticky routing for WebSockets) and the pool changes over time. Say why: only 1/N of the keys move when a node joins or leaves, so warm caches survive. Add 'virtual nodes' to show you know raw rings are lumpy. Related: Scaling databases: replication, sharding, partitioning and Caching.

Health checks, ejection and draining

▶ Video lesson: Health checks, ejection and draining 3:55 · 6 scenes · narrated, pause anytime and explore

A balancer that cannot tell a dead server from a live one multiplies the failure: it keeps sending a third of the traffic into a black hole. Health checking is the feedback loop that fixes this, and there are two kinds:

  • Active checks: the balancer probes each server on a schedule (an HTTP GET /healthz every few seconds, or a TCP connect for L4). A server becomes unhealthy after N failures in a row (the unhealthy threshold) and healthy again after M passes in a row (the healthy threshold). Detection time is roughly interval × threshold.
  • Passive checks (outlier detection): the balancer watches real traffic and ejects a server for a while after K consecutive errors or timeouts. It reacts within a request or two, but it needs traffic to notice anything.
stateDiagram-v2
  [*] --> Starting
  Starting --> Healthy: passes 2 probes
  Healthy --> Unhealthy: fails 3 probes
  Unhealthy --> Healthy: passes 2 probes
  Healthy --> Draining: deregistered for a deploy
  Draining --> Removed: connections done or timeout
  Removed --> [*]
The lifecycle of one backend as the balancer sees it. The two thresholds differ on purpose so a flapping server does not bounce in and out.

A server fails, or is drained, and traffic shifts

Rows are the clients, the balancer's probes and three servers; one tick is one probe interval (2 s). Compare how many requests fail when detection relies on probes alone, when the balancer also watches live traffic, and when a deploy drains the server first.

Health-check design choices

Shallow versus deep checks

A shallow check ('the process answers') is cheap and safe. A deep check ('the database and cache are reachable') catches more, but a shared dependency outage then marks every server unhealthy at once and turns a partial failure into a total one. Keep balancer checks shallow, or add safeguards.

Panic mode (fail open)

Some balancers ignore health status when too few hosts look healthy (Envoy's panic threshold defaults to 50%), because spreading traffic over everything beats sending it nowhere.

Interval, timeout and thresholds

Faster probes and fewer strikes detect failures sooner but add probe load and risk flapping on a slow GC pause or a brief network blip. Typical values are 5-10 s intervals with 2-3 strikes; pair them with passive checks for speed.

Warm-up and slow start

A freshly started server has cold caches and unoptimised code. Ramping its share of traffic over a minute avoids overloading it, and is essential with least-connections, which would otherwise send the empty newcomer everything.

Retries and timeouts

Balancers can retry a failed request on another server, which hides most single-server failures from users. Retry only idempotent requests, set a retry budget, and keep timeouts short, or retries amplify an overload. See Reliability patterns.

Sticky sessions, stateless services and TLS

A sticky session (session affinity) makes the balancer send one client to the same server every time, usually with a cookie the balancer inserts, or by hashing the client IP. It exists because some applications keep user state in server memory. The alternative is to make servers stateless, so that any server can handle any request.

Pin the client or move the state

Sticky sessions

The balancer pins a client to one server; that server's memory holds the session.

  • Simple for legacy apps, and keeps per-user caches warm.
  • Load becomes uneven: a few heavy users overload one server.
  • If the server dies, its users lose their sessions.
  • Deploys and scale-in must drain carefully; autoscaling is awkward.

Stateless servers

Session state lives outside the app: in a shared store such as Redis, or in a signed token the client carries.

  • Any server can serve any request, so scaling, failover and deploys are trivial.
  • Load spreads evenly.
  • Costs: an extra hop to the session store, or token size and revocation to manage.

Two ways to be stateless

The server signs a small set of claims; any server holding the secret can verify it with no lookup. The trade-off is revocation: a token stays valid until it expires, so keep lifetimes short or keep a denylist. In production use a vetted library (JWT, with a key rotation plan) rather than hand-rolled code; this shows the idea.

import base64, hashlib, hmac, json, time

SECRET = b"rotate-me"        # shared by every app server, loaded from a secrets manager

def issue(user_id: int, ttl: int = 3600) -> str:
    claims = json.dumps({"uid": user_id, "exp": int(time.time()) + ttl}).encode()
    body = base64.urlsafe_b64encode(claims).decode()
    sig = hmac.new(SECRET, body.encode(), hashlib.sha256).hexdigest()
    return f"{body}.{sig}"

def verify(token: str) -> int | None:
    body, _, sig = token.rpartition(".")
    expected = hmac.new(SECRET, body.encode(), hashlib.sha256).hexdigest()
    if not hmac.compare_digest(sig, expected):
        return None
    claims = json.loads(base64.urlsafe_b64decode(body))
    return claims["uid"] if claims["exp"] > time.time() else None

The cookie carries only a random session ID; the data lives in a shared store. Logging a user out or revoking a stolen session is one delete, but the store is now a dependency that must itself be highly available.

import json, secrets
import redis

r = redis.Redis()

def create_session(user_id: int, ttl: int = 3600) -> str:
    sid = secrets.token_urlsafe(32)
    r.set(f"sess:{sid}", json.dumps({"uid": user_id}), ex=ttl)
    return sid                                  # sent to the browser in a cookie

def load_session(sid: str) -> dict | None:
    raw = r.get(f"sess:{sid}")
    return json.loads(raw) if raw else None

def logout(sid: str) -> None:
    r.delete(f"sess:{sid}")                      # revocation is a single DEL

Stickiness is still legitimate in a few cases: WebSockets and other long-lived connections (one connection naturally stays on one server), uploads being assembled in a server's temp directory, and cache affinity, where consistent hashing by user ID keeps each user's data warm on one node. Default to stateless and make stickiness an optimisation, never a correctness requirement.

Where does TLS end?

TLS (the encryption behind HTTPS) can be terminated at the balancer, passed through to the servers, or terminated and then re-established. Step through the three layouts.

flowchart LR
  C1[Client] -->|HTTPS| LB1[Balancer<br/>decrypts] -->|plain HTTP| S1[Server]
  C2[Client] -->|HTTPS| LB2[Balancer<br/>forwards bytes] -->|HTTPS| S2[Server<br/>decrypts]
  C3[Client] -->|HTTPS| LB3[Balancer<br/>decrypts, inspects] -->|new HTTPS| S3[Server<br/>decrypts again]
Terminate (top), pass through (middle), re-encrypt (bottom). The more the balancer can see, the more it can do, and the more of the path is exposed or re-encrypted.

One side effect to plan for: behind a proxy, backends see the balancer's address, not the client's. An L7 balancer adds the original address in an X-Forwarded-For header (and the original scheme in X-Forwarded-Proto; the standard form is the Forwarded header, RFC 7239). An L4 balancer can prepend the client address to the TCP stream with the PROXY protocol. Backends must trust these only when the request comes from the balancer's own addresses, or any client can forge its IP.

Reverse proxy, load balancer and API gateway

These three terms describe overlapping roles, and products such as nginx, Envoy and HAProxy often do all of them. Tell them apart by responsibility:

  • A reverse proxy stands in front of servers and handles requests on their behalf: it hides the origin, terminates TLS, and may cache, compress and rewrite. It can front a single server.
  • A load balancer distributes requests across many interchangeable instances of one service and removes unhealthy ones.
  • An API gateway is the front door for many different services. On top of routing it enforces API-level policy: authentication, rate limits per client, request validation, versioning, protocol translation and response aggregation.

One public request, three internal calls. Everything the services would otherwise repeat (TLS, auth, limits, tracing) happens once at the edge.

What belongs in a gateway: uniform, cross-cutting policy. TLS, token validation, coarse authorisation by scope, rate limits, request size limits, CORS, request IDs and tracing, routing, canary weights. What does not: business logic, per-record authorisation ('does this user own this order?') and data joins. A gateway that accumulates domain logic becomes a bottleneck every team must change. For different client types (mobile, web, partners) a common pattern is one thin gateway per client, a backend for frontend, that aggregates the calls that client needs.

The gateway is a dependency of everything

A gateway sits on every request path, so treat it like production-critical infrastructure: run several instances behind an L4 balancer, keep it stateless (rate-limit counters live in Redis), give calls to backends short timeouts and a circuit breaker (Reliability patterns), and decide up front what happens to rate limiting if Redis is down (fail open or closed).

Load balancer versus gateway, in four sentences

'The load balancer spreads traffic across instances of one service and removes unhealthy ones. The gateway is the single entry point for many services and applies API policy: authentication, rate limits, routing, aggregation. In practice the gateway runs behind an L4 balancer and itself balances to each service, so I'd draw one box for each responsibility even if one product implements both.'

Going global: DNS, GSLB and anycast

One region is one failure domain and one geography. To serve users worldwide, or to survive the loss of a region, traffic has to be steered between regions before it reaches any regional balancer. There are two main mechanisms.

  • DNS-based global server load balancing (GSLB): the authoritative DNS server returns a different IP address depending on where the query comes from, measured latency, region health or configured weights. Route 53's latency, geolocation, failover and weighted policies are examples.
  • Anycast: the same IP prefix is announced from many locations over BGP, and the network delivers each packet to the topologically nearest one. CDNs, public DNS resolvers and global accelerators work this way.

They combine well: anycast to a global edge that terminates the connection near the user, then a private backbone to the nearest healthy region.

Between services inside a region, a third style avoids the central balancer altogether: client-side balancing. Each client (a gRPC library, or a sidecar proxy in a service mesh) learns the list of instances from service discovery and chooses among them itself, usually with least-request or power-of-two-choices. There is no extra network hop and no balancer to fail, at the price of putting the logic and the instance list in every client.

Removing the load balancer as a single point of failure

A load balancer removes the single point of failure of one app server and creates one of its own, so 'what if the load balancer dies?' is a standard follow-up. There are three standard answers:

  • Active-passive pair on a virtual IP. Two balancers share a floating address (VRRP, for example with keepalived). The active one owns it; the standby watches heartbeats and takes the address over within seconds if the active one stops. Simple, but the standby is idle, and connections tracked only in the dead balancer's memory are lost unless state is synchronised.
  • Active-active. Several balancers all take traffic, spread by DNS (multiple A records), by the network (ECMP routing, often with anycast), or by an L4 tier in front. Capacity scales and nothing idles, but any node must send a given flow to the same backend, typically with consistent hashing.
  • A managed, multi-zone balancer. In the cloud the provider runs balancer nodes in every zone you enable behind one DNS name, scales them, and replaces failed ones. You still choose at least two zones and make sure the targets are spread across them.

Load-balancer checklist for a design discussion

A model answer to 'where does the load balancer fit and what if it fails?'

'Clients resolve our hostname through latency-based DNS to the nearest region. In each region an L4 balancer fronts a fleet of L7 balancers across three zones; they terminate TLS and route by path to the API and static pools. Within a pool I'd use least-request, with active health checks every 5 seconds and passive ejection after two errors, so detection is a few seconds; deploys drain connections for 30 seconds. App servers are stateless, with sessions in Redis, so no stickiness. The balancer tier is redundant across zones, so no single failure takes the front door down.'
