Message queues & streaming (Kafka)

A queue between two services turns a traffic spike into a backlog instead of an outage. This chapter shows why to decouple, how point-to-point queues, pub/sub and Kafka-style logs differ, how partitions and consumer groups give you order and parallelism, what 'at-least-once' means for the code you write, and how retries, dead-letter queues and backpressure keep a pipeline healthy, so you can choose and defend a messaging design in an interview.

After this chapter you can
  • Explain what a queue buys you (burst absorption, failure isolation, independent scaling) and what it costs
  • Choose between a point-to-point queue, pub/sub and a log-based stream for a given requirement
  • Describe topics, partitions, offsets and consumer groups, and why order is guaranteed only within a partition
  • Compare at-most-once, at-least-once and exactly-once-ish delivery, and write an idempotent consumer
  • Design retries, a dead-letter queue and backpressure, and size a consumer pool from rates and processing time
  • Name the situations where a queue is the wrong tool

Why put a queue in the middle?

▶ Video lesson: Why put a queue in the middle? 4:00 · 7 scenes · narrated, pause anytime and explore

Take an order service that, once an order is saved, must send an email, reserve stock and tell analytics. Calling those three services inline ties checkout to the slowest and least reliable of them: a slow email provider means a slow checkout, an inventory outage means failed orders.

A message queue is a durable buffer between a producer (the code that has work) and a consumer (the code that does it). The producer hands over a message and returns as soon as the broker has stored it. That one step changes three things:

  • Bursts become backlog. Traffic is spiky and consumer capacity is flat. The queue holds the difference (its depth) instead of turning it into errors.
  • Failures stay local. If the consumer is down for ten minutes, messages wait. Customers see "order received" and the work completes later.
  • Each side scales on its own. Add consumers when the backlog grows. The producer neither knows nor cares.

The price: the response no longer contains the result, the system becomes eventually consistent (the email goes out seconds later, not before the page loads), and you now run and monitor a broker.

Burst, outage, and a queue in the middle

The email service handles 5 messages per second. Compare what the customer sees (the ok and failed counts under the API box) with what happens inside. In the queue scenarios watch the depth rise during the burst, and fall once arrivals drop below capacity.

A queue converts overload into latency, and latency has to be bounded. If arrivals exceed capacity for long enough, the backlog grows without limit and every message gets slower. The backpressure section shows how to notice that and cap it.

Three models: queue, pub/sub, log

'Message queue' covers three different designs. They differ in what happens to a message after someone reads it and in how many readers see it. Interviews reward being precise about which one you mean.

ModelWho gets a messageAfter it is readReplay?Typical products
Point-to-point queue (work queue)one consumer; consumers competedeleted on acknoSQS, RabbitMQ queues, Celery
Pub/subevery subscriber, each gets its own copyeach copy deleted on ackno (unless a subscriber stores it)SNS + SQS, RabbitMQ fanout exchange, Google Pub/Sub
Log-based streamevery consumer group, each at its own offsetkept until retention expiresyes: move the offset backKafka, Kinesis Data Streams, Redpanda
The decisive column is 'after it is read': a queue forgets, a log remembers.

Point-to-point is the work-queue model: many producers, many competing consumers, each job done once. Use it for background jobs (resize this image, send this email).

flowchart LR
  P1[Producer A] --> Q{{Order queue}}
  P2[Producer B] --> Q
  Q --> C1[Consumer 1]
  Q --> C2[Consumer 2]
  Q --> C3[Consumer 3]
Competing consumers: add consumers to drain the queue faster. Ordering across consumers is not preserved.

Pub/sub answers a different question: several different services each need to react to the same event. The publisher does not know its subscribers, and adding one must not change the publisher.

flowchart LR
  PUB[Order service] --> T{{Topic: order placed}}
  T --> S1[[Email queue]]
  T --> S2[[Inventory queue]]
  T --> S3[[Analytics queue]]
  S1 --> W1[Email service]
  S2 --> W2[Inventory service]
  S3 --> W3[Analytics job]
One event, three independent copies. A slow subscriber only backs up its own queue.

A log-based stream keeps the messages. Consumers do not take messages out; they remember a position (an offset) in an append-only log. That one difference gives you replay, many independent readers, and ordering you can reason about.

flowchart LR
  PR[Producer] -->|append| LOG[Partition log<br/>offsets 0 to 9]
  LOG -->|offset 8| G1[Group: billing]
  LOG -->|offset 4| G2[Group: analytics]
  LOG -->|offset 0| G3[Group: new search index]
Three groups read the same log at three different positions, without affecting each other.

Kafka: topics, partitions, offsets, consumer groups

▶ Video lesson: Kafka: partitions, offsets and consumer groups 4:28 · 7 scenes · narrated, pause anytime and explore

Kafka is the log-based model at scale. Five terms carry almost every interview question:

  • A topic is a named stream, for example orders.
  • A topic is split into partitions. Each partition is an ordered, append-only log, and a message's position in it is its offset (0, 1, 2, ...). Offsets are per partition, not per topic.
  • The producer chooses the partition, normally hash(key) mod number_of_partitions, so every message with the same key (say a user id) lands in the same partition. Without a key, messages are spread across partitions.
  • A consumer group is a set of consumers sharing a group id. Kafka gives each partition to exactly one consumer in the group, so a partition is always processed in order by one consumer at a time. Different groups are independent and each keeps its own offsets.
  • A consumer commits its offset (stored in an internal topic) to say "everything before this is handled". After a crash or a rebalance, the next owner of the partition resumes from the committed offset.

Durability comes from replication: each partition has a leader and followers on other brokers (replication factor 3 is typical). With producer acks=all and min.insync.replicas=2, an acknowledged write survives the loss of one broker.

Partitions, offsets and a rebalance

Three partitions, one consumer group. Green cells are processed and committed; amber cells are processed but not yet committed. Use the scenario menu to add a consumer, crash one, or add more consumers than partitions.

Order is guaranteed within a partition only. If one user's events must be processed in order, give them the same key. Choose the key from the ordering you need, then check that it spreads load: a single very hot key means one hot partition and one overloaded consumer.

Delivery guarantees: what the ack really means

▶ Video lesson: Delivery guarantees: what the ack really means 4:16 · 7 scenes · narrated, pause anytime and explore

A broker and a consumer are two machines, and an acknowledgement can be lost on either hop. So every system makes you choose which failure you prefer:

  • At-most-once. Ack (or commit) first, then process. A crash after the ack loses the message. Fine for metrics samples and debug logs.
  • At-least-once. Process first, then ack. A crash before the ack means redelivery, so the handler can run twice for one message. This is the default for SQS Standard and for Kafka consumers that commit after processing.
  • Exactly-once. Each message's effect happens once. No network offers exactly-once delivery. What systems offer is at-least-once delivery plus de-duplication: Kafka's idempotent producer and transactions (exactly-once for read-process-write inside Kafka), SQS FIFO's five-minute deduplication window, and, for effects outside the broker, an idempotent consumer.

  participant P as Producer
  participant B as Broker
  participant C as Consumer

  B->>C: deliver m1
  C->>D: charge the card
  Note over C: crashes before acking
  B->>C: redeliver m1 (no ack in time)
  C->>D: charge the card again
  C-->>B: ack
At-least-once in one picture: the broker cannot tell 'slow' from 'dead', so it delivers again.

Three ways a consumer can crash

Same message, same crash, three consumer designs. Compare the rows in the database at the end.

An idempotent consumer: the dedup check and the effect share one transaction

import sqlite3

db = sqlite3.connect("payments.db")
db.executescript('''
    CREATE TABLE IF NOT EXISTS processed (message_id TEXT PRIMARY KEY);
    CREATE TABLE IF NOT EXISTS charges (order_id TEXT, cents INTEGER);
''')

def handle(message: dict) -> None:
    try:
        with db:                                    # one transaction: both inserts commit, or neither does
            db.execute("INSERT INTO processed VALUES (?)", (message["id"],))   # unique key: duplicates raise
            db.execute("INSERT INTO charges VALUES (?, ?)", (message["order_id"], message["cents"]))
    except sqlite3.IntegrityError:
        return                                      # already handled: skip the effect, then ack as usual
If the effect is an external API call instead of a row, pass the message id to that API as its idempotency key so the provider does the de-duplication.

Interviewer: 'Can you get exactly-once?' A strong answer: 'Not literally, because an acknowledgement can always be lost. I use at-least-once delivery and make the consumer idempotent: a unique message id checked in the same transaction as the side effect, or an idempotency key sent to the payment API. Kafka transactions give exactly-once for read-process-write inside Kafka, but external effects still need idempotency.'

When processing fails: retries, dead letters, backpressure

Handlers fail. What matters is what the system does next.

Retries. Most failures are transient: a timeout, a locked row, a downstream 503. Retry them, but not immediately and not all at once. Wait exponentially longer each time (1 s, 2 s, 4 s, 8 s...) and add random jitter. Without jitter a thousand failed messages retry in the same instant and knock the service over again.

Poison messages. Some failures are permanent: malformed JSON, a reference to a deleted row, a bug in the handler. Retrying never helps. In a queue that redelivers on failure, such a message loops forever and burns capacity; in an ordered partition it also blocks everything behind it. A dead-letter queue (DLQ) is a side queue that receives a message after N failed attempts, together with the error. It keeps the main flow moving, preserves the evidence, and gives you something to alert on and to redrive once the bug is fixed.

stateDiagram-v2
  [*] --> Visible: send
  Visible --> InFlight: receive
  InFlight --> Deleted: ack in time
  InFlight --> Visible: timeout or nack
  Visible --> DeadLetter: receives exceed max
  Deleted --> [*]
  DeadLetter --> [*]
An SQS-style message lifecycle. The receive counter is what turns an endless retry loop into a dead letter.

Kafka has no built-in dead-letter queue. The usual pattern is for the consumer to publish the failed record, with the error in a header, to a topic such as orders.dlq, commit past it, and move on. A retry topic with a delay in front of the DLQ gives you backoff without blocking the partition. The first decision, in any system, is whether the failure is worth retrying at all.

flowchart TD
  F[Handler raised an error] --> T{Transient?<br/>timeout, 503, lock}
  T -->|yes| R{Attempts left?}
  R -->|yes| B[Retry later<br/>backoff plus jitter]
  R -->|no| D[Dead-letter queue]
  T -->|no| D
  D --> A[Alert and inspect]
  A --> X{Bug or bad data?}
  X -->|code bug| FIX[Deploy fix, then redrive]
  X -->|bad data| DROP[Repair or discard]
Classify the failure first. Retrying a permanent failure only delays the DLQ.

Backpressure is everything that stops a fast producer from drowning a slow consumer. A queue absorbs the first minutes of imbalance. After that something has to push back:

  • Watch the right number. Queue depth alone is ambiguous. The age of the oldest message (SQS) or the consumer lag (Kafka: end offset minus committed offset) tells you how late you are.
  • Scale consumers on lag, in Kafka up to the partition count.
  • Bound the queue: a maximum length, a retention limit, or a TTL on messages whose answer will be stale by the time you process them.
  • Slow or shed the producers: block or reject publishes (HTTP 429 or 503), apply per-tenant quotas, drop low-priority work first.
  • Limit what a consumer holds. RabbitMQ prefetch and Kafka max.poll.records cap how much a consumer pulls before it must finish.

Sizing a consumer pool, and the time to catch up

Workers in use = arrival rate × time per message (Little's law). Change the outage length to see why a short outage can mean a long catch-up: the backlog drains only at the spare capacity. If capacity is not above the arrival rate, the drain time explodes: the backlog never clears.

Ordering vs parallelism, retention and replay

Order and parallelism pull in opposite directions: the more strictly you order, the fewer things can run at once.

Ordering you ask forHow you get itParallelism you keepTypical use
Noneany worker takes any message (SQS Standard, competing consumers)as many workers as you can runindependent jobs: resize an image, send an email
Per keykey to partition (Kafka) or message group id (SQS FIFO)up to the number of partitions or groupsthe events of one user, account or order
Globalone partition and one consumernone: the throughput of one consumerrare; usually a sign to add sequence numbers instead
Ask for the weakest ordering your correctness argument allows.

Three traps live here:

  • Retries reorder. If message 5 fails and is retried after 6 and 7 have succeeded, effects happen out of order. Either block the partition until 5 succeeds (head-of-line blocking), or make handlers tolerant: carry a version or sequence number and ignore an update older than what is stored.
  • Hot keys. All events for one key go to one partition, so one very active account can overload a consumer while the others idle. Salting the key (user-42#3) spreads the load but gives up strict per-key order.
  • Changing the partition count. hash(key) mod N changes when N changes. After adding partitions, the same key can land in a different partition while its older messages still wait in the old one, so per-key order breaks across the change. Plan headroom up front (partitions can be added, never removed) but do not pick thousands: each partition costs file handles, replication traffic and rebalance time.

Retention and replay. A classic queue deletes a message on ack. A log keeps messages for a retention period (seven days by default in Kafka) or up to a size, or indefinitely on a compacted topic that keeps the latest value per key. Replaying means moving a group's offset back. Use it to:

  • fix a bug and reprocess the last two days of events,
  • bring up a new service or search index from offset 0,
  • audit exactly what was sent.

Replay re-triggers side effects, so consumers must be idempotent (again). Retention also has a compliance edge: data you keep for replay is data you must be able to delete when a user asks.

Kafka questions interviewers like

A consumer is slow. What happens?

If it does not call poll() again within max.poll.interval.ms (five minutes by default), the group assumes it is stuck and rebalances: its partitions move, and its late commit is rejected, so the batch is processed twice. Fixes: lower max.poll.records, move slow work off the polling thread, or raise the interval deliberately.

How does Kafka avoid losing acknowledged data?

Each partition is replicated (replication factor 3 is typical). With producer acks=all the leader acknowledges only after all in-sync replicas have the record, and min.insync.replicas=2 makes the write fail rather than succeed with a single copy. Unclean leader election, which could promote an out-of-date replica, is off by default.

Why is Kafka fast?

It appends sequentially to disk, leans on the OS page cache, batches and compresses records, and serves consumers with zero-copy transfers (sendfile). Partitions then spread that work across brokers and consumers.

What is log compaction?

A retention mode that keeps only the latest record for each key (a record with a null value, a tombstone, deletes the key). The topic becomes a changelog of current state: useful for rebuilding a cache or table from scratch.

How do you get exactly-once in Kafka?

The idempotent producer (sequence numbers per producer and partition) removes duplicates caused by producer retries. Transactions write output records and the consumer's offsets atomically, and consumers read with isolation.level=read_committed. This covers read-process-write inside Kafka. A side effect outside Kafka still needs an idempotent consumer.

Can I add partitions to a live topic?

Yes, but never remove them. New partitions change where keys map, so per-key order can break across the change, and existing data is not redistributed.

The same consumer in each system

Long polling avoids empty responses. The message is deleted only after the handler returns; if it raises, the message reappears after the visibility timeout.

import boto3

sqs = boto3.client("sqs")
QUEUE_URL = "https://sqs.eu-west-1.amazonaws.com/123456789012/orders"

while True:
    resp = sqs.receive_message(QueueUrl=QUEUE_URL, MaxNumberOfMessages=10,
                               WaitTimeSeconds=20, VisibilityTimeout=60)
    for msg in resp.get("Messages", []):
        handle(msg["Body"])                       # if this raises, the message comes back after 60 s
        sqs.delete_message(QueueUrl=QUEUE_URL, ReceiptHandle=msg["ReceiptHandle"])

Auto-commit is off: the offset is committed only after the handler succeeds, which is at-least-once. Real code commits per batch, not per message.

from confluent_kafka import Consumer

consumer = Consumer({
    "bootstrap.servers": "broker:9092",
    "group.id": "billing",
    "enable.auto.commit": False,            # we decide when an offset counts as done
    "auto.offset.reset": "earliest",
})
consumer.subscribe(["orders"])

while True:
    msg = consumer.poll(1.0)
    if msg is None:
        continue
    if msg.error():
        raise RuntimeError(msg.error())
    handle(msg.key(), msg.value())
    consumer.commit(message=msg, asynchronous=False)    # commits offset + 1 after success

The key picks the partition, so all events for one order stay in order. Idempotence and acks=all stop producer retries from losing or duplicating records.

from confluent_kafka import Producer

producer = Producer({"bootstrap.servers": "broker:9092", "enable.idempotence": True, "acks": "all"})

def on_delivery(err, msg):
    if err is not None:
        log.error("publish failed: %s", err)    # retry, or park it in an outbox

def publish_order(order_id: str, payload: bytes) -> None:
    producer.produce("orders", key=order_id, value=payload, on_delivery=on_delivery)
    producer.poll(0)                            # serve delivery callbacks

# on shutdown: producer.flush()

prefetch_count caps unacknowledged messages per consumer, which is backpressure at the consumer.

import pika

conn = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
ch = conn.channel()
ch.queue_declare(queue="orders", durable=True)
ch.basic_qos(prefetch_count=10)                 # at most 10 unacked messages per consumer

def on_message(channel, method, properties, body):
    handle(body)
    channel.basic_ack(delivery_tag=method.delivery_tag)

ch.basic_consume(queue="orders", on_message_callback=on_message)
ch.start_consuming()

When not to use a queue, and how to say all this

A queue decouples in time. Skip it when you cannot afford that:

  • The caller needs the answer now. A page that shows the result of the work should call the service synchronously. Request/reply over queues is possible and almost always worse than a plain RPC.
  • Low volume and a reliable callee. One service calling another a few times a minute needs a timeout and a retry, not a broker.
  • You want a database. Queues do not support queries, random access or updates. Do not park data in a queue to look it up later.
  • You need one transaction across a database write and a publish. "Save the order, then publish the event" is a dual write: a crash between the two leaves an order with no event. Use the transactional outbox.
  • Strict global order at high throughput. Settle for per-key order, or accept a one-consumer ceiling.

Publishing reliably

Dual write

Two systems, two commits, no atomicity.

def place_order(order):
    db.insert_order(order)                      # 1. commits
    broker.publish("order.placed", order)       # 2. a crash right here: order saved, event lost

Transactional outbox

One commit. A relay does the publishing afterwards.

def place_order(order):
    with db.transaction():                      # one atomic commit
        db.insert_order(order)
        db.insert_outbox("order.placed", order) # the event is just another row

# A relay (a poller, or CDC such as Debezium) publishes unsent outbox rows, then marks them sent.
# After a crash it may publish a row twice, so consumers stay idempotent.

Messaging checklist for a design discussion

A strong answer to 'order placed, fan out to email, inventory and analytics': 'I publish an order.placed event through a transactional outbox to a Kafka topic keyed by order id, which gives per-order ordering and parallelism across orders. Email, inventory and analytics are separate consumer groups, so each scales and fails on its own. Delivery is at-least-once and handlers are idempotent on event id. Failures retry with backoff and jitter, then go to a dead-letter topic, and I alert on consumer lag and DLQ depth. If all I needed was "send this email later", I would use SQS and skip the cluster.'
