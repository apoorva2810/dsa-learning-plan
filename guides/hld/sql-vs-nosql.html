Databases: SQL vs NoSQL

Choosing a database is choosing which questions will be cheap. This chapter covers the relational model and normalisation, ACID and indexes in one screen, the four NoSQL families and their data models, why access patterns come before schemas in NoSQL design, how far a relational database really scales, and a decision flowchart and comparison table you can use in any design interview.

  • Describe ACID and what an index buys and costs, and link them to the database chapters
  • Describe the key-value, document, wide-column and graph models and the workload each fits

  • Walk through a decision flowchart and defend a polyglot design with one system of record

The relational model and normalisation

▶ Video lesson: Normalisation: store each fact once 3:20 · 6 scenes · narrated, pause anytime and explore

A relational database stores data in tables of rows and columns. A primary key identifies a row. A foreign key is a column that points at another table's primary key, and the database can enforce that the pointer is valid. You query with SQL, and joins combine tables at read time, so a question you have not thought of yet is usually just another query.

The design discipline is normalisation: store each fact once. See what happens when you do not:

order_idcustomer_namecustomer_emailproduct_titleproduct_priceqty
1001Annann@example.comKeyboard49.001
1001Annann@example.comMouse19.001
1007Annann@example.comMouse19.001

Ann's email is stored three times and the mouse's price twice. That produces three classic anomalies:

  • Update: change Ann's email in two of the three rows and the data disagrees with itself.
  • Insert: you cannot record a new customer, or a product nobody has bought yet, without inventing an order.
  • Delete: delete Ann's only order and you lose her details, and the product's price, with it.

The normal forms are rules that remove these. In one line, first to third normal form: every column holds one atomic value, and every non-key column depends on the key, the whole key, and nothing but the key. The fix is to split the table so each fact lives in one place and rows are linked by keys:

ACID and indexes in one screen

What the relational engines give you for free, in four letters (the full treatment is in ACID & transactions):

  • Atomicity: a transaction is all or nothing. The debit and the credit both happen, or a rollback undoes both.
  • Consistency: a transaction takes the database from one valid state to another. The database enforces the constraints you declared (keys, UNIQUE, CHECK); anything beyond that is your application's job.
  • Isolation: concurrent transactions behave as if they ran one after another, to a degree you choose. Stronger isolation prevents more anomalies and costs more concurrency (PostgreSQL defaults to read committed, MySQL's InnoDB to repeatable read).
  • Durability: once COMMIT returns, the data survives a crash, because the change reached a write-ahead log on disk first.

A transfer as one transaction (PostgreSQL, psycopg 3)

import psycopg

def transfer(conn: psycopg.Connection, src: int, dst: int, cents: int) -> None:
    with conn.transaction():                            # BEGIN ... COMMIT, or ROLLBACK if anything raises
        row = conn.execute("SELECT balance FROM accounts WHERE id = %s FOR UPDATE", (src,)).fetchone()
        if row[0] < cents:
            raise ValueError("insufficient funds")      # the exception rolls everything back: atomicity
        conn.execute("UPDATE accounts SET balance = balance - %s WHERE id = %s", (cents, src))
        conn.execute("UPDATE accounts SET balance = balance + %s WHERE id = %s", (cents, dst))
FOR UPDATE locks the source row so two concurrent transfers cannot both pass the balance check.

Most NoSQL stores guarantee atomicity only for a single item or partition and give weaker isolation by default. Several now offer multi-item transactions (MongoDB, DynamoDB), with limits and a performance cost.

Indexes, briefly (details in Indexing & query performance): an index is a separate sorted structure, a B+ tree in most relational engines, that maps column values to rows. It turns a full table scan into a logarithmic lookup. The trade is that every write must update every index, and indexes take space. Index the columns you filter, join and sort on, mind the column order of a composite index (a lookup can use any left prefix of it), and check plans with EXPLAIN.

CREATE INDEX idx_orders_customer_date ON orders (customer_id, placed_on DESC);
-- serves: WHERE customer_id = 7 ORDER BY placed_on DESC LIMIT 10

The NoSQL families

'NoSQL' is a label for stores that gave up some relational promise (a fixed schema, joins, multi-row transactions) in exchange for something else: horizontal scale, a flexible data shape, or very low latency for a narrow set of operations. The four families differ by data model, so choose by the shape of your access patterns.

Key-value (Redis, DynamoDB, Memcached, etcd)

A giant hash map: get(key), put(key, value). The store never looks inside the value, so the only query is by key. That restriction is what makes it fast and trivially shardable: hash the key, pick a node. Typical uses: sessions, carts, feature flags, rate-limit counters.

flowchart LR
  K1[session:9f3a] --> V1[cart and login blob]
  K2[user:42:profile] --> V2[JSON profile blob]
  K3[rate:ip:203.0.113.7] --> V3[counter 17]
Lookup by exact key only. The value is opaque to the store, so there is no 'find all carts over 50 dollars'.

Document (MongoDB, Couchbase, Firestore)

Self-contained JSON-like documents with nested objects and arrays, grouped in collections whose documents may differ in shape. You can index and query inside a document (items.sku). The design idea is to store together what is read together, so one read returns a whole aggregate such as an order with its items, at the price of duplicating some facts. Typical uses: catalogues, content, user profiles, event payloads.

flowchart TD
  D[order 1001] --> C[customer: Ann]
  D --> I[items array]
  I --> I1[Keyboard x1]
  I --> I2[Mouse x1]
  D --> S[status: shipped]
One read returns the whole aggregate, so no join is needed. The customer's name is a copy.

Wide-column (Cassandra, ScyllaDB, Bigtable, HBase)

Rows are grouped by a partition key, which decides which node stores them. Inside a partition, rows are kept sorted by clustering columns. Writes are very fast (append to a commit log and an in-memory table, an LSM design). A query must supply the partition key, and range queries follow the clustering order. There are no joins and little ad-hoc querying, so you model one table per query. Typical uses: time series, message history, activity feeds at huge write volume.

flowchart LR
  Q[Query: user 42,<br/>latest messages] -->|hash of user 42| P1
  Q -.->|never asked| P2
  subgraph N1[Node 1]
    P1[Partition user 42<br/>10:01 hi<br/>10:02 ok<br/>10:05 bye]
  end
  subgraph N2[Node 2]
    P2[Partition user 77<br/>09:58 yo<br/>10:03 ok]
  end
The partition key sends the query to one node; the clustering order (time) makes 'latest N' a short sequential read.

Graph (Neo4j, Amazon Neptune)

Nodes and edges, both with properties, and an engine that stores adjacency so that walking an edge is a pointer hop, not a join. Queries such as 'friends of friends who liked this' or 'shortest path' stay fast as the depth grows, where a relational self-join explodes. Typical uses: social graphs, fraud rings, recommendations, permission models.

flowchart LR
  Ann((Ann)) -->|FOLLOWS| Bob((Bob))
  Bob -->|FOLLOWS| Cara((Cara))
  Ann -->|LIKES| Post1[Post 1]
  Cara -->|WROTE| Post1
The relationships are first-class data. 'Whose posts does Ann's network like?' is a short walk over edges.

Model for the queries: denormalisation and single-table design

▶ Video lesson: Model for the queries: who pays? 4:14 · 8 scenes · narrated, pause anytime and explore

Relational design starts from the entities, normalises them, and answers any question later with a join. NoSQL design starts from the queries: list the access patterns (get an order with its items; list a customer's recent orders), then shape the data so that each one is a single cheap read. That usually means duplicating facts. This is denormalisation, and the question to ask is always who pays: reads get cheaper and simpler, writes get more expensive, and copies can drift apart.

DynamoDB's single-table design is the extreme form. Items of different types share a partition key so they come back together in one Query, and the sort key groups and orders them inside the partition:

PK (partition key)SK (sort key)Attributes
CUSTOMER#7PROFILEname = Ann, email = ann@example.com
CUSTOMER#7ORDER#2026-10-01#1001total = 6800, status = shipped
CUSTOMER#7ORDER#2026-10-12#1007total = 1900, status = placed
ORDER#1001ITEM#P1title = Keyboard, qty = 1, unit_price = 4900
ORDER#1001ITEM#P2title = Mouse, qty = 1, unit_price = 1900
'A customer's latest orders' is one Query on pk = CUSTOMER#7 with sk beginning ORDER#, newest first. 'An order's items' is one Query on pk = ORDER#1001. Both are single-partition reads.

Query, Scan, and a new index on a partitioned table

The partition key decides which node holds an item, and the sort key orders items inside it. Compare what a key-based Query touches with what a Scan touches, then see what a brand-new access pattern costs. Cells are in sort-key order; amber is the item collection the partition key locates, green the items read and returned, purple the items scanned.

The same order, modelled both ways

Normalised (SQL)

SELECT o.id, c.name, p.title, i.qty, i.unit_price_cents
FROM orders o
JOIN customers c   ON c.id = o.customer_id
JOIN order_items i ON i.order_id = o.id
JOIN products p    ON p.id = i.product_id
WHERE o.id = 1001;
  • Each fact is stored once; renaming a product is one row
  • A new question is just a new query
  • The join work happens at read time

Denormalised (document or single table)

{
  "pk": "ORDER#1001",
  "customer": {"id": 7, "name": "Ann"},
  "items": [
    {"sku": "P1", "title": "Keyboard", "qty": 1, "unit_price": 4900},
    {"sku": "P2", "title": "Mouse", "qty": 1, "unit_price": 1900}
  ],
  "total": 6800
}
  • One read returns the page, and the key shards cleanly
  • Titles and names are copies: renaming means rewriting many documents, or accepting staleness
  • A new question usually needs a new copy or index

Fetching the order page

SELECT o.id, c.name, p.title, i.qty, i.unit_price_cents

One round trip; the customer snapshot and the items are inside the document.

from pymongo import MongoClient

orders = MongoClient()["shop"]["orders"]
order = orders.find_one({"_id": 1001})            # customer and items come back embedded

One Query on the partition key returns every item of the collection.

import boto3
from boto3.dynamodb.conditions import Key

table = boto3.resource("dynamodb").Table("shop")
items = table.query(KeyConditionExpression=Key("pk").eq("ORDER#1001"))["Items"]   # header and ITEM# rows

def recent_orders(customer_id: int, limit: int = 10) -> list[dict]:
    resp = table.query(
        KeyConditionExpression=Key("pk").eq(f"CUSTOMER#{customer_id}") & Key("sk").begins_with("ORDER#"),
        ScanIndexForward=False,                   # newest first: the date is inside the sort key
        Limit=limit,
    )
    return resp["Items"]

A join, application-side joins, a denormalised read, and the write bill

The order page needs data from four logical tables. The label under the app server counts network round trips; the label under the database counts rows touched. The last scenario shows what denormalising costs when a shared fact changes.

Snapshots are the one place where denormalising is simply correct. An order must keep the price, name and address as they were at purchase, whatever the catalogue does later. Copy on purpose when the fact is meant to be frozen; be wary when the copy is supposed to stay live.

You can scale SQL further than you think

"NoSQL because it scales" is the most common weak answer in a design interview. Scaling is a ladder, and a relational database has many rungs before sharding:

  1. Fix the queries and indexes. Most slow databases are missing an index or issuing N+1 queries.
  2. Cache hot reads (Redis) in front of it.
  3. Add read replicas for read-heavy traffic. They lag the primary slightly, so read-your-own-writes needs care.
  4. Buy a bigger machine. Dozens of cores, hundreds of GB of RAM and fast NVMe are one click away. Vertical scaling is unfashionable and very effective.
  5. Partition big tables by time or range, so queries and maintenance touch less data.
  6. Shard by a key (Citus, Vitess, or in the application) when one primary's writes or storage genuinely run out.

A well-tuned single PostgreSQL or MySQL primary routinely serves thousands to tens of thousands of simple transactions per second and holds multiple terabytes. Treat that as an order of magnitude: it depends on row size, indexes, hardware and the workload. So do the arithmetic before leaving it:

Does it fit on one database node?

Defaults describe a large consumer product: 50 million users placing 10 orders a year, kept for 5 years. Change them to yours. Compare the write rate with the thousands per second a single primary handles, and the size with what fits on one machine.

Signals that you have genuinely outgrown one primary: sustained write rates beyond what a single node can commit (tens of thousands per second), a hot working set that no longer fits in RAM, a need for active-active writes in several regions, or key-based access at a fan-out that only a partitioned store serves. Without one of those, you are paying for distribution you do not need: no cross-partition joins, weaker transactions, and a data model frozen around today's queries.

The strong answer is an estimate, not a product name: 'Peak is about 150 writes per second and the table reaches roughly 2.5 TB in five years. That fits a PostgreSQL primary with two read replicas and a cache. I would shard, or move one workload to a partitioned store, only when the numbers say so.' Interviewers are listening for whether you reach for distribution by reflex.

Polyglot persistence and the databases you will be asked about

Real systems use several stores, each for the workload it suits: PostgreSQL for orders, Redis for sessions and caching, Elasticsearch for search, a warehouse for analytics. The rule that keeps this sane is one system of record; every other store is a derived view that can be rebuilt from it. Feed the derived stores from a change stream (change data capture from the database log, or a transactional outbox, see Message queues & streaming (Kafka)) and not by having the application write to each store in turn: a crash between two writes leaves them disagreeing.

flowchart LR
  APP[App servers] --> PG[(Postgres<br/>system of record)]
  APP --> RD[(Redis<br/>cache and sessions)]
  PG --> CDC[Change stream<br/>CDC or outbox]
  CDC --> ES[(Elasticsearch<br/>search index)]
  CDC --> WH[(Warehouse<br/>analytics)]
  APP --> ES
Writes go to one place. Everything else is fed from the change stream and can be rebuilt.

Every extra datastore is another thing to operate, secure, back up, upgrade and keep consistent. Add one for a workload the primary cannot serve, not for novelty, and never let a derived store become the only copy of anything.

How to say it in an interview

Traps interviewers listen for

Choosing NoSQL for the scale you hope to have

Do the estimate. Premature distribution costs you joins, transactions and flexibility today for headroom you may never need.

Using MongoDB like a relational database

Normalising everything and joining with $lookup gives you the weaknesses of both worlds. If the data really is relational, use a relational database.

Modelling DynamoDB or Cassandra before listing the access patterns

The table design is the set of queries it can answer. A pattern you forgot later means a new index, a new table, or a scan.

Hot partition keys

A low-cardinality or time-based key (the current date, a status flag) concentrates writes on one partition. Use a high-cardinality key, or add a suffix to spread a hot key at the cost of a fan-out read.

Treating a cache or search index as the system of record

Redis and Elasticsearch can lose or lag. Keep a durable source of truth they can be rebuilt from.

Forgetting stale reads

Read replicas and eventually consistent NoSQL reads can return old data. Say where that is acceptable (a feed) and where it is not (a balance just after a transfer).

Database-choice checklist for a design discussion

A strong answer to 'which database for an order service?': 'PostgreSQL. Orders, customers and payments need transactions, foreign keys and ad-hoc reporting, and the numbers (a few hundred writes per second at peak, a few TB in five years) fit one primary with two read replicas and a Redis cache. Product search goes to Elasticsearch, fed from the change stream, so it is a rebuildable view. If the activity-feed write rate later outgrows a primary, I would move just that workload to a partitioned store such as Cassandra or DynamoDB, modelled from its access patterns: by user, newest first.'
