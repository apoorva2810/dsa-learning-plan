Scaling databases: replication, sharding, partitioning

A single database server runs out of read capacity, write capacity, storage or availability, and each shortage has a different fix. This chapter shows how replication copies data for reads and failover and what replication lag does to users, how leader-follower, multi-leader and leaderless replication handle writes, how failover goes wrong (split brain) and how fencing prevents it, how range, hash and directory sharding split data, why consistent hashing keeps rebalancing cheap, what cross-shard queries and transactions cost, and how to argue 'not yet' when an interviewer pushes you to shard.

After this chapter you can
  • Say which bottleneck (reads, writes, storage, availability) each technique fixes, and scale up before scaling out
  • Explain replication lag and fix read-your-writes and monotonic-read anomalies
  • Compare leader-follower, multi-leader and leaderless replication, and explain failover, split brain and fencing
  • Choose range, hash or directory sharding and a partition key that avoids hot partitions
  • Show with numbers why consistent hashing moves about 1/N of the keys while hash mod N moves almost all of them
  • Explain the cost of cross-shard queries and transactions, and decide when sharding is justified

Scale up first, then out

A single database server runs out of one of four things, and each shortage has its own cure:

  • Read capacity: more queries than one machine's CPU, memory and disks can serve. Cure: a cache, then read replicas.
  • Write capacity: more inserts and updates than one machine can log and apply. Cure: a bigger machine, then sharding.
  • Storage: data plus indexes outgrow the disks, or backups, restores and schema changes start taking days. Cure: archive cold rows, then shard.
  • Availability: one machine is one hardware fault away from an outage. Cure: replicas that can take over.

Vertical scaling (scaling up) means a bigger machine. Nothing in the application changes, there is still one copy of the truth, and joins, transactions and constraints keep working. Managed database instances with more than a hundred vCPUs and terabytes of RAM are a menu option, enough for most companies' main database. The limits: price climbs steeply at the top end, there is a ceiling, and it is still one machine to lose or to restart for an upgrade.

Horizontal scaling (scaling out) adds machines, in two ways that are easy to mix up. Replication keeps a full copy of the data on several machines. Partitioning, usually called sharding when the parts live on different machines, splits the data so that each machine holds only a part.

Replication copies the same rows to more machines; sharding puts different rows on different machines. Only sharding adds write capacity.

Read replicas and replication lag

▶ Video lesson: Read replicas and replication lag 4:08 · 8 scenes · narrated, pause anytime and explore

In leader-follower replication (also called primary-replica) one node, the leader, takes every write and records it in a log; the followers receive that log and replay it in the same order. PostgreSQL streams its write-ahead log (WAL); MySQL ships its binary log. A follower is therefore an exact copy of the leader as of some recent moment.

What matters is when the leader tells the client "committed":

  • Asynchronous: as soon as the leader's own log is on disk. Fast, and followers can be far away, but a follower can fall seconds behind, and if the leader dies, its last writes may exist nowhere else.
  • Synchronous: only after a follower has received (and usually flushed) the record too. A leader crash loses nothing that was acknowledged, but every commit pays a network round trip, and a slow synchronous follower slows every write.
  • Semi-synchronous: one follower synchronous, the rest asynchronous (MySQL's semi-sync replication, or PostgreSQL's synchronous_standby_names naming one standby). The usual compromise: two durable copies of every write without waiting for the slowest replica.
sequenceDiagram
  participant C as Client
  participant L as Leader
  participant S as Sync follower
  participant A as Async follower
  C->>L: INSERT order 1001
  L->>L: append to WAL and flush
  L->>S: ship WAL record
  S-->>L: received and flushed
  L-->>C: COMMIT OK
  L->>A: ship WAL record, a little later
Semi-synchronous commit: the client waits for one follower, never for all of them. The async follower is the one that can lag.

Read replicas multiply read capacity: point reads at N followers and each serves 1/N of them. The price is replication lag, the delay between a commit on the leader and the moment a follower has applied it. It is usually milliseconds and sometimes seconds or minutes: a follower stuck behind a long query, a network blip, a huge batch update. Lag loses nothing; it shows users the past. The simulation shows how that surfaces:

  • Read-your-writes breaks: a user writes, then reads from a follower that has not applied the write, and their own change seems to vanish. Fix: read a user's own recently changed data from the leader, or from a follower that has replayed past the write's log position.
  • Monotonic reads break: two reads land on two followers with different lag, so a value appears and then disappears. Fix: pin each user's reads to one follower, for example by hashing the user id.
  • Consistent prefix breaks: with partitioned data, a reader can see a reply before the message it answers, because the two rows replicated along different paths. Fix: keep causally related writes in one partition, or track dependencies (Consistency models & the CAP theorem covers this).

Read-your-writes routing in Python

Simple and approximate: it assumes lag stays under the window, so pick a window well above the lag you normally see, and alert when lag exceeds it.

import time


class ReplicaRouter:
    # reads go to followers, except a user's own data just after that user wrote

    def __init__(self, leader, followers, window_s: float = 5.0):
        self.leader = leader
        self.followers = followers
        self.window_s = window_s                    # comfortably above the usual replication lag
        self.last_write: dict[int, float] = {}      # user_id -> time of last write (keep it in Redis in production)

    def for_write(self, user_id: int):
        self.last_write[user_id] = time.time()
        return self.leader

    def for_read(self, user_id: int, own_data: bool):
        wrote = self.last_write.get(user_id)
        if own_data and wrote is not None and time.time() - wrote < self.window_s:
            return self.leader                      # read-your-writes
        return self.followers[user_id % len(self.followers)]   # one follower per user: monotonic reads

Exact: remember the WAL position after the user's write and only read from a follower that has replayed past it. It holds however large the lag grows.

import psycopg


def write(leader: psycopg.Connection, session: dict, sql: str, params: tuple) -> None:
    with leader.transaction():
        leader.execute(sql, params)
    # a WAL position at or after this commit: any follower that has replayed past it has the write
    session["min_lsn"] = leader.execute("SELECT pg_current_wal_lsn()").fetchone()[0]


def read(followers: list[psycopg.Connection], leader: psycopg.Connection, session: dict, sql: str, params: tuple):
    need = session.get("min_lsn")
    for f in followers:
        if need is None or f.execute("SELECT pg_last_wal_replay_lsn() >= %s::pg_lsn", (need,)).fetchone()[0]:
            return f.execute(sql, params).fetchall()
    return leader.execute(sql, params).fetchall()   # no follower has caught up yet: ask the leader

Replicas are not backups. A DELETE without a WHERE, or a bad migration, reaches every follower within milliseconds. Keep point-in-time backups (a base backup plus archived WAL) as well; some teams also run a delayed replica that deliberately trails by an hour (PostgreSQL recovery_min_apply_delay, MySQL SOURCE_DELAY) as a fast undo.

Three replication topologies

Who may accept a write decides almost everything else: whether two writes can conflict, what a read can return, and what happens when a node fails. There are three answers.

Leader-follower: one node takes the writes

The default in PostgreSQL, MySQL, MongoDB replica sets and Redis. Each shard has exactly one leader at a time, so its writes have a single order and can never conflict.

flowchart LR
  W[Writers] -->|all writes| L[(Leader)]
  L -->|replication log| F1[(Follower 1)]
  L -->|replication log| F2[(Follower 2)]
  RD[Readers] -.->|most reads| F1
  RD -.->|most reads| F2
  RD -.->|fresh reads| L
One writer, many readers. The dotted reads are cheap and may be stale; the read to the leader is fresh.

Multi-leader: one leader per region

Several nodes accept writes, typically one per data centre (or one per device in offline-first apps, where every phone is a leader), and they replicate to each other asynchronously.

flowchart LR
  CE[EU users] -->|writes| LE[(Leader EU)]
  CU[US users] -->|writes| LU[(Leader US)]
  LE -->|async| LU
  LU -->|async| LE
Local writes in every region, at the price of conflicts when two regions change the same record.

Leaderless: any replica, plus quorums

There is no leader. The client, or whichever node receives the request (the coordinator), sends it to several replicas at once and counts the answers. This is the design of Amazon's Dynamo paper (2007), used by Cassandra, ScyllaDB and Riak. The quorum maths, and what it does and does not guarantee, is in Consistency models & the CAP theorem.

flowchart LR
  C[Client or<br/>coordinator] -->|write v2| R1[(Replica 1)]
  C -->|write v2| R2[(Replica 2)]
  C -->|write v2| R3[(Replica 3)]
  C -.->|read| R2
  C -.->|read| R3
Writes and reads both go to several replicas; overlap between the two sets is what makes reads fresh.

Failover and split brain

With a single leader, a dead leader stops all writes, so the system must fail over: promote a follower and send everyone to it. Four steps, each of which can go wrong:

  1. Detect. Heartbeats stop for longer than a timeout. A timeout cannot tell a crashed node from a paused one or a cut link: too short and a garbage-collection pause triggers a needless failover, too long and every real failure lasts that long.
  2. Elect the follower with the most recent data. That needs agreement: consensus inside the database (Raft, Paxos) or an external coordinator such as etcd or ZooKeeper (Patroni does this for PostgreSQL).
  3. Reconfigure clients and routers to write to the new leader: service discovery, a virtual IP, or a proxy.
  4. Fence the old leader, so that if it comes back, or was never really dead, it cannot accept writes.

With asynchronous replication, step 2 has a built-in loss: writes the old leader acknowledged but had not shipped are discarded when it rejoins. GitHub's October 2018 outage began with a 43-second network partition that triggered a cross-country database failover; with writes on both sides, the site ran degraded for about 24 hours while the data was reconciled.

Split brain is the worst case. The old leader was cut off rather than dead, so it keeps serving the clients on its side while the other side elects a replacement: two leaders accept writes, and the data forks into histories that cannot be merged automatically. The defences are majority quorums (with 3 or 5 voters, only one side of a partition can elect a leader or commit a write) and fencing tokens: every election increments an epoch (Raft calls it the term), and storage rejects writes that carry an older one.

sequenceDiagram
  participant O as Old leader
  participant M as Coordinator
  participant N as New leader
  participant S as Storage
  M->>O: heartbeat, no reply for 10 s
  M->>N: promote, epoch 8
  N->>S: write with token 8
  O->>S: write with token 7
  S-->>O: rejected, 7 is older than 8
Fencing: the deposed leader is stopped by the thing it writes to, not by its own judgement.

Asynchronous replication plus automatic failover can lose acknowledged writes. The client heard 'committed' before any follower had the record; if that leader dies, the promoted follower never saw it. Where a write must survive (payments, orders), commit to at least one other replica before acknowledging (semi-synchronous replication, or a consensus-based database), and make sure failover promotes only a replica that has every acknowledged write.

Sharding strategies and hot partitions

▶ Video lesson: Sharding: hash, range, directory, and hot keys 5:40 · 7 scenes · narrated, pause anytime and explore

Sharding splits one data set across machines so each holds and serves a fraction of it. Every row has a partition key (user id, tenant id, order id), and a rule maps the key to a shard. A good rule spreads data and traffic evenly and keeps rows that are read together on the same shard. There are three families of rules:

  • Range: each shard owns a contiguous range of keys (a-f, g-m ..., or ids 0-999,999 ...). Neighbouring keys sit together, so a range scan touches one or two shards, and a shard that grows too large splits in two. The risk is hot spots: when keys arrive in order (timestamps, auto-increment ids), every new write lands on the last range.
  • Hash: the shard comes from a hash of the key. Keys spread evenly whatever their pattern, but neighbours are scattered, so a range scan must ask every shard. hash(key) mod N is the naive version; changing N moves almost every key, which is why real systems hash into a fixed number of slots or onto a ring.
  • Directory: a lookup table maps each key, usually a tenant, to a shard. Placement is an explicit decision, so you can give a huge tenant its own shard, keep an EU customer on an EU shard, or move one tenant at a time. The directory sits on every request's path, so it must be cached and replicated.

Hot partitions and key design

Even a perfect hash spreads keys, not requests. A hot partition is a shard that receives far more than its share: a celebrity's account, a product in a flash sale, a counter everyone increments, or today's date at the front of a range key. Rules of thumb for choosing the partition key:

  • High cardinality. Millions of distinct values (user id), not a handful (country, status). A key with 4 distinct values can never use more than 4 shards.
  • Spread writes over time. Do not lead a range key with a timestamp or a sequence; prefix it with a hash or a bucket number, or use hash sharding.
  • Co-locate what is read together. Shard orders, order items and payments by customer_id and "a customer's orders" is a single-shard query; shard them by order_id and it scatters.
  • Split a known hot key on purpose. Write to one of k sub-keys and read all k (write sharding, or salting). Writes spread over up to k shards; each read costs k lookups, so cache the total if reads are hot too.
import random

BUCKETS = 10

def like(r, post_id: int) -> None:
    r.incr(f"likes:{post_id}:{random.randrange(BUCKETS)}")        # writes land on 10 keys, so 10 shards

def like_count(r, post_id: int) -> int:
    return sum(int(r.get(f"likes:{post_id}:{b}") or 0) for b in range(BUCKETS))   # a read pays 10 lookups

Consistent hashing and rebalancing

▶ Video lesson: Consistent hashing: add a server, move one arc 4:19 · 6 scenes · narrated, pause anytime and explore

Shards get added (growth) and removed (failure, cost cuts), so the key-to-shard mapping must survive a change in the number of shards. hash(key) mod N does not: a key stays put only if its hash leaves the same remainder under the old and the new divisor, which happens for about 1 key in N + 1. Going from 4 shards to 5 moves about 80% of the data.

Consistent hashing (Karger et al., 1997) puts servers and keys on the same circle of hash values. A key belongs to the first server clockwise from it. A new server takes over only the arc just before it, so about 1/N of the keys move, all from one neighbour; a removed server hands its arc to the next one. Virtual nodes give each server many small arcs instead of one large one, which evens out the load and spreads a failed server's keys over all survivors. Finding a key's owner is a binary search over the sorted ring positions (Binary Search), and the ring also says where the replicas go: the next distinct servers clockwise.

A hash ring: add a server, lose a server, then use virtual nodes

Three servers and twelve keys on a ring of 360 positions; colours show which server owns each key. Count how many keys change owner in each scenario, and where they go.

A ring with virtual nodes and a replica preference list

import bisect
import hashlib


def h(value: str) -> int:
    # stable 64-bit hash: Python's built-in hash() of a str changes between processes, so never route with it
    return int.from_bytes(hashlib.md5(value.encode()).digest()[:8], "big")


class Ring:
    def __init__(self, nodes: list[str], tokens_per_node: int = 16):
        self.points = sorted((h(f"{node}#{i}"), node) for node in nodes for i in range(tokens_per_node))
        self.positions = [p for p, _ in self.points]

    def owner(self, key: str) -> str:
        i = bisect.bisect(self.positions, h(key)) % len(self.points)    # first token clockwise, wrapping past the end
        return self.points[i][1]

    def replicas(self, key: str, n: int = 3) -> list[str]:
        # preference list: the first n DISTINCT nodes clockwise; Dynamo-style stores keep the copies there
        start = bisect.bisect(self.positions, h(key))
        found: list[str] = []
        for step in range(len(self.points)):
            node = self.points[(start + step) % len(self.points)][1]
            if node not in found:
                found.append(node)
                if len(found) == n:
                    break
        return found


ring = Ring(["db1", "db2", "db3", "db4"])
print(ring.owner("user:42"), ring.replicas("user:42"))       # db3 ['db3', 'db2', 'db1']

keys = [f"user:{i}" for i in range(100_000)]
before = {k: ring.owner(k) for k in keys}
bigger = Ring(["db1", "db2", "db3", "db4", "db5"])
moved = sum(before[k] != bigger.owner(k) for k in keys)
print(f"ring: {moved / len(keys):.0%} moved")                  # 21%; the ideal is 1/5 = 20%
print(f"mod:  {sum(h(k) % 4 != h(k) % 5 for k in keys) / len(keys):.0%} moved")   # 80%
bisect finds the first token clockwise in O(log T) for T tokens. replicas() is the preference list: the extra copies of a key live on the next distinct nodes around the ring.

Rebalancing in practice

Placement is half the problem; moving data without downtime is the other half. Production systems use one of three schemes:

  • Many fixed partitions. Create far more partitions than nodes (say 1,024 for 8 nodes) and never change the count. A key's partition is fixed for life; a new node takes whole partitions from the others, and only the partition-to-node map changes. Redis Cluster (16,384 hash slots), Elasticsearch, Couchbase and Riak work this way. Pick the count for the largest cluster you expect, since changing it later is a full reshuffle.
  • Dynamic splitting. Range-partitioned stores split a partition when it grows past a size threshold (or gets too hot) and merge small ones: HBase regions, Bigtable tablets, MongoDB chunks, CockroachDB ranges.
  • Tokens per node. Each node owns a fixed number of ring positions, so more nodes means more, smaller arcs. Cassandra's vnodes (num_tokens, 16 by default since 4.0) are this scheme.

Be careful with automatic rebalancing: an overloaded node can look dead, its data starts moving, the copying adds load to its neighbours, and one slow node becomes a cluster-wide incident. Many operators let the system propose a plan and have a person approve it, and always throttle the copy. The move itself is a background copy followed by a short cutover:

sequenceDiagram
  participant R as Cluster config
  participant S as Source node
  participant T as Target node
  R->>T: assign p7, state importing
  S->>T: bulk copy p7 snapshot
  S->>T: stream writes since snapshot
  R->>S: pause writes to p7 briefly
  S->>T: final writes, caught up
  R->>R: owner of p7 is now T
  R->>S: drop old copy of p7
Moving one partition online. Only the short pause is visible to users; everything else runs while traffic flows.

Cross-shard queries and transactions

Sharding makes the designed query cheap: anything that names the partition key goes to one shard, and that shard does the same small amount of work however many shards exist. Everything else gets more expensive as shards are added.

  • Scatter-gather queries. A query without the partition key ("the 20 newest orders across all customers", "find the user with this email" on a table sharded by user_id) goes to every shard; each returns its own top 20 and the router merges and re-sorts them. Every such query costs N shard requests and waits for the slowest shard.
  • Secondary indexes. A local index lives on each shard and covers only that shard's rows: writes stay on one shard, but reads by the indexed column scatter. A global index is partitioned by the indexed value: a read goes to one index shard, but a write must also update an index entry that usually lives on another shard, so global indexes are typically updated asynchronously and lag (DynamoDB's global secondary indexes are eventually consistent).
  • Joins. The database cannot join rows that live on different shards. Co-locate them with the same shard key, copy small reference tables to every shard, or join in the application.
  • Uniqueness and ids. A UNIQUE (email) constraint or an auto-increment counter holds only within one shard. Use a global index or a lookup service for uniqueness, and globally unique ids (UUIDs, or Snowflake-style ids built from a timestamp, a machine number and a sequence).
  • Transactions. Anything that must change two shards atomically needs a distributed commit protocol.

Fan-out makes the slowest shard everyone's problem

A scatter-gather query waits for every shard it asks. If one shard is slow 1% of the time (a garbage-collection pause, a cold cache, a compaction), how often is the whole query slow?

sequenceDiagram
  participant C as Coordinator
  participant A as Shard A
  participant B as Shard B
  C->>A: PREPARE debit Ann 50
  C->>B: PREPARE credit Bob 50
  A-->>C: YES, locked and logged
  B-->>C: YES, locked and logged
  C->>A: COMMIT
  C->>B: COMMIT
Two-phase commit across two shards: two round trips, with both rows locked from the first message to the last.

Hence slow and fragile: two round trips under lock, throughput set by the slowest participant, and a coordinator failure that can freeze rows. Spanner and CockroachDB run two-phase commit (or a variant) over participants that are themselves replicated with consensus, so one crash does not block for long, but these transactions still cost more than single-shard ones.

The usual design answer is to avoid needing them. Pick a shard key that keeps each transaction on one shard (a customer's orders, cart and payments all by customer_id), or split the process into local transactions with compensating steps, a saga: debit Ann, then credit Bob, and if the credit fails, refund the debit. A saga gives up isolation, since others can see the in-between state. ACID & transactions covers single-node transactions.

When to shard, and how to say it

Should we shard? Usually: not yet

Sharding is close to a one-way door. Once data is split, cross-shard joins, transactions, unique constraints and ad-hoc queries are gone or expensive, every schema change runs once per shard, and the shard key is very hard to change later. First use the cheaper rungs: fix queries and indexes, add a cache and read replicas, buy a bigger instance, archive cold rows, and move one heavy workload (sessions, events, search) to a store built for it. Shard when the numbers say one primary's write rate or data size runs out within your planning horizon, and say that number out loud.

How many shards, and what does adding one cost?

Size for whichever runs out first, storage or write rate. The per-shard limits are planning numbers you would measure on your own hardware, not constants. Back-of-envelope estimation covers the inputs.

flowchart TD

  Q1 -->|no| Q2{Reads or writes?}
  Q2 -->|reads| RD[Cache and<br/>read replicas]
  Q2 -->|writes or size| Q3{Bigger machine<br/>lasts 1-2 years?}

  Q3 -->|no| Q4{Can a workload or<br/>old data move out?}

Sharding is the last box on purpose: every earlier box is cheaper and keeps a single copy of the truth.

Scaling-the-database checklist for a design discussion

A strong answer to 'the database can't keep up, what do you do?': 'First I find out which resource is exhausted. For reads I add a Redis cache and two read replicas, and route a user's reads of their own profile to the leader for a few seconds after they edit it. At our peak of about 3,000 writes a second a larger primary is enough, so I would not shard yet. If writes grow tenfold, I shard by user_id into 1,024 logical shards mapped onto physical nodes, so adding a node moves whole shards. Queries without a user_id, such as admin search, go to a separate index fed from the change stream instead of fanning out to every shard.'
