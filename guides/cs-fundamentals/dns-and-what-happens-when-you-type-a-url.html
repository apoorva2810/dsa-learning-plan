DNS & what happens when you type a URL

Before a single byte of HTTP moves, the browser has to turn a name into an address. This chapter follows a DNS lookup through the stub resolver, the recursive resolver, and the root, TLD and authoritative servers; explains record types, TTLs and every cache on the path; shows how DNS steers traffic between regions; and then strings the whole page load together, from URL parsing to first paint, with a latency budget per stage. It is the classic closing question of a systems interview.

After this chapter you can
  • Trace a recursive DNS resolution through root, TLD and authoritative servers and say what each one returns
  • Explain TTLs, caching layers and negative caching, and predict how long a record change takes to reach users
  • Choose the right record type (A, AAAA, CNAME, MX, NS, TXT, SRV) and know why a CNAME cannot sit at the zone apex
  • Describe how DNS supports load balancing and geo-routing, and where it falls short of a real load balancer
  • Walk the full page-load pipeline in order and give a rough latency for each stage
  • Diagnose common DNS failures: stale caches, NXDOMAIN caching, resolver timeouts, provider outages

Names and the DNS hierarchy

The Domain Name System is a distributed, hierarchical, heavily cached database that maps names to records, most often an IP address. No single machine holds it. A name is read from right to left: in www.example.com. the trailing dot is the root, com is a top-level domain (TLD), example.com is a zone that someone registered, and www is a record inside that zone. Each level delegates to the next by publishing NS records that name the servers responsible below it.

flowchart TD
  Root["Root zone .<br/>13 server names, anycast"] --> Com["com TLD zone<br/>run by the registry"]
  Root --> Org["org, net, in, uk ...<br/>other TLD zones"]
  Com --> Ex["example.com zone<br/>ns1.example.com"]
  Com --> Other["other .com zones"]
  Ex --> Www["www  A  93.184.216.34"]
  Ex --> Mail["example.com  MX  mail.example.com"]
Each box knows only about the level directly below it. The records people care about sit at the bottom, in the zone the owner controls.
RoleWho runs itWhat it doesCaches?
Stub resolveryour OS (a library call such as getaddrinfo)asks one configured resolver; does no walking itselfshort-lived, by TTL
Recursive resolveryour ISP, your company, or a public service (8.8.8.8, 1.1.1.1)does the full lookup on behalf of many clientsyes: the main cache, shared by all its users
Root and TLD serversICANN-coordinated operators and registriesanswer with referrals to the next leveln/a: they serve zones
Authoritative serverthe domain owner or their DNS provideranswers with the zone's records (the final answer)n/a: it is the source
'DNS server' is ambiguous. In an interview say which of these four roles you mean.

Recursive resolution step by step

▶ Video lesson: Resolving a name, step by step 4:22 · 7 scenes · narrated, pause anytime and explore

The client sends one recursive query ("give me the final answer") to its resolver. The resolver then performs iterative queries: it asks each server in the chain, and each replies either with the answer or with a referral ("I do not know, ask these servers"). Queries are small UDP packets to port 53; the protocol falls back to TCP for answers too large for a datagram. Run all four cache states below: the same lookup costs anywhere from 5 ms to 100 ms.

Resolving www.example.com: cold, warm, cached and non-existent

The orange box is the server doing work; the thick arrow is the message in flight. Faded servers are not contacted. Watch the resolver's cache fill up on the right, and the elapsed time in the status bar.

Interviewers ask 'what is the difference between recursive and iterative DNS queries?'. Answer: 'The client-to-resolver query is recursive: the resolver promises to return a final answer or an error. The resolver-to-server queries are iterative: each server returns either the answer or a referral to a server closer to it, and the resolver follows the chain. The resolver caches every step by its TTL, so most lookups never reach the root or TLD at all.'

A name can have several records of different types. The apex (example.com itself) always has SOA and NS, which is why a CNAME cannot live there; providers offer ALIAS, ANAME or 'CNAME flattening' to fake it.
flowchart LR
  Q["www.shop.example"] -->|"CNAME, TTL 300"| C1["shop.example.cdn.net"]
  C1 -->|"CNAME, TTL 60"| C2["edge-eu1.cdn.net"]
  C2 -->|"A, TTL 20"| IP["203.0.113.9"]
The resolver follows the chain and caches every link under its own TTL. The CDN can move its edge address within 20 s without the site owner touching anything.

Looking at DNS from the command line and from Python

$ dig +noall +answer www.example.com A
www.example.com.    300   IN   A    93.184.216.34
#                   ^TTL left in the resolver's cache

$ dig +trace www.example.com A       # walk the hierarchy yourself, as a resolver would
.                   518400  IN  NS  a.root-servers.net.
com.                172800  IN  NS  a.gtld-servers.net.
example.com.        172800  IN  NS  a.iana-servers.net.

Addresses are illustrative. Note the TTLs shrinking as you go down: referrals live for days, leaf records for minutes.

The same from Python

import socket
import dns.resolver          # pip install dnspython

# What your programs normally do: ask the OS resolver (it consults caches, hosts file, then the configured recursive resolver)
for family, _, _, _, sockaddr in socket.getaddrinfo("example.com", 443, type=socket.SOCK_STREAM):
    print(family.name, sockaddr[0])

# Ask the DNS protocol directly, and see the TTL
answer = dns.resolver.resolve("example.com", "MX")
for record in answer:
    print(record.preference, record.exchange)
print("seconds the resolver may cache this:", answer.rrset.ttl)
Python does not cache lookups itself. A pooled HTTP connection keeps using the address it resolved earlier, so a DNS change does not move existing connections.

TTLs and the caches on the path

Every record has a TTL (time to live, in seconds): the longest a cache may reuse it without asking again. It is how the owner trades freshness against load. There is no push and no invalidation in DNS, only expiry, so a change can take up to one TTL to reach everyone. And there are many caches in series.

flowchart LR
  App["Browser<br/>cache about a minute"] --> OS["OS stub resolver<br/>cache, hosts file"]
  OS --> Router["Home router<br/>forwarder, often caches"]
  Router --> Rec["Recursive resolver<br/>shared cache"]
  Rec --> Auth["Authoritative server<br/>source of truth"]
A lookup stops at the first layer that has a fresh answer. Only the last box can change the answer.

Changing a record: how a change spreads through caches

Three resolvers see traffic at different moments. The operator changes the address at minute 3. Each box is a cached copy for one TTL.

What a TTL costs and what it buys

The TTL is both the staleness window and the divisor of your DNS load. Pick it from the failover time you can tolerate.

DNS for load balancing and traffic steering

Because the authoritative server chooses what to answer, DNS can steer clients: return different addresses to different people, or drop an address when its health check fails. It is the first, coarsest layer of load balancing.

PolicyHow it answersTypical use
Round robinreturns all addresses, in rotating ordercheap spreading across identical servers
Weightedreturns addresses in proportion to weightscanaries and gradual migrations (send 5% to the new stack)
Latency-basedthe region with the lowest measured latency to the resolvermulti-region applications
Geolocationby the country or continent of the resolver or clientdata residency, localised sites
Failoverprimary while its health check passes, else the secondaryactive-passive disaster recovery
Anycast is a different tool: one IP announced from many places and the network's routing picks the nearest. Resolvers, CDNs and DDoS scrubbing use it.
flowchart LR
  U1["User in Mumbai"] --> R1["Recursive resolver<br/>in India"]
  U2["User in Dublin"] --> R2["Recursive resolver<br/>in Ireland"]
  R1 --> DNS["Authoritative DNS<br/>latency policy and health checks"]
  R2 --> DNS
  DNS -->|"answer: ap-south address"| M["Mumbai region<br/>load balancer"]
  DNS -->|"answer: eu-west address"| D["Dublin region<br/>load balancer"]
The authoritative server sees the resolver's address (or a truncated client subnet), not the user's, so steering is only as accurate as that proxy.

Know the limits. Failover through DNS is only as fast as the TTL plus caches that stretch it, and some clients ignore TTLs or keep a resolved address for the life of a connection. Load spreading is crude, because one resolver serving a whole ISP sends all its users to one address. So use DNS to pick a region, and a real load balancer (see Load balancers, reverse proxies & API gateways) to spread load and react to failures within seconds.

When DNS goes wrong

The failure catalogue

'I changed the record but users still see the old address'

Caches expire; they are never invalidated. Each resolver serves the old value for up to one TTL, browsers and OS caches add their own, and some resolvers and runtimes clamp or ignore TTLs (JVMs have cached lookups for the life of the process in some configurations). Fix: lower the TTL a day or more before a planned change; after it, verify with dig @authoritative-server versus a public resolver.

Negative caching: a new record that 'doesn't exist'

If a resolver recently got NXDOMAIN for a name, it may keep returning it for the zone's negative TTL (the SOA's last field, often minutes to an hour) even after you create the record. Create records before anything looks them up, or keep the negative TTL low.

Slow or failing resolvers

The stub tries its configured resolvers in order, with a timeout of several seconds, so one dead resolver makes every new connection stall for seconds before the next is tried. Applications that resolve on a request path should set timeouts and tolerate stale results; monitor resolver latency.

A DNS provider outage

If all your name servers are at one provider, an outage there makes your domain unreachable for anyone whose cached records have expired, however healthy your servers are. Large sites use two independent providers and keep TTLs long enough for caches to ride out an outage.

Delegation mistakes

The NS records at the registrar (the parent) must match the servers that actually serve the zone. A mismatch or a 'lame' delegation produces intermittent failures that depend on which server a resolver picks.

DNS as service discovery

Kubernetes and cloud load balancers rely on DNS names whose addresses change often, so TTLs are short (5 to 60 s) and clients must re-resolve. Long-lived pooled connections, and clients that resolve once at start-up, keep talking to an address that no longer exists.

Encrypted DNS in one paragraph

Classic DNS travels as plain text over UDP port 53, so anyone on the path can read your queries and alter the answers. DNS over TLS (DoT, port 853) and DNS over HTTPS (DoH, port 443) wrap the stub-to-resolver leg in encryption. They hide queries from the network and block tampering on that leg, but the resolver itself still sees every name, which moves trust to whoever you choose. DoH is hard to distinguish from ordinary HTTPS, which helps users behind filtering networks and annoys enterprises that filter by DNS. DNSSEC is a separate mechanism: it signs records so a resolver can detect forged answers, but it does not encrypt anything.

The interview answer

A strong answer to 'what happens when you type a URL?' sounds like: 'The browser parses the URL, checks the HSTS list and its HTTP cache, then resolves the host name: browser cache, OS, and a recursive resolver that walks root, TLD and authoritative servers if it has no cached answer. With the address it opens a TCP connection (or QUIC), then does a TLS 1.3 handshake: two round trips in all before the request is sent. The GET goes through a CDN and load balancer to an app server that uses a cache and database to build the HTML. The browser parses the response as it streams in, fetches CSS, JavaScript and images over the same connection, builds the DOM and CSSOM, lays out and paints. The big levers are fewer round trips: caching, keep-alive, a CDN near the user, and HTTP/3.'

Can you walk the whole pipeline, and defend each stage?
