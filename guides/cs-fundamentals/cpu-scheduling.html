CPU scheduling

The scheduler decides which ready process gets the CPU next. This chapter defines what 'good' means (turnaround, waiting, response, throughput), runs the same five processes through FCFS, SJF, SRTF, round robin, priority and MLFQ as Gantt charts you can step through, and ends with how Linux and Python's own schedulers really behave.

After this chapter you can
  • Compute turnaround, waiting and response time from arrival, burst, first-run and completion times
  • Draw the Gantt chart for FCFS, SJF, SRTF, round robin, priority and MLFQ on a small workload by hand
  • Explain the convoy effect, starvation and aging, and the round-robin quantum trade-off with numbers
  • State the MLFQ rules and why Linux's CFS/EEVDF uses virtual runtime instead of fixed priorities
  • Pick a scheduling policy for a stated goal and defend it in an interview

What the scheduler is trying to optimise

Whenever a CPU is free, the CPU scheduler picks one of the Ready tasks to run (see the process states in Processes & threads). The dispatcher then does the context switch. Every algorithm in this chapter is a different answer to 'which one?', and the right answer depends on what you measure.

For one process, four times matter: arrival (it became ready), burst (CPU time it needs), first run (it first got the CPU) and completion (it finished). From them:

MetricFormulaPlain meaningWho cares
Turnaround timecompletion − arrivaltotal time in the systembatch jobs
Waiting timeturnaround − bursttime spent in the ready queue, not runningeverybody; the number schedulers minimise most often
Response timefirst run − arrivalhow long until the job first sees the CPUinteractive users
Throughputjobs completed ÷ timework finished per unit timeoperators of busy systems
CPU utilisationbusy time ÷ total timehow much of the CPU did useful workcost
Fairness / no starvationevery ready job eventually runsnobody waits forevermulti-user systems
Waiting time excludes the job's own execution, so it measures what the scheduler is responsible for.

These defaults are P2 under non-preemptive SJF in the workload used below: it arrives at t=2, needs 4 ticks, first runs at t=11 and finishes at t=15.

The metrics pull against each other. Shortest-job-first minimises average waiting but can starve long jobs. Round robin gives good response and usually worsens turnaround. A real scheduler picks a trade-off for its workload; there is no universally best one.

flowchart LR
  Arr[New process] --> RQ[Ready queue]
  RQ --> Sch{Scheduler<br/>picks one}
  Sch --> Disp[Dispatcher<br/>context switch]
  Disp --> CPU[CPU]
  CPU -- slice ends or preempted --> RQ
  CPU -- blocks on I/O or lock --> WQ[Wait queue]
  WQ -- event done --> RQ
  CPU -- exits --> Done[Terminated]
Where the scheduler sits: it chooses from the ready queue; everything that leaves the CPU either goes back to it, waits, or ends.

Preemptive or not

A scheduling decision is needed at four moments: a running process (A) blocks, (B) is interrupted and returns to Ready, (C) a waiting process becomes ready, or (D) a process exits. A non-preemptive scheduler only acts at A and D: once a process has the CPU it keeps it until it blocks or finishes. A preemptive scheduler acts at all four and may take the CPU away. Preemption is what makes interactive systems feel responsive, and what makes shared data dangerous (see Synchronisation & deadlocks).

stateDiagram-v2
  Ready --> Running : dispatch
  Running --> Waiting : A blocks on I/O
  Running --> Ready : B interrupted
  Waiting --> Ready : C I/O completes
  Running --> Terminated : D exits
The four moments at which the scheduler may run. Non-preemptive schedulers only act on A and D.

Each algorithm in a few lines of Python

Run jobs in arrival order, each to completion. No starvation, but the average wait depends entirely on the order. The convoy effect: one long CPU-bound job at the front makes every short job queue behind it, and the I/O devices sit idle because the short I/O-bound jobs never get to issue their next request.

def fcfs(procs):                          # procs: list of (name, arrival, burst)
    clock, gantt = 0, []
    for name, arrival, burst in sorted(procs, key=lambda p: p[1]):
        clock = max(clock, arrival)       # the CPU idles until the job arrives
        gantt.append((name, clock, clock + burst))
        clock += burst
    return gantt

When the CPU is free, run the ready job with the shortest burst; ties go to the earlier arrival. Provably optimal for average waiting time when everything is ready at once, but it needs the burst length in advance and is non-preemptive, so a long job that arrived first still blocks later short ones.

import heapq

def sjf(procs):
    pending = sorted(procs, key=lambda p: p[1])          # by arrival
    ready, gantt, clock, i = [], [], 0, 0                # ready: heap of (burst, arrival, name)
    while i < len(pending) or ready:
        while i < len(pending) and pending[i][1] <= clock:
            name, arrival, burst = pending[i]
            heapq.heappush(ready, (burst, arrival, name))
            i += 1
        if not ready:
            clock = pending[i][1]                        # idle until the next arrival
            continue
        burst, arrival, name = heapq.heappop(ready)
        gantt.append((name, clock, clock + burst))
        clock += burst
    return gantt

The preemptive SJF: always run the job with the least remaining time, so a short arrival interrupts a long job. It has the lowest possible average waiting time, at the price of more switches and starvation of long jobs.

import heapq

def srtf(procs):
    pending = sorted(procs, key=lambda p: p[1])
    ready, gantt, clock, i = [], [], 0, 0                # ready: heap of (remaining, arrival, name)
    while i < len(pending) or ready:
        while i < len(pending) and pending[i][1] <= clock:
            name, arrival, burst = pending[i]
            heapq.heappush(ready, (burst, arrival, name))
            i += 1
        if not ready:
            clock = pending[i][1]
            continue
        remaining, arrival, name = heapq.heappop(ready)
        next_arrival = pending[i][1] if i < len(pending) else float("inf")
        run = min(remaining, next_arrival - clock)       # until done or until someone new arrives
        if gantt and gantt[-1][0] == name and gantt[-1][2] == clock:
            gantt[-1] = (name, gantt[-1][1], clock + run)  # merge with the previous slice
        else:
            gantt.append((name, clock, clock + run))
        clock += run
        if remaining > run:
            heapq.heappush(ready, (remaining - run, arrival, name))
    return gantt

FCFS with a clock: each job runs for at most one quantum, then goes to the back of the queue. With n ready jobs, nobody waits more than (n−1) quanta for the next turn.

from collections import deque

def round_robin(procs, quantum):
    pending = deque(sorted(procs, key=lambda p: p[1]))
    remaining = {name: burst for name, _, burst in procs}
    ready, gantt, clock = deque(), [], 0
    while pending or ready:
        while pending and pending[0][1] <= clock:        # arrivals join the queue ...
            ready.append(pending.popleft()[0])
        if not ready:
            clock = pending[0][1]
            continue
        name = ready.popleft()
        run = min(quantum, remaining[name])
        gantt.append((name, clock, clock + run))
        clock += run
        remaining[name] -= run
        while pending and pending[0][1] <= clock:        # ... before the preempted job rejoins
            ready.append(pending.popleft()[0])
        if remaining[name]:
            ready.append(name)
    return gantt

Run the best-priority ready job. It is SJF with a different key: SJF is priority scheduling where priority is the predicted burst. The danger is starvation; the cure is aging, letting waiting time raise priority.

def effective_priority(job, now, age_every=3):
    waited = now - job.ready_since                 # ticks spent waiting since it became ready
    return job.priority - waited // age_every      # lower number = more important

def pick(ready, now):
    return min(ready, key=lambda j: (effective_priority(j, now), j.arrival))

Several queues; the highest non-empty one runs. Jobs start at the top, drop a level when they use a whole quantum, and are all lifted back periodically. The scheduler learns who is interactive without being told.

from collections import deque

class MLFQ:
    def __init__(self, quanta=(2, 4, 8)):
        self.quanta = quanta
        self.queues = [deque() for _ in quanta]

    def add(self, job):                         # new jobs start at the top
        self.queues[0].append(job)

    def pick(self):                             # highest non-empty queue, round robin inside it
        for level, queue in enumerate(self.queues):
            if queue:
                return level, queue.popleft(), self.quanta[level]

    def used_full_quantum(self, job, level):    # CPU hog: demote
        self.queues[min(level + 1, len(self.queues) - 1)].append(job)

    def blocked_early(self, job, level):        # behaved interactively: keep its level
        self.queues[level].append(job)

    def boost(self):                            # every S ticks: lift everyone, so nothing starves
        for queue in self.queues[1:]:
            self.queues[0].extend(queue)
            queue.clear()

Shortest-job-first needs the future. Real systems predict the next CPU burst from history with an exponential average: next estimate = α × last actual burst + (1 − α) × previous estimate. With α = 0.5 the estimate follows recent behaviour but forgets old bursts geometrically.

Predicting the next CPU burst

Starting from an estimate of 10 and an actual last burst of 6, with α = 0.5, the next estimate is 8. Raise α to trust recent history more.

Round robin and the quantum

▶ Video lesson: Round robin and the quantum 3:50 · 7 scenes · narrated, pause anytime and explore

Round robin is the baseline for time sharing, and the quantum (time slice) is its whole design decision:

  • As the quantum grows without bound, round robin becomes FCFS.
  • As it shrinks towards the switch cost, the CPU spends its time switching: overhead is c ÷ (q + c) for switch cost c.
  • A common rule of thumb is to choose q so that most CPU bursts (say 80%) finish within one quantum. Interactive tasks then complete their short bursts without being preempted, while CPU hogs get sliced.
  • Response time grows with load: with n ready jobs the worst-case wait for your next turn is about (n − 1) × q.

The quantum trade-off, with switching costs

Three jobs, bursts 6, 3 and 5, switch cost 1 tick (exaggerated). Compare how much time is wasted and how soon each job first runs.

Overhead and worst-case wait for a time slice

Realistic numbers: a quantum of 10 ms and a switch of 10 µs cost 0.1%. Shrink the quantum to 100 µs and the same switch costs 9%.

CPython does round robin on its own threads: the GIL is handed over after the 5 ms switch interval when another thread is waiting (see Processes & threads). The same trade-off applies: a shorter interval improves latency and increases hand-off overhead.

Priority scheduling, starvation and aging

▶ Video lesson: Priorities, starvation and aging 3:54 · 7 scenes · narrated, pause anytime and explore

Each process has a priority and the scheduler runs the best ready one. Priorities are external (set by the user or admin: Unix nice, a service tier) or internal (computed by the OS from behaviour, such as how often a process blocks for I/O). The flaw is starvation: a steady supply of important work means a low-priority job may never run. The cure is aging: increase a job's priority the longer it waits, so some day it wins.

Starvation, and aging as the fix

A low-priority job L and a stream of high-priority H jobs. Run it without aging, then with aging.

Priorities create a second problem when jobs share locks: a low-priority job holding a lock can block a high-priority one while a medium-priority job runs freely. That is priority inversion; it is covered, with the fix, in Synchronisation & deadlocks.

Multilevel feedback queue: learning who is interactive

SJF needs burst lengths, which the OS does not know. MLFQ infers them from behaviour. It keeps several queues with different priorities (and usually longer quanta lower down) and applies these rules:

  1. Run a job from the highest non-empty queue; jobs in the same queue take turns (round robin).
  2. A new job starts in the top queue.
  3. A job that uses its whole quantum is assumed to be CPU-bound and moves down one queue.
  4. A job that blocks before its quantum ends (waiting for a key press or a disk) stays where it is.
  5. Every so often, move all jobs back to the top queue.
flowchart TD
  New[New job] --> Q0[Queue 0<br/>quantum 2, highest]
  Q0 -- blocks before quantum ends --> IO[I/O wait<br/>keeps its level]
  IO --> Q0
  Q0 -- uses the full quantum --> Q1[Queue 1<br/>quantum 4]
  Q1 -- uses the full quantum --> Q2[Queue 2<br/>quantum 8, lowest]
  Q2 -.->|every S ticks| Boost[Priority boost<br/>everything back to Queue 0]
  Boost --> Q0
A job's life in MLFQ. Short, interactive jobs stay near the top; CPU hogs sink; the periodic boost keeps the bottom from starving.

How MLFQ is gamed, and the fix

Yielding just before the quantum ends

A program can issue a trivial I/O just before its quantum expires. Under the simple rule 4 it then never gets demoted and monopolises the top queue. The fix is to account for the total CPU time used at a level (an allotment), regardless of how many times the job gave up the CPU, and to demote when the allotment is spent.

Choosing the parameters

Number of queues, quantum per level, and the boost period S are tuning knobs with no universal values. Too long a boost period starves; too short a period ruins the priority separation. Solaris, BSD and Windows all use descendants of MLFQ.

In practice: Linux and Python

Linux's fair scheduler. Linux's normal tasks used the Completely Fair Scheduler (CFS) from 2.6.23 until 6.5. It has no fixed time slices. Each runnable task has a virtual runtime: the CPU time it has used, scaled by a weight derived from its nice value (a lower nice means a bigger weight, so its virtual clock runs slower). Tasks wait in a red-black tree ordered by virtual runtime and the scheduler always runs the leftmost one, the task that has received the least CPU relative to what it is owed. A task runs for a share of a target latency period, bounded below by a minimum granularity so that switching stays cheap. A task that slept is placed near the smallest virtual runtime, so an interactive task runs soon after waking but cannot hoard credit. Each nice step changes the weight by about 25%, so two CPU-bound tasks one level apart split the CPU roughly 55 to 45.

EEVDF. Since Linux 6.6 the fair class replaces CFS's pick rule with EEVDF (Earliest Eligible Virtual Deadline First). Each task has a lag, how much CPU it is owed compared with what it got; only tasks with non-negative lag are eligible, and among those the one with the earliest virtual deadline runs. A task can request a shorter slice, which gives a latency-sensitive task an earlier deadline without giving it a bigger share of the CPU. Weights and nice still decide the shares.

flowchart TD
  Pick[Core needs a task] --> Stop[Stop class<br/>kernel housekeeping]
  Stop --> DL[Deadline class<br/>SCHED_DEADLINE, EDF]
  DL --> RT[Real-time class<br/>SCHED_FIFO, SCHED_RR]
  RT --> Fair[Fair class<br/>normal tasks, nice values<br/>CFS then EEVDF]
  Fair --> Idle[Idle class<br/>run the idle task]
Linux asks its scheduling classes in strict order; each arrow means 'if this class has nothing runnable, ask the next one'.

os.nice(10)                                  # lower my weight: others win ties for CPU (never raises privilege)

nice changes CFS/EEVDF weight, not a strict priority. Real-time policies are strict priorities and need care.

asyncio is a cooperative scheduler. The event loop keeps a FIFO queue of ready callbacks and runs each until it hits an await. It never preempts, so it has the FCFS weakness exactly: one coroutine that computes without awaiting is the long job at the front of the queue, and everything else waits behind it.

The convoy effect inside an event loop

import asyncio
import time

start = time.perf_counter()

async def heartbeat():
    for _ in range(4):
        print(f"beat at {time.perf_counter() - start:.1f}s")
        await asyncio.sleep(0.2)               # yields to the loop

async def hog():
    end = time.perf_counter() + 1.0
    while time.perf_counter() < end:           # never awaits: nobody else can run for a full second
        pass

async def main():
    await asyncio.gather(heartbeat(), hog())   # the second beat arrives after about 1.0 s, not 0.2 s

asyncio.run(main())
# fix: await asyncio.to_thread(cpu_bound_fn)  or run it in a process pool

Containers. In Kubernetes a CPU limit of 500m is enforced by the kernel's CFS bandwidth controller: the container may use 50 ms of CPU in every 100 ms period, and when that budget is spent all its threads are throttled until the next period. That produces p99 latency spikes in services that are not even CPU-saturated. Check nr_throttled in the cgroup's cpu.stat.

How to answer 'which scheduling algorithm would you use?' Name the goal first. 'For interactive work I care about response time, so round robin or a multilevel feedback queue, because the OS cannot know burst lengths in advance and MLFQ learns them from behaviour. For batch throughput, SJF minimises average waiting but needs predictions and starves long jobs, so I'd add aging. Linux uses a fair-share scheduler (CFS, now EEVDF) and puts hard real-time work in separate classes.' Then volunteer the trade-off you accepted.

Questions interviewers ask next

Why is SJF optimal for average waiting time?

With all jobs ready, the job in position k adds its burst to the wait of every job behind it, so total waiting is the sum of burst_k × (n − k). The largest multipliers should go to the smallest bursts. Swapping an adjacent pair with the longer job first lowers the total by long − short, so sorting by burst is optimal. With arrivals over time, the preemptive form (SRTF) is the optimal one.

Scheduler vs dispatcher?

The scheduler is the policy: it chooses the next process. The dispatcher is the mechanism: it performs the context switch, switches to user mode and jumps to the right instruction. The time it takes is the dispatch latency.

What is the convoy effect?

A long CPU-bound job holds the CPU while short or I/O-bound jobs queue behind it. The queue drains slowly and I/O devices idle. In the convoy workload above, average waiting is 6.75 ticks under FCFS and 1.00 under SRTF.

How would you detect scheduling problems in production?

Run-queue length and load average (vmstat 1, column r; uptime), per-process context switches (pidstat -w), scheduling latency (perf sched latency, the eBPF runqlat tool) and cgroup throttling (cpu.stat). A high load average with idle CPUs points at tasks stuck in uninterruptible I/O wait, not at the scheduler.
