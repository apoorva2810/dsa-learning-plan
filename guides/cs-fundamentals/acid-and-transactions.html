ACID & transactions

A transaction groups statements so they succeed or fail together, even when the server crashes or other clients write the same rows. This chapter shows what each ACID letter prevents, how a write-ahead log makes commits durable and crashes recoverable, which anomalies each isolation level allows (as timelines you can step through), how locking differs from MVCC, why deadlocks happen, and why distributed systems prefer sagas to two-phase commit.

After this chapter you can
  • Name the concrete failure each ACID property prevents and the mechanism that provides it
  • Recognise dirty read, non-repeatable read, phantom, lost update and write skew from a two-transaction timeline
  • Choose an isolation level and a fix (FOR UPDATE, atomic UPDATE, version column, retry) for a given race
  • Explain how a write-ahead log gives atomicity and durability, and what the three recovery passes do
  • Compare two-phase locking with MVCC and describe how a database detects and resolves a deadlock
  • Explain why two-phase commit blocks, and when a saga is the better tool

Why transactions exist

▶ Video lesson: Why transactions exist 4:05 · 6 scenes · narrated, pause anytime and explore

A transaction is a group of reads and writes that the database treats as one unit of work. You mark the boundaries with BEGIN and COMMIT (or ROLLBACK to give up). Without them most databases run every statement as its own transaction, which is called autocommit.

Two kinds of trouble make transactions necessary:

  • Failures. The process, the host or the network dies between two statements.
  • Concurrency. Other clients read and write the same rows while your work is half done.

The standard example is a bank transfer: debit account A, credit account B. Step through what happens when the failure strikes in the middle, first with no transaction and then with one.

A transfer, a crash, and what the database does about it

Three runs of the same 30-unit transfer. Watch the total money in the status bar, and the three places state lives: memory, the data files, and the write-ahead log (WAL).

If only the app dies in the middle of a transaction, the database notices the closed connection and rolls the open transaction back on its own. The runs above use the harder case, where the database host itself loses power.

ACID, letter by letter

ACID is four promises. Each one is defined by the failure it removes, so learn them that way.

PromiseFailure it preventsMechanism
AtomicityAll statements in the transaction take effect, or none doA crash between debit A and credit B leaves money missingUndo information in the log; rollback
ConsistencyEach transaction takes the database from one valid state to anotherA balance goes negative, an order points at a deleted customer, two users share one emailConstraints (PRIMARY KEY, UNIQUE, FOREIGN KEY, CHECK, NOT NULL) plus the application's own rules
IsolationConcurrent transactions do not see each other's half-finished workTwo buyers both get the last seat; a report adds up one half of a transferLocks, MVCC snapshots, conflict detection at commit
DurabilityAfter COMMIT returns, the data survives a crash or power lossAn order the customer was told is confirmed vanishes after a restartCommit record fsynced to the write-ahead log; replication and backups for lost machines
Atomicity, isolation and durability are things the database does for you. Consistency is a shared job: the database enforces the rules you declare, and your code must keep the rest.

The C is the odd one out. The database cannot know that "total money must stay constant" unless you express it as a constraint or write the transaction correctly. And it is unrelated to the C in the CAP theorem, which is about replicas agreeing (see Consistency models & the CAP theorem).

A transaction moves through a small set of states. The interesting rule: a transaction is committed only when its commit record is durable, not when your code reaches the last statement.

stateDiagram-v2
  [*] --> Active : BEGIN
  Active --> PartiallyCommitted : last statement done
  PartiallyCommitted --> Committed : commit record flushed
  Active --> Failed : error or crash
  PartiallyCommitted --> Failed : flush fails
  Failed --> Aborted : rolled back
  Committed --> [*]
  Aborted --> [*]
Two exits only. Everything that goes wrong funnels into Aborted, and the log is what makes the rollback possible.

A transfer as one transaction

The balance >= amount test lives in the UPDATE itself, so the check and the write cannot be separated by another transaction. Raising inside the block rolls everything back.

import psycopg

def transfer(conn: psycopg.Connection, src: int, dst: int, amount: int) -> None:
    # BEGIN ... COMMIT; any exception inside the block triggers ROLLBACK
    with conn.transaction():
        cur = conn.execute(
            "UPDATE accounts SET balance = balance - %s WHERE id = %s AND balance >= %s",
            (amount, src, amount),
        )
        if cur.rowcount != 1:                       # unknown account or insufficient funds
            raise ValueError("cannot debit")        # raising rolls the whole transaction back
        conn.execute("UPDATE accounts SET balance = balance + %s WHERE id = %s", (amount, dst))
BEGIN;
UPDATE accounts SET balance = balance - 30 WHERE id = 1 AND balance >= 30;
UPDATE accounts SET balance = balance + 30 WHERE id = 2;
COMMIT;          -- or ROLLBACK; to discard both updates

Pitfalls that catch people in practice

Holding a transaction open across slow work

Calling a remote API or waiting for user input inside a transaction keeps its locks (or its snapshot) alive for seconds. Other writers queue up, and in MVCC databases old row versions cannot be cleaned up. Keep transactions short and do the slow work before BEGIN.

Assuming SELECT-then-UPDATE is safe

Reading a value, deciding in Python, and writing back is a check-then-act race. Make the check part of the write (WHERE balance >= 30), lock the row (FOR UPDATE), or use a version column. The write-anomaly section below shows each.

Not retrying

Serialization failures (SQLSTATE 40001) and deadlock victims (40P01 in PostgreSQL) are normal at higher isolation levels. The right response is to rerun the whole transaction from BEGIN, with a small randomised backoff. That makes idempotent transaction bodies a design requirement.

Driver autocommit surprises

In psycopg 3, leaving a with psycopg.connect(...) block commits and closes the connection. In sqlite3 and psycopg2, with conn: commits or rolls back but leaves the connection open. DDL is transactional in PostgreSQL but commits implicitly in MySQL.

Partial failure inside a transaction

In PostgreSQL an error aborts the whole transaction: every later statement fails until you ROLLBACK. If you want to recover from one failing statement, wrap it in a SAVEPOINT and ROLLBACK TO it.

Write-ahead logging and crash recovery

Changing a data page in place on disk is slow (random I/O) and not atomic (a crash can leave half a page written). Databases therefore obey the write-ahead rule: describe every change in the WAL (write-ahead log, an append-only file) and flush that description to disk before the change itself may reach the data files. Two consequences make ACID affordable:

  • Commit is one sequential write. A transaction is committed when its commit record is safely in the log (fsync has returned). Dirty data pages are written later, in any order (the no-force policy).
  • Pages may reach disk early. To free memory, the buffer manager may flush a page that holds uncommitted changes (the steal policy). That is safe only because the log holds the old value needed to undo it.

Crash recovery then has three passes, in the order known from the ARIES algorithm: analysis (what was active?), redo (repeat history so the pages match the log), undo (roll back every transaction with no commit record).

flowchart TD
  U["UPDATE / INSERT / DELETE"] --> L["Append log record<br/>old and new value"]
  L --> P["Change page in memory"]
  P --> C{"COMMIT?"}
  C -->|yes| F["Append commit record<br/>and fsync the WAL"]
  F --> K["Tell the client: committed"]
  K -.-> D["Later: write dirty pages<br/>to disk at a checkpoint"]
  X(["Crash"]) --> A["1. Analysis<br/>who was active?"]
  A --> R["2. Redo<br/>replay the log forward"]
  R --> N["3. Undo<br/>roll back uncommitted work"]
  N --> O(["Open for traffic"])
The top chain is normal operation; the bottom chain runs only after a crash. The log is the single source of truth both times.

What an fsync costs per commit

Each durable commit waits for the WAL to reach stable storage. Group commit lets many transactions that are committing at the same moment share one fsync. Latencies are order-of-magnitude: local NVMe is well under 1 ms, network-attached cloud disks are 1-5 ms.

Engines differ in detail. PostgreSQL recovery is redo only: old row versions stay in the table, and a transaction with no commit record is simply treated as aborted. InnoDB keeps a redo log and undo logs (the undo log also serves MVCC reads). Both let you trade durability for speed: PostgreSQL synchronous_commit = off and InnoDB innodb_flush_log_at_trx_commit = 2 can lose the last moments of commits in a crash, but never corrupt the database.

Isolation levels and the read anomalies

▶ Video lesson: Isolation levels and the read anomalies 4:07 · 8 scenes · narrated, pause anytime and explore

Running transactions strictly one after another would be perfectly safe and painfully slow. Isolation levels let you choose how much interleaving to allow. Each level is defined by the anomalies it still permits:

  • Dirty read: you read a value another transaction wrote but has not committed (it may roll back).
  • Non-repeatable read: you read the same row twice and get different values, because someone committed in between.
  • Phantom read: you run the same range query twice and get different rows, because someone inserted or deleted a matching row.

Write anomalies: lost update and write skew

▶ Video lesson: Lost update and write skew 4:05 · 7 scenes · narrated, pause anytime and explore

The 1992 SQL standard stops at phantoms, but two more anomalies cause most real bugs. Both involve a transaction deciding from a read and then writing.

  • Lost update: two transactions read a value, each computes a new one, and the later write silently overwrites the earlier one.
  • Write skew: two transactions read overlapping data, then write different rows, and the combination breaks a rule that each transaction checked. Snapshot isolation does not catch it, because no row was written twice.

Lost update and write skew, with their fixes

Pick a scenario. In the lost-update runs, watch the stock row. In the write-skew runs, watch how many doctors remain on call.

Four fixes for a lost update

Read in one statement, compute in Python, write in another. Any transaction can slip in between.

def buy_naive(conn, item_id: int) -> None:
    with conn.transaction():
        (stock,) = conn.execute("SELECT stock FROM items WHERE id = %s", (item_id,)).fetchone()
        if stock < 1:
            raise RuntimeError("sold out")
        conn.execute("UPDATE items SET stock = %s WHERE id = %s", (stock - 1, item_id))   # blind overwrite

Best when the change is a formula. The database applies it to the latest committed row, and rowcount tells you whether the check passed.

def buy_atomic(conn, item_id: int) -> None:
    with conn.transaction():
        cur = conn.execute("UPDATE items SET stock = stock - 1 WHERE id = %s AND stock >= 1", (item_id,))
        if cur.rowcount != 1:
            raise RuntimeError("sold out")

Best when you must read the row, run real logic, then write. Concurrent transactions queue on the lock. Lock rows in a consistent order to avoid deadlocks.

def buy_locked(conn, item_id: int) -> None:
    with conn.transaction():
        (stock,) = conn.execute("SELECT stock FROM items WHERE id = %s FOR UPDATE", (item_id,)).fetchone()
        if stock < 1:
            raise RuntimeError("sold out")
        conn.execute("UPDATE items SET stock = %s WHERE id = %s", (stock - 1, item_id))

No lock is held while the user thinks. The save succeeds only if nobody changed the row since it was loaded; otherwise reload, merge and try again.

def save_title(conn, doc_id: int, new_title: str, expected_version: int) -> bool:
    cur = conn.execute(
        "UPDATE docs SET title = %s, version = version + 1 WHERE id = %s AND version = %s",
        (new_title, doc_id, expected_version),
    )
    conn.commit()
    return cur.rowcount == 1        # False: someone saved first, so reload and retry

Write skew is the anomaly interviewers use to separate 'I know the four levels' from 'I understand them'. The honest answer: raise the level to SERIALIZABLE and retry on 40001; or make the rule a database constraint; or lock the rows the decision depends on (SELECT ... FOR UPDATE on both doctors' rows turns the race into a queue).

Locking versus MVCC

Databases enforce isolation in two main ways, and most modern engines mix them.

Two-phase locking (2PL). A transaction takes a shared (S) lock to read and an exclusive (X) lock to write. It acquires locks as it goes (the growing phase) and, in strict 2PL, releases them all only at commit or abort. S is compatible with S, and everything else conflicts, so readers block writers and writers block readers.

sequenceDiagram
  participant T1
  participant LM as Lock manager
  participant T2
  T1->>LM: lock S on row x
  LM-->>T1: granted
  T2->>LM: lock X on row x
  LM-->>T2: wait, T1 holds S
  T1->>LM: COMMIT and release locks
  LM-->>T2: granted X
  T2->>LM: UPDATE x then COMMIT
Strict 2PL: T2's write waits for T1's read lock, which is held until T1 ends.

MVCC (multi-version concurrency control). Instead of overwriting a row, a write creates a new version tagged with the writing transaction. Each reader is given a snapshot, a rule for which versions count as visible (those committed before the snapshot was taken, plus the reader's own writes). Readers never wait for writers.

flowchart LR
  V1["Version 1<br/>x = 100<br/>txn 10"]
  V2["Version 2<br/>x = 80<br/>txn 20"]
  V3["Version 3<br/>x = 60<br/>txn 30, not committed"]
  V1 -->|superseded by| V2
  V2 -->|superseded by| V3
  RA(["Reader A<br/>snapshot after txn 10"]) -.->|sees| V1
  RB(["Reader B<br/>snapshot after txn 20"]) -.->|sees| V2
  W(["Writer txn 30"]) -.->|sees its own write| V3
One logical row, three physical versions. Which one you read depends on your snapshot, not on who is writing right now.
Locking (strict 2PL)MVCC (snapshots)
Reader vs writerReaders block writers and writers block readersNeither blocks the other: readers use an old version
Writer vs writerThe second writer waits for the lockThe second writer waits (or aborts on conflict) for the same row
What a read seesThe latest committed data, held stable by locksA consistent snapshot as of statement or transaction start

Weak spotA long report stalls every updateSnapshot isolation allows write skew unless you add SERIALIZABLE or locks
Most production engines are MVCC for reads and use row locks for writers, which is why both columns apply to them.

Deadlocks

A deadlock is a cycle of transactions that each hold a lock another one needs. Nothing can proceed, so the database must break the cycle by choosing a victim and aborting it. The classic recipe is two transfers running in opposite directions, each locking the source account first.

flowchart LR
  RowA[("Row A")] -->|locked by| T1((T1))
  RowB[("Row B")] -->|locked by| T2((T2))
  T1 -.->|wants| RowB
  T2 -.->|wants| RowA
Follow the arrows: T1 waits for T2, T2 waits for T1. A cycle in this wait-for graph is a deadlock.

Deadlocks are a normal event in any system with concurrent writers, not a bug to eliminate completely. Three habits keep them rare and harmless:

  • Lock in a consistent order. Always lock the lower account id first, whatever the transfer direction.
  • Keep transactions short and touch as few rows as possible.
  • Retry. The victim receives an error (40P01 in PostgreSQL, error 1213 in MySQL); rerun the transaction.

Ordered locking plus retry

import random
import time
from psycopg import errors

RETRYABLE = (errors.DeadlockDetected, errors.SerializationFailure)

def transfer_safely(conn, src: int, dst: int, amount: int, attempts: int = 5) -> None:
    first, second = sorted((src, dst))                   # same order for every caller
    for attempt in range(attempts):
        try:
            with conn.transaction():
                conn.execute("SELECT id FROM accounts WHERE id IN (%s, %s) ORDER BY id FOR UPDATE", (first, second))
                conn.execute("UPDATE accounts SET balance = balance - %s WHERE id = %s", (amount, src))
                conn.execute("UPDATE accounts SET balance = balance + %s WHERE id = %s", (amount, dst))
            return
        except RETRYABLE:
            if attempt == attempts - 1:
                raise
            time.sleep(random.uniform(0, 0.05 * 2 ** attempt))   # jittered backoff
Ordered FOR UPDATE removes the opposite-order cycle; the retry loop handles whatever conflicts remain.

Transactions across services: two-phase commit and sagas

Everything so far assumed one database. When an operation spans two databases or two services (create the order, charge the card, reserve stock), a local transaction cannot cover it. The textbook answer is two-phase commit (2PC): a coordinator asks every participant to prepare (do the work, make it durable, promise to be able to commit), and only if all vote yes does it tell them to commit.

sequenceDiagram
  participant C as Coordinator
  participant O as Orders DB
  participant P as Payments DB
  C->>O: PREPARE
  C->>P: PREPARE
  O-->>C: vote YES, logged as prepared
  P-->>C: vote YES, logged as prepared
  C->>C: write COMMIT decision to its log
  C->>O: COMMIT
  C->>P: COMMIT
  O-->>C: ack
  P-->>C: ack
Phase 1 collects promises; phase 2 delivers the decision. The coordinator's log write is the real commit point.

2PC is correct and expensive. If the coordinator crashes after participants voted yes but before they learn the decision, they must keep their locks and wait (the blocking problem). It also needs every participant to be up, two round trips, and several fsyncs. Inside one trusted system (XA transactions, Spanner's commits across shards) that cost is acceptable. Across independently owned microservices it usually is not.

A saga replaces one big atomic transaction with a sequence of local transactions, each committed immediately. If a later step fails, the saga runs compensating actions for the steps that already succeeded (refund the card, release the stock). An orchestrator (or events between services) drives the sequence.

sequenceDiagram
  participant O as Orchestrator
  participant P as Payments
  participant I as Inventory
  participant S as Shipping
  O->>P: charge card
  P-->>O: ok
  O->>I: reserve stock
  I-->>O: ok
  O->>S: create shipment
  S-->>O: failed
  O->>I: release stock, compensating
  O->>P: refund card, compensating
No global lock and no global rollback: each step commits, and failure triggers explicit undo actions in reverse order.
Two-phase commitSaga
AtomicityAll participants commit or none doEach step commits locally; failure triggers compensating steps
IsolationPrepared rows stay locked until the decisionNone across steps: other requests can see intermediate state (use 'pending' statuses)
Failure modeCoordinator crash after prepare blocks participantsA compensation can fail too; steps need retries and idempotency
CostTwo round trips plus fsyncs; every participant must be upSteps run independently, works with queues and async calls
Use whenA few trusted databases under one operatorMicroservices with their own databases, calls to outside parties
Sagas give up isolation and instant atomicity in exchange for availability. Write each step and each compensation to be idempotent, and persist the saga's state.

To make 'write to my database and publish an event' atomic without 2PC, use the transactional outbox: insert the event row into an outbox table in the same local transaction as the business change, and let a relay publish it afterwards. Delivery is at-least-once, so consumers must be idempotent.

The interview angle: double booking

The usual form of the question is "two users book the last seat at the same time; how do you prevent a double booking?". It is a lost-update problem on a row, and the full walk-through is in Case study: movie ticket booking. The core move is to make claiming the seat a single atomic statement, so the database serialises the two attempts on that row.

Claim a seat atomically

def hold_seat(conn, show_id: int, seat_no: str, user_id: int) -> bool:
    with conn.transaction():
        cur = conn.execute(
            "UPDATE seats SET status = 'HELD', held_by = %s, held_until = now() + interval '5 minutes' "
            "WHERE show_id = %s AND seat_no = %s AND status = 'FREE'",
            (user_id, show_id, seat_no),
        )
        return cur.rowcount == 1          # 1: you got it, 0: someone else did
Two concurrent calls: the database makes one UPDATE wait for the other, re-checks status = 'FREE' on the committed row, and the loser updates zero rows.

A strong answer sounds like: 'I would never read availability and then write in a second step. I make the claim atomic: an UPDATE with WHERE status = FREE and a check on the row count, so exactly one transaction wins and the other sees zero rows. For a multi-seat booking I wrap everything in one transaction, lock the seat rows in a fixed order with FOR UPDATE to avoid deadlocks, and retry on serialization errors. A UNIQUE constraint on (show, seat) in the bookings table is the last line of defence. Seats held but never paid for expire through a held_until timestamp.'
