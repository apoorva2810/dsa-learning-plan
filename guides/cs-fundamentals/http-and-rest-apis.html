HTTP & REST APIs

Almost every interview design ends with 'and the client calls an API'. This chapter takes an HTTP message apart byte by byte, explains safe and idempotent methods and why retries need idempotency keys, gives the status codes, headers and caching rules that matter, sets out REST resource-design rules with good and bad examples, and covers pagination, versioning, error bodies, authentication (sessions, JWT, OAuth 2) and the differences between HTTP/1.1, HTTP/2 and HTTP/3 and between REST, GraphQL and gRPC.

After this chapter you can
  • Read and write an HTTP request and response, naming each part and the header that governs it
  • Classify methods as safe and idempotent, and make a POST safe to retry with an idempotency key
  • Pick the right status code for common situations (401 vs 403, 400 vs 422, 409 vs 412, 502 vs 503 vs 504)
  • Design resource URLs, pagination, versioning and error bodies that other teams can use without asking you questions
  • Explain sessions versus JWT and walk through the OAuth 2.0 authorisation-code flow with PKCE
  • Use ETags and Cache-Control correctly, and say what HTTP/2 and HTTP/3 change

Anatomy of a request and response

▶ Video lesson: An HTTP message, byte by byte 4:00 · 6 scenes · narrated, pause anytime and explore

HTTP is a request-response protocol. A client sends a request over a connection (TCP, as in TCP/IP essentials, or QUIC for HTTP/3); the server sends back exactly one response. It is stateless: the server keeps no memory of the previous request on that connection, so anything it must know (who you are, which cart) is either sent again with each request or looked up by an identifier the request carries. That is what lets any server behind a load balancer answer any request.

What the interviewer is checking: do you know HTTP is just text (or frames) with a fixed shape, and that semantics live in the method, the status code and the headers, not in the URL alone? A good habit when designing an API is to write the request and response as raw HTTP on the whiteboard.

Methods, safety and idempotency

▶ Video lesson: Why retries need an idempotency key 4:12 · 7 scenes · narrated, pause anytime and explore

Two properties of a method decide how clients, caches and proxies may treat it:

  • Safe means the request is read-only: it does not ask the server to change anything. Caches and crawlers may call it freely.
  • Idempotent means that sending the request n times leaves the server in the same state as sending it once. Clients and proxies may therefore retry an idempotent request after a timeout without asking anyone.
MethodSafeIdempotentBodyTypical use
GETyesyesnoread a resource or a collection
HEADyesyesnoheaders only: existence, size, ETag
OPTIONSyesyesnowhich methods are allowed; CORS preflight
PUTnoyesyesreplace a resource at a URL the client knows
DELETEnoyesrarelyremove a resource (a second DELETE ends in the same state)
PATCHnonot guaranteedyespartial update
POSTnonoyescreate a subordinate resource or trigger an action
'Idempotent' is about the server's state, not the response: the second DELETE may return 404 instead of 204.

POST is the awkward one, and it is the method used for orders and payments. The classic failure is a response lost in the network: the server did the work, the client timed out, and a retry does the work again.

A lost response and a retry: with and without an idempotency key

The first attempt succeeds on the server but the client never hears about it. Compare what a retry does in each run.

Server side: record the key and the response in the same transaction

import hashlib
import json
from psycopg.types.json import Jsonb

def create_order(conn, idem_key: str, payload: dict) -> tuple[int, dict]:
    body_hash = hashlib.sha256(json.dumps(payload, sort_keys=True).encode()).hexdigest()
    with conn.transaction():
        claimed = conn.execute(
            "INSERT INTO idempotency_keys (key, body_hash) VALUES (%s, %s) ON CONFLICT (key) DO NOTHING",
            (idem_key, body_hash),
        ).rowcount
        if not claimed:    # seen before; a concurrent twin blocks on the unique index until the first commits
            saved_hash, status, response = conn.execute(
                "SELECT body_hash, status_code, response FROM idempotency_keys WHERE key = %s", (idem_key,)
            ).fetchone()
            if saved_hash != body_hash:
                return 422, {"detail": "this Idempotency-Key was used with a different request"}
            return status, response                      # replay the original answer
        order_id = conn.execute(
            "INSERT INTO orders (item_id, quantity) VALUES (%s, %s) RETURNING id",
            (payload["item_id"], payload["quantity"]),
        ).fetchone()[0]
        response = {"id": order_id, **payload, "status": "pending"}
        conn.execute("UPDATE idempotency_keys SET status_code = 201, response = %s WHERE key = %s",
                     (Jsonb(response), idem_key))
        return 201, response
The unique index on key makes the database the referee. Expire old keys after a day or so. Stripe and most payment APIs work this way; an IETF draft standardises the Idempotency-Key header.

A strong answer to 'how do you make a payment API safe to retry?': 'The client generates a UUID per logical operation and sends it as an Idempotency-Key header, reusing it on every retry. The server inserts the key with a unique constraint in the same transaction as the payment and stores the response. A repeat finds the key and replays the stored response instead of charging again; the same key with a different body is rejected with 422. The client retries only on timeouts, 429 and 5xx, with exponential backoff and jitter.'

Status codes and headers that matter

The status code is the machine-readable verdict. Clients branch on its class: 2xx succeeded, 3xx look elsewhere, 4xx the caller's fault (do not retry unchanged), 5xx the server's fault (retry may help). Use the narrowest accurate code; do not return 200 with an error in the body.

200OKsuccess with a body (GET, PUT, PATCH)
201CreatedPOST created a resource; include a Location header with its URL

204No Contentsuccess and nothing to return (DELETE, some PUTs)

302 / 307Found / Temporary Redirecttemporary move (307 keeps the method)

Retry rule of thumb: network errors, 429, 502, 503, 504 are worth retrying (with backoff and only if the method is idempotent or carries an idempotency key). Other 4xx never succeed unchanged.

Pairs that get confused

401 vs 403

401: who are you? The request lacks valid credentials, and logging in might fix it. 403: I know who you are, and no. Retrying with the same credentials will never work.

400 vs 422

400 is for requests the server cannot parse or understand structurally. 422 is for well-formed requests that fail semantic validation (a negative quantity, an end date before the start date). Many teams use 400 for both; pick one convention and document it.

409 vs 412

409 reports a conflict with the resource's current state (the username is taken). 412 reports that a precondition the client set with a header (If-Match: "v7") no longer holds. 412 is the answer to optimistic concurrency.

502 vs 503 vs 504

502: the proxy reached the upstream and got garbage or a refused connection. 503: the service itself says it cannot serve now (overload, maintenance), ideally with Retry-After. 504: the proxy waited for the upstream and ran out of time.

301/302 vs 307/308

Browsers historically turned a redirected POST into a GET for 301 and 302. 307 and 308 were added so the method and body are preserved. Use 308/307 for API redirects.

Designing REST resources

REST designs an API around resources (things with an identity) rather than operations. A resource has a URL, clients manipulate it through a representation (usually JSON), and the HTTP method says what to do. Rules that keep an API predictable:

  • Nouns, plural, lower case: /orders, /orders/42, /users/7/orders. The method is the verb.
  • Collection and item: GET /orders lists, POST /orders creates, GET /orders/42 reads, PUT or PATCH updates, DELETE removes.
  • Nest at most two levels, to express ownership. Every resource should also be reachable by its own id.
  • Filter, sort and page with query parameters: /orders?status=open&sort=-created_at&limit=20.
  • Return the right status and the created or updated representation. Use Location after a 201.
  • Model actions as sub-resources or state changes when a CRUD verb does not fit: POST /orders/42/cancellation or PATCH /orders/42 with {"status": "cancelled"}.
  • Be consistent: one naming style (snake_case or camelCase) and one error format everywhere.

Nouns, not verbs

Verbs in the URL

Every operation invents its own name, and GET /deleteOrder can be triggered by a crawler or a link prefetcher.

Resources and methods

Clients already know the pattern, and caches and proxies understand the methods.

Plural collections, filters in the query string

A path per question

Singular and plural are mixed, and every filter or sort order needs its own endpoint to build, document and cache.

One collection, parameters narrow it

The collection is always plural, filters and sorting compose, and a - prefix means descending.

GET /orders/42

Shallow nesting

Deep paths

The client must know the whole ancestry just to read one review, and every parent id becomes part of the cache key.

GET /customers/7/orders/9/items/3/reviews/5

Own ids, nest for ownership

A review has a globally unique id. Nesting is used to list or create inside a parent.

GET /reviews/5
GET /orders/9/items
POST /items/3/reviews

200 for everything

Monitoring, retries, caches and client libraries all believe the call succeeded.

Generic HTTP software can act on the status; people and programs read the details.

What 'REST' formally requires

The constraints

Roy Fielding's dissertation lists: client-server separation, statelessness, cacheability, a uniform interface (identified resources, manipulation through representations, self-descriptive messages, and hypermedia as the engine of application state, HATEOAS), a layered system, and optional code on demand.

What most APIs actually are

Most 'REST APIs' are HTTP-and-JSON resource APIs without hypermedia links. That is fine and usually the right trade-off, but in an interview say 'resource-oriented HTTP API' if you are not returning links, and be ready to explain statelessness and cacheability, which you do get.

PUT vs PATCH vs POST

PUT replaces the whole resource and is idempotent: send the complete representation. PATCH sends only the changes (JSON Merge Patch, RFC 7396, or JSON Patch, RFC 6902); make it idempotent by sending absolute values, not increments. POST creates when the server chooses the id, or triggers an action.

Pagination, versioning and error bodies

Any endpoint that returns a list needs pagination from day one, because adding it later breaks clients. The two styles mirror the database trade-off from Indexing & query performance.

Offset versus cursor

Offset: ?limit=20&offset=100

Simple and lets users jump to page 6, but deep pages are slow (the database skips the first rows) and the list shifts when items are added: a record can appear on two pages or none.

GET /posts?limit=20&offset=100

{"data": [...], "total": 4812}

Cursor: ?limit=20&cursor=...

The cursor is an opaque token encoding the last item seen (for example its sort key and id). Stable under inserts and fast at any depth, but no jumping to page N.

GET /posts?limit=20&cursor=eyJ0IjoiMjAyNi0xMC0wMSIsImlkIjo5MDAxfQ

{"data": [...], "next_cursor": "eyJ0Ijoi...", "has_more": true}
Versioning strategyExampleGoodCostly
URI path/v1/ordersobvious, easy to route, test and cachethe URL of the same resource changes between versions
Media type headerAccept: application/vnd.shop.v2+jsonclean URLs, versions per resourcehidden, harder to try in a browser

No versions, evolve compatiblyadd fields, never remove or renamenothing to migrateneeds discipline and tolerant clients
Adding an optional field or a new endpoint is not a breaking change. Version only when you must remove or change behaviour, and announce retirement with Deprecation and Sunset headers.

Content-Type: application/problem+json

  "title": "Item is out of stock",

}
type is a stable identifier clients can switch on; title and detail are for people. Add extension members such as errors freely.

Authentication: sessions, JWT and OAuth 2

Authentication establishes who is calling; authorisation decides what they may do. HTTP is stateless, so each request has to carry proof of identity. The two common carriers are an opaque session id in a cookie and a self-contained signed token (usually a JWT) in the Authorization header.

Server-side session (cookie)Signed token (JWT)
What the client holdsan opaque random ida signed set of claims (user id, expiry, scopes)
Server statesession data in Redis or a databasenone: any server with the key can verify it
Revocationdelete the session: immediatehard: valid until it expires, unless you keep a deny-list; use short lifetimes
Size per requestsmalllarger header on every call
Natural fitbrowser applications on one domainAPIs, microservices, mobile clients, third-party access
Main risksCSRF (use SameSite, CSRF tokens), session fixationtoken theft, accepting alg: none, long-lived tokens
Cookies should be HttpOnly (not readable by scripts), Secure (HTTPS only) and SameSite=Lax or Strict. A JWT is signed, not encrypted: never put secrets in it.

When a user lets one application act on their behalf at another service ("sign in with Google", "let this app read my calendar"), the standard is OAuth 2.0, and the flow to know is the authorisation code flow with PKCE. The app never sees the user's password; it receives a short-lived access token limited to the scopes the user approved.

Two trips through the browser (front channel) and two direct server-to-server calls (back channel). The access token never passes through the browser URL.

JWT pitfalls

Always verify, never trust the header

Check the signature with a key you configured, pin the allowed algorithms, and reject alg: none. Validate exp, iss and aud; allow a few seconds of clock skew.

Logout and revocation

A stateless token cannot be recalled. Keep access tokens to minutes, rotate refresh tokens, and keep a small deny-list (or a per-user 'tokens valid after' timestamp) when instant revocation matters.

Where to store it in a browser

Cookies marked HttpOnly resist theft by injected scripts but need CSRF protection; localStorage is readable by any script on the page. For first-party web apps, server-side sessions are often simpler and safer.

Caching and conditional requests

Responses can be stored by the browser and by shared caches (CDNs, proxies) if headers allow it. Two ideas cover almost everything. Freshness: while a stored copy is fresh (max-age), reuse it with no request at all. Validation: once it is stale, ask the server whether it is still current by sending the validator you stored (If-None-Match: <ETag>); a 304 Not Modified reply with no body means "keep using it", which saves the transfer but not the round trip. The broader caching picture is in Caching.

sequenceDiagram
  participant B as Browser cache
  participant S as Server
  B->>S: GET /logo.png
  S-->>B: 200 OK with ETag v7 and Cache-Control max-age=60
  Note over B: for 60 s the copy is fresh and is reused with no request at all
  B->>S: GET /logo.png with If-None-Match v7
  S-->>B: 304 Not Modified, no body
  Note over B: reuse the stored copy, fresh for another 60 s
The second request still costs a round trip but carries no body. Within the freshness window it costs nothing.
Cache-Control directiveMeaning
max-age=Nfresh for N seconds in any cache
s-maxage=Nlike max-age, but for shared caches (CDN, proxy) only
no-cachemay be stored, but must be revalidated with the origin before every reuse
no-storenever store it (sensitive responses)

'no-cache' does not mean 'do not cache'; that is no-store. Add Vary: Accept-Encoding (or other request headers) when the response depends on them.

Validators have a second use: optimistic concurrency. A client that read version v7 of a document sends its edit with If-Match: "v7". If someone else saved in between, the ETag no longer matches and the server answers 412 Precondition Failed instead of overwriting. It is the HTTP form of the lost-update fix in ACID & transactions.

Putting it together in Python

Requests cross several components on the way in, and putting each concern at the cheapest place keeps handlers small. The gateway is covered in Load balancers, reverse proxies & API gateways, and rate limiting and retries in Reliability patterns.

A client that is safe to call: timeouts, backoff, one idempotency key per operation

import random
import time
import uuid

import requests

RETRYABLE_STATUS = {429, 502, 503, 504}

def create_order(session: requests.Session, base_url: str, token: str, payload: dict, attempts: int = 4) -> dict:
    key = str(uuid.uuid4())                       # one key for every attempt of this logical operation
    for attempt in range(attempts):
        try:
            resp = session.post(
                f"{base_url}/v1/orders",
                json=payload,
                headers={"Authorization": f"Bearer {token}", "Idempotency-Key": key},
                timeout=(3.05, 10),               # (connect, read) seconds; without a timeout requests waits forever
            )
        except (requests.ConnectionError, requests.Timeout):
            resp = None                           # outcome unknown: safe to retry because of the key
        if resp is not None and resp.status_code not in RETRYABLE_STATUS:
            resp.raise_for_status()               # other 4xx/5xx raise; a 2xx falls through
            return resp.json()
        if attempt == attempts - 1:
            raise RuntimeError("order service unavailable")
        delay = float(resp.headers.get("Retry-After", 0)) if resp is not None else 0.0     # seconds form; it can also be an HTTP date
        time.sleep(max(delay, random.uniform(0, 0.2 * 2 ** attempt)))   # exponential backoff with jitter

What retries cost the server

Retries repair transient failures, but they also multiply load exactly when the server is struggling. Raise the failure chance towards 1 to see a retry storm: every client sends all of its attempts.

A small FastAPI service following the rules

from fastapi import FastAPI, Header, HTTPException, Query, Response, status
from pydantic import BaseModel, Field

app = FastAPI()
ORDERS: dict[int, dict] = {}
SEEN: dict[str, dict] = {}                        # idempotency key -> stored response (use a database in real life)

class OrderIn(BaseModel):
    item_id: int
    quantity: int = Field(gt=0, le=10)             # violations become 422 automatically

@app.post("/v1/orders", status_code=status.HTTP_201_CREATED)
def create_order(body: OrderIn, response: Response, idempotency_key: str = Header(...)):
    if idempotency_key in SEEN:
        return SEEN[idempotency_key]               # replay the first answer
    order = {"id": len(ORDERS) + 1, **body.model_dump(), "status": "pending"}
    ORDERS[order["id"]] = order
    SEEN[idempotency_key] = order
    response.headers["Location"] = f"/v1/orders/{order['id']}"
    return order

@app.get("/v1/orders/{order_id}")
def get_order(order_id: int):
    if order_id not in ORDERS:
        raise HTTPException(status_code=404, detail="order not found")
    return ORDERS[order_id]

@app.get("/v1/orders")
def list_orders(limit: int = Query(20, ge=1, le=100), after: int = 0):      # keyset pagination on the id
    page = [o for o in ORDERS.values() if o["id"] > after][:limit]
    return {"data": page, "next_cursor": page[-1]["id"] if len(page) == limit else None}
FastAPI validates types and ranges for you and documents the API at /docs. Replace the dictionaries with a database and the unique-key insert shown earlier.

API design checklist

A strong answer to 'design an API for X' walks the same path every time: resources and their ids; URLs and methods for each use case; request and response shapes; status codes and one error format; pagination for every list; idempotency for anything that moves money or creates things; authentication and scopes; versioning and rate limits. Say each choice aloud with its reason, for example 'cursor pagination because the feed changes constantly'.
