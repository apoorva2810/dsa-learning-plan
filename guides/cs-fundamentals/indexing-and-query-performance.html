Indexing & query performance

An index is a second, sorted structure that turns an O(n) scan into a handful of page reads. This chapter builds a B+ tree step by step (search, range scan, insert and split), then covers clustered versus secondary indexes, composite index column order and the leftmost-prefix rule, covering, partial and inverted indexes, why the planner sometimes ignores an index, how to read EXPLAIN, and the N+1 and pagination traps. It ends with a checklist for a slow query.

After this chapter you can

  • Trace a B+ tree search, a range scan and an insert that splits a page
  • Choose between clustered, secondary, covering, partial and expression indexes
  • Apply the leftmost-prefix rule to decide the column order of a composite index
  • Read an EXPLAIN plan and say why the planner ignored an index
  • Fix an N+1 query and replace OFFSET pagination with keyset pagination

Why a full scan is O(n)

A table is stored as a heap: rows packed into fixed-size pages (8 KiB in PostgreSQL, 16 KiB in InnoDB), in the order they happened to arrive. The page is the unit of I/O; the database never reads half a page. With nothing else to go on, SELECT * FROM orders WHERE id = 38 must read every page and test every row, because any row might match. That is a full table scan, and its cost grows linearly with the table: O(n) page reads.

An index is a separate structure, kept sorted by the indexed column(s), that lets the database jump straight to the matching rows. Sorted order is the whole trick. Binary search over n sorted entries needs log2(n) steps, but disks read pages, not single entries. A B+ tree therefore packs hundreds of keys into each page, so one page read narrows the search by a factor of several hundred. The number of reads is the height of the tree: usually 3 or 4, even for hundreds of millions of rows.

Pages touched: full scan versus index lookup

Change the table size and watch the scan grow while the index height barely moves. Fan-out is how many key-and-pointer entries fit in one page after leaving room for inserts (the fill factor). Throughput of 1 GB/s is a fast sequential read from a local SSD.

What the interviewer is checking: do you see an index as a data structure with a cost, not magic? A quotable answer: 'Without an index the database reads every page of the table, which is O(n). A B+ tree on the column lets it read one page per level, typically three or four, so lookups are O(log n) with a very large base. The price is extra storage and slower writes, because every insert must also update the tree.'

The B+ tree

▶ Video lesson: Searching a B+ tree 4:07 · 7 scenes · narrated, pause anytime and explore

A B+ tree is a balanced, high-fan-out search tree in which every node is one disk page.

  • Internal pages hold sorted separator keys and child pointers. A page with k keys has k + 1 children; child i covers keys from separator i-1 up to (not including) separator i.
  • Leaf pages hold the actual index entries (the key plus a pointer to the row, or the row itself) in sorted order. Leaves are linked left to right, so a range scan follows the chain instead of climbing the tree again.
  • The tree is balanced: every leaf sits at the same depth and every page except the root is kept at least about half full. Height is therefore the logarithm of n to the base of the fan-out.
flowchart LR
  R["Root page<br/>1 page<br/>500 children"] --> M["Level 2<br/>500 pages<br/>500 children each"]
  M --> L["Leaf level<br/>250,000 pages<br/>about 500 entries each"]
  L --> T["Up to 125 million<br/>table rows"]
With about 500 keys per page, three levels index 125 million rows. The top two levels are only 501 pages, so they live in memory.

Inserts, splits and the cost of writes

▶ Video lesson: Inserts, splits and the write tax 4:08 · 7 scenes · narrated, pause anytime and explore

An insert is a search followed by a write. The database descends to the leaf where the key belongs and, if the leaf has room, adds the key in sorted position. If the leaf is full, the page splits into two half-full pages, and the first key of the new right page is promoted to the parent as a separator. If the parent is full it splits too, and so on up to the root. Only a split of the root adds a level, which is why the tree stays perfectly balanced.

Insert and split: leaf split, a cascade, and growing from empty

Pages hold at most 3 keys. A page that would hold a fourth key overflows and splits. The third scenario inserts ten ascending keys into an empty tree.

Sequential keys versus random keys

Where the new key lands matters. Ascending keys (auto-increment ids, timestamps, time-ordered identifiers such as UUIDv7 or ULID) always go into the right-most leaf: that page stays in memory and old pages are never touched again. Random keys (UUIDv4, hashes) land on a random leaf: each insert is a likely cache miss on a random page, pages split all over the tree, and the index ends up larger and sparser. InnoDB's documentation puts pages at about 15/16 full after sequential inserts and anywhere between 1/2 and 15/16 full after random ones. This is a common reason a table with a random UUID primary key slows down once its index outgrows memory.

Every index is a tax on writes

An insert adds an entry to the table and to every index. An update of an indexed column removes one entry and adds another. Each change is also written to the log. Reads get faster; writes get slower.

Write cost of adding indexes

An illustrative model: one table change plus one change per secondary index for every inserted row. Real costs depend on caching and batching, but the proportionality is real.

Index what your queries need, not every column. Look for unused indexes (PostgreSQL: pg_stat_user_indexes with idx_scan = 0; MySQL: the sys.schema_unused_indexes view) and drop them: they cost write throughput, memory and storage and return nothing.

Clustered, secondary and covering indexes

So far the leaf entries pointed at rows. Where the rows actually live decides what an index lookup costs.

  • A clustered index is the table: rows are stored in the leaves of a B+ tree ordered by the key, normally the primary key. There is at most one per table. InnoDB always works this way, and SQL Server calls it the clustered index.
  • A secondary index is a separate B+ tree whose leaves hold the indexed columns plus a locator for the row. In InnoDB the locator is the primary-key value, so a lookup walks the secondary tree and then the clustered tree. PostgreSQL has no clustered index (the table is an unordered heap) and its locator is a physical address (page and slot), so a lookup walks one tree and then fetches one heap page.
  • A covering index contains every column the query needs, so the database answers from the index alone and skips the second step. This is an index-only scan.

In PostgreSQL an index-only scan also needs the visibility map: pages not yet marked all-visible still need a heap visit, so VACUUM matters.

In InnoDB every secondary index carries a copy of the primary key, so a wide primary key (a 36-character UUID string) inflates every index on the table. Prefer a compact key such as a BIGINT or a 16-byte binary UUID.

Composite indexes and the leftmost prefix

▶ Video lesson: The leftmost-prefix rule 4:01 · 7 scenes · narrated, pause anytime and explore

A composite (multi-column) index sorts entries by the first column, then by the second within equal first values, and so on, like a phone book sorted by surname and then by first name. That ordering decides which queries can use it.

The leftmost-prefix rule: an index on (a, b, c) can seek using a; using a and b; or using a, b and c. It cannot seek using b or c alone, because entries with the same b are scattered through the whole index. Read the columns left to right: equality tests extend the prefix, the first range test can still bound the scan, and everything after it can only filter.

flowchart TD
  S(["Index on a, b, c<br/>take the next column, left to right"]) --> Q1{"Equality<br/>test on it?"}
  Q1 -->|yes| ADD["Add it to the seek prefix"]
  ADD --> MORE{"Any column<br/>left?"}
  MORE -->|yes| Q1
  MORE -->|no| ALL(["Whole key used for the seek"])
  Q1 -->|no| Q2{"Range test<br/>on it?"}
  Q2 -->|yes| RNG["Use it as the scan bound.<br/>Later columns only filter"]
  Q2 -->|no| STOP["Stop here.<br/>Later columns only filter"]
Walk the example WHERE a = 1 AND b > 5 AND c = 3 through the rule: the seek uses a and b, and c is only a filter.
Predicate on an index (country, city, age)How the index is used

PostgreSQL 18 and MySQL 8.0.13+ can skip-scan a missing leading column when it has few distinct values. Treat that as a bonus, not as a design.

Which predicates can narrow the scan?

The same 15-entry index for every scenario, sorted by (country, city, age). Green entries match, red entries were examined and rejected. Count the red ones: that is wasted work.

Choosing the column order

  1. Equality columns first, then the range or sort column last.
  2. Among equality columns, put first the one that appears in the most queries, since it serves the most prefixes. Selectivity is a tiebreaker, not the main rule.
  3. An index on (a, b) already serves WHERE a = ?, so a separate index on (a) is redundant.
  4. For ORDER BY ... LIMIT, end the index with the sort column so the database can read the first rows in order and stop.

Same columns, different order

INDEX (created_at, status)

For WHERE status = 'open' ORDER BY created_at DESC LIMIT 20 the database can walk the newest entries and test status on each. If 'open' is rare it reads thousands of entries to find 20.

CREATE INDEX idx_tickets_created_status ON tickets (created_at, status);

INDEX (status, created_at)

It seeks straight to status = 'open', reads the 20 newest entries (they are already in created_at order) and stops. No sort, no wasted entries.

CREATE INDEX idx_tickets_status_created ON tickets (status, created_at);

Partial, expression and covering indexes (PostgreSQL syntax)

-- partial: index only the rows you ever query; tiny and cheap to maintain
CREATE INDEX idx_orders_open ON orders (created_at) WHERE status = 'open';

-- expression: makes WHERE lower(email) = 'a@x.com' indexable (and enforces case-insensitive uniqueness)
CREATE UNIQUE INDEX idx_users_email_ci ON users (lower(email));

-- covering: answer the query from the index leaf alone
CREATE INDEX idx_users_email_incl ON users (email) INCLUDE (name);
MySQL 8.0.13+ supports functional indexes (an expression in parentheses) but has no partial indexes. For covering, add the extra column to the key instead of INCLUDE.

A full-text search needs a different shape. An inverted index maps every term to the list of documents that contain it (a posting list). Answering "fast AND index" means looking up two posting lists and intersecting them, which is cheap because both lists are sorted. A B+ tree on the whole text column cannot do this: it can match a prefix, never a word in the middle.

flowchart LR
  Q["Query: fast AND index"] --> T1["term: fast"]
  Q --> T2["term: index"]
  T1 --> D1["documents 3, 8, 21"]
  T2 --> D2["documents 3, 5, 21, 34"]
  D1 --> X["Intersect: documents 3 and 21"]
  D2 --> X
Each term has a sorted posting list; the answer is the intersection.

Selectivity, statistics and EXPLAIN

The query planner does not "use an index if one exists". It estimates the cost of each plan and picks the cheapest, using statistics the database collects (row counts, distinct values, most common values, histograms). The key input is selectivity: the fraction of rows a predicate matches. WHERE id = 38 matches one row in a million: highly selective. WHERE is_active = true may match 95% of the rows: barely selective.

An index lookup costs roughly one random page read per matching row. A full scan reads pages sequentially, which is far cheaper per page. Once a predicate matches more than a few percent of the rows, scanning wins, and a good planner correctly ignores the index.

Where an index stops paying off

A deliberately simple model: a scan costs one unit per page; an index scan costs random_page_cost units per matching row, never more than one visit per page. PostgreSQL's default random_page_cost is 4; on SSDs people set it near 1.1. Real planners add CPU costs and account for how well the index order matches the table order.

Why isn't my index used?

The predicate matches too many rows

Selectivity is low (a status column where 70% of rows are 'done'). Scanning is cheaper, and the planner is right. A partial index on the rare value (WHERE status = 'pending') is the usual cure.

A function or cast wraps the column

WHERE lower(email) = ?, WHERE DATE(created_at) = ?, WHERE id + 1 = ? compare computed values, which the plain index does not contain. Rewrite so the column stands alone (created_at >= ? AND created_at < ?), or create an expression index. A predicate the index can use directly is called sargable.

Type mismatch

Comparing a string column with a number (WHERE phone = 5551234 on a VARCHAR) forces the engine to convert every stored value, so the index cannot be used. Pass parameters with the column's type.

Leading wildcard

LIKE 'son%' can use a B+ tree (it is a range); LIKE '%son' cannot, because the sort order says nothing about the end of a string. Use a trigram or full-text index.

Wrong column order or a skipped column

The leftmost-prefix rule: an index on (country, city) does not help WHERE city = ?. Reorder the index or add a second one for the other access path.

OR across different columns, or negation

a = 1 OR b = 2 needs two indexes combined (a bitmap OR) or a scan; <> and NOT IN match most rows. Rewriting as UNION ALL of two indexable queries often helps.

Stale statistics or a tiny table

After a bulk load the planner may still believe the table is small. Run ANALYZE (PostgreSQL) or ANALYZE TABLE (MySQL). And for a table of a few pages, a scan really is faster.

Reading EXPLAIN

EXPLAIN shows the plan the optimiser chose; EXPLAIN ANALYZE runs the query and adds the real row counts and timings. A plan is a tree. Rows flow upward from the leaves, so read it from the innermost, most indented nodes outward. The two things to compare are estimated versus actual rows (a gap of 10x or more points to stale or misleading statistics) and where the time goes.

Foreign keys, N+1 queries and pagination

Index your foreign keys

PostgreSQL indexes the referenced primary key automatically but not the referencing column; InnoDB creates an index on a foreign-key column if you did not. Without one, WHERE customer_id = ?, joins from parent to child and the check that runs on DELETE FROM customers all scan the child table, and the delete holds locks while it does.

The N+1 query

Loading a list and then touching a related object in a loop sends one query for the list and one more per row. With ORMs it hides behind attribute access, so it is invisible in the code and obvious in the query log.

N+1 versus one query

1 + N queries

Each order.customer access lazily loads the customer: 51 queries for 50 orders.

orders = Order.objects.filter(status="open")[:50]      # 1 query
for order in orders:
    print(order.customer.name)                        # +1 query per order

Join or batch the related rows

select_related joins in SQL (1 query); prefetch_related fetches all related rows with one IN query (2 queries).

orders = Order.objects.filter(status="open").select_related("customer")[:50]    # 1 query, with a JOIN
for order in orders:
    print(order.customer.name)                                                  # no extra queries

Pagination: OFFSET versus keyset

OFFSET n makes the database produce the first n rows and throw them away, so page 5,000 does 5,000 pages of work and the results shift whenever rows are inserted. Keyset (also called seek or cursor) pagination remembers the last row of the previous page and asks for rows after it, which the index answers directly.

Page 5,000 of a feed

OFFSET: O(offset) work

Reads and discards 100,000 rows to return 20, and may skip or repeat rows if the table changes between requests.

SELECT id, title FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 100000;

Keyset: O(log n + 20)

The index on (created_at, id) seeks to the last row seen and reads 20 entries. The id breaks ties, so the order is total.

SELECT id, title FROM posts
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;

The trade-off: keyset pagination cannot jump to "page 500" or show a total page count, and it needs a unique sort key. For feeds and infinite scroll that is exactly what you want. An API usually hides the last-seen key in an opaque cursor token, as discussed in HTTP & REST APIs.

A slow-query checklist, and the interview angle

Slow query checklist

A strong answer to 'this query is slow, what do you do?' sounds like: 'I would not guess. I take the exact query and run EXPLAIN ANALYZE on realistic data, then compare estimated and actual rows and find the node that dominates. If it is a sequential scan with a selective filter I add an index whose columns are ordered equality first, then range or sort, and check the predicate is sargable. If the planner still scans, I look at statistics and selectivity. I also weigh the cost: each index slows writes, so I remove ones I am replacing. After the change I re-run EXPLAIN and compare timings.'
