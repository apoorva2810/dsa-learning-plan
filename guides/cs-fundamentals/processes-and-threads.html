Processes & threads

A process owns memory and files; a thread is a schedulable path of execution inside it. This chapter shows what the kernel keeps for each, how states and context switches work, how fork/exec create processes, how processes talk, and what the GIL means for choosing between threading, multiprocessing and asyncio in Python.

After this chapter you can
  • Draw a process's address space and say exactly what threads share and what each thread owns
  • Walk a process through its states and name the events that move it between them
  • Explain what a context switch saves, why a process switch costs more than a thread switch, and how to see switches in Python
  • Describe fork, exec and wait, copy-on-write, and why zombies and orphans happen
  • Explain what the GIL serialises, why I/O-bound threads still help, and pick threading, multiprocessing or asyncio for a workload

What the OS keeps for a process and for a thread

▶ Video lesson: What a process owns, what a thread owns 3:49 · 6 scenes · narrated, pause anytime and explore

A program is a file on disk: machine code plus initial data. A process is a program in execution. The kernel gives it a private virtual address space, a table of open files, an identity (process ID, user) and at least one thread. A thread is one path of execution inside a process, and it is the unit the scheduler puts on a CPU.

The distinction interviewers care about is ownership. The process owns the resources: memory, files, sockets, signal handlers. A thread owns only what it needs to be at a different point in the program: a program counter, registers and a stack. Everything else it shares with its siblings.

Left: the usual layout of one process, high addresses at the top. Right: a second and third thread add stacks (blue) but share the heap, globals, code and libraries (green).

  Proc --> Files[Open files<br/>sockets, pipes]
  Proc --> Env[Identity and handlers<br/>user, cwd, signals]
  Proc --> T1[Thread 1<br/>stack, registers]
  Proc --> T2[Thread 2<br/>stack, registers]
  Proc --> T3[Thread 3<br/>stack, registers]
Ownership tree: the process holds the shared resources, each thread holds only its execution state.

The control blocks

The kernel tracks each process in a process control block (PCB; task_struct in Linux). Linux does not draw a hard line between processes and threads: both are tasks. A thread is a task created with clone() flags that share the address space, file table and signal handlers; a process is a task that shares none of them.

Reach for processes when

  • the work is CPU-bound Python and you want all cores
  • a crash or memory leak in one worker must not take down the others
  • you need to run untrusted or flaky code (plugins, converters)
  • you want to kill a stuck task for real (terminate()), which a thread cannot offer

Reach for threads when

  • the work is I/O-bound: HTTP calls, database queries, file reads
  • workers must share large in-memory data without copying it
  • tasks are tiny and start-up cost would dominate
  • you call C extensions that release the GIL (NumPy on big arrays, zlib, hashing)

Process vs thread, in 30 seconds. A process is an isolated instance of a program: its own virtual address space, file table and identity, so a crash or a bug stays inside it. A thread is a path of execution inside a process; it shares the heap, globals and open files with its siblings and owns only a stack and registers. Threads are cheaper to create and switch and share data for free, which is exactly why they need locks. Processes cost more but give isolation, and in Python they give real parallelism for CPU-bound work.

Process states

At any moment a process (more precisely, each of its threads) is in one of a few states. The scheduler only chooses among Ready tasks. A Waiting (blocked) task is skipped until the thing it waits for happens: a disk read finishes, a lock is released, a packet arrives, a timer expires.

stateDiagram-v2
  [*] --> New
  New --> Ready : admitted
  Ready --> Running : dispatched
  Running --> Ready : preempted
  Running --> Waiting : blocks on I/O or lock
  Waiting --> Ready : event done
  Running --> Terminated : exits
  Terminated --> [*]
Follow one process through a typical life: it runs, blocks on a read, gets the CPU back, is preempted once, then exits.

Load average

On Linux the load average is the average number of tasks in state R plus D. A load of 8 on an 8-core box means the CPUs are just busy; the same load with idle CPUs usually means many tasks stuck in D, i.e. a slow disk or a hung NFS mount.

Context switches: what they cost

▶ Video lesson: Context switches: what they really cost 4:03 · 7 scenes · narrated, pause anytime and explore

A context switch is the kernel stopping one task and starting another on the same CPU. It saves the outgoing task's registers, lets the scheduler pick the next one, and restores that task's registers. It is triggered by a timer interrupt (time slice used up), a blocking system call, a higher-priority task becoming ready, or an explicit yield.

There are two costs. The direct cost is the kernel work above, on the order of a microsecond or two. The indirect cost is what the CPU has to rebuild afterwards: the CPU caches hold the previous task's data, and after a process switch the TLB (the cache of address translations) holds translations for the wrong address space. The indirect cost is often larger than the direct one.

Context switch: thread to thread vs process to process

One CPU, two tasks. Step through a switch and compare what the kernel has to do when B is a thread of the same process and when B is a different process.

Put numbers on it with simple arithmetic: at about 1 µs per switch and 100,000 switches per second, a core spends 10% of its time switching, before counting cache misses. That is how a server with thousands of busy threads ends up slower than one with a few dozen: it is paying for switching instead of work.

In Python you can see the two kinds of switch your process incurs. A voluntary switch happens when the task blocks (I/O bound); an involuntary one when the kernel preempts it (CPU bound).

Counting context switches from Python

import resource
import time

def switches() -> tuple[int, int]:
    r = resource.getrusage(resource.RUSAGE_SELF)
    return r.ru_nvcsw, r.ru_nivcsw          # voluntary (blocked), involuntary (preempted)

before = switches()
for _ in range(20):
    time.sleep(0.01)                         # each sleep blocks: a voluntary switch
mid = switches()
end = time.perf_counter() + 1.0
while time.perf_counter() < end:             # burn CPU: never blocks, so only preemption can switch us out
    pass
after = switches()
print("blocking loop:", mid[0] - before[0], "voluntary,", mid[1] - before[1], "involuntary")
print("spinning loop:", after[0] - mid[0], "voluntary,", after[1] - mid[1], "involuntary")
vmstat 1 (column cs) and /proc/<pid>/status (voluntary_ctxt_switches, nonvoluntary_ctxt_switches) show the same counters system-wide and per process. A lone spinner on an idle core may see few involuntary switches; they climb when other tasks compete for the CPU.

Switching between asyncio tasks never enters the kernel: an await that suspends just returns control to the event loop inside one thread. That is why one event loop can juggle tens of thousands of waiting connections where tens of thousands of OS threads would drown in switches and stacks.

Creating processes: fork, exec and wait

On Unix a new process is created in two steps. fork() makes a near-identical copy of the calling process: it returns the child's PID in the parent and 0 in the child. exec() replaces the calling process's program with a different one: same PID, brand-new address space. A shell runs a command by forking, letting the child set up redirections and environment, and then calling exec. The parent calls wait() to sleep until the child exits and to collect its exit status.

Copying the whole address space on fork() would be wasteful, especially when exec throws it away a moment later. Kernels use copy-on-write: parent and child initially share the same physical pages, marked read-only, and a page is copied only when one of them writes to it.

sequenceDiagram
  participant Sh as Shell (parent)
  participant K as Kernel
  participant Ch as Child
  Sh->>K: fork()
  K-->>Sh: returns 5001 (child PID)
  K-->>Ch: returns 0 (copy starts here)
  Sh->>K: waitpid(5001)
  Ch->>K: execve("/bin/ls")
  K-->>Ch: new program image, same PID
  Ch->>K: exit(0)
  K-->>Sh: waitpid returns, child reaped
How a shell runs ls. The parent blocks in waitpid while the child execs and exits.

Copy-on-write after fork

Watch the page tables. Nothing is copied at fork(); each write to a shared page copies exactly one page.

fork, exec and wait in Python (POSIX only)

import os

pid = os.fork()
if pid == 0:                                  # child: fork returned 0
    os.execvp("ls", ["ls", "-l"])             # replaces the program; only returns on failure
    os._exit(127)                             # exec failed: leave without running parent's cleanup
else:                                         # parent: fork returned the child's PID
    _, status = os.waitpid(pid, 0)            # block until the child exits, then reap it
    print("child", pid, "exit code", os.waitstatus_to_exitcode(status))
In real code prefer subprocess.run, which does this safely (and uses posix_spawn or vfork where it can).

Python's multiprocessing start methods

fork, spawn, forkserver

multiprocessing can start workers three ways.

  • fork: the child is a copy of the parent. Fast, inherits everything, but unsafe in a program that already has threads: only the forking thread exists in the child, so a lock held by another thread at that moment stays locked forever.
  • spawn: start a fresh interpreter and import your main module. Slower, safe, and the reason for the if __name__ == "__main__": guard (without it every child would re-run your script and start more children). Arguments must be picklable.
  • forkserver: a clean helper process forks workers on request.

Defaults: Windows and macOS use spawn. Linux used fork through Python 3.13 and uses forkserver from 3.14. Pick explicitly with multiprocessing.get_context("spawn") if your code must behave the same everywhere.

Zombies and orphans

Two ways the parent/child relationship goes wrong, with opposite causes. A zombie is a child that has exited while the parent never called wait(): its memory is gone but its process-table entry (PID, exit status) stays. An orphan is a child still running after its parent exited; the kernel re-parents it to PID 1 (init or systemd) or to the nearest subreaper.

flowchart TD
  Exit[Child calls exit] --> Zombie[Zombie<br/>status kept, memory freed]
  Zombie --> Wait{Parent waits?}
  Wait -- yes --> Reaped[Reaped<br/>PID freed]
  Wait -- never --> Leak[Zombie lingers<br/>PID stays in use]
  PExit[Parent exits first] --> Orphan[Orphan<br/>child still running]
  Orphan --> Init[Adopted by init<br/>PID 1]
  Init --> Reaped
Zombie: the child finished first and nobody collected it. Orphan: the parent finished first and somebody else adopts the child.

Making a zombie on purpose

import os
import time

pid = os.fork()
if pid == 0:
    os._exit(0)             # child exits at once
print("child", pid, "has exited; parent has not waited")
time.sleep(60)              # in another terminal: ps -o pid,stat,comm -p <pid>   -> state Z
os.waitpid(pid, 0)          # reaping removes the zombie

How processes talk: IPC

Isolation means processes cannot just read each other's variables. They go through the kernel, which offers several inter-process communication (IPC) mechanisms. The choice is mostly about message shape, who may connect, and whether the data is copied.

Shared memory between two Python processes

from multiprocessing import Process, shared_memory

def worker(name: str) -> None:
    shm = shared_memory.SharedMemory(name=name)    # attach to the existing block
    shm.buf[0] = 42                                # visible to the creator at once: no copy, no pickling
    shm.close()

if __name__ == "__main__":
    shm = shared_memory.SharedMemory(create=True, size=1024)
    p = Process(target=worker, args=(shm.name,))
    p.start()
    p.join()
    print(shm.buf[0])                              # 42
    shm.close()
    shm.unlink()                                   # release the block exactly once
Two writers on the same bytes need a lock or semaphore, or you have a race condition across processes.

multiprocessing.Queue and Pool.map pickle every argument and result and push the bytes through a pipe. For small tasks that pickling tax can cost more than the computation. Send chunky work, send references (file paths, ids) instead of big objects, or share memory.

The GIL: what it serialises

▶ Video lesson: The GIL: what it really serialises 4:11 · 7 scenes · narrated, pause anytime and explore

CPython's global interpreter lock is a mutex that lets only one thread execute Python bytecode at a time within an interpreter. It exists because CPython manages memory with reference counts, which are plain integers inside every object. Two threads incrementing one count at once would corrupt it; a single lock makes that safe, keeps single-threaded code fast, and makes writing C extensions simpler.

What the GIL does and does not do:

  • It serialises bytecode execution. Two CPU-bound threads take turns, whatever the number of cores. The lock is handed over roughly every sys.getswitchinterval() = 5 ms when another thread is waiting.
  • It is released around blocking system calls: socket.recv, file.read, time.sleep, waiting on a lock. While one thread waits for the network, another can run Python. This is why I/O-bound threads help.
  • Many C extensions release it for long operations: NumPy on large arrays, zlib, hashlib on big buffers.
  • It does not make your code thread-safe. It makes each bytecode atomic, not your sequence of them.

Two tasks: threads (GIL) vs processes

The same two tasks in three settings. A tick is one 5 ms GIL switch interval. Watch the GIL holder lane for threads, and the fixed start-up cost for processes.

The GIL protects the interpreter, not your data. counter += 1 is a read, an add and a write; another thread can run between them and updates get lost. In a short test with four threads, a loop doing d['k'] = d.get('k', 0) + 1 200,000 times each ended near 435,000 instead of 800,000 on CPython 3.12. See Synchronisation & deadlocks for races and Concurrency & thread safety for the Python-side fixes.

Where the GIL is heading

Free-threaded builds (PEP 703)

CPython 3.13 added an optional free-threaded build without the GIL, and 3.14 lists it as officially supported (PEP 779). The default build still has the GIL. Extensions must opt in, and check at runtime with sys._is_gil_enabled() (3.13+). Free threading makes races like the one above more visible, not less.

Sub-interpreters

Since 3.12 each sub-interpreter can have its own GIL (PEP 684), and 3.14 adds the concurrent.interpreters module (PEP 734). They give multi-core parallelism inside one process, with isolated state like processes but cheaper start-up.

Why use threads in Python at all? Because most programs spend most of their time waiting, not computing. While a thread waits on the network or disk it has released the GIL, so other threads run. A pool of threads turns 100 sequential HTTP calls of 200 ms into roughly 20 ms-plus of waiting overlapped, while CPU-bound work needs processes (or native code) to scale across cores.

The same idea three ways

Blocking calls release the GIL, so the waits overlap.

from concurrent.futures import ThreadPoolExecutor
import urllib.request

def fetch(url: str) -> int:
    with urllib.request.urlopen(url, timeout=10) as resp:   # blocks in a syscall: GIL released
        return len(resp.read())

def fetch_all(urls: list[str]) -> list[int]:
    with ThreadPoolExecutor(max_workers=32) as pool:
        return list(pool.map(fetch, urls))

Each worker has its own interpreter and GIL. Keep tasks chunky and arguments small.

from concurrent.futures import ProcessPoolExecutor
import os

def work(n: int) -> int:
    return sum(i * i for i in range(n))              # pure-Python CPU work

if __name__ == "__main__":                           # required with spawn and forkserver
    jobs = [10_000_000] * 8
    with ProcessPoolExecutor(max_workers=os.cpu_count()) as pool:
        totals = list(pool.map(work, jobs))          # arguments and results are pickled

One thread; every await is a point where another task may run. Never call a blocking function inside a coroutine.

import asyncio
import time

async def fetch(i: int) -> int:
    await asyncio.sleep(1)               # stands in for a network call: yields to the loop
    return i

def blocking_report() -> str:
    time.sleep(1)                        # blocking: would freeze every task if called directly
    return "done"

async def main() -> None:
    results = await asyncio.gather(*(fetch(i) for i in range(1000)))   # about 1 s in total
    report = await asyncio.to_thread(blocking_report)                    # push blocking work to a thread
    print(len(results), report)

asyncio.run(main())

How many threads and processes does an I/O-bound Python service need?

Little's law gives the requests in flight: concurrency = arrival rate × time in system. Only the CPU part of each request holds the GIL, so one process can serve at most 1000 / cpu_ms requests per second however many threads it has.

User threads, kernel threads and interview prep

Kernel threads are known to and scheduled by the OS: they can run on different cores and a blocking system call blocks only the calling thread. User-level threads are managed by a runtime library inside one process; the kernel sees a single thread. Switching them needs no system call, but a blocking call can stall them all and they cannot use several cores unless the runtime multiplexes them over several kernel threads. The usual mappings:

Follow-up questions to rehearse

What happens to the other threads when a multithreaded process calls fork()?

Only the calling thread exists in the child. If another thread held a lock (or was inside malloc) at that moment, the child inherits the locked lock with nobody left to release it, and deadlocks. That is why you exec straight after fork in threaded programs, or use spawn.

Concurrency vs parallelism?

Concurrency is structuring a program as independently progressing tasks, possibly on one core by interleaving. Parallelism is executing tasks at the same instant on several cores. asyncio and GIL-bound threads give concurrency; processes give parallelism.

Can a process have no threads?

No. A process always has at least one thread (the main thread). Once its last thread has exited, only the zombie entry is left, waiting for the parent to reap it.

How does a thread get its own stack if the heap is shared?

At creation the runtime reserves a stack region (typically 8 MiB of address space on Linux, committed lazily page by page) plus a guard page. Variables local to a function live there; objects allocated with malloc, including all Python objects, live on the shared heap.

Why can't I kill a thread?

Because it shares memory with its siblings: stopping it at an arbitrary point could leave a lock held or a structure half-updated. Threads must be asked to stop (an Event). Processes can be terminated safely because the kernel cleans up the whole address space.

Self-check before an interview

Classic mistakes: saying threads share everything (stacks and registers are private); saying the GIL makes Python code thread-safe; recommending multiprocessing for an I/O-bound scraper; forgetting the __main__ guard; calling a blocking function inside a coroutine.
