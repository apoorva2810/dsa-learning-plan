Synchronisation & deadlocks

Threads and processes that share data need rules. This chapter shows a race condition you can watch happen, the tools that prevent it (mutexes, semaphores, condition variables, monitors), the producer-consumer and readers-writers problems, and then deadlock: the four conditions, detection with a wait-for graph, prevention with lock ordering, avoidance with the Banker's algorithm, plus livelock, starvation and priority inversion.

  • Solve producer-consumer with semaphores and with a condition variable, and say why the order of waits matters

  • Detect a deadlock by finding a cycle in a wait-for graph, and run the Banker's algorithm on a small example

Races and critical sections

▶ Video lesson: Races: watch an update get lost 3:58 · 7 scenes · narrated, pause anytime and explore

Threads share memory, so two of them can touch the same data at overlapping moments. A race condition is a bug where the result depends on the exact interleaving of their steps. The classic form is the lost update: counter += 1 looks like one step but is really three (load the value, add one, store it back). If two threads load the same old value, both store the same new one, and one increment vanishes.

The stretch of code that touches shared data is a critical section. Any solution that protects it must provide:

  • Mutual exclusion: at most one thread inside at a time.
  • Progress: if nobody is inside, a thread that wants in is not held up by threads that do not.
  • Bounded waiting: a waiting thread gets in after a limited number of others have gone first (no starvation).

Lost update: watch the interleaving

Two threads, counter += 1 each. Compare an unlucky interleaving, a lucky one (same code, right answer), and the same code under a mutex.

Races hide. In a test on CPython 3.12, four threads each doing counter += 1 a million times lost no updates in three runs: the interpreter only considers switching threads at certain points, so that short sequence is rarely split. Put a function call between the read and the write and the same four threads lost about 9% of the updates; the dict version d['k'] = d.get('k', 0) + 1 lost almost half. A test that passes is not evidence of safety. (Free-threaded builds, with no GIL, make such races easier to hit.) The Python-side fixes are in Concurrency & thread safety.

The bug and the fix

import threading

counter = 0
lock = threading.Lock()

def unsafe(n: int) -> None:
    global counter
    for _ in range(n):
        tmp = counter          # load
        tmp += 1               # add
        counter = tmp          # store: another thread may have stored since our load

def safe(n: int) -> None:
    global counter
    for _ in range(n):
        with lock:             # only one thread at a time runs the three steps
            counter += 1

threads = [threading.Thread(target=safe, args=(100_000,)) for _ in range(4)]
for th in threads:
    th.start()
for th in threads:
    th.join()
print(counter)                 # 400000 every time with the lock
with lock: releases the lock even if the body raises, which a bare acquire/release pair does not unless you use try/finally.

Mutex, semaphore, condition variable, monitor

All four are ways to make a thread wait without burning CPU, and they differ in what they model.

  • A mutex (lock) protects a critical section: lock, work, unlock. Exactly one holder.
  • A semaphore is a counter. acquire() (the classic wait or P) decrements it and blocks at zero; release() (signal or V) increments it and wakes a waiter. It counts how many units of something are available, and nobody owns it.
  • A condition variable lets a thread wait until a predicate about shared state becomes true (queue not empty, flag set). It is always used together with a lock: wait() atomically releases the lock and sleeps, and re-acquires the lock before returning.
  • A monitor is the structured form: data, the lock that protects it, and its condition variables bundled so that only one thread is inside at a time. Java's synchronized with wait/notify is a monitor. Python has no keyword for it, but a class with one Condition and with self._cond: in every method is one.

A binary semaphore is not the same as a mutex: a mutex has an owner and a semaphore does not. CPython's plain Lock is closer to a binary semaphore (any thread may release it); RLock enforces ownership.

The four in Python's threading module

One thread inside at a time.

import threading

balance = 100
lock = threading.Lock()

def withdraw(amount: int) -> bool:
    global balance
    with lock:                          # check-then-act must be one atomic unit
        if balance >= amount:
            balance -= amount
            return True
        return False

Allow at most N threads into a section, for example a connection pool.

import threading

pool = threading.BoundedSemaphore(5)     # at most 5 concurrent database calls

def query(sql: str):
    with pool:                           # acquire on entry, release on exit
        return run_query(sql)            # up to 5 threads here at once

Wait for a predicate. Always wait() inside a while loop that re-checks it.

import threading
from collections import deque

items: deque = deque()
cond = threading.Condition()

def consumer():
    with cond:
        while not items:                 # while, not if: re-check after every wake-up
            cond.wait()                  # releases the lock, sleeps, re-acquires on wake
        return items.popleft()

def producer(x):
    with cond:
        items.append(x)
        cond.notify()                    # wake one waiter

Data, lock and conditions in one object; every public method takes the lock.

import threading
from collections import deque

class BoundedBuffer:
    def __init__(self, capacity: int):
        self._items: deque = deque()
        self._capacity = capacity
        self._lock = threading.Lock()
        self._not_full = threading.Condition(self._lock)    # two conditions, one lock
        self._not_empty = threading.Condition(self._lock)

    def put(self, item) -> None:
        with self._not_full:
            while len(self._items) >= self._capacity:
                self._not_full.wait()
            self._items.append(item)
            self._not_empty.notify()

    def get(self):
        with self._not_empty:
            while not self._items:
                self._not_empty.wait()
            item = self._items.popleft()
            self._not_full.notify()
            return item

  C->>CV: wait() (queue empty)
  P->>L: acquire

  P->>L: release

  C->>C: re-check: is the queue still non-empty?
Why wait() releases the lock, and why you re-check the predicate in a while loop.

Locks cap your speed-up (Amdahl's law)

If every task spends a fraction s of its time inside one shared lock, that part runs serially. The speed-up with N threads is 1 ÷ (s + (1 − s) ÷ N) and can never exceed 1 ÷ s.

Keep critical sections short and do not call slow things (I/O, other locks, user callbacks) while holding a lock. The calculator above is the reason: with 20% of the work inside the lock, 16 threads give about 4x and no number of threads gives more than 5x.

Classic problems: producer-consumer and readers-writers

Producer-consumer (bounded buffer): producers add items to a buffer of fixed size, consumers remove them. Three things must hold: a producer must wait when the buffer is full, a consumer must wait when it is empty, and the buffer itself must not be corrupted by two threads at once. The textbook solution uses three guards:

  • empty: a semaphore counting free slots, starting at the capacity.
  • full: a semaphore counting filled slots, starting at 0.
  • mutex: protects the buffer structure.

Producer: wait(empty), wait(mutex), add, signal(mutex), signal(full). Consumer: wait(full), wait(mutex), remove, signal(mutex), signal(empty).

Producer and consumer with a bounded buffer

Two lanes, one shared buffer (queue view). Blocking appears as dashed boxes: the side that is faster ends up waiting for the slower one.

The order of the waits is the whole trick

Take the mutex first: deadlock

def producer(item):
    mutex.acquire()
    empty.acquire()          # blocks while holding the mutex ...
    buf.append(item)         # ... so the consumer can never get the
    mutex.release()          #     mutex to free a slot: deadlock
    full.release()

Wait for the slot first

def producer(item):
    empty.acquire()          # wait for a free slot; no lock held while waiting
    with mutex:
        buf.append(item)
    full.release()

In practice: let queue.Queue do it

import queue
import threading

buf: queue.Queue = queue.Queue(maxsize=3)      # put() blocks when full, get() blocks when empty

def producer() -> None:
    for item in range(10):
        buf.put(item)                          # the three guards are inside
    buf.put(None)                              # sentinel: tells the consumer to stop

def consumer() -> None:
    while (item := buf.get()) is not None:
        print("got", item)

threading.Thread(target=producer).start()
threading.Thread(target=consumer).start()
queue.Queue is a ready-made monitor. Prefer it to hand-rolled semaphores, and prefer message passing to shared state when you can.

Readers-writers: many threads read a structure, some write it. Readers can share; a writer needs exclusive access. The design question is who waits when both are present, and each answer starves someone:

VariantRuleWho can starveUse when
Readers preferencea reader enters unless a writer is currently writingwriters (a steady stream of readers never lets them in)reads dominate and stale writes are acceptable
Writers preferenceonce a writer is waiting, new readers waitreaderswrites must be seen quickly
Fair (FIFO)requests are served in arrival order, consecutive readers batchednobodythe default when you need guarantees; lower throughput
There is no free lunch: you choose which side may starve, or pay with throughput for fairness.

A readers-preference lock in Python

import threading

class ReadWriteLock:
    """Many readers or one writer. Readers-preference: writers can starve."""

    def __init__(self) -> None:
        self._readers = 0
        self._count_lock = threading.Lock()      # protects the reader count
        self._write_lock = threading.Lock()      # held by a writer, or by the whole group of readers

    def acquire_read(self) -> None:
        with self._count_lock:
            self._readers += 1
            if self._readers == 1:               # first reader locks writers out
                self._write_lock.acquire()

    def release_read(self) -> None:
        with self._count_lock:
            self._readers -= 1
            if self._readers == 0:               # last reader lets writers in
                self._write_lock.release()       # may be a different thread than the one that acquired: fine for threading.Lock

    def acquire_write(self) -> None:
        self._write_lock.acquire()

    def release_write(self) -> None:
        self._write_lock.release()
The standard library has no read-write lock. This works because threading.Lock, unlike a POSIX mutex, may be released by a thread other than the owner.

Deadlock: four conditions

▶ Video lesson: Deadlock: the four conditions 3:54 · 7 scenes · narrated, pause anytime and explore

A deadlock is a set of threads each waiting for something another one in the set holds, so none can ever proceed. The simplest recipe is two locks taken in opposite orders.

sequenceDiagram
  participant T1 as Thread 1
  participant LA as Lock A
  participant LB as Lock B
  participant T2 as Thread 2
  T1->>LA: acquire A (granted)
  T2->>LB: acquire B (granted)
  T1->>LB: acquire B (blocks, T2 holds it)
  T2->>LA: acquire A (blocks, T1 holds it)
Each thread holds what the other needs. Nothing times out, nothing is interrupted: the program just hangs with 0% CPU.

Edward Coffman showed in 1971 that deadlock needs all four of these at once. Break any one and deadlock is impossible, which is the basis of every prevention technique.

flowchart TD
  ME[Mutual exclusion<br/>a resource has one owner] --> DL{{All four at once:<br/>DEADLOCK}}
  HW[Hold and wait<br/>keep one, ask for more] --> DL
  NP[No preemption<br/>only the owner can release] --> DL
  CW[Circular wait<br/>a ring of waiters] --> DL
  F1[Share it: read-only data,<br/>lock-free structures] -.->|breaks| ME
  F2[Take all locks at once,<br/>or release before waiting] -.->|breaks| HW
  F3[trylock with timeout,<br/>back off and retry] -.->|breaks| NP
  F4[Global lock order] -.->|breaks| CW
The four conditions (top) and the standard way to break each (bottom). Lock ordering is the cheapest in application code.

All three are 'nothing gets done' with different symptoms: a hung process at 0% CPU, a busy one at 100%, or one unlucky client.

Detecting deadlock and recovering

▶ Video lesson: Detecting deadlock: find the cycle 4:04 · 6 scenes · narrated, pause anytime and explore

Instead of preventing deadlock, a system can let it happen and notice. With single-instance resources the check is a cycle search. Draw a resource-allocation graph: an edge from a resource to the process holding it, and from a process to the resource it is waiting for. Collapse the resources and you get a wait-for graph with an edge P to Q if P waits for something Q holds. A cycle in the wait-for graph is a deadlock. (With several identical units per resource a cycle is necessary but not sufficient; a matrix algorithm like the Banker's safety check decides.)

It is the same problem as cycle detection in a directed graph, which you have already solved in Course Schedule.

Building the graph and finding the cycle

Requests arrive one at a time. Top: the resource-allocation graph. Bottom: the wait-for graph derived from it. A cycle turns red.

Recovery means breaking the cycle by force:

  • Terminate all deadlocked processes (certain, expensive), or one at a time until the cycle disappears. Choose the victim by priority, work done, resources held and how often it has been picked before, or the same process is victimised forever (starvation).
  • Preempt a resource from one process and give it to another, rolling the victim back to a safe point.

Real examples: a database runs a deadlock detector on lock waits. PostgreSQL starts checking after deadlock_timeout (1 second by default) and aborts one transaction with error 40P01; the application must retry it. Operating systems and plain threading.Lock do not detect deadlocks in user code, which is why unbounded lock.acquire() calls are a latent hang. Use timeouts, and for a hung Python process dump every thread's stack (faulthandler.dump_traceback_later(30), or py-spy dump --pid PID) to see who waits for what.

Preventing and avoiding deadlock

Prevention removes one of the four conditions by design; avoidance lets all four be possible but refuses requests that could lead to deadlock. In application code the practical tools are lock ordering and timeouts.

Two practical defences

Give every lock a rank (an ID, an address) and always acquire in rank order. A cycle needs someone to take a lower-ranked lock while holding a higher one, which the rule forbids.

import threading

class Account:
    def __init__(self, account_id: int, balance: int):
        self.id = account_id
        self.balance = balance
        self.lock = threading.Lock()

def transfer(src: Account, dst: Account, amount: int) -> None:
    if src is dst:
        return                                              # a second acquire of the same plain Lock would hang
    first, second = sorted((src, dst), key=lambda a: a.id)  # always lock the lower id first
    with first.lock:
        with second.lock:
            src.balance -= amount
            dst.balance += amount

Break 'no preemption' by giving up. If the second lock is not available quickly, release the first, wait a random time and retry. The randomness avoids livelock.

import random
import threading
import time

def acquire_both(a: threading.Lock, b: threading.Lock) -> None:
    while True:
        a.acquire()
        if b.acquire(timeout=0.05):
            return                                    # got both
        a.release()                                    # give up what we hold ...
        time.sleep(random.uniform(0, 0.01))            # ... and retry at a random moment

Avoidance: the Banker's algorithm

Avoidance needs each process to declare its maximum claim up front. The OS keeps the system in a safe state: one where there is some order (a safe sequence) in which every process can get its remaining need, finish, and release everything. A request is granted only if the resulting state is still safe. An unsafe state does not mean deadlock has happened or will, only that the OS can no longer guarantee it will not.

flowchart TD
  S[Work starts as Available<br/>nobody is marked finished] --> F{Is there an unfinished process<br/>whose Need fits in Work?}
  F -- yes --> R[Pretend it finishes<br/>and returns its Allocation<br/>Work grows, mark it finished]
  R --> F
  F -- no --> C{Is everyone marked finished?}
  C -- yes --> Safe[SAFE<br/>the order found is a safe sequence]
  C -- no --> Unsafe[UNSAFE<br/>no guarantee that all can finish]
The safety algorithm. The Banker's algorithm = 'tentatively grant the request, run this test, roll back if it fails'.

Banker's is a teaching tool more than a production one: processes rarely know their maximum claims, the set of processes changes, and the check costs O(m × n²) per request for n processes and m resource types. Real systems prevent with lock ordering, detect with timeouts and graphs, or ignore the problem (the 'ostrich algorithm' of most general-purpose OSes) and leave it to applications.

Livelock, starvation and priority inversion

Livelock: two threads each see the other's lock, politely release and retry, in lock-step, forever. The CPU is busy, nothing completes. Two people stepping aside in the same direction in a corridor is the picture. Randomised back-off (above) breaks the symmetry.

Starvation: some thread never gets what it needs because others keep winning: a low-priority job under a stream of high-priority ones, a writer under readers-preference. Fair queues and aging fix it, as in the scheduling chapter.

Priority inversion: a low-priority task holds a lock that a high-priority task needs, and a medium-priority task keeps the low one off the CPU, so the high-priority task is effectively waiting behind a medium one. Mars Pathfinder kept resetting in 1997 for exactly this reason; the fix was enabling priority inheritance on the mutex.

sequenceDiagram
  participant L as Low priority
  participant K as Mutex
  participant H as High priority
  participant M as Medium priority
  L->>K: lock (granted)
  H->>H: becomes ready, preempts L
  H->>K: lock (blocks, L holds it)
  M->>M: becomes ready, runs instead of L
  M->>M: keeps running for a long time
  M-->>L: finally done, L runs again
  L->>K: unlock
  K-->>H: H finally gets the lock
High waits for Low, Low waits for the CPU, and Medium owns the CPU. A task that has nothing to do with the lock has delayed the most important one.

Spinlocks vs blocking locks

When a lock is taken, a waiter has two options. A spinlock busy-waits, repeatedly testing the lock with an atomic instruction (test-and-set or compare-and-swap) until it opens. A blocking lock (a mutex in the usual sense) puts the waiter to sleep and lets the OS wake it.

Spinning wastes the waiter's CPU time for as long as it waits, but costs no context switch. Sleeping wastes nothing while asleep, but costs about two context switches and a wake-up delay. So the rule is: spin only if the lock will be held for less time than a sleep-wake cycle, and only if the holder is running on another core right now. If the holder has been descheduled, a spinner burns its whole time slice waiting for a thread that cannot run; on a single core spinning is always wrong. Kernels spin in interrupt handlers (which are not allowed to sleep) with very short critical sections. Modern mutexes are adaptive: spin briefly, then sleep (Linux futex-based locks handle the uncontended case entirely in user space).

flowchart TD
  Q[Thread must wait for a lock] --> A{May the thread sleep here?<br/>No in interrupt handlers}
  A -- no --> Spin[Spinlock<br/>short critical section only]
  A -- yes --> B{Is the hold time tiny and the<br/>holder running on another core?}
  B -- yes --> Ad[Spin briefly, then sleep<br/>adaptive mutex]
  B -- no --> Blk[Blocking mutex<br/>sleep until woken]
Choosing how to wait. In Python application code the answer is nearly always the bottom right: a blocking Lock.

In CPython, spinning on a flag in pure Python is the worst of both worlds: the spinner holds the GIL for its whole switch interval while it waits for another thread that needs the GIL to release the flag. Use threading.Lock, Event or Condition, which sleep.

Interview prep

'Two threads deadlock. How do you diagnose and fix it?' Diagnose: the process hangs at near 0% CPU; take a thread dump (py-spy dump, faulthandler, jstack) and look for threads blocked in acquire that hold a lock another one wants. Name the four conditions. Fix: impose a global lock order so a cycle cannot form; if order cannot be known in advance, use acquire(timeout=...) with back-off; shorten critical sections and never call out to unknown code while holding a lock. Mention that databases detect deadlocks and abort a victim, so application code must retry.

Questions interviewers ask next

Mutex vs binary semaphore?

A mutex is for mutual exclusion and has an owner: the thread that locked it unlocks it, which enables priority inheritance and recursive locking. A binary semaphore is a signalling mechanism: one thread can signal and another wait, with no ownership. Using a semaphore as a lock works but loses owner checks and priority inheritance.

What is a spurious wakeup, and why the while loop?

A thread blocked in wait() can return without any notify (an implementation allowance on some platforms), and even with a real notify another thread may have consumed the condition first. So the predicate must be re-checked in a loop after every wake-up.

notify() vs notify_all()?

notify wakes one waiter, notify_all wakes every waiter, which then re-check and mostly go back to sleep. Use notify_all when different waiters wait for different predicates on one condition, or when you are unsure; use notify when any single waiter can take the work.

Is a safe state deadlock-free? Is an unsafe state a deadlock?

A safe state guarantees a way for everyone to finish, so no deadlock can be forced. An unsafe state is not itself a deadlock; it only removes the guarantee. Banker's refuses to enter unsafe states.

Why is RLock needed?

With a plain lock, a thread that calls a method which takes the lock from inside another method that already holds it deadlocks on itself. A reentrant lock lets the owner acquire it again and counts the acquisitions. It hides the problem of unclear lock ownership, so use it deliberately.
