Memory management & virtual memory

Every process sees its own private address space; the hardware and the OS quietly map it onto limited, shared physical memory. This chapter walks through paging and address translation, the TLB, multi-level page tables, page faults and demand paging, page-replacement policies, thrashing, and what stack, heap, malloc and Python's allocator do with all of it.

After this chapter you can
  • Translate a virtual address by hand: split it into page number and offset, look up the frame, and say what a page fault or protection fault does
  • Compute page-table sizes and the number of levels from address bits, page size and entry size
  • Explain what the TLB caches, how a miss differs from a page fault, and why TLB reach matters
  • Run FIFO, LRU, Optimal and Clock on a reference string and recognise Belady's anomaly
  • Describe thrashing and the working set, and explain stack, heap, mmap, swap and the OOM killer in terms of pages

Why virtual addresses?

Early systems let programs use physical addresses directly. That fails three ways: a bug in one program can overwrite another program or the OS, a program has to be loaded at the exact addresses it was built for, and a program cannot be larger than the free memory. Virtual memory removes all three. Each process gets its own virtual address space (up to 128 TiB for user space on x86-64 Linux), and the hardware MMU (memory management unit) translates every virtual address to a physical one on each access, using tables the OS maintains. That one level of indirection buys a lot:

  • Isolation: address 0x1000 in process A and in process B are different memory. A process cannot even name another's memory.
  • Relocation: a program always sees the same virtual layout; the OS places it in whatever physical frames are free, scattered anywhere.
  • Protection: each page carries read, write and execute permissions, so code is read-only and data is not executable.
  • Sharing: one physical copy of libc can appear in every process; fork shares pages copy-on-write; two processes can map the same shared memory.
  • Lazy allocation and overcommit: pages exist only once touched, so a process may reserve far more address space than there is RAM, and pages that do not fit can live on disk.
  • Files as memory: mmap maps a file into the address space.

The costs are a translation on every access (which the TLB hides) and the memory for the page tables themselves.

Paging and address translation

▶ Video lesson: Paging: translate an address by hand 4:03 · 6 scenes · narrated, pause anytime and explore

Memory is cut into fixed-size blocks: pages in the virtual address space and frames in physical memory, normally 4 KiB each. A page table maps page numbers to frame numbers. A virtual address splits into a page number (the high bits) and an offset (the low bits, 12 of them for 4 KiB pages). The offset is the position inside the page and is not translated; the page number is the index into the table.

Each page-table entry (PTE) holds the frame number plus control bits:

PTE fieldWhat it does
Present (valid)1 if the page is in RAM. If 0, any access raises a page fault; the OS keeps the swap or file location in the spare bits
Permissions (read, write, execute)violations raise a fault: this is how code stays read-only and a write to NULL-ish memory becomes SIGSEGV
User/supervisorwhether user-mode code may touch the page at all (kernel memory is mapped but off limits)
Accessedset by the hardware on any use; the Clock policy reads and clears it
Dirtyset by the hardware on a write; a dirty page must be written back before its frame can be reused
No-execute (NX)data pages cannot be run as code, which blocks a whole class of injection attacks
Frame numberwhere in physical memory the page lives
x86-64 PTEs are 8 bytes. Other architectures differ in layout but not in ideas.

How big is a page table?

With 48-bit virtual addresses, 4 KiB pages and 8-byte entries, a single flat table would need 512 GiB for every process. Change the numbers to see why multi-level tables exist.

Small pages (4 KiB)Huge pages (2 MiB or 1 GiB)
Page-table sizelarge: one entry per 4 KiBmuch smaller: one entry covers 2 MiB and the last table level disappears
Internal fragmentationsmall: on average half a page lost per regionup to a whole huge page lost per region
TLB reach (entries × page size)64 entries cover only 256 KiB64 entries cover 128 MiB
Finding frameseasy: any free 4 KiB frameneeds contiguous aligned memory; compaction can stall
Good forgeneral workloads, fine-grained sharing and swappingbig heaps: databases, VMs, numeric code (watch tail latency with transparent huge pages)
Page size is a trade between table size, wasted space and TLB coverage. Paging has no external fragmentation, only internal.

The TLB

▶ Video lesson: The TLB: why translation is almost free 4:22 · 7 scenes · narrated, pause anytime and explore

A page table lives in RAM, so naively every load or store would first need a table lookup in RAM: with a 4-level table that is four extra memory references per access. The translation lookaside buffer (TLB) removes almost all of them. It is a small, very fast cache inside the CPU that remembers recent page-number to frame-number translations (tens to a couple of thousand entries, usually in two levels). A hit costs about one cycle; a miss triggers a hardware page-table walk (on x86 and ARM; some architectures trap to software) and the result is cached.

Two properties explain most TLB behaviour:

  • TLB reach = entries × page size. A program whose hot data spans more pages than the TLB holds keeps missing, even if all of it is in RAM and in the CPU cache. This is why huge pages help big heaps.
  • Address-space tags. Translations belong to one address space. Without tags the kernel must flush the TLB on every process switch; with tags (ASID on ARM, PCID on x86) entries from several processes coexist and a switch costs nothing extra. On a multicore machine, changing a mapping also needs a TLB shootdown: an inter-processor interrupt telling other cores to drop the stale entry.

Multi-level page tables

A flat table with one entry per page is hopeless: the calculator above shows 512 GiB per process for 48-bit addresses, almost all of it describing addresses the process never uses. The fix is a tree of tables. The virtual address is cut into several indices; each indexes one level; only the subtrees that cover mapped memory exist. On x86-64 a 48-bit address is 9 + 9 + 9 + 9 bits of index plus a 12-bit offset, and every table is exactly one 4 KiB page of 512 entries.

flowchart LR
  VA[Virtual address<br/>9 + 9 + 9 + 9 + 12 bits]
  CR3[CR3 register<br/>root table address] --> L4[Level 4 table<br/>index = bits 47 to 39]
  L4 --> L3[Level 3 table<br/>index = bits 38 to 30]
  L3 --> L2[Level 2 table<br/>index = bits 29 to 21]
  L2 --> L1[Level 1 table<br/>index = bits 20 to 12]
  L1 --> Frame[Physical frame<br/>plus the 12-bit offset]
The 4-level walk on x86-64. Each arrow is one memory reference when the TLB misses.

A process that uses a code region, a heap and a stack, each far from the others, needs the root table plus at most three lower tables for each region: about ten 4 KiB pages, 40 KiB, instead of 512 GiB. Tables are allocated on demand as the process touches new regions. Other systems: 32-bit x86 used two levels (10 + 10 + 12 bits); recent x86-64 hardware supports a fifth level (57-bit addresses) for very large address spaces.

Page faults and demand paging

With demand paging the OS does not load or even allocate a page until the program touches it. malloc(1 GiB) or mmap of a big file returns almost instantly because it only records "this range is valid" in the process's region list; the page-table entries stay empty. The first access to each page faults, and the handler decides what to do:

flowchart TD
  F[Page fault at address X] --> V{Is X inside a mapped region?}
  V -- no --> Seg[SIGSEGV<br/>segmentation fault]
  V -- yes --> P{Does the access match<br/>the permissions?}
  P -- no --> Seg
  P -- yes --> K{Where is the page?}
  K -- never touched --> Z[Zero-fill a new frame<br/>minor fault]
  K -- shared or copy-on-write --> C[Map or copy a frame<br/>minor fault]
  K -- already in the page cache --> M[Map the cached frame<br/>minor fault]
  K -- in swap or on disk --> D[Read it from disk<br/>major fault, process sleeps]
  Z --> R[Update the page table<br/>restart the instruction]
  C --> R
  M --> R
  D --> R
What the kernel's fault handler decides. Only the last branch waits for the disk.

How rare must page faults be?

A major fault is millions of times slower than a memory access. Even one in ten thousand accesses faulting makes the machine about 9 times slower.

Demand paging, measured from Python (Linux)

import resource

def minor_faults() -> int:
    return resource.getrusage(resource.RUSAGE_SELF).ru_minflt

SIZE = 256 * 1024 * 1024                    # 256 MiB = 65,536 pages of 4 KiB

before = minor_faults()
lazy = bytes(SIZE)                          # calloc: the kernel hands out zero pages lazily, nothing is touched yet
print("bytes(256 MiB):    ", minor_faults() - before, "minor faults")

before = minor_faults()
eager = bytearray(SIZE)                     # CPython zero-fills the buffer, which touches every page
print("bytearray(256 MiB):", minor_faults() - before, "minor faults")
On one Linux machine with 4 KiB pages we measured 3 and 65,537 faults. Allocating is not using: the pages materialise on first touch, one fault each. ru_majflt counts the major ones.

Page replacement and thrashing

▶ Video lesson: Page replacement: who gets evicted? 5:57 · 7 scenes · narrated, pause anytime and explore

When a fault needs a frame and none is free, the OS must evict a page: write it to disk if it is dirty, mark its entry not-present, and reuse the frame. Which page? A policy is judged by the number of faults it causes on a reference string (the sequence of pages touched).

  • FIFO: evict the oldest page. Trivial to implement, but ignores how useful a page is.
  • LRU: evict the page unused for the longest time. Good, since recent use predicts future use, but exact LRU needs bookkeeping on every access.
  • Optimal (OPT): evict the page whose next use is farthest in the future. Provably fewest faults, impossible in practice, and the benchmark.
  • Clock (second chance): pages in a circle with the hardware's accessed bit; the hand clears bits as it sweeps and evicts the first page with bit 0. It approximates LRU cheaply, and real kernels use variants (Linux keeps active and inactive lists, and has an optional multi-generation LRU).

Counted by the same code that drives the simulation. On Belady's string FIFO goes from 9 faults with 3 frames to 10 with 4; LRU and OPT never get worse with more memory.

Thrashing and the working set

Locality is what makes paging work: at any moment a program uses a small working set of pages (those referenced in the last Δ accesses). If the frames given to a process cover its working set, it faults rarely. Thrashing is what happens when they do not: the process faults, waits for the disk, faults again, and spends nearly all its time paging. The classic trap is a feedback loop: low CPU utilisation makes the scheduler admit more processes, which take frames from the others, which fault more.

flowchart LR
  Util[CPU utilisation drops] --> Admit[Scheduler admits<br/>more processes]
  Admit --> Frames[Each process gets<br/>fewer frames]
  Frames --> Faults[Page-fault rate climbs]
  Faults --> Disk[Processes queue<br/>for the paging disk]
  Disk --> Util
The thrashing loop. The cure is to break it: give each process at least its working set, or run fewer processes.

Stack, heap and allocators

StackHeap
What lives therelocal variables, return addresses, saved registers, one frame per callanything with a lifetime beyond one call: malloc blocks, all Python objects
Allocationmove the stack pointer: a few instructionsan allocator searches its free lists, may ask the OS for more pages
Freeingautomatic on returnexplicit free, or garbage collection and reference counts in Python
Size limitfixed per thread, typically 8 MiB on Linux (ulimit -s)bounded by address space, RAM plus swap, and cgroup limits
Fails withstack overflow: runaway recursion hits a guard page, SIGSEGVout of memory: malloc returns NULL, MemoryError, or the OOM killer
Fragmentationnoneexternal: free space split into pieces too small to use
Both are just ranges of virtual pages; they differ in how their lifetimes are managed.

malloc. The C allocator (glibc on Linux) asks the OS for big chunks and hands out small pieces. Small requests come from a heap grown with brk; very large ones (128 KiB and up by default) get their own mmap region, which is handed straight back to the OS on free. Freed small blocks go to free lists for reuse, so a process's resident size often stays high after it has freed memory.

Python's allocator. Every Python value is an object on the heap. For objects of 512 bytes or less CPython uses its own allocator, pymalloc: it takes large arenas from the OS with mmap (1 MiB on 64-bit builds of recent versions), carves them into pools that each serve one size class, and hands out fixed-size blocks. Larger requests go to malloc. An arena is returned to the OS only when all of it is free, so a long-running process with scattered survivors keeps memory it is not using. The recursion limit (sys.getrecursionlimit(), 1000) protects the C stack from runaway recursion with a clean RecursionError. For data-structure sizes see What data structures look like in memory.

Seeing where Python's memory goes

import sys
import tracemalloc

tracemalloc.start()
data = [str(i) for i in range(100_000)]                 # 100,000 string objects on the heap
current, peak = tracemalloc.get_traced_memory()
print(f"{current / 1e6:.1f} MB in Python objects, peak {peak / 1e6:.1f} MB")
print(sys.getsizeof(data), "bytes for the list itself: it only stores pointers")

top = tracemalloc.take_snapshot().statistics("lineno")[:3]
for stat in top:                                         # which lines allocated the most
    print(stat)
resource.getrusage(resource.RUSAGE_SELF).ru_maxrss gives the process's peak resident set (KiB on Linux, bytes on macOS).

mmap, swap and running out of memory

Memory-mapped files. mmap makes a file (or an anonymous region) part of the address space. Pages are faulted in from the page cache as you touch them, so there is no read system call and no copy into a user buffer; a MAP_SHARED mapping is also how processes share memory. Databases (LMDB, SQLite's mmap mode) and loaders of big arrays use it.

Searching a big file through mmap

import mmap

with open("big.log", "rb") as f:
    with mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_READ) as m:   # maps the whole file: no data read yet
        print(m[:80])                                              # touching bytes faults the first page in
        pos = m.find(b"ERROR")                                     # the search faults pages in as it advances
        print("first ERROR at byte", pos)

Swap is disk space used as a backing store for anonymous pages (stack, heap) that have no file to go back to. It lets the OS evict cold pages to make room for hot ones, but a working set that does not fit in RAM turns into thrashing, so many servers and Kubernetes nodes run without swap.

Overcommit and the OOM killer. Linux by default lets processes reserve more in total than there is RAM plus swap (only single, absurdly large requests are refused), betting that not every page will be touched. Ten processes can each malloc 1 GiB on a 4 GiB machine and every call succeeds. The reckoning comes later: when pages are actually touched and no frame can be found, the kernel's OOM killer picks a process and sends it SIGKILL. In a container the same happens at the cgroup's memory limit, and the process dies with exit code 137 (128 + signal 9) and no Python traceback.

flowchart TD
  Died[My Python process died] --> Q1{Python traceback printed?}
  Q1 -- MemoryError --> ME[malloc failed: address-space or ulimit limit,<br/>or one allocation too large for the machine]
  Q1 -- RecursionError --> RE[Python recursion limit reached:<br/>recurse less or iterate]
  Q1 -- no traceback --> Q2{Exit status}
  Q2 -- 137 or SIGKILL --> OOM[OOM killer or cgroup limit:<br/>check dmesg and container memory limit]
  Q2 -- 139 or SIGSEGV --> SEG[Segmentation fault:<br/>C extension bug or C stack overflow]
  Q2 -- other --> Other[Look at logs, signals, exit code]
Reading a death. Each branch points to a different part of the memory system.

Interview prep

'Explain virtual memory.' Each process gets a private address space made of fixed-size pages. A page table maps virtual pages to physical frames, and the MMU translates every access, caching translations in the TLB. That gives isolation, per-page protection, sharing and the ability to map more than RAM: pages are loaded on first touch (demand paging) and cold ones are evicted by a replacement policy such as an LRU approximation. A page fault is the trap that lets the OS fix up a missing page and restart the instruction. Then mention the costs: translation overhead (hidden by the TLB), page-table memory (multi-level tables), and thrashing when the working set exceeds RAM.

Questions interviewers ask next

TLB miss vs page fault?

A TLB miss means the translation is not cached; the hardware walks the page table (a few memory references, tens to hundreds of nanoseconds) and carries on. A page fault means the page-table entry itself says the page is not in RAM; the OS must run, possibly doing disk I/O (microseconds to milliseconds). A miss is routine; a major fault is an event.

Why can the processes on a machine allocate more memory in total than it has?

Allocation only reserves address space; frames are assigned on first touch, and the default heuristic overcommit mode refuses only requests that are obviously impossible. A program that never touches most of what it reserved never uses it. If too many touch their pages at once, the OOM killer steps in.

How does fork() copy a gigabyte so quickly?

It does not. It copies the page tables and marks all writable pages read-only and shared (copy-on-write). A frame is duplicated only when one side writes to it. See Processes & threads.

Paging vs swapping?

Paging moves individual pages between RAM and disk, on demand. Classic swapping moved whole processes. Linux's 'swap' area holds individual evicted pages, so in modern usage the terms overlap.

Internal vs external fragmentation?

Paging has only internal fragmentation: the unused tail of the last page in a region. Variable-size allocation (malloc, old segmentation) suffers external fragmentation: enough free bytes in total, but not in one piece.

Why do LRU and OPT never show Belady's anomaly?

They are stack algorithms: the set of pages kept with n frames is always a subset of the set kept with n + 1 frames, so more memory cannot cause more faults. FIFO has no such inclusion property.
