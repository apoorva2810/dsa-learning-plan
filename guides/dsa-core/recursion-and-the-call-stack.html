Recursion & the call stack

Recursion is a function solving a problem by calling itself on a smaller one. This chapter shows what a call actually does to the stack, how a missing base case becomes a RecursionError, why naive Fibonacci builds an exponential tree of calls, how memoisation collapses that tree into a chain, how to convert recursion into a loop with an explicit stack, and how the same shapes reappear in trees, backtracking and dynamic programming.

After this chapter you can
  • Trace a recursive function through the pushing and popping of stack frames and say what each frame holds
  • State the three requirements of a correct recursion (base case, progress, trust) and the failure each one prevents, including Python's recursion limit
  • Draw the call tree of a recursive function and read time (number of calls) and space (depth) off it
  • Turn exponential recursion into linear with memoisation (functools.cache) or a bottom-up loop, and state the space each costs
  • Convert a recursive algorithm into an iterative one with an explicit stack, including post-order work
  • Recognise the common recursion shapes and the topic that drills each one

What a call actually does

▶ Video lesson: What a call actually does 4:23 · 7 scenes · narrated, pause anytime and explore

When a function is called, the interpreter creates a frame: a record holding the function's arguments and local variables, the position in the code to resume at, and room for intermediate results. Frames live on the call stack, last in, first out. The running function is the top frame. A return pops it, and execution resumes in the frame below, which receives the return value.

Recursion is only a function whose body contains a call to itself. Each such call pushes another frame for the same code with different values: factorial(3), factorial(2) and factorial(1) each have their own n, and all three are alive at the same moment. Nothing special happens in the language. The stack does all the bookkeeping.

Watching the stack: factorial

Run the simulation and watch the call stack on the left. The first scenario is the correct function: frames pile up on the way down to the base case and are popped on the way back, each one completing a multiplication. The second removes the base case.

Frames pushed and popped

Top of the stack is the running call; the frames below it are paused. Watch the frame text change from 'waiting' to 'got a value' as results flow back.

factorial, the way the simulation runs it

def factorial(n: int) -> int:
    if n <= 1:                      # base case: answer directly, no further call
        return 1
    return n * factorial(n - 1)     # progress: n - 1 is closer to the base case; trust it to be right

# factorial(4) -> 4 * factorial(3) -> 4 * (3 * factorial(2)) -> 4 * (3 * (2 * factorial(1)))
# calls: 4, deepest stack: 4 frames  ->  time O(n), space O(n)
Writing n <= 1 rather than n == 1 also makes factorial(0) terminate instead of recursing forever.

Base case, progress and the recursion limit

A correct recursion has three parts. Check them in this order when you write one and when you debug one:

  1. Base case. An input small enough to answer directly, with no further call. Without it the recursion never stops.
  2. Progress. Every recursive call must be on a strictly smaller input (smaller n, a shorter list, a subtree, a narrower range) so the base case is eventually reached. Calling f(n) from f(n) or f(n + 1) from f(n) never terminates.
  3. Trust. Assume the recursive call returns the right answer for the smaller input and write only the step that turns it into the answer for this one. Do not expand the whole stack in your head; that is what the call stack is for.

Most recursion bugs are one of these three:

MistakeTypical symptom
No base caseRecursionError: maximum recursion depth exceeded
Base case never reached (no progress, wrong argument, off-by-one)RecursionError, or a wrong answer for edge sizes
Base case too narrow (handles n == 1 but not 0, or one element but not the empty list)RecursionError or an exception on the empty input
Combining step wrong (returns the wrong thing, forgets one branch)A wrong answer, no crash
Shared mutable state not undone between branches (backtracking)Results contaminated by earlier branches
When a recursive function misbehaves, test the smallest inputs first: the empty case, one element, two elements.

Python's recursion limit. CPython guards the stack with a recursion limit, 1000 by default (sys.getrecursionlimit()). Exceeding it raises RecursionError rather than crashing the interpreter. The limit is about depth, not about the total number of calls: fib(30) makes 2.7 million calls and never goes deeper than 30. sys.setrecursionlimit(n) only moves the guard. Every frame still costs memory, and on many builds a deep enough recursion crashes the interpreter outright instead of raising an exception. If depth can reach 10⁴ or 10⁵ (a linked list of 100,000 nodes, a degenerate tree, a flood fill over a large grid), convert to an explicit stack instead.

Measuring the limit

import sys

def depth(n=0):
    try:
        return depth(n + 1)
    except RecursionError:
        return n

print(sys.getrecursionlimit())      # 1000
print(depth())                      # about 990 to 998: a few frames were already in use
A recursive function over a list of 1,000 items already needs about 1,000 frames: plan for the limit in any problem whose input is a linked list or a long string.

Time is the size of the tree, space is its depth

▶ Video lesson: Time is the tree, space is its depth 3:36 · 6 scenes · narrated, pause anytime and explore

Draw the call tree: one node per call, children are the calls it makes. Two facts follow, and they are the key to analysing any recursion:

  • Time is the number of nodes in the tree (times the work done per node outside its recursive calls).
  • Space is the depth of the tree (times the frame size), because the stack only ever holds the calls on one path from the root to the current call.

Fibonacci, fib(n) = fib(n−1) + fib(n−2), makes two calls per call. Its tree has about 1.618ⁿ nodes but is only n deep.

flowchart TD

  F2b --> F0a["fib 0"]
  F2a --> F1c["fib 1"]
  F2a --> F0b["fib 0"]
The same tree answers two questions: how much work (all the nodes) and how much memory (the longest path).

The exponential tree of naive Fibonacci

Red circles are calls whose argument was already computed earlier in the run: pure repeated work. The stack on the left never grows beyond n frames.

In fib(5) there are 15 calls but only 6 distinct arguments (0 to 5), so 9 calls recompute something the run already knew. The count of calls is 2·F(n+1) − 1 where F is the Fibonacci sequence: 15 for n = 5, 177 for n = 10, 21,891 for n = 20, 2.7 million for n = 30 and 331 million for n = 40.

How bad is naive Fibonacci?

The call count is 2·F(n+1) − 1, approximated here with the golden ratio. On the machine used to write this chapter, CPython 3.12 made about 20 million of these calls per second; 10 million is a safer default.

Memoisation: from a tree to a chain

▶ Video lesson: Memoisation: from a tree to a chain 3:55 · 7 scenes · narrated, pause anytime and explore

The repeated work in the Fibonacci tree is the bottleneck, and the cure is to remember: the first time fib(k) is computed, store the answer in a table (the memo); every later request is a lookup. Because each of the n + 1 distinct sub-problems is computed once, the number of calls drops from exponential to about 2n − 1, and the call tree collapses into a chain down the left edge with one cheap memo hit hanging off each level.

Memoised Fibonacci: the same recursion, a collapsed tree

Green circles are memo hits: they return at once and have no children. Compare the number of calls with the naive tree.

Four ways to write it

O(φⁿ) time, O(n) stack. Correct and hopeless beyond n ≈ 35.

def fib(n: int) -> int:
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

Top-down: keep the recursion, add a lookup. O(n) time, O(n) memo and O(n) stack.

def fib(n: int, memo: dict[int, int] | None = None) -> int:
    if memo is None:
        memo = {}
    if n < 2:
        return n
    if n not in memo:
        memo[n] = fib(n - 1, memo) + fib(n - 2, memo)
    return memo[n]

The idiomatic version: the decorator keeps the memo for you. The arguments must be hashable (ints, strings, tuples; not lists or dicts).

from functools import cache

@cache
def fib(n: int) -> int:
    return n if n < 2 else fib(n - 1) + fib(n - 2)

# fib.cache_info() reports hits and misses; fib.cache_clear() empties the memo

No recursion at all: compute the sub-problems in dependency order. O(n) time, O(1) space with two variables, and no recursion limit. This is the dynamic-programming form.

def fib(n: int) -> int:
    prev, cur = 0, 1                 # fib(0), fib(1)
    for _ in range(n):
        prev, cur = cur, prev + cur
    return prev

Memoisation removes repeated work, not depth. A memoised fib(5000) still recurses 5,000 levels and raises RecursionError; the bottom-up loop does not. That is why interviewers often follow 'add memoisation' with 'now make it iterative'. This progression (naive recursion → memoised recursion → table → rolling variables) is the whole of 1-D Dynamic Programming and 2-D Dynamic Programming, and the space step is covered in Complexity & optimisation.

From recursion to iteration

Sometimes you must remove the recursion: the depth could exceed the limit, or the interviewer asks for it. Two situations, two techniques.

Tail calls become loops. If the recursive call is the very last thing the function does, with nothing left to do after it returns, the new call can simply reuse the variables: that is a while loop.

Tail recursion into a loop

Recursive: one frame per step

def sum_to(n, acc=0):
    if n == 0:
        return acc
    return sum_to(n - 1, acc + n)   # nothing to do after the call: a tail call

# sum_to(1100)  ->  RecursionError

Loop: constant space

def sum_to(n):
    acc = 0
    while n > 0:
        acc += n                    # the parameters become loop variables
        n -= 1
    return acc

# sum_to(10**7)  ->  fine

Python does not eliminate tail calls. A tail-recursive function still pushes one frame per call and hits the recursion limit; writing it in 'tail form' buys nothing. Guido van Rossum's reasons are that discarding frames would erase the stack traces you need for debugging, and that code relying on it would not run on interpreters without it. In an interview, say so and convert the tail call to a loop by hand.

Everything else needs an explicit stack. When a function does work after its recursive calls, or calls itself more than once, you cannot overwrite the variables; you need to remember pending work. The call stack did that for you; now you hold the same information yourself in a list.

What the call stack kept for each callWhat your explicit stack must keep
the arguments (node, lo, hi, r, c)the same values, pushed as a tuple or a single object
local variables (partial results)extra fields in the tuple, or variables declared outside the loop
where to resume (the line after the call)a marker such as (node, children_done), or the shape of the loop itself
the return value, handed to the calleran accumulator variable, a result list, or values pushed on a second stack
Converting is bookkeeping: for each thing a frame held, decide where it lives now.

Iterative inorder traversal. The stack holds exactly the ancestors whose left subtree is being explored: the pending frames of the recursive version.

Inorder traversal: call stack vs your own stack

Recursive

def inorder(root):
    out = []

    def visit(node):
        if node is None:                 # base case
            return
        visit(node.left)
        out.append(node.val)             # work between the two calls
        visit(node.right)

    visit(root)
    return out

Explicit stack

def inorder(root):
    out, stack, node = [], [], root
    while node or stack:
        while node:                      # descend, remembering the path
            stack.append(node)
            node = node.left
        node = stack.pop()               # 'return' from the deepest left call
        out.append(node.val)             # the line after visit(node.left)
        node = node.right                # then visit(node.right)
    return out

Flood fill: when the depth could be a million

Recursive DFS

def fill(r, c):
    if not (0 <= r < rows and 0 <= c < cols) or grid[r][c] != "1":
        return
    grid[r][c] = "0"
    fill(r + 1, c); fill(r - 1, c)
    fill(r, c + 1); fill(r, c - 1)

# a 1000 x 1000 grid of land can recurse 10**6 deep: RecursionError

DFS with an explicit stack

def fill(r, c):
    stack = [(r, c)]
    while stack:
        r, c = stack.pop()
        if not (0 <= r < rows and 0 <= c < cols) or grid[r][c] != "1":
            continue
        grid[r][c] = "0"
        stack.extend(((r + 1, c), (r - 1, c), (r, c + 1), (r, c - 1)))

# the list grows on the heap, not on the call stack: no recursion limit

Work after the calls: post-order with an explicit stack

Show the pattern

When code must run after the recursive calls (post-order, or combining children's results), push the node twice: once to process its children, and once, marked, to run the 'after' code when they are all done.

def postorder(root):
    out, stack = [], [(root, False)]
    while stack:
        node, children_done = stack.pop()
        if node is None:
            continue
        if children_done:
            out.append(node.val)              # the code that ran after both recursive calls
        else:
            stack.append((node, True))        # come back to this node later
            stack.append((node.right, False)) # pushed first, so processed last
            stack.append((node.left, False))
    return out

Stacks are last-in-first-out, so push the sub-calls in the reverse of the order you want them handled. The (node, flag) pair is the 'where to resume' information a frame used to carry.

Saying it in the interview

Before you write a recursive function, say these four things

A strong answer to 'what is the complexity of this recursion?' sounds like: 'Each call makes two calls on inputs of size n − 1, so the call tree has about 2ⁿ nodes: exponential time. The stack only holds one root-to-leaf path, so space is O(n). The sub-problems overlap: there are only n distinct arguments, so memoising turns it into O(n) time and O(n) space. Because Python limits recursion to about 1,000 frames, for large n I would write the bottom-up loop, which is also O(1) space.'

Follow-ups to expect

What happens at the recursion limit, and can you raise it?

CPython raises RecursionError at 1,000 frames by default. sys.setrecursionlimit raises the guard, not the memory, and a deep enough recursion can still crash the interpreter. The professional answer is to remove the recursion (explicit stack or loop) when depth is unbounded.

Is tail recursion optimised in Python?

No. Each tail call still pushes a frame. Convert tail calls to loops yourself.

Top-down or bottom-up dynamic programming?

Top-down (recursion plus memo) is easiest to write straight from the recurrence and only computes reachable states. Bottom-up (a loop over a table) has no recursion limit, lower constant factors, and makes rolling-variable space optimisation obvious. Know both; start top-down in the interview.

Why does my memoised function raise TypeError: unhashable type?

functools.cache and dict memos need hashable arguments. Lists and dicts are not hashable; pass a tuple, an index, or a string instead.

How do I get the recursion's space down?

For tail calls, a loop (O(1)). For tree walks, nothing beats O(h) unless you change the algorithm (for example Morris traversal, O(1) extra space, which temporarily rewires the tree). For divide and conquer, recurse on the smaller half first and loop on the larger (quicksort's O(log n) stack).
