Complexity & optimisation

Big-O is a way of counting work as the input grows. This chapter builds it from counting operations, shows how the classes diverge with a simulation and a calculator that turns them into seconds, explains amortised cost with a dynamic array, accounts for space including the call stack, and then lists the concrete moves that turn O(n) extra space into O(1), each with a before-and-after in Python and the problems from the 150 that drill it.

After this chapter you can
  • Derive the time complexity of a function by counting its operations and applying the simplification rules (drop constants and lower-order terms, add sequential parts, multiply nested ones)
  • Solve a divide-and-conquer recurrence such as T(n) = 2T(n/2) + n with a recursion tree
  • Estimate real run time from n and operations per second, and say which classes are out of reach for a given constraint
  • Explain why appending to a dynamic array is amortised O(1) and recognise the same argument in sliding windows and monotonic stacks
  • Count space correctly, including the recursion stack and hidden copies such as slices and sorted()
  • Apply the six O(n) → O(1) space moves and state what each one costs you

Counting operations, not seconds

▶ Video lesson: Counting operations, not seconds 4:09 · 6 scenes · narrated, pause anytime and explore

Seconds depend on the machine, the language and the input. Big-O answers a different question: how does the amount of work grow when the input grows? You count the steps the algorithm performs as a function of n (the size of the input, which you should define out loud: 'n is the length of nums') and keep only the part that dominates when n is large.

Count one concrete function:

Count the comparisons

def count_zero_sum_pairs(nums):                 # n = len(nums)
    total = 0                                   # 1 step
    for i in range(len(nums)):                  # outer loop: n iterations
        for j in range(i + 1, len(nums)):       # inner loop: n-1, n-2, ..., 1, 0 iterations
            if nums[i] + nums[j] == 0:          # 1 comparison per inner iteration
                total += 1
    return total                                # 1 step

# comparisons = (n-1) + (n-2) + ... + 1 + 0 = n(n-1)/2 = n^2/2 - n/2
# keep the fastest-growing term (n^2/2), drop the constant factor (1/2)  ->  O(n^2)
Half of the n² pairs are skipped by starting the inner loop at i + 1, and it is still O(n²): constants do not change the class.

Five rules cover almost every function you will analyse:

  1. Drop constants: 3n and n/2 are both O(n).
  2. Drop lower-order terms: n² + n + 7 is O(n²).
  3. Sequential blocks add, so keep the larger: an O(n) pass followed by an O(n²) pass is O(n²).
  4. Nested blocks multiply: a loop of n iterations whose body costs O(log n) is O(n log n).
  5. Different inputs get different letters: looping over a and then over b is O(a + b); nested it is O(a·b). Never write O(n²) for two arrays of different lengths.

Always say which case you mean. Worst case is the default. If the average differs, say that too (quicksort is O(n log n) on average and O(n²) in the worst case).

Recurrences: counting a recursive function

A recursive function has no loop to count, so write its cost as an equation: T(n) = (number of recursive calls) × T(smaller input) + (work done outside the calls). Then draw the call tree and add up the work level by level. Merge sort is the standard example: T(n) = 2·T(n/2) + n, because it makes two calls on halves and merges them in linear time. Recursion & the call stack animates these trees as the calls execute.

Memorise the shape of the first six; they cover most interview recursions.

The Master theorem in three lines

Show me

For T(n) = a·T(n/b) + O(n^d) compare d with log_b(a). If d > log_b(a) the root dominates: O(n^d). If they are equal every level costs the same: O(n^d · log n). If d < log_b(a) the leaves dominate: O(n^(log_b a)). Merge sort: a = 2, b = 2, d = 1, and log₂ 2 = 1, so O(n log n). Binary search: a = 1, b = 2, d = 0, log₂ 1 = 0, so O(log n). Balanced tree walk: a = 2, b = 2, d = 0, log₂ 2 = 1 > 0, so O(n). In an interview, drawing the first three levels of the tree is just as convincing and easier to get right.

How the classes grow

The five classes you meet every day are O(1), O(log n), O(n), O(n log n) and O(n²). The simulation doubles n and counts operations with constants set to 1. Operation counts as n grows

Use the Next button once per step. The O(n²) bar on the left is always as tall as the chart allows; everything else shrinks relative to it.

A practical consequence is the doubling test. If you cannot read the complexity off the code, time it at n and at 2n. About the same time means O(1); a small constant added means O(log n); twice means O(n); slightly more than twice means O(n log n); four times means O(n²); eight times means O(n³).

From operation counts to seconds

Enter the input size and how many simple operations per second your environment manages. About 10⁷ for CPython (a loop body with a few bytecodes), 10⁸ to 10⁹ for compiled languages. The exponential row has its own size, because 2ⁿ at n = 100,000 would not fit in any number.

Big-O hides constants. An O(n) algorithm with a heavy body can lose to an O(n log n) one at n = 1,000, and CPython's constants are far larger than C++'s. Pick the class first, then care about constants. When two classes both fit the budget, prefer the simpler code.

Amortised analysis: the cost of one append

▶ Video lesson: Amortised cost: why append is O(1) 4:24 · 6 scenes · narrated, pause anytime and explore

Some operations are usually cheap and occasionally expensive. Amortised cost is the total cost of a sequence of operations divided by the number of operations. It is a guarantee over the whole sequence, for the worst input, not an average over random inputs. The classic case is list.append: most appends write into a spare slot; when the buffer is full the list allocates a larger one and copies everything.

Run the simulation. The bars are the cost of each append; the dashed line is the running average. Then switch to the second scenario, where the buffer grows by one slot at a time instead of by a factor.

Doubling the buffer, and what happens if you do not

Green bars are cheap appends; red bars include a copy. In the doubling run the spikes get rarer exactly as fast as they get taller.

Why doubling works. After the buffer reaches size n, the total number of elements ever copied is 1 + 2 + 4 + … + n/2 < n. So n appends cost at most n writes plus n copies: under 3n in total, under 3 per append, constant. A banker's version: charge each append 3 coins, spend 1 on its own write, and bank 2 to pay for copying itself and one older element at the next resize.

Why +1 fails. Growing by a constant amount means a copy of the whole array at every resize, 1 + 2 + … + n = n(n+1)/2. Any growth factor above 1 gives amortised O(1); any constant increment does not.

CPython does not double. A list grows to about n + n/8 + 6 slots (rounded to a multiple of 4), so capacities run 0, 4, 8, 16, 24, 32, 40, 52, 64, 76 and so on. The argument is the same with a different constant; What data structures look like in memory shows the real numbers.

The same pattern is behind most 'it looks quadratic but it is linear' arguments. Count what happens to each element, not to each iteration:

Looks quadratic, is linear

def next_greater(nums: list[int]) -> list[int]:
    res = [-1] * len(nums)
    stack: list[int] = []                         # indices whose answer is still unknown
    for i, x in enumerate(nums):
        while stack and nums[stack[-1]] < x:      # an inner loop inside an outer loop ...
            res[stack.pop()] = x                  # ... but every index is popped at most once
        stack.append(i)                           # and pushed exactly once
    return res
Pushes: n. Pops: at most n. Total work over the whole call: at most 2n, so O(n), although a single iteration may pop many.

Worst case, amortised, average: three different promises

Worst case

The most any single operation can cost, for the worst input. list.append is O(n) in the worst case (the resize).

Amortised

The cost per operation averaged over a sequence, for the worst input sequence. No randomness involved. list.append is amortised O(1).

Average (expected)

The cost averaged over random inputs, or over the algorithm's own random choices. Quicksort with a random pivot is O(n log n) expected; a dict lookup is O(1) expected for a good hash function and O(n) if every key collides.

Hidden copies: recursion on slices

nums[1:] copies at every level

def sum_list(nums):
    if not nums:
        return 0
    return nums[0] + sum_list(nums[1:])    # copies n-1, n-2, ... items

# time:  n + (n-1) + ... + 1 = O(n^2) element copies
# space: all n slices are alive at the deepest call -> O(n^2)
#        (plus n frames, and the recursion limit of 1000 stops you at about n = 1000)

An index shares the one list

def sum_list(nums, i=0):
    if i == len(nums):
        return 0
    return nums[i] + sum_list(nums, i + 1)  # no copies

# time:  O(n)
# space: O(n) for the n frames; a for-loop with a running total would be O(1)

Where Python hides space (and where it does not)

Copies

s[::-1], nums[a:b], list(x), x.copy(), sorted(x), s.split(), a + b for lists and strings, copy.deepcopy. Each is O(size of the result).

Lazy, O(1) space

range(10**9) (it stores only start, stop and step, not the numbers), generators and generator expressions, enumerate, zip, reversed, map, filter, and dictionary views such as d.items(). sum(x for x in nums) uses O(1) space; sum([x for x in nums]) builds a list first.

In place, but not free

list.sort() sorts in place, but Timsort may borrow up to n/2 slots while merging, so 'O(1) space' is a slight simplification. list.pop(0) and insert(0, x) use no extra space but cost O(n) time because every element shifts.

Strings

Strings are immutable. s += c creates a new string; building one character at a time is O(n²) in the worst case. Collect pieces in a list and ''.join(pieces) once.

From O(n) to O(1) extra space: the catalogue

'Can you do it in O(1) extra space?' is the most common follow-up after a correct solution. The answer is almost never inspiration; it is one of six moves. For each, ask what the extra memory was doing, because the replacement depends on it.

1. Two pointers instead of an array of prefix results

The memory was remembering something about the left (or right) side so the other side could use it. What replaces it: two indices that walk inward, plus one or two running variables. You pay with a harder correctness argument, and usually you need a sorted order or a 'the smaller side decides' property. Practise: Trapping Rain Water, Valid Palindrome, Container With Most Water, Two Sum II - Input Array Is Sorted.

Trapping Rain Water: from two arrays to two variables

Before: O(n) extra space

def trap(height):
    n = len(height)
    if n == 0:
        return 0
    left_max = [0] * n                    # tallest bar at or left of i
    right_max = [0] * n                   # tallest bar at or right of i
    left_max[0] = height[0]
    for i in range(1, n):
        left_max[i] = max(left_max[i - 1], height[i])
    right_max[-1] = height[-1]
    for i in range(n - 2, -1, -1):
        right_max[i] = max(right_max[i + 1], height[i])
    return sum(min(left_max[i], right_max[i]) - height[i] for i in range(n))

After: O(1) extra space

def trap(height):
    lo, hi = 0, len(height) - 1
    left_max = right_max = water = 0
    while lo < hi:
        if height[lo] < height[hi]:       # the left wall is lower, so it decides
            left_max = max(left_max, height[lo])
            water += left_max - height[lo]
            lo += 1
        else:                             # the right wall is lower or equal
            right_max = max(right_max, height[hi])
            water += right_max - height[hi]
            hi -= 1
    return water

Why the right-hand version is correct: the water above a bar is limited by the smaller of the tallest bars on its two sides, and we always advance the pointer whose bar is lower. Say height[lo] < height[hi]. The bar at hi is on the right and at least as tall as height[lo]; and every bar the left pointer has already passed was lower than some bar on the right at that moment. So the left running maximum can never exceed the tallest bar on the right, the left side is the limiting side, and left_max - height[lo] is exact. The mirrored argument covers the right pointer. Say that in the interview.

2. Mark inside the input instead of a visited set

The memory was a set or matrix of flags: 'seen', or 'this row must be zeroed'. What replaces it: a spare bit of the input itself, such as the sign of a number or the first row and column of a matrix. You pay by changing the input (ask first, or restore it), and the trick fails when the spare bit is already in use. Practise: Set Matrix Zeroes.

Set Matrix Zeroes: from two sets to the matrix's own first row and column

Before: O(m + n) extra space

def set_zeroes(matrix):
    m, n = len(matrix), len(matrix[0])
    rows = {i for i in range(m) for j in range(n) if matrix[i][j] == 0}
    cols = {j for i in range(m) for j in range(n) if matrix[i][j] == 0}
    for i in range(m):
        for j in range(n):
            if i in rows or j in cols:
                matrix[i][j] = 0

After: O(1) extra space

def set_zeroes(matrix):
    m, n = len(matrix), len(matrix[0])
    first_row_zero = any(matrix[0][j] == 0 for j in range(n))   # the markers
    first_col_zero = any(matrix[i][0] == 0 for i in range(m))   # overwrite these
    for i in range(1, m):
        for j in range(1, n):
            if matrix[i][j] == 0:
                matrix[i][0] = 0          # column 0 remembers: row i must be zeroed
                matrix[0][j] = 0          # row 0 remembers: column j must be zeroed
    for i in range(1, m):
        for j in range(1, n):
            if matrix[i][0] == 0 or matrix[0][j] == 0:
                matrix[i][j] = 0
    if first_row_zero:
        for j in range(n):
            matrix[0][j] = 0
    if first_col_zero:
        for i in range(m):
            matrix[i][0] = 0

The two booleans exist because the first row and column are doing double duty: they hold markers and their own data, so their original zero-ness must be saved before the markers overwrite it.

3. Rolling variables instead of a DP table

The memory was holding every sub-answer although each one is read only by the next one or two. What replaces it: one variable per sub-answer still needed. You pay by losing the history: you get the value of the optimum but cannot trace back which choices produced it. Rule of thumb: if dp[i] reads only dp[i-1] and dp[i-2], keep two variables; if row i of a 2-D table reads only row i-1, keep one row. Practise: Climbing Stairs, House Robber, Min Cost Climbing Stairs, Maximum Subarray, and the 2-D cases Unique Paths and Longest Common Subsequence, which drop from O(m·n) to O(n).

House Robber: from a table to two variables

Before: O(n) extra space

def rob(nums):
    if not nums:
        return 0
    dp = [0] * (len(nums) + 1)            # dp[i] = best loot from the first i houses
    dp[1] = nums[0]
    for i in range(2, len(nums) + 1):
        dp[i] = max(dp[i - 1], dp[i - 2] + nums[i - 1])
    return dp[-1]

After: O(1) extra space

def rob(nums):
    prev2 = prev1 = 0                     # best loot for i-2 houses, for i-1 houses
    for x in nums:
        prev2, prev1 = prev1, max(prev1, prev2 + x)
    return prev1

Why two cells are enough

Grey cells in the table are never read again. The only information that matters at step i is in the two cells before it, which is exactly what prev2 and prev1 hold.

4. Algebra and bits instead of a set or counter

The memory was counting or recording values to find the odd one out. What replaces it: an identity that cancels everything you do not care about. x ^ x == 0 and x ^ 0 == x, and XOR is commutative, so pairs vanish whatever the order. Or a total that is known in closed form, 0 + 1 + … + n = n(n+1)/2. You pay in generality: the trick works only while the problem has that algebraic structure (change 'twice' to 'three times' and XOR stops working). Practise: Single Number, Missing Number.

Single Number and Missing Number: from a counter to an identity

Before: O(n) extra space

from collections import Counter

def single_number(nums):
    counts = Counter(nums)
    return next(v for v, c in counts.items() if c == 1)

def missing_number(nums):                  # values are 0..n with one missing
    seen = set(nums)
    return next(i for i in range(len(nums) + 1) if i not in seen)

After: O(1) extra space

def single_number(nums):
    acc = 0
    for x in nums:
        acc ^= x                           # every pair cancels, the single value is left
    return acc

def missing_number(nums):                  # values are 0..n with one missing
    n = len(nums)
    return n * (n + 1) // 2 - sum(nums)    # expected total minus actual total

5. Reuse the input or the output as the workspace

The memory was a second copy of the data: a prefix array, a rotated matrix, a reversed list. What replaces it: writing partial results into the output array you must return anyway, or rearranging the input in place. You pay by modifying the input, and by needing a stated convention: 'O(1) extra space not counting the output'. Practise: Product of Array Except Self, Rotate Image, Reverse Linked List.

Product of Array Except Self: the output array doubles as the prefix array

Before: two extra arrays

def product_except_self(nums):
    n = len(nums)
    prefix = [1] * n                       # product of everything left of i
    suffix = [1] * n                       # product of everything right of i
    for i in range(1, n):
        prefix[i] = prefix[i - 1] * nums[i - 1]
    for i in range(n - 2, -1, -1):
        suffix[i] = suffix[i + 1] * nums[i + 1]
    return [prefix[i] * suffix[i] for i in range(n)]

After: O(1) beyond the output

def product_except_self(nums):
    n = len(nums)
    out = [1] * n                          # holds the prefix products first
    for i in range(1, n):
        out[i] = out[i - 1] * nums[i - 1]
    suffix = 1                             # running product of everything to the right
    for i in range(n - 1, -1, -1):
        out[i] *= suffix
        suffix *= nums[i]
    return out

6. Floyd's cycle detection instead of a visited set

The memory was a set of nodes (or indices) already visited, to notice the first repeat. What replaces it: two pointers moving at different speeds along the same chain. If the chain loops, the fast pointer must catch the slow one. You pay with a narrower domain (every element needs exactly one 'next': a linked list, or an array whose values are indexes into itself) and a proof that takes a minute to explain. Practise: Linked List Cycle, Find the Duplicate Number, Happy Number.

flowchart LR

Nodes 2 to 5 form the cycle. Slow moves one step per round, fast moves two; they land on the same node inside the loop.

Linked List Cycle: from a set of nodes to two pointers

Before: O(n) extra space

def has_cycle(head):
    seen = set()
    while head:
        if head in seen:                   # identity-based hash of the node object
            return True
        seen.add(head)
        head = head.next
    return False

After: O(1) extra space

def has_cycle(head):
    slow = fast = head
    while fast and fast.next:
        slow = slow.next                   # one step
        fast = fast.next.next              # two steps
        if slow is fast:
            return True
    return False

Find the Duplicate Number: the array is the linked list (i → nums[i])

def find_duplicate(nums: list[int]) -> int:
    # values are in 1..n and there are n+1 of them, so following i -> nums[i] never leaves the array;
    # two indexes pointing at the same value are two arrows into one node: the cycle entrance is the duplicate
    slow = fast = nums[0]
    while True:                                # phase 1: find a meeting point inside the cycle
        slow = nums[slow]
        fast = nums[nums[fast]]
        if slow == fast:
            break
    slow = nums[0]                             # phase 2: restart one pointer from the start
    while slow != fast:                        # both now move one step; they meet at the entrance
        slow = nums[slow]
        fast = nums[fast]
    return slow
O(n) time, O(1) space, and the input is never modified, which is exactly what the problem demands.

When you offer one of these in an interview, name the 'You give up' column too. That is what turns a trick into a trade-off.

Trading time for space (and saying so)

Most optimisations move cost between time and space rather than removing it. A hash map buys time with memory. Sorting buys memory with time (n log n) and often lets you finish in O(1) extra space. Precomputation, such as prefix sums, spends one linear pass and O(n) memory to make every later query O(1). Memoisation spends memory to avoid recomputing.

Contains Duplicate shows the whole menu on one problem:

ApproachTimeExtra spaceNotes
Compare every pairO(n²)O(1)fine up to about n = 10³; stops early on the first duplicate
Sort, then compare neighboursO(n log n)O(1) to O(n)nums.sort() mutates the input; sorted(nums) copies it; Timsort may borrow up to n/2 slots

There is no 'best' row without a constraint. Memory-bound? Take the middle row. Latency-bound? Take the last.

When the interviewer asks 'can you do better?', ask which resource: 'Do you want to reduce time or memory? My current solution is O(n) time and O(n) space. I can get O(n log n) time and O(1) extra space by sorting in place, or keep O(n) time if memory is fine.' That question is the senior signal. It shows you know the trade-off exists and that the right answer depends on the constraint.
