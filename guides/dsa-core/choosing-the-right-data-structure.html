Choosing the right data structure

Every data structure makes some operations cheap and pays for it with others. This chapter starts from the operation your brute force repeats, follows a decision flowchart to the structure that makes it cheap, shows what each Python container really costs, replays one workload on a list and on a heap, and lists the places where the obvious choice is the wrong one.

After this chapter you can
  • Name the operation an inner loop repeats and pick the structure that makes it cheap
  • Walk the decision flowchart from an operation (lookup, end access, min/max, prefix, range, grouping) to a Python structure
  • Quote the real cost of list, deque, dict, set, heapq, bisect and Counter operations, including the hidden O(n) ones
  • Explain why a heap beats a list for repeated 'take the smallest', and when it does not
  • Combine two structures (dict + linked list, dict + bisect, two heaps) when one is not enough
  • Say the choice in an interview: the operation, its current cost, the new structure, the new total

Start from the operations, not the structure

Every data structure is a deal. It makes a few operations cheap and pays for that with the others. A list reads any position instantly and appends cheaply, but asking "is 7 in here?" scans the whole list. A heap hands you the smallest item instantly, but asking "is 7 in here?" scans just as much. Neither is "the best". Each is the best at something.

So the question is not "which structure is good?" but "which operation does my algorithm repeat most?". Take the brute force you already have and underline what the innermost loop does on every pass. It is almost always one of these:

  • look something up: "have I seen this?", "how many times?", "what is attached to this key?"
  • take from an end: the newest item (undo, nesting) or the oldest item (queue, BFS)
  • get the smallest or largest: again and again, while items keep arriving
  • match by string prefix: "which words start with pre?"
  • ask about a range: a sum over positions l..r, a count between two values, the value nearest to x
  • merge groups: "are these two in the same group?", with groups joining over time
  • follow connections: the neighbours of a node, the prerequisites of a course
  • read by position: the i-th item, in the order it arrived (the plain list, and the default)

The verb on that line decides the structure. The rest of this chapter is the map from verb to structure, with prices attached. For how to count those prices, see Complexity & optimisation; for how the containers are laid out in memory, see What data structures look like in memory.

Say the verb before you say the structure. 'The loop asks for the cheapest pending task on every iteration' is a sentence the interviewer can agree with. 'I'll use a heap' with no reason sounds memorised, and it leaves the interviewer guessing whether you know why.

Two branches that hide several answers

"I need order" means six different things

The word order is the most overloaded in problem statements. Before you pick a container, decide which order the problem needs.

flowchart LR
  O(["I need some<br/>kind of order"]) --> Q(["Which order<br/>do I mean?"])
  Q -- position --> LST["list"]
  Q -- arrival --> DQ["deque"]
  Q -- recency --> OD["OrderedDict"]
  Q -- priority --> HP["heap"]
  Q -- "sorted order" --> SB["sorted list<br/>+ bisect"]
  Q -- "key insertion" --> DC["plain dict"]
Six meanings of 'order', six containers. Only the sorted list keeps every item in sorted order; the heap guarantees just the top.

The dict family

"Look something up" splits again, depending on what is attached to the key. Pick the smallest tool that fits; the lighter type documents your intent.

flowchart LR
  K(["I need O(1)<br/>lookup"]) --> V{{"Value attached<br/>to each key?"}}
  V -- no --> SET["set"]
  V -- yes --> C{{"What kind<br/>of value?"}}
  C -- "a count" --> CNT["Counter"]
  C -- "a list of items" --> DD["defaultdict(list)"]
  C -- "anything else" --> DICT["dict"]
  DICT --> R{{"Reorder keys or<br/>evict the oldest?"}}
  R -- yes --> OD["OrderedDict"]
  R -- no --> PL["plain dict<br/>is enough"]
Presence only: set. A count: Counter. Groups: defaultdict(list). Anything else: dict. Only reach for OrderedDict when you must reorder keys.

What Python's containers cost

The table lists the average cost of the operations you reach for. Amortised means averaged over a long run: an occasional resize is paid for by many cheap calls. For dict and set, "average" assumes a decent hash function; in an interview treat them as O(1) and mention the collision caveat only if asked.

The expensive operations hide inside friendly syntax. x in my_list, my_list.pop(0), my_list.insert(0, x), my_list.remove(x), my_list.index(x), my_list.count(x), a slice a[l:r], and s += t on strings all do linear work. One of them inside a loop of n iterations turns an O(n) solution into O(n²).

Feel the difference: list.pop(0) versus deque.popleft()

import timeit

n = 100_000
as_list = timeit.timeit("q.pop(0)", setup=f"q = list(range({n}))", number=n // 2)
as_deque = timeit.timeit("q.popleft()", setup=f"from collections import deque; q = deque(range({n}))", number=n // 2)
print(f"list.pop(0):      {as_list:.3f} s")
print(f"deque.popleft():  {as_deque:.4f} s")
Run it. Both loops do the same logical thing; the list moves up to 100,000 pointers on every call, so the gap is orders of magnitude and grows with n.

The idioms you will type a hundred times

from collections import Counter, defaultdict

def has_duplicate(nums: list[int]) -> bool:
    seen = set()
    for x in nums:
        if x in seen:                  # O(1) average
            return True
        seen.add(x)
    return False

def two_sum(nums: list[int], target: int) -> list[int]:
    index_of = {}                      # value -> position
    for i, x in enumerate(nums):
        if target - x in index_of:
            return [index_of[target - x], i]
        index_of[x] = i
    return []

def frequent_and_groups(words: list[str]):
    freq = Counter(words)              # Counter({'a': 3, 'b': 1})
    top2 = freq.most_common(2)         # O(n log 2)
    groups = defaultdict(list)         # key -> list, created on first use
    for w in words:
        groups[tuple(sorted(w))].append(w)
    return top2, groups
from collections import deque

def bfs_order(graph: dict, start):
    queue = deque([start])
    seen = {start}
    order = []
    while queue:
        node = queue.popleft()         # O(1); list.pop(0) would be O(n)
        order.append(node)
        for nxt in graph[node]:
            if nxt not in seen:
                seen.add(nxt)
                queue.append(nxt)
    return order

recent = deque(maxlen=3)               # keeps only the 3 newest items
for x in range(10):
    recent.append(x)
print(list(recent))                    # [7, 8, 9]
import heapq

h = []
heapq.heappush(h, (2, "write report"))    # (priority, task): tuples compare left to right
heapq.heappush(h, (1, "fix outage"))
print(h[0])                               # (1, 'fix outage'): peek at the smallest, O(1)
print(heapq.heappop(h))                   # (1, 'fix outage'): O(log n)

items = [5, 1, 4, 2, 3]
heapq.heapify(items)                      # list -> heap in O(n)
print(heapq.nlargest(2, items))           # [5, 4]: O(n log 2)

max_heap = []                             # heapq is a min-heap: store negatives for a max-heap
for x in (5, 1, 4):
    heapq.heappush(max_heap, -x)
print(-heapq.heappop(max_heap))           # 5
import bisect

a = [1, 3, 3, 3, 7, 9]
print(bisect.bisect_left(a, 3))           # 1: first index where a[i] >= 3
print(bisect.bisect_right(a, 3))          # 4: first index where a[i] > 3
print(bisect.bisect_right(a, 3) - bisect.bisect_left(a, 3))   # 3 copies of 3

def floor(a: list[int], x: int):
    """Largest element <= x, or None."""
    i = bisect.bisect_right(a, x)
    return a[i - 1] if i else None

print(floor(a, 6))                        # 3
bisect.insort(a, 5)                       # keeps a sorted; O(n) because later items shift
print(a)                                  # [1, 3, 3, 3, 5, 7, 9]
class DSU:
    def __init__(self, n: int):
        self.parent = list(range(n))
        self.size = [1] * n

    def find(self, x: int) -> int:
        while self.parent[x] != x:
            self.parent[x] = self.parent[self.parent[x]]    # path halving
            x = self.parent[x]
        return x

    def union(self, a: int, b: int) -> bool:
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False                                    # already connected
        if self.size[ra] < self.size[rb]:
            ra, rb = rb, ra
        self.parent[rb] = ra                                # attach the smaller tree
        self.size[ra] += self.size[rb]
        return True
class Trie:
    def __init__(self):
        self.root = {}

    def insert(self, word: str) -> None:
        node = self.root
        for ch in word:
            node = node.setdefault(ch, {})
        node["$"] = True                  # end-of-word marker

    def starts_with(self, prefix: str) -> bool:
        node = self.root
        for ch in prefix:
            if ch not in node:
                return False
            node = node[ch]
        return True

Same workload, two structures

▶ Video lesson: List versus heap, counted 4:08 · 6 scenes · narrated, pause anytime and explore

Costs are easier to believe when you watch them add up. A scheduler always runs the task with the smallest priority number next, and new tasks keep arriving. The first scenario keeps a backlog of 12 tasks and repeats a new task arrives, run the smallest. The second is a one-off: take the 4 smallest numbers out of a batch.

Repeatedly take the smallest: list versus heap

Top: a plain list, which must scan everything to find its minimum. Below it: a binary min-heap, whose smallest item is always the root. Watch the two comparison counters in the chips, and step through a full run before you read the final note.

Constants matter at small n. At 12 items the two structures are within a small factor, and for a one-off batch the heap's build cost can erase its edge. Structure choice is about what happens at 10^5 or 10^6 items, or when the same operation repeats thousands of times, which is exactly what interview constraints tell you.

When the obvious choice is wrong

▶ Video lesson: Reading your own slow solution 3:53 · 6 scenes · narrated, pause anytime and explore

Each of these starts from a structure that looks natural and works on the examples, then fails on the large tests.

BFS needs a queue, and a list is not one

List as a queue

queue.pop(0) removes the first item and shifts every other item one slot left. With a million nodes in the queue each pop moves up to a million pointers, so BFS silently becomes O(n²). It passes the samples and times out on the big tests.

def bfs_slow(graph, start):
    queue = [start]
    seen = {start}
    while queue:
        node = queue.pop(0)            # O(n): everything shifts left
        for nxt in graph[node]:
            if nxt not in seen:
                seen.add(nxt)
                queue.append(nxt)

deque.popleft()

A deque is a chain of small blocks with pointers to both ends, so adding or removing at either end touches a constant number of items. BFS is back to O(V + E).

from collections import deque

def bfs(graph, start):
    queue = deque([start])
    seen = {start}
    while queue:
        node = queue.popleft()         # O(1)
        for nxt in graph[node]:
            if nxt not in seen:
                seen.add(nxt)
                queue.append(nxt)

Top k: do you really need everything sorted?

Sort it all, slice k

O(n log n) time and O(n) extra memory, and it needs all the data up front. Fine when n is small or k is close to n. Wasteful when you want the top 10 of a stream of billions, and impossible if the stream never ends.

def k_largest_sorted(nums: list[int], k: int) -> list[int]:
    return sorted(nums, reverse=True)[:k]

Keep a min-heap of size k

The heap holds the k largest values seen so far, with the smallest of them on top. A new value either beats that one (swap it in, O(log k)) or is ignored. O(n log k) time, O(k) memory, works on a stream.

import heapq

def k_largest_heap(nums, k: int) -> list[int]:
    heap: list[int] = []
    for x in nums:
        heapq.heappush(heap, x)
        if len(heap) > k:
            heapq.heappop(heap)        # drop the smallest of the k + 1
    return sorted(heap, reverse=True)

More cases where the first idea is wrong

A set to remove duplicates, but order matters

A set forgets order. list(dict.fromkeys(items)) removes duplicates and keeps the first occurrence of each, in the original order, in O(n).

A heap when you must delete or update an arbitrary item

heapq can only remove the top. Removing the middle is O(n). The standard workaround is lazy deletion: push a fresh entry and, when popping, skip entries that are out of date. Dijkstra's algorithm does exactly this (see Network Delay Time).

A list of tuples as the visited set

(r, c) in visited_list scans the list on every check. A set of tuples is O(1). Tuples are hashable because they are immutable; lists are not, so [r, c] cannot be stored in a set.

Floats or lists as dict keys

Lists are unhashable, so use tuples. Floats hash fine but 0.1 + 0.2 != 0.3, so two values you consider equal may land in different buckets. Use integers, Fraction, or round to a fixed precision.

Recursion for DFS on a very deep structure

CPython's default recursion limit is 1000 frames, so a path of 10^5 nodes raises RecursionError. Use an explicit stack (a list) or raise the limit knowing it risks a crash. See Recursion & the call stack.

Counter when you only need presence

Counter stores a count per key. If the question is 'seen or not', a set is lighter and says what you mean.

Reading your own slow solution

When a solution times out, do not tune the loop. Find the one line inside it that does linear work, and change the container that line touches. Step through the chart: each step is a symptom, the fix, and the new cost.

flowchart LR
  TLE(["Too slow? Find the O(n)<br/>line inside a loop"]) --> Q(["What does that<br/>line do?"])
  Q -- "x in a_list" --> A1["use a set"]
  Q -- "pop(0), insert(0, x)" --> A2["use a deque"]
  Q -- "min or max of changing data" --> A3["use a heap"]
  Q -- "sort after each insert" --> A4["insort, or a heap"]
  Q -- "count(x), index(x)" --> A5["Counter, or a dict<br/>of positions"]
  Q -- "sum(a[l:r]), slices" --> A6["prefix sums"]
  Q -- "s += piece" --> A7["list of pieces,<br/>then join"]
  Q -- "compare every pair" --> A8["sort + two pointers,<br/>or hash"]
Match the slow line to its symptom. In every row the fix replaces one O(n) step with O(1) or O(log n), not the whole algorithm.

Structures that work in pairs

Many classic problems are one structure that is fast at A and slow at B, glued to another that is the opposite. The pairing is the whole trick, so recognise it when you see it.

  TKV["Time-based store"] --> H2["dict<br/>find the key"]
  TKV --> BS["sorted list + bisect<br/>latest at or before t"]
  MS["Min stack"] --> S1["stack<br/>the values"]
  MS --> S2["second stack<br/>running minimum"]

Five problems, each solved by two cooperating structures. Each structure covers the weakness of the other.

When two operations compete: a leaderboard

A leaderboard supports three calls: add_score(player, points), top(k) and rank(player). No single structure is best at all three, so the right design depends on which call dominates. In an interview, ask how often each is called; the answer decides between the rows below.

Before I commit to a structure

A strong answer sounds like: 'The slow part is finding the cheapest pending task: it is a scan of the list, O(n) per step and O(n²) overall. I need the minimum repeatedly while tasks keep arriving, so I'll keep a min-heap: push and pop are O(log n), so the total is O(n log n), and memory is O(n). If I also had to cancel arbitrary tasks I would add a dict of cancelled ids and skip them when they surface.' Operation, current cost, structure, new total, and the one caveat.
