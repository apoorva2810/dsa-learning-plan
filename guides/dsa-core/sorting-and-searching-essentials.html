Sorting & searching essentials

Sorting and binary search sit behind a large share of interview solutions. This chapter steps through insertion, merge, quick and heap sort so you can explain their cost and stability, covers how Python's Timsort and key= work, shows when counting and radix sort beat n log n, and then pins down binary search: one template, the variants (first true, last true, insert position), the classic bugs, and searching on the answer.

After this chapter you can
  • Trace insertion, merge, quick (Lomuto) and heap sort, and state each one's time, extra space and stability
  • Explain stability with an example and use it to sort by several keys
  • Use sorted, list.sort, key= and functools.cmp_to_key, and say what Timsort does (runs, galloping, O(n) on sorted input)
  • Choose counting, bucket or radix sort when the key range is small
  • Write binary search for an exact match, the first true, the last true and an insert position without off-by-one errors
  • Recognise a binary search on the answer and write its feasibility check

Why sorting, and which sorts to know

Sorting turns many O(n²) searches into O(n log n) ones. It is the first move in interval problems (sort by start), two pointers (sort, then converge from both ends), greedy (sort by deadline or by ratio) and top-k questions. In Python you almost always call sorted. In an interview you may still be asked to explain, or to write, the classic algorithms, so know each one's cost, its memory use, and whether it is stable (equal keys keep their original relative order; see below).

Two ideas explain most rows of the table. Incremental sorts (insertion) grow a sorted prefix one item at a time. Divide-and-conquer sorts (merge, quick) split the input and then combine or partition. Heap sort instead extracts the maximum again and again. And there is a hard floor: a sort that only compares items needs at least log2(n!), about n log2 n, comparisons in the worst case, because n items have n! possible orders and each comparison can at best halve the possibilities.

What the growth rates mean at scale

Sort a million items at ten million comparisons per second, a rough CPython-scale budget. The O(n log n) sorts take a couple of seconds; a quadratic sort needs hours.

Which sort? Key range first, then 'is the library allowed', then size and order, then stability and memory.

When asked 'which sort would you use?', a strong answer is: 'In Python, sorted. It is Timsort: stable, O(n log n) worst case and O(n) on data that is already mostly ordered. If I had to implement one myself I would write merge sort when I need stability or a guaranteed bound, and quick sort with a random pivot when I need it in place.'

Insertion sort: the sorted prefix

Sorting a hand of playing cards is insertion sort. Keep the cards you have placed so far in order; pick up the next card, slide it left past every larger card, and let go. The shaded prefix is always sorted; each new key is inserted into it.

The cost is the number of shifts, which equals the number of inversions (pairs that are out of order). Sorted input has none, so it costs n - 1 comparisons: O(n). Reversed input has n(n-1)/2, so O(n²). It sorts in place and is stable, because the loop moves a key left only past items that are strictly larger. Because it is so fast on short or nearly sorted data, real libraries use it as the base case: Python's sort uses a (binary) insertion sort to build short runs.

Insertion sort

def insertion_sort(a: list[int]) -> None:
    for i in range(1, len(a)):
        key = a[i]
        j = i - 1
        while j >= 0 and a[j] > key:      # strictly greater: equal items keep their order (stable)
            a[j + 1] = a[j]               # shift the larger item right
            j -= 1
        a[j + 1] = key                    # drop the key into the gap

Merge sort: split, then merge

▶ Video lesson: Merge sort: split, then merge 3:56 · 6 scenes · narrated, pause anytime and explore

Merge sort uses one observation: merging two sorted lists is cheap. Walk both with one finger each and always take the smaller head; that is a single pass, O(n). So split the array in half, sort each half the same way (recursion), and merge. A single item is already sorted, which is the base case.

There are log2 n levels of splitting and every level merges n items in total, so the cost is O(n log n) whatever the input order. The price is O(n) extra memory for the merged output. If ties are taken from the left run, equal items keep their order: merge sort is stable. It also works well on linked lists (no extra array needed) and on data too large for memory, and the same split-and-merge idea counts inversions in O(n log n).

Merge sort

def merge_sort(a: list[int]) -> list[int]:
    if len(a) <= 1:
        return a                                   # base case: already sorted
    mid = len(a) // 2
    left, right = merge_sort(a[:mid]), merge_sort(a[mid:])
    out: list[int] = []
    i = j = 0
    while i < len(left) and j < len(right):
        if right[j] < left[i]:                     # strictly smaller: on a tie the LEFT item goes first (stable)
            out.append(right[j])
            j += 1
        else:
            out.append(left[i])
            i += 1
    return out + left[i:] + right[j:]              # one side is empty: append what is left of the other
Slicing copies, which is fine for an interview. The index-based version avoids the copies but has the same O(n log n).

Quick sort: partition around a pivot

Quick sort reverses merge sort's trade. Do the work before recursing: pick a pivot and partition the range so that everything smaller is on its left and everything larger on its right. The pivot is then in its final place, and the two sides are sorted independently. There is no merge step and no extra array.

The Lomuto partition below takes the last item as the pivot. Keep a boundary i for the end of the small region and scan with j; whenever a[j] is small, grow the region and swap it in. At the end swap the pivot into position i + 1.

The cost depends on how even the splits are. Balanced splits give log2 n levels of n work: O(n log n) on average. If every partition peels off a single item, there are n levels: O(n²). A fixed pivot (the last item) on already sorted input does exactly that, so use a random pivot or the median of three. Quick sort is not stable, since swaps jump over equal items.

Quick sort with the Lomuto partition

def quick_sort(a: list[int], lo: int = 0, hi: int | None = None) -> None:
    if hi is None:
        hi = len(a) - 1
    if lo >= hi:
        return
    p = partition(a, lo, hi)
    quick_sort(a, lo, p - 1)
    quick_sort(a, p + 1, hi)

def partition(a: list[int], lo: int, hi: int) -> int:
    pivot = a[hi]
    i = lo - 1                                    # a[lo..i] are all <= pivot
    for j in range(lo, hi):
        if a[j] <= pivot:
            i += 1
            a[i], a[j] = a[j], a[i]
    a[i + 1], a[hi] = a[hi], a[i + 1]             # the pivot lands in its final place
    return i + 1

Quick sort details interviewers ask about

How do you avoid the worst case?

Choose the pivot at random (swap a random item to the end before partitioning) or use the median of the first, middle and last items. Introsort, used by C++ std::sort, also switches to heap sort if the recursion gets too deep, which guarantees O(n log n).

How much memory does it use?

No extra array, but the recursion stack: O(log n) on average. To keep it O(log n) even in the worst case, recurse into the smaller side and loop on the larger one.

What about many equal items?

With <= in the Lomuto test, an array of equal items puts everything in the small region every time, which is the O(n²) case again. A three-way partition (less, equal, greater) handles duplicates in O(n).

What is quickselect?

Partition once, then recurse into only the side that contains position k. The expected cost is n + n/2 + n/4 + ... = O(n). It finds the k-th smallest or largest without sorting everything; see Kth Largest Element in an Array. The heap alternative is O(n log k) and works on streams.

Heap sort: a heap, then drain it

Heap sort turns the array itself into a max-heap (a binary tree stored in the list where each parent is at least as large as its children). Building it bottom-up takes O(n). Then repeat: swap the root, which is the maximum, with the last item of the heap; the maximum is now in its final place; shrink the heap by one and sift the new root down to repair the heap. Each of the n repairs costs O(log n).

The bound is O(n log n) in every case with O(1) extra memory, which is why introsort keeps it as a fallback. It is not stable, and because it jumps around the array it is slower than quick sort in practice. For the heap structure itself see Heap / Priority Queue and Choosing the right data structure.

Heap sort, in place

def heap_sort(a: list[int]) -> None:
    n = len(a)

    def sift_down(i: int, size: int) -> None:
        while True:
            big, left, right = i, 2 * i + 1, 2 * i + 2
            if left < size and a[left] > a[big]:
                big = left
            if right < size and a[right] > a[big]:
                big = right
            if big == i:
                return
            a[i], a[big] = a[big], a[i]
            i = big

    for i in range(n // 2 - 1, -1, -1):           # phase 1: build a max-heap in O(n)
        sift_down(i, n)
    for end in range(n - 1, 0, -1):               # phase 2: move the max to the end, repair, repeat
        a[0], a[end] = a[end], a[0]
        sift_down(0, end)

Stability, and what Python's sort does

A sort is stable if items with equal keys keep their original relative order. It sounds like a detail until you sort records by more than one key. Sort by the less important key first, then by the more important key with a stable sort: the second pass leaves items that tie on the important key in the order the first pass put them.

Timsort, the sort behind sorted and list.sort

Python's sort is Timsort, designed by Tim Peters for real data, which is rarely random: it often contains long stretches that are already ordered. It is stable, never worse than O(n log n), and takes O(n) comparisons on input that is already sorted (or reversed), because it sees one long run and has nothing to merge.

flowchart LR
  IN["Input list"] --> RUNS["Find natural runs:<br/>ascending, or descending then reversed"]
  RUNS --> EXT["Extend short runs to a minimum length<br/>with binary insertion sort"]
  EXT --> STK["Push runs on a stack"]
  STK --> MRG["Merge neighbouring runs<br/>of similar size"]
  MRG -.-> GAL["Galloping: when one run keeps winning,<br/>leap ahead by doubling steps"]
  MRG --> OUT["One sorted list"]
Timsort in one picture: detect order that already exists, make short runs with insertion sort, merge runs of similar size.

Python's sorting API

sorted(iterable) returns a new list from any iterable. list.sort() sorts in place and returns None, so a = a.sort() is a classic bug. Both accept key= and reverse=.

nums = [3, 1, 2]
print(sorted(nums))          # [1, 2, 3]; nums is unchanged
nums.sort()                  # in place; returns None
nums.sort(reverse=True)      # [3, 2, 1]; reverse=True still keeps equal items in their original order
print(nums)

key is called once per item, and the sort then compares the keys with <. Return a tuple to sort by several fields; negate a number to reverse just that field.

words = ["pear", "fig", "banana", "kiwi"]
print(sorted(words, key=len))                           # ['fig', 'pear', 'kiwi', 'banana'] (pear stays before kiwi: stable)

people = [("Ann", 25), ("Bob", 22), ("Cat", 25), ("Dan", 22)]
print(sorted(people, key=lambda p: p[1]))               # [('Bob', 22), ('Dan', 22), ('Ann', 25), ('Cat', 25)]
print(sorted(people, key=lambda p: (-p[1], p[0])))      # age descending, then name ascending

Python 3 has no cmp= argument. When the order is defined by comparing two items (not by a key you can compute for one), wrap a comparison function with functools.cmp_to_key. Classic case: arrange numbers to form the largest concatenation.

from functools import cmp_to_key

def largest_number(nums: list[int]) -> str:
    strs = [str(n) for n in nums]

    def compare(a: str, b: str) -> int:
        if a + b > b + a:
            return -1                    # a first: a + b makes the bigger number
        if a + b < b + a:
            return 1
        return 0

    strs.sort(key=cmp_to_key(compare))
    return "0" if strs[0] == "0" else "".join(strs)

print(largest_number([3, 30, 34, 5, 9]))    # 9534330

Stability lets you sort by several keys one pass at a time, least important key first. A tuple key does the same in one pass; use two passes when one key must go ascending and another descending and negation is not possible (strings).

rows = [("Eve", "HR"), ("Bob", "IT"), ("Ann", "HR"), ("Dan", "IT")]
rows.sort(key=lambda r: r[0])        # pass 1: by name
rows.sort(key=lambda r: r[1])        # pass 2: by department; stability keeps names ordered inside each
print(rows)                          # [('Ann', 'HR'), ('Eve', 'HR'), ('Bob', 'IT'), ('Dan', 'IT')]

Python sorting gotchas

Mixing types

sorted([3, 'a']) raises TypeError: Python 3 will not compare an int with a str. Convert first or give a key.

Sorting a dict by value, with a tie-break

sorted(counts.items(), key=lambda kv: (-kv[1], kv[0])) orders by count descending, then key ascending. Counting first with Counter and then sorting is the usual shape of top-k problems; Top K Frequent Elements can also be solved with a bucket sort in O(n).

Lists of lists compare element by element

[1, 5] < [1, 7] is True. That is why sorting intervals with intervals.sort() orders them by start and then by end, which is what Merge Intervals needs.

Sorting is O(n log n): do it once

Sorting inside a loop turns O(n log n) into O(n² log n). Sort once outside, or keep the data in a heap or with bisect.insort if items keep arriving.

Beating n log n when keys are small

The n log n floor applies only to sorts that compare items. If the keys are integers in a small range, you can sort without comparing at all.

  • Counting sort counts how many times each key occurs (an array of size k), turns the counts into running totals (the end position of each key in the output), and then places the items. Time and space are O(n + k). Place items scanning the input from right to left to keep it stable.
  • Radix sort sorts by one digit at a time, least significant digit first, using a stable sort (such as counting sort) for each digit. For d-digit numbers in base b it costs O(d (n + b)), which beats n log n when d is small.
  • Bucket sort spreads items into buckets by value range, sorts each bucket and concatenates; expected O(n) when the values are spread evenly.

You will meet this idea in problems that sort by frequency (a count can only be 1 to n, so bucket by count) or by a small alphabet (26 letters): see Top K Frequent Elements and Valid Anagram.

Counting sort and radix sort in Python

def counting_sort(nums: list[int], k: int) -> list[int]:
    """Sort integers in range(k) in O(n + k)."""
    count = [0] * k
    for x in nums:
        count[x] += 1
    for v in range(1, k):
        count[v] += count[v - 1]              # count[v] is now the end position of value v
    out = [0] * len(nums)
    for x in reversed(nums):                  # right to left keeps equal items in input order: stable
        count[x] -= 1
        out[count[x]] = x
    return out

print(counting_sort([2, 5, 3, 0, 2, 3, 0, 3], 6))   # [0, 0, 2, 2, 3, 3, 3, 5]
def radix_sort(nums: list[int]) -> list[int]:
    """Least-significant-digit radix sort for non-negative integers."""
    exp = 1
    biggest = max(nums, default=0)
    while biggest // exp > 0:
        buckets: list[list[int]] = [[] for _ in range(10)]
        for x in nums:                        # appending in order makes each pass stable
            buckets[(x // exp) % 10].append(x)
        nums = [x for bucket in buckets for x in bucket]
        exp *= 10
    return nums

print(radix_sort([170, 45, 75, 90, 802, 24, 2, 66]))   # [2, 24, 45, 66, 75, 90, 170, 802]

Binary search: one template, three variants

▶ Video lesson: Binary search: find the boundary 4:12 · 7 scenes · narrated, pause anytime and explore

Binary search is not really about sorted arrays. It works whenever you can ask a yes/no question whose answers, in index order, look like No No No Yes Yes Yes: the answer flips once. A sorted array gives that for questions like "is a[i] >= x?". Each step asks the question at the middle, learns which half cannot contain the flip, and throws that half away, so n items take about log2 n steps (a million items, 20 steps).

Before writing a line, say the invariant aloud: what range is guaranteed to still contain the answer? Then every line of the loop either keeps that promise or shrinks the range. The two templates below use different range conventions: closed (lo..hi both included) for the exact match, half-open (lo..hi-1, with hi as a sentinel meaning "none") for boundaries. Learn both; never mix them inside one function.

Template 1: exact match, closed range [lo, hi]

def binary_search(a: list[int], target: int) -> int:
    lo, hi = 0, len(a) - 1                  # invariant: if target is present, it is in a[lo..hi]
    while lo <= hi:
        mid = lo + (hi - lo) // 2           # same as (lo + hi) // 2 in Python; the safe habit for Java or C++
        if a[mid] == target:
            return mid
        if a[mid] < target:
            lo = mid + 1                    # mid is ruled out, and so is everything left of it
        else:
            hi = mid - 1                    # mid is ruled out, and so is everything right of it
    return -1                               # the range is empty: not present

Template 2: first True, half-open range [lo, hi)

def first_true(lo: int, hi: int, ok) -> int:
    """Smallest x in [lo, hi) with ok(x) True, or hi if there is none.
    ok must look like False, False, ..., True, True over the range."""
    while lo < hi:                          # invariant: the answer is in [lo, hi]
        mid = (lo + hi) // 2
        if ok(mid):
            hi = mid                        # mid might be the answer: keep it
        else:
            lo = mid + 1                    # mid is not the answer: drop it
    return lo                               # lo == hi

# last True in [lo, hi]: the answer is one before the first False
def last_true(lo: int, hi: int, ok) -> int:
    return first_true(lo, hi + 1, lambda x: not ok(x)) - 1

Binary search with lo, mid and hi

Dimmed cells have been ruled out. The first two scenarios use the closed-range template; the last two use the half-open boundary template, where the ∅ cell on the right is the sentinel position n.

bisect in practice

import bisect

a = [1, 2, 4, 4, 4, 4, 7, 9, 12, 15]
print(bisect.bisect_left(a, 4))                       # 2: first index with a[i] >= 4
print(bisect.bisect_right(a, 4))                      # 6: first index with a[i] > 4
print(bisect.bisect_right(a, 4) - bisect.bisect_left(a, 4))   # 4 copies of 4

def contains(a: list[int], x: int) -> bool:
    i = bisect.bisect_left(a, x)
    return i < len(a) and a[i] == x                   # check the bounds first: i can be len(a)

def floor(a: list[int], x: int):
    """Largest element <= x, or None."""
    i = bisect.bisect_right(a, x)
    return a[i - 1] if i else None

def ceiling(a: list[int], x: int):
    """Smallest element >= x, or None."""
    i = bisect.bisect_left(a, x)
    return a[i] if i < len(a) else None
From Python 3.10, bisect functions also accept key=, applied to the items of the list (not to x).

The classic bugs, and searching on the answer

▶ Video lesson: Binary search on the answer 4:09 · 6 scenes · narrated, pause anytime and explore

Last True: the infinite loop

Rounds down, then sets lo = mid

With lo = 3, hi = 4, the middle (3 + 4) // 2 is 3, the same as lo. If ok(3) is true then lo = mid changes nothing, and the loop repeats forever.

def last_true_buggy(lo: int, hi: int, ok) -> int:
    while lo < hi:
        mid = (lo + hi) // 2           # rounds DOWN
        if ok(mid):
            lo = mid                    # no progress when hi == lo + 1
        else:
            hi = mid - 1
    return lo

Round up when you assign lo = mid

Rounding up makes mid strictly greater than lo whenever lo < hi, so each branch shrinks the range. The rule: if a branch keeps mid (lo = mid or hi = mid), the rounding of mid must push away from that pointer.

def last_true(lo: int, hi: int, ok) -> int:
    while lo < hi:
        mid = (lo + hi + 1) // 2       # rounds UP
        if ok(mid):
            lo = mid                    # mid stays: lo moves because mid > lo
        else:
            hi = mid - 1
    return lo

More binary search bugs (click each)

Off by one on hi

Mixing the two conventions is the most common bug. hi = len(a) with while lo <= hi reads a[len(a)] and raises IndexError. hi = len(a) - 1 with while lo < hi never checks the last candidate. Pick one pair and stay in it: closed [lo, hi] with <= and mid ± 1, or half-open [lo, hi) with <, hi = mid and lo = mid + 1.

Using the result without checking the bounds

A boundary search can return len(a) when no item passes the test. a[lo] then fails. Check lo < len(a) before indexing, as in the contains helper above.

A predicate that is not monotone

Binary search silently returns garbage if the answers do not flip exactly once. A rotated array is not sorted, so Search in Rotated Sorted Array first decides which half is sorted, then searches there. Find Minimum in Rotated Sorted Array uses the monotone test 'is a[i] <= a[-1]?'.

Duplicates and exact match

The exact-match template returns some matching index, not the first or last. For 'first occurrence' use bisect_left; for 'last occurrence' use bisect_right - 1.

Overflow in other languages

(lo + hi) // 2 cannot overflow in Python, whose integers are unbounded. In Java or C++ it can, so write lo + (hi - lo) / 2 out of habit.

Floating-point searches

For real-valued answers (a square root, a minimum time) lo < hi may never become false. Loop a fixed number of times (60 to 100 halvings is plenty) or until hi - lo < eps.

Binary search on the answer

Sometimes the thing you search is not an index but a value of the answer itself. The shape: "find the smallest (or largest) X such that something is possible", where possibility is easy to check for a given X and only ever gets easier as X grows. Define feasible(x), confirm it flips once, pick the range of possible answers, and run first_true.

The recipe for any 'smallest x that works' problem. The check is usually a short greedy loop.

Koko Eating Bananas: searching the answer

The bars show the hours needed at each speed, with the limit h as a line. The pattern 'too slow, too slow, then fast enough from here on' is the False..True shape. Binary search finds the flip after evaluating only a few speeds.

Two problems, one recipe

Smallest eating speed that finishes all piles within h hours. See Koko Eating Bananas.

def min_eating_speed(piles: list[int], h: int) -> int:
    def can_finish(k: int) -> bool:
        return sum((p + k - 1) // k for p in piles) <= h      # ceil(p / k) hours per pile

    lo, hi = 1, max(piles)             # the answer is in [1, max(piles)]
    while lo < hi:
        mid = (lo + hi) // 2
        if can_finish(mid):
            hi = mid                   # mid works: try slower
        else:
            lo = mid + 1               # mid is too slow
    return lo

Split an array into m contiguous parts so that the largest part sum is as small as possible (LeetCode 410; same shape as shipping packages within D days). The check is greedy: start a new part when adding the next item would exceed the cap.

def split_array(nums: list[int], m: int) -> int:
    def parts_needed(cap: int) -> int:
        parts, current = 1, 0
        for x in nums:
            if current + x > cap:      # this item would overflow the part: start a new one
                parts += 1
                current = 0
            current += x
        return parts

    lo, hi = max(nums), sum(nums)      # the cap is at least the biggest item and at most the whole sum
    while lo < hi:
        mid = (lo + hi) // 2
        if parts_needed(mid) <= m:
            hi = mid                   # the cap works: try a smaller one
        else:
            lo = mid + 1
    return lo

print(split_array([7, 2, 5, 10, 8], 2))   # 18

How the binary-search problems use these templates

  • Binary Search: Template 1, verbatim.
  • Search a 2D Matrix: treat the matrix as one sorted list of rows * cols items; index i is matrix[i // cols][i % cols]; then Template 1.
  • Koko Eating Bananas: search on the answer, first_true over speeds.
  • Find Minimum in Rotated Sorted Array: first_true with the test a[i] <= a[-1]; the minimum is the first item of the second sorted block.
  • Search in Rotated Sorted Array: at each step one half is sorted; test whether the target lies in it, then keep or drop that half.
  • Time Based Key-Value Store: bisect_right on a key's timestamps, minus one, gives the latest value at or before the query time.
  • Median of Two Sorted Arrays: binary search on how many items of the shorter array go to the left half.

Say the invariant before the code: 'I'll keep lo and hi as the range that can still contain the answer, half-open on the right. If mid passes the test it might be the answer, so hi = mid; if it fails it cannot be, so lo = mid + 1. The range shrinks every iteration, so the loop ends, and lo is the answer.' Interviewers listen for that sentence far more than for the code.
