Pattern recognition map

Interview problems are rarely new: they are familiar patterns written in unfamiliar clothes. This chapter teaches you to read a statement for its signals, follow decision trees from signal to pattern, name the template to reach for, and find the problems in the 150 that drill each pattern.

After this chapter you can
  • Pull the signals out of a statement: the input shape, the question word and the limits
  • Use the answer type and the constraints to narrow a problem to a family in under a minute
  • Walk three decision trees from a signal to a pattern for arrays and strings, linked structures and graphs, and counting and optimisation
  • Name the template and a drill problem for each of the 18 topics
  • Tell look-alike patterns apart: sliding window vs prefix sums, BFS vs DFS vs Dijkstra, DP vs greedy
  • Say the signal, pattern and template aloud before writing any code

A statement is a bundle of signals

▶ Video lesson: Read the last sentence first 4:01 · 6 scenes · narrated, pause anytime and explore

Interview problems are rarely new. They are familiar patterns written in unfamiliar clothes: a story about delivery trucks that is really a sliding window, a story about courses that is really a graph. What separates fast solvers from slow ones is not a bigger bag of tricks. It is reading the statement for signals: small phrases that point to a pattern.

Signals come in three layers:

  • The input: its shape and any promised property. Sorted, a tree node, a grid, [start, end] pairs, a string of brackets, a linked list head.
  • The question: the verb and the type of answer. Longest, how many ways, return all, fewest steps, k-th largest, is it possible.
  • The limits: n <= 20 allows exponential search, n up to 10^5 asks for O(n log n) or better, a value up to 10^9 begs for a logarithm.

Each layer narrows the field. The input and the question together usually name the pattern; the limits confirm it or send you back. Start with the cheapest layer to read: what kind of answer must the function return?

flowchart LR
  READ(["Read the last sentence:<br/>what must I return?"]) --> ANS(["What kind<br/>of answer?"])
  ANS -- "yes or no" --> YN["Check a property"]
  ANS -- "one number" --> NUM["Optimise or count"]
  ANS -- "an index, value, node" --> ONE["Find one thing"]
  ANS -- "every answer" --> MANY["Generate them all"]
  ANS -- "an order" --> ORD["Rearrange or schedule"]
  YN --> YN2["hash set, two pointers, BFS or DFS,<br/>greedy check, boolean DP"]
  NUM --> NUM2["DP, greedy, sliding window, heap,<br/>binary search on the answer"]
  ONE --> ONE2["hash map, binary search, stack,<br/>two pointers, tree search"]
  MANY --> MANY2["backtracking on a tiny input"]
  ORD --> ORD2["sort, heap, topological sort"]
Step 1 of the method: the answer type picks the family before you read any detail.

Saying 'the answer is a single number and the choices overlap, so I'm thinking DP' before you touch the keyboard is worth more than silent typing. The interviewer sees your reasoning, and a wrong guess at this stage costs ten seconds to correct instead of twenty minutes.

Constraints are signals too

The limits in the statement are the problem setter telling you which complexity is expected. As a rule of thumb for CPython with a few seconds of budget, count on roughly 10^7 simple steps per second; the intended solution fits comfortably inside that.

Three decision trees: from signal to pattern

▶ Video lesson: Walking Tree A and Tree B 4:24 · 6 scenes · narrated, pause anytime and explore

Three trees cover the 150. Tree A is for flat input (arrays, strings, numbers). Tree B is for input with links: lists, trees, grids, graphs and words. Tree C is for questions that count, optimise or list. In every tree, the first yes wins, so the questions are ordered from the cheapest signal to the vaguest.

Tree B: decide what the input is, then, for grids and graphs, what the question asks for.

Tree C: counting, optimising and listing

flowchart TD
  C0(["Count, optimise<br/>or list"]) --> C1{"Must I list every answer,<br/>with a tiny input?"}
  C1 -- yes --> BT["Backtracking"]
  C1 -- no --> C2{"Input is [start, end] pairs?"}
  C2 -- yes --> IV["Sort, then sweep<br/>merge, heap of end times"]
  C2 -- no --> C3{"Bits, XOR, 32-bit<br/>or digit arithmetic?"}
  C3 -- yes --> BM["Bit tricks or math"]

  C4 -- yes --> BA["Binary search on the answer"]
  C4 -- no --> C5{"Min, max, count or possible<br/>over a sequence of choices?"}
  C5 -- yes --> C6{"Does a small counterexample break<br/>'always take the best now'?"}
  C6 -- yes --> DP["Dynamic programming"]

Tree C: the DP versus greedy decision is the last question, after the cheap and explicit signals are ruled out.

More than one branch often fits. Prefer the pattern that uses every promise in the statement. Sorted plus pair with a target fits both a hash map and two pointers, but only two pointers uses the sorted promise to need no extra memory.

Patterns against signals

Which signal points at which pattern

● means the signal points straight at the pattern. ○ means it is a plausible alternative worth checking. Read a row to learn what triggers a pattern; read a column to see which patterns compete for a signal. A column with several ● (cycle) is a reminder to ask what kind of graph or list you have.

Two columns teach the most. Cycle has three strong answers (fast and slow pointers for a list, union-find for an undirected graph, topological sort for a directed one), so the next question is always what is the structure? Optimal substructure is the only column where DP is the strong answer and greedy only a maybe: that is the counterexample test from Tree C.

Look-alikes: telling neighbours apart

▶ Video lesson: Telling look-alikes apart 4:06 · 7 scenes · narrated, pause anytime and explore

Most wrong turns come from two patterns that look alike on the surface. The most common pair is a sliding window and a prefix-sum count: both talk about contiguous subarrays, but only one survives negative numbers.

Count subarrays with sum k, when the numbers can be negative

Sliding window (wrong)

A window works only when growing it pushes the sum one way and shrinking pushes it the other. With negative numbers a longer window can have a smaller sum, so 'shrink while too big' throws away windows that would have worked. On [1, -1, 1] with k = 1 this returns 2; the right answer is 3.

def count_subarrays_wrong(nums: list[int], k: int) -> int:
    left = total = count = 0
    for right, x in enumerate(nums):
        total += x
        while total > k and left <= right:    # assumes shrinking always lowers the sum
            total -= nums[left]
            left += 1
        if total == k:
            count += 1
    return count

Prefix sums + hash map

A subarray nums[i..j] sums to k exactly when prefix[j+1] - prefix[i] == k. Keep a count of every prefix sum seen so far; at each position, the number of earlier prefixes equal to prefix - k is the number of subarrays ending here. No monotonicity needed: O(n) time, O(n) memory.

from collections import defaultdict

def count_subarrays(nums: list[int], k: int) -> int:
    seen = defaultdict(int)
    seen[0] = 1                         # the empty prefix
    prefix = count = 0
    for x in nums:
        prefix += x
        count += seen[prefix - k]       # earlier prefixes that leave exactly k in between
        seen[prefix] += 1
    return count

Pairs that get confused (click each)

Two pointers or sliding window?

Ask what lives between the pointers. If the pointers are just two positions that converge on a target (sum of the two values), it is two pointers. If you maintain something about the range between them (a count, a sum, a set of letters) while the range grows and shrinks, it is a sliding window. See Two Pointers and Sliding Window.

BFS, DFS or Dijkstra?

Equal-cost steps and the word fewest or shortest: BFS. Regions, counts, reachability: either, and DFS is shorter. Edges with different non-negative costs: Dijkstra. Negative edges or a limit on the number of edges: Bellman-Ford. A path that must not reuse a cell: backtracking. See Graphs and Advanced Graphs.

DFS flood fill or union-find?

A one-off count of components on a fixed graph: DFS or BFS is simplest. Edges arrive over time, or you answer repeated 'are these connected?' questions: union-find. Both appear in Number of Islands and Number of Connected Components in an Undirected Graph.

DP or greedy?

Try to break greedy with a tiny input. Coins 1, 3, 4 and amount 6: greedy gives 4+1+1, the best is 3+3, so it is DP (Coin Change). If you cannot break it and can explain why the local choice is safe, greedy is faster and shorter (Jump Game, Gas Station).

DP or backtracking?

Both explore choices. If the problem asks you to list every solution, it is backtracking and the output is exponential anyway. If it asks only for a count or a best value and the same sub-problems repeat, it is DP. Backtracking with a cache on its arguments is top-down DP.

Heap or sort?

Need everything ordered, once: sort. Need only the k best, or the best of a collection that keeps changing: heap (Kth Largest Element in an Array, Find Median from Data Stream). See Choosing the right data structure.

Hash map or sort plus two pointers?

A hash map is O(n) time and O(n) memory and keeps original indices. Sorting plus two pointers is O(n log n) time and O(1) extra memory but loses the indices, which matters when the answer is a pair of indices (Two Sum versus Two Sum II - Input Array Is Sorted).

Binary search or two pointers on a sorted array?

Binary search finds one position or boundary in O(log n). Two pointers walk the array to compare pairs in O(n). If the question is 'where is x' or 'the smallest value that works', binary search; if it is 'which pair', two pointers. See Sorting & searching essentials.

Saying it out loud

Before I write code, I have said

A strong answer sounds like: 'The array is sorted and I need two numbers with a given sum. That is a two-pointer problem: one pointer at each end; if the sum is too small I move the left one right, otherwise the right one left. It is O(n) time and O(1) space. A hash map would also be O(n) but needs O(n) memory, so I would mention it as the alternative if the array were not sorted.' Signal, pattern, template, complexity, alternative.

When the signals do not settle it, say that too: 'Two things fit, a heap and a sorted list. The list gives me ranks but costs O(n) per insert; the heap is O(log n) but cannot answer rank queries. Which operation matters most here?' Naming the trade-off is itself a strong signal. The method for the rest of the conversation is in How to approach any problem.
