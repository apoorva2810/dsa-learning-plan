What data structures look like in memory

Complexity tables tell you what an operation costs; the memory layout tells you why. This chapter shows contiguous and linked storage, why arrays beat linked lists in practice (cache lines), and what a Python list, dict, set, string, tuple and deque really are, with simulations of list growth, dict probing and a ring buffer, and the sys.getsizeof numbers behind them.

After this chapter you can
  • Contrast contiguous and linked layouts and predict the cost of indexing, inserting and scanning for each
  • Explain cache lines and why scanning an array beats chasing pointers even when both are O(n)
  • Describe a Python list as a resizable array of pointers, and explain append growth, the O(n) cost of insert(0), and the [[0]*3]*3 aliasing bug
  • Walk through a dict insert and lookup: hash, slot, probe on collision, tombstones, resize at 2/3 full, and why keys must be hashable
  • Explain why string concatenation in a loop can be O(n²), and choose between list, tuple, set, dict and deque for an operation
  • Read a sys.getsizeof table and estimate the memory of a million-element container

Contiguous vs linked

Memory is one long row of numbered byte slots. A data structure is a rule for placing values in that row and finding them again. Two rules underlie almost everything you will meet:

  • Contiguous (array-like). The n elements sit side by side. Element i lives at base + i × element_size, so reading it is one multiplication and one addition: O(1) whatever n is. The price is rigidity. Inserting in the middle means sliding everything after it, and growing past the allocated block means finding a bigger block and copying.
  • Linked. Every element lives in its own node, which stores the value and the address of the next node. Nodes can be anywhere. Inserting after a node you already hold rewires two pointers: O(1). The price is that you cannot compute where element i is; you follow i pointers from the head.
Top: addresses step by a fixed amount, so the CPU can compute where a[3] is. Bottom: each next address is stored inside the previous node.

On paper the linked list wins at inserting and the array wins at indexing. The next section explains why the array also wins most of the 'ties'.

Everything else is built from these two ideas. A hash table is an array indexed by a computed slot. A binary heap is a tree stored in an array (which is why heapq operates on a plain list). A B-tree node is a small sorted array. An adjacency list is an array of lists. When you meet a new structure, ask which parts are contiguous and which are linked; the costs follow.

Cache lines: why arrays win in practice

▶ Video lesson: Cache lines: why arrays win in practice 3:24 · 7 scenes · narrated, pause anytime and explore

Scanning an array and scanning a linked list are both O(n). On a real CPU the array scan is commonly 10 to 100 times faster. The reason is the memory hierarchy: the processor has a few small, fast caches in front of slow main memory.

A CPU does not fetch single bytes from RAM. It fetches a cache line, typically 64 bytes, and keeps it in cache. Reading a[0] pulls in a[0] through a[7] (for 8-byte elements) in one trip, so the next seven reads are cache hits. A hardware prefetcher notices the sequential pattern and requests the next line before you ask. A linked list offers no such pattern: the address of node k + 1 is stored inside node k, so the CPU cannot even start fetching it until node k has arrived. If the nodes were allocated at different times they sit in different lines, and nearly every hop goes all the way to RAM.

A rough cost model for scanning n elements

A model, not a benchmark: it ignores everything except misses and hits. Defaults describe an array of 8-byte slots against a linked list whose every hop misses. Real ratios depend on how the nodes were allocated; a freshly built list with sequential allocation behaves better, an aged one with scattered nodes behaves worse.

Python blurs this picture, so be precise in an interview. A list of ints is a contiguous array of pointers; the int objects live elsewhere, so a scan still dereferences one pointer per element. A linked list built from Python objects is worse (every node is a full object), and interpreter overhead of tens of nanoseconds per bytecode hides some of the cache effect. The principle still holds, and it is fully visible when you switch to array.array or NumPy, which store raw values back to back.

A Python list is an array of pointers

▶ Video lesson: A Python list is an array of pointers 4:17 · 7 scenes · narrated, pause anytime and explore

A CPython list is a small header (length, allocated capacity, pointer to the array) plus a separate C array of 8-byte pointers to the element objects, which live elsewhere on the heap. Every slot costs 8 bytes whatever it refers to. a[i] is ob_item[i]: O(1). Small ints (−5 to 256) and interned strings are shared singletons, so many slots can point at the same object.

flowchart LR
  H["list header<br/>len 3, allocated 4<br/>56 bytes"] --> P["ob_item<br/>array of pointers<br/>4 slots x 8 bytes"]
  P --> I0["int 1000<br/>28 bytes"]
  P --> I1["int 2000<br/>28 bytes"]
  P --> I2["int 3000<br/>28 bytes"]
  P -.-> S3["spare slot"]
The list owns the pointer array; the ints are separate objects. sys.getsizeof measures the first two boxes only.

Multiplying a list repeats the pointers. Fine for immutable items, a bug for mutable ones.

The aliasing bug, and the identity check that exposes it

bad = [[0] * 3] * 3
bad[0][0] = 1
print(bad)                    # [[1, 0, 0], [1, 0, 0], [1, 0, 0]]   one row, three names
print(bad[0] is bad[1])       # True: the same object

good = [[0] * 3 for _ in range(3)]
good[0][0] = 1
print(good)                   # [[1, 0, 0], [0, 0, 0], [0, 0, 0]]
print(good[0] is good[1])     # False

alias = good                  # the same list object
copy = good[:]                # a new pointer array, but the rows are still shared
print(alias is good, copy is good, copy[0] is good[0])    # True False True
is compares object identity. When two 'different' lists change together, check is first. For a real copy of nested data use copy.deepcopy or rebuild the rows.

Dicts and sets: hash tables in CPython

▶ Video lesson: Inside a dict: hash, slot, probe 4:24 · 6 scenes · narrated, pause anytime and explore

A dict maps keys to values without scanning. It turns each key into an integer with hash(key) and uses that integer to choose a slot. Since Python 3.6, CPython keeps two arrays:

  • indices: a sparse array whose length is a power of two (8, 16, 32, …). Each cell is empty, a tombstone, or the number of an entry.
  • entries: a dense array of (hash, key, value) triples in insertion order. This is why dicts remember insertion order (guaranteed since 3.7) and why iterating a dict is fast.

Lookup. Take i = hash & mask (mask = size − 1). If indices[i] is empty, the key is absent. Otherwise inspect that entry: if its stored hash matches and the keys are identical (is) or equal (==), you are done. If not, it is a collision (two keys wanted the same slot) and the search moves to another slot, computed as i = (5·i + perturb + 1) & mask, where perturb starts as the whole hash and is shifted right 5 bits each round. All of this happens inside one table, which is called open addressing. (Java's HashMap instead chains colliding entries in a list.)

flowchart TD
  K["key"] --> H["h = hash of key"]
  H --> S["slot i = h and mask"]
  S --> E{"indices at i<br/>empty?"}
  E -->|"yes"| NF["absent"]
  E -->|"no"| M{"stored hash and key<br/>match?"}
  M -->|"yes"| F["found: return value"]
  M -->|"no, collision"| P["next slot:<br/>5 times i, plus perturb, plus 1"]
  P --> E
The lookup loop. Every extra trip around the loop (slot empty? → match? → next slot) is a collision; keeping the table at most 2/3 full keeps the expected number of trips small.

Insert probes the same way to the first free slot, appends the entry to entries, and writes its number into indices. Resize. A table is kept at most 2/3 full. When the entries array is full (5 of 8 usable, then 10 of 16, then 21 of 32, …) the next insertion allocates a table sized from 3 × live entries (rounded up to a power of two), copies the live entries over in order, and rebuilds indices. One resize costs O(n) but happens after Θ(n) inserts, so insertion is amortised O(1), by the same argument as append. Delete cannot simply empty a slot: another key's probe path may run through it, so the slot becomes a tombstone that lookups skip. Space is reclaimed at the next resize.

Run the simulation. Keys 3, 11, 19, 27 all want slot 3 in an 8-slot table; the sixth insertion triggers a resize; a delete leaves a tombstone. The second scenario gives every key the same hash to show the worst case.

Inside a dict: collisions, resize, tombstones

The top array is the sparse indices (slot → entry number, with the key written under each used slot). The lower array is the dense entries, and the small table is what Python code sees. The pointer marks the slot being examined; red slots are collisions.

Why keys must be hashable and (effectively) immutable. The table finds a key by recomputing hash(key). If a key could change after insertion, its hash would change and the entry would sit in a slot nobody looks at. Hence TypeError: unhashable type: 'list'. The contract is: if a == b then hash(a) == hash(b). Define __eq__ on your class and you must define a consistent __hash__, or leave instances unhashable. A tuple is hashable when all its elements are, which is why (row, col) works as a visited-set key in grid problems.

Sets are the same idea without values. Each slot stores (hash, key) directly (there is no separate entries array), so a set has no insertion order: iteration follows the table. CPython's set also probes a handful of neighbouring slots before jumping, because adjacent slots share a cache line. Sets resize when about 3/5 full, to roughly four times their element count while small, so their size jumps in big steps. The practical rules: use a set for membership tests, and never x in some_list inside a loop.

Strings and tuples: immutability and its costs

A str is an immutable array of characters. CPython stores 1, 2 or 4 bytes per character depending on the widest character in the string (PEP 393), so an ASCII string costs 41 bytes plus one per character on CPython 3.12. s[i] and len(s) are O(1); slicing and concatenation copy, O(size of the result); == stops at the first difference; the hash is computed once and cached inside the object, which makes strings cheap dict keys.

Immutability means you can never edit a string in place. Every "change" builds a new one, and that sets a trap: appending to a string in a loop.

Building a string: concatenate vs join

s += piece in a loop

def build(pieces):
    s = ""
    for p in pieces:
        s += p            # may allocate a new string and copy everything so far
    return s

# worst case: 1 + 2 + ... + n characters copied  ->  O(n^2)

Collect, then join once

def build(pieces):
    parts = []
    for p in pieces:
        parts.append(p)   # O(1) amortised, no characters copied
    return "".join(parts) # one pass: allocate the final size, copy each piece once

# O(total length)

The honest version of the story has a wrinkle. CPython can sometimes grow the string in place (realloc) when the variable holds the only reference to it, which makes s += c inside a function look linear. On one run (CPython 3.12) appending 80,000 characters took about 5 ms that way, and ''.join about 4 ms. Add a second reference to the old string (alias = s before the +=) and the same loop took about 60 ms, with each doubling of n multiplying the time by three to four: quadratic. PEP 8 says not to rely on the trick: it is fragile in CPython and absent in other implementations. In an interview, say 'strings are immutable, so repeated concatenation is O(n²) in the worst case; I collect pieces and join'.

Tuples versus lists. A tuple is a fixed-size array of pointers stored inside the object itself, with no separate buffer and no spare capacity. It cannot grow or have slots reassigned, which makes it smaller (a 3-tuple is 64 bytes; the equivalent list is 88) and hashable. The immutability is shallow: a tuple containing a list still lets you change that list.

deque and the ring buffer

list.pop(0) and insert(0, x) shift every pointer, which is fatal for a queue. The textbook fix is a ring buffer: a fixed array plus a head index (the oldest element) and a size. The next free slot is always (head + size) % capacity, and dequeuing just advances head, also modulo the capacity. Indexes wrap around the end of the array, so nothing ever moves and both ends are O(1). When the buffer is full, allocate a bigger array and copy the elements in logical order starting at head; that costs O(n) once per doubling, so appends stay amortised O(1).

A ring buffer in motion

Watch head and tail chase each other around the array. The first scenario is a queue that wraps and then grows; the second adds at the left end too.

CPython's collections.deque gets the same O(1) at both ends with a different layout: a doubly linked list of 64-slot blocks. Appending fills the right-hand block and links a new block when it is full; appendleft does the same on the left. Elements inside a block are contiguous (cache friendly), there is no big copy on growth, and the cost of reaching d[i] in the middle is O(n) (it walks blocks), which is why you should not index a deque deeply.

  MB <--> RB["right block<br/>64 slots"]
  RB <-.-> NB["new block<br/>linked on demand"]
A hybrid: linked at the block level, contiguous inside each block.

What things cost in bytes

sys.getsizeof(obj) returns the size of the object itself, not of what it points to. For a list that is the header and the pointer array but not the ints; for a dict it is the tables but not the keys and values. The numbers below were measured on CPython 3.12 (64-bit Linux). Other versions differ by a few bytes: for example str headers shrank by 8 bytes in 3.12.

'Shallow' is the key word. To measure everything an object keeps alive, use tracemalloc (below) or sum the sizes yourself.

Measuring the real footprint of a million integers

import tracemalloc
from array import array

def megabytes(build):
    tracemalloc.start()
    obj = build()                                  # keep a reference so nothing is freed
    current, _peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return current / 1e6

N = 10**6
print(megabytes(lambda: list(range(N))))           # about 40.0: 8 MB of pointers + 32 MB of int objects
print(megabytes(lambda: [0] * N))                  # about  8.0: every slot points at the same 0
print(megabytes(lambda: array("q", range(N))))     # about  8.2: raw 8-byte integers, no objects
print(megabytes(lambda: array("i", range(N))))     # about  4.1: raw 4-byte integers
print(megabytes(lambda: set(range(N))))            # about 65.5
print(megabytes(lambda: dict.fromkeys(range(N))))  # about 73.9
Measured on CPython 3.12. A list of distinct ints costs about 40 bytes per element; the same data as raw machine integers costs 4 to 8.

Saying it in an interview

Questions that probe this chapter

What happens, step by step, on d[key] = value?

Compute hash(key). Mask it to a slot. If the slot is empty, append (hash, key, value) to the entries array and store its number in the slot. If it is occupied by a different key, probe the next slot with i = (5i + perturb + 1) & mask until an empty one is found. If the entries array is full, resize first: roughly double the table and re-slot every live entry. Average O(1); worst case O(n) when many keys collide.

Why is x in my_list O(n) but x in my_set O(1)?

A list stores no information about where a value is, so it compares element by element. A set hashes x and goes straight to the one slot (and its few probe neighbours) where x could be. On 100,000 integers that was about 0.13 s against 0.06 ms for 200 lookups.

Why can a tuple be a dict key but a list cannot?

Keys need a stable hash, and a == b must imply hash(a) == hash(b). A list can change after insertion, so its hash would change and the entry would be lost; Python refuses to hash it. A tuple's contents cannot be reassigned, so its hash (computed from its items) is stable, provided the items are hashable too.

Do dicts and sets keep order?

Dicts keep insertion order (guaranteed since 3.7) because iteration walks the dense entries array. Sets have no entries array; they iterate in table order, which depends on hashes and insertion history. Never rely on set order.

What does del d[k] do to the table?

It leaves a tombstone in indices and empties the entry. Emptying the slot would break the probe path of any key that collided past it. The space comes back only at the next resize, which is why a dict that grew and then shrank can keep its large footprint.

s += c in a loop: O(n) or O(n²)?

In the worst case O(n²), because strings are immutable and each concatenation can copy everything built so far. CPython sometimes resizes in place when nothing else references the string, so a naive benchmark can look linear. Collect pieces in a list and ''.join them.

Queue in Python: list, deque or ring buffer?

list.pop(0) is O(n). Use collections.deque (append, popleft, both O(1)). If you must implement the structure yourself, a ring buffer is the array-based answer: head, size, indexes taken modulo capacity, grow by doubling.

A strong answer to 'how does a Python dict work?' sounds like: 'It is an open-addressing hash table. CPython keeps a sparse array of indices and a dense, insertion-ordered array of entries. A lookup hashes the key, masks it to a slot, and compares the entry there; on a collision it probes the next slot using a recurrence that mixes in higher hash bits. The table is kept under two-thirds full and resized when it fills, so inserts are amortised O(1) and lookups are O(1) on average, O(n) in the degenerate case where everything collides. Deletes leave tombstones so probe chains stay intact.'
