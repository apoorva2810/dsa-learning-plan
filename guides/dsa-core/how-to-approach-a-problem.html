How to approach any problem

A coding interview scores how you reach an answer as much as the answer itself. This chapter gives you a six-step method you can run on any unfamiliar problem, shows it on Two Sum from brute force to a one-pass hash map, tells you what to say at each step, teaches you to read the constraints for the complexity the interviewer expects, and gives you a short playbook for the moment you are stuck.

After this chapter you can
  • Run the six steps (restate, examples and edge cases, brute force, optimise, code, verify) in order on a problem you have not seen
  • Derive an optimal solution from a brute force by naming the repeated work and choosing the structure that removes it
  • Read the input constraints and name the complexity class the problem setter intends (n up to 20, 10^3, 10^5, 10^18)
  • Narrate your reasoning with the phrases that earn credit at each step, and spot the common anti-patterns in your own habits
  • Dry-run your code on a normal case and an edge case before the interviewer asks, and finish with a time and space statement
  • Get unstuck with a fixed playbook instead of going silent

What the interviewer is scoring

A coding round is graded on several signals at once, and the final code is only one of them. Feedback forms usually have headings like these:

  • Problem solving: did you break the problem down, find a workable approach, and improve it when asked?
  • Coding: is the code correct, readable and idiomatic, and did you write it without long stalls?
  • Verification: did you test your own code before being asked, and did you find your own bugs?
  • Communication: could the interviewer follow your reasoning, and did you take hints well?

Two candidates can finish with the same working function and receive very different feedback. One sat silent for ten minutes, produced the optimal solution from memory, and could not say why it works. The other started from brute force, found the wasted work aloud, fixed it, and tested the result. The second candidate scores higher on every heading above, and the second pattern is a habit you can train. The method in this chapter is that habit written down.

If the clock says minute 20 and the board is empty, say the brute force out loud now. A correct slow solution on the board, with its complexity, gives you something to improve and gives the interviewer something to grade. A perfect idea that is still in your head gives neither.

The six steps

The method is a pipeline with one loop: step 6 sends you back to step 5 whenever a trace finds a bug. Each step ends with a concrete output, and producing that output is how you know the step is finished. Click through the diagram, then read the table.

StepYou produceQuestion to ask yourself
1. Restate and clarifyA one-sentence spec and a list of assumptionsWhat exactly goes in, what comes out, and what is guaranteed?
2. Examples and edge casesTwo or three inputs with known answers, one degenerateWhat do my hands do on a small input?
3. Brute forceA correct baseline with time and spaceWhat is the simplest thing that is certainly right, and what does it cost?
4. OptimiseAn approach and a target complexity the interviewer agrees withWhich work is repeated, and which structure removes it?

Finishing a step means you can point at its output.

Two rules keep the method honest. Never skip step 3, even when you recognise the problem: the brute force is the baseline your optimisation is measured against, and explaining it proves you did not just recall an answer. Never start step 5 before the interviewer has heard the plan from step 4. Waiting for a nod costs thirty seconds; discovering after fifteen minutes of typing that the plan was wrong costs the interview.

The method on a real problem: Two Sum

▶ Video lesson: Two Sum: from brute force to one pass 4:27 · 8 scenes · narrated, pause anytime and explore

Two Sum is the smallest problem in which every step matters. Given an array of integers nums and an integer target, return the indices of the two numbers that add up to target. Exactly one solution exists, and the same element may not be used twice. The full statement is Two Sum.

Play the simulation from the start. The first two steps restate the problem and work an example by hand. The grid is step 3: every pair, checked row by row, with a running count. The remaining steps replace the inner loop with a dictionary lookup and show both strategies side by side.

Two Sum: brute force, then the insight, then one pass

Switch scenarios to see the answer in the middle of the array, and the duplicate case [3, 3] that explains why the map is read before it is written.

flowchart LR
  A["Try every pair<br/>O(n^2) time, O(1) space"] --> B["The inner loop is a search<br/>for target - x"]
  B --> C["A search can be a lookup<br/>hash map: value to index"]
  C --> D["One pass: look up first,<br/>then store x<br/>O(n) time, O(n) space"]
The optimisation is a rewrite of the inner loop, not a trick. This shape (search becomes lookup) repeats all over the 150.

Three implementations of Two Sum

Step 3. Correct, no extra memory, O(n²) time. Say it, and code it only if asked.

def two_sum_brute(nums: list[int], target: int) -> list[int]:
    n = len(nums)
    for i in range(n):
        for j in range(i + 1, n):          # j > i: an element never pairs with itself
            if nums[i] + nums[j] == target:
                return [i, j]
    return []                               # the problem promises an answer; be explicit anyway

Step 5. The invariant: before iteration i, seen maps every value in nums[:i] to its index.

def two_sum(nums: list[int], target: int) -> list[int]:
    seen: dict[int, int] = {}               # value -> index of an earlier element
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:                    # look up BEFORE storing x
            return [seen[need], i]
        seen[x] = i
    return []

A follow-up you should expect: if nums is already sorted, two pointers need no extra memory (Two Sum II - Input Array Is Sorted).

def two_sum_sorted(nums: list[int], target: int) -> list[int]:
    lo, hi = 0, len(nums) - 1
    while lo < hi:
        s = nums[lo] + nums[hi]
        if s == target:
            return [lo, hi]
        if s < target:
            lo += 1                         # sum too small: move the small end up
        else:
            hi -= 1                         # sum too big: move the large end down
    return []

The takeaway is the shape of the move, not the problem. The brute force contained a repeated search; a hash map makes a search O(1); the cost is O(n) memory. You will do the same thing on Contains Duplicate, Valid Anagram and Longest Consecutive Sequence, each time with a different structure doing the lookup.

What to say out loud

The interviewer can grade only what they hear, and they can give a hint only to someone who is talking. Narrate decisions, not every hesitation: what you are about to do, why, and what you expect it to cost. The conversation below is a complete Two Sum round compressed to eleven lines. Step through it and notice that every line the candidate speaks belongs to one of the six steps.

sequenceDiagram
  participant Y as You
  participant I as Interviewer
  Y->>I: Restate: array and target in, two indices out, right?
  I-->>Y: Yes, exactly one pair exists
  Y->>I: Clarify: duplicates? negatives? reuse of an element?
  I-->>Y: Duplicates and negatives yes, no reuse
  Y->>I: Examples: 3 2 4 target 6 gives 1 2, and 3 3 target 6 gives 0 1
  Y->>I: Brute force: all pairs, O of n squared time, O of 1 space
  Y->>I: Optimise: the inner loop is a search, so a hash map gives O of n
  I-->>Y: Sounds good, go ahead
  Y->>I: Code: look up before storing, so no element pairs with itself
  Y->>I: Verify: trace 3 3 with target 6, then a one element input
  Y->>I: Close: O of n time and space, sorted input needs only two pointers
Six of the eleven lines come before any code is written. That ratio is the point.

Silence reads as being stuck. Compare 'umm…' with 'I'm weighing two options: sort first for O(n log n) time and no extra memory, or a hash map for O(n) time and O(n) memory. Since the array is unsorted and memory is not mentioned as a constraint, I'll take the hash map.' The second sentence contains no new idea. It contains engineering judgement, and that is what is being scored.

Read the constraints first

▶ Video lesson: Read the constraints first 3:31 · 7 scenes · narrated, pause anytime and explore

Problem setters pick constraints so that the intended solution runs in about a second and slower ones do not. That makes the constraints the cheapest hint in the problem. A workable budget is about 10^8 simple operations. That is generous for C++ or Java. CPython manages only around 10^7 simple operations per second, so treat 10^8 as the ceiling and prefer the cheaper class whenever two fit.

Invert the question: from the largest n, which complexity can you afford?

Constraints also describe values, not only sizes. Values up to 10^9 force 64-bit arithmetic in C++ or Java (Python integers do not overflow, but say so). A small value range (letters, digits, 0 <= x <= 100) invites a counting array instead of a hash map. A grid with m × n ≤ 10^6 cells is a linear-time problem in the number of cells.

Read the constraints before you design. The class on the right of the arrow is what the setter has in mind.

How large can n be?

Set the number of simple operations you can afford. O(n), O(n²), O(n³) and O(2^n) have closed forms; the O(n log n) figure is a one-step approximation of the solution of n·log₂(n) = budget. Use 10^8 for a compiled language and 10^7 for CPython.

When the constraints are missing, ask: 'What input sizes should I expect? That tells me whether an O(n²) approach is acceptable.' Asking this is a senior signal, because it shows you know that the right algorithm depends on the scale.

When you are stuck

Everyone gets stuck, and interviewers watch what you do next. The fix is not a flash of insight, it is a fixed procedure that turns 'I have no idea' into a smaller question. The flowchart is the procedure; the table below it is the lookup from a symptom (what is repeated or slow) to the tool that usually removes it. A good hint request is specific: 'I think the inner loop is really a lookup problem. Is there a structure you'd expect me to use here?' A bad one is 'I'm stuck, can you help?'. The first shows your reasoning and lets the interviewer confirm it with one word.

Anti-patterns to unlearn

Silent coding vs narrated coding

Types for eight minutes without a word

The interviewer sees a cursor moving. They cannot tell a careful plan from a lost candidate, cannot steer you away from a dead end, and have nothing to write under communication except 'quiet'. When a bug appears, you debug alone while they watch.

Says what each block is for

'This loop keeps the invariant that seen holds everything before i.' 'I'm putting the empty-input check first so the rest can assume at least one element.' The interviewer follows the plan, can correct a wrong assumption early, and sees how you debug because you describe it.

Assuming vs asking

Silently assumes the input is friendly

Assumes the array is sorted, non-empty, free of duplicates, and may be modified. Writes code that is correct for the assumed input and wrong for the real one. The first test the interviewer runs is the case you assumed away.

Turns each assumption into a question

'Can the array be empty? Can values repeat? Is it sorted? May I sort a copy, or modify in place?' Each answer removes a branch from the design, and each question shows you know where bugs hide. Write the answers down and use them in the verify step.

'Looks right' vs a dry run

Passes the sample, ships the bug

def two_sum(nums, target):
    seen = {}
    for i, x in enumerate(nums):
        seen[x] = i                    # stored first
        if target - x in seen:
            return [seen[target - x], i]

# sample: two_sum([2, 7, 11, 15], 9) -> [0, 1]   looks right, ship it?
# but two_sum([3, 2, 4], 6)          -> [0, 0]   3 paired with itself

Traces an edge case and finds it

def two_sum(nums, target):
    seen = {}
    for i, x in enumerate(nums):
        if target - x in seen:         # look up first
            return [seen[target - x], i]
        seen[x] = i                    # then store

# dry run [3, 2, 4], target 6:
# i=0 x=3 need=3 seen={}        -> miss, store {3: 0}
# i=1 x=2 need=4 seen={3: 0}    -> miss, store {3: 0, 2: 1}
# i=2 x=4 need=2 seen has 2:1   -> return [1, 2]

More habits that cost points

Jumping to the memorised optimal solution

If you cannot show how you would arrive at the idea, the interviewer assumes you recalled it. The usual follow-up ('now what if the array is sorted?') then breaks you, because you never understood which part of the problem the idea exploits. Walk the brute-force-to-optimal path even when you know the end.

Coding before the plan is agreed

If the interviewer would have rejected the approach, you find out after the typing. Thirty seconds of 'does this direction sound OK?' is the cheapest insurance in the interview.

Debugging by random edits

Flipping < to <= and re-running is not available in a whiteboard-style round, and it reads badly even when it is. Trace the failing input and look at the variable that is wrong first.

Ignoring hints

A hint is the interviewer steering you toward the intended solution. Acknowledge it ('that suggests the order of the elements matters') and use it. Arguing for your current approach after a hint is the worst available move.

Over-engineering

Classes, factories and configuration for a ten-line function signal poor judgement in an algorithm round. Plain functions and clear names are what is being read.

Silently mutating the input

Sorting or overwriting the caller's list changes the contract. If it helps, ask first, or work on a copy and say what it costs in space.

Not stating complexity

Always give time and space without being asked, and include the recursion stack or hidden copies in the space. See Complexity & optimisation.

Verify, then close

Verification is a procedure, not a feeling. Pick the smallest example that exercises the main branch, then walk the code line by line, writing the value of every changing variable after each iteration (the Two Sum simulation above is exactly this table). Repeat with an edge case. Most bugs live at the boundaries, so make the second trace a boundary.

A five-line test harness you can write on the spot

def check(nums, target, expected):
    got = two_sum(nums, target)
    assert sorted(got) == sorted(expected), (nums, target, got)

check([2, 7, 11, 15], 9, [0, 1])               # the sample from the statement
check([3, 2, 4], 6, [1, 2])                    # catches the 'pairs with itself' bug
check([3, 3], 6, [0, 1])                       # duplicates are fine, reusing one element is not
check([-1, -2, -3, -4, -5], -8, [2, 4])        # negatives
check([0, 4, 3, 0], 0, [0, 3])                 # zeros
In an interview you will not run it, but writing the cases down tells the interviewer what you are checking.

Follow-ups to expect on Two Sum (and how to answer)

What if the array is already sorted?

Use two pointers from both ends: O(n) time and O(1) space (Two Sum II - Input Array Is Sorted). The sorted order lets each comparison discard one candidate for good.

What if I need every pair, or the count of pairs?

Keep scanning instead of returning at the first hit, and count with a Counter. To list distinct value pairs, sort and use two pointers while skipping equal values. 3Sum is this idea with one more loop around it.

What if the data does not fit in memory?

Partition the data on a key that both members of a pair share, for example min(x, target - x). Then each partition fits in memory and the hash-map pass runs per partition. Or sort externally and run two pointers.

What if there are many queries with different targets on one array?

Preprocess once. Sort once and answer each query with a two-pointer pass, or build a value-to-indices map once and answer each query in O(n) lookups. State which cost you are optimising.

How fast is a dict lookup, really?

O(1) on average and O(n) in the worst case when many keys collide. The honest answer in an interview is 'amortised constant, linear in the adversarial worst case'. The mechanism is in What data structures look like in memory.

A strong closing sounds like: 'The solution is O(n) time and O(n) space, because the dictionary can hold up to n values. I traded memory for time; if memory were tight and the input sorted, I would switch to two pointers for O(1) space. I traced the duplicate case [3, 3] and the one-element case, and both behave.' It names both complexities, the trade-off, a variation and the evidence, in four sentences.
