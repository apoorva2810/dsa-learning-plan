Merge k Sorted Lists Hard

LeetCode #23 ↗
Status

Merge k sorted linked lists into one sorted list.

Problem

You are given a list lists of k linked lists. Each linked list is sorted in ascending order.

Merge all of them into one sorted linked list and return its head. lists may be empty, and any of the lists in it may be empty.

On this site a test input such as [[1, 4, 5], [1, 3, 4], [2, 6]] is turned into a Python list of three ListNode heads before your function is called.

Constraints

  • k == len(lists)
  • 0 <= k <= 10^4
  • 0 <= len(lists[i]) <= 500
  • -10^4 <= lists[i][j] <= 10^4
  • each lists[i] is sorted in ascending order
  • the total number of nodes N is at most 10^4

Think first try before reading the solution

You already know how to merge two sorted lists in linear time. What does it cost to merge the k lists into the result one after another?
The next node of the answer is always the smallest of the k current fronts. Which data structure gives you the smallest of k items quickly, and lets you add a new one?
Put the head of every list into a min-heap keyed by value (with the list index as a tie-breaker). Pop the smallest, attach it, and push its successor. Alternatively, merge the lists in pairs, round after round, like merge sort.

Key idea

At every moment, the next node of the merged list is the smallest of the k current fronts (the first not-yet-used node of each list). Scanning all k fronts for every node costs O(k) per node, O(N · k) in total.

A min-heap keeps a collection so that its smallest item is always at the top: it is a binary tree stored in a Python list, where every parent is no bigger than its children, and heapq.heappush / heapq.heappop each cost O(log size). Keep exactly one front per list in the heap: pop the smallest, attach it to the answer, and push the next node from the same list. The heap never holds more than k items, so each of the N nodes costs O(log k): O(N log k).

Divide and conquer reaches the same bound without a heap: merge list 0 with 1, 2 with 3, and so on. Each round halves the number of lists and moves every node once, and there are about log k rounds. Merging the lists one by one into a growing result is the trap: the first list's nodes get walked again in every one of the k merges.

Approaches from the obvious one to the one you want in an interview

Walk every list, copy all N values into one Python list, sort it, and build a new linked list from the sorted values.

Simple and correct, O(N log N) time. It ignores that each input is already sorted, which is what allows O(N log k) (much better when k is small compared to N), and it uses O(N) extra memory for the values and new nodes.

Python

class Solution:
    def mergeKLists(self, lists: List[Optional[ListNode]]) -> Optional[ListNode]:
        values = []
        for node in lists:
            while node:                      # copy every value out
                values.append(node.val)
                node = node.next
        values.sort()
        dummy = tail = ListNode()
        for v in values:                     # rebuild a sorted list
            tail.next = ListNode(v)
            tail = tail.next
        return dummy.next
Time O(N log N)Space O(N)

Sorting N values dominates; N = total number of nodes.

When to use: A fine first answer to state; then improve it using the sorted inputs.

Keep a min-heap with one entry per non-empty list: its current front node, as (value, list index, node).

  1. Push every non-empty head.
  2. Pop the smallest entry, attach its node to the answer (tail.next = node; tail = node).
  3. If that node has a successor, push it: it is the new front of the same list.
  4. Repeat until the heap is empty.

The heap holds at most k entries, so each push and pop costs O(log k), and each of the N nodes is pushed and popped once. The list index in the tuple is a tie-breaker: it stops Python from comparing two ListNodes, which it cannot do.

Dry run

  1. [[1,4,5], [1,3,4], [2,6]]: heap = {1 (list 0), 1 (list 1), 2 (list 2)}
  2. pop 1 (list 0), push 4 → heap {1, 2, 4}; pop 1 (list 1), push 3 → {2, 3, 4}
  3. pop 2 (list 2), push 6; pop 3, push 4; pop 4 (list 0), push 5; pop 4 …
  4. heap empty → [1, 1, 2, 3, 4, 4, 5, 6]

Python

class Solution:
    def mergeKLists(self, lists: List[Optional[ListNode]]) -> Optional[ListNode]:
        heap = []
        for i, node in enumerate(lists):
            if node:                                       # skip empty lists
                heapq.heappush(heap, (node.val, i, node))  # i breaks ties
        dummy = tail = ListNode()
        while heap:
            val, i, node = heapq.heappop(heap)             # smallest front
            tail.next = node
            tail = node
            if node.next:                                  # the same list's next node
                heapq.heappush(heap, (node.next.val, i, node.next))
        return dummy.next
Time O(N log k)Space O(k)

N pushes and N pops on a heap of at most k entries.

When to use: The usual interview answer, and the right tool when lists arrive as streams.

Reuse the two-list merge. In each round, merge list 0 with list 1, list 2 with list 3, and so on; an unpaired last list moves on unchanged. The number of lists halves every round, so there are about log₂ k rounds, and within one round every node is moved at most once (O(N) per round).

Total O(N log k), the same as the heap, and no heap is needed: the only extra memory is the list of each round's results (O(k)), or O(1) if you merge in place by index. Compare this with merging one by one into a growing result, which re-walks the early nodes k times: O(N · k).

Dry run

  1. round 1: merge [1,4,5] + [1,3,4] → [1,1,3,4,4,5]; [2,6] has no partner
  2. round 2: merge [1,1,3,4,4,5] + [2,6] → [1,1,2,3,4,4,5,6]
  3. one list left → return it

Python

class Solution:
    def mergeKLists(self, lists: List[Optional[ListNode]]) -> Optional[ListNode]:
        if not lists:
            return None
        while len(lists) > 1:
            merged = []
            for i in range(0, len(lists), 2):              # pair up neighbours
                a = lists[i]
                b = lists[i + 1] if i + 1 < len(lists) else None
                merged.append(self.mergeTwo(a, b))
            lists = merged                                 # about half as many lists
        return lists[0]

    def mergeTwo(self, a, b):
        dummy = tail = ListNode()
        while a and b:
            if a.val <= b.val:
                tail.next = a
                a = a.next
            else:
                tail.next = b
                b = b.next
            tail = tail.next
        tail.next = a if a else b
        return dummy.next
Time O(N log k)Space O(k)

About log k rounds of O(N) work. The list of round results is the only extra memory (O(k)); merging in place by index would make it O(1).

When to use: When you want to reuse Merge Two Sorted Lists, or avoid a heap altogether.

Common mistakes

  • Pushing (node.val, node): when two values are equal, Python compares the nodes next and raises TypeError: '<' not supported between instances of 'ListNode'. Push (node.val, i, node) with a unique i.
  • Merging sequentially (result = merge(result, lists[i]) for each i) is O(N · k): early nodes are re-walked in every merge.
  • Empty inputs: lists = [] and lists that are None inside lists. Skip None heads before pushing, and return None for no nodes.
  • Divide and conquer with an odd number of lists: the unpaired last list must be carried into the next round.
  • Using the recursive two-list merge inside divide and conquer: the final merges handle long lists and can exceed Python's recursion limit.

Python notes

  • heapq works on a plain list: heapq.heappush(h, item), heapq.heappop(h), and h[0] is the smallest item.
  • Tuples compare item by item, so (val, i, node) orders by val, then by i, and never reaches node because each list has at most one entry in the heap at a time.
  • heapq.heapify(h) turns an existing list into a heap in O(k), slightly faster than k pushes.
