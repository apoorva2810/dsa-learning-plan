Time Based Key-Value Store Medium

LeetCode #981 ↗
Status

Store several timestamped values per key and look up the value that was current at a given time.

Problem

Design a key-value store that remembers history: the same key can be set many times, each at a timestamp, and you can ask what the value of a key was at any moment.

Implement the class TimeMap:

  • TimeMap() creates an empty store.
  • set(key, value, timestamp) stores value for key at time timestamp.
  • get(key, timestamp) returns the value from the latest set for key whose timestamp is <= timestamp. If there is no such call (the key was never set, or only set later), return the empty string "".

The timestamps passed to set are strictly increasing across all calls.

Examples

Example 1
Input: ["TimeMap","set","get","get","set","get","get"] [[],["foo","bar",1],["foo",1],["foo",3],["foo","bar2",4],["foo",4],["foo",5]]
Output: [null, null, "bar", "bar", null, "bar2", "bar2"]
At time 3 the latest value of "foo" is still "bar" (set at 1). From time 4 on it is "bar2".
Example 2
Input: ["TimeMap","set","set","get","get","get"] [[],["love","high",10],["love","low",20],["love",5],["love",10],["love",15]]
Output: [null, null, null, "", "high", "high"]
Nothing was set for "love" at or before time 5, so the answer is the empty string.

Constraints

  • 1 <= len(key), len(value) <= 100; lowercase letters and digits
  • 1 <= timestamp <= 10^7
  • timestamps of set calls are strictly increasing
  • at most 2 * 10^5 calls to set and get in total

Think first try before reading the solution

Keep, for each key, the list of (timestamp, value) pairs in the order they were set. In what order are those timestamps?
get(key, t) asks for the last entry whose timestamp is <= t. In a sorted list, "the last position with value <= t" is a binary search.
bisect.bisect_right(times, t) counts the timestamps <= t. Subtract one to get the index, and return "" when the result is -1.

Key idea

Because set timestamps only ever increase, appending each new (timestamp, value) to its key's list keeps that list sorted for free: no insertion work, O(1) per set.

A get(key, t) is then a question about a sorted list: where is the last timestamp that is not after t? That is a binary search. bisect_right(times, t) returns the first position whose time is greater than t; the position just before it holds the answer. If that position is -1, every stored time is later than t and the answer is "". Each get costs O(log m), where m is the number of values stored for that key.

Approaches from the obvious one to the one you want in an interview

Store a list of (timestamp, value) pairs per key; set appends. For get, walk the list from the end (the newest entry) toward the start and return the first value whose timestamp is <= t.

set is O(1), but a get for an early time walks the whole history: O(m) for a key with m values. With 2·10⁵ calls that can reach about 10¹⁰ steps.

Python

class TimeMap:
    def __init__(self):
        self.store = defaultdict(list)          # key -> [(timestamp, value), ...] in time order

    def set(self, key: str, value: str, timestamp: int) -> None:
        self.store[key].append((timestamp, value))

    def get(self, key: str, timestamp: int) -> str:
        for t, value in reversed(self.store.get(key, [])):   # newest first
            if t <= timestamp:
                return value
        return ""
Time O(1) set, O(m) getSpace O(total sets)

m = number of values stored for the key being read.

When to use: Fine when most queries ask about recent times; otherwise too slow.

Keep two parallel lists per key, times[key] and values[key]. set appends to both; since timestamps only increase, times[key] is always sorted.

get(key, t):

  1. i = bisect_right(times[key], t) - 1. bisect_right returns the first position whose time is > t, so i is the last position whose time is <= t.
  2. If i >= 0, return values[key][i]; otherwise return "".

Both steps rely on the list being sorted, which the increasing timestamps guarantee for free.

Dry run

  1. set("foo", "bar", 1) → times [1], values ["bar"]
  2. get("foo", 1) → bisect_right([1], 1) = 1 → i = 0 → "bar"
  3. get("foo", 3) → bisect_right([1], 3) = 1 → i = 0 → "bar"
  4. set("foo", "bar2", 4) → times [1, 4]
  5. get("foo", 4) → bisect_right([1, 4], 4) = 2 → i = 1 → "bar2"
  6. get("foo", 0) would give bisect_right = 0 → i = −1 → ""

Python

class TimeMap:
    def __init__(self):
        self.times = defaultdict(list)          # key -> timestamps, increasing (set calls come in time order)
        self.values = defaultdict(list)         # key -> value stored at the matching timestamp

    def set(self, key: str, value: str, timestamp: int) -> None:
        self.times[key].append(timestamp)       # stays sorted for free
        self.values[key].append(value)

    def get(self, key: str, timestamp: int) -> str:
        times = self.times.get(key, [])         # .get: do not create entries for unknown keys
        # first position with time > timestamp, minus one = last position with time <= timestamp
        i = bisect.bisect_right(times, timestamp) - 1
        return self.values[key][i] if i >= 0 else ""
Time O(1) set, O(log m) getSpace O(total sets)

Appending is O(1); each get is one binary search over the key's m timestamps.

When to use: The standard answer. Explain why the list is sorted without any sorting.

Watch it run

Interviewers often ask you to write the binary search yourself. Search the key's (timestamp, value) list for the last pair with timestamp <= t: whenever pairs[mid] qualifies, remember its value as the best answer so far and look further right (lo = mid + 1); otherwise look left (hi = mid - 1). When the range is empty, the remembered value is the answer (or "" if nothing qualified).

Same O(log m). It avoids the library and keeps each pair together in one list.

Python

class TimeMap:
    def __init__(self):
        self.store = defaultdict(list)          # key -> [(timestamp, value), ...] in time order

    def set(self, key: str, value: str, timestamp: int) -> None:
        self.store[key].append((timestamp, value))

    def get(self, key: str, timestamp: int) -> str:
        pairs = self.store.get(key, [])
        answer = ""
        lo, hi = 0, len(pairs) - 1
        while lo <= hi:
            mid = (lo + hi) // 2
            if pairs[mid][0] <= timestamp:
                answer = pairs[mid][1]          # qualifies; a later pair might qualify too
                lo = mid + 1
            else:
                hi = mid - 1                    # too late: look left
        return answer
Time O(1) set, O(log m) getSpace O(total sets)

When to use: When asked not to use bisect.

Common mistakes

  • bisect_left instead of bisect_right: when a stored time equals t exactly, bisect_left points at it and the - 1 steps back to the previous value. get("foo", 4) above would return "bar" instead of "bar2".
  • Not handling index -1: in Python values[-1] is the newest value, so a query earlier than every set silently returns the wrong answer instead of "".
  • Reading self.values[key] on a defaultdict inside get inserts an empty list for every unknown key. Use .get(key, []).
  • Bisecting a list of (timestamp, value) tuples with a bare integer raises TypeError (an int cannot be compared with a tuple). Keep a separate list of timestamps, or pass key= (Python 3.10+).

Python notes

  • defaultdict(list) creates each key's list on its first set.
  • bisect.bisect_right(a, x) is the number of elements <= x, so bisect_right(a, x) - 1 is the index of the last one (or -1).
  • Since Python 3.10, bisect.bisect_right(pairs, t, key=lambda p: p[0]) searches a list of tuples by timestamp directly.
  • Two parallel lists (times, values) keep the call simple and work on every Python 3 version.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Snapshot Array LC 1146 — the same idea per array index: store (snap_id, value) changes and answer get(index, snap_id) with bisect_right - 1.
  • What if set timestamps can arrive out of order? — appending no longer keeps the list sorted. bisect.insort keeps it sorted but costs O(m) per insert (elements shift); a balanced tree or sortedcontainers.SortedList makes inserts O(log m).
  • Stock Price Fluctuation LC 2034 — prices arrive out of order and can be corrected: a dict from timestamp to price plus min/max heaps with lazy deletion.
  • Design Hit Counter LC 362 — timestamps increase here too; count hits in the last 300 seconds with a deque, or bisect for where the window starts.
  • LRU Cache LC 146 — another dictionary-plus-ordering design: there the order is recency of use and must be updated in O(1).
