Lemonade Change Easy 250

LeetCode #860 ↗
Status

Decide whether a lemonade stand can hand back the right change to every customer in line, starting with an empty till.

Problem

A lemonade stand sells one cup for $5. Customers stand in a line and each buys exactly one cup, paying with a single bill of $5, $10 or $20. The list bills gives the bill each customer pays with, in the order they are served.

You must give back the exact change so that every customer pays $5 in the end. The till is empty before the first customer, so the only money you can hand back is money earlier customers gave you.

Return True if every customer can be served, and False as soon as one cannot.

Examples

Example 1
Input: bills = [5, 5, 10, 20, 5]
Output: true
Two fives go into the till. The $10 customer gets a $5 back, leaving one 5 and one 10. The $20 customer is owed $15: hand over the 10 and the 5. The last customer pays exactly.
Example 2
Input: bills = [5, 10, 10]
Output: false
After the first two customers the till holds a single $10 bill and no $5. The third customer pays $10 and is owed $5, which you cannot give.
Example 3
Input: bills = [5, 5, 5, 5, 10, 20, 10, 10]
Output: true
For the $20, hand back a 10 and a 5, not three 5s. That keeps enough 5s for the two $10 customers who follow.

Constraints

  • 1 <= len(bills) <= 10^5
  • bills[i] is 5, 10 or 20

Think first try before reading the solution

Work out what each bill needs: a $5 needs no change, a $10 needs $5 back, a $20 needs $15 back. Which bills can you ever hand back?
You never hand back a $20, because the largest change owed is $15. So the till is described by just two numbers: how many $5 bills and how many $10 bills it holds. A $20 can be changed in two ways, so ask which way leaves you better off.
A $5 bill can change a $10 and can also be part of the change for a $20. A $10 bill is only ever useful as part of the change for a $20. Spend the less useful bill first: for a $20, give a 10 and a 5 if you can, and three 5s only if you have no 10.

Key idea

Each customer pays $5 for the cup, so what you owe back depends on the bill:

  • $5: nothing is owed. Keep the bill.
  • $10: $5 is owed, so you must hold a five.
  • $20: $15 is owed, which can be paid two ways: a ten and a five, or three fives.

Only fives and tens are ever handed back, so two counters, fives and tens, describe the whole till. (Twenties go in the drawer and never come out, so they need no counter.)

The choice for a $20 is the only real decision. A five is the flexible bill: it can change a $10 and it can be part of any $15. A ten is less useful: its only job is to be part of the $15 for a $20. So spend the less useful bill first: give a ten and a five when you have them, and three fives only when you have no ten.

Why it never hurts (an exchange argument: swap one choice for another and show the result is no worse). After giving ten + five, the till holds two more fives and one fewer ten than after giving three fives. If a later $20 would have used that extra ten together with a five, the richer till pays it with three fives instead, since it has two spare. A ten has no other use, because only a $20 customer is ever handed one back. So the ten + five plan never gets stuck sooner than the three-fives plan.

Approaches from the obvious one to the one you want in an interview

Search all the plans. Walk down the line with the current till (fives, tens). A $5 or a $10 customer has only one way to be served. A $20 customer has two: ten + five, or three fives. Try one, and if the rest of the line then fails, undo it and try the other. The answer is True if any plan serves everyone.

It is correct, but each $20 customer can double the number of plans to try. With k twenties the search can grow like 2 to the power k, and the recursion goes as deep as the line is long. The next approach shows why only one of the two choices ever needs to be tried.

Dry run

  1. bills = [5, 5, 5, 5, 10, 20, 10, 10]: the first five customers leave fives = 3, tens = 1
  2. the $20 customer: try ten + five first → fives = 2, tens = 0
  3. the two $10 customers use two fives → the line ends, return True (three fives would be tried only if this failed)

Python

class Solution:
    def lemonadeChange(self, bills: List[int]) -> bool:
        def serve(i: int, fives: int, tens: int) -> bool:   # can customers i, i + 1, ... all be served from this till?
            if i == len(bills):
                return True
            bill = bills[i]
            if bill == 5:
                return serve(i + 1, fives + 1, tens)        # exact payment, keep the five
            if bill == 10:                                  # owed $5
                return fives >= 1 and serve(i + 1, fives - 1, tens + 1)
            # bill == 20, owed $15: try each way of making it
            if tens >= 1 and fives >= 1 and serve(i + 1, fives - 1, tens - 1):   # 10 + 5
                return True
            return fives >= 3 and serve(i + 1, fives - 3, tens)                  # 5 + 5 + 5

        return serve(0, 0, 0)
Time O(n · 2ᵏ)Space O(n)

k is the number of $20 customers; each can branch two ways. The recursion is n frames deep.

When to use: To define the problem and to check the greedy answer on small inputs. Never for a long line.

Keep two counters, fives and tens, and serve the customers in order:

  • $5: fives += 1.
  • $10: you need a five. If fives == 0, return False. Otherwise fives -= 1 and tens += 1.
  • $20: prefer a ten and a five: if both counters are above 0, subtract one from each. Otherwise, if fives >= 3, take three fives. Otherwise return False.

If the loop finishes, everyone was served. The ten + five rule is safe because a ten has only one use, as part of the change for a $20, while two spare fives can always replace it. One pass, two integers.

Dry run

  1. bills = [5, 5, 5, 5, 10, 20, 10, 10], fives = tens = 0
  2. four $5 customers: fives = 4
  3. $10: give a 5 back → fives = 3, tens = 1
  4. $20: owed $15 and we hold a ten and a five → fives = 2, tens = 0
  5. $10: fives = 1, tens = 1; the last $10: fives = 0, tens = 2
  6. the line ends, return True

Python

class Solution:
    def lemonadeChange(self, bills: List[int]) -> bool:
        fives = tens = 0                         # the only bills we ever hand back; twenties stay in the drawer
        for bill in bills:
            if bill == 5:
                fives += 1                       # exact payment, no change
            elif bill == 10:
                if fives == 0:                   # a $10 customer is owed $5
                    return False
                fives -= 1
                tens += 1
            else:                                # bill == 20, owed $15
                if tens >= 1 and fives >= 1:     # prefer 10 + 5: a ten helps no one else
                    tens -= 1
                    fives -= 1
                elif fives >= 3:                 # otherwise 5 + 5 + 5
                    fives -= 3
                else:
                    return False
        return True                              # everyone was served
Time O(n)Space O(1)

One pass over the line; two integer counters.

When to use: The standard answer. Be ready to explain why ten + five is never worse than three fives.

Common mistakes

  • Tracking only the total money in the till. After [5, 10] the till holds $10, yet the next $10 customer is owed $5 and you have no $5 bill. The bill types matter, not the total.
  • Giving three fives for a $20 even when a ten is available. For [5, 5, 5, 5, 10, 20, 10, 10] that spends the fives the last two customers need and returns False, while ten + five returns True.
  • Forgetting to store the $10 you receive. That ten is what makes ten + five change possible for a later $20.
  • Not returning at the first customer you cannot serve. Customers are served in order and a missed customer cannot be repaired by later ones, so return False right there.
  • Letting the first customer pay with a $10 or $20. The till starts empty, so [10] and [20] are already False.

Python notes

  • fives = tens = 0 sets both counters at once. This is safe for integers because += makes a new integer each time.
  • The return False inside the loop ends the whole function at the first customer you cannot serve. No flag variable is needed.
  • The final else handles bill == 20, which the constraints guarantee, since only 5, 10 and 20 are possible.
  • A collections.Counter or a dict keyed by bill value also works, but for three denominations two named variables read more clearly.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Coin Change LC 322 — arbitrary coin values. Taking the biggest coin first stops working: for coins 1, 3, 4 and amount 6, greedy gives 4 + 1 + 1, but 3 + 3 uses fewer coins. That needs dynamic programming.
  • Assign Cookies LC 455 — another "spend the least valuable thing that still works" greedy: give each child the smallest cookie that satisfies them, so the big cookies stay available for greedier children.
  • Hand of Straights LC 846 — another problem where a local rule (always start a group from the smallest card left) is safe and the counts of what remains are all you track.
  • What if there are more bill values, or a different price? — keep one counter per bill value. The brute-force search from approach 1 still works. Whether a simple "biggest bills first" rule is safe depends on the bill values, so it needs its own argument.
  • Return the first customer you cannot serve — return the index i at the failure instead of False, and -1 if everyone is served.
