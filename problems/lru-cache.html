LRU Cache Medium

LeetCode #146 ↗
Status

A fixed-size key-value cache that evicts the least recently used key, with O(1) get and put.

Problem

Design a Least Recently Used (LRU) cache: a key-value store with a fixed capacity. When it is full and a new key arrives, it throws out the key that was used least recently.

Implement the class LRUCache:

  • LRUCache(capacity) creates an empty cache that holds at most capacity keys.
  • get(key) returns the value stored for key, or -1 if it is not there. A successful get counts as a use of the key.
  • put(key, value) stores value under key (overwriting an existing value). This is also a use. If it adds a new key and the cache now holds more than capacity keys, remove the least recently used key.

Both get and put must run in O(1) average time.

Examples

Example 1
Input: ["LRUCache","put","put","get","put","get","put","get","get","get"] [[2],[1,1],[2,2],[1],[3,3],[2],[4,4],[1],[3],[4]]
Output: [null, null, null, 1, null, -1, null, -1, 3, 4]
get(1) makes 1 more recent than 2, so put(3, 3) evicts 2. Then put(4, 4) evicts 1, the least recently used by then.

Constraints

  • 1 <= capacity <= 3000
  • 0 <= key <= 10^4
  • 0 <= value <= 10^5
  • at most 2 * 10^5 calls to get and put

Think first try before reading the solution

A dictionary gives O(1) lookup by key, but cannot tell you which key was used least recently. What structure keeps items in usage order and can move any one of them to the 'most recent' end in O(1)?
A doubly linked list can unlink any node in O(1), if you already hold that node. Who can hand you the node for a key in O(1)?
Combine them: a dictionary key -> node, and a doubly linked list ordered from least to most recently used, with dummy head and tail nodes so that inserting and removing never need special cases.

Key idea

The cache needs two abilities at once: find a key fast (a hash map does that) and keep keys in usage order, where any key can jump to the 'most recent' end and the oldest can be dropped, all in O(1). A Python list keeps order, but moving or removing an item in the middle shifts everything after it: O(n).

A doubly linked list (every node knows both its prev and its next) can unlink a node in O(1): just connect its two neighbours to each other. The catch is that you need the node in hand, and finding it would take a walk. The dictionary removes the walk: it maps each key straight to its node.

So: dictionary key → node, plus a doubly linked list from least recent (right after a dummy head) to most recent (right before a dummy tail). get and put look the node up, unlink it, and re-insert it before tail. Eviction removes head.next. Each node also stores its key, so after evicting a node we know which dictionary entry to delete.

Approaches from the obvious one to the one you want in an interview

Store values in a dictionary, and keep a separate Python list of keys from least to most recently used. On every use, remove the key from wherever it is in the list and append it at the end; to evict, pop the first key.

It behaves correctly, but list.remove(key) has to search for the key and shift everything after it, and list.pop(0) shifts the whole list: O(capacity) per operation. With 3000 keys and 2 · 10⁵ calls that is far from O(1).

Python

class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.values = {}                      # key -> value
        self.order = []                       # keys, least recently used first

    def get(self, key: int) -> int:
        if key not in self.values:
            return -1
        self.order.remove(key)                # O(n): find the key and shift the rest
        self.order.append(key)                # now the most recently used
        return self.values[key]

    def put(self, key: int, value: int) -> None:
        if key in self.values:
            self.order.remove(key)            # existing key: just refresh its position
        elif len(self.values) == self.capacity:
            oldest = self.order.pop(0)        # O(n): every other key shifts left
            del self.values[oldest]
        self.values[key] = value
        self.order.append(key)
Time O(capacity) per callSpace O(capacity)

Searching and shifting inside the order list dominates every call.

When to use: Only to show which operation needs the linked list.

Python's collections.OrderedDict remembers the order of its keys and can move any key to the end with move_to_end(key) and remove the first key with popitem(last=False), both in O(1). Internally it is exactly the optimal design below: a hash map whose entries are linked in a doubly linked list.

get moves the key to the end; put sets the value, moves the key to the end, and pops the first key if the cache grew past its capacity.

Python

class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.cache = OrderedDict()            # keys in usage order, least recent first

    def get(self, key: int) -> int:
        if key not in self.cache:
            return -1
        self.cache.move_to_end(key)           # mark as most recently used
        return self.cache[key]

    def put(self, key: int, value: int) -> None:
        if key in self.cache:
            self.cache.move_to_end(key)
        self.cache[key] = value
        if len(self.cache) > self.capacity:
            self.cache.popitem(last=False)    # evict the least recently used
Time O(1) per callSpace O(capacity)

move_to_end and popitem(last=False) are O(1) linked-list operations inside OrderedDict.

When to use: Same complexity as building it yourself and much shorter. Say it, then be ready to implement the list by hand.

Two structures that point into each other:

  • nodes: a dictionary from key to its list node, for O(1) lookup;
  • a doubly linked list of nodes from least recently used (just after a dummy head) to most recently used (just before a dummy tail). Each node stores key, val, prev and next.

Two helpers do all the pointer work: _unlink(node) connects the node's neighbours to each other, and _append(node) inserts it before tail. get = look up, unlink, append. put on an existing key = update the value, unlink, append. put on a new key = create, append, store in nodes; if the size passes capacity, unlink head.next and delete its key from nodes. The dummy nodes mean no operation ever has to check for an empty list or a missing neighbour.

Dry run

  1. capacity 2: put(1,1), put(2,2) → list head ⇄ 1 ⇄ 2 ⇄ tail
  2. get(1) → unlink 1, append → head ⇄ 2 ⇄ 1 ⇄ tail, return 1
  3. put(3,3) → append 3 → size 3 > 2 → evict head.next = 2 → head ⇄ 1 ⇄ 3 ⇄ tail
  4. get(2) → not in nodes → -1

Python

class DNode:                                  # a doubly linked list node
    def __init__(self, key=0, val=0):
        self.key = key                        # needed to delete the dict entry on eviction
        self.val = val
        self.prev = None
        self.next = None


class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.nodes = {}                       # key -> DNode
        self.head = DNode()                   # dummy: head.next is the least recently used
        self.tail = DNode()                   # dummy: tail.prev is the most recently used
        self.head.next = self.tail
        self.tail.prev = self.head

    def _unlink(self, node):                  # O(1): the neighbours skip over node
        node.prev.next = node.next
        node.next.prev = node.prev

    def _append(self, node):                  # O(1): insert node just before tail
        last = self.tail.prev
        last.next = node
        node.prev = last
        node.next = self.tail
        self.tail.prev = node

    def get(self, key: int) -> int:
        if key not in self.nodes:
            return -1
        node = self.nodes[key]
        self._unlink(node)                    # move it to the most-recent end
        self._append(node)
        return node.val

    def put(self, key: int, value: int) -> None:
        if key in self.nodes:                 # existing key: update and refresh
            node = self.nodes[key]
            node.val = value
            self._unlink(node)
            self._append(node)
            return
        node = DNode(key, value)
        self.nodes[key] = node
        self._append(node)
        if len(self.nodes) > self.capacity:
            lru = self.head.next              # least recently used
            self._unlink(lru)
            del self.nodes[lru.key]
Time O(1) per callSpace O(capacity)

One dictionary operation and a fixed number of pointer updates per call; at most capacity + 1 nodes exist.

When to use: The answer interviewers are looking for; the same map-into-a-list design powers LFU caches and similar structures.

Common mistakes

  • A singly linked list is not enough: unlinking a node needs the node before it, and finding that is O(n).
  • Forgetting that get is a use: a successful get must move the key to the most-recent end, not only put.
  • put on an existing key must update the value and move it. Creating a second node leaves a stale node in the list that is later evicted by mistake.
  • Evicting when an existing key is updated: an overwrite does not grow the cache, so only a brand-new key can trigger eviction.
  • Not storing the key inside each node: when the least recently used node is evicted you must also delete its dictionary entry, and the node is the only place that knows its key.

Python notes

  • collections.OrderedDict is a dictionary plus a doubly linked list: move_to_end(key) and popitem(last=False) are both O(1). Interviewers often accept it, then ask you to build the linked list yourself.
  • Plain dicts keep insertion order since Python 3.7, so d[key] = d.pop(key) moves a key to the end and next(iter(d)) is the oldest key: another O(1) average implementation.
  • The node class is called DNode here because Node is already defined on this site (it is LeetCode's graph/random-list node).

Follow-up questions

What an interviewer might ask next, and what changes.

  • LFU Cache LC 460 — evict the least frequently used key: keep a dictionary of frequency → doubly linked list plus the current minimum frequency.
  • All O`one Data Structure LC 432 — increment/decrement counts and report a max and a min key in O(1): a doubly linked list of count buckets, with a key → bucket map.
  • Design Linked List LC 707 — implement the list operations themselves (get, add at index, delete at index); good practice for the sentinel-node technique.
  • Entries that expire (TTL) — store an expiry time in each node and treat an expired node as missing on get; eviction can still take head.next.
  • Many threads using the cache — get mutates the order too, so both operations need a lock; large systems split the cache into independently locked shards.
