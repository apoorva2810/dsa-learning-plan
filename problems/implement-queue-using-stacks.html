Implement Queue using Stacks Easy 250

LeetCode #232 ↗
Status

Build a first-in-first-out queue when the only containers you may use are last-in-first-out stacks.

Problem

Build a queue (first in, first out) using only stacks (last in, first out) underneath. A stack may be used only through its own operations: put an item on top, take the top item off, look at the top item, ask for the size, and ask whether it is empty. No indexing into the middle and no removing from the bottom.

Implement the class MyQueue:

  • MyQueue() creates an empty queue.
  • push(x) adds x at the back of the queue.
  • pop() removes the item at the front of the queue and returns it.
  • peek() returns the item at the front without removing it.
  • empty() returns True if the queue has no items.

pop and peek are only called on a non-empty queue. Follow-up: can every operation take amortised O(1) time? That means any sequence of n operations costs O(n) in total, even if one single operation is slower.

Examples

Example 1
Input: ["MyQueue","push","push","peek","pop","empty"] [[],[1],[2],[],[],[]]
Output: [null, null, null, 1, 1, false]
The 1 went in first, so both peek and pop give 1. The 2 is still inside, so the queue is not empty.
Example 2
Input: ["MyQueue","push","push","push","pop","push","pop","peek"] [[],[1],[2],[3],[],[4],[],[]]
Output: [null, null, null, null, 1, null, 2, 3]
pop returns the oldest item, 1. The 4 joins at the back, behind 2 and 3, so the next pop is 2 and peek shows 3.

Constraints

  • 1 <= x <= 9
  • at most 100 calls to push, pop, peek and empty in total
  • every pop and peek is called on a non-empty queue

Think first try before reading the solution

A stack hands back the newest item first; a queue must hand back the oldest. What happens to the order of the items if you move them one by one from one stack onto another?
After moving everything, the oldest item is on top of the second stack, which is exactly what pop and peek need. Do you have to move the items back afterwards?
Keep an inbox for every push and an outbox for every pop and peek. Pour the inbox into the outbox only when the outbox is empty. Why is that safe, and why is it cheap?

Key idea

A stack gives back the newest item first, but a queue must give back the oldest. Pouring one stack into another, one item at a time, reverses the order: the item that sat at the bottom (the oldest) lands on top. So a single pour turns "newest first" into "oldest first", the order a queue needs.

The slow idea is to pour everything out, take the front, and pour everything back on every pop. The pour back undoes the reversal, which is wasted work, because the second stack already has the right order. So do not pour back. Keep two stacks: the inbox receives every push; the outbox serves every pop and peek. Only when the outbox is empty do we pour the whole inbox into it. Anything already in the outbox is older than everything in the inbox, so it must be served first, and that is exactly what happens.

A single pop can still pour many items. But every item is poured once in its life (inbox to outbox), so a sequence of m operations costs O(m) in total. This is called amortised O(1): the average cost per operation over a whole sequence, even though one operation can be expensive.

Approaches from the obvious one to the one you want in an interview

Keep all items in one stack. push is a plain push, so the newest item is on top. But the front of the queue, the oldest item, is at the bottom. To reach it, pour every item into a helper stack (this reverses the order, so the oldest is now on top), take or read it there, and pour the rest back (which reverses it again, restoring the original order).

It is correct, but each pop and peek moves every item twice: O(n) per call. It shows the useful trick, that pouring reverses a stack, and also the waste: the pour back throws away a perfectly good "oldest first" order.

Dry run

  1. push(1), push(2): stack [1, 2], 2 on top.
  2. peek(): pour 2, then 1 onto the helper → helper [2, 1], 1 on top. Read 1. Pour back → stack [1, 2].
  3. pop(): pour out again → helper [2, 1]; take 1; pour 2 back → stack [2].
  4. empty(): the stack has an item → False.

Python

class MyQueue:
    def __init__(self):
        self.stack = []                        # newest item on top; the front of the queue is at the bottom

    def _pour(self, source, target):
        while source:                          # move items one by one: this reverses their order
            target.append(source.pop())

    def push(self, x: int) -> None:
        self.stack.append(x)                   # O(1)

    def pop(self) -> int:
        helper = []
        self._pour(self.stack, helper)         # the oldest item is now on top of the helper
        front = helper.pop()
        self._pour(helper, self.stack)         # reverse again: the original order is back
        return front

    def peek(self) -> int:
        helper = []
        self._pour(self.stack, helper)
        front = helper[-1]
        self._pour(helper, self.stack)
        return front

    def empty(self) -> bool:
        return not self.stack
Time O(1) push and empty, O(n) pop and peekSpace O(n)

Every pop and peek moves all n items out and back again.

When to use: Only as the baseline; it shows what the second stack is really for.

Watch it run

Use two stacks with different jobs.

  • inbox receives every push. Its top is the newest item.
  • outbox serves every pop and peek. Its top is the oldest item, the front of the queue.
  • If the outbox is empty when a pop or peek needs it, pour the whole inbox into the outbox. Otherwise leave it alone.
  • empty() is true only when both stacks are empty.

Why it is correct: the outbox always holds items older than anything in the inbox, in oldest-on-top order, so serving from the outbox first is exactly first-in-first-out. Why it is fast: an item moves from the inbox to the outbox once and never moves again. Over m operations there are at most m pushes, so at most m moves in total: amortised O(1) per call.

Dry run

  1. push(1), push(2), push(3): inbox [1, 2, 3], outbox [].
  2. pop(): outbox empty → pour: outbox [3, 2, 1], 1 on top. Return 1. outbox [3, 2].
  3. push(4): inbox [4]. The outbox is untouched.
  4. pop(): outbox not empty → return its top, 2. outbox [3].
  5. pop(): return 3. outbox [].
  6. pop(): outbox empty → pour inbox [4] → outbox [4] → return 4.

Python

class MyQueue:
    def __init__(self):
        self.inbox = []                        # new items land here (newest on top)
        self.outbox = []                       # items leave from here (oldest on top)

    def _refill(self) -> None:
        if not self.outbox:                    # pour only when the outbox has run dry
            while self.inbox:
                self.outbox.append(self.inbox.pop())

    def push(self, x: int) -> None:
        self.inbox.append(x)                   # O(1)

    def pop(self) -> int:
        self._refill()
        return self.outbox.pop()               # the top of the outbox is the front

    def peek(self) -> int:
        self._refill()
        return self.outbox[-1]

    def empty(self) -> bool:
        return not self.inbox and not self.outbox   # items may be waiting in either stack
Time O(1) amortised for every operationSpace O(n)

One pop can pour n items, but each item is poured once; m operations cost O(m) in total.

When to use: The standard answer, and exactly what the amortised follow-up asks for.

Watch it run

Do the work at push time so that the front of the queue is always on top of one stack. To add x at the back: pour the existing items onto a helper (they are reversed), put x on the now-empty stack (it sits at the bottom), then pour the items back on top of it (reversed again, so they are in their original order, all above x).

Then pop is a plain pop, peek is stack[-1] and empty is a length check, all O(1). The price is O(n) per push. Choose it only when pushes are rare and reads are frequent.

Python

class MyQueue:
    def __init__(self):
        self.stack = []                        # top = front of the queue (the oldest item)

    def push(self, x: int) -> None:
        helper = []
        while self.stack:                      # move the older items out of the way
            helper.append(self.stack.pop())
        self.stack.append(x)                   # the new item goes to the bottom: the back of the queue
        while helper:                          # older items go back on top, in their original order
            self.stack.append(helper.pop())

    def pop(self) -> int:
        return self.stack.pop()

    def peek(self) -> int:
        return self.stack[-1]

    def empty(self) -> bool:
        return not self.stack
Time O(n) push, O(1) pop, peek and emptySpace O(n)

Each push moves the n older items out and back.

When to use: If pushes are rare and pops and peeks are very frequent; otherwise prefer the inbox and outbox.

Common mistakes

  • Pouring the inbox into the outbox on every pop, even when the outbox still holds items. New items would land on top of older ones and come out first. Pour only when the outbox is empty.
  • Pushing a new item straight onto the outbox. It would sit on top, in front of items that arrived earlier.
  • Writing empty() as not self.outbox. Items waiting in the inbox count too: the queue is empty only when both stacks are.
  • Forgetting that peek needs the same refill as pop. After a push on an empty queue the front is still inside the inbox.
  • Pouring back after every pop (the baseline below). It is correct, but every pop then moves every item twice.
  • Calling pop O(n) and concluding that n operations cost O(n²). Only the first pop after a refill is slow; each item is poured once, so the whole sequence costs O(n).

Python notes

  • A Python list is the stack: append pushes, pop() removes the top, stack[-1] peeks, not stack tests emptiness. All O(1).
  • The pour is while self.inbox: self.outbox.append(self.inbox.pop()). self.outbox = self.inbox[::-1] gives the same result, but slicing is not a stack operation, so say so if you use it in an interview.
  • pop(0), insert(0, x) and reverse() are not stack operations either, and pop(0) costs O(n).
  • Create both lists in __init__ on self, so every queue gets its own stacks.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Implement Stack using Queues LC 225 — the mirror problem. Its standard answers pay O(n) on every push (or every pop), because a queue hands back its oldest item, not its newest.
  • Min Stack LC 155 — another design on stacks: each entry carries extra data (the minimum at that height) so the minimum is always one lookup away.
  • Sliding Window Maximum LC 239 — a queue that must also report its maximum: keep the maximum next to every item in both stacks, or use a monotonic deque.
  • Design Circular Queue LC 622 — build the queue on a fixed-size array with head and tail indices that wrap around, instead of on stacks.
  • Worst case O(1) per call — a single call can still pour n items. To bound every call, spread the pour over several calls (incremental reversal, as in real-time queues). Interviews almost always settle for amortised.
