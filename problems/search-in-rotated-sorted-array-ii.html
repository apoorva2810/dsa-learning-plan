Search in Rotated Sorted Array II Medium 250

LeetCode #81 ↗
Status

Decide whether a target is in a rotated sorted list that may contain duplicates.

Problem

You are given a list nums that was sorted in non-decreasing order (duplicates allowed) and then rotated at some unknown position: the list was cut at an index k and the two pieces swapped, so [0, 1, 2, 4, 4, 4, 5, 6, 6, 7] might appear as [4, 5, 6, 6, 7, 0, 1, 2, 4, 4].

Given an integer target, return True if target is in nums, otherwise False.

Because of the duplicates, no algorithm can guarantee O(log n) for every input; aim to use as few comparisons as possible and understand why the worst case is linear.

Examples

Example 1
Input: nums = [2, 5, 6, 0, 0, 1, 2], target = 0
Output: true
The list is [0, 0, 1, 2, 2, 5, 6] rotated; 0 is in it (twice).
Example 2
Input: nums = [2, 5, 6, 0, 0, 1, 2], target = 3
Output: false
Example 3
Input: nums = [1, 0, 1, 1, 1], target = 0
Output: true
Both ends and the middle hold 1, so the first look cannot tell which half is sorted. Drop both ends and look again.

Constraints

  • 1 <= len(nums) <= 5000
  • -10^4 <= nums[i], target <= 10^4
  • nums is guaranteed to be a non-decreasing list rotated at some index (possibly 0)

Think first try before reading the solution

Start from Search in Rotated Sorted Array: cut the range at mid; one of the two halves is sorted, and a sorted half can be tested by its two ends. What breaks when values repeat?
The test nums[lo] <= nums[mid] says 'the left half is sorted'. With duplicates it can be true even when the left half is not sorted: [1, 1, 1, 0, 1], mid = 2. When does this happen? Only when nums[lo] == nums[mid] == nums[hi].
In that one ambiguous case, nums[lo] and nums[hi] both equal nums[mid], which is not the target, so both ends can be discarded safely: lo += 1, hi -= 1. Every other case works exactly as before.

Key idea

In Search in Rotated Sorted Array the trick is: cut lo..hi at mid; at least one half is sorted, and you can tell which by comparing nums[lo] with nums[mid]. A sorted half is easy to test (is the target between its ends?), so you either dive into it or throw it away. Each round halves the range.

Duplicates break exactly one thing: when nums[lo] == nums[mid] == nums[hi], the comparison says nothing about where the drop (the rotation point) is. [1, 1, 1, 0, 1] and [1, 0, 1, 1, 1] look identical from those three positions, yet the 0 is on different sides. But in that case you do know something: both ends equal nums[mid], and nums[mid] is not the target (you just checked), so neither end can be the answer. Drop both ends, shrink by two, and try again.

That shrink is why the worst case is linear: for [1, 1, 1, …, 1] with target 2 every round is ambiguous and the range shrinks by two instead of half. No algorithm can do better in the worst case, because a single different value could hide at any position and only a direct look can rule a position out. On ordinary inputs the search still runs in about log₂ n rounds.

Approaches from the obvious one to the one you want in an interview

Look at every element. Rotation and duplicates do not matter, and the cost is O(n). Since this problem's worst case is O(n) anyway, the scan is not as far behind as usual, but on typical inputs the search below needs about log₂ n looks instead of n.

Python

class Solution:
    def search(self, nums: List[int], target: int) -> bool:
        for value in nums:
            if value == target:
                return True
        return False

When to use: Tiny lists, or when you have no time to get the cases right.

Build the answer from searches you already know, with one fix for duplicates.

  1. If target == nums[0], return True at once. Then strip copies of nums[0] from the end (hi -= 1 while nums[hi] == nums[0]). Those copies cannot be the target, and once nums[hi] != nums[0] every value in the first sorted run is strictly larger than every value in the second run.
  2. Find the rotation point p (the index of the minimum) with the Find Minimum in Rotated Sorted Array loop; after the strip it is exact even with duplicates inside the runs.
  3. Values larger than nums[0] can only be in the first run 0..p-1, smaller ones only in p..hi. Binary search that run with the ordinary loop.

Three loops instead of one, but each is a textbook piece. The strip is where the worst case hides: [1, 1, 1, …, 1] is stripped one element at a time.

Dry run

  1. [2, 5, 6, 0, 0, 1, 2], target 0: target ≠ nums[0] = 2; strip the trailing 2 → hi = 5
  2. rotation point: mid = 2 → 6 > nums[5] = 1 → lo = 3; mid = 4 → 0 ≤ 1 → hi = 4; mid = 3 → 0 ≤ 0 → hi = 3 → p = 3
  3. 0 < nums[0] = 2 → search the run 3..5 = [0, 0, 1] → mid = 4 holds 0 → True

Python

class Solution:
    def search(self, nums: List[int], target: int) -> bool:
        if target == nums[0]:
            return True
        lo, hi = 0, len(nums) - 1
        while lo < hi and nums[hi] == nums[0]:
            hi -= 1                             # copies of nums[0] at the end: never the target, and they hide the drop
        end = hi
        # 1) rotation point p: the minimum of nums[0..end] (exact now that nums[end] != nums[0])
        while lo < hi:
            mid = (lo + hi) // 2
            if nums[mid] > nums[hi]:
                lo = mid + 1                    # mid is in the first (larger) run
            else:
                hi = mid                        # mid is in the second run, which starts at or before mid
        p = lo
        # 2) pick the run that can hold the target
        if p == 0:
            lo, hi = 0, end                     # not rotated (after stripping): one sorted run
        elif target > nums[0]:
            lo, hi = 0, p - 1                   # the first run holds every value above nums[0]
        else:
            lo, hi = p, end                     # the second run holds every value below nums[0]
        # 3) ordinary binary search on a sorted run
        while lo <= hi:
            mid = (lo + hi) // 2
            if nums[mid] == target:
                return True
            if nums[mid] < target:
                lo = mid + 1
            else:
                hi = mid - 1
        return False
Time O(n) worst, O(log n) typicalSpace O(1)

The strip can touch n elements; the two searches are O(log n) each.

When to use: When you want to reuse Find Minimum, or need the rotation point for something else.

Keep lo..hi as the part of the list that can still hold the target and look at mid:

  • nums[mid] == target → True.
  • nums[lo] == nums[mid] == nums[hi] → the ambiguous case: the drop may be on either side. Both ends equal nums[mid], which is not the target, so discard them: lo += 1, hi -= 1.
  • nums[lo] <= nums[mid] → the left half lo..mid is sorted. If nums[lo] <= target < nums[mid] the target can only be there (hi = mid - 1); otherwise it is in the right part (lo = mid + 1).
  • otherwise the right half mid..hi is sorted: dive in if nums[mid] < target <= nums[hi] (lo = mid + 1), else hi = mid - 1.

This is Search in Rotated Sorted Array plus one branch. The branch shrinks by two instead of halving, so a list of equal values costs O(n); anything else runs in about log₂ n rounds.

Dry run

  1. [2, 5, 6, 0, 0, 1, 2], target 0: lo = 0, hi = 6
  2. mid = 3 → nums[3] = 0 is the target → True (one round)
  3. [1, 0, 1, 1, 1], target 0: mid = 2 → 1 ≠ 0 and nums[0] = nums[2] = nums[4] = 1 → lo = 1, hi = 3
  4. mid = 2 → 1 ≠ 0; nums[1] = 0 ≤ 1 → left half 1..2 sorted; 0 ≤ 0 < 1 → hi = 1
  5. mid = 1 → nums[1] = 0 → True

Python

class Solution:
    def search(self, nums: List[int], target: int) -> bool:
        lo, hi = 0, len(nums) - 1
        while lo <= hi:
            mid = (lo + hi) // 2
            if nums[mid] == target:
                return True
            if nums[lo] == nums[mid] == nums[hi]:
                lo += 1                         # ambiguous: cannot tell which half is sorted, but both ends
                hi -= 1                         # equal nums[mid] != target, so they are safe to drop
            elif nums[lo] <= nums[mid]:         # left half lo..mid is sorted
                if nums[lo] <= target < nums[mid]:
                    hi = mid - 1                # target lies inside the sorted left half
                else:
                    lo = mid + 1                # otherwise it can only be in the right part
            else:                               # right half mid..hi is sorted
                if nums[mid] < target <= nums[hi]:
                    lo = mid + 1                # target lies inside the sorted right half
                else:
                    hi = mid - 1                # otherwise it can only be in the left part
        return False
Time O(n) worst, O(log n) typicalSpace O(1)

Each round either halves the range or shrinks it by two; only runs of equal values force the latter.

When to use: The expected answer: the known template plus one guard for duplicates.

Common mistakes

  • Using the Search in Rotated Sorted Array code unchanged: with [1, 1, 1, 0, 1] and target 0, nums[lo] <= nums[mid] claims the left half is sorted, the target is not between 1 and 1, so the search jumps right and misses the 0.
  • Resolving the ambiguous case with lo = mid + 1 or hi = mid - 1: half the range is thrown away without knowing that the target is not there. Only lo += 1 and hi -= 1 are safe, because those two positions were just seen.
  • Expecting O(log n): on [1, 1, 1, 1, 1, 1] with target 2 the range shrinks by two per round, so the loop runs n / 2 times. That is unavoidable for any algorithm, not a bug in this one.
  • Writing the range tests with the wrong strictness: nums[lo] <= target < nums[mid] and nums[mid] < target <= nums[hi]. mid is already known not to be the target, the ends are still candidates.
  • Returning an index: with duplicates the target may appear many times, which is why this version returns a boolean.

Python notes

  • Chained comparisons read naturally: nums[lo] == nums[mid] == nums[hi] and nums[lo] <= target < nums[mid] are each one expression, evaluated left to right.
  • target in nums is the brute force in one call: correct, O(n), and the right answer only if the list is tiny.
  • The -1 of the original problem becomes False here; keep the boolean, do not return -1 for "not found".

Follow-up questions

What an interviewer might ask next, and what changes.

  • Search in Rotated Sorted Array LC 33 — the distinct-values version: the same loop without the nums[lo] == nums[mid] == nums[hi] branch, guaranteed O(log n).
  • Find Minimum in Rotated Sorted Array II LC 154 — same duplicate trouble when locating the rotation point: compare nums[mid] with nums[hi] and shrink hi by one when they are equal.
  • Find Minimum in Rotated Sorted Array LC 153 — the distinct-values version of finding the rotation point, used by the two-pass approach below.
  • Check if Array Is Sorted and Rotated LC 1752 — count the positions where nums[i] > nums[i + 1] cyclically: a rotated sorted array has at most one drop.
  • What if you must return an index of the target? — return mid instead of True on a hit: any index of a duplicate is acceptable, the search is unchanged.
  • Why can no algorithm guarantee O(log n) here? — adversary argument: answer every probe with 1 for [1, 1, …, 1]; the one position you did not probe could hold the target, so n − 1 probes cannot distinguish 'present' from 'absent'.
