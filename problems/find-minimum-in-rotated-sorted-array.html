Find Minimum in Rotated Sorted Array Medium

LeetCode #153 ↗
Status

Find the smallest value of a sorted list that has been rotated, in O(log n).

Problem

A list of distinct integers was sorted in increasing order and then rotated some number of times between 1 and n. Rotating once moves the last element to the front: [0, 1, 2, 4, 5, 6, 7] rotated 4 times becomes [4, 5, 6, 7, 0, 1, 2], and rotated 7 times it is back to [0, 1, 2, 4, 5, 6, 7].

Given the rotated list nums, return its minimum element. Your algorithm must run in O(log n) time.

Examples

Example 1
Input: nums = [3, 4, 5, 1, 2]
Output: 1
The sorted list [1, 2, 3, 4, 5] rotated 3 times.
Example 2
Input: nums = [4, 5, 6, 7, 0, 1, 2]
Output: 0
Example 3
Input: nums = [11, 13, 15, 17]
Output: 11
Rotated 4 times, which is the original order.

Constraints

  • n == len(nums), 1 <= n <= 5000
  • -5000 <= nums[i] <= 5000
  • all values are distinct
  • nums is sorted and rotated between 1 and n times

Think first try before reading the solution

A rotated sorted list is two increasing runs, for example [4, 5, 6, 7] then [0, 1, 2]. Where is the minimum?
Look at nums[mid] and nums[hi]. If nums[mid] > nums[hi], the list goes down somewhere between them. What does that say about where the minimum is?
If nums[mid] > nums[hi], the minimum is right of mid: lo = mid + 1. Otherwise mid..hi is sorted and the minimum is at mid or to its left: hi = mid. Stop when lo == hi.

Key idea

Rotation cuts a sorted list into two increasing runs and swaps them: every value in the first run is larger than every value in the second. The minimum is the first element of the second run, the one place where the list steps down.

Compare the middle with the right end. If nums[mid] > nums[hi], a step down must happen between them, so the minimum is strictly right of mid. If nums[mid] < nums[hi], then mid..hi climbs steadily, so nothing to the right of mid is smaller than nums[mid]: the minimum is mid or something to its left. Either way half of the range goes, and when one index is left, it is the minimum. That is O(log n).

Approaches from the obvious one to the one you want in an interview

Look at every element and keep the smallest, or equivalently find the one place where nums[i] < nums[i - 1]. It is O(n) and ignores that the two runs are sorted, which is exactly the structure binary search exploits.

Python

class Solution:
    def findMin(self, nums: List[int]) -> int:
        smallest = nums[0]
        for value in nums:
            if value < smallest:
                smallest = value
        return smallest
Time O(n)Space O(1)

When to use: Unsorted data; otherwise only as the baseline.

Keep a range lo..hi that always contains the minimum, and shrink it until one element is left:

  • nums[mid] > nums[hi] → the step down lies after mid, so the minimum is in mid + 1 .. hi: lo = mid + 1.
  • otherwise mid..hi is increasing → the minimum is in lo .. mid: hi = mid.

hi = mid keeps mid because it might be the minimum, which is why the loop runs while lo < hi and stops with a single candidate.

Dry run

  1. [4, 5, 6, 7, 0, 1, 2]: lo = 0, hi = 6
  2. mid = 3 → 7 > 2 → lo = 4
  3. mid = 5 → 1 < 2 → hi = 5
  4. mid = 4 → 0 < 1 → hi = 4
  5. lo == hi == 4 → minimum 0

Python

class Solution:
    def findMin(self, nums: List[int]) -> int:
        lo, hi = 0, len(nums) - 1
        while lo < hi:                          # more than one candidate left
            mid = (lo + hi) // 2
            if nums[mid] > nums[hi]:
                lo = mid + 1                    # the step down is right of mid, so is the minimum
            else:
                hi = mid                        # mid..hi is increasing: the minimum is mid or left of it
        return nums[lo]
Time O(log n)Space O(1)

The range halves every round.

When to use: The standard answer.

Watch it run

A second common way to write it: keep a running best. If the current window lo..hi is already sorted (nums[lo] < nums[hi]), its first element is its minimum, so take it and stop. Otherwise look at nums[mid], update best, and move toward the unsorted half: if nums[mid] >= nums[lo], mid is in the left run, so search right; else search left.

Same O(log n), and it can stop early, but there is more to keep consistent (a running answer, >= versus >), which is why the right-end comparison is usually preferred.

Python

class Solution:
    def findMin(self, nums: List[int]) -> int:
        best = nums[0]
        lo, hi = 0, len(nums) - 1
        while lo <= hi:
            if nums[lo] < nums[hi]:             # this window is sorted: its first element is its minimum
                best = min(best, nums[lo])
                break
            mid = (lo + hi) // 2
            best = min(best, nums[mid])
            if nums[mid] >= nums[lo]:           # mid is in the left (larger) run
                lo = mid + 1
            else:                               # mid is in the right run; the minimum is at mid or left of it
                hi = mid - 1
        return best
Time O(log n)Space O(1)

When to use: If you prefer the inclusive lo <= hi template everywhere.

Common mistakes

  • Comparing nums[mid] with nums[lo] in this template: for an unrotated list [1, 2, 3, 4, 5], nums[mid] > nums[lo] sends lo to the right, past the minimum. The right end is the safe comparison.
  • Setting hi = mid - 1 when nums[mid] < nums[hi]: mid itself may be the minimum ([3, 1, 2] at mid = 1).
  • Looping while lo <= hi with hi = mid: when lo == hi the range never shrinks and the loop does not end.
  • Returning lo (an index) instead of nums[lo] (the value). The index is useful too: it is the number of rotations.

Python notes

  • min(nums) is the one-line answer, but it is O(n); the problem asks for O(log n).
  • The loop ends with lo == hi, so nums[lo] and nums[hi] are the same element.
  • Chained comparisons read well when checking a window: nums[lo] < nums[hi] means the window lo..hi is not rotated.
