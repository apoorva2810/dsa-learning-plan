Search in Rotated Sorted Array Medium

LeetCode #33 ↗
Status

Find a target's index in a sorted list that was rotated at an unknown point, in O(log n).

Problem

A list of distinct integers was sorted in increasing order and then possibly rotated at an unknown index k, so that it reads nums[k], …, nums[n-1], nums[0], …, nums[k-1]. For example [0, 1, 2, 4, 5, 6, 7] rotated at index 3 becomes [4, 5, 6, 7, 0, 1, 2].

Given the rotated list nums and an integer target, return the index of target, or -1 if it is absent. Your algorithm must run in O(log n) time.

Examples

Example 1
Input: nums = [4, 5, 6, 7, 0, 1, 2], target = 0
Output: 4
Example 2
Input: nums = [4, 5, 6, 7, 0, 1, 2], target = 3
Output: -1
Example 3
Input: nums = [1], target = 0
Output: -1

Constraints

  • 1 <= len(nums) <= 5000
  • -10^4 <= nums[i], target <= 10^4
  • all values are distinct
  • nums is sorted in increasing order, possibly rotated

Think first try before reading the solution

Plain binary search fails because comparing the target with nums[mid] no longer tells you which side to keep. But cut the range at mid: is at least one of the two halves still sorted?
nums[lo] <= nums[mid] means the left half lo..mid is sorted; otherwise the right half mid..hi is. In a sorted half you can check whether the target lies inside it with two comparisons.
If the target is inside the sorted half, search that half; otherwise search the other half. Each round still discards half the range.

Key idea

The rotation point (where the values drop) is in at most one of the two halves around mid, so the other half is sorted. You can tell which by comparing its ends: if nums[lo] <= nums[mid], nothing drops between them, and the left half is sorted; otherwise the drop is on the left and the right half mid..hi is sorted.

A sorted half has a known smallest and largest value (its two ends), so "is the target in it?" is one range check. If yes, keep that half; if no, the target can only be in the other half. Either way half of the range goes, exactly as in plain binary search, so the whole search is O(log n).

Approaches from the obvious one to the one you want in an interview

Compare every element with the target. It works for any list, rotated or not, and costs O(n). The problem requires O(log n), so this only serves as the baseline: the work it wastes is everything the sorted runs could have told us.

Python

class Solution:
    def search(self, nums: List[int], target: int) -> int:
        for i, value in enumerate(nums):
            if value == target:
                return i
        return -1
Time O(n)Space O(1)

When to use: Tiny inputs only.

Reuse two searches you already know.

  1. Find the index p of the minimum with the "compare nums[mid] with nums[hi]" search from Find Minimum in Rotated Sorted Array. The list is the sorted run p..n-1 followed by the sorted run 0..p-1.
  2. Every value in 0..p-1 is at least nums[0], and every value in p..n-1 is smaller than nums[0]. So one comparison with nums[0] tells you which run can contain the target; binary search only that run.

Two O(log n) searches. It is easy to get right because each piece is a textbook search, at the cost of a second loop.

Dry run

  1. [4, 5, 6, 7, 0, 1, 2], target 0: the minimum is at p = 4
  2. 0 < nums[0] = 4 → the target can only be in the run 4..6
  3. binary search [0, 1, 2] (indices 4..6) → index 4

Python

class Solution:
    def search(self, nums: List[int], target: int) -> int:
        # 1) p = index of the minimum, where the second sorted run starts
        lo, hi = 0, len(nums) - 1
        while lo < hi:
            mid = (lo + hi) // 2
            if nums[mid] > nums[hi]:
                lo = mid + 1
            else:
                hi = mid
        p = lo
        # 2) values >= nums[0] live in 0..p-1 (when rotated); the rest live in p..n-1
        if p > 0 and target >= nums[0]:
            lo, hi = 0, p - 1
        else:
            lo, hi = p, len(nums) - 1
        while lo <= hi:                         # ordinary binary search on one sorted run
            mid = (lo + hi) // 2
            if nums[mid] == target:
                return mid
            if nums[mid] < target:
                lo = mid + 1
            else:
                hi = mid - 1
        return -1
Time O(log n)Space O(1)

Two binary searches over at most n elements each.

When to use: When you want to build from known pieces, or need the rotation point anyway.

One binary search with an extra decision each round:

  1. If nums[mid] == target, done.
  2. If nums[lo] <= nums[mid], the left half lo..mid is sorted. Keep it when nums[lo] <= target < nums[mid]; otherwise keep the right half.
  3. Else the right half mid..hi is sorted. Keep it when nums[mid] < target <= nums[hi]; otherwise keep the left half.

The rotation point can only be on one side of mid, so the test in step 2 always identifies a genuinely sorted half, and the range check on that half is reliable. Half the range is discarded every round.

Dry run

  1. [4, 5, 6, 7, 0, 1, 2], target 0: lo = 0, hi = 6
  2. mid = 3 (7): 4 ≤ 7 → left half sorted; 0 is not in [4, 7) → lo = 4
  3. mid = 5 (1): 0 ≤ 1 → left half 4..5 sorted; 0 ≤ 0 < 1 → hi = 4
  4. mid = 4 (0) → found, return 4

Python

class Solution:
    def search(self, nums: List[int], target: int) -> int:
        lo, hi = 0, len(nums) - 1
        while lo <= hi:
            mid = (lo + hi) // 2
            if nums[mid] == target:
                return mid
            if nums[lo] <= nums[mid]:                   # left half lo..mid is sorted
                if nums[lo] <= target < nums[mid]:
                    hi = mid - 1                        # target lies inside the sorted left half
                else:
                    lo = mid + 1
            else:                                       # right half mid..hi is sorted
                if nums[mid] < target <= nums[hi]:
                    lo = mid + 1                        # target lies inside the sorted right half
                else:
                    hi = mid - 1
        return -1
Time O(log n)Space O(1)

One binary search; each round does a constant number of comparisons.

When to use: The usual interview answer. Say out loud why one half must be sorted.

Common mistakes

  • Using a strict nums[lo] < nums[mid] to detect the sorted left half: when lo == mid (a two-element range) the one-element left half is sorted but the test says no. [3, 1] with target 1 then searches the wrong side.
  • Range checks that drop a boundary: the sorted left half holds targets with nums[lo] <= target < nums[mid] (mid was already tested), the sorted right half nums[mid] < target <= nums[hi].
  • Deciding by target < nums[mid] alone, as in plain binary search: across the rotation point a smaller target can sit to the right ([4, 5, 6, 7, 0, 1, 2], target 0).
  • Forgetting that the list may not be rotated at all; the same code must still work (it does: the left half always tests as sorted).

Python notes

  • Chained comparisons make the range checks readable: nums[lo] <= target < nums[mid] is one expression.
  • nums.index(target) would be O(n) and raises ValueError when the target is missing.
  • With the rotation point p known, the k-th smallest value is nums[(p + k) % n]: another way to binary search the 'unrotated' order without moving any data.
