Split Array Largest Sum Hard 250

LeetCode #410 ↗
Status

Cut a list into k contiguous pieces so that the largest piece sum is as small as possible.

Problem

You are given a list of non-negative integers nums and an integer k. Cut the list into exactly k non-empty contiguous pieces (you may not reorder elements; every element belongs to one piece).

Each way of cutting has a largest piece sum: the biggest total among its k pieces. Return the smallest possible largest piece sum over all ways of cutting.

Examples

Example 1
Input: nums = [7, 2, 5, 10, 8], k = 2
Output: 18
Cut into [7, 2, 5] and [10, 8]: sums 14 and 18, so the largest is 18. Every other cut has a larger piece: [7, 2, 5, 10] | [8] gives 24, [7, 2] | [5, 10, 8] gives 23.
Example 2
Input: nums = [1, 2, 3, 4, 5], k = 2
Output: 9
[1, 2, 3] | [4, 5] has sums 6 and 9. No cut makes the largest piece smaller than 9.
Example 3
Input: nums = [1, 4, 4], k = 3
Output: 4
Three elements, three pieces: each element alone; the largest is 4.

Constraints

  • 1 <= len(nums) <= 1000
  • 0 <= nums[i] <= 10^6
  • 1 <= k <= min(50, len(nums))

Think first try before reading the solution

Turn the question around. Instead of asking 'what is the best largest sum?', ask 'if no piece may exceed a limit L, how few pieces do I need?' Answer that greedily: extend the current piece until the next element would push it over L.
If a limit L works (greedy needs at most k pieces), every larger limit works too. So the limits 0, 1, 2, … read no, no, …, no, yes, yes, …: sorted. Find the first yes.
The first yes lies between max(nums) (one piece must hold the largest element) and sum(nums) (one piece holds everything). Binary search it; each check is one O(n) pass. The greedy may use fewer than k pieces: extra cuts never raise the maximum, so that still counts as a yes.

Key idea

Ask the question backwards. Choosing the cuts that minimise the largest piece is hard, but checking a limit is easy: walk the list, keep a running total, and start a new piece whenever adding the next element would exceed the limit. That greedy walk uses the fewest pieces possible for that limit, because closing a piece earlier than necessary never helps. If it needs at most k pieces, the limit is achievable (if it used fewer than k, cut some piece further; that only makes pieces smaller).

The check is monotonic: a bigger limit never needs more pieces. So all limits from max(nums) to sum(nums) split into a run that fails followed by a run that works, and the answer is the first limit that works. Binary search that range with the greedy walk as the test: about log₂(sum) ≈ 30 passes of O(n), against O(k · n²) for the classic dynamic program. This is the same problem as Capacity to Ship Packages: pieces are days, the limit is the capacity.

The dynamic program is still worth knowing: dp[j][i], the best largest sum when the first i elements form j pieces, is the minimum over the last cut p of max(dp[j-1][p], sum(nums[p..i-1])). It is the natural first idea and the one interviewers expect you to recognise as too slow for n = 1000.

Approaches from the obvious one to the one you want in an interview

Recursively choose where the first piece ends, then solve the rest with one piece fewer. The best largest sum is the minimum over all choices of max(first piece, best of the rest).

Every arrangement of k − 1 cuts among n − 1 gaps is explored: C(n − 1, k − 1) ways, exponential in k. It restates the problem faithfully and is the starting point for the dynamic program, but it cannot handle n = 1000.

Dry run

  1. [7, 2, 5, 10, 8], k = 2: cut after 7 → max(7, 25) = 25
  2. cut after 2 → max(9, 23) = 23; after 5 → max(14, 18) = 18; after 10 → max(24, 8) = 24
  3. minimum is 18

Python

class Solution:
    def splitArray(self, nums: List[int], k: int) -> int:
        n = len(nums)

        def best(start: int, pieces: int) -> int:
            # smallest possible largest sum when nums[start:] is cut into `pieces` pieces
            if pieces == 1:
                return sum(nums[start:])        # no choice left: one piece takes the rest
            answer = float("inf")
            first = 0
            # the first piece is nums[start:end]; leave at least pieces - 1 elements for the rest
            for end in range(start + 1, n - pieces + 2):
                first += nums[end - 1]
                answer = min(answer, max(first, best(end, pieces - 1)))
            return answer

        return best(0, k)
Time O(C(n − 1, k − 1) · n)Space O(k)

Every way to place k − 1 cuts, with a sum per piece.

When to use: Only to state the problem as a recursion; it is the unmemoised form of the DP.

Memoise the recursion. Let dp[j][i] be the best largest sum when the first i elements form exactly j pieces. The last piece is nums[p..i-1] for some cut p, and the elements before it form j − 1 pieces as well as possible:

dp[j][i] = min over p in [j-1, i-1] of max(dp[j-1][p], prefix[i] − prefix[p])

with dp[1][i] = prefix[i]. Prefix sums make each piece sum O(1). The table has k · n cells and each scans up to n cuts, so O(k · n²): about 50 million steps for n = 1000, k = 50, too slow in Python, but a correct and classic solution that interviewers expect you to know.

Dry run

  1. [7, 2, 5, 10, 8], k = 2: dp[1] = prefix sums 7, 9, 14, 24, 32
  2. dp[2][2] = max(dp[1][1], 2) = 7
  3. dp[2][3] = min(max(7, 7), max(9, 5)) = 7; dp[2][4] = min(max(7, 17), max(9, 15), max(14, 10)) = 14
  4. dp[2][5] = min(max(7, 25), max(9, 23), max(14, 18), max(24, 8)) = 18

Python

class Solution:
    def splitArray(self, nums: List[int], k: int) -> int:
        n = len(nums)
        prefix = [0]
        for x in nums:
            prefix.append(prefix[-1] + x)       # prefix[i] = sum of the first i elements

        INF = float("inf")
        # dp[j][i]: best largest sum when the first i elements form exactly j pieces
        dp = [[INF] * (n + 1) for _ in range(k + 1)]
        dp[0][0] = 0
        for j in range(1, k + 1):
            for i in range(j, n + 1):           # at least j elements for j pieces
                for p in range(j - 1, i):       # the last piece is nums[p:i]
                    last_piece = prefix[i] - prefix[p]
                    dp[j][i] = min(dp[j][i], max(dp[j - 1][p], last_piece))
        return dp[k][n]
Time O(k · n²)Space O(k · n)

k · n cells, each a scan over up to n cut positions.

When to use: When k is tiny, or to show you know the DP before improving on it.

Watch it run

Search the answer instead of the cuts. For a candidate limit L, a greedy walk tells in O(n) how few pieces keep every piece sum <= L: extend the current piece until the next element would exceed L, then start a new one. If it needs at most k pieces, L is achievable; if it needs more, L is too small, and so is every smaller limit.

  • Range: lo = max(nums), hi = sum(nums).
  • pieces_needed(mid) <= k → hi = mid (mid works, maybe smaller does too).
  • otherwise → lo = mid + 1.
  • Stop at lo == hi.

About log₂(sum) ≤ 30 passes over the list: O(n · log(sum)), independent of k.

Dry run

  1. [7, 2, 5, 10, 8], k = 2: lo = 10, hi = 32
  2. mid = 21 → [7, 2, 5] [10, 8] = 2 pieces ✓ → hi = 21
  3. mid = 15 → [7, 2, 5] [10] [8] = 3 pieces ✗ → lo = 16
  4. mid = 18 → [7, 2, 5] [10, 8] ✓ → hi = 18; mid = 17 → 3 pieces ✗ → lo = 18 → answer 18

Python

class Solution:
    def splitArray(self, nums: List[int], k: int) -> int:
        def pieces_needed(limit: int) -> int:
            count, running = 1, 0                # the first piece is open from the start
            for x in nums:
                if running + x > limit:         # x would overflow this piece: close it, open a new one
                    count += 1
                    running = 0
                running += x
            return count

        lo, hi = max(nums), sum(nums)           # the largest element must fit .. one piece holds everything
        while lo < hi:
            mid = (lo + hi) // 2
            if pieces_needed(mid) <= k:
                hi = mid                        # mid is achievable (extra cuts never raise the maximum)
            else:
                lo = mid + 1                    # mid is too tight, so is everything below it
        return lo                               # lo == hi: the smallest achievable largest sum
Time O(n · log(sum))Space O(1)

About 30 greedy passes for sums up to 10⁹; k does not appear at all.

When to use: The expected answer for n = 1000, and the template shared with Koko and Capacity to Ship.

Common mistakes

  • Starting the search at lo = 0 or lo = 1 and letting the greedy count pieces anyway: with a limit below max(nums) the element that does not fit is counted as a piece that exceeds the limit, so the check lies. Start at max(nums).
  • Treating 'fewer than k pieces' as a failure: the greedy minimises pieces, and extra cuts never increase the largest sum, so pieces <= k is the right test, not pieces == k.
  • Forgetting that zeros are allowed: [0, 0, 0, 5, 0] with k = 3 is 5, and a greedy that starts a new piece on running + x >= limit instead of > miscounts when the limit is hit exactly.
  • In the DP, indexing the last cut wrongly: p must leave at least j - 1 elements for the earlier pieces and at least one for the last, so it runs from j - 1 to i - 1.
  • Using hi = mid - 1 after a successful check in the while lo < hi template: mid may be the answer. Keep it with hi = mid.

Python notes

  • itertools.accumulate(nums, initial=0) builds the prefix sums the DP needs: prefix[i] is the sum of the first i elements, so sum(nums[p:i]) == prefix[i] - prefix[p].
  • functools.cache on the recursive brute force turns it into the memoised DP with one line; the table version below is the same computation written bottom-up.
  • Python 3.10+: limits = range(max(nums), sum(nums) + 1) then limits[bisect.bisect_left(limits, True, key=fits)] runs the binary search on the answer with a key function.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Capacity To Ship Packages Within D Days LC 1011 — the same problem in a story: weights are the numbers, days are the pieces, the capacity is the limit.
  • Koko Eating Bananas LC 875 — binary search on the answer with an even simpler check: a sum of ceilings instead of a greedy walk.
  • Minimize Max Distance to Gas Station LC 774 — the limit is a real number: binary search on floats with a tolerance, the check counts stations per gap.
  • Painter's Partition / Allocate Books — classic interview names for exactly this problem: boards are elements, painters are pieces, time is the limit.
  • Divide Chocolate LC 1231 — maximise the smallest piece instead: the greedy closes a piece as soon as it reaches the limit, and you search for the last limit that still yields k + 1 pieces.
  • What if the pieces need not be contiguous? — then it is multiway number partitioning, NP-hard; the greedy check no longer works and you need search or heuristics.
