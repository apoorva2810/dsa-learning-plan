Find K Closest Elements Medium 250

LeetCode #658 ↗
Status

Pick the k values of a sorted list that are closest to x, by binary searching where the answer starts.

Problem

You are given a list arr sorted in ascending order (values may repeat), an integer k and a target value x. Return the k values of arr that are closest to x, in ascending order.

A value a is closer to x than a value b when |a - x| < |b - x|, or when the two distances are equal and a < b. In other words, a tie goes to the smaller value.

Examples

Example 1
Input: arr = [2, 4, 6, 8, 10], k = 3, x = 7
Output: [4, 6, 8]
6 and 8 are 1 away. 4 and 10 are both 3 away, and the tie goes to the smaller value, 4.
Example 2
Input: arr = [1, 2, 3, 4, 5], k = 4, x = 10
Output: [2, 3, 4, 5]
x is beyond the right end, so the four largest values are the closest.
Example 3
Input: arr = [-5, 0, 3, 3, 9], k = 2, x = 2
Output: [3, 3]
Both 3s are 1 away; the next closest value, 0, is 2 away.

Constraints

  • 1 <= k <= len(arr)
  • 1 <= len(arr) <= 10^4
  • arr is sorted in ascending order
  • -10^4 <= arr[i], x <= 10^4

Think first try before reading the solution

The list is sorted, so the k closest values always sit next to each other. If a value is in the answer, every value between it and x is at least as close. What does that say about the shape of the answer?
The answer is a window arr[start : start + k]. Which values of start are possible, and how could you compare two neighbouring windows cheaply?
The windows starting at s and s + 1 differ only by arr[s] (leaving) and arr[s + k] (entering). Whichever of the two is farther from x should not be in the answer, and that decision is monotone along s: binary search on start in 0 .. n - k.

Key idea

In a sorted list, the k values closest to x always form one consecutive block. If a value is in the answer, every value between it and x is at least as close, so it is in the answer too. The whole problem is therefore to find where the block starts.

The start can be any index from 0 to n - k. Compare the window that starts at mid with the one that starts at mid + 1: they share k - 1 values and differ only in arr[mid] (leaving) and arr[mid + k] (entering). If arr[mid] is strictly farther from x, the block should start to the right of mid. Otherwise (including a tie, where the smaller value wins) it can start at mid or to its left.

That yes/no answer flips only once along the start positions (first "go right", then "stay"), so binary search applies: about log₂(n − k) comparisons to find the start, then O(k) to copy the answer.

Approaches from the obvious one to the one you want in an interview

Sort all values by how close they are to x (distance first, then the smaller value on a tie), keep the first k, and sort those back into ascending order.

It never uses the fact that arr is already sorted. The sort costs O(n log n) and the copies O(n), while the real answer is one consecutive block that can be located much faster.

Dry run

  1. arr = [2, 4, 6, 8, 10], k = 3, x = 7 → distances 5, 3, 1, 1, 3
  2. Sorted by (distance, value): 6, 8, 4, 10, 2. The first three are 6, 8, 4.
  3. Sort those ascending → [4, 6, 8].

Python

class Solution:
    def findClosestElements(self, arr: List[int], k: int, x: int) -> List[int]:
        by_distance = sorted(arr, key=lambda v: (abs(v - x), v))   # closest first; a tie goes to the smaller value
        return sorted(by_distance[:k])                              # the k closest, back in ascending order
Time O(n log n)Space O(n)

Sorting n values by distance, then sorting k of them; the sorted copy holds n values.

When to use: A quick first answer that ignores the sorted input.

The answer is a block of k consecutive values, so start with the whole list as the block and remove the farther end until only k values remain. If arr[left] is farther from x than arr[right], drop the left end; otherwise (including a tie, where the smaller value wins) drop the right end.

That is n - k steps with O(1) extra memory, which already uses the sorted order. It is slow when k is small, because it discards almost the whole list one value at a time.

Dry run

  1. arr = [2, 4, 6, 8, 10], k = 3, x = 7 → left = 0, right = 4
  2. 2 is 5 away, 10 is 3 away → the left end is farther → left = 1
  3. 4 is 3 away, 10 is 3 away → a tie, so the smaller value stays → drop 10, right = 3
  4. 3 values remain: [4, 6, 8].

Python

class Solution:
    def findClosestElements(self, arr: List[int], k: int, x: int) -> List[int]:
        left, right = 0, len(arr) - 1
        while right - left + 1 > k:                        # still more than k values in the block
            if abs(arr[left] - x) > abs(arr[right] - x):
                left += 1                                  # the left end is farther: drop it
            else:
                right -= 1                                 # the right end is farther or tied: drop it
        return arr[left:right + 1]
Time O(n)Space O(1)

The loop runs n - k times; the final slice copies k values (the output).

When to use: Simple and linear. Prefer the binary search when n is large and k is small.

Binary search the start of the block. Let lo = 0 and hi = n - k. While lo < hi, take mid and compare the window's left end arr[mid] with the value just outside its right end, arr[mid + k]:

  • if arr[mid] is strictly farther from x (x - arr[mid] > arr[mid + k] - x), the block starts further right: lo = mid + 1;
  • otherwise (a tie keeps the smaller value, so it ends up here too), the block can start at mid or earlier: hi = mid.

When lo == hi, the answer is arr[lo : lo + k]. Each step halves the range of possible starts, so the search takes O(log(n − k)) comparisons, and copying the answer takes O(k).

Dry run

  1. arr = [2, 4, 5, 8, 9, 12, 13, 15, 20], k = 4, x = 10 → possible starts 0..5
  2. mid = 2: window [5, 8, 9, 12]; 5 is 5 away, 13 is 3 away → left end farther → lo = 3
  3. mid = 4: window [9, 12, 13, 15]; 9 is 1 away, 20 is 10 away → left end closer → hi = 4
  4. mid = 3: window [8, 9, 12, 13]; 8 is 2 away, 15 is 5 away → left end closer → hi = 3 → start 3, answer [8, 9, 12, 13].

Python

class Solution:
    def findClosestElements(self, arr: List[int], k: int, x: int) -> List[int]:
        lo, hi = 0, len(arr) - k                    # the window can start anywhere from 0 to n - k
        while lo < hi:
            mid = (lo + hi) // 2
            # the windows at mid and mid + 1 differ by arr[mid] (leaving) and arr[mid + k] (entering)
            if x - arr[mid] > arr[mid + k] - x:
                lo = mid + 1                        # arr[mid] is farther: the window starts further right
            else:
                hi = mid                            # arr[mid + k] is farther or tied: start at mid or earlier
        return arr[lo:lo + k]
Time O(log(n − k) + k)Space O(1)

O(log(n - k)) comparisons to find the start, then O(k) to copy the answer (the output itself).

When to use: The standard answer for a sorted list: it only looks at about log n values before copying the result.

Common mistakes

  • Searching with hi = len(arr) - 1. The window arr[mid : mid + k] then runs past the end and arr[mid + k] raises IndexError. The last possible start is n - k, so hi = len(arr) - k.
  • Mixing binary-search templates. Here mid itself may be the right start, so use while lo < hi with hi = mid (not mid - 1), and lo = mid + 1 only when arr[mid] is strictly farther.
  • Getting ties wrong. When the two ends are equally far from x, the smaller value must stay, so the test for moving right is a strict >; a tie sets hi = mid.
  • Comparing only arr[mid] with x. The decision needs both values that differ between the two windows: arr[mid] and arr[mid + k].
  • Returning the values in distance order. The result must be ascending; slicing arr[lo : lo + k] gives that for free, while the brute force has to sort again.

Python notes

  • sorted(arr, key=lambda v: (abs(v - x), v)) sorts by distance first and by value on ties: tuples compare element by element.
  • arr[lo:lo + k] copies the answer in O(k), and it is already in ascending order.
  • (lo + hi) // 2 cannot overflow in Python. In languages with fixed-size integers, write lo + (hi - lo) // 2.
  • bisect.bisect_left(arr, x) returns the insertion index of x, which is what the 'find x, then expand' variant starts from.

What an interviewer might ask next, and what changes.

  • Binary Search LC 704 — the plain version of halving a sorted list to find one value.
  • Search Insert Position LC 35 — the position where x would be inserted: the first step of the other common solution, which finds that spot and then expands outwards, taking the closer neighbour each time.
  • K Closest Points to Origin LC 973 — 'k closest' with no sorted order and in 2-D: keep a max-heap of size k instead of searching a window.
  • Kth Missing Positive Number LC 1539 — binary search on a quantity that grows with the index: how many numbers are missing before position i.
  • Find Peak Element LC 162 — binary search by comparing a value with its neighbour to decide which half to keep, as here with arr[mid] and arr[mid + k].
  • What if the list is not sorted? — the answer is no longer a block. Sort first (O(n log n)), or keep a max-heap of the k best candidates while scanning (O(n log k)).
