Accounts Merge Medium 250

LeetCode #721 ↗
Status

Merge accounts that share an email into one account per person, with the emails sorted.

Problem

You get a list accounts. Each entry is a list of strings whose first element is a person's name and whose remaining elements are emails belonging to that person's account.

Two accounts belong to the same person if they share at least one email, and this spreads: if account A shares an email with B, and B shares one with C, then A, B and C are all the same person. Two accounts with the same name but no shared email may be different people, so names alone never merge anything. All accounts of one person carry the same name.

Return the merged accounts: one list per person, in the form [name, email1, email2, ...] with the emails in sorted (ASCII) order and no duplicates. The merged accounts themselves may be returned in any order.

Examples

Example 1
Input: accounts = [["John", "johnsmith@mail.com", "john_newyork@mail.com"], ["John", "johnsmith@mail.com", "john00@mail.com"], ["Mary", "mary@mail.com"], ["John", "johnnybravo@mail.com"]]
Output: [["John", "john00@mail.com", "john_newyork@mail.com", "johnsmith@mail.com"], ["Mary", "mary@mail.com"], ["John", "johnnybravo@mail.com"]]
The first two John accounts share johnsmith@mail.com, so they are one person. The third John shares nothing with them: same name, different person.
Example 2
Input: accounts = [["Alex", "a@x.com", "b@x.com"], ["Alex", "c@x.com"], ["Alex", "d@x.com", "c@x.com"], ["Alex", "b@x.com", "d@x.com"], ["Sam", "s@x.com"]]
Output: [["Alex", "a@x.com", "b@x.com", "c@x.com", "d@x.com"], ["Sam", "s@x.com"]]
Accounts 0 and 3 share b@x.com; accounts 1, 2 and 3 are linked through c@x.com and d@x.com. The fourth account bridges two groups that had nothing in common before.
Example 3
Input: accounts = [["Bob", "bob@x.com", "b@x.com"], ["Bob", "bob2@x.com"]]
Output: [["Bob", "b@x.com", "bob@x.com"], ["Bob", "bob2@x.com"]]
No shared email, so the two Bobs stay separate. Inside an account the emails are sorted, so b@x.com comes before bob@x.com.

Constraints

  • 1 <= len(accounts) <= 1000
  • 2 <= len(accounts[i]) <= 10 (one name plus 1 to 9 emails)
  • 1 <= len(accounts[i][j]) <= 30
  • names are letters only; emails contain '@' and '.'

Key idea

Two accounts that share an email are the same person, and the relation spreads along chains. So picture every account as a node and every shared email as an edge between two accounts: a person is a connected component of that graph, and the answer lists each component's emails.

Building the edges is the only subtle part. Comparing every pair of accounts costs O(n²) set intersections. Instead, walk the emails once with a dictionary owner: the first account that lists an email becomes its owner, and any later account that lists the same email gets joined to that owner. Each email creates at most one edge.

Union-find keeps the components as trees. Every account points towards a root that names its group; find(i) follows the pointers, and union(a, b) hangs one root under the other. After one pass over all emails, accounts with the same root are the same person. Finally gather every email under find(owner[email]), sort each bucket, and put the name in front.

Approaches from the obvious one to the one you want in an interview

Keep a list of groups, each a set of emails. Go through the accounts: if an account shares an email with an existing group, pour its emails into that group; otherwise start a new group. Then repeat the whole pass on the groups themselves, because an account processed late can bridge two groups that were separate earlier. Stop when a pass merges nothing.

Every pass compares each group with every other group through a set intersection, O(n² · K) with K emails per account, and a chain of bridges can need up to n passes. That is far too slow for 1000 accounts, and the repeated passes are exactly the waste union-find removes.

Dry run

  1. Example 2: accounts 0 and 1 start groups {a, b} and {c}; account 2 shares c → group {c, d}
  2. Account 3 ({b, d}) shares b with {a, b} → pour it in: {a, b, d}. The {c, d} group now also shares d
  3. Pass 1 changed something, so run pass 2: {a, b, d} and {c, d} share d → {a, b, c, d}; Sam's group alone
  4. Pass 3 changes nothing → stop. Sort each group and prepend its name

Python

class Solution:
    def accountsMerge(self, accounts: List[List[str]]) -> List[List[str]]:
        groups = [[account[0], set(account[1:])] for account in accounts]
        changed = True
        while changed:                               # repeat until no two groups share an email
            changed = False
            merged = []
            for name, emails in groups:
                for group in merged:                 # does an earlier group share an email?
                    if group[1] & emails:            # shared email: same person (and same name)
                        group[1] |= emails
                        changed = True
                        break
                else:
                    merged.append([name, set(emails)])
            groups = merged
        return [[name] + sorted(emails) for name, emails in groups]
Time O(n³ · K)Space O(n · K)

Up to n passes, each comparing O(n²) pairs of groups with set intersections over K emails.

When to use: Never for real input; it shows why one careful pass with union-find is the goal.

Accounts are the nodes. Walk the emails once with a dictionary owner: the first account to list an email owns it; when a later account i lists an email owned by j, call union(j, i), which joins the two groups by hanging one root under the other. Because union works on roots, a late account that touches two different groups merges both of them in one step: no second pass is ever needed.

Afterwards every account has a root, and find(owner[email]) tells which person each email belongs to. Bucket the emails by root, sort each bucket, and put the root account's name in front. The sort dominates: O(N log N) for N total emails, and the union-find work is near-constant per email thanks to path halving.

Dry run

  1. Example 2: account 0 owns a and b; account 1 owns c; account 2 owns d, then lists c (owner 1) → parent[2] = 1
  2. Account 3 lists b (owner 0) → parent[3] = 0; then d (owner 2, root 1) → find(2) = 1, find(3) = 0 → parent[0] = 1
  3. Account 4 owns s. Roots: 1 and 4 → two people
  4. Bucket by root: 1 → {a, b, c, d}, 4 → {s}. Sort, prepend names: [Alex, a, b, c, d], [Sam, s]

Python

class Solution:
    def accountsMerge(self, accounts: List[List[str]]) -> List[List[str]]:
        n = len(accounts)
        parent = list(range(n))                      # union-find over account indexes

        def find(x: int) -> int:
            while parent[x] != x:
                parent[x] = parent[parent[x]]        # path halving keeps the trees shallow
                x = parent[x]
            return x

        def union(a: int, b: int) -> None:
            root_a, root_b = find(a), find(b)
            if root_a != root_b:
                parent[root_b] = root_a              # hang one root under the other

        owner = {}                                   # email -> first account that listed it
        for i, account in enumerate(accounts):
            for email in account[1:]:
                if email in owner:
                    union(owner[email], i)           # shared email: same person
                else:
                    owner[email] = i
        emails_of = defaultdict(list)                # root account -> every email of that person
        for email, i in owner.items():
            emails_of[find(i)].append(email)
        return [[accounts[root][0]] + sorted(emails) for root, emails in emails_of.items()]
Time O(N log N)Space O(N)

N = total emails. One near-constant union-find step per email; sorting each bucket dominates.

When to use: The expected answer: one pass to build the groups, no recursion, and bridges are free.

Watch it run

Make the emails the nodes instead. Inside each account, link every email to the account's first email (a star, so k - 1 edges for k emails). Two accounts that share an email now sit in the same connected component, because that email is a node of both stars.

Run a DFS from every email not yet visited, collect the component, sort it, and look up the name through an email → name map. Same O(N log N) overall, but the graph itself is bigger (a node per email instead of per account), and a recursive DFS on a long chain of accounts can hit Python's recursion limit, so the iterative stack version is safer.

Dry run

  1. Example 1: stars johnsmith–john_newyork (account 0), johnsmith–john00 (account 1), mary alone, johnnybravo alone
  2. DFS from johnsmith reaches john_newyork and john00 → one component of three emails → sort → John's account
  3. DFS from mary → [Mary, mary]. DFS from johnnybravo → [John, johnnybravo]

Python

class Solution:
    def accountsMerge(self, accounts: List[List[str]]) -> List[List[str]]:
        graph = defaultdict(list)                    # email -> neighbouring emails
        name_of = {}                                 # email -> name of its person
        for account in accounts:
            name, emails = account[0], account[1:]
            for email in emails:
                name_of[email] = name
                if email != emails[0]:               # star: every email links to the first email
                    graph[emails[0]].append(email)
                    graph[email].append(emails[0])
        seen = set()
        result = []
        for email in name_of:                        # every distinct email, once
            if email in seen:
                continue
            seen.add(email)
            stack, component = [email], []
            while stack:                             # iterative DFS collects one person's emails
                cur = stack.pop()
                component.append(cur)
                for nxt in graph[cur]:
                    if nxt not in seen:
                        seen.add(nxt)
                        stack.append(nxt)
            result.append([name_of[email]] + sorted(component))
        return result
Time O(N log N)Space O(N)

Each email is visited once by the DFS; sorting the components dominates.

When to use: When you prefer an explicit graph, or already have a DFS component routine to reuse.

Common mistakes

  • Merging accounts by name. Same name does not mean same person (the third John in example 1). Only a shared email merges two accounts.
  • Comparing each account with the groups formed so far and stopping after one pass. A later account can bridge two earlier groups (example 2), which that single pass never notices. Union-find handles the bridge because union works on roots, not on the accounts themselves.
  • Grouping emails by owner[email] instead of find(owner[email]). An owner that was merged into another group later is no longer a root, so its emails would land in a stale, separate account.
  • Forgetting to sort, or sorting by a lowercase key. The expected order is plain ASCII: sorted(emails) with no key, so B@x.com comes before a@x.com.
  • Connecting every pair of emails inside an account when building a DFS graph (k² edges per account). Linking each email to the account's first email gives the same components with k - 1 edges.

Python notes

  • name, *emails = account unpacks the name and the rest of the list in one line.
  • sorted(emails) on strings gives ASCII order (digits before uppercase before lowercase), which is exactly the order the problem asks for. Do not pass key=str.lower.
  • defaultdict(list) makes the bucketing one line: emails_of[find(i)].append(email).
  • Dictionary iteration order is insertion order, so iterating owner visits every distinct email exactly once.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Number of Connected Components in an Undirected Graph LC 323 — the same union-find on plain edges; count the successful unions instead of collecting emails.
  • Redundant Connection LC 684 — the same find and union, but the question is which edge joins two already-connected nodes.
  • Smallest String With Swaps LC 1202 — union the indices joined by swap pairs, then sort the characters inside each group: the same 'group, then sort each bucket' finish.
  • Similar String Groups LC 839 — the nodes are strings and an edge exists when two strings differ in at most two positions, so building the edges costs O(n² · L) comparisons; the union-find part is unchanged.
  • Sentence Similarity II LC 737 — union the word pairs declared similar, then two sentences match when every word pair shares a root.
  • What if accounts arrive one by one and you must answer 'same person?' at any time? — keep the union-find alive: union on arrival, compare roots on a query, and only build the sorted lists when someone asks for them.
