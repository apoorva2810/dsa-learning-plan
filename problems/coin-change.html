Coin Change Medium

LeetCode #322 ↗
Status

Find the fewest coins that add up to an amount, using each coin type as often as you like.

Problem

You are given a list coins of coin values (you have an unlimited supply of each) and an integer amount. Return the fewest coins whose values add up to exactly amount, or -1 if no combination works.

An amount of 0 needs 0 coins.

Examples

Example 1
Input: coins = [1, 2, 5], amount = 11
Output: 3
5 + 5 + 1.
Example 2
Input: coins = [2], amount = 3
Output: -1
Only even totals can be made.
Example 3
Input: coins = [1, 3, 4], amount = 6
Output: 2
3 + 3. Taking the biggest coin first gives 4 + 1 + 1, which is one coin more.

Constraints

  • 1 <= len(coins) <= 12
  • 1 <= coins[i] <= 2^31 - 1
  • 0 <= amount <= 10^4

Think first try before reading the solution

Why does "always take the biggest coin that fits" fail? Try coins = [1, 3, 4], amount = 6.
Think about the last coin of an optimal answer for amount a. If it is c, the other coins form an optimal answer for a - c. So fewest(a) = 1 + min(fewest(a - c)) over the coins c <= a.
Fill dp[0..amount] from small to large with dp[0] = 0 and every other cell starting at infinity ("not possible yet"). The answer is dp[amount], or -1 if it is still infinity.

Key idea

Greedy is the trap. With [1, 3, 4] and amount 6, taking the 4 first forces 4 + 1 + 1, while 3 + 3 uses two coins. With [3, 5] and amount 9, greedy takes 5 and gets stuck at 4, although 3 + 3 + 3 works. A coin that looks best now can make the remainder expensive, so the choices have to be compared.

The DP question is about the last coin. Any optimal way to pay a ends with some coin c; remove it and what is left is a way to pay a - c, and it must be an optimal one (otherwise swapping in a better one would improve a). So

dp[a] = 1 + min(dp[a - c] for every coin c <= a), with dp[0] = 0.

Amounts that cannot be made stay at infinity, which never wins a min. Every cell reads only smaller amounts, so filling dp[1], dp[2], ..., dp[amount] in order works. The table has amount + 1 cells and each tries every coin: O(amount × k) time for k coin types.

Approaches from the obvious one to the one you want in an interview

fewest(a) tries every coin c <= a as the last coin and recurses on a - c; fewest(0) = 0, and an amount with no fitting coin is infinity. The minimum over all choices is the answer.

Every distinct order of coins is explored separately (5 + 1 and 1 + 5 lead to the same remainders), so the number of calls explodes: with coins [1, 5, 10, 25] and amount 63 this makes about 390 million calls.

Dry run

  1. coins = [1, 3, 4], fewest(6) = 1 + min(fewest(5), fewest(3), fewest(2))
  2. fewest(3) = 1 + min(fewest(2), fewest(0)) = 1 + 0 = 1
  3. fewest(2) = 2 and fewest(5) = 2 (4 + 1), each recomputing smaller amounts again
  4. fewest(6) = 1 + min(2, 1, 2) = 2

Python

class Solution:
    def coinChange(self, coins: List[int], amount: int) -> int:
        INF = float("inf")

        def fewest(a: int) -> float:
            """Fewest coins that sum to a (INF if impossible)."""
            if a == 0:
                return 0
            best = INF
            for c in coins:
                if c <= a:                                # c could be the last coin
                    best = min(best, fewest(a - c) + 1)
            return best

        answer = fewest(amount)
        return -1 if answer == INF else answer
Time O(k^(amount / min coin))Space O(amount / min coin)

Up to k branches per call, and the depth is the number of coins in the longest sum.

When to use: Only to discover the recurrence; it passes the small tests here and nothing bigger.

Cache fewest(a). There are only amount + 1 distinct amounts, each tries k coins, so the work is O(amount × k). The weakness is depth: with a coin of value 1, fewest(10000) calls fewest(9999), which calls fewest(9998), ... 10^4 nested calls, far beyond Python's default limit of 1000.

Time O(amount · k)Space O(amount)

amount + 1 states, k coins tried per state; cache and call stack up to amount deep.

When to use: Fine when amounts are small; for 10^4 it needs sys.setrecursionlimit in Python.

Fill dp[0..amount] in increasing order: dp[0] = 0, everything else starts at infinity. For each amount a, try every coin c <= a as the last coin and keep dp[a] = min(dp[a], dp[a - c] + 1).

Smaller amounts are final before any larger amount reads them, so one pass is enough. Infinity marks amounts that cannot be made; it is never smaller than a real count, so it never wins.

Dry run

  1. coins = [1, 3, 4], amount = 6: dp = [0, ∞, ∞, ∞, ∞, ∞, ∞]
  2. dp[1] = 1, dp[2] = 2, dp[3] = min(dp[2] + 1, dp[0] + 1) = 1
  3. dp[4] = min(dp[3] + 1, dp[1] + 1, dp[0] + 1) = 1, dp[5] = min(2, 3, 2) = 2
  4. dp[6] = min(dp[5] + 1, dp[3] + 1, dp[2] + 1) = min(3, 2, 3) = 2

Python

class Solution:
    def coinChange(self, coins: List[int], amount: int) -> int:
        INF = float("inf")
        dp = [0] + [INF] * amount          # dp[a] = fewest coins that make a; INF = impossible (so far)
        for a in range(1, amount + 1):     # small amounts first: dp[a - c] is already final
            for c in coins:
                if c <= a:                 # coin c could be the last coin of the sum
                    dp[a] = min(dp[a], dp[a - c] + 1)
        return dp[amount] if dp[amount] != INF else -1
Time O(amount · k)Space O(amount)

amount cells, each trying k coins; one list of amount + 1 entries.

When to use: The standard answer: no recursion limit, and the loop order is easy to justify.

Watch it run

View amounts as nodes and coins as edges from x to x + c. Breadth-first search (BFS) explores all sums reachable with 1 coin, then with 2 coins, and so on, so the first time it reaches amount the number of levels is the fewest coins. A seen set makes sure each amount is queued once.

The worst case is the same O(amount × k) as the table, but BFS can stop early when the answer needs few coins, and it never touches amounts larger than the target.

Dry run

  1. coins = [1, 3, 4], amount = 6: level 1 from 0 reaches 1, 3, 4
  2. level 2 from 1 reaches 2, 5 (4 already seen); from 3 reaches 6 → answer 2

Python

class Solution:
    def coinChange(self, coins: List[int], amount: int) -> int:
        if amount == 0:
            return 0
        seen = {0}
        queue = deque([0])                 # sums reachable with `coins_used` coins
        coins_used = 0
        while queue:
            coins_used += 1
            for _ in range(len(queue)):    # one BFS level = one more coin
                total = queue.popleft()
                for c in coins:
                    nxt = total + c
                    if nxt == amount:
                        return coins_used
                    if nxt < amount and nxt not in seen:
                        seen.add(nxt)
                        queue.append(nxt)
        return -1
Time O(amount · k)Space O(amount)

Each amount below the target is queued at most once and tries k coins.

When to use: When you recognise "fewest steps" as a shortest path; it often finishes early.

Common mistakes

  • Greedy by largest coin: wrong on [1, 3, 4] → 6 (gives 3 coins, best is 2), and it can even miss every solution, as on [3, 5] → 9.
  • Starting the table at 0 instead of infinity. A minimum that starts at 0 never changes; use float("inf") (or amount + 1, which is more coins than any real answer needs).
  • Forgetting to turn infinity into -1 at the end, or answering -1 for amount = 0 (the answer is 0 coins).
  • Top-down recursion with coin 1 and amount 10^4 nests 10^4 calls and raises RecursionError in Python. The bottom-up table has no depth at all.
  • Reading dp[a - c] without checking c <= a: a negative index silently reads from the end of the list.

Python notes

  • float("inf") is larger than every integer and inf + 1 is still inf, so impossible amounts never win a min.
  • @cache makes the top-down version O(amount × k), but the recursion can be amount frames deep (with a coin of 1). Python's default recursion limit is 1000, so amount = 10^4 raises RecursionError unless you raise the limit. Prefer the bottom-up loop.
  • dp = [0] + [INF] * amount builds the table in one line: index 0 is the base case, everything else starts as "not possible yet".

Follow-up questions

What an interviewer might ask next, and what changes.

  • Coin Change II LC 518 — count the combinations instead of minimising: dp[a] += dp[a - c], with the coin loop outside the amount loop so each combination is counted once, not once per ordering.
  • Combination Sum IV LC 377 — count ordered sequences: the same +=, but the amount loop is outside, so 1 + 2 and 2 + 1 both count.
  • Perfect Squares LC 279 — this exact problem where the coins are the squares 1, 4, 9, ... up to n.
  • Minimum Cost For Tickets LC 983 — the "coins" are 1-, 7- and 30-day passes with prices, and the amount is the travel calendar.
  • Return the coins themselves — store last_coin[a] whenever dp[a] improves, then walk a → a - last_coin[a] back to 0.
  • When is greedy correct? — for "canonical" systems such as 1, 5, 10, 25 greedy is optimal; for arbitrary coins it is not, and checking canonicity is its own problem. DP works for any coin set.
