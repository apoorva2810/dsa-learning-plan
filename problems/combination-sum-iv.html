Combination Sum IV Medium 250

LeetCode #377 ↗
Status

Count the ordered lists of numbers, repeats allowed, that add up to a target.

Problem

You are given a list nums of distinct positive integers and an integer target.

Return how many sequences of numbers taken from nums add up to exactly target. A number may be used as many times as you like, and the order counts: 1, 2 and 2, 1 are two different sequences.

  • If no sequence reaches the target, return 0.
  • The answer is guaranteed to fit in a signed 32-bit integer.

Despite the word "combination" in the title, order matters here. Coin Change II counts the order-free version.

Examples

Example 1
Input: nums = [1, 2], target = 4
Output: 5
The sequences are 1+1+1+1, 1+1+2, 1+2+1, 2+1+1 and 2+2.
Example 2
Input: nums = [2, 3], target = 7
Output: 3
Only the numbers 2, 2, 3 work, but they can stand in three orders: 2+2+3, 2+3+2 and 3+2+2.
Example 3
Input: nums = [4], target = 6
Output: 0
The only number is 4, and no number of 4s adds up to 6.

Constraints

  • 1 <= len(nums) <= 200
  • 1 <= nums[i] <= 1000
  • all values in nums are different
  • 1 <= target <= 1000
  • the answer fits in a signed 32-bit integer

Think first try before reading the solution

Describe a sequence by its last number. If the last number is x and the whole sequence adds up to t, what must the numbers in front of x add up to?
They form a sequence that adds up to t - x, and every such sequence can be extended by x. So the count for t is the sum, over every number x <= t, of the count for t - x. What is the count for 0?
Fill dp[0..target] from small to large with dp[0] = 1 (the empty sequence). Each cell reads only smaller cells, so two nested loops with a += are the whole algorithm.

Key idea

A counting problem needs a way to cut every answer into a smaller problem of the same shape without missing or repeating any. Look at the last number of a sequence.

Every sequence that adds up to t ends in exactly one number x from nums. Remove it and what remains is a sequence that adds up to t - x. Going the other way, take any sequence that adds up to t - x and append x: you get a sequence for t. So the sequences for t that end in x correspond one-to-one with the sequences for t - x, and since each sequence has exactly one last number, adding over all x counts everything once:

dp[t] = sum of dp[t - x] for every x in nums with x <= t, and dp[0] = 1.

The base case is 1, not 0: there is exactly one way to add up to nothing, the empty sequence (no numbers at all). Every other cell is built on top of that 1.

Order counts for free. 1, 2 ends in 2, so it is counted through dp[1]; 2, 1 ends in 1, so it is counted through dp[2]. They are different last numbers, hence different terms of the sum.

The loops are ordered totals outside, numbers inside: for each total t we let every number be the last one. Swap them (numbers outside) and you count each multiset of numbers once, which is Coin Change II.

Approaches from the obvious one to the one you want in an interview

count(r) = the number of ordered sequences that add up to r. Try every number x <= r as the last one: what stands in front of it is a sequence that adds up to r - x, so add count(r - x). count(0) = 1 (the empty sequence), and a remaining value below every number gives an empty sum, 0.

It is correct, but count(r - 1) and count(r - 2) both call count(r - 3), and so on down the line: the same subproblems are solved again and again. With nums = [1, 2, 3] the number of calls grows by about 1.8 times for every +1 on the target: 600 calls for target 10, 6,872 for 14, 266,079 for 20 and over 100 million for 30.

Dry run

  1. nums = [1, 2], target = 3: count(3) = count(2) (last number 1) + count(1) (last number 2)
  2. count(2) = count(1) + count(0) = ? + 1
  3. count(1) = count(0) = 1 (the number 2 is too big); this value is computed a second time for count(3)
  4. count(2) = 1 + 1 = 2, so count(3) = 2 + 1 = 3: 1+1+1, 2+1 and 1+2

Python

class Solution:
    def combinationSum4(self, nums: List[int], target: int) -> int:
        def count(remaining: int) -> int:
            """Ordered sequences from nums that add up to `remaining`."""
            if remaining == 0:                      # nothing left to add: the empty sequence finishes it
                return 1
            total = 0
            for x in nums:
                if x <= remaining:                  # x can be the last number of the sequence
                    total += count(remaining - x)   # the numbers in front of it add up to remaining - x
            return total

        return count(target)
Time O(k^(target / min num))Space O(target / min num)

Up to k = len(nums) branches per call; the depth is at most target divided by the smallest number.

When to use: Only to discover the recurrence; it is fine for tiny targets and hopeless for 100.

Wrap count in @cache. There are only target + 1 different arguments, and each one tries k numbers, so the work drops to O(target × k). Every call after the first for the same r is a lookup.

The weakness is depth: with a 1 in nums, count(1000) calls count(999), which calls count(998), and so on, a thousand frames deep. That is the limit of Python's default recursion depth.

Python

class Solution:
    def combinationSum4(self, nums: List[int], target: int) -> int:
        @cache                                      # each remaining value is solved once
        def count(remaining: int) -> int:
            if remaining == 0:
                return 1
            total = 0
            for x in nums:
                if x <= remaining:
                    total += count(remaining - x)
            return total

        return count(target)
Time O(target · k)Space O(target)

target + 1 states, k numbers tried in each; the cache and the call stack both hold up to target entries.

When to use: Good when you think recursively first; switch to the loop if the target can be near Python's recursion limit.

Fill dp[0..target] from small to large. dp[0] = 1 and every other cell starts at 0. For each total t, let every number x <= t be the last one and add the cell it leaves behind: dp[t] += dp[t - x].

Cells below t are already final when t reads them, so one pass is enough, and there is no recursion. Totals are the outer loop: that is what lets 1, 2 and 2, 1 both count.

Dry run

  1. nums = [1, 2], target = 4: dp = [1, 0, 0, 0, 0]
  2. dp[1] = dp[0] = 1 (the number 2 is too big)
  3. dp[2] = dp[1] + dp[0] = 1 + 1 = 2: 1+1 and 2
  4. dp[3] = dp[2] + dp[1] = 2 + 1 = 3: 1+1+1, 2+1 (end in 1) and 1+2 (ends in 2)
  5. dp[4] = dp[3] + dp[2] = 3 + 2 = 5: the answer

Python

class Solution:
    def combinationSum4(self, nums: List[int], target: int) -> int:
        dp = [1] + [0] * target                     # dp[t] = ordered sequences that add up to t; the empty one makes 0
        for t in range(1, target + 1):              # small totals first, so dp[t - x] is already final
            for x in nums:
                if x <= t:                          # x can be the last number of a sequence for t
                    dp[t] += dp[t - x]              # sequences for t - x, each followed by x
        return dp[target]
Time O(target · k)Space O(target)

target cells, each trying k numbers; one list of target + 1 integers.

When to use: The standard answer: no recursion limit, and the loop order is easy to justify.

Common mistakes

  • Counting 1, 2 and 2, 1 once. The answer for nums = [1, 2], target = 4 is 5, not the 3 order-free combinations (1+1+1+1, 1+1+2, 2+2).
  • Putting the numbers in the outer loop. dp[t] += dp[t - x] with the numbers outside counts combinations: example 1 returns 3 instead of 5 and example 2 returns 1 instead of 3. Keep the totals outside.
  • Starting with dp[0] = 0. Every cell is built from dp[0], so the whole table stays 0. The empty sequence is the one way to add up to nothing.
  • Reading dp[t - x] without checking x <= t. A negative index does not crash, it reads from the end of the list: nums = [2, 3], target = 1 returns 1 instead of 0.
  • Top-down recursion with a 1 in nums is target calls deep. At target = 1000 that is more than Python's default recursion limit of 1000 allows (RecursionError); the loops have no depth at all.

Python notes

  • dp = [1] + [0] * target builds the whole table: index 0 is the base case, everything else starts at zero.
  • The inner loop can be one line, dp[t] = sum(dp[t - x] for x in nums if x <= t), and means the same thing. The explicit loop is easier to step through.
  • Python integers never overflow, so no % MOD and no long are needed.
  • @cache goes on a function defined inside the method, so every call starts with an empty cache. The recursion is target / min(nums) frames deep; with a 1 in nums and target = 1000 that reaches Python's default limit.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Climbing Stairs LC 70 — this exact problem with nums = [1, 2]: the steps you may take are the numbers, and the order of steps matters, so dp[t] = dp[t - 1] + dp[t - 2].
  • Coin Change II LC 518 — count combinations where order is ignored: put the coin loop outside the amount loop so each multiset of coins is built in only one order.
  • Coin Change LC 322 — the fewest numbers instead of the number of sequences: min(dp[t], dp[t - x] + 1). With min the loop order no longer matters.
  • Combination Sum LC 39 — list the combinations instead of counting them: counting needs only a table, but listing needs backtracking, and the output itself can be exponentially large.
  • What if nums may contain negative numbers? — sequences such as +1, -1, +1, -1, ... can be as long as you like, so the count is infinite. Limit the length to L numbers and the state becomes (length, running sum), with sums ranging below 0 and above target.
