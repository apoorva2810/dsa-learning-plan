Evaluate Division Medium 250

LeetCode #399 ↗
Status

Given ratios like a / b = 2.0, answer queries c / d by chaining the known ratios, or -1.0 if impossible.

Problem

You get a list equations of variable-name pairs and a list values of the same length: equations[i] = [A, B] together with values[i] = v means A / B = v. Every value is positive and the equations never contradict each other.

You also get queries, where queries[j] = [C, D] asks for the value of C / D. Return one float per query, in order. If the ratio cannot be worked out from the equations (a variable never appears in any equation, or no chain of equations links the two), return -1.0 for that query.

A variable divided by itself is 1.0, but only if the variable appears in some equation; x / x for an unknown x is -1.0.

Examples

Example 1
Input: equations = [["a", "b"], ["b", "c"]], values = [2.0, 3.0], queries = [["a", "c"], ["b", "a"], ["a", "e"], ["a", "a"], ["x", "x"]]
Output: [6.0, 0.5, -1.0, 1.0, -1.0]
a / c = (a / b) · (b / c) = 2 · 3 = 6. b / a is the reverse of a / b, so 1 / 2. e and x appear in no equation, so anything involving them is -1.0, while a / a = 1.0.
Example 2
Input: equations = [["a", "b"], ["c", "d"], ["b", "c"]], values = [2.0, 2.0, 2.0], queries = [["a", "d"], ["d", "a"], ["b", "d"]]
Output: [8.0, 0.125, 4.0]
a = 2b, b = 2c and c = 2d, so a = 8d. The third equation joins two groups that were separate before it.
Example 3
Input: equations = [["a", "b"]], values = [0.5], queries = [["a", "b"], ["b", "a"], ["a", "c"], ["x", "y"]]
Output: [0.5, 2.0, -1.0, -1.0]
Only a and b are known. b / a is 1 / 0.5 = 2; c, x and y are unknown.

Constraints

  • 1 <= len(equations) <= 20, len(values) == len(equations)
  • 1 <= len(queries) <= 20
  • variable names are 1 to 5 lowercase letters or digits
  • 0.0 < values[i] <= 20.0, and the equations are consistent (no contradictions, no division by zero)

Think first try before reading the solution

a / b = 2 and b / c = 3 give a / c = 6: ratios chain by multiplying. Which structure lets you follow such chains from one variable to another?
Make each equation an edge a → b with weight a / b, plus the reverse edge b → a with weight b / a = 1 / v. Then c / d is the product of the weights along any path from c to d.
For many queries, store each variable's ratio to its group's root with a weighted union-find: c / d = (c / root) / (d / root) when c and d share a root, and -1.0 otherwise.

Key idea

Ratios multiply along a chain: (a / b) · (b / c) = a / c, because the bs cancel. So draw every equation a / b = v as an arrow a → b with weight v, and add the reverse arrow b → a with weight 1 / v. A query c / d is then the product of the weights along any path from c to d, and if there is no path (or a variable is not in the graph at all) the answer is -1.0. The equations are consistent, so every path gives the same product.

A depth-first search per query, carrying the running product, answers each query in O(V + E). With 20 equations that is plenty, and it is the version most interviewers expect first.

To answer many queries faster, use a weighted union-find: every variable points towards a root and remembers its ratio to its parent. find(x) returns the root and x / root (multiplying ratios on the way up, and compressing the path). Two variables share a root exactly when they are connected, and then c / d = (c / root) / (d / root). Each query becomes two near-constant find calls and one division.

Approaches from the obvious one to the one you want in an interview

Build a weighted graph: for a / b = v, store graph[a][b] = v and graph[b][a] = 1 / v. For a query c / d, run a DFS from c that carries the running product c / current. Stepping from node to nxt multiplies by node / nxt, so when the search reaches d the product is exactly c / d.

A seen set stops the search from looping. If c or d is not in the graph, or the search runs out of nodes without reaching d, the answer is -1.0. Each query costs one search, O(V + E); with at most 20 equations this is instant, and it is the version to reach for first.

Dry run

  1. Example 1: graph a → b (2), b → a (0.5), b → c (3), c → b (1/3)
  2. Query a / c: push (a, 1) → pop a, push (b, 1 × 2 = 2) → pop b, push (c, 2 × 3 = 6) → pop c: found, 6.0
  3. Query b / a: pop b, push (a, 0.5) and (c, 3) → pop c (nothing new) → pop a: found, 0.5
  4. a / e: e unknown → -1.0; a / a: start is the target → 1.0; x / x: unknown → -1.0

Python

class Solution:
    def calcEquation(self, equations: List[List[str]], values: List[float],
                     queries: List[List[str]]) -> List[float]:
        graph = defaultdict(dict)                    # graph[a][b] = a / b
        for (a, b), v in zip(equations, values):
            graph[a][b] = v
            graph[b][a] = 1 / v                      # the reverse edge

        def ratio(src: str, dst: str) -> float:      # src / dst, or -1.0
            if src not in graph or dst not in graph:
                return -1.0
            stack = [(src, 1.0)]                     # (variable, src / variable so far)
            seen = {src}
            while stack:
                node, product = stack.pop()
                if node == dst:
                    return product
                for nxt, weight in graph[node].items():   # weight = node / nxt
                    if nxt not in seen:
                        seen.add(nxt)
                        stack.append((nxt, product * weight))
            return -1.0                              # not connected

        return [ratio(c, d) for c, d in queries]
Time O(Q · (V + E))Space O(V + E)

One depth-first search per query over V variables and 2E directed edges.

When to use: The usual interview answer: short, and fast enough for a handful of queries.

Watch it run

Give each variable a parent pointer and a ratio = variable / parent. find(x) climbs to the root, multiplies the ratios on the way, and returns (root, x / root); while climbing it re-points x straight at the root with that full ratio (path compression), so later lookups are near-constant.

To add a / b = v: with a = ra · root_a and b = rb · root_b, hang root_a under root_b with ratio root_a / root_b = v · rb / ra. If the roots are already equal the equation is redundant. A query c / d is then two finds: same root gives (c / root) / (d / root), different roots give -1.0.

Processing is one pass over the equations plus two near-constant finds per query, O((E + Q) · α), instead of a full search per query. Also handy when equations and queries arrive mixed: no graph rebuild is needed.

Dry run

  1. Example 2: a / b = 2 → a under b, ratio 2. c / d = 2 → c under d, ratio 2
  2. b / c = 2: find(b) = (b, 1), find(c) = (d, 2). b = 2 · c = 2 · 2 · d, so b under d with ratio 2 × 2 / 1 = 4
  3. Query a / d: find(a) climbs a → b → d: 2 × 4 = 8; find(d) = 1. Answer 8 / 1 = 8.0
  4. Query d / a: 1 / 8 = 0.125. Query b / d: 4 / 1 = 4.0

Python

class Solution:
    def calcEquation(self, equations: List[List[str]], values: List[float],
                     queries: List[List[str]]) -> List[float]:
        parent: Dict[str, str] = {}
        ratio: Dict[str, float] = {}                 # ratio[x] = x / parent[x]

        def find(x: str) -> Tuple[str, float]:       # (root, x / root)
            if parent[x] == x:
                return x, 1.0
            root, parent_ratio = find(parent[x])    # parent[x] / root
            parent[x] = root                         # path compression
            ratio[x] *= parent_ratio                 # x / root = (x / parent) * (parent / root)
            return root, ratio[x]

        for (a, b), v in zip(equations, values):
            for var in (a, b):
                if var not in parent:
                    parent[var] = var
                    ratio[var] = 1.0
            root_a, ra = find(a)                     # a = ra * root_a
            root_b, rb = find(b)                     # b = rb * root_b
            if root_a != root_b:
                parent[root_a] = root_b
                ratio[root_a] = v * rb / ra          # root_a / root_b, since a = v * b

        answers = []
        for c, d in queries:
            if c not in parent or d not in parent:
                answers.append(-1.0)
                continue
            root_c, rc = find(c)
            root_d, rd = find(d)
            answers.append(rc / rd if root_c == root_d else -1.0)
        return answers
Time O((E + Q) · α(V))Space O(V)

One union per equation and two finds per query; α is the inverse Ackermann function, effectively constant.

When to use: Many queries, or equations and queries interleaved: no per-query search and no graph to rebuild.

Watch it run

Keep a table ratio[a][b] for every known pair, seeded with the equations, their reverses and x / x = 1. Then let each variable take a turn as the middle of a chain: whenever ratio[a][mid] and ratio[mid][b] are known and ratio[a][b] is not, set it to their product. After every variable has been the middle, the table holds the ratio of every connected pair, so each query is a dictionary lookup.

This is Floyd–Warshall with multiplication instead of addition and "known" instead of "shorter". O(V³) for V variables, trivial here, but it computes every pair even when only a few are asked about.

Dry run

  1. Example 1: table a/b = 2, b/a = 0.5, b/c = 3, c/b = 1/3, plus a/a = b/b = c/c = 1
  2. mid = b: a/b and b/c known, a/c not → a/c = 2 × 3 = 6; c/b and b/a → c/a = 1/6
  3. Queries: a/c = 6.0, b/a = 0.5, a/e → e not in the table → -1.0, a/a = 1.0, x/x → -1.0

Python

class Solution:
    def calcEquation(self, equations: List[List[str]], values: List[float],
                     queries: List[List[str]]) -> List[float]:
        ratio = defaultdict(dict)                    # ratio[a][b] = a / b when known
        for (a, b), v in zip(equations, values):
            ratio[a][b] = v
            ratio[b][a] = 1 / v
            ratio[a][a] = ratio[b][b] = 1.0
        variables = list(ratio)
        for mid in variables:                        # allow chains that pass through mid
            for a in variables:
                if mid in ratio[a]:
                    for b in variables:
                        if b in ratio[mid] and b not in ratio[a]:
                            ratio[a][b] = ratio[a][mid] * ratio[mid][b]
        return [ratio[c].get(d, -1.0) if c in ratio else -1.0 for c, d in queries]
Time O(V³ + Q)Space O(V²)

Three nested loops over the variables, then one lookup per query.

When to use: When nearly every pair will be asked about, or you want the full ratio table anyway.

Common mistakes

  • Forgetting the reverse edge. With only a → b stored, the query b / a finds no path and wrongly returns -1.0.
  • Returning 1.0 for x / x when x appears in no equation. The problem wants -1.0 for unknown variables, even divided by themselves (the last query of example 1).
  • Multiplying in the wrong direction. Walking from node to nxt multiplies by node / nxt; the stored weight of the edge you walk, not its reverse.
  • In the union-find, re-pointing a variable at the root during path compression without updating its ratio. x / root is (x / parent) · (parent / root): multiply when you shortcut.
  • Testing floats for equality (for example if product == 1.0). The input is guaranteed consistent, so you never need to compare computed ratios; return whatever the path or the roots give.

Python notes

  • defaultdict(dict) gives a weighted adjacency map in one line: graph[a][b] = v and graph[b][a] = 1 / v.
  • zip(equations, values) walks both lists together: for (a, b), v in zip(equations, values): unpacks the pair and its value at once.
  • Return -1.0, a float, not -1, so the answer list is uniformly floats.
  • Make find return a tuple (root, ratio) and unpack it: root_c, rc = find(c). The recursive find is fine here; at most 40 variables means a depth of at most 40.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Satisfiability of Equality Equations LC 990 — the same union-find without weights: union every a==b, then any a!=b whose letters share a root is a contradiction.
  • Redundant Connection LC 684 — plain union-find on numbered nodes; here the nodes are strings and each pointer carries a ratio.
  • Accounts Merge LC 721 — union-find again, but the grouping is the whole answer; nothing is multiplied along the way.
  • Network Delay Time LC 743 — also a weighted graph, but weights add instead of multiply and you need the shortest path, so any-path DFS is replaced by Dijkstra.
  • Path with Maximum Probability LC 1514 — weights multiply like here, but different paths give different products and you want the best one: Dijkstra with a max-heap.
  • What if the equations could contradict each other? — when union finds both variables already under one root, compare the implied ratio ra / rb with the given value (within a small tolerance) and report the contradiction.
