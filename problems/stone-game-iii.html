Stone Game III Hard 250

LeetCode #1406 ↗
Status

Two players take 1 to 3 piles from the front of a row and add up the values; decide who finishes ahead.

Problem

Alice and Bob play a game on a row of stone piles. stoneValue[i] is the value of the pile at position i, and a value may be negative.

They alternate turns, Alice first. On a turn the player must take 1, 2 or 3 piles from the front of what is left (passing is not allowed) and adds their values to their own score. The game ends when no piles remain.

Both players are perfect: each tries to finish with the higher score. Return "Alice" if Alice finishes ahead, "Bob" if Bob does, and "Tie" if the scores are equal.

Examples

Example 1
Input: stoneValue = [5, -3, 10, -4, 12]
Output: "Alice"
Alice takes only the 5. Bob takes -3 and 10 (7), then Alice takes -4 and 12 (8): 13 against 7. Taking three piles first (12) would leave Bob -4 and 12, a lead of only 4.
Example 2
Input: stoneValue = [2, 3, -1, 8]
Output: "Bob"
Alice's best is 2 and 3 (5); Bob then takes -1 and 8 (7). Any other first move lets Bob collect even more.
Example 3
Input: stoneValue = [4, -3, 2, 5]
Output: "Tie"
Alice takes 4. Bob takes -3, 2 and 5, which is also 4. Taking more first only helps Bob.

Constraints

  • 1 <= len(stoneValue) <= 5 * 10^4
  • -1000 <= stoneValue[i] <= 1000

Key idea

The game seems to need two scores and a note of whose turn it is. It does not. From any point the game is described by how many piles are already gone, and both players want the same thing from opposite sides: to end ahead.

So track one signed number, the lead of the player about to move: their score minus the other player's, counted over the piles that remain. Let dp[i] be that lead when piles i..n-1 remain and both play perfectly.

Suppose the mover takes the next k piles (1, 2 or 3), worth s in total. They gain s, and then the other player moves with piles i + k.. left, where that player leads by dp[i + k]. So after this move the first player's lead is s - dp[i + k]: what they took, minus the lead they just handed over. They pick the k that makes it largest:

dp[i] = max over k = 1, 2, 3 of (stoneValue[i] + ... + stoneValue[i + k - 1]) - dp[i + k], with dp[n] = 0.

One max is enough, with no separate min for the opponent, because dp[i + k] already assumes the opponent plays their best. A player must take at least one pile, so a cell can be negative: when the only pile left is worth -5, the mover has to take it, and dp[n - 1] = -5.

Each cell reads only the three cells to its right, so fill i = n - 1, n - 2, ..., 0. Alice moves first, so the answer is the sign of dp[0]: positive is Alice, negative is Bob, zero is a tie. That is three additions per cell, O(n) time, and since only three cells are ever read, three variables would be enough for O(1) space.

Approaches from the obvious one to the one you want in an interview

lead(i) = the best lead (score of the player to move minus the other player's) when piles i.. remain. The mover tries k = 1, 2, 3, takes those k piles for a total s, and the opponent then faces lead(i + k), so the mover's lead is s - lead(i + k). Take the best k; lead(n) = 0. Alice wins if lead(0) > 0.

It is correct, but lead(i + 1), lead(i + 2) and lead(i + 3) all ask for the same later positions, so the same subproblems are solved over and over. The number of calls grows by about 1.84 times for every extra pile: 600 calls for 10 piles, 266,079 for 20 and over 100 million for 30.

Dry run

  1. stoneValue = [4, -3, 2]: lead(0) = best of take 1 → 4 - lead(1), take 2 → 1 - lead(2), take 3 → 3 - lead(3)
  2. lead(3) = 0; lead(2) = 2 (the last pile is forced); lead(1) = best of -3 - 2 = -5 and -1 - 0 = -1 → -1
  3. lead(0) = best of 4 - (-1) = 5, 1 - 2 = -1, 3 - 0 = 3 → 5, so Alice wins by 5
  4. lead(2) was needed by both lead(0) (take 2) and lead(1) (take 1): the repeated work

Python

class Solution:
    def stoneGameIII(self, stoneValue: List[int]) -> str:
        n = len(stoneValue)

        def lead(i: int) -> int:
            """Best (mover's score - other player's score) when piles i.. remain, with perfect play."""
            if i == n:                                  # no piles left: nobody leads
                return 0
            best = float("-inf")
            taken = 0
            for k in range(1, 4):                       # take 1, 2 or 3 piles
                if i + k > n:
                    break
                taken += stoneValue[i + k - 1]          # value of the k piles just taken
                best = max(best, taken - lead(i + k))   # the opponent now leads by lead(i + k)
            return best

        result = lead(0)
        return "Alice" if result > 0 else "Bob" if result < 0 else "Tie"
Time O(3^n)Space O(n)

Three branches per call and a depth of up to n; the call count grows by about 1.84 per pile.

When to use: Only to discover the recurrence; it is fine for about 20 piles and hopeless for 50,000.

Wrap lead in @cache. There are only n + 1 different positions, and each does at most three additions, so the time drops to O(n). Every later call for the same i is a lookup.

The weakness is depth: lead(0) calls lead(1), which calls lead(2), and so on, so a row of 50,000 piles nests 50,000 calls, far beyond Python's default limit of 1000.

n + 1 states with at most three additions each; the cache and the call stack hold up to n entries.

When to use: Fine for short rows; for the full 5 × 10^4 piles switch to the loop.

dp[i] = the lead of the player to move when piles i.. remain, with dp[n] = 0. Fill i = n - 1 down to 0: the mover tries k = 1, 2, 3 (as long as i + k <= n), keeps a running sum taken of the piles they take, and the cell is the best of taken - dp[i + k].

Every cell reads only cells to its right, which are already final, so one right-to-left pass is enough and there is no recursion at all. The sign of dp[0] decides the winner. Only dp[i + 1..i + 3] are ever read, so three variables could replace the list.

Dry run

  1. stoneValue = [4, -3, 2]: dp = [?, ?, ?, 0]
  2. dp[2]: only one pile is left, so take 1: 2 - 0 = 2
  3. dp[1]: take 1: -3 - 2 = -5; take 2: -1 - 0 = -1 → dp[1] = -1
  4. dp[0]: take 1: 4 - (-1) = 5; take 2: 1 - 2 = -1; take 3: 3 - 0 = 3 → dp[0] = 5 > 0, so Alice

Python

class Solution:
    def stoneGameIII(self, stoneValue: List[int]) -> str:
        n = len(stoneValue)
        dp = [0] * (n + 1)                              # dp[i] = mover's lead when piles i.. remain; dp[n] = 0
        for i in range(n - 1, -1, -1):                  # right to left: dp[i + k] is already final
            best = float("-inf")
            taken = 0
            for k in range(1, 4):                       # take 1, 2 or 3 piles
                if i + k > n:
                    break
                taken += stoneValue[i + k - 1]          # value of the k piles just taken
                best = max(best, taken - dp[i + k])     # what I took, minus the lead I hand over
            dp[i] = best
        lead = dp[0]
        return "Alice" if lead > 0 else "Bob" if lead < 0 else "Tie"
Time O(n)Space O(n)

n cells, three additions each; one list of n + 1 integers (O(1) with three rolling variables).

When to use: The standard answer: linear time, no recursion limit, and the loop order follows from the dependencies.

Common mistakes

  • Greedy: take the group of piles with the best immediate sum. On [1, -1, 2, -1, 3] taking the first three piles (sum 2) lets Bob take the last two (also 2) for a tie, while taking only the first pile wins for Alice, 3 to 1.
  • Starting the maximum at 0, as if a player could pass. A player must take at least one pile, so [-5] is a win for Bob. Start each cell at minus infinity (or at the value of taking one pile).
  • Carrying two scores and a turn flag. The state is only the index; one signed lead removes the player from it. Memoising on (index, turn) also doubles the number of states for nothing.
  • Reading past the end of the row. With two piles left only k = 1 and k = 2 are legal, so stop the loop at i + k > n.
  • Top-down recursion on a row of 5 × 10^4 piles nests that many calls and exceeds Python's recursion limit of 1000. The loop from right to left has no depth.

Python notes

  • float("-inf") is smaller than every integer, so max(best, candidate) works from the first candidate on. After the first k the value is an ordinary int again.
  • A running taken += stoneValue[i + k - 1] gives the sum of the first k piles without slicing or sum() each time.
  • "Alice" if lead > 0 else "Bob" if lead < 0 else "Tie" is a chained conditional expression: read it left to right.
  • @cache goes on a function defined inside the method, so each call starts with an empty cache. The recursion is n deep, so it fails on the largest inputs; the loop does not.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Stone Game LC 877 — piles are taken from either end and the number of piles is even: a DP over intervals dp[l][r] = max(piles[l] - dp[l + 1][r], piles[r] - dp[l][r - 1]), though a parity argument shows Alice always wins.
  • Stone Game II LC 1140 — a player may take up to 2M piles from the front, where M grows with the biggest take: the state becomes (i, M), but each cell is still 'what I take minus the lead I hand over'.
  • Predict the Winner LC 486 — take one number from either end of the array: the same lead idea over a shrinking interval.
  • Stone Game IV LC 1510 — a move removes any perfect-square number of stones and the player who cannot move loses: the cell is now a win/lose boolean, dp[n] is true if some square leaves a losing position.
  • Use O(1) memory — keep dp[i + 1], dp[i + 2] and dp[i + 3] in three variables and shift them each step; the table is not needed once the loop is written.
  • What if a move may take up to K piles? — loop k from 1 to K with a running sum, or use prefix sums: O(n × K) time.
