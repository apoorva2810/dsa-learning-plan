Range Sum Query 2D - Immutable Medium 250

LeetCode #304 ↗
Status

Preprocess a fixed matrix so that the sum of any rectangle can be answered in O(1).

Problem

You are given a matrix of integers that never changes. Build a class that can answer many questions of the form "what is the sum of the values inside this rectangle?".

Implement the class NumMatrix:

  • NumMatrix(matrix) receives the matrix (a list of m rows with n integers each) and may preprocess it.
  • sumRegion(row1, col1, row2, col2) returns the sum of every matrix[r][c] with row1 <= r <= row2 and col1 <= c <= col2. (row1, col1) is the top-left cell of the rectangle and (row2, col2) the bottom-right one, both included.

There can be many thousands of sumRegion calls, so each one should be fast.

Output: [null, 11, 28, 10]
Rows 1..2 × columns 1..2 hold 6, 3, 2, 0 → 11. Rows 0..2 × columns 0..3 is the whole matrix → 28. Rows 0..1 × columns 2..3 hold 1, 4, 3, 2 → 10.
Example 2
Input: ["NumMatrix","sumRegion","sumRegion"] [[[[1,2,3]]],[0,1,0,2],[0,0,0,0]]
Output: [null, 5, 1]
A single row: columns 1..2 hold 2 + 3 = 5, and a one-cell rectangle is the cell itself.
Example 3
Input: ["NumMatrix","sumRegion","sumRegion","sumRegion"] [[[[3,0,1,4,2],[5,6,3,2,1],[1,2,0,1,5],[4,1,0,1,7],[1,0,3,0,5]]],[2,1,4,3],[1,1,2,2],[1,2,2,4]]
Output: [null, 8, 11, 12]
Rows 2..4 × columns 1..3: (2+0+1) + (1+0+1) + (0+3+0) = 8. Then 6+3+2+0 = 11, then (3+2+1) + (0+1+5) = 12.

Constraints

  • 1 <= m, n <= 200 (m rows, n columns)
  • -10^4 <= matrix[r][c] <= 10^4
  • 0 <= row1 <= row2 < m and 0 <= col1 <= col2 < n
  • at most 10^4 calls to sumRegion

Key idea

In one dimension, a prefix sum prefix[i] = sum of the first i values lets you answer the sum of any range as a subtraction: prefix[r + 1] - prefix[l]. Two totals, one subtraction, O(1).

The same idea works in two dimensions. Let P[r][c] be the sum of the whole rectangle whose top-left corner is (0, 0) and whose bottom-right corner is (r − 1, c − 1). Then a rectangle with corners (row1, col1) and (row2, col2) is the big prefix rectangle ending at (row2, col2), minus the strip of rows above row1, minus the strip of columns left of col1. Those two strips overlap in the block above-left of the rectangle, which was subtracted twice, so add it back once. This add-and-remove bookkeeping is called inclusion–exclusion. Four table lookups answer any query.

Building P is itself the same formula in miniature: P[r + 1][c + 1] = the cell itself + the prefix above + the prefix to the left − their overlap. The extra zero row and zero column mean no cell needs a special case.

Approaches from the obvious one to the one you want in an interview

Store the matrix. Each sumRegion loops over the rows row1..row2 and the columns col1..col2 and adds the cells.

Nothing is precomputed, so the constructor is free, but a query costs as many additions as the rectangle has cells, up to m · n. With 10,000 queries on a 200 × 200 matrix that is up to 400 million additions. The problem says the matrix is immutable precisely so that work can be done once, up front, and reused.

Python

class NumMatrix:
    def __init__(self, matrix: List[List[int]]):
        self.matrix = matrix               # nothing to prepare

    def sumRegion(self, row1: int, col1: int, row2: int, col2: int) -> int:
        total = 0
        for r in range(row1, row2 + 1):    # every row of the rectangle
            for c in range(col1, col2 + 1):
                total += self.matrix[r][c]
        return total
Time O(1) build, O(m · n) per querySpace O(1)

A query visits every cell of its rectangle; the biggest rectangle is the whole matrix.

When to use: Only when there are very few queries compared with the matrix size.

For every row build a one-dimensional prefix list: rows[r][c + 1] = sum of matrix[r][0..c]. The sum of columns col1..col2 in row r is then one subtraction, rows[r][col2 + 1] - rows[r][col1].

A query adds one such difference per row of the rectangle: O(m) instead of O(m · n). Good, but a tall rectangle still costs a loop. The 2-D table in the next approach removes that loop too.

Python

class NumMatrix:
    def __init__(self, matrix: List[List[int]]):
        self.rows = []
        for row in matrix:
            prefix = [0]                   # prefix[c + 1] = sum of row[0..c]
            for value in row:
                prefix.append(prefix[-1] + value)
            self.rows.append(prefix)

    def sumRegion(self, row1: int, col1: int, row2: int, col2: int) -> int:
        total = 0
        for r in range(row1, row2 + 1):    # one subtraction per row of the rectangle
            total += self.rows[r][col2 + 1] - self.rows[r][col1]
        return total
Time O(m · n) build, O(m) per querySpace O(m · n)

The build visits every cell once; a query does one subtraction per row it spans.

When to use: A natural stepping stone; fine when rectangles are short (few rows).

Build a table P with an extra zero row and column where P[r + 1][c + 1] is the sum of the rectangle matrix[0..r][0..c]. Each cell comes from its neighbours: the cell itself, plus the prefix above, plus the prefix to the left, minus the prefix above-left that both of those already contain.

A query is the same picture at a larger scale: take the big prefix rectangle ending at (row2, col2), subtract the strip above row1 and the strip left of col1, and add back the above-left block that was subtracted twice:

P[row2+1][col2+1] − P[row1][col2+1] − P[row2+1][col1] + P[row1][col1]

Four lookups, so every query is O(1) after an O(m · n) build.

Dry run

  1. matrix = [[3,0,1,4],[5,6,3,2],[1,2,0,1]]
  2. P = [[0,0,0,0,0],[0,3,3,4,8],[0,8,14,18,24],[0,9,17,21,28]]
  3. sumRegion(1, 1, 2, 2) = P[3][3] − P[1][3] − P[3][1] + P[1][1] = 21 − 4 − 9 + 3 = 11
  4. sumRegion(0, 0, 2, 3) = P[3][4] − P[0][4] − P[3][0] + P[0][0] = 28 − 0 − 0 + 0 = 28

Python

class NumMatrix:
    def __init__(self, matrix: List[List[int]]):
        m, n = len(matrix), len(matrix[0])
        # P[r + 1][c + 1] = sum of matrix[0..r][0..c]; row 0 and column 0 stay 0
        self.P = [[0] * (n + 1) for _ in range(m + 1)]
        for r in range(m):
            for c in range(n):
                self.P[r + 1][c + 1] = (matrix[r][c]
                                        + self.P[r][c + 1]       # rectangle above
                                        + self.P[r + 1][c]       # rectangle to the left
                                        - self.P[r][c])          # their overlap, counted twice

    def sumRegion(self, row1: int, col1: int, row2: int, col2: int) -> int:
        P = self.P
        return (P[row2 + 1][col2 + 1]      # everything up to the bottom-right corner
                - P[row1][col2 + 1]        # minus the strip above the rectangle
                - P[row2 + 1][col1]        # minus the strip to its left
                + P[row1][col1])           # the above-left block was removed twice
Time O(m · n) build, O(1) per querySpace O(m · n)

One pass over the matrix to fill (m + 1) × (n + 1) cells; a query reads exactly four of them.

When to use: The standard answer whenever the matrix does not change and there are many queries.

Common mistakes

  • Forgetting to add P[row1][col1] back: the block above-left of the rectangle sits in both strips you subtracted, so without the correction it is removed twice.
  • Off-by-one in the padded table: the bottom-right lookup is P[row2 + 1][col2 + 1], and the strips are P[row1][...] and P[...][col1] (not row1 - 1). Writing the four indices down against a drawing avoids this.
  • Building P without the zero row and column and special-casing r == 0 or c == 0: it works but doubles the number of branches to get wrong. The padding removes every if.
  • Creating the table with [[0] * (n + 1)] * (m + 1): that is one row object repeated, so writing to any row changes all of them. Use a list comprehension.
  • Re-scanning the rectangle on every call: with 10^4 queries on a 200 × 200 matrix that is up to 4 × 10^8 additions, far beyond the time limit, while the table costs 40,000 cells once.

Python notes

  • [[0] * (n + 1) for _ in range(m + 1)] builds m + 1 independent rows; [[0] * (n + 1)] * (m + 1) aliases a single row.
  • itertools.accumulate(row, initial=0) builds a one-dimensional prefix list in one line (Python 3.8+).
  • A design problem is tested by a sequence of calls: the first entry is the constructor, and its result is null.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Range Sum Query - Immutable LC 303 — the one-dimensional version: a single prefix list and prefix[r + 1] - prefix[l].
  • Range Sum Query - Mutable LC 307 — values can change: a prefix list would need O(n) to repair, so a Fenwick tree or segment tree gives O(log n) for both update and query.
  • Range Sum Query 2D - Mutable LC 308 — updates in two dimensions: a 2-D Fenwick tree, O(log m · log n) per operation.
  • Matrix Block Sum LC 1314 — one rectangle query per cell, each clamped to the matrix borders: build the same table once, then answer m · n queries in O(1) each.
  • Number of Submatrices That Sum to Target LC 1074 — fix a pair of rows, collapse the columns between them into one list of sums, then it is Subarray Sum Equals K with a hash map.
  • What if the matrix is huge but there are only a few queries? — building the table costs O(m · n); if there are fewer queries than that, scanning each rectangle directly can be cheaper. Preprocessing pays off only when it is reused.
