Coin Change II Medium

LeetCode #518 ↗
Status

Count the different combinations of coins that add up to an amount, when every coin type can be used as often as you like.

Problem

You are given an integer amount and a list coins of distinct coin values. You have an unlimited supply of every coin type.

Return the number of combinations of coins that add up to exactly amount. A combination ignores order: two combinations differ only if some coin value is used a different number of times, so 2 + 1 + 1 + 1 and 1 + 2 + 1 + 1 are the same combination.

  • If no combination makes amount, return 0.
  • The amount 0 can be made in exactly one way: use no coins.
  • The answer is guaranteed to fit in a signed 32-bit integer.

The method takes amount first and coins second (the reverse of Coin Change).

Examples

Example 1
Input: amount = 5, coins = [1, 2, 5]
Output: 4
The four combinations are 5, 2 + 2 + 1, 2 + 1 + 1 + 1 and 1 + 1 + 1 + 1 + 1.
Example 2
Input: amount = 3, coins = [2]
Output: 0
Coins of 2 can never make an odd amount.
Example 3
Input: amount = 10, coins = [10]
Output: 1
A single coin of 10.

Constraints

  • 1 <= len(coins) <= 300
  • 1 <= coins[i] <= 5000
  • all values in coins are different
  • 0 <= amount <= 5000
  • the answer fits in a signed 32-bit integer

Think first try before reading the solution

In Coin Change (fewest coins) 1 + 2 and 2 + 1 cost the same, so order never mattered. Here you count combinations, so each one must be counted exactly once. How can you build every sum so that its coins always appear in one fixed order?
Decide the coin types one at a time, in the order they appear in coins. For the current type you either use at least one more copy of it, or you stop using it for good and move on to the next type. Let ways(i, remaining) count the combinations that make remaining from coin types i onward.
As a table, dp[i][a] = combinations that make a using only the first i coin types, so dp[i][a] = dp[i - 1][a] + dp[i][a - coin]: never use the coin, or use at least one. Row i reads only row i - 1 and its own earlier cells, so a single list is enough when the loop over coins is the outer one.

Key idea

If the question were "how many sequences of coins add up to the amount", the natural recurrence would be ways(a) = sum of ways(a - c) over every coin c, and 1 + 2 and 2 + 1 would be counted separately. A combination has no order, so every combination has to be built in only one order.

The trick is to decide the coin types one at a time, in a fixed order: first how many copies of the first type (0, 1, 2, ...), then how many of the second, and so on. Every combination is exactly one list of copy counts, so nothing is counted twice. Let dp[i][a] be the number of combinations that make a using only the first i coin types, and let coin be the newest one. Split the combinations by that coin:

  • those that never use it: dp[i - 1][a];
  • those that use it at least once: take one copy away and a combination of a - coin remains. It is still a combination of the first i types, because it may contain more copies of the coin, so it is dp[i][a - coin].

So dp[i][a] = dp[i - 1][a] + dp[i][a - coin]. Base cases: dp[i][0] = 1 (the empty combination) and dp[0][a] = 0 for a > 0 (no coins, nothing can be paid).

Why the coin loop is the outer loop. Row i reads only row i - 1 and cells to its own left, so one list is enough: for coin in coins: for a in range(coin, amount + 1): dp[a] += dp[a - coin]. After the pass for the k-th coin, dp[a] means "combinations of a from the first k coin types", and each pass only adds the combinations that use the new coin at least once. Every combination is therefore added exactly once, during the pass of the last coin type (in coins order) that it uses. If the loops were swapped (amount outside, coins inside), each amount would add dp[a - c] for every coin c as the last coin of a sequence, so dp[a] would count ordered sequences: amount 3 with coins [1, 2] would give 3 (1+1+1, 1+2, 2+1) instead of 2.

Why the amount loop goes upward. The coin has an unlimited supply, so dp[a - coin] must already include this coin's pass. Scanning a from small to large guarantees that. Target Sum and Partition Equal Subset Sum, where each number is used once, scan downward instead.

Approaches from the obvious one to the one you want in an interview

Decide the coin types in a fixed order. Let ways(i, remaining) be the number of combinations that make remaining using only the coin types i, i + 1, .... Look at coin type i:

  • use it: pay one copy, leaving remaining - coins[i], and stay on type i because more copies are allowed: ways(i, remaining - coins[i]);
  • never use it: move on to type i + 1 for good: ways(i + 1, remaining).

The two cases do not overlap and together cover every combination, so the answer is their sum. remaining == 0 is one way (the empty combination); remaining < 0 or no coin types left is zero ways. Because the recursion never goes back to an earlier coin type, 2 + 1 and 1 + 2 cannot be two different branches: each combination is generated once.

Without a cache the same (i, remaining) pairs are recomputed along many branches (exponential time). With @cache there are only n × (amount + 1) different calls, each doing O(1) work.

Dry run

  1. amount = 3, coins = [1, 2]: ways(0, 3) = ways(0, 2) (use a 1) + ways(1, 3) (never use 1)
  2. ways(1, 3): only coin 2 is left; 3 is odd, so it is 0
  3. ways(0, 2) = ways(0, 1) + ways(1, 2); ways(1, 2) = ways(1, 0) + ways(2, 2) = 1 + 0 = 1 (the single coin 2)
  4. ways(0, 1) = ways(0, 0) + ways(1, 1) = 1 + 0 = 1 (the single coin 1)
  5. ways(0, 2) = 1 + 1 = 2, so ways(0, 3) = 2 + 0 = 2: 1 + 1 + 1 and 1 + 2

Python

class Solution:
    def change(self, amount: int, coins: List[int]) -> int:
        n = len(coins)

        @cache                                          # one stored answer per (i, remaining)
        def ways(i: int, remaining: int) -> int:
            """Combinations that make `remaining` using only coins[i:]."""
            if remaining == 0:                          # paid exactly: the empty combination
                return 1
            if remaining < 0 or i == n:                 # overpaid, or no coin types left
                return 0
            return (ways(i, remaining - coins[i])       # use coin i (more copies stay allowed)
                    + ways(i + 1, remaining))           # never use coin i from now on

        return ways(0, amount)
Time O(n · amount)Space O(n · amount)

n × (amount + 1) states, O(1) work each. The call stack can be amount / min(coins) frames deep.

When to use: The natural first version. With a coin of 1 and an amount in the thousands it is too deep for Python's default recursion limit, so switch to the table.

Store the answers of the recursion in a table. dp[i][a] = number of combinations that make a using only the first i coin types (coins[:i]). Column 0 is 1 in every row (the empty combination); row 0 has no coin types, so every positive amount is 0.

Every other cell splits on the newest coin c = coins[i - 1]:

dp[i][a] = dp[i - 1][a] + dp[i][a - c]

  • dp[i - 1][a] (the cell above): combinations that never use c;
  • dp[i][a - c] (the cell c places to the left, in the same row): combinations that use c at least once. Remove one copy and a combination of a - c remains, which may still contain c, so the row does not change. The term is 0 when c > a.

Fill the rows from top to bottom. The rows are the outer dimension, so the coin types are introduced one at a time, which is what makes this count combinations instead of orderings. The answer is the bottom-right cell dp[n][amount].

Dry run

  1. amount = 5, coins = [1, 2, 5]; row ∅ = [1, 0, 0, 0, 0, 0]
  2. row {1} = [1, 1, 1, 1, 1, 1]: with only 1s, every amount has exactly one combination
  3. row {1,2} = [1, 1, 2, 2, 3, 3]: e.g. dp[2][4] = dp[1][4] + dp[2][2] = 1 + 2 = 3
  4. row {1,2,5} = [1, 1, 2, 2, 3, 4]: only dp[3][5] changes, by dp[3][0] = 1 (the single coin 5) → answer 4

Python

class Solution:
    def change(self, amount: int, coins: List[int]) -> int:
        n = len(coins)
        # dp[i][a] = combinations that make a using only coins[:i]
        dp = [[0] * (amount + 1) for _ in range(n + 1)]
        for i in range(n + 1):
            dp[i][0] = 1                                # pay nothing: the empty combination
        for i in range(1, n + 1):
            coin = coins[i - 1]                         # the newest coin type in this row
            for a in range(1, amount + 1):
                dp[i][a] = dp[i - 1][a]                 # never use this coin type
                if a >= coin:
                    dp[i][a] += dp[i][a - coin]         # use at least one: same row, the coin stays available
        return dp[n][amount]
Time O(n · amount)Space O(n · amount)

One O(1) update for each of the (n + 1) × (amount + 1) cells. No recursion.

When to use: When you want to see (or debug) the whole table; it is the stepping stone to the one-list version.

Watch it run

Row i of the table reads only row i - 1 (the same column) and cells to its own left. So one list dp can play every row in turn: before the pass for a coin, dp[a] is the cell above; during the pass, dp[a - coin] has already been updated, which is exactly the cell to the left in the same row.

dp = [1, 0, 0, ..., 0]
for coin in coins:                       # outer: one table row per coin type
    for a in range(coin, amount + 1):    # upward: dp[a - coin] already includes this coin
        dp[a] += dp[a - coin]

Why the coin loop is outside. After the pass for the k-th coin, dp[a] counts combinations of a from the first k coin types. The pass only adds the combinations that use the new coin at least once, so each combination is added once, during the pass of the last coin type it uses. With the loops swapped, every amount sums dp[a - c] over all coins c as the last coin, which counts ordered sequences (that is Combination Sum IV).

Why the amount loop goes upward. The supply is unlimited, so the cell to the left must already contain this coin.

Dry run

  1. amount = 5, coins = [1, 2, 5], dp = [1, 0, 0, 0, 0, 0]
  2. coin 1: dp[a] += dp[a - 1] for a = 1..5 → [1, 1, 1, 1, 1, 1]
  3. coin 2: dp[2] += dp[0] → 2, dp[3] += dp[1] → 2, dp[4] += dp[2] → 3, dp[5] += dp[3] → 3 → [1, 1, 2, 2, 3, 3]
  4. coin 5: dp[5] += dp[0] → 4 → [1, 1, 2, 2, 3, 4]; the answer is dp[5] = 4
  5. Swapping the loops would give 9 for this input: it counts ordered sequences such as 2 + 2 + 1 and 1 + 2 + 2

Python

class Solution:
    def change(self, amount: int, coins: List[int]) -> int:
        dp = [1] + [0] * amount                 # dp[a] = combinations of a from the coin types handled so far
        for coin in coins:                      # OUTER loop: add one coin type at a time
            for a in range(coin, amount + 1):   # UPWARD: dp[a - coin] already counts uses of this coin
                dp[a] += dp[a - coin]
        return dp[amount]
Time O(n · amount)Space O(amount)

n passes over at most amount cells; a single list of amount + 1 integers.

When to use: The interview answer: four lines, and the loop order is easy to justify with the table.

Common mistakes

  • Swapping the loops (amounts outside, coins inside) counts ordered sequences, not combinations: amount = 3, coins = [1, 2] returns 3 instead of 2, and example 1 returns 9 instead of 4. Keep the coin loop outside.
  • Running the amount loop downward, as in a 0/1 knapsack, lets each coin type be used at most once. Example 1 would return 1 (only 5). Unlimited coins need the upward direction.
  • Forgetting the base case dp[0] = 1. If every cell starts at 0, nothing ever adds the first 1 and the answer is always 0, even for amount = 10, coins = [10].
  • Top-down recursion with a coin of 1 and amount = 5000 is 5000 calls deep, far past Python's default recursion limit of 1000 (RecursionError). The loops have no depth at all.
  • Reading dp[a - coin] without making sure coin <= a: a negative index silently reads from the end of the list. Starting the inner loop at range(coin, amount + 1) removes the need for a check.

Python notes

  • dp = [1] + [0] * amount builds the whole list: index 0 is the base case (one way to pay nothing), the rest start at zero ways.
  • for a in range(coin, amount + 1) starts at coin, so a - coin is never negative and no if is needed. A coin larger than amount gives an empty range and is skipped for free.
  • The order of coins does not change the answer: [5, 2, 1] and [1, 2, 5] both give 4 for amount 5.
  • @cache keys on the pair (i, remaining). Define the cached function inside the method so every test starts with an empty cache. The recursion is amount / min(coins) frames deep, which is why the loops win for large amounts.
  • Python integers never overflow, so no % MOD is needed. In a language with 32-bit integers it is the guarantee in the statement that keeps the sums safe.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Coin Change LC 322 — fewest coins instead of the number of combinations: dp[a] = min(dp[a], dp[a - c] + 1). Loop order no longer matters, because min does not care in which order the options are seen.
  • Combination Sum IV LC 377 — count ordered sequences, so 1 + 2 and 2 + 1 differ: the same dp[a] += dp[a - c], but with the amount loop outside and the coin loop inside.
  • Combination Sum LC 39 — list the combinations instead of counting them: backtracking with a start index, which is the same 'fixed coin order' idea that prevents duplicates.
  • Target Sum LC 494 — every number is used exactly once with a plus or minus sign: a counting 0/1 knapsack whose inner loop runs downward.
  • Partition Equal Subset Sum LC 416 — yes/no instead of counting, and each number at most once: booleans in the same 1-D table, scanned from high to low.
  • Each coin type has a limited supply — bounded knapsack: if coin c has k copies, dp_new[a] is the sum of dp_old[a - j * c] for j = 0..k, which a sliding sum computes in O(1) per cell.
