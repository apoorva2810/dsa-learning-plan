Combination Sum Medium

LeetCode #39 ↗
Status

Find every combination of the given numbers, each usable any number of times, that adds up to a target.

Problem

You are given a list candidates of distinct positive integers and a positive integer target. Return every unique combination of candidates whose sum is exactly target.

  • The same candidate may be used any number of times in a combination.
  • Two combinations are different if some candidate is used a different number of times. [2, 3] and [3, 2] are the same combination.
  • The combinations can be returned in any order. If there are none, return an empty list.

Examples

Example 1
Input: candidates = [2, 3, 6, 7], target = 7
Output: [[2, 2, 3], [7]]
2 + 2 + 3 = 7 uses the candidate 2 twice, which is allowed. 7 on its own also works.
Example 2
Input: candidates = [2, 3, 5], target = 8
Output: [[2, 2, 2, 2], [2, 3, 3], [3, 5]]
Example 3
Input: candidates = [2], target = 1
Output: []
The only candidate is bigger than the target.

Constraints

  • 1 <= len(candidates) <= 30
  • 2 <= candidates[i] <= 40, all distinct
  • 1 <= target <= 40
  • fewer than 150 combinations reach the target

Think first try before reading the solution

Build a combination one number at a time. After choosing some numbers, what do you still need to reach target? Keep track of that remaining amount.
[2, 3] and [3, 2] must not both appear. If a combination may only grow in the order the candidates are listed (never going back to an earlier candidate), every combination is built in exactly one way. How can an index tell the recursion where it is allowed to continue from?
Loop over the candidates from a start index. After choosing candidates[i], recurse with the same i (the number may repeat) and the smaller remainder. A remainder of 0 means record the path. Sort the candidates and you can stop the loop as soon as one candidate is bigger than the remainder.

Key idea

Think of paying an exact amount with coins you may use as often as you like. Choose a coin, pay it, and ask the same question about the smaller amount that is left. A remainder of 0 means you have an answer; a candidate larger than the remainder cannot be chosen.

Two ideas make the search both correct and quick:

  • Fix the order. If every combination is built in the order the candidates are listed, each one is built exactly once. A start index enforces that: a call may only choose candidates at or after start. After choosing candidates[i] the next call gets start = i, not i + 1, because the same number may be used again.
  • Prune. Sort the candidates. If candidates[i] is larger than what remains, every later candidate is larger still, so one break discards the rest of the loop together with every branch below it.

Every choice lowers the remainder by at least the smallest candidate, so the recursion is at most target / smallest calls deep.

Approaches from the obvious one to the one you want in an interview

The most direct idea: keep adding any candidate to the path until the remainder reaches 0 (record it) or a candidate no longer fits (skip it). Because any candidate may come at any position, each combination is found once for every order of its numbers: [2, 2, 3], [2, 3, 2] and [3, 2, 2] are all built. Sorting every finished sequence and storing it in a set collapses them into one.

It is correct, but it repeats work. A combination of k numbers is built up to k! times (fewer when numbers repeat), and the search tree has up to n^(target/smallest) leaves. The next approach removes the repeats at the source, instead of cleaning them up afterwards.

Dry run

  1. candidates = [2, 3, 6, 7], target = 7.
  2. Sequences that reach 7: [2, 2, 3], [2, 3, 2], [3, 2, 2] and [7].
  3. Sort each one and add it to a set: {(2, 2, 3), (7,)}.
  4. Three of the four finished sequences were the same combination in different orders.

Python

class Solution:
    def combinationSum(self, candidates: List[int], target: int) -> List[List[int]]:
        found = set()                            # sorted tuples: [2, 3] and [3, 2] become one entry
        path = []

        def build(remaining: int) -> None:
            if remaining == 0:                   # exact: remember this sequence in sorted form
                found.add(tuple(sorted(path)))
                return
            for c in candidates:                 # ANY candidate may come next, so orders repeat
                if c <= remaining:               # one that is too big can never help
                    path.append(c)
                    build(remaining - c)
                    path.pop()

        build(target)
        return [list(combo) for combo in found]
Time O(n^(t/m))Space O(t/m)

n candidates, target t, smallest candidate m: a path has at most t/m numbers and each step has up to n choices. The recursion is t/m deep; the set of answers is not counted.

When to use: As the starting point. It shows exactly what the start index is for.

Sort the candidates and let each call choose from a start index onwards. backtrack(start, remaining):

  • if remaining == 0, path adds up to the target: record a copy;
  • otherwise loop i from start. If candidates[i] > remaining, break: it is sorted, so every later candidate is also too big. Else append candidates[i], recurse with backtrack(i, remaining - candidates[i]), then pop it.

Recursing with i (not i + 1) allows reuse; never looking at an index below start means each combination is built in just one order. The break cuts off whole branches that could never reach the target, which is the pruning the brute force lacks. The worst case is still exponential, but only the branches that fit under the target are visited.

Dry run

  1. candidates = [2, 3, 6, 7], target = 7. bt(0, 7): choose 2 → bt(0, 5) → choose 2 → bt(0, 3) → choose 2 → bt(0, 1): 2 > 1, break.
  2. Back in bt(0, 3): choose 3 → bt(1, 0): remainder 0 → record [2, 2, 3]. Then 6 > 3: break.
  3. Back in bt(0, 5): choose 3 → bt(1, 2): 3 > 2, break. Then 6 > 5: break.
  4. Back at the root: choose 3 → bt(1, 4) (a 3 leaves 1, dead end; 6 > 4, break). Choose 6 → bt(2, 1): 6 > 1, break.
  5. Choose 7 → bt(3, 0): record [7]. Result: [[2, 2, 3], [7]].

Python

class Solution:
    def combinationSum(self, candidates: List[int], target: int) -> List[List[int]]:
        candidates = sorted(candidates)          # sorted, so one too-big candidate rules out all later ones
        result = []
        path = []

        def backtrack(start: int, remaining: int) -> None:
            if remaining == 0:                   # the path adds up to the target
                result.append(path[:])
                return
            for i in range(start, len(candidates)):
                if candidates[i] > remaining:    # this and every later candidate is too big: prune
                    break
                path.append(candidates[i])                       # choose
                backtrack(i, remaining - candidates[i])          # explore; i (not i + 1) allows reuse
                path.pop()                                       # un-choose

        backtrack(0, target)
        return result
Time O(n^(t/m))Space O(t/m)

Same worst-case bound as the brute force, but each combination is built once and branches that exceed the target are cut at the first too-big candidate. The recursion is at most t/m deep.

When to use: The standard answer. Say why start removes duplicates and why break is safe after sorting.

Watch it run

Build the answers for small sums first and reuse them. Let ways[s] be the list of all combinations that add up to s. There is exactly one way to reach 0 (take nothing), so ways[0] = [[]]. For each candidate c and each sum s from c up to target, every combination in ways[s - c] extended with c is a combination for s.

Two details carry the idea. Going through s in increasing order means ways[s - c] may already contain combinations that use c, which is how c gets reused. And putting the candidates in the outer loop builds every combination in the order of the candidate list, exactly once: the start index again, in table form. Swapping the loops would count [2, 3] and [3, 2] separately.

There is no recursion, but the table keeps combinations for every sum up to the target, including sums that never reach it, so it uses more memory and cannot prune. With counts in the cells instead of lists it is the Coin Change II solution.

Python

class Solution:
    def combinationSum(self, candidates: List[int], target: int) -> List[List[int]]:
        ways = [[] for _ in range(target + 1)]   # ways[s]: all combinations that add up to s
        ways[0] = [[]]                           # one way to make 0: take nothing
        for c in candidates:                     # candidates outside: each combination built in one order
            for s in range(c, target + 1):       # increasing s lets c be used again
                for combo in ways[s - c]:
                    ways[s].append(combo + [c])
        return ways[target]
Time O(n · t · S)Space O(t · S)

S is the largest number of combinations stored for one sum (each up to t/m long, which the formula leaves out). S can grow exponentially with t, like the answer itself.

When to use: When you also need counts, or want to see the link to Coin Change II. For listing answers, backtracking is simpler and prunes.

Common mistakes

  • Recursing with i + 1 instead of i. That forbids reuse, so [2, 2, 3] is never found. (i + 1 is the right choice in Combination Sum II, where each number may be used once.)
  • Restarting the loop at index 0 in every call. The same combination is then built in every order ([2, 2, 3], [2, 3, 2], [3, 2, 2]) and the answer fills with duplicates.
  • Checking the remainder only after recursing. Because numbers can repeat, 2 → 2 → 2 → … never ends unless a candidate larger than the remainder is rejected before the recursive call.
  • Using break on unsorted candidates. break is only valid because sorting guarantees that every later candidate is at least as large; on unsorted input use continue, or you will drop valid answers.
  • Storing path itself instead of a copy (path[:]): every stored combination ends up empty.

Python notes

  • sorted(candidates) returns a new list. candidates.sort() would reorder the caller's list in place, a side effect most callers do not expect.
  • for i in range(start, len(candidates)) lets the loop variable double as the next start.
  • remaining is passed as an argument (remaining - candidates[i]) instead of being changed in place, so there is nothing to undo for it. Only path is shared between calls, so only path needs pop().
  • In the table version combo + [c] builds a new list each time, so stored combinations never share structure.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Combination Sum II LC 40 — each number may be used once and the input can contain duplicates: recurse with i + 1, and skip a candidate equal to the previous one at the same depth.
  • Combination Sum III LC 216 — choose exactly k different digits from 1 to 9 that add up to n: the same skeleton with a second stop condition on the length of path.
  • Combination Sum IV LC 377 — count the ordered sequences (so [1, 2] and [2, 1] count twice): you only need a number, so a DP over the remaining amount replaces the search.
  • Coin Change II LC 518 — count the combinations instead of listing them: the table approach here with a number in each cell instead of a list of lists, candidates in the outer loop.
  • Coin Change LC 322 — the fewest numbers that reach the target, repeats allowed: the same unbounded choice, but a minimum instead of a list, so DP replaces backtracking.
  • What if candidates could be zero or negative? — there would be infinitely many combinations (add a 0 as often as you like, or +3 and −3), and the recursion would not terminate. Positive candidates are what guarantee the remainder keeps shrinking.
