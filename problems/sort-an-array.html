Sort an Array Medium 250

LeetCode #912 ↗
Status

Sort a list of integers from smallest to largest without the library sort, in O(n log n) time.

Problem

You are given a list of integers nums. Return the same numbers arranged in ascending order (smallest first).

  • Write the sorting yourself: the built-in sorted() and list.sort() are not allowed.
  • The list can be long, so aim for O(n log n) time. Quadratic methods such as insertion sort or bubble sort are too slow.
  • Use as little extra memory as you reasonably can.
  • Values may repeat and may be negative.

Examples

Example 1
Input: nums = [6, 2, 9, 4, 1, 7]
Output: [1, 2, 4, 6, 7, 9]
Six distinct numbers, placed in increasing order.
Example 2
Input: nums = [3, -1, 3, 0, -4]
Output: [-4, -1, 0, 3, 3]
Negative numbers come before zero, and the two 3s end up next to each other.
Example 3
Input: nums = [5, 4, 3, 2, 1]
Output: [1, 2, 3, 4, 5]
A list in reverse order is the worst case for insertion sort.

Constraints

  • 1 <= len(nums) <= 5 * 10^4
  • -5 * 10^4 <= nums[i] <= 5 * 10^4
  • no built-in sort; target O(n log n) time

Think first try before reading the solution

Insertion, bubble and selection sort all take about n² steps. For 50,000 numbers that is over a billion. You need a method that does roughly n × log n steps instead.
Merging two lists that are already sorted is easy: look at the front of each, take the smaller one, repeat. How many steps does that take for n values in total?
Cut the list in half, sort each half with the same method, then merge the two sorted halves. A list of 0 or 1 values is sorted already, so the recursion has somewhere to stop.

Key idea

Sorting a jumble from scratch is hard, but merging two sorted lists is easy: the smallest value overall is one of the two fronts, so you compare the fronts, take the smaller, and repeat. Every value is looked at once, so a merge of n values costs O(n).

That suggests divide and conquer (split a problem into smaller copies of itself, solve those, combine the answers): cut the list in half, sort each half the same way, and merge. One value on its own is already sorted, so the recursion bottoms out there. This is merge sort.

Count the work. Halving n until only 1 is left takes about log2(n) levels, and the merges on any one level add up to n values. So the total is n steps per level × log2(n) levels = O(n log n). For 50,000 numbers that is roughly 50,000 × 16 = 800,000 steps instead of over a billion.

Approaches from the obvious one to the one you want in an interview

Keep the left part of the list sorted. Take the next value (the key), slide every bigger value in the sorted part one cell to the right, and drop the key into the gap. It is how most people sort a hand of playing cards.

It is correct, simple, and sorts in place, but a value may have to slide past every value before it. In the worst case (a list in reverse order) value number i moves i cells, so the total is 1 + 2 + ... + (n - 1) = n(n - 1) / 2 moves. For 50,000 numbers that is about 1.25 billion moves, far too slow.

Dry run

  1. nums = [6, 2, 9, 4, 1, 7]; the prefix [6] counts as sorted
  2. key 2: 6 is bigger and shifts right, 2 drops into index 0 → [2, 6, 9, 4, 1, 7]
  3. key 9: 6 is not bigger, nothing moves
  4. key 4: 9 and 6 shift right → [2, 4, 6, 9, 1, 7]
  5. key 1: 9, 6, 4 and 2 all shift right → [1, 2, 4, 6, 9, 7]
  6. key 7: only 9 shifts → [1, 2, 4, 6, 7, 9] (8 shifts in total)

Python

class Solution:
    def sortArray(self, nums: List[int]) -> List[int]:
        for i in range(1, len(nums)):
            key = nums[i]                      # next value to insert into the sorted prefix nums[0..i-1]
            j = i - 1
            while j >= 0 and nums[j] > key:    # shift every bigger value one cell to the right
                nums[j + 1] = nums[j]
                j -= 1
            nums[j + 1] = key                  # drop the key into the gap
        return nums
Time O(n²)Space O(1)

A value may slide past every value before it: n(n-1)/2 shifts in the worst case. Only a few variables are extra.

When to use: Tiny lists, or lists that are already almost sorted (then it costs close to O(n)).

Watch it run

Use divide and conquer: split the problem into smaller copies of itself, solve those, and combine the answers.

  1. Split. Cut the range in half. A range of 0 or 1 cells is already sorted, so the recursion stops there.
  2. Sort both halves with the same method.
  3. Merge. Both halves are sorted now, so the smallest value of the range is one of the two fronts. Compare the fronts, move the smaller one into a scratch list, advance that side, and repeat. When one half is empty, the rest of the other half is already in order, so copy it over. Finally copy the scratch list back into the range.

A merge looks at each cell once, so it costs O(length of the range). The recursion halves the range, so it has about log2(n) levels, and the merges on one level add up to n cells. That is n × log2(n) in total, and it holds for every input, sorted or not.

The scratch list (buffer) is created once and shared by all merges, so the extra memory is O(n) plus the O(log n) recursion stack. The sort is stable: on a tie the left value goes first.

Dry run

  1. nums = [6, 2, 9, 4, 1, 7] → split into [6, 2, 9] and [4, 1, 7]
  2. [6, 2, 9] → split into [6, 2] and [9]; [6, 2] → split into [6] and [2]
  3. merge [6] and [2] → [2, 6]; merge [2, 6] and [9] → [2, 6, 9]
  4. [4, 1, 7] → the same way: [4] and [1] merge into [1, 4], then with [7] into [1, 4, 7]
  5. merge [2, 6, 9] and [1, 4, 7]: 1, 2, 4, 6, 7 are taken in turn, then the leftover 9 → [1, 2, 4, 6, 7, 9]

Python

class Solution:
    def sortArray(self, nums: List[int]) -> List[int]:
        buffer = [0] * len(nums)               # scratch space shared by every merge

        def merge_sort(lo: int, hi: int) -> None:   # sorts nums[lo..hi], both ends included
            if lo >= hi:                       # 0 or 1 cell: already sorted
                return
            mid = (lo + hi) // 2
            merge_sort(lo, mid)                # sort the left half
            merge_sort(mid + 1, hi)            # sort the right half
            i, j, k = lo, mid + 1, lo          # fronts of the two halves, next free buffer slot
            while i <= mid and j <= hi:
                if nums[i] <= nums[j]:         # on a tie take the left value: equal values keep their order
                    buffer[k] = nums[i]
                    i += 1
                else:
                    buffer[k] = nums[j]
                    j += 1
                k += 1
            while i <= mid:                    # right half used up: copy the rest of the left half
                buffer[k] = nums[i]
                i += 1
                k += 1
            while j <= hi:                     # left half used up: copy the rest of the right half
                buffer[k] = nums[j]
                j += 1
                k += 1
            nums[lo:hi + 1] = buffer[lo:hi + 1]    # write the merged run back

        merge_sort(0, len(nums) - 1)
        return nums
Time O(n log n)Space O(n)

About log2(n) levels, each merging n cells in total. The buffer holds n values; the recursion adds O(log n) frames.

When to use: The standard interview answer: the O(n log n) bound holds for every input and the sort is stable. Quicksort is as fast on average but has a quadratic worst case.

Watch it run

Use the list itself as a max-heap: a binary tree stored in the array, where the children of index i sit at 2i + 1 and 2i + 2, and every parent is at least as big as its children. The biggest value then sits at index 0.

  1. Build the heap. From the last parent back to index 0, sift down each value: swap it with its larger child until it is no smaller than both of its children.
  2. Sort. Swap the root (the biggest value) with the last cell of the heap, shrink the heap by one cell, and sift the new root down. The finished tail grows from the right.

Each sift-down follows one path from a node toward a leaf, O(log n), and there are O(n) of them, so the time is O(n log n). Nothing is copied: the extra memory is a few variables, so the space is O(1). The price is that equal values can change their relative order (the sort is not stable).

Python

class Solution:
    def sortArray(self, nums: List[int]) -> List[int]:
        n = len(nums)

        def sift_down(root: int, size: int) -> None:   # restore the heap rule below `root`, inside nums[0..size-1]
            while True:
                child = 2 * root + 1                   # left child
                if child >= size:                      # no children: done
                    return
                if child + 1 < size and nums[child + 1] > nums[child]:
                    child += 1                         # the right child is larger
                if nums[root] >= nums[child]:          # heap rule holds
                    return
                nums[root], nums[child] = nums[child], nums[root]
                root = child

        for start in range(n // 2 - 1, -1, -1):        # 1. build a max-heap, last parent first
            sift_down(start, n)
        for end in range(n - 1, 0, -1):                # 2. move the biggest value to the end, shrink the heap
            nums[0], nums[end] = nums[end], nums[0]
            sift_down(0, end)
        return nums
Time O(n log n)Space O(1)

O(n) sift-downs, each at most O(log n); the list is rearranged in place with no buffer.

When to use: When memory is tight and a stable order does not matter.

Common mistakes

  • Choosing a quadratic algorithm (insertion, bubble or selection sort). It is correct, but at 50,000 values the worst case is about 1.25 billion steps, which is too slow.
  • Quicksort with a fixed pivot (always the first or last value) degrades to O(n²) on a list that is already sorted or holds many equal values. If you pick quicksort, choose the pivot at random and handle equal values explicitly.
  • Forgetting the leftovers in the merge: when one half runs out, the rest of the other half must still be copied. Without it, values silently disappear.
  • Taking from the right half on a tie (< instead of <=). For plain integers the result is the same, but equal records swap places, so the sort is no longer stable (stable = equal values keep their input order).
  • A recursive call whose range does not get smaller never ends. Stop when the range has 0 or 1 cells (lo >= hi) and make sure both halves are strictly shorter than the whole.

Python notes

  • Python's own sorted() and list.sort() use Timsort, a hybrid of merge sort and insertion sort. Use them in real code; this exercise asks you to build the idea yourself.
  • nums[lo:hi + 1] = buffer[lo:hi + 1] is a slice assignment: it overwrites that range of nums in place with the values on the right, so the caller's list is the one that changes.
  • (lo + hi) // 2 is integer division. Python integers never overflow, so unlike Java or C++ there is no need for lo + (hi - lo) // 2.
  • The merge sort recursion is only about log2(n) frames deep (around 16 for 50,000 values), far below Python's default recursion limit.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Sort Colors LC 75 — only three possible values: counting, or a one-pass three-way partition, sorts in O(n) with no comparisons at all.
  • Merge Two Sorted Lists LC 21 — the merge step on its own, done on linked lists: you re-link nodes instead of copying into a buffer.
  • Sort List LC 148 — merge sort on a linked list: find the middle with slow and fast pointers instead of indexing, and the merge needs no scratch buffer.
  • Kth Largest Element in an Array LC 215 — you do not need the whole list sorted: a heap or quickselect finds the k-th value with less work.
  • Count of Smaller Numbers After Self LC 315 — merge sort that counts while it merges: each right-half value taken before a left-half value is one smaller value that started to its right.
  • What if the list is already almost sorted? — insertion sort costs about n plus the number of out-of-order pairs, so it can beat merge sort when each value is close to its final place.
