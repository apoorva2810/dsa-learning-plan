Path with Minimum Effort Medium 250

LeetCode #1631 ↗
Status

Hike from the top-left to the bottom-right cell so that the biggest single climb or drop on the way is as small as possible.

Problem

You are given heights, a rows × cols grid of positive integers; heights[r][c] is the height of cell (r, c). You start on (0, 0) and want to reach (rows - 1, cols - 1), moving one cell at a time up, down, left or right.

The effort of a route is the largest height difference between any two consecutive cells on it (one single climb or drop, not the total). Return the smallest effort of any route from the top-left to the bottom-right cell.

Examples

Example 1
Input: heights = [[1, 2, 2], [3, 8, 2], [5, 3, 5]]
Output: 2
Go down the left column and along the bottom: 1 → 3 → 5 → 3 → 5. The biggest step is 2. The route 1 → 2 → 2 → 2 → 5 along the top and right has a step of 3.
Example 2
Input: heights = [[1, 2, 3], [3, 8, 4], [5, 3, 5]]
Output: 1
The route 1 → 2 → 3 → 4 → 5 climbs by exactly 1 each time.
Example 3
Input: heights = [[1, 2, 1, 1, 1], [1, 2, 1, 2, 1], [1, 2, 1, 2, 1], [1, 2, 1, 2, 1], [1, 1, 1, 2, 1]]
Output: 0
Snake through the cells of height 1: down the left column, along the bottom, up the middle, along the top and down the right column. No step changes height.

Constraints

  • rows == len(heights), cols == len(heights[r])
  • 1 <= rows, cols <= 100
  • 1 <= heights[r][c] <= 10^6

Think first try before reading the solution

A route's cost is not a sum. If you walk 1 → 3 → 5 → 3 → 5, which single number describes its effort? How does that change the usual shortest-path thinking?
Two directions: (a) guess an effort e and ask whether you can cross using only steps of size ≤ e; a yes for e is also a yes for every larger e, so binary search the smallest yes. (b) Run Dijkstra with 'largest step so far' as the distance.
Dijkstra: a min-heap of (effort, r, c). Stepping to a neighbour costs max(effort, |h_neighbour - h_here|). Keep best[r][c], skip a popped entry whose effort is larger than best, and return when the corner pops.

Key idea

Picture every cell as a node and every pair of neighbouring cells as an edge weighted by their height difference. A route's effort is the largest edge on it, so you want the route whose largest edge is smallest: a bottleneck (or minimax) path, the same question as Swim in Rising Water, except that the weight sits on the edge between two cells instead of on the cell you enter.

Dijkstra works unchanged once you redefine "distance" as "largest step so far". Pop the cell with the smallest known effort; its value is final, because any other route to it must already contain a step at least that large. Then offer each neighbour max(effort, step). Because the step depends on which neighbour you arrive from, a cell can receive a cheaper offer after a dearer one, so keep a best table and ignore stale heap entries, exactly as in Network Delay Time.

The other route to the answer is binary search on the effort. "Can I cross with every step ≤ e?" is a plain BFS, and the answers are monotonic: no, no, …, no, yes, yes, …. Binary search over 0 … 10^6 finds the first yes in about 20 BFS runs.

Approaches from the obvious one to the one you want in an interview

Walk every possible route with a depth-first search, carrying the largest step taken so far, and remember the smallest value with which the corner is reached. Cells on the current route are marked so the walk never loops, and a branch is abandoned as soon as its effort is already no better than the best complete route.

It is correct, and the pruning helps on small grids, but the number of routes grows exponentially with the grid: a 100 × 100 grid has astronomically many self-avoiding paths, and the recursion alone can go 10,000 calls deep.

Dry run

  1. Example 1: the first complete route found is 1 → 2 → 2 → 2 → 5 with effort 3 (the step 2 → 5)
  2. Branches through the 8 are cut as soon as their effort reaches 3 or more
  3. 1 → 3 → 5 → 3 → 5 reaches the corner with effort 2 → best = 2

Python

class Solution:
    def minimumEffortPath(self, heights: List[List[int]]) -> int:
        rows, cols = len(heights), len(heights[0])
        best = math.inf                            # smallest effort of a complete route so far
        on_route = [[False] * cols for _ in range(rows)]

        def explore(r: int, c: int, effort: int) -> None:
            nonlocal best
            if effort >= best:                     # this route can no longer beat the best one
                return
            if (r, c) == (rows - 1, cols - 1):
                best = effort
                return
            on_route[r][c] = True
            for nr, nc in ((r + 1, c), (r - 1, c), (r, c + 1), (r, c - 1)):
                if 0 <= nr < rows and 0 <= nc < cols and not on_route[nr][nc]:
                    step = abs(heights[nr][nc] - heights[r][c])
                    explore(nr, nc, max(effort, step))   # a route costs its largest step
            on_route[r][c] = False                 # backtrack: free the cell for other routes

        explore(0, 0, 0)
        return best

Fix a limit e and ask: can I reach the corner using only steps whose height difference is at most e? That is a breadth-first search over the grid that refuses any step larger than e.

The answer is monotonic: if e works then every larger limit works too (it allows a superset of the steps). So the answers over e = 0, 1, 2, … read no, no, …, no, yes, yes, …, and binary search finds the first yes with lo = 0, hi = max height and about 20 BFS runs. Each BFS is O(rows · cols).

Dry run

  1. Example 1: lo = 0, hi = 8 (the tallest cell)
  2. mid = 4 → can cross → hi = 4. mid = 2 → can cross (1 → 3 → 5 → 3 → 5) → hi = 2
  3. mid = 1 → from 1 only the 2 is reachable, then the 2s, and the 5 is out of reach → lo = 2
  4. lo == hi == 2 → answer 2

Python

class Solution:
    def minimumEffortPath(self, heights: List[List[int]]) -> int:
        rows, cols = len(heights), len(heights[0])

        def can_cross(limit: int) -> bool:         # BFS using only steps of size <= limit
            seen = {(0, 0)}
            queue = deque([(0, 0)])
            while queue:
                r, c = queue.popleft()
                if (r, c) == (rows - 1, cols - 1):
                    return True
                for nr, nc in ((r + 1, c), (r - 1, c), (r, c + 1), (r, c - 1)):
                    if (0 <= nr < rows and 0 <= nc < cols and (nr, nc) not in seen
                            and abs(heights[nr][nc] - heights[r][c]) <= limit):
                        seen.add((nr, nc))
                        queue.append((nr, nc))
            return False

        lo, hi = 0, max(max(row) for row in heights)   # no step can exceed the tallest height
        while lo < hi:
            mid = (lo + hi) // 2
            if can_cross(mid):
                hi = mid                           # mid works: the answer is mid or smaller
            else:
                lo = mid + 1                       # mid is too small
        return lo

log₂(10⁶) ≈ 20 BFS runs, each visiting every cell once; H is the tallest height.

When to use: Easy to get right, and the 'smallest value that passes a yes/no check' pattern transfers to many problems.

Treat cells as nodes and define the distance of a route as its largest step. Dijkstra then works unchanged:

  1. best[0][0] = 0; push (0, 0, 0).
  2. Pop the smallest (effort, r, c). If effort > best[r][c], a cheaper route was found after this entry was pushed: skip it. If it is the corner, return effort.
  3. For each neighbour, new_effort = max(effort, |heights[nr][nc] - heights[r][c]|). If that beats best[nr][nc], record it and push.

Why is a popped value final? Any other route to that cell would have to pass through a cell with a larger or equal effort first, and max never lets a route get cheaper as it grows. Unlike Swim in Rising Water, a cell can receive a cheaper offer later (the step depends on the neighbour you arrive from), hence the best table and the stale check.

Each cell is pushed at most four times, so O(rows · cols · log(rows · cols)); the heap does the "guessing" that binary search did, in a single pass that stops as soon as the corner is reached.

Dry run

  1. Example 1: pop (0, (0,0)) → push (1, (0,1)) and (2, (1,0))
  2. Pop (1, (0,1)) → (0,2) at 1, (1,1) at 6. Pop (1, (0,2)) → (1,2) at 1. Pop (1, (1,2)) → (2,2) at 3
  3. Pop (2, (1,0)) → (2,0) at 2, (1,1) improves to 5. Pop (2, (2,0)) → (2,1) at 2
  4. Pop (2, (2,1)) → (2,2) improves from 3 to 2. Pop (2, (2,2)): the corner → answer 2

Python

class Solution:
    def minimumEffortPath(self, heights: List[List[int]]) -> int:
        rows, cols = len(heights), len(heights[0])
        best = [[math.inf] * cols for _ in range(rows)]   # best[r][c] = smallest known effort to reach (r, c)
        best[0][0] = 0
        heap = [(0, 0, 0)]                         # (effort so far, r, c)
        while heap:
            effort, r, c = heapq.heappop(heap)
            if effort > best[r][c]:                # stale entry: a cheaper route was found later
                continue
            if (r, c) == (rows - 1, cols - 1):
                return effort
            for nr, nc in ((r + 1, c), (r - 1, c), (r, c + 1), (r, c - 1)):
                if 0 <= nr < rows and 0 <= nc < cols:
                    step = abs(heights[nr][nc] - heights[r][c])
                    new_effort = max(effort, step)         # a route costs its largest step, not the sum
                    if new_effort < best[nr][nc]:
                        best[nr][nc] = new_effort
                        heapq.heappush(heap, (new_effort, nr, nc))
        return best[rows - 1][cols - 1]
Time O(rows · cols · log(rows · cols))Space O(rows · cols)

Each cell has at most 4 edges, so at most 4 · rows · cols pushes, each O(log) in the heap.

When to use: The standard answer. Mention binary search as the alternative with a similar bound.

Common mistakes

  • Marking a cell visited when it is pushed, as in Swim in Rising Water. There the cost of entering a cell depended only on that cell; here it depends on the neighbour you come from, so a later offer can be cheaper. Keep best[r][c] and skip stale pops instead.
  • Adding the differences up as in ordinary Dijkstra. The effort is the largest single step: combine with max.
  • Comparing step < best[nr][nc] instead of max(effort, step) < best[nr][nc]: a tiny step at the end of an expensive route does not make the route cheap.
  • Binary-search bounds that miss the answer. The effort can be as large as 10^6 - 1; start with lo = 0 and hi = max height (or 10^6), and move hi = mid on success so the loop ends on the first yes.
  • A recursive DFS for the reachability check or the brute force on a 100 × 100 grid: 10,000 nested calls exceed Python's default recursion limit. Use BFS with a deque.

Python notes

  • Heap entries (effort, r, c) compare by effort first; ties fall through to the row and column, which is harmless.
  • math.inf is a safe "no route known yet" value for the best table: every real effort is smaller.
  • max(max(row) for row in heights) gives the tallest height in one line, a valid upper bound for the binary search.
  • for nr, nc in ((r + 1, c), (r - 1, c), (r, c + 1), (r, c - 1)): lists the four neighbours; check the bounds before indexing, because negative indices wrap around silently.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Swim in Rising Water LC 778 — the weight sits on the cell you enter, so max(level, grid[nr][nc]); marking on push becomes safe there because the first offer a cell gets is already its lowest.
  • Path With Maximum Minimum Value LC 1102 — the mirror image: maximise the smallest cell on the route, with a max-heap and min instead of max.
  • Find the Safest Path in a Grid LC 2812 — first a multi-source BFS computes each cell's distance to the nearest thief, then the same binary-search-plus-BFS (or max-Dijkstra) finds the route whose smallest distance is largest.
  • Network Delay Time LC 743 — ordinary Dijkstra with + instead of max; the stale-entry check is identical.
  • Union-find instead of a heap — sort the rows·cols·2 edges by difference and join their cells one by one; the difference of the edge that first puts (0, 0) and the corner in one set is the answer, O(E log E) with no heap.
  • What if moves were also allowed diagonally? — only the neighbour list changes: eight offsets instead of four. The algorithm and the bounds stay.
