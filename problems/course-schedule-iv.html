Course Schedule IV Medium 250

LeetCode #1462 ↗
Status

For each query [u, v], say whether course u must be taken (directly or indirectly) before course v.

Problem

There are numCourses courses numbered 0 to numCourses - 1. Each pair [a, b] in prerequisites means course a must be taken before course b. Note the direction: here the first course comes first.

Prerequisites chain: if a must come before b and b before c, then a is an (indirect) prerequisite of c.

You also get queries, where queries[j] = [u, v] asks: is course u a prerequisite of course v, directly or through other courses? Return a list of booleans, one per query, in the same order.

  • The rules never form a cycle, every pair is distinct, and u != v in every query.

Examples

Example 1
Input: numCourses = 2, prerequisites = [[1, 0]], queries = [[0, 1], [1, 0]]
Output: [false, true]
Course 1 comes before course 0. So 0 is not a prerequisite of 1, but 1 is a prerequisite of 0.
Example 2
Input: numCourses = 3, prerequisites = [[1, 2], [1, 0], [2, 0]], queries = [[1, 0], [1, 2]]
Output: [true, true]
1 is a direct prerequisite of both 0 and 2.
Example 3
Input: numCourses = 5, prerequisites = [[0, 1], [1, 2], [3, 4]], queries = [[0, 2], [2, 0], [1, 4], [3, 4]]
Output: [true, false, false, true]
0 → 1 → 2 makes 0 an indirect prerequisite of 2. Nothing links the chain 0-1-2 to the pair 3-4, so [1, 4] is false.

Constraints

  • 2 <= numCourses <= 100
  • 0 <= len(prerequisites) <= numCourses * (numCourses - 1) / 2
  • prerequisites[i] = [a, b] with 0 <= a, b < numCourses and a != b; all pairs distinct
  • the prerequisite graph has no cycles
  • 1 <= len(queries) <= 10^4, queries[j] = [u, v] with u != v

Key idea

Draw each rule [a, b] as an arrow a → b. Course u is a prerequisite of v exactly when a chain of arrows leads from u to v. So every query is a reachability question on the same graph.

One search per query answers it, but up to 10^4 queries would repeat the same walks. Flip the work around: compute, once, for every course c the set prereqs[c] of every course that must come before it. Afterwards each query [u, v] is just u in prereqs[v].

The sets must be built in the right order. A course's set is complete only when the sets of all courses pointing to it are complete. Kahn's algorithm (process courses whose in-degree, the number of unprocessed incoming arrows, has dropped to 0) visits courses in exactly that order. When course c leaves the queue, push prereqs[c] ∪ {c} into the set of every course c points to.

Approaches from the obvious one to the one you want in an interview

Store the arrows as an adjacency list and answer each query [u, v] with its own depth-first search from u. If the search reaches v, u is a prerequisite of v.

Correct, and fine for a handful of queries. But every query walks the same graph again, so 10^4 queries on 100 courses can do 10^4 · (V + E) work, most of it repeated. The visited set is still needed: a DAG has no cycles, but without it a search can revisit the same course through many different paths.

Dry run

  1. Rules [[0, 1], [1, 2], [3, 4]] → nxt = {0: [1], 1: [2], 2: [], 3: [4], 4: []}
  2. Query [0, 2]: search 0 → 1 → 2, reaches 2 → True
  3. Query [2, 0]: search from 2 finds no arrow → False. Query [1, 4]: 1 → 2, no 4 → False
  4. Query [3, 4]: 3 → 4 → True. Answer [True, False, False, True]

Python

class Solution:
    def checkIfPrerequisite(self, numCourses: int, prerequisites: List[List[int]],
                            queries: List[List[int]]) -> List[bool]:
        nxt = [[] for _ in range(numCourses)]        # nxt[a] = courses that must come after a
        for before, after in prerequisites:
            nxt[before].append(after)

        def reaches(src: int, dst: int) -> bool:     # DFS along the arrows
            seen = {src}
            stack = [src]
            while stack:
                course = stack.pop()
                if course == dst:
                    return True
                for later in nxt[course]:
                    if later not in seen:
                        seen.add(later)
                        stack.append(later)
            return False

        return [reaches(u, v) for u, v in queries]
Time O(Q · (V + E))Space O(V + E)

Each of the Q queries may walk every course and every arrow.

When to use: Few queries, or a graph too large to store all prerequisite sets.

Precompute prereqs[c], the set of every course that must come before c, then answer each query by lookup.

Build the sets in topological order with Kahn's queue. A course enters the queue when its in-degree (unprocessed incoming arrows) reaches 0, which happens only after every course pointing to it has been popped and has passed its own complete set along. So when course c is popped, prereqs[c] is final, and for every arrow c → d we add c itself plus all of prereqs[c] to prereqs[d].

Each arrow triggers one set union of at most V elements: O(V · E) to build, plus O(1) per query. With 100 courses that is tiny, and 10^4 queries cost 10^4 lookups instead of 10^4 searches.

Dry run

  1. Rules [[0, 1], [0, 2], [1, 3], [2, 3]] → in-degree [0, 1, 1, 2]; queue [0]; all sets empty
  2. Pop 0: arrow 0 → 1 gives prereqs[1] = {0} (1 joins the queue); arrow 0 → 2 gives prereqs[2] = {0}
  3. Pop 1: arrow 1 → 3 gives prereqs[3] = {0, 1}; in-degree of 3 drops to 1, it waits
  4. Pop 2: arrow 2 → 3 gives prereqs[3] = {0, 1, 2}; 3 joins the queue. Pop 3: nothing to pass on
  5. Query [0, 3]: 0 in {0, 1, 2} → True. Query [1, 2]: 1 in {0} → False

Python

class Solution:
    def checkIfPrerequisite(self, numCourses: int, prerequisites: List[List[int]],
                            queries: List[List[int]]) -> List[bool]:
        nxt = [[] for _ in range(numCourses)]        # nxt[a] = courses that must come after a
        indegree = [0] * numCourses
        for before, after in prerequisites:
            nxt[before].append(after)
            indegree[after] += 1
        prereqs = [set() for _ in range(numCourses)]  # prereqs[c] = every course that must come before c
        queue = deque(c for c in range(numCourses) if indegree[c] == 0)
        while queue:
            course = queue.popleft()                 # prereqs[course] is complete now
            for later in nxt[course]:
                prereqs[later].add(course)           # the direct rule course -> later
                prereqs[later] |= prereqs[course]    # and everything that comes before course
                indegree[later] -= 1
                if indegree[later] == 0:             # every arrow into later has been processed
                    queue.append(later)
        return [u in prereqs[v] for u, v in queries]
Time O(V · E + Q)Space O(V²)

Each arrow does one set union of at most V courses; each query is one set lookup.

When to use: The expected answer: one topological pass, then every query is a constant-time lookup.

Watch it run

Keep a boolean table reach[i][j]: can i come (directly or indirectly) before j? Start with the direct rules. Then let every course take a turn as the middle of a chain: for each mid, whenever reach[i][mid] and reach[mid][j], set reach[i][j]. After all n turns the table holds every indirect prerequisite, so each query is one cell.

This is the Floyd–Warshall idea with "and/or" instead of "add/min": O(V³) = 10^6 for 100 courses, which is fine. It needs no topological order and also works on graphs with cycles, but it does V³ work even when the graph has few arrows, where the Kahn version does far less.

Dry run

  1. Rules [[0, 1], [1, 2], [3, 4]] → ✓ at (0, 1), (1, 2), (3, 4)
  2. mid = 1: 0 comes before 1 and 1 before 2 → new ✓ at (0, 2)
  3. mid = 0, 2, 3, 4: nothing new. Query [0, 2] → ✓ → True; [2, 0] → False; [1, 4] → False; [3, 4] → True

Python

class Solution:
    def checkIfPrerequisite(self, numCourses: int, prerequisites: List[List[int]],
                            queries: List[List[int]]) -> List[bool]:
        n = numCourses
        reach = [[False] * n for _ in range(n)]      # reach[i][j]: i comes before j
        for before, after in prerequisites:
            reach[before][after] = True
        for mid in range(n):                         # allow chains that pass through mid
            for i in range(n):
                if reach[i][mid]:
                    for j in range(n):
                        if reach[mid][j]:
                            reach[i][j] = True       # i -> mid -> j
        return [reach[u][v] for u, v in queries]
Time O(V³ + Q)Space O(V²)

Three nested loops over the courses, then one table lookup per query.

When to use: When you want the full reachability table and V is small, or the graph may contain cycles.

Common mistakes

  • Reading [a, b] the Course Schedule I/II way (b before a). Here [a, b] means a comes first; the arrow is a → b. Flip it and every answer flips with it.
  • Passing only the course itself along an arrow (prereqs[later].add(course)) and forgetting the union with prereqs[course]. Then 0 → 1 → 2 never records 0 as a prerequisite of 2.
  • Propagating in input order instead of topological order. If a course passes its set on before that set is complete, the courses after it never receive the late additions.
  • [set()] * n creates n references to one shared set, so every course ends up with the same prerequisites. Use [set() for _ in range(n)].
  • Dropping the visited set in the brute-force search because 'the graph has no cycles'. On a layered DAG with many diamonds the search then revisits the same courses an exponential number of times.

Python notes

  • prereqs[later] |= prereqs[course] is an in-place set union; prereqs[later].add(course) adds one element.
  • Bitmask variant: store each set as an int, mask[later] |= mask[course] | (1 << course), and answer a query with (mask[v] >> u) & 1. Python ints have unlimited width, so 100 bits is one object and one | per arrow.
  • deque(c for c in range(n) if indegree[c] == 0) seeds the queue from a generator.
  • A list comprehension [u in prereqs[v] for u, v in queries] produces the boolean answers in query order.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Course Schedule LC 207 — the arrows may form a cycle and the question is only whether an order exists; here the graph is guaranteed acyclic and the question is reachability.
  • Course Schedule II LC 210 — the same Kahn loop, but you record the order in which courses leave the queue instead of propagating sets.
  • All Ancestors of a Node in a Directed Acyclic Graph LC 2192 — exactly this precomputation; return each node's set as a sorted list instead of answering queries.
  • Find All Possible Recipes from Given Supplies LC 2115 — Kahn on a recipe graph where the initial queue is the supplies; a recipe is possible when its in-degree reaches 0.
  • Build a Matrix With Conditions LC 2392 — two independent topological sorts (rows and columns) decide where each number goes.
  • What if numCourses were 10^5 with few arrows? — the sets could hold 10^5 courses each, far too much memory. Store each set as a Python int bitmask (one union per arrow is one |), or go back to one search per query.
