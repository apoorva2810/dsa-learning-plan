Find in Mountain Array Hard 250

LeetCode #1095 ↗
Status

Find the smallest index of a target in a hidden mountain-shaped array while reading it at most 100 times.

Problem

A mountain array climbs strictly up to one highest value (the peak) and then falls strictly down. It has at least 3 values and the peak is never the first or the last one: a[0] < a[1] < … < a[p] > … > a[n-1].

The array is hidden. All you get is an object mountain_arr with two methods:

  • mountain_arr.length() returns how many values it holds;
  • mountain_arr.get(i) returns the value at index i.

Given an integer target, return the smallest index i with mountain_arr.get(i) == target, or -1 if no index holds that value.

Every call to get counts, and a solution that makes more than 100 of them is judged wrong. length() is free.

Examples

Example 1
Input: mountain_arr = [2, 5, 9, 14, 11, 6, 3], target = 6
Output: 5
6 appears once, on the way down, at index 5.
Example 2
Input: mountain_arr = [1, 4, 7, 10, 8, 4, 2], target = 4
Output: 1
4 appears on both slopes (index 1 and index 5). The smaller index is the answer.
Example 3
Input: mountain_arr = [1, 3, 6, 9, 5, 2], target = 7
Output: -1
7 lies between 6 and 9 in value, but no cell holds it.

Constraints

  • 3 <= mountain_arr.length() <= 10^4
  • 0 <= target <= 10^9
  • 0 <= mountain_arr.get(index) <= 10^9
  • at most 100 calls to get

Think first try before reading the solution

Reading every cell costs n calls of get, but only 100 are allowed, so a scan is out for big arrays. Binary search needs sorted data. Is any part of a mountain sorted?
The rising side is sorted ascending and the falling side is sorted descending. If you knew where the peak is, you could binary search each side. How do you find the peak with a binary search? Compare get(mid) with get(mid + 1): is it still climbing, or already falling?
Search the rising side first: it has the smaller indices, so a hit there is the answer. Only if it misses, search the falling side, where every comparison is mirrored (bigger values are on the left).

Key idea

Binary search needs sorted data, and a mountain is not sorted. But it is two sorted runs glued at the peak: a rising run on the left and a falling run on the right. So find the seam first, then binary search each run.

Finding the peak. Pick an index mid and look at its right neighbour. If get(mid) < get(mid + 1) you are still on the way up, so the peak is to the right of mid. Otherwise you are on the way down (or on the peak itself), so the peak is at mid or to its left. That yes/no answer flips exactly once as mid moves right, which is all a binary search needs. Each round reads two cells and halves the range.

Searching the runs. Search the rising run first. It holds the smaller indices, so a hit there is already the answer and the falling run is never read. Only if the target is missing there, search the falling run. It is sorted too, just backwards: a value that is too small means the target would be to the left, where the values are bigger.

Total reads: about 2 · log n for the peak plus log n for each run, roughly 55 for n = 10,000. A linear scan could need 10,000.

Approaches from the obvious one to the one you want in an interview

Read the cells from the left and stop at the first one that equals the target. The first match from the left is the smallest index, so no extra logic is needed, and it works for any array.

The catch is the budget: it can make as many as n get calls. On a mountain with 10,000 values that is 10,000 reads against a limit of 100, so this only passes small inputs. It ignores the one thing the problem gives you for free, the mountain shape.

Dry run

  1. mountain_arr = [2, 5, 9, 14, 11, 6, 3], target 6
  2. get(0) = 2, get(1) = 5, get(2) = 9, get(3) = 14, get(4) = 11, get(5) = 6 → match at index 5.
  3. That is 6 calls for 7 cells. For 10,000 cells the same scan can spend 10,000 calls.

Python

class MountainArray:                              # stand-in for the hidden object LeetCode gives you
    def __init__(self, values):
        self.values = values

    def get(self, index):                         # on LeetCode only 100 calls to get() are allowed
        return self.values[index]

    def length(self):
        return len(self.values)


class Solution:
    def findInMountainArray(self, target: int, mountain_arr: 'MountainArray') -> int:
        if isinstance(mountain_arr, list):        # this page passes a plain list; LeetCode passes the real object
            mountain_arr = MountainArray(mountain_arr)
        for index in range(mountain_arr.length()):
            if mountain_arr.get(index) == target:  # scanning left to right, the first hit has the smallest index
                return index
        return -1
Time O(n) get callsSpace O(1)

One read per cell in the worst case, far above the limit of 100 for large arrays.

When to use: Only to see what the call limit rules out.

Three binary searches, each cheap:

  1. Peak. While lo < hi, let mid = (lo + hi) // 2 and compare get(mid) with get(mid + 1). If the next value is bigger, the peak is to the right (lo = mid + 1); otherwise it is at mid or to its left (hi = mid). When lo == hi, that index is the peak.
  2. Rising side (indices 0..peak), searched first because it has the smaller indices. Ordinary binary search; return the index on a hit.
  3. Falling side (indices peak + 1..n - 1), only if step 2 missed. The same search with the direction mirrored.

One helper, search(lo, hi, rising), covers both slopes. In each round it reads one cell. If the value is too small and the slope rises (or too big and the slope falls), the target can only be to the right; in the other two cases, to the left. Every round halves its range.

Dry run

  1. mountain_arr = [2, 5, 9, 14, 11, 6, 3], target 6, lo = 0, hi = 6
  2. Peak: mid = 3 → 14 > 11, falling → hi = 3. mid = 1 → 5 < 9, climbing → lo = 2. mid = 2 → 9 < 14 → lo = 3. lo == hi → peak = 3.
  3. Rising side 0..3: mid = 1 → 5 is too small → lo = 2. mid = 2 → 9 is too big → hi = 1. Empty: not here.
  4. Falling side 4..6: mid = 5 → 6 == target → return 5.
  5. Total: 9 get calls here (6 for the peak, then 2 and 1 for the two slopes). On n = 10,000 the same plan stays near 55.

Python

class MountainArray:                              # stand-in for the hidden object LeetCode gives you
    def __init__(self, values):
        self.values = values

    def get(self, index):                         # on LeetCode only 100 calls to get() are allowed
        return self.values[index]

    def length(self):
        return len(self.values)


class Solution:
    def findInMountainArray(self, target: int, mountain_arr: 'MountainArray') -> int:
        if isinstance(mountain_arr, list):        # this page passes a plain list; LeetCode passes the real object
            mountain_arr = MountainArray(mountain_arr)
        n = mountain_arr.length()

        # 1) find the peak: binary search on "is the next value bigger?"
        lo, hi = 0, n - 1
        while lo < hi:
            mid = (lo + hi) // 2
            if mountain_arr.get(mid) < mountain_arr.get(mid + 1):
                lo = mid + 1                      # still climbing: the peak is to the right
            else:
                hi = mid                          # falling, or already on the peak: it is mid or to the left
        peak = lo

        # 2) binary search one slope; `rising` says which way the values run
        def search(lo, hi, rising):
            while lo <= hi:
                mid = (lo + hi) // 2
                value = mountain_arr.get(mid)     # read each cell once per round
                if value == target:
                    return mid
                too_small = value < target
                if too_small == rising:           # too small on the way up, or too big on the way down
                    lo = mid + 1                  # the target can only be to the right
                else:
                    hi = mid - 1                  # otherwise it can only be to the left
            return -1

        found = search(0, peak, True)             # the rising side first: it holds the smaller indices
        if found != -1:
            return found
        return search(peak + 1, n - 1, False)     # then the falling side
Time O(log n) get callsSpace O(1)

About 2 reads per round for the peak and 1 per round for each slope; each phase halves its range. Near 55 reads for n = 10,000.

When to use: The interview answer. Say why the rising side goes first.

Watch it run

Same plan, but let the standard library run the two slope searches. Since Python 3.10, bisect_left(a, x, key=f) applies f to each element it probes and compares the result with x. Hand it a range of indices as a and get as the key, and it binary searches the hidden array without copying it.

The rising side already increases with the index. The falling side decreases, so negate both the key and the target: -get(i) increases with i. bisect_left then returns the first position whose key is at least x, so one more get confirms that it really equals the target.

Dry run

  1. Peak search as before: [2, 5, 9, 14, 11, 6, 3] → peak = 3.
  2. Rising: bisect_left(range(0, 4), 6, key=get) → position 3 (value 14 is the first one ≥ 6); get(3) = 14 ≠ 6, so no hit.
  3. Falling: bisect_left(range(4, 7), -6, key=-get) → position 1, which is index 5; get(5) = 6 → return 5.

Python

from bisect import bisect_left


class MountainArray:                              # stand-in for the hidden object LeetCode gives you
    def __init__(self, values):
        self.values = values

    def get(self, index):                         # on LeetCode only 100 calls to get() are allowed
        return self.values[index]

    def length(self):
        return len(self.values)


class Solution:
    def findInMountainArray(self, target: int, mountain_arr: 'MountainArray') -> int:
        if isinstance(mountain_arr, list):        # this page passes a plain list; LeetCode passes the real object
            mountain_arr = MountainArray(mountain_arr)
        n = mountain_arr.length()

        lo, hi = 0, n - 1                         # the peak, exactly as before
        while lo < hi:
            mid = (lo + hi) // 2
            if mountain_arr.get(mid) < mountain_arr.get(mid + 1):
                lo = mid + 1
            else:
                hi = mid
        peak = lo

        rising = range(0, peak + 1)               # bisect over the indices; get() is the key
        pos = bisect_left(rising, target, key=mountain_arr.get)
        if pos < len(rising) and mountain_arr.get(rising[pos]) == target:
            return rising[pos]

        falling = range(peak + 1, n)              # negate values and target so the keys increase with the index
        pos = bisect_left(falling, -target, key=lambda index: -mountain_arr.get(index))
        if pos < len(falling) and mountain_arr.get(falling[pos]) == target:
            return falling[pos]
        return -1
Time O(log n) get callsSpace O(1)

The same three phases; each bisect probes about log n cells and adds one confirming read.

When to use: Short and idiomatic in Python 3.10+. Be ready to write the loop by hand, since many interviewers want to see it.

Common mistakes

  • Running the rising-side rule on the falling side. There, a value that is too small means 'go left', not 'go right', because the values grow towards the peak, which is on the left.
  • Returning the first match from the falling run, or searching both runs and picking whichever answers first. [1, 4, 7, 10, 8, 4, 2] holds a 4 at index 1 and at index 5, and the answer is 1. Search the rising run first and stop at its hit.
  • Peak search with hi = mid - 1, or comparing with get(mid - 1). With while lo < hi compare mid with mid + 1 and set hi = mid (the peak may be mid itself). mid + 1 is always a valid index because mid < hi.
  • Burning the call budget: reading the same cell twice in a round (for example calling get(mid) again in every if). The peak search already costs two reads per round; store each read in a variable.
  • Finding the peak with max or a loop: that reads all n cells, and the limit is 100.

Python notes

  • LeetCode hands you a MountainArray object that you must not look inside. This page cannot, so every solution starts with a tiny stand-in class and one line that wraps a plain list in it. Leave both out when you submit on LeetCode.
  • (lo + hi) // 2 cannot overflow in Python. In Java or C++ write lo + (hi - lo) / 2.
  • Since Python 3.10, bisect_left(a, x, key=f) applies f to each probed element. Passing a range of indices as a searches over positions and calls get only for the probes, so nothing is copied.
  • The helper search is a closure: it reads target and mountain_arr from the enclosing method, which keeps its own parameter list short.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Peak Index in a Mountain Array LC 852 — only the first half of this solution: find the peak with the mid versus mid + 1 comparison.
  • Find Peak Element LC 162 — the array may have several peaks and no mountain shape; the same neighbour comparison still lands on one of them, because you always walk towards the larger neighbour.
  • Search in Rotated Sorted Array LC 33 — also two sorted runs with a seam, but the seam is a drop, handled by asking which half is sorted instead of comparing neighbours.
  • Find Minimum in Rotated Sorted Array LC 153 — finds the seam alone: compare nums[mid] with nums[hi] and keep the side that still contains the drop.
  • Valid Mountain Array LC 941 — check the shape instead of searching it: walk up, walk down, and make sure the two walks used the whole array.
  • Flat spots allowed — if neighbours may be equal, get(mid) == get(mid + 1) no longer says on which side the peak is, and the worst case becomes linear.
