Design HashSet Easy 250

LeetCode #705 ↗
Status

Build your own hash set of integers (add, remove, contains) without using set or dict.

Problem

Design your own hash set for integer keys, without using Python's built-in set or dict.

Implement the class MyHashSet:

  • MyHashSet() creates an empty set.
  • add(key) inserts key. Adding a key that is already in the set changes nothing.
  • remove(key) deletes key. Removing a key that is not in the set changes nothing.
  • contains(key) returns True if key is in the set and False otherwise.

Every key is an integer from 0 to 10^6.

Examples

Example 1
Input: ["MyHashSet","add","add","add","contains","contains","remove","contains","add","contains"] [[],[7],[2],[12],[12],[3],[2],[2],[7],[7]]
Output: [null, null, null, null, true, false, null, false, null, true]
With 5 buckets, 7, 2 and 12 all leave remainder 2, so they share one bucket (a collision). Removing 2 leaves 7 and 12 behind, and adding 7 a second time changes nothing.
Example 2
Input: ["MyHashSet","add","add","remove","contains"] [[],[4],[4],[4],[4]]
Output: [null, null, null, null, false]
Adding 4 twice still stores it once, so a single remove is enough to delete it.
Example 3
Input: ["MyHashSet","remove","contains","add","contains"] [[],[9],[9],[9],[9]]
Output: [null, null, false, null, true]
Removing a key that was never added does nothing and does not raise an error.

Constraints

  • 0 <= key <= 10^6
  • at most 10^4 calls in total to add, remove and contains

Think first try before reading the solution

A plain list of keys works, but every operation has to scan it. Could the key itself tell you where to look?
Keys go up to 10^6, so you could keep one True/False slot for every possible key. What does that cost in memory, and what would you do if keys went up to 10^9?
Use a much smaller table and let key % size pick the slot, so several keys share a slot. Make each slot a short list (a bucket) and search only that one list.

Key idea

A set has to answer "is this key in here?" quickly. Scanning a list is O(n) because the key says nothing about where it would be stored. A hash set fixes that by letting the key decide its own address: a hash function turns a key into a position, and only that one position needs to be searched.

Here the hash function is the remainder key % B for a fixed number of buckets B. Two different keys can land in the same bucket, which is called a collision (with B = 5, the keys 7 and 12 both give 2). So each bucket holds a small list, the chain, of all the keys that hashed to it. To add, remove or test a key, jump to its bucket and scan only that chain. If the keys spread out evenly, each chain holds about n / B keys, so with a sensible B every operation is O(1) on average. A prime B (like 1009) spreads patterned keys, such as all multiples of 10, better than a round number like 1000, because the pattern shares no factor with B.

Approaches from the obvious one to the one you want in an interview

Keep every key in a single Python list. add appends it unless it is already there, contains uses in, and remove uses list.remove when the key is present. It is correct and has no limit on the key range, but nothing in the key says where it is stored, so every operation scans the whole list: O(n) per call.

Python

class MyHashSet:
    def __init__(self):
        self.keys = []

    def add(self, key: int) -> None:
        if key not in self.keys:         # O(n): scans the whole list
            self.keys.append(key)

    def remove(self, key: int) -> None:
        if key in self.keys:             # O(n) scan, then O(n) to close the gap
            self.keys.remove(key)

    def contains(self, key: int) -> bool:
        return key in self.keys          # O(n)
Time O(n) per callSpace O(n)

n is the number of keys stored; every call scans them.

When to use: Only as a baseline: it shows what the other two approaches improve.

Because keys are at most 10^6, give every possible key its own slot in a list of 10^6 + 1 booleans. The key is the index: add sets present[key] = True, remove sets it to False, and contains reads it. Every call is a single list access, so O(1) in the worst case.

The cost is memory: the list always has a million slots, however few keys you store, and the idea falls apart if the keys can go up to 10^9. Hashing keeps the O(1) speed while shrinking the table to a size you choose.

Python

class MyHashSet:
    def __init__(self):
        self.present = [False] * (10 ** 6 + 1)   # one slot for every possible key 0..10^6

    def add(self, key: int) -> None:
        self.present[key] = True

    def remove(self, key: int) -> None:
        self.present[key] = False

    def contains(self, key: int) -> bool:
        return self.present[key]
Time O(1) per callSpace O(R), R = size of the key range

Each call is one list access; the table has R = 10^6 + 1 slots no matter how many keys are stored.

When to use: When the key range is small and known. It is the simplest way to make a set fast.

Make a small array of B buckets, each an empty list. The hash function key % B says which bucket a key belongs to, and a bucket holds every key that landed there (its chain).

  • add(key): go to the bucket and append the key unless it is already in that list.
  • remove(key): go to the bucket and remove the key if it is in that list.
  • contains(key): go to the bucket and test whether the key is in that list.

Two keys with the same remainder collide, and that is fine: they simply share a chain. With a prime B like 1009 and at most 10^4 calls, a chain holds about 10 keys, so each call scans a handful of keys instead of the whole set. The average cost is O(1) (more precisely O(n / B)); the worst case is O(n) if every key hashes to the same bucket.

Dry run

  1. 5 buckets for the example: add(7) → 7 % 5 = 2 → bucket 2 = [7]
  2. add(2) → bucket 2 = [7, 2] (collision); add(12) → bucket 2 = [7, 2, 12]
  3. contains(12) → scan only bucket 2 → True; contains(3) → bucket 3 is empty → False
  4. remove(2) → bucket 2 = [7, 12]; contains(2) → False

Python

class MyHashSet:
    def __init__(self):
        self.num_buckets = 1009                          # a prime number spreads keys evenly
        self.buckets = [[] for _ in range(self.num_buckets)]

    def _index(self, key: int) -> int:
        return key % self.num_buckets                    # the hash function: which bucket?

    def add(self, key: int) -> None:
        bucket = self.buckets[self._index(key)]
        if key not in bucket:                            # a set stores each key once
            bucket.append(key)

    def remove(self, key: int) -> None:
        bucket = self.buckets[self._index(key)]
        if key in bucket:                                # removing a missing key must not raise
            bucket.remove(key)

    def contains(self, key: int) -> bool:
        return key in self.buckets[self._index(key)]
Time O(1) average per callSpace O(B + n)

Each call scans one chain of about n / B keys. B buckets plus n stored keys.

When to use: The answer to give: it is how real hash tables work. Mention resizing for a growing set.

Common mistakes

  • Appending in add without checking first. A key stored twice survives one remove, so contains keeps returning True after the key was deleted. Test key not in bucket before appending.
  • list.remove(key) raises ValueError when the key is missing, but the problem says removing an absent key does nothing. Test key in bucket first.
  • Making the buckets with [[]] * B. That repeats one list object B times, so all buckets are the same list and every key lands in the same chain. Use [[] for _ in range(B)].
  • Indexing with the key itself in a small table: buckets[key] raises IndexError as soon as key reaches the table size. Always take key % size first.
  • Choosing a bucket count that shares a factor with the keys, such as 1000 buckets for keys that are multiples of 10: only a tenth of the buckets are ever used and the chains grow ten times longer. A prime count avoids this.

Python notes

  • Python's own set and dict are hash tables built on this idea (they use open addressing rather than chains). Interviewers ask you to build one to see that you know how they work.
  • key % size always gives a number from 0 to size - 1 for a positive size in Python, even for negative keys. In some other languages the remainder of a negative number is negative.
  • [[] for _ in range(B)] creates B separate empty lists. [[]] * B creates one list and B references to it.
  • key in bucket is a linear scan of that one list. That is fine because the chain is short; it is the table, not the chain, that makes the lookup fast.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Design HashMap LC 706 — store (key, value) pairs in the chains instead of bare keys; put must overwrite the value of a key that is already there.
  • LRU Cache LC 146 — a hash map plus a doubly linked list: the map finds a key in O(1) and the list keeps the usage order.
  • Insert Delete GetRandom O(1) LC 380 — a set that can also return a random element: keep the values in a list plus a map of positions, and delete by swapping the victim with the last element.
  • Contains Duplicate LC 217 — the most common use of a set: remember what you have seen and test each new value in O(1).
  • What if the key range is huge or unknown? — count the keys and resize: when n / B passes a limit such as 0.75, allocate twice as many buckets and re-insert every key. Doubling keeps the average cost of add at O(1).
  • Open addressing instead of chaining — no chains: a colliding key goes into the next free slot of one flat array. Lookups probe slot after slot, and removal needs a 'deleted' marker so that probing does not stop early.
