Find Median from Data Stream Hard

LeetCode #295 ↗
Status

Numbers arrive one at a time; at any moment, report the median of everything seen so far.

Problem

The median of a list of numbers is its middle value once the list is sorted. With an even count there are two middle values and the median is their average: the median of [2, 3, 4] is 3, and of [2, 3] it is 2.5.

Implement the class MedianFinder:

  • MedianFinder() starts with no numbers.
  • addNum(num) adds the integer num to the collection.
  • findMedian() returns the median of all numbers added so far, as a float. Answers within 10⁻⁵ of the true median are accepted.

findMedian is only called after at least one addNum.

Examples

Example 1
Input: ["MedianFinder","addNum","addNum","findMedian","addNum","findMedian"] [[],[1],[2],[],[3],[]]
Output: [null, null, null, 1.5, null, 2.0]
After 1 and 2 the median is (1 + 2) / 2 = 1.5. After adding 3 the sorted numbers are [1, 2, 3], so the median is 2.
Example 2
Input: ["MedianFinder","addNum","findMedian","addNum","findMedian","addNum","findMedian"] [[],[5],[],[15],[],[1],[]]
Output: [null, null, 5.0, null, 10.0, null, 5.0]
[5] → 5; [5, 15] → (5 + 15) / 2 = 10; [1, 5, 15] → 5.

Constraints

  • -10^5 <= num <= 10^5
  • findMedian is called only when at least one number has been added
  • at most 5 * 10^4 calls to addNum and findMedian in total

Think first try before reading the solution

Sorting on every findMedian is O(n log n) per call. Which values do you actually need to know to report the middle?
Cut the sorted numbers into a lower half and an upper half. The median depends only on the largest value of the lower half and the smallest value of the upper half; the order inside each half never matters.
Keep the lower half in a max-heap and the upper half in a min-heap, the lower half the same size or one bigger. Send each new number through the lower half (push it, then move the lower half's largest across), then fix the sizes.

Key idea

Picture the numbers sorted and cut in the middle. The median only needs the values right next to the cut: the largest of the lower half and the smallest of the upper half. Nothing else has to be in order.

Two heaps keep exactly those two values on top:

  • small, the lower half, as a max-heap. Python only has min-heaps, so it stores -x and -small[0] is its largest value.
  • large, the upper half, as a min-heap, so large[0] is its smallest value.

Two rules hold after every addNum: (1) every value in small is ≤ every value in large, and (2) small has the same size as large or exactly one more. Then the median is -small[0] when the count is odd, and (-small[0] + large[0]) / 2 when it is even.

To add a number without comparing anything by hand, push it into small and then move small's largest value into large. Whatever arrived, the value that crosses is the right one, so rule 1 holds. If that left large bigger than small, move large's smallest back, which restores rule 2. That is at most five pushes and pops, O(log n) per addNum, and findMedian only reads the tops: O(1).

Approaches from the obvious one to the one you want in an interview

Append every number to a list. On findMedian, sort a copy and read the middle (or average the two middle values).

addNum is O(1), but each findMedian re-sorts all n numbers: O(n log n) per query. With tens of thousands of interleaved calls, almost all of that sorting repeats work done for the previous query.

Dry run

  1. add 1, add 2 → [1, 2]; findMedian sorts → [1, 2] → (1 + 2) / 2 = 1.5
  2. add 3 → [1, 2, 3]; findMedian sorts again → middle value 2

Python

class MedianFinder:
    def __init__(self):
        self.nums = []

    def addNum(self, num: int) -> None:
        self.nums.append(num)

    def findMedian(self) -> float:
        s = sorted(self.nums)                    # O(n log n) on every call
        mid = len(s) // 2
        if len(s) % 2:                           # odd count: one middle value
            return float(s[mid])
        return (s[mid - 1] + s[mid]) / 2         # even count: average the two middle values
Time O(1) add, O(n log n) findMedianSpace O(n)

n = numbers added so far; every query sorts all of them again.

When to use: Only when queries are rare compared with additions.

Keep the list sorted at all times: bisect.insort finds the insert position by binary search and inserts there. Then findMedian just reads the middle, O(1).

The binary search is O(log n), but inserting into a Python list shifts every later element, so addNum is O(n). That is a big improvement over sorting per query, and fine for moderate n, but the shifting is still linear work.

Dry run

  1. add 5 → [5]; add 15 → [5, 15]; add 1 → [1, 5, 15] (1 is inserted at the front, shifting both)
  2. findMedian → the middle index 1 → 5

Python

class MedianFinder:
    def __init__(self):
        self.nums = []                           # always sorted

    def addNum(self, num: int) -> None:
        bisect.insort(self.nums, num)            # O(log n) search + O(n) shift

    def findMedian(self) -> float:
        mid = len(self.nums) // 2
        if len(self.nums) % 2:
            return float(self.nums[mid])
        return (self.nums[mid - 1] + self.nums[mid]) / 2
Time O(n) add, O(1) findMedianSpace O(n)

The insert shifts up to n elements (fast memmove, but still linear).

When to use: When you also need other ranks, or n stays in the low thousands.

Split the numbers at the median:

  • small: the lower half as a max-heap (store -x);
  • large: the upper half as a min-heap.

Two invariants (rules that hold after every call): every value in small ≤ every value in large, and len(small) is len(large) or len(large) + 1.

addNum(num):

  1. push num into small;
  2. pop small's largest value and push it into large. This keeps the halves in order without any comparison of our own: if num was too big for the lower half, it is the value that moves up;
  3. if large is now bigger than small, move large's smallest value back.

findMedian(): odd count → -small[0]; even count → (-small[0] + large[0]) / 2.

Dry run

  1. add 5: small [5] → move 5 to large → large bigger → move 5 back → small [5], large []
  2. add 15: small [15, 5] → move 15 to large → small [5], large [15] → equal sizes, done
  3. add 1: small [5, 1] → move 5 up → small [1], large [5, 15] → move 5 back → small [5, 1], large [15]
  4. findMedian: 3 numbers, odd → top of small → 5.0
  5. add 3: small [5, 3, 1] → move 5 up → small [3, 1], large [5, 15] → equal sizes → findMedian = (3 + 5) / 2 = 4.0

Python

class MedianFinder:
    def __init__(self):
        self.small = []                          # lower half, max-heap: stores -x
        self.large = []                          # upper half, min-heap

    def addNum(self, num: int) -> None:
        # pass num through the lower half: its largest value moves up,
        # so every value in small stays <= every value in large
        heapq.heappush(self.small, -num)
        heapq.heappush(self.large, -heapq.heappop(self.small))
        if len(self.large) > len(self.small):    # keep small the same size or one bigger
            heapq.heappush(self.small, -heapq.heappop(self.large))

    def findMedian(self) -> float:
        if len(self.small) > len(self.large):    # odd count: the middle value is small's top
            return float(-self.small[0])
        return (-self.small[0] + self.large[0]) / 2
Time O(log n) add, O(1) findMedianSpace O(n)

At most five pushes/pops per add on heaps of about n/2 items; the median reads two tops.

When to use: The standard answer for a running median.

Common mistakes

  • Sign mix-ups on the max-heap: push -num, read -small[0], and negate exactly once when moving a value between the heaps (heappush(large, -heappop(small))). A missing minus puts the halves out of order without any error.
  • Pushing the new number straight into whichever heap 'looks right' and only balancing the sizes. Rebalancing can then carry a value across in the wrong direction, so small ends up holding something bigger than large's top. Passing every number through small first avoids the comparison entirely.
  • Allowing either heap to be the bigger one: findMedian then has to work out which side holds the extra number. Fix the rule (here small holds it) and restore it after every add.
  • Integer division: (a + b) // 2 gives 1 for 1 and 2 (and rounds negative sums down). Use / 2.
  • Reading large[0] after a single addNum: large is still empty. Decide odd/even from the sizes before touching the second top.

Python notes

  • -self.small[0] reads the largest value of the lower half; self.large[0] the smallest value of the upper half.
  • heapq.heappushpop(self.small, -num) pushes and pops in a single pass over the heap, so the first two lines of addNum can become heapq.heappush(self.large, -heapq.heappushpop(self.small, -num)).
  • / always returns a float in Python 3; float(...) makes the odd case a float as well.
  • bisect.insort keeps a plain list sorted at O(n) per insert; sortedcontainers.SortedList (not in the standard library) does the same in about O(log n).

Follow-up questions

What an interviewer might ask next, and what changes.

  • What if every number is in the range [0, 100]? — keep 101 counters: addNum is O(1) and findMedian walks at most 101 buckets to find the middle count.
  • What if 99% of the numbers are in [0, 100]? — use the 101 buckets plus a counter (or small sorted list) for outliers below 0 and above 100; the median almost always lands inside the buckets.
  • Sliding Window Median LC 480 — numbers also leave the window, and a heap cannot delete from the middle: keep the two heaps with lazy deletion (remember which values left and discard them only when they reach a top), or use a sorted list.
  • IPO LC 502 — two heaps with different jobs: projects you cannot afford yet (min-heap by capital) feed a max-heap of affordable ones by profit.
  • Median of Two Sorted Arrays LC 4 — the data is fixed and already sorted: binary-search where the cut goes instead of maintaining heaps.
  • Kth Largest Element in a Stream LC 703 — track one fixed rank from the top instead of the middle: a single min-heap of size k.
