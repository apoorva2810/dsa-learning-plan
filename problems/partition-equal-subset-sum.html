Partition Equal Subset Sum Medium

LeetCode #416 ↗
Status

Decide whether a list of positive numbers can be split into two groups with the same sum.

Problem

Given a list nums of positive integers, return True if the numbers can be divided into two groups with equal sums (every number goes into exactly one group), and False otherwise.

Examples

Example 1
Input: nums = [1, 5, 11, 5]
Output: true
[1, 5, 5] and [11] both sum to 11.
Example 2
Input: nums = [1, 2, 3, 5]
Output: false
The total is 11, which is odd.
Example 3
Input: nums = [1, 2, 5]
Output: false
The total 8 is even, but no group of these numbers sums to 4.

Constraints

  • 1 <= len(nums) <= 200
  • 1 <= nums[i] <= 100

Think first try before reading the solution

If the two groups have equal sums, what must each sum be? What does that say about an odd total?
The question is really: is there a subset that adds up to total / 2? The rest of the numbers then form the other half automatically.
Process the numbers one at a time and keep the set of all subset sums you can make so far (never above the target). Each new number x adds s + x for every old sum s.

Key idea

Two equal groups means each group sums to total / 2. So an odd total is impossible, and otherwise the problem is subset sum: can some subset make exactly target = total // 2? (If one group makes the target, the leftover numbers make the other half.)

Trying all 2^n subsets is hopeless for 200 numbers, but the sums are small: never more than target (at most 10,000). So track which sums are reachable instead of which subsets produce them. Start with {0} (the empty subset). For each number x, every sum you could make before is still possible, and so is that sum plus x. After the last number, check whether target is reachable.

As a table this is dp[s] = "some subset of the numbers seen so far sums to s". Each number updates the table once, and the update must run from high s to low s so that the same number is never used twice in one pass.

Approaches from the obvious one to the one you want in an interview

After the parity check, ask can(i, remaining): can a subset of nums[i:] add up to remaining? Either nums[i] goes into the subset (can(i + 1, remaining - nums[i])) or it does not (can(i + 1, remaining)). Stop with True at remaining == 0 and with False when the numbers run out or remaining goes negative.

Each number doubles the number of paths, so the worst case is 2^n calls, far too many for 200 numbers.

Dry run

  1. nums = [1, 5, 11, 5]: total 22, target 11
  2. take 1 → need 10 from [5, 11, 5]: take 5 → need 5: skip 11, take 5 → 0 → True

Python

class Solution:
    def canPartition(self, nums: List[int]) -> bool:
        total = sum(nums)
        if total % 2:                          # an odd total cannot split into equal integers
            return False
        target = total // 2

        def can(i: int, remaining: int) -> bool:
            """Can a subset of nums[i:] add up to exactly `remaining`?"""
            if remaining == 0:
                return True
            if i == len(nums) or remaining < 0:
                return False
            return (can(i + 1, remaining - nums[i])    # put nums[i] in the subset
                    or can(i + 1, remaining))          # leave it out

        return can(0, target)
Time O(2ⁿ)Space O(n)

Two branches per number; the recursion is n deep.

When to use: Only to show the take/skip structure.

The same recursion, cached. The state is the pair (i, remaining), with i from 0 to n and remaining from 0 to target, so at most n × target calls ever do work: about 200 × 10,000 = 2 million in the worst case. That is O(n · target) time, the same as the tables below, but it also stores up to that many results.

Python

class Solution:
    def canPartition(self, nums: List[int]) -> bool:
        total = sum(nums)
        if total % 2:
            return False

        @cache                                 # one result per (i, remaining) pair
        def can(i: int, remaining: int) -> bool:
            if remaining == 0:
                return True
            if i == len(nums) or remaining < 0:
                return False
            return can(i + 1, remaining - nums[i]) or can(i + 1, remaining)

        return can(0, total // 2)
Time O(n · target)Space O(n · target)

n × target states, O(1) work each; the cache holds them all.

When to use: When the recursion is how you first see the problem; the 1-D table uses far less memory.

Forget which subsets exist; keep only which sums they make. Start with {0}. For each number x, the new reachable sums are the old ones plus every old + x (ignore anything above target, which can never help). Return True as soon as target appears.

The set never holds more than target + 1 values, so each number costs O(target) and the whole thing is O(n · target). It is easy to reason about: after processing k numbers, the set is exactly the subset sums of those k numbers.

Dry run

  1. nums = [1, 5, 11, 5], target 11, reachable = {0}
  2. 1 → {0, 1}
  3. 5 → {0, 1, 5, 6}
  4. 11 → adds 11 (0 + 11) → target reached → True

Python

class Solution:
    def canPartition(self, nums: List[int]) -> bool:
        total = sum(nums)
        if total % 2:
            return False
        target = total // 2
        reachable = {0}                        # subset sums of the numbers processed so far
        for x in nums:
            # built from the OLD set, so x is used at most once
            reachable |= {s + x for s in reachable if s + x <= target}
            if target in reachable:
                return True
        return False
Time O(n · target)Space O(target)

At most target + 1 sums in the set; each number touches each of them once.

When to use: The most readable version; it only stores sums that actually occur.

Watch it run

The same idea in a list: dp[s] is True when some subset of the numbers so far sums to s, with dp[0] = True. For each number x, set dp[s] = True whenever dp[s - x] is True.

The loop over s must go from target down to x. Then dp[s - x] (a smaller index) has not been touched yet in this pass, so it still describes subsets without x, and each number is used at most once. Going upward would let one number be counted again and again, which is the unbounded (Coin Change) version of the problem.

Dry run

  1. nums = [1, 5, 11, 5], target 11: dp = [T, F, F, ..., F]
  2. x = 1: dp[1] = dp[0] → T
  3. x = 5: dp[6] = dp[1] → T, dp[5] = dp[0] → T
  4. x = 11: dp[11] = dp[0] → T → return True

Python

class Solution:
    def canPartition(self, nums: List[int]) -> bool:
        total = sum(nums)
        if total % 2:
            return False
        target = total // 2
        dp = [False] * (target + 1)            # dp[s] = some subset of the numbers so far sums to s
        dp[0] = True                           # the empty subset
        for x in nums:
            for s in range(target, x - 1, -1):     # high to low: x is used at most once
                if dp[s - x]:
                    dp[s] = True
            if dp[target]:
                return True
        return False
Time O(n · target)Space O(target)

n passes over at most target + 1 cells; one boolean list.

When to use: The standard 0/1 knapsack answer; explain why the inner loop runs backwards.

Common mistakes

  • Skipping the odd-total check and using total // 2: for [1, 2, 3, 5] (total 11) the target becomes 5, the subset [5] is found, and the answer is wrongly True.
  • Updating the boolean array left to right for each number: dp[s - x] may already include x, so x is used again. On [1, 2, 5] the 1 alone would mark 1, 2, 3 and 4 reachable and return True.
  • Adding to a set while iterating over it (for s in reachable: reachable.add(s + x)) raises RuntimeError; build the new sums from the old set first.
  • Greedy (largest numbers first while they fit): [2, 2, 2, 2, 3, 3] needs 7, greedy takes 3 + 3 = 6 and gets stuck, but 3 + 2 + 2 = 7 works.

Python notes

  • reachable |= {s + x for s in reachable if s + x <= target} evaluates the comprehension from the old set before the update, so x is used at most once per pass.
  • range(target, x - 1, -1) walks from target down to x, which is the right-to-left order the 0/1 table needs.
  • A top-down version uses @cache on (i, remaining) and recurses up to len(nums) = 200 deep, below Python's default recursion limit of 1000. It stores up to n × target results, more memory than the 1-D table.
  • Python integers are arbitrary-precision, so bits = 1; for x in nums: bits |= bits << x is a fast, legal bitset.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Target Sum LC 494 — put + or - before each number to reach a target: the plus-group must sum to (total + target) / 2, so it becomes counting subset sums.
  • Partition to K Equal Sum Subsets LC 698 — k groups instead of two: reachable sums no longer suffice; use backtracking with pruning or a bitmask DP over used elements.
  • Last Stone Weight II LC 1049 — minimise the difference between the two groups: compute the reachable sums and pick the one closest to total / 2.
  • Coin Change II LC 518 — each coin may be used many times, so the inner loop runs left to right; here each number is used at most once, so it runs right to left.
  • Ones and Zeroes LC 474 — the same 0/1 choice per item with two capacities (zeros and ones): a 2-D table updated from high to low.
  • Bitset trick — store the reachable sums as bits of one Python integer: bits |= bits << x does a whole pass at once, then test (bits >> target) & 1.
