Course Schedule II Medium

LeetCode #210 ↗
Status

Return one order in which all courses can be taken, or an empty list if no order exists.

Problem

There are numCourses courses numbered 0 to numCourses - 1. Each pair [a, b] in prerequisites means course b must be finished before course a.

Return a list containing every course exactly once, in an order that respects every rule. If several orders work, return any of them. If no order works, return an empty list [].

  • Every rule appears at most once, and no course is its own prerequisite.

Examples

Example 1
Input: numCourses = 2, prerequisites = [[1, 0]]
Output: [0, 1]
Example 2
Input: numCourses = 4, prerequisites = [[1, 0], [2, 0], [3, 1], [3, 2]]
Output: [0, 1, 2, 3]
[0, 2, 1, 3] is just as correct: 1 and 2 only need 0, and 3 needs both of them.
Example 3
Input: numCourses = 2, prerequisites = [[1, 0], [0, 1]]
Output: []
The two rules contradict each other, so no order exists.

Constraints

  • 1 <= numCourses <= 2000
  • 0 <= len(prerequisites) <= numCourses * (numCourses - 1)
  • prerequisites[i] = [a, b] with 0 <= a, b < numCourses and a != b
  • all pairs are distinct

Key idea

Draw the rules as arrows b → a ("b before a"). An answer is a topological order: a list of the nodes in which every arrow points from an earlier entry to a later one. Such a list exists exactly when the graph has no cycle.

Kahn's algorithm builds the list directly. Count each course's in-degree (how many prerequisites it still waits for). Courses with in-degree 0 go in a queue. Each time you take a course out, append it to the answer and lower the in-degree of every course it unlocks; any that reach 0 join the queue. A course is appended only after all of its prerequisites were appended, so the answer is valid. If the queue empties early, the courses left over sit on a cycle or wait behind one, and the answer is [].

Several answers are often valid, because courses that become free at the same time can be taken in any order.

Approaches from the obvious one to the one you want in an interview

Build the order the way a person would with pen and paper: scan all courses, place the first unplaced course whose prerequisites are all placed, and start the scan again. If a full scan finds nothing to place while courses remain, they wait on each other in a cycle.

Each scan rereads every course and its rule list, and you need one scan per course placed: O(V · (V + E)). The waste is that after placing a course, only the courses it unlocks could have become ready, yet the scan rechecks everything.

Dry run

  1. Rules [[1, 0], [2, 0], [3, 1], [3, 2]] → needs = {1: [0], 2: [0], 3: [1, 2]}
  2. Scan: 0 needs nothing → place 0. Rescan: 1 needs 0 (placed) → place 1. Rescan: 2 → place 2. Rescan: 3 → place 3
  3. Answer [0, 1, 2, 3]. Four scans for four courses; each scan can read all the rules.

Python

class Solution:
    def findOrder(self, numCourses: int, prerequisites: List[List[int]]) -> List[int]:
        needs = [[] for _ in range(numCourses)]     # needs[a] = prerequisites of a
        for course, pre in prerequisites:
            needs[course].append(pre)
        placed = [False] * numCourses
        order = []
        while len(order) < numCourses:
            for course in range(numCourses):        # look for any course that is ready
                if not placed[course] and all(placed[p] for p in needs[course]):
                    placed[course] = True
                    order.append(course)
                    break
            else:                                   # the scan found nothing: the rest form or wait on a cycle
                return []
        return order
Time O(V · (V + E))Space O(V + E)

V scans (one per course placed); each scan may read every course and every rule.

When to use: Never in an interview; it shows which repeated work the queue removes.

Course Schedule's Kahn loop with one extra line: append each course to order as it leaves the queue.

  1. Build unlocks[b] (courses that need b) and indegree[a] (rules a still waits for).
  2. Queue every course with in-degree 0.
  3. Pop a course, append it, and lower the in-degree of everything it unlocks; push those that reach 0.
  4. If order has all numCourses courses, return it; otherwise a cycle blocked the rest, so return [].

A course is only queued after its last prerequisite was popped, so every course lands after all of its prerequisites. Each course and each rule is handled once: O(V + E).

Dry run

  1. Rules [[1, 0], [2, 0], [3, 1], [3, 2]] → in-degree {0: 0, 1: 1, 2: 1, 3: 2}; queue [0]
  2. Pop 0 → order [0]; 1 and 2 drop to 0 → queue [1, 2]
  3. Pop 1 → order [0, 1]; 3 drops to 1. Pop 2 → order [0, 1, 2]; 3 drops to 0 → queue [3]
  4. Pop 3 → order [0, 1, 2, 3]: four courses = numCourses → return it

Python

class Solution:
    def findOrder(self, numCourses: int, prerequisites: List[List[int]]) -> List[int]:
        unlocks = [[] for _ in range(numCourses)]   # unlocks[b] = courses that need b
        indegree = [0] * numCourses
        for course, pre in prerequisites:
            unlocks[pre].append(course)
            indegree[course] += 1
        queue = deque(c for c in range(numCourses) if indegree[c] == 0)
        order = []
        while queue:
            pre = queue.popleft()
            order.append(pre)                       # all of pre's prerequisites are already in `order`
            for course in unlocks[pre]:
                indegree[course] -= 1
                if indegree[course] == 0:
                    queue.append(course)
        return order if len(order) == numCourses else []
Time O(V + E)Space O(V + E)

Each course is queued and appended once; each rule decrements one counter once.

When to use: The standard answer: iterative, easy to explain, and the cycle check is a single length comparison.

Watch it run

Think recursively: to take course a, first take every prerequisite of a, then take a. A depth-first search along the "needs" direction (from a course to its prerequisites) does exactly that, and appending each course when its search finishes produces a valid order directly.

Cycle detection uses the three colours from Course Schedule: grey means "placement in progress". If a course needs a grey course, that course is (indirectly) waiting for the current one, which is a cycle. Black means already placed, so it can be skipped. Same O(V + E); the trade-off is recursion depth on long chains.

Dry run

  1. take(0): no prerequisites → order [0]
  2. take(1): needs 0 (black, placed) → order [0, 1]. take(2) → order [0, 1, 2]
  3. take(3): needs 1 and 2, both placed → order [0, 1, 2, 3]
  4. With [[1, 0], [0, 1]]: take(0) → needs 1 → take(1) → needs 0, which is grey → cycle → []

Python

class Solution:
    def findOrder(self, numCourses: int, prerequisites: List[List[int]]) -> List[int]:
        needs = [[] for _ in range(numCourses)]     # needs[a] = prerequisites of a
        for course, pre in prerequisites:
            needs[course].append(pre)
        WHITE, GREY, BLACK = 0, 1, 2
        colour = [WHITE] * numCourses
        order = []

        def take(course: int) -> bool:              # False if a cycle is found
            colour[course] = GREY                   # placement in progress
            for pre in needs[course]:
                if colour[pre] == GREY:             # pre waits for course: a cycle
                    return False
                if colour[pre] == WHITE and not take(pre):
                    return False
            colour[course] = BLACK
            order.append(course)                    # every prerequisite is already in `order`
            return True

        for course in range(numCourses):
            if colour[course] == WHITE and not take(course):
                return []
        return order
Time O(V + E)Space O(V + E)

Each course is entered once and each rule followed once; the call stack can reach V frames.

When to use: When recursion reads more naturally to you, or you already have a DFS for cycle detection.

Common mistakes

  • Returning a partial order when a cycle exists. Check len(order) == numCourses and return [] otherwise; a partial list is a wrong answer, not a 'best effort'.
  • Drawing the arrow the wrong way. [a, b] means b comes first. Course Schedule I gives the same yes/no answer with reversed arrows, but here the order would come out backwards.
  • In the DFS version, appending a course when you enter it instead of when it finishes. A course is only safe to place once everything it needs is already placed.
  • Forgetting courses with no rules at all. They have in-degree 0, so they must be in the initial queue, or they never appear in the answer.

Python notes

  • deque(c for c in range(n) if indegree[c] == 0) seeds the queue from a generator in one line.
  • [[] for _ in range(n)] gives n independent lists; [[]] * n would share one list n times.
  • In the DFS version the answer is filled in finishing order. Following the arrows forward, that order must be reversed (order[::-1]); walking them backwards (course → its prerequisites), as the DFS approach does, it is already correct.

Follow-up questions

What an interviewer might ask next, and what changes.

  • Course Schedule LC 207 — only a yes/no answer: the same loop, but count the courses instead of storing them.
  • Alien Dictionary LC 269 — the rules are hidden in a sorted word list. Derive the arrows from adjacent words, then run this exact algorithm on letters.
  • Parallel Courses LC 1136 — minimum number of semesters: process the queue one whole level per semester and count the levels.
  • Minimum Height Trees LC 310 — the same peeling idea on an undirected tree: repeatedly remove leaves (degree 1) until one or two centre nodes remain.
  • Sort Items by Groups Respecting Dependencies LC 1203 — two levels of ordering: topologically sort the groups, then the items inside each group.
  • What if the answer must be the smallest order alphabetically? — replace the queue with a min-heap so the smallest free course is always taken next: O((V + E) log V).
